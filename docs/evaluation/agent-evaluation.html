Agent Evaluation

Measure what the agent accomplished, how reliably it accomplished it, and what the entire system spent getting there.

Foundations → Graders → Models → Agents → Training → Worked comparison.

1. The experimental subject is a system, not a checkpoint

An agent's actions depend on its weights, prompt, context management, tool schemas, memory, orchestration, runtime and environment. “The same model” can produce different outcomes with a different retry policy or context truncation rule. Name the experimental subject explicitly:

Agent system = model + harness + tools + environment + budget. Version the evaluator too: a grader change can alter the score without any behavior change.
QuestionComparisonClaim it supports
Did training improve the policy?Base vs candidate weights; same harness, task set, tools, grader and budget.A checkpoint difference under this fixed setup. Training-seed replication is needed for a broader claim about the training recipe.

If both weights and harness change, a four-cell comparison helps: A/old, B/old, A/new, B/new. The difference between the two harness gains reveals interaction; do not assume that a harness gain measured on A transfers unchanged to B. See Agent Architectures for what these harnesses contain.

2. Grade outcomes; use trajectories to explain them

For a repository task, did the patch satisfy independent tests without breaking existing behavior? For a booking task, did the final database state match the authorized request? A convincing final message or plausible tool-call sequence is not proof of completion.

End state is necessary but not always sufficient. An agent could reach the right state after an unauthorized action, data disclosure, or costly irreversible operation. Enforce constraints throughout the trajectory and report their violations separately. A benchmark's hidden answer must remain outside the agent's accessible state.

Audit the grader with known good, bad and malformed attempts before optimizing against it. Protect grading inputs from instructions embedded in agent output. Separate judge failures from negative judgments. The grader audit and reward-design guide explain the two sides.

3. “Can succeed eventually” is not “succeeds consistently”

For a fixed task with success probability \(p\), suppose trials are independent, use the same protocol, and reset all state. Two different questions then have opposite curves:

\[ \Pr(\text{at least one success in }k)=1-(1-p)^k,\qquad \Pr(\text{all }k\text{ trials succeed})=p^k. \]

pass@k asks whether at least one of \(k\) attempts succeeds. pass^k, the reliability metric introduced in τ-bench, asks whether all \(k\) succeed. At \(p=0.6\), four independent attempts give 97.4% at-least-one success but only 13.0% all-four success. Neither number means “the agent is 97% reliable.”

p = 60%, k = 4: at least one 97.4%; all trials 13.0%; fixed four-attempt cost 4× one attempt. At 60% per-trial success, four attempts give 97.4% at-least-one success and 13.0% all-four success.

From finite samples to a benchmark average

For task \(i\), sample \(n_i\) attempts and observe \(c_i\) successes. For \(n_i\ge k\), the fraction of \(k\)-subsets containing a success and the fraction containing only successes are

\[ \widehat{\mathrm{pass@}k}_i=1-\frac{\binom{n_i-c_i}{k}}{\binom{n_i}{k}}, \qquad \widehat{\mathrm{pass}^{k}}_i=\frac{\binom{c_i}{k}}{\binom{n_i}{k}}. \]

Use \(\binom{m}{k}=0\) when \(m<k\), and average task-level estimates with declared task weights. Under i.i.d. trials for each task these estimate the corresponding probabilities. Do not substitute the overall average success rate into the powers: generally \(\mathbb E[p_i^k]\ne(\mathbb E[p_i])^k\). If attempts share state, adapt to previous failures, or have correlated outages, explain that protocol rather than asserting independence.

Finding a correct answer is not the same as selecting it. pass@k can use an oracle grader after all attempts. A deployed best-of-k system needs a selector that may choose incorrectly. Measure the selected output and charge generation, verification and selection costs; do not expose hidden evaluation answers to that selector.

4. Freeze execution and account for every scheduled attempt

Pin the model identity, harness commit, prompt/template, tool definitions, environment image and data snapshot, grader version, sampling settings, seeds where supported, and token/turn/time limits. A seed is a reproducibility aid, not a promise of deterministic remote APIs or parallel GPU execution.

Reset files, databases, memory and caches that carry task information between episodes. If persistent memory is part of the evaluated product, define the session sequence and isolation boundary instead of pretending each episode starts fresh. For interactive tasks, version the user simulator and evaluate whether its behavior represents the intended users.

Report successes / valid graded attempts, successes / all scheduled attempts, and invalid attempts / all scheduled attempts. The all-scheduled metric measures observed operational success; treating invalids as non-success is not a claim that the model would have failed those tasks. Differential outages can still confound the model comparison. A high invalid rate is grounds to stop and repair the experiment, not evidence for a weaker model.

Log every execution retry and its cost. Predeclare how retries map to the scheduled task/trial slots; never keep only the best retry or selectively rerun candidate failures. Interleave or randomize A/B execution order to reduce time-dependent confounding. Pair by task, not by arbitrary row order.

5. Separate learning gains, compute gains and release evidence

Evaluation-Driven Training explains checkpoint selection bias, retention constraints and the final confirmation gate.

Start agent training with a baseline under a frozen evaluation protocol. Use development tasks to diagnose failures and choose checkpoints, then compare the selected candidate on untouched tasks. Report new wins and regressions, not only the net average. Repeats belong within task-level uncertainty calculations; multiple runs of one task do not provide coverage of multiple distinct tasks.

Compare weights at the same inference budget to isolate one useful learning claim. Also report quality at several budgets if the system can trade compute for outcomes. Better task success achieved by four times the rollout budget may be valuable, but it answers a different question from better weights at fixed cost.

Use failure slices to choose the next intervention: training data for a capability gap, harness changes for context loss, tool fixes for schema errors, and grader repair for false positives. Preserve the final test boundary while making those changes.

Offline evidence is a gate, not a production guarantee. Historical replay cannot fully recreate how users respond to changed actions. Shadow runs reveal some integration issues but not the impact of executed actions. Controlled online experiments need guardrails, consent/privacy controls, and rollback. See The Production Learning Loop.
