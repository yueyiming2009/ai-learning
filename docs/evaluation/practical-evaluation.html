A Paired Evaluation, End to End

Forty tasks, two attempts per system, one reproducible analysis—and a candidate that is not ready to pass the declared quality gate.

Evaluation Foundations → Agent Evaluation → Worked comparison.
Evidence boundary: this is a synthetic analysis exercise, not a model benchmark. The Python below creates explicit teaching records and analyzes them without network access, external packages or a model. It does not execute agents, establish a real training gain, validate a sandbox, or measure safety. Replace the fixture with audited real records only after the execution controls in the last section are in place.

1. Freeze the comparison and its decision rule

Imagine a baseline A and one candidate B selected on development tasks. The final comparison has 40 equally weighted held-out tasks, with two independently reset scheduled attempts per task and system. The model weights are the intended difference; harness, tasks, graders, decoding settings and limits stay fixed.

Protocol itemTeaching choice—not a universal recommendation
Identityfixture-v1; systems A and B; fixed-harness-v1; fixed-grader-v1.
BudgetSame 2,000-token cap per attempt; no retries. An evaluation-invalid attempt stays in its scheduled slot.
Primary outcomeMean task-level success fraction over all scheduled attempts. Invalid attempts count as observed non-success here, with their rate also reported.
UncertaintyResample paired tasks with replacement; 4,000 percentile-bootstrap replicates, random seed 17, two-sided 95% interval.
Offline quality gateLower interval bound at least +5 percentage points; B's mean tokens at most 15% above A; invalid rate at most 5% for both systems.
Not covered by this gateSafety, policy compliance, tool cost, latency and production impact. Separate evidence is required before deployment.

These thresholds are declared before reading outcomes in the imagined experiment. The fixture is constructed to teach the analysis, not to justify these thresholds. In real work, choose them from task value, risk and evaluation power on development data.

2. Preserve attempts, including the inconvenient ones

Each record has a task ID, system ID, repeat number, protocol ID, status and token count. Status is one of pass, fail or invalid. The invalid cases here represent a grader outage after generation, so token usage is still charged. They are not invalid model answers; malformed model output would be a valid failure under this protocol.

The table compactly specifies every synthetic outcome. A pair such as “pass, fail” means two scheduled attempts on one task, not a pass@2 aggregate.

Before calculating any averages, reconcile the records with an independently defined manifest. Reject duplicate keys, missing tasks, missing repeats, unknown statuses and mismatched protocols. Pairing two files by row order is not a substitute for matching keys.

3. Run the analysis using only Python's standard library

Save the following as paired_eval.py and run python3 paired_eval.py (Python 3.9+). It creates no files and performs no network calls. The bootstrap resamples task-level paired differences, keeping the observed repeats together rather than treating 80 attempts as 80 independent tasks.

import random
from statistics import mean

PROTOCOL = "fixture-v1"
TASKS = tuple(f"task-{i:02d}" for i in range(40))
SYSTEMS = ("A", "B")
REPEATS = (0, 1)


def fixture():
    specs = [
        (14, ("pass", "pass"), ("pass", "pass")),
        (8, ("fail", "fail"), ("fail", "fail")),
        (6, ("fail", "fail"), ("pass", "pass")),
        (2, ("pass", "pass"), ("fail", "fail")),
        (4, ("pass", "fail"), ("pass", "pass")),
        (2, ("pass", "pass"), ("pass", "fail")),
        (2, ("fail", "fail"), ("invalid", "fail")),
        (2, ("invalid", "pass"), ("pass", "pass")),
    ]
    records = []
    task_number = 0
    for count, a_statuses, b_statuses in specs:
        for _ in range(count):
            task_id = f"task-{task_number:02d}"
            task_number += 1
            for system, statuses in zip(SYSTEMS, (a_statuses, b_statuses)):
                for repeat, status in enumerate(statuses):
                    records.append({
                        "task_id": task_id,
                        "system": system,
                        "repeat": repeat,
                        "protocol": PROTOCOL,
                        "status": status,
                        "tokens": 1000 if system == "A" else 1100,
                    })
    return records


def validate(records):
    expected = {(t, s, r) for t in TASKS for s in SYSTEMS for r in REPEATS}
    keyed = {}
    for row in records:
        key = (row["task_id"], row["system"], row["repeat"])
        if key in keyed:
            raise ValueError(f"duplicate attempt: {key}")
        if row["protocol"] != PROTOCOL:
            raise ValueError(f"protocol mismatch: {key}")
        if row["status"] not in {"pass", "fail", "invalid"}:
            raise ValueError(f"unknown status: {key}")
        if type(row["tokens"]) is not int or not 0 <= row["tokens"] <= 2000:
            raise ValueError(f"invalid token accounting: {key}")
        keyed[key] = row
    if set(keyed) != expected:
        raise ValueError("records do not match the scheduled task/trial manifest")
    return keyed


def summarize(records, system):
    rows = [r for r in records if r["system"] == system]
    successes = sum(r["status"] == "pass" for r in rows)
    invalids = sum(r["status"] == "invalid" for r in rows)
    valid = len(rows) - invalids
    return {
        "successes": successes,
        "scheduled": len(rows),
        "all_rate": successes / len(rows),
        "valid_rate": successes / valid if valid else None,
        "invalid_rate": invalids / len(rows),
        "tokens": mean(r["tokens"] for r in rows),
    }


def quantile(sorted_values, p):
    position = (len(sorted_values) - 1) * p
    left = int(position)
    right = min(left + 1, len(sorted_values) - 1)
    return sorted_values[left] + (position - left) * (
        sorted_values[right] - sorted_values[left]
    )


records = fixture()
keyed = validate(records)
deltas = []
for task in TASKS:
    rates = {}
    for system in SYSTEMS:
        rates[system] = mean(
            keyed[(task, system, r)]["status"] == "pass" for r in REPEATS
        )
    deltas.append(rates["B"] - rates["A"])

rng = random.Random(17)
bootstrap = sorted(
    mean(rng.choices(deltas, k=len(TASKS))) for _ in range(4000)
)
lo, hi = quantile(bootstrap, 0.025), quantile(bootstrap, 0.975)
summary = {s: summarize(records, s) for s in SYSTEMS}
for system, s in summary.items():
    valid_text = "N/A" if s["valid_rate"] is None else f'{s["valid_rate"]:.1%}'
    print(
        f'{system}: {s["successes"]}/{s["scheduled"]} scheduled successes; '
        f'all={s["all_rate"]:.1%}, valid={valid_text}, '
        f'invalid={s["invalid_rate"]:.1%}, mean tokens={s["tokens"]:.0f}'
    )
print(f'Paired change: {100 * mean(deltas):+.1f} pp')
print(f'Task bootstrap 95% interval: [{100 * lo:+.1f}, {100 * hi:+.1f}] pp')
print(
    "Task means improved/regressed/unchanged:",
    sum(d > 0 for d in deltas),
    sum(d < 0 for d in deltas),
    sum(d == 0 for d in deltas),
)
token_ratio = summary["B"]["tokens"] / summary["A"]["tokens"]
quality_gate = (
    lo >= 0.05
    and token_ratio <= 1.15
    and max(s["invalid_rate"] for s in summary.values()) <= 0.05
)
print("Offline quality gate:", "PASS" if quality_gate else "KEEP IN DEVELOPMENT")

Expected output

A: 42/80 scheduled successes; all=52.5%, valid=53.8%, invalid=2.5%, mean tokens=1000
B: 54/80 scheduled successes; all=67.5%, valid=69.2%, invalid=2.5%, mean tokens=1100
Paired change: +15.0 pp
Task bootstrap 95% interval: [+1.2, +30.0] pp
Task means improved/regressed/unchanged: 12 4 24
Offline quality gate: KEEP IN DEVELOPMENT

The bootstrap interval is conditional on this observed fixture and its task-sampling assumptions; it is not a guarantee of exact 95% coverage. Forty independent tasks with only two observed repeats are a small study. Related tasks require larger clusters; uncertainty over fresh retries or training seeds may require additional design and replication. More bootstrap replicates reduce numerical simulation noise, not the underlying lack of task coverage.

4. Read the report as a decision, not a victory announcement

B has a 15-percentage-point observed advantage, at 10% more generated tokens on average. The lower interval bound is only about +1.2 points, below the declared +5-point minimum. The offline quality gate therefore fails even though the point estimate is positive and the interval does not include zero.

The 12 improved and 4 regressed task means include partial changes across two attempts. They are not 12 new perfect solves and 4 entirely lost tasks. Also, equal invalid counts do not prove outages were harmless: they occurred on different task/system pairs. Inspect invalid reasons and, if needed, repair and rerun under a predeclared symmetric policy rather than dropping those rows.

Correct conclusion: this synthetic candidate does not clear the example's practical-effect threshold. Do not lower the threshold after seeing the result or keep adding tasks until it passes. Plan additional evidence with an appropriate sampling/stopping design; if the report guides new training, treat these tasks as development feedback and preserve another final holdout.

A passing offline quality gate would still not authorize deployment. This fixture has no evidence about authorization failures, privacy, real-world tool costs, latency tails, rare catastrophic outcomes or user impact.

5. Replace the fixture, not the experimental controls

BoundaryRequired real-run artifact
Protocol and provenanceImmutable manifest with task/split hashes, model identity, harness commit, tool schemas, image/data snapshots, grader version, decoding and resource limits. IDs in this tutorial are labels, not real artifact hashes.
