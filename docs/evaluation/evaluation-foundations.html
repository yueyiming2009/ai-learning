Evaluation Foundations

A score is an observation under a protocol. Build the protocol that makes the observation useful evidence.

Learning path: Foundations → Agent Evaluation → A Paired Evaluation, End to End. Browse the Evaluation domain.

1. Write the claim before choosing the benchmark

“Model B is better” leaves out the work, the user population, the resource budget, and the acceptable failures. A testable claim is narrower: “B resolves more of our held-out repository tasks than A, with the same tools and token limit, without increasing unauthorized actions.”

Let \(x\sim D\) be a task drawn from the intended distribution, \(S\) the evaluated system, \(u\) its execution randomness, and \(g\) the grader. An evaluation estimates

\[ \mu(S;D,g)=\mathbb E_{x\sim D,u}\big[g(x,S(x;u))\big]. \]

Changing \(D\), the budget inside \(S\), or \(g\) changes what the number means. Even an exact estimate of this quantity need not measure actual user benefit if the task sample or grader is a poor proxy. Statistical precision cannot repair the wrong question.

Contract fieldDecide before collecting results
Population and unitWhich tasks, users, languages, repositories, or time periods? Is the independent unit a question, a repository, or a user?
System and budgetWeights/API version, prompt, tokenizer/template, harness, tools, decoding, maximum tokens, turns and time.
Outcome and graderWhat counts as success? Who or what verifies it? How are partial credit, refusals and invalid runs handled?
DecisionPrimary metric, minimum useful improvement, safety/reliability guardrails, uncertainty method and stopping rule.

Do not compress everything into a composite score first. Task accuracy, calibration, safety, robustness, latency and cost can move in opposite directions. A critical policy violation should not disappear inside an average of otherwise successful tasks.

2. “Held out” is a boundary, not a filename

PartitionAllowed useWhat breaks the boundary
TrainingWeight updates, demonstrations, preference pairs, reward optimization and synthetic-data generation.Including final-test questions, solutions, grader secrets, or near-duplicate variants.
Development / validationChoose checkpoints, prompts, curricula, graders, harnesses and hyperparameters.Calling a repeatedly tuned development score an independent final result.
Locked final testEstimate the frozen candidate's performance under the predeclared protocol.Inspect failures, change the system, and report a rerun as if no feedback had occurred.

Split at the level of the generalization claim. Different task IDs from the same repository do not establish repository generalization. Paraphrases of one question, tasks sharing a template, and episodes from one user may cross a random row split. Group related examples before splitting; use a time split when future behavior is the claim.

Deduplicate exact and near-duplicate content across sources and record provenance. Keep test answers out of retrieval indexes, examples, agent memory and training-time tools. A private test reduces some leakage risks; it does not prove a base model never saw related material. When pretraining data are undisclosed, state that contamination is unverified.

If a test informs the next iteration, it is now development feedback. Preserve another untouched test for the next independent claim, or disclose reuse. Repeatedly querying a “hidden” leaderboard can also tune a system to that leaderboard.

3. Evaluate the measurement instrument

An executable checker can be incomplete, a human rubric ambiguous, and an LLM judge biased. Before trusting any of them, assemble an adjudicated audit set with known correct, incorrect, malformed and adversarial outputs. Include the failure modes your candidate is likely to produce.

GraderUseful evidenceRequired audit
Exact match / executable testsA defined answer or behavior passed specific checks.Alternative valid outputs, missing requirements, flaky tests, false passes, and attempts to modify or bypass checks.
Human rubricJudgments against explicit criteria.Blind model identities, train raters, measure disagreement by criterion, and adjudicate ambiguous cases.
LLM judgeA scalable approximation to the chosen rubric or human preference.Calibrate against human labels; swap answer order; test verbosity, self-preference and injected instructions. Freeze judge version, prompt and decoding.

Report false acceptance and false rejection separately; overall agreement can hide a grader that accepts nearly everything in an easy dataset. Break errors down by task slice and re-audit after a distribution shift. A stronger judge is not automatically an unbiased judge.

A training reward and an evaluation grader can share a mechanism, but must not be treated as independent evidence merely because the files differ. Use held-out tasks and checks, inspect rewarded behaviors, and add independent human or executable audits where the same blind spot could be exploited. See Verifiers & Reward Design for the optimization side of this problem.

4. Compare paired outcomes, not two leaderboard decimals

Run A and B on the same \(n\) tasks under the same protocol. For binary success, write \(a_i,b_i\in\{0,1\}\) and \(d_i=b_i-a_i\). A newly solved task contributes \(+1\), a regression contributes \(-1\), and agreement contributes zero:

\[ \widehat\Delta=\frac{1}{n}\sum_i d_i =\frac{n_{\text{gain}}-n_{\text{regress}}}{n},\qquad \widehat{\mathrm{SE}}(\widehat\Delta) =\sqrt{\frac{\sum_i(d_i-\widehat\Delta)^2}{n(n-1)}}. \]

This estimates uncertainty over independently sampled tasks. Do not decide significance by whether separate confidence intervals for A and B overlap; directly estimate the paired difference. For a finite fixed benchmark, the mean is an exact summary of the observed runs; interpreting an interval requires a task-sampling and/or run-randomness model.

For intuition, suppose 18% of tasks improve and 10% regress: the observed gain is 8 percentage points. With \(q=0.28\) the fraction of discordant pairs, the standard error simplifies to \(\sqrt{(q-\widehat\Delta^2)/(n-1)}\). The plot keeps those proportions fixed while changing the number of tasks.

200 tasks: +8.0 pp; approximate 95% interval +0.7 to +15.3 pp. At 50 tasks the approximate interval includes zero; at 200 tasks it is about +0.7 to +15.3 percentage points.

These are illustrative pointwise normal-approximation intervals, not a confidence sequence or a license to stop sampling when the lower curve crosses zero. No real model results are plotted.

The approximation \(\widehat\Delta\pm1.96\,\widehat{\mathrm{SE}}\) is a teaching tool: small samples, rare discordant pairs and boundary cases need more care. An all-identical observed sample does not prove zero population uncertainty. For real comparisons, a paired task bootstrap is one option; for sparse binary discordances, an exact paired test can assess a no-difference hypothesis, but it does not establish a useful effect size.

Repeated attempts are not additional independent tasks. Average repeats within each task, then resample whole paired task records. If tasks share a repository or user, consider that larger cluster as the resampling unit. This still does not capture variation across training seeds, unseen domains, grader errors or future environment drift. The worked comparison implements the paired task bootstrap.

5. Put evaluation inside the training loop, without leaking the test

StageDevelopment evidenceDecision and caveat
Pretraining / continued trainingHeld-out loss by source, language and domain; downstream capability probes.Choose mixtures and checkpoints. Lower token loss is not automatically better instruction following; perplexity comparisons need tokenizer-aware accounting.
SFT / distillationInstruction adherence, task correctness, refusal behavior and retained base capabilities.Choose data and stopping points. Imitating reference wording is not the same as solving the task.
RL / agentic trainingTraining reward plus held-out task outcomes, exploit audits, cost and regression slices.Adjust curriculum and select checkpoints. Reward rising while independent outcomes stagnate is a diagnostic, not a success.
Release / deploymentFrozen final-test report under the intended serving stack; controlled online outcomes and guardrails.Recheck after quantization, prompt, tool or harness changes. Offline improvement does not establish causal product impact.

Predeclare the primary comparison and minimum useful gain. Treat broad slice exploration as diagnosis, not dozens of independent confirmatory discoveries. Selecting the best of many checkpoints introduces selection bias; use development data for that search and a final holdout for the chosen candidate. Repeated interim looks need a planned stopping rule or an appropriate sequential procedure.

Training reward tells us what we optimized. Independent evaluation tests whether that optimization produced the behavior we wanted. Neither a small p-value nor a high benchmark score replaces a deployment decision with explicit safety, reliability and cost requirements.
