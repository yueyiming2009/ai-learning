Evaluating Language Models

Choose a capability, make the protocol comparable, and keep a benchmark score narrower than the claim it supports.

Foundations → Graders → Models → Agents → Training → Worked comparison.

1. Predicting held-out text and being useful are different tests

Held-out negative log-likelihood measures how much probability a model assigns to reference continuations. For \(N\) scored tokens, the average loss and perplexity are

\[ L=-\frac{1}{N}\sum_{t=1}^{N}\log p_\theta(x_t\mid x_{<t}),\qquad \mathrm{PPL}=\exp(L). \]

This is useful for comparing pretraining checkpoints on a frozen text distribution. It does not directly test whether a sampled answer is correct, an instruction is followed, or a refusal is appropriate. Teacher-forced scoring supplies the reference prefix; free generation instead conditions on the model's own previous outputs.

Compare loss by source and language, not just over one changing aggregate. Pin the text, tokenizer, scored positions, context/window policy and document boundaries. Token-level perplexities from different tokenizers are not directly comparable. For identical text with \(B\) bytes, a common reporting unit is

\[ \mathrm{bits/byte}=\frac{-\sum_t\log p_\theta(x_t\mid x_{<t})}{B\log 2}. \]

Byte normalization fixes the reporting unit, not differences in available context, preprocessing or scored content. See Perplexity for the derivation and sliding-window details. Keep downstream capability checks alongside loss.

2. Build a capability matrix, not a benchmark shopping list

Start from the intended workload and include counterexamples to the claim you want to make. Public suites provide useful reference points; private, provenance-tracked application tasks test relevance. Neither replaces contamination controls or an independent final holdout.

CapabilityWhat to measureWhat a narrow score misses
Knowledge and reasoningAnswer correctness across difficulty, domain and language; robust parsing, appropriate uncertainty and fixed reasoning budgets.Multiple-choice recognition is not open-ended solving. A correct answer does not establish a faithful reasoning trace; a plausible trace does not establish correctness.
CodeIndependent functional tests, edge cases and regression checks. HumanEval is a function-completion example.Passing a finite test suite is not complete correctness. Repository-level tasks with execution tools become agent-system evaluations.
Instruction followingCheck individual constraints and whole-prompt success. IFEval illustrates objectively verifiable instructions.Matching a word count or JSON schema does not establish truthfulness or overall usefulness. Distinguish mechanical constraints from semantic rubric criteria.
Long contextVary context length, evidence position, distractors, number of relevant spans and required synthesis.A large advertised window or a single-needle retrieval win does not establish robust use of that context. Lost in the Middle motivates position-sensitive testing.
Multimodal understandingVisual perception plus reasoning over charts, documents and other relevant media; preserve image resolution and preprocessing. MMMU is one image-rich reference suite.Text-only shortcuts can hide whether the image mattered. Use text-only ablations; one image benchmark does not establish audio/video competence.
Factuality and grounded answersClaim-level correctness, support in supplied evidence, citation validity and answer completeness.A supported quotation can omit the answer; a correct claim may be unsupported by the supplied sources. Retrieval quality and generation faithfulness need separate diagnosis.
Safety and robustnessBoundary violations, benign-request over-refusal, distribution shifts, paraphrases and adversarial conditions relevant to the application.Average helpfulness does not certify safety; refusing everything is not good performance either. Report severity and slices rather than offsetting harmful outcomes with easy wins.

For incomplete or subjective outcomes, use criterion-level human or audited model judges. Evaluate the grader's errors, not just its ability to produce a score. Keep benchmark release/version and scoring variant attached to every result.

3. Freeze how the model is asked and how the answer is scored

Protocol choiceWhy it can change the result
Likelihood vs generationRanking answer strings by conditional log-probability is not the same experiment as generating an answer or a choice letter. Length normalization changes the ranking rule; state whether it is used.
Prompt and examplesSystem instructions, chat template, few-shot count, exemplar selection/order and answer format affect behavior. Never select examples using test answers.
Sampling and reasoningTemperature, top-p, stop sequences, reasoning effort and maximum output affect success and cost. Greedy one-attempt accuracy, repeated-attempt average, majority vote and pass@k are different metrics.
Parsing and gradingAnswer extraction, whitespace normalization, unit handling and ambiguous answers need a frozen rule. Do not silently re-prompt malformed outputs or revise the parser only for one model.
Runtime and interfaceRecord weights/API version, quantization, tokenizer, supported template and tool access. A moving API alias is not an immutable model identity.
Failures and repeatsKeep truncations, refusals, outages and missing attempts visible under a declared policy. Repeats improve estimation of stochastic behavior, not coverage of new tasks.

Fair does not always mean byte-identical prompts. Different packaged models may require different supported chat templates. For a product comparison, use appropriate interfaces under a declared common task and resource contract; label this a packaged-system comparison. For a checkpoint ablation, keep the interface fixed to isolate the weight change.

Report matched-budget comparisons and quality–cost curves where feasible. Equal token caps do not guarantee equal compute across tokenizers, architectures, hidden reasoning policies or tool usage. Record actual usage and which resource was matched: attempts, tokens, latency, monetary cost or measured compute. An oracle pass@k result does not measure a deployed selector's accuracy; the distinction is derived in Agent Evaluation.

4. An aggregate score silently chooses a task distribution

Suppose two synthetic models have the following exact success probabilities under one fixed protocol. These are teaching assumptions, not estimated benchmark results.

If the routine-task weight is \(w\), the aggregate scores are \(S_A(w)=0.9w+0.4(1-w)\) and \(S_B(w)=0.8w+0.6(1-w)\). Their difference is \(S_A-S_B=0.3w-0.2\), so the ranking flips at \(w=2/3\).

A micro-average weights each example equally, so larger datasets dominate. A macro-average weights categories equally, which answers a different question. Neither is automatically the deployment distribution. Report per-slice results and the weighting rule; do not average loss, accuracy and preference scores as if their scales were interchangeable.

5. Accuracy does not tell you when to trust the answer

For a declared binary event such as “this answer is correct,” let \(q_i\) be the reported probability and \(y_i\) the outcome. The binary Brier score is \(\frac{1}{n}\sum_i(q_i-y_i)^2\). Calibration asks whether answers assigned similar probabilities succeed at about that rate; discrimination asks whether confidence ranks correct answers above incorrect ones. These are different properties.

Use reliability diagrams with bin counts and uncertainty, and report a proper scoring rule such as Brier score or log loss when meaningful probabilities are available. A single expected calibration error depends on the binning and can hide poor slices. A generated “90% confident” string or the probability of one answer token is not automatically a calibrated probability of semantic correctness.

If the system may abstain, report both coverage and error among answered questions, plus how abstentions are handled downstream. Higher accuracy after refusing the hardest half of the workload is not the same service. Select confidence thresholds on development data.

6. Make a model result interpretable and reusable

A useful report identifies the candidate, task version/split, prompt and runtime contract, scorer, budget, all-attempt accounting, primary comparison, paired uncertainty and important slices. Include what is unavailable: undisclosed pretraining data, unknown contamination, inaccessible reasoning-token counts or a vendor result that has not been reproduced.

Do not merge unlike evidence into a controlled comparison. A vendor-reported score, an independently rerun score, and a reproduction under modified settings are three evidence types. Preserve their provenance and protocol differences. The MAI-Thinking-1 case study illustrates reporting those limits without inventing missing experimental controls.

Use Evaluation-Driven Training to turn a development report into a checkpoint or data decision. Use the worked comparison for explicit paired accounting, and keep the final holdout out of that selection loop.
