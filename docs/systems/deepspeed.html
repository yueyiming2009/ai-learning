DeepSpeed — Memory-First Training at Any Scale

Where Megatron asks "how do I split the computation," DeepSpeed asks "how do I stop replicating state" — and pushes that question further than anyone else: shard it (ZeRO), move it to CPU (Offload), page it to disk (Infinity), compress the collectives it costs (ZeRO++). All while wrapping your existing model unchanged, which is how it became the scaling engine inside Hugging Face's training stack.

One of three framework deep dives — the others are Megatron-LM → and TorchTitan →; the cross-framework comparison and decision guide live on Training Frameworks →. The ZeRO math itself — bytes per parameter per rung, the 1.5×-communication-for-1/N-state trade — is derived on Data Parallelism & the ZeRO ladder →.

1 · The organizing idea — memory is the product

DeepSpeed is Microsoft Research's training library, and its founding artifact is the 2020 ZeRO paper (Rajbhandari et al., "Zero Redundancy Optimizer"). The observation: in mixed-precision Adam training, every data-parallel replica carries ≈ 16 bytes per parameter — 2 (bf16 weights) + 2 (bf16 grads) + 12 (fp32 master weights + Adam moments) — and under classic DDP all of it is replicated N times. The model states, not the activations, are what cap trainable model size; and the replication is pure redundancy that can be sharded away, paying only communication.

Everything DeepSpeed ships follows from taking that observation to its limit. Where Megatron restructures the computation and demands the model be rewritten in its blocks, DeepSpeed restructures only the state, which is why it can wrap any nn.Module untouched — the property its whole adoption story (§5) rests on.

2 · The ZeRO ladder

The rungs, with per-GPU model-state bytes for \(\Psi\) parameters at DP degree \(N\) (derivations on the ZeRO page):

RungWhat it shardsBytes / param / GPU
DDP Nothing — full replication \(16\)
ZeRO-1 Optimizer state (fp32 master + moments) over the DP group \(4 + 12/N\)
ZeRO-2 + gradients \(2 + 14/N\)
ZeRO-3 + parameters — nothing replicated; params all-gather just-in-time per layer and are freed after use \(16/N\)

Stages 1–2 are nearly free: the communication volume matches DDP's (a reduce-scatter plus an all-gather in place of one all-reduce). Stage 3 is the consequential step — it adds a parameter all-gather in forward and backward (the 1.5× communication trade) and changes the execution model: parameters materialize layer by layer, which DeepSpeed implements with Python hooks that intercept module access (a mechanism choice with consequences, §7). Stage 3 is the same math FSDP implements — the engineering comparison is in §7's box.

3 · Off the GPU — ZeRO-Offload and ZeRO-Infinity

Sharding divides state by \(N\); offload removes it from HBM entirely. This is the territory DeepSpeed owns outright — no other major stack goes as far down the memory hierarchy:

ZeRO-Offload — the optimizer moves to the host

Optimizer state lives in CPU RAM, and the update step runs on the CPU: gradients stream host-ward during backward, a hand-vectorized CPU Adam (AVX-optimized, an order of magnitude faster than a naive loop) applies the update, and fresh parameters stream back. The design keeps the GPU↔CPU traffic at 4 bytes per parameter each way per step and overlaps it with compute — enabling a ~10B-parameter fine-tune on a single GPU. The tax is real: every step crosses PCIe (~64 GB/s on Gen5 vs. multiple TB/s of HBM — see GPU generations for how Grace-coherent systems change this arithmetic), and the CPU update sits on the critical path if compute per step is small.

ZeRO-Infinity — the NVMe tier

Parameters, gradients, and optimizer state page between GPU HBM, CPU RAM, and NVMe, with bandwidth-aware partitioning so all ranks' NVMe devices stream in parallel. Capacity becomes bounded by disk, not HBM — trillion-parameter-scale states on a modest cluster. The purpose is capacity, not speed: NVMe paging keeps a run alive, and the honest framing is "the model trains slowly" versus "the model doesn't train."

4 · ZeRO++ — attacking stage 3's communication bill

ZeRO-3's weakness is communication volume on slow interconnects — the parameter all-gathers and gradient reduce-scatter cross the network every step, and on Ethernet-class clusters or at small per-GPU batch they dominate. ZeRO++ is a bundle of three mitigations:

  • qwZ — quantized weight all-gather. Parameters gather in blockwise-quantized int8 instead of bf16: half the volume, dequantized on arrival before compute.
  • hpZ — hierarchical secondary partition. A second, intra-node copy of the parameter shards: forward all-gathers cross the network once, but backward's re-gather is served entirely from NVLink-local shards — trading a slice of memory to keep repeat traffic inside the node.
  • qgZ — quantized gradient reduce-scatter. Gradients reduce in int4 via a hierarchical all-to-all that dequantizes at each reduction hop to protect accuracy.

Together these cut inter-node communication ~4× — which is best read as a statement about where DeepSpeed expects to run: commodity clusters with thin networks, exactly where Megatron's NVLink-first assumptions break down.

5 · The adoption model — a JSON file, not a rewrite

DeepSpeed's second defining trait is how it attaches: deepspeed.initialize() wraps your existing model and optimizer, and everything else is a JSON config. This is why it became the default scaling engine inside Hugging Face Trainer/Accelerate — the typical DeepSpeed user never calls DeepSpeed directly, they pass --deepspeed ds_config.json: 

{
  "train_micro_batch_size_per_gpu": 4,
  "bf16": { "enabled": true },
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": { "device": "cpu" },
    "overlap_comm": true
  }
}

The config-file interface is a genuine design position, with both edges: capability arrives without touching training code (a fine-tune scales from one GPU to a cluster by editing JSON), but the abstraction is opaque — when a run OOMs or slows down, the debugging surface is a config schema and engine internals rather than code you wrote. It also makes DeepSpeed the natural backend for other people's frameworks: HF Trainer, Accelerate, and Lightning all expose it as a strategy flag.

6 · Beyond ZeRO — the rest of the toolbox

ComponentOne-line identity
Pipeline engine 1F1B pipeline parallelism over nn.Sequential-style stage lists — used by the historical Megatron-DeepSpeed hybrids (BLOOM, MT-NLG) that paired Megatron's TP with DeepSpeed's ZeRO-DP and PP.
DeepSpeed-MoE An early production EP stack: expert parallelism with its own ep_size axis over ZeRO-DP (see MoE Parallelism), plus MoE-specific inference optimizations.
Ulysses DeepSpeed's sequence parallelism for long context: all-to-all that reshards sequence-sharded activations to head-sharded for attention and back — the alternative to ring-style CP, covered on Sequence Parallelism.
DeepSpeed-Chat The 2023 RLHF pipeline (actor/critic/reward on one engine, with a hybrid engine flipping between training and generation modes) — historically important; superseded by dedicated RL frameworks (see the RL framework landscape).
Inference / FastGen / MII Kernel-injection inference and a serving layer — active research artifacts, but production serving consolidated on vLLM/SGLang/TensorRT-LLM (see online inference).

The pattern across the table: DeepSpeed's center of gravity has always been the memory engine. The satellite systems pioneered territory (MoE serving, RLHF pipelines, sequence parallelism) that later, more specialized stacks occupied — Ulysses being the one with the most enduring direct influence.

7 · Honest caveats — and the FSDP question

  • TP is not a first-class native axis the way it is in Megatron — you bring Megatron-style TP to it (the Megatron-DeepSpeed pattern), or go without. For most fine-tuning that's fine; for frontier pretraining it's why the hybrids existed.
  • The hooks fight the compiler. ZeRO-3's per-parameter materialization via Python hooks that intercept module access interacts awkwardly with torch.compile — the same reason FSDP1's wrapper approach was rebuilt as FSDP2 on DTensor.
  • Offload trades step time for capacity — a feature when the alternative is not training at all, a trap when a sharded-only config would have fit. Reach for offload after sharding, not instead of it.
  • Momentum has shifted. With FSDP2 native in PyTorch and HF Accelerate supporting both, the default for new code has drifted PyTorch-native; DeepSpeed remains entrenched in existing configs, in offload-dependent workflows, and on thin-network clusters where ZeRO++ earns its keep.
DeepSpeed ZeRO-3 vs. FSDP — same math, different engineering
DeepSpeed ZeRO-3
Per-parameter partitioning via Python hooks that intercept module access; JSON-config driven; richest offload story (CPU/NVMe); ZeRO++ compressed collectives; turnkey inside HF Trainer. External library with its own runtime and optimizer wrappers.
FSDP2
Per-parameter sharding as DTensor — a core PyTorch type. Composes natively with torch.compile, TP, and device meshes (the composition TorchTitan demonstrates). Leaner offload (CPU only), but no impedance mismatch with the rest of the PyTorch stack. No EP axis of its own — EP comes from an EP-native MoE stack (see MoE Parallelism →).

Summary

The idea

DP's 16 bytes/param of replicated model state is pure redundancy. Shard it (ZeRO-1/2/3), then leave HBM entirely (Offload's CPU Adam, Infinity's NVMe paging) — while wrapping any nn.Module unchanged.

The comm bill

Stages 1–2 ≈ free; stage 3 pays 1.5× plus per-layer gathers. ZeRO++ claws it back on thin networks: int8 weight gathers, intra-node secondary shards, int4 hierarchical gradient reduction — ~4× less inter-node traffic.

The adoption model

A JSON config attached to unmodified code — which made DeepSpeed the scaling engine inside HF Trainer/Accelerate, and the backend other frameworks expose as a flag.

The position today

Reach for it when the model doesn't fit and you won't restructure: offload/Infinity capacity, thin-network clusters, existing HF configs. For new PyTorch-native code, FSDP2 does stage-3 math without the hook machinery.
