The PyTorch Execution Model

What a line of PyTorch actually does — tensors as handles to device memory, the autograd graph recorded as you go, eager vs. graph dispatch, and the ATen operator → dispatcher → CUDA-kernel path. Then the reason eager execution leaves performance on the table, and the ladder that climbs back: CUDA graphs, torch.compile, and hand-written kernels.

Where this sits: this is the layer above the kernel. GPU Hardware for ML covers the memory hierarchy (HBM → SRAM → registers) and the roofline model that the performance argument here rests on; GPU Kernels in Triton is where you write the fused kernel this page motivates. Read this one first if the sentence “PyTorch operators leave performance on the table” isn’t yet obvious.

What actually runs when you write a line of PyTorch

PyTorch code reads like NumPy. You write

y = x.relu()

and a tensor comes back. But that one line is not a function call in the NumPy sense — it is an instruction to a runtime. Behind it, three things happen that NumPy never does:

It drives a device

x is a handle to a block of memory that may live in GPU HBM. The operation launches a GPU kernel that reads and writes that memory — the Python call just enqueues it.

It records a graph

If x needs gradients, the op also appends a node to a backward graph so a later .backward() can replay it in reverse.

It goes through a dispatcher

The call is routed through PyTorch’s operator dispatcher, which picks the right kernel — CPU vs. CUDA, autograd-aware or not, autocast or not — before any compute happens.

This page walks down that stack: what a tensor really is (§tensors), the graph autograd records (§autograd), why running one op at a time is a choice called eager mode (§eager vs. graph), how a call finds its kernel (§dispatch), and then the two ways eager leaves performance on the table (§cost) and how to win it back (§the fix ladder). The payoff is the sentence the Triton page opens with — by the end it should read as a consequence, not an assertion.

Tensors: storage, views, and strides

A PyTorch tensor is not the data. It is a small piece of metadata that points at the data:

FieldWhat it holds
storageA pointer to a flat, 1-D, contiguous block of memory — on CPU it is host RAM, on a CUDA tensor it is a block of HBM. This is the only thing that owns bytes.
dtypeHow to interpret each element (float32, bfloat16, int64, …) and therefore its size in bytes.
shape (sizes)The logical \(n\)-dimensional extent, e.g. (M, N).
strideHow many elements to step in storage to advance one index along each dimension.
storage_offsetWhere in the storage this tensor’s first element begins (lets a tensor start partway into a shared buffer).
deviceWhich device the storage lives on (cpu, cuda:0, …).

The key consequence: a tensor is a handle to device memory. Remember that — the entire performance argument later is about how many times those bytes cross the bus between HBM and the compute units.

Strides make layout explicit

For a contiguous (row-major) matrix of shape \((M, N)\), the strides are \((N, 1)\): stepping one row means jumping \(N\) elements; stepping one column means jumping \(1\). Element \((i, j)\) lives at storage_offset + i·stride[0] + j·stride[1]. Strides are why many tensor operations cost nothing:

A view shares storage — no copy, no kernel

These operations return a new tensor that points at the same storage, with different metadata:

  • x.T / x.transpose(0,1) — swaps the sizes and strides. A \((M,N)\) tensor with strides \((N,1)\) becomes \((N,M)\) with strides \((1,N)\). Zero bytes move.
  • x[2:5], x.unsqueeze(0), x.expand(...), x.view(...) — all just rewrite shape/stride/offset.

After a transpose the tensor is non-contiguous: walking it in row-major order no longer walks memory in order. That is fine for math, but a GPU kernel that assumes a contiguous, coalesced layout cannot run on it directly. So PyTorch exposes x.contiguous(), which does launch a copy kernel to materialize a fresh row-major buffer. Operations that need contiguity either call it for you or raise. The lesson: some ops are pure metadata (free); others move bytes (a kernel). Telling them apart is the first half of reasoning about PyTorch performance.

Autograd: the graph PyTorch records as you go

PyTorch builds its backward graph define-by-run: there is no separate “compile” step where you declare the network. The graph is constructed as a side effect of running the forward pass. Whenever an operation consumes a tensor with requires_grad=True, autograd does three things:

  1. Runs the forward op normally, producing the output tensor.
  2. Creates a backward node — a grad_fn such as ReluBackward0 or MmBackward0 — that knows how to turn an upstream gradient into gradients for this op’s inputs.
  3. Sets the output’s .grad_fn to that node and wires its .next_functions to the inputs’ nodes, extending the graph by one edge.

The result is a DAG whose leaves are the parameters (requires_grad=True tensors you created) and whose root is the loss. Calling loss.backward() walks this DAG in reverse topological order, and at each node applies the vector–Jacobian product — multiplying the incoming gradient by that op’s local Jacobian without ever forming the Jacobian. That mechanism is the subject of its own page; here we only care about its systems footprint.

The math of each grad_fn: see Backpropagation — The Vector–Jacobian Product for why the backward node multiplies by a Jacobian-transpose and how the per-op rules are derived. This page treats those nodes as black boxes with a known cost.

Two costs autograd imposes

Backward replays operators

Every forward op spawns a backward op. A model is therefore (roughly) two sweeps of operators per step — so launch overhead and HBM traffic count at least twice.

Saved tensors cost memory

A node stashes the forward values its backward needs (inputs, or the output). These saved activations are why training memory dwarfs inference, and what activation checkpointing trades away.

So “run a model” is never a single pass. It is a forward sweep that also builds and feeds a graph, followed by a backward sweep that replays it. Every cost discussed below — the per-op launch, the round-trip to HBM — is paid on both.

Eager vs. graph execution

That PyTorch runs one operator at a time, immediately, is a deliberate design called eager execution — and it is the source of both PyTorch’s ergonomics and its performance gaps.

The two execution models
Eager (default)Graph mode
When ops runImmediately, as the Python line executes.The whole computation is captured first, then run.
What the framework seesOne operator at a time. No knowledge of what comes next.The entire graph — so it can optimize globally.
Optimization possibleNone across ops: every intermediate is materialized.Fuse ops, pick layouts, plan memory, remove dead nodes.
DebuggingTrivial — set a breakpoint, print(x), use Python control flow.Harder — you debug a captured IR, not your Python.
Python on the hot pathYes — the interpreter dispatches every op.No — after capture, replay skips Python.

Eager won the framework wars because define-by-run makes models feel like ordinary programs: dynamic shapes, data-dependent branches, and pdb all just work. The price is that the runtime has no lookahead. It cannot fuse a + b with the * c that follows, because when it runs a + b it does not yet know * c exists. Graph mode recovers that lookahead by capturing a representation of the computation before running it — which is exactly what torch.compile does under the hood (§the fix ladder). Everything in between here explains why that lookahead is worth recovering.

Operators and the dispatcher

What you call a “PyTorch operation” is, underneath, an operator in PyTorch’s C++ tensor library, ATen. There are a couple of thousand of them — aten::add, aten::mm, aten::relu, aten::native_layer_norm, aten::_softmax. Every tensor method, every torch.* function, and every infix operator (+, @) bottoms out in one of these.

A given operator is not a single function — it has many implementations, one per situation: a CPU kernel, a CUDA kernel, an autograd wrapper that records the backward node, an autocast wrapper that inserts a cast, and more. Choosing the right one for a particular call is the job of the dispatcher.

Dispatch keys

From the inputs, PyTorch computes a dispatch key set — a bitset of properties: which device (CPU / CUDA), whether autograd is required, whether autocast is active, the layout, and so on. The dispatcher processes these keys in priority order, each key’s handler doing its bit and then redispatching to the next. For y = x.relu() on a CUDA tensor that requires grad:

#LayerWhat happens
1Python bindingx.relu() calls the C++ entry point for the aten::relu operator.
2DispatcherComputes the key set from x: {Autograd, AutocastCUDA?, CUDA}. Highest-priority key first.
3Autograd keyRecords a ReluBackward0 node, saves what backward needs, then redispatches to the next key.
4CUDA keyThe actual CUDA implementation enqueues relu_kernel<<<grid, block>>> on the stream.
5GPUThe kernel reads x from HBM, computes max(x, 0), writes y to HBM.

So one innocuous Python call traverses several handlers before any arithmetic happens, and the backend op ultimately launches at least one GPU kernel. That layered indirection is flexible and clean — it is how the same relu serves CPU, CUDA, autograd, autocast, and meta tensors without any of them knowing about the others. It is also the source of the per-op overhead we turn to next.

The cost of eager execution

Per operator, PyTorch is fast: each ATen kernel is hand-tuned C++/CUDA. The performance that leaks is not inside an op — it is between ops, and it has two distinct causes. Which one bites depends on how big your tensors are.

Cost 1 — kernel-launch overhead (the CPU can’t keep up)

Launching a kernel is not free. Each op pays, on the CPU, for the Python interpreter, the dispatcher walk above, and the driver call (cudaLaunchKernel) — together on the order of a few microseconds. CUDA launches are asynchronous: the CPU enqueues kernels onto a stream and the GPU pulls from that queue. As long as each kernel runs longer than it takes the CPU to queue the next one, the GPU stays saturated and the launch cost hides. But when kernels are tiny — small tensors, or a long chain of cheap elementwise ops — the CPU cannot enqueue fast enough, the queue drains, and the GPU sits idle between kernels. The workload is launch-bound (a.k.a. CPU-bound): in a profiler you see gaps between kernels and GPU utilization well below 100%.

Cost 2 — HBM round-trips (the bytes move too many times)

Even with launch cost fully hidden, eager pays a second tax. Each operator reads its inputs from HBM and writes its output back to HBM, because the next operator is a separate kernel that can only communicate through memory. Chain several ops and every intermediate makes a full round-trip. For memory-bound ops (elementwise, normalization, softmax) where there is almost no arithmetic per byte, HBM bandwidth is the wall — and you hit it once per op instead of once for the whole chain. This is precisely the claim the Triton page opens with.

A worked example: quick-GELU as three ops

Take \(y = x \cdot \sigma(1.702\,x)\) — the “quick GELU” approximation — over a tensor of \(N\) elements in bf16 (2 bytes each). In eager mode this is three operators, each a kernel, each round-tripping HBM:

Eager: 3 kernels, 3 HBM round-trips

read x → t1 = 1.702*x → write t1
read t1 → t2 = sigmoid(t1) → write t2
read x, t2 → y = x*t2 → write y

≈ 7N elements move through HBM · 3 kernel launches.

Fused: 1 kernel, 1 HBM round-trip

read x once → keep in registers
registers → compute 1.702·x, σ, multiply in place
registers → write y once

≈ 2N elements move through HBM · 1 kernel launch.

The fused version moves ~3.5× fewer bytes and pays one launch instead of three. The arithmetic — a scalar multiply and a sigmoid — is identical and trivially cheap; nothing about the math got faster. The win is entirely in not shipping t1 and t2 out to HBM and back. For a bandwidth-bound op, fewer bytes is less time. (This generalizes the fused-softmax result on the Triton page: there, four passes collapse to two.)

One picture: which regime are you in?

Model one elementwise op as costing max(launch_overhead, bytes / bandwidth) — the CPU floor or the memory ramp, whichever is larger. Below a crossover size the launch floor dominates (launch-bound); above it the bandwidth ramp dominates (bandwidth-bound). Drag the tensor size to see where a single op lands, and the chain length to see what fusing the chain saves.

Assumptions (illustrative): bf16 (2 B/element), one read + one write per op, ~2 TB/s HBM bandwidth, ~5 µs fixed launch overhead per kernel. The crossover sits near 2.5 M elements: smaller and you are launch-bound (the CPU can’t feed the GPU); larger and you are bandwidth-bound (the bytes are the wall). Fusion wins in both regimes — it turns k launches and k round-trips into one of each.

Numbers are illustrative — exact launch overhead depends on the CPU, Python, and CUDA version, and bandwidth on the GPU. The shape is what matters: a flat floor, a linear ramp, and a crossover whose existence is the whole point.

Closing the gap: the fix ladder

The two costs have a shared cure — stop treating each op as an isolated kernel — but three rungs of increasing effort and control. Climb only as far as you need.

Rung 1 — CUDA graphs: kill the launch overhead

If the bottleneck is launch-bound (many small kernels), capture the exact sequence of kernel launches once and replay it as a single unit. The CPU-side dispatch and per-launch driver cost vanish; the same kernels run, but with no gaps. This is what inference servers mean by disabling eager mode (e.g. vLLM’s enforce_eager=False captures CUDA graphs for the decode step). It removes Cost 1 but not Cost 2 — the bytes still round-trip — and it needs static shapes, since a captured graph is fixed.

Rung 2 — torch.compile: fuse automatically

torch.compile(model) recovers the graph-mode lookahead from §eager vs. graph. TorchDynamo traces your Python into an FX graph; TorchInductor then fuses elementwise and reduction ops and codegens a single kernel for each fused group — in fact it generates Triton kernels for the GPU. The quick-GELU chain above becomes one kernel automatically. This attacks both costs at once (one launch, one round-trip) and is the right default: a one-line change that captures most of the available win.

Rung 3 — hand-written kernels: when the compiler can’t

Sometimes the fusion you need crosses a boundary the compiler won’t — a matmul fused with a softmax and a second matmul, kept entirely in SRAM, as in FlashAttention — or the algorithm is novel enough that no pattern matches. Then you drop down and write the kernel yourself in Triton (or CUDA). You give up torch.compile’s automation and take full control of the memory-access pattern. This is the handoff to the Triton page, which builds exactly this kind of fused kernel from a blank file.

The sentence, earned

PyTorch operators are fast per-op — but eager runs each as an isolated kernel, so a chain pays k launches and round-trips HBM k times. That is the performance left on the table. The ladder picks it back up: CUDA graphs for launch overhead, torch.compile for automatic fusion, and a hand-written Triton kernel when you need the last word.
