GPU Kernels in Triton

From a blank file to a memory-bandwidth-bound fused softmax — the SPMD programming model, how Triton maps blocks to SMs, and why kernel fusion eliminates HBM round-trips.

Pre-reading: GPU Hardware for ML covers the memory hierarchy (HBM → L2 → SRAM/shared memory → registers) and the roofline model. Knowing what "memory-bandwidth-bound" means before reading the softmax section will make the motivation obvious. The PyTorch Execution Model explains how PyTorch runs operators one at a time and why fusing them matters — the "why" behind every kernel on this page.

Why write GPU kernels at all?

PyTorch operators are fast for standard operations but leave performance on the table when an algorithm naturally chains several operations together. The cost lives in HBM bandwidth: each unfused operator reads its input from HBM and writes its output back, only to have the next operator read it again.

A custom kernel can keep intermediate results in on-chip SRAM and only touch HBM for the final read and write. For memory-bandwidth-bound workloads — softmax, layer norm, dropout, elementwise ops — this is the difference between saturating bandwidth once vs. three or four times.

CUDA lets you write kernels at the warp and shared-memory level but requires managing thread indices, synchronization barriers, and bank conflicts by hand. Triton raises the abstraction one level: you write in terms of blocks of elements rather than individual threads, and the compiler handles the low-level tiling and synchronization. You still control the memory access pattern; you just don't count threads.

What Triton hides

Thread indices within a block, warp synchronization, shared-memory bank conflicts, auto-vectorization.

What you control

Which block each program processes, how many elements per block, load/store patterns and masks, numeric algorithm.

Typical win

1–4× throughput for memory-bound ops (softmax, layer norm). Near-peak FLOP/s for fused matmul ops like FlashAttention.

The Triton mental model

SPMD: one program, many instances

Triton kernels follow the SPMD (single program, multiple data) model — the same program specification runs as many independent instances simultaneously, each operating on a different slice of the data. You write the logic for one instance; the GPU runs thousands in parallel.

Each instance is called a program and gets a unique integer ID from tl.program_id(axis). That ID is the only thing distinguishing one instance from another — the rest of the code is identical. Your kernel body uses the ID to compute which slice of the input/output to read and write.

Blocks, not threads

The fundamental unit in Triton is the block: a contiguous chunk of elements processed together. Inside the kernel you work with 1-D (or 2-D) arrays of shape BLOCK_SIZE rather than individual scalars. tl.arange(0, BLOCK_SIZE) gives you the offset indices within that block; adding them to the block's base pointer gives you the memory addresses to load.

The three-line pattern every kernel follows
  1. Compute base offset: pid * BLOCK_SIZE — where in the array this program starts.
  2. Build element offsets: base + tl.arange(0, BLOCK_SIZE) — the exact addresses to load.
  3. Guard with a mask: offsets < n_elements — prevent out-of-bounds reads on the last (potentially partial) block.

The launch grid

When you call a Triton kernel, you pass it a launch grid — a tuple that says how many program instances to create. For a 1-D kernel processing n_elements elements in blocks of BLOCK_SIZE, the grid has ceil(n_elements / BLOCK_SIZE) programs. Each program covers exactly one block.

The grid can be a tuple or a callable that takes a dict of meta-parameters (including BLOCK_SIZE) and returns a tuple. The callable form lets you vary the grid based on autotuning choices.

Kernel 1: Vector add

The warmup. Two vectors \(x\) and \(y\) of length \(N\), output \(z = x + y\). Nothing compute-intensive — the point is to see the SPMD pattern in the simplest possible setting.

The kernel

import torch
import triton
import triton.language as tl

@triton.jit
def add_kernel(
    x_ptr,                        # pointer to first input vector
    y_ptr,                        # pointer to second input vector
    out_ptr,                      # pointer to output vector
    n_elements,                   # total length of each vector
    BLOCK_SIZE: tl.constexpr,     # elements per program (compile-time constant)
):
    pid = tl.program_id(axis=0)                # which block am I?
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements              # guard last partial block

    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)

The launcher

def add(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    out = torch.empty_like(x)
    n = x.numel()
    # ceil(n / BLOCK_SIZE) programs, each handling one block
    grid = lambda meta: (triton.cdiv(n, meta['BLOCK_SIZE']),)
    add_kernel[grid](x, y, out, n, BLOCK_SIZE=1024)
    return out
Tracing a single program

Say N = 3000, BLOCK_SIZE = 1024. Grid has ceil(3000/1024) = 3 programs.

  • Program 0: offsets = [0…1023], all valid
  • Program 1: offsets = [1024…2047], all valid
  • Program 2: offsets = [2048…3071], mask keeps only [2048…2999] — the rest are out-of-bounds loads that return zero and out-of-bounds stores that are no-ops

Performance

Vector add is memory-bandwidth-bound — each element is loaded twice and stored once (3 passes × 4 bytes for FP32), and there are essentially no FLOPs. Peak bandwidth on an H100 is ~3.35 TB/s; on a T4 it's ~320 GB/s. A Triton vector-add kernel will typically match PyTorch's + operator because they're both doing the same three HBM accesses.

Key observation

The win from writing a custom kernel is not doing the arithmetic faster. It's eliminating HBM round-trips by fusing multiple operations. Vector add has nothing to fuse — so the Triton and PyTorch numbers match. The fused softmax below is where fusion pays.

Kernel 2: Fused softmax

Row-wise softmax: given a matrix of shape \((M, N)\), compute

\[ \text{softmax}(x)_j = \frac{e^{x_j - \max_k x_k}}{\sum_k e^{x_k - \max_k x_k}} \]

for each row independently. The max subtraction is numerically required (prevents overflow for large logits) and changes nothing mathematically — exponentials of shifted values cancel in numerator and denominator.

Why naive softmax is slow

The naive implementation requires three separate passes over each row, each touching HBM:

Naive: 3 HBM passes per row

HBM read → compute max(x)
HBM write → store x − max
HBM read → compute exp and sum
HBM write → store softmax

4 HBM transactions per row. Each row element crosses HBM 3–4 times.

Fused: 2 HBM passes per row

HBM read once → keep in SRAM
SRAM → compute max, exp, sum in place
SRAM → divide and HBM write once

2 HBM transactions per row. Intermediate values never leave the SM.

The constraint: this only works when an entire row of N elements fits in SRAM (the SM's shared memory). For typical LLM attention heads this is true — a row of 4096 FP16 values is 8 KB, well within the 96–256 KB shared memory budget of modern SMs.

The kernel

@triton.jit
def softmax_kernel(
    out_ptr, x_ptr,
    x_row_stride, out_row_stride,  # stride in elements between rows
    n_rows, n_cols,
    BLOCK_SIZE: tl.constexpr,      # must be >= n_cols, padded to next power of 2
):
    # Each program handles one row
    row = tl.program_id(0)
    row_start = x_ptr + row * x_row_stride

    col_offsets = tl.arange(0, BLOCK_SIZE)
    mask = col_offsets < n_cols

    # Pass 1 (in SRAM): load the row, compute max, shift, exp, sum, normalize
    x = tl.load(row_start + col_offsets, mask=mask, other=-float('inf'))

    x_max = tl.max(x, axis=0)          # scalar: max of valid elements
    x_shift = x - x_max                 # shift for numerical stability
    numerator = tl.exp(x_shift)
    denominator = tl.sum(numerator, axis=0)   # sum of exp
    softmax_out = numerator / denominator

    # Pass 2: write output row
    out_start = out_ptr + row * out_row_stride
    tl.store(out_start + col_offsets, softmax_out, mask=mask)

The launcher

def softmax(x: torch.Tensor) -> torch.Tensor:
    assert x.ndim == 2
    n_rows, n_cols = x.shape
    # BLOCK_SIZE must be >= n_cols and a power of 2
    BLOCK_SIZE = triton.next_power_of_2(n_cols)

    out = torch.empty_like(x)
    # One program per row
    softmax_kernel[(n_rows,)](
        out, x,
        x.stride(0), out.stride(0),
        n_rows, n_cols,
        BLOCK_SIZE=BLOCK_SIZE,
    )
    return out

Walking through the numerics

Tracing a single row

Input row: [2.0, 1.0, 0.1], padded to BLOCK_SIZE=4 with -inf.

  1. x_max = max(2.0, 1.0, 0.1, -inf) = 2.0
  2. x_shift = [0.0, -1.0, -1.9, -inf]
  3. numerator = [1.0, 0.368, 0.150, 0.0] (exp of shifted)
  4. denominator = 1.0 + 0.368 + 0.150 + 0.0 = 1.518
  5. softmax = [0.659, 0.242, 0.099, 0.0] (padded slot contributes 0)
  6. Store only the first n_cols=3 positions (mask handles this)

Why the -inf padding works

The padded positions are loaded with other=-float('inf'). When we compute exp(-inf) = 0, those positions contribute nothing to the sum — and the mask on tl.store ensures they are never written back to the output. The max reduction treats -inf as smaller than any real value, so it also doesn't affect x_max. The padding is numerically invisible.

Autotuning BLOCK_SIZE

For a fixed n_cols, the right BLOCK_SIZE is determined at launch time. Triton's @triton.autotune decorator lets you declare multiple configurations (different block sizes, number of warps) and the compiler will benchmark them and cache the winner:

@triton.autotune(
    configs=[
        triton.Config({'BLOCK_SIZE': bs, 'num_warps': nw})
        for bs in [512, 1024, 2048, 4096]
        for nw in [4, 8]
    ],
    key=['n_cols'],
)

Where this leads

The fused softmax is the simplest example of the kernel fusion pattern. The same idea — load once, compute entirely in SRAM, write once — applies at larger scale:

FlashAttention extends the fused softmax idea to the full self-attention mechanism. It uses the online softmax recurrence — a running max and running sum updated tile by tile — to keep the \(N \times N\) attention matrix entirely in SRAM even when it is too large to fit at once. The FlashAttention page goes through the tiling algorithm and IO complexity analysis.

Connection to the GPU hardware: The reason SRAM matters is that its bandwidth to the compute units is ~10–100× higher than HBM's. See the GPU hardware page for the memory hierarchy, roofline model, and why the H100 has 50 MB L2 and 50 MB of SRAM spread across its SMs.
