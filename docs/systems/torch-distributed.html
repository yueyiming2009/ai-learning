Data Parallelism — Replicate, Shard, and the ZeRO Ladder

One training job across N GPUs, each holding a slice of the batch. The entire design space is a single dial: how much of the model state each GPU keeps. DDP replicates all of it; FSDP shards all of it; the ZeRO ladder is every rung between — all built on the same handful of torch.distributed collectives.

This page builds on the comm layer from Sharding & Collectives → (AllReduce, AllGather, ReduceScatter and their byte costs) and NCCL → (how those collectives run on the wire). The orthogonal model-parallel axis is Tensor Parallelism →.

Data parallelism is the first parallelism you reach for and the backbone of nearly every large training run. The recipe is three lines: put a copy of the model on each of \(N\) GPUs, feed each copy a different shard of the batch, and synchronize gradients so the copies take an identical optimizer step and never drift apart. It scales throughput almost linearly — until the model state stops fitting on one GPU. Everything interesting about modern data parallelism is the answer to that problem, and you read the whole answer off one number: bytes of model state per GPU. Replicate it (DDP), shard it (FSDP), or anywhere between (ZeRO).

1 · The foundation: torch.distributed

Before the strategies, the layer they all stand on. A distributed run is \(N\) ordinary processes, one per GPU, each running the same script. The launcher (torchrun) spawns them and stamps each with the environment it needs; each process then calls init_process_group — which is torch.distributed, historically the c10d library. It forms the process group and binds a backend (NCCL on GPUs) that actually moves the bytes.

torchrun — launcher · spawns N processes, sets RANK / WORLD_SIZE / MASTER_ADDR
▼ each process calls init_process_group
torch.distributed (c10d) — ProcessGroup + collectives: all_reduce, all_gather, reduce_scatter, broadcast, send/recv
DDP FSDP Tensor Parallel Pipeline Parallel Expert Parallel
▼ backend
NCCL — GPU collective implementation (rings / trees / NVLS)

The one thing to carry out of this section: every strategy in that middle row — data-parallel or model-parallel — is just a pattern of collective calls over a process group. DDP and FSDP differ only in which collectives they issue and what state they keep between them. The rest of the page is those patterns.

2 · The primitives you actually need

To make \(N\) independent processes behave as one training job you have to coordinate exactly four things. The whole c10d API is those four and little else:

What you must coordinateThe call
Identity — which rank am I, how many of us?get_rank(), get_world_size()
Rendezvous — find each other, pick a backendinit_process_group(backend="nccl")
Reduction — combine tensors across ranksall_reduce, all_gather, reduce_scatter, broadcast
Scoping — restrict a collective to a subsetnew_group(ranks=[…]) / DeviceMesh
 
import os, torch, torch.distributed as dist

dist.init_process_group(backend="nccl")          # rendezvous (reads RANK/WORLD_SIZE/MASTER_ADDR from the env)
torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))   # pin this process to its GPU
dist.all_reduce(grad, op=dist.ReduceOp.SUM)       # every rank ends up with the summed grad

Two facts do a lot of work later. First, the backend is what turns an abstract collective into hardware traffic — nccl for GPUs (the case that matters; see NCCL), gloo for CPU/debugging, mpi on HPC clusters. Second, a subgroup is a parallelism axis. new_group carves a subset of ranks into their own process group with its own communicator; a collective issued on it touches only those ranks. The tensor-parallel group, the data-parallel group, the pipeline-parallel group are each one such subgroup — which is exactly how a framework like Megatron builds its TP/DP/PP/EP groups once at startup and then routes every collective to the right one (§6).

3 · DDP — replicate, and the memory wall

DistributedDataParallel is the bottom of the dial: every GPU holds a full replica of the model — parameters, gradients, and optimizer state. Forward and backward run independently per replica; the only sync is on the gradients.

The DDP step
  1. Each replica runs forward + backward on its own micro-batch → local gradients.
  2. Gradients are AllReduced (averaged) across replicas — bucketed and overlapped with backward, so early layers reduce while later layers are still computing.
  3. Every replica now holds the same averaged gradient → identical optimizer step → replicas stay in lock-step.
from torch.nn.parallel import DistributedDataParallel as DDP
model = DDP(model.to(local_rank), device_ids=[local_rank])   # installs the gradient-AllReduce hooks

The cost is one gradient AllReduce per step; the limitation is the whole point of everything that follows. DDP replicates all three pieces of state, so it works only while the model, its gradients, and its optimizer state fit on one GPU. Count the bytes for mixed-precision AdamW:

The 16-bytes-per-parameter wall
\[ \underbrace{2}_{\substack{\text{fp16}\\\text{weight}}} \;+\; \underbrace{2}_{\substack{\text{fp16}\\\text{grad}}} \;+\; \underbrace{4}_{\substack{\text{fp32}\\\text{master}}} \;+\; \underbrace{4}_{\substack{\text{fp32}\\\text{momentum}}} \;+\; \underbrace{4}_{\substack{\text{fp32}\\\text{variance}}} \;=\; 16\ \text{bytes / param} \]

So a \(7\text{B}\) model needs \(7\times10^9 \times 16 \approx 112\ \text{GB}\) of state — already past an 80 GB H100, before a single byte of activations. DDP cannot help: every replica carries the full \(16M\). That factor of 16 — and the fact that it is replicated \(N\) times across the cluster for no reason — is exactly what sharding attacks.

4 · FSDP — shard the state

FullyShardedDataParallel keeps the data-parallel structure — split the batch, one process per GPU — but shards parameters, gradients, and optimizer state across the \(N\) data-parallel ranks. Each rank permanently owns only \(1/N\) of every weight. The full weights for a layer are reconstructed just-in-time, used, and immediately freed — so peak memory is set by the largest single layer, not the whole model.

FSDP is not built on top of DDP — the two are siblings. FSDP is what you get when you take DDP and shard its redundant state instead of replicating it, splitting the single gradient AllReduce into a ReduceScatter plus the AllGathers needed to rebuild weights on demand. Step through one layer's life on a single rank:

FSDP unit lifecycle — memory on one rank N = 4 ranks · 6-block model · each block = 4 tiles

Notice the shape: a low shard baseline that is always resident, with a single block-sized spike riding on top during compute and dropping straight back down. DDP, by contrast, sits pinned at the full model height the entire step. That gap is the memory win — and the price is the second AllGather in the backward pass. 

# FSDP2 (torch >= 2.4) — per-parameter sharding on DTensor
from torch.distributed.fsdp import fully_shard
for block in model.layers:
    fully_shard(block)        # each block is one all-gather/free unit
fully_shard(model)
DDP vs FSDP — same family, opposite ends of the dial
DDP — replicate

Full model on every GPU. One gradient AllReduce per step. Least communication; capped by single-GPU memory.

FSDP — shard

Each GPU holds \(1/N\). AllGather weights just-in-time (forward and backward) + ReduceScatter grads. More communication, but model size is no longer bounded by one device.

FSDP1 flattens each unit's parameters into one FlatParameter and shards that buffer; FSDP2 shards each parameter individually as a DTensor, which composes cleanly with tensor parallelism (§6) and simplifies distributed checkpointing and partial freezing. New code should prefer FSDP2 (fully_shard).

5 · The ZeRO ladder — DDP and FSDP are two rungs

DeepSpeed's ZeRO formalizes the dial. The three replicated tensors — optimizer state, gradients, parameters — are sharded one at a time; each stage saves more memory and pays a little more communication. DDP is the bottom rung (nothing sharded), FSDP the top (everything sharded).

Where the ~1.5× communication comes from

Count bytes moved per rank per step for \(M\) bytes of parameters across \(N\) ranks. From the collectives cost model, each primitive moves a payload scaled by \((N-1)/N\), which \(\to 1\) for large \(N\): an AllGather or a ReduceScatter costs \(\approx 1\times\) the payload, and an AllReduce \(\approx 2\times\) (it is a ReduceScatter followed by an AllGather).

ForwardBackwardTotal / step
DDP—AllReduce grads \(\approx 2M\)\(\approx 2M\)
FSDPAllGather params \(\approx M\)AllGather params \(\approx M\) + ReduceScatter grads \(\approx M\)\(\approx 3M\)
The trade, in one ratio
\[ \frac{\text{FSDP comm}}{\text{DDP comm}} \;=\; \frac{3M}{2M} \;=\; 1.5\times, \qquad \frac{\text{FSDP state}}{\text{DDP state}} \;=\; \frac{16M/N}{16M} \;=\; \frac{1}{N}. \]

That is the whole bargain: 50% more communication buys an \(N\)-fold cut in per-GPU state. The extra \(M\) is the second weight AllGather FSDP needs in the backward pass — the spike you stepped through in §4, paid twice. Megatron's DistributedOptimizer is the ZeRO-1 point on this ladder: it shards optimizer state and fp32 master weights across the DP group and pairs a ReduceScatter gradient path with an AllGather of the updated params, while leaving the parameters themselves replicated.

6 · Composing with the model-parallel axes

Data parallelism is one axis. At frontier scale it is combined with the orthogonal model-parallel axes — tensor, pipeline, and (for MoE) expert parallel — that split the model itself rather than the batch. Each axis is one set of process groups; a GPU belongs to one group per axis. DeviceMesh lays this out from a named grid and builds the per-axis subgroups for you. 

from torch.distributed.device_mesh import init_device_mesh

# 8 GPUs as a 2-D mesh: 2-way data-parallel x 4-way tensor-parallel
mesh = init_device_mesh("cuda", (2, 4), mesh_dim_names=("dp", "tp"))
dp_group = mesh["dp"].get_group()   # FSDP / gradient sync here
tp_group = mesh["tp"].get_group()   # Megatron AllReduce per layer here

The topology mapping falls out of each axis's communication cost: tensor parallel innermost (an AllReduce on the critical path of every layer → keep it inside one NVLink node), then context/expert parallel, then pipeline parallel (cheap point-to-point activations between stages), with data parallel outermost (one reduction per step, overlappable). In such a 3-D layout the DP axis is normally FSDP rather than plain DDP, so every axis is independently memory-efficient.

The tensor-parallel axis — column/row sharding, one AllReduce per block, the single-node cap — is worked out in full in Tensor Parallelism →. For the axes that tolerate slower inter-node fabric: Pipeline Parallelism → (P2P activations between stages, bubble schedules), Sequence Parallelism → (shard the token axis for long-context training), and MoE Parallelism → (AlltoAll expert dispatch, EP vs TP on FFN weights). To watch every axis fire on a real step, the verl PPO walkthrough → traces each NCCL call across TP/DP/PP.

7 · In practice

  • Bring-up is two lines. torchrun --standalone --nproc_per_node=8 train.py spawns 8 processes; each calls init_process_group("nccl"), pins its GPU from LOCAL_RANK, and wraps the model in DDP or FSDP. That is the whole handshake.
  • Collectives must match across ranks. Every rank has to issue the same collective the same number of times or the job hangs. The classic cause is a ragged last batch (uneven WORLD_SIZE division) desyncing the AllReduce — set drop_last=True. Rank-divergent control flow (an early continue on one rank) hangs the same way.
  • NCCL hang at the first step is usually network/topology, not your code — NCCL_DEBUG=INFO shows the rings being built; NCCL_P2P_DISABLE=1 is a blunt diagnostic.
  • Direction of travel. FSDP2 and tensor/pipeline parallel are converging on DTensor — a sharded-tensor type carrying its placement on a DeviceMesh — so one model is sharded along several axes by annotation rather than by stacked wrappers.

Summary

One dial

Data parallelism = replicate the model, split the batch, sync grads. The only choice is how much state each GPU keeps.

DDP ↔ FSDP

Siblings, not parent/child. DDP replicates (state \(16M\), comm \(2M\)); FSDP shards (state \(16M/N\), comm \(3M\)).

The bargain

The ZeRO ladder: 1.5× communication buys an \(N\)-fold cut in per-GPU state. FSDP ≈ ZeRO-3.

Foundation

All of it is collective calls over torch.distributed process groups; subgroups / DeviceMesh add the orthogonal model-parallel axes.
