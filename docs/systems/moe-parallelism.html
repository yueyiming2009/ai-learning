MoE Parallelism — EP, TP, and Throughput Tradeoffs

How distributed expert pools exchange tokens: EP groups versus local expert groups, logical payload versus network traffic, and the memory, load-balance, and topology tradeoffs behind an EP plan.

Prerequisites: MoE Routing → (gating network, top-K, auxiliary loss), Tensor Parallelism →, Data Parallelism & ZeRO →, Pipeline Parallelism →, Sequence Parallelism →, and Sharding & Collectives → (AlltoAll). For a concrete training step using EP, see PPO in slime/Miles →.

1 · How MoE changes the compute picture

A standard transformer FFN is a dense two-projection block: every token passes through the same \(W_\text{up}[D, 4D]\) and \(W_\text{down}[4D, D]\). All \(8D^2\) parameters are active for every token. The table uses this two-projection convention; a gated SwiGLU FFN has a third matrix.

A Mixture-of-Experts FFN replaces this with \(E\) independent expert FFNs plus a learned router. The router maps each input token to a probability distribution over experts and selects the top-\(K\) experts to process that token. Only those \(K\) experts activate; the remaining \(E-K\) are skipped.

PropertyDense FFNMoE FFN (\(E\) experts, top-\(K\))
Active params per token\(2 \times D \times 4D = 8D^2\)\(K \times 2 \times D \times D_e\) (where \(D_e\) is per-expert width)
Total params (FFN)\(8D^2\)\(E \times 2 \times D \times D_e\)
FLOPs per token\(16D^2\)\(K \times 4 \times D \times D_e\)
Weight memory\(8D^2\) params\(E \times 2 \times D \times D_e\) params (much larger)
CommunicationAllReduce (with TP)AlltoAll dispatch + AlltoAll combine

The MoE tradeoff: you multiply total parameters by \(E/K\) relative to a dense FFN of the same activated compute, gaining model capacity at the cost of weight memory and a new communication pattern. Typical values: \(E = 64,\ K = 2\), so weight memory is \(32\times\) a dense equivalent at the same FLOPs/token.

The MoE constraint
Expert weights scale as \(O(E)\). EP distributes whole experts in the baseline below; TP and parameter sharding can also distribute their weights. See expert granularity for why hundreds of narrow experts can have dense-like active arithmetic.

2 · AlltoAll dispatch — the cost model

In a conventional dense TP FFN, GPUs apply different weight shards to the same token population and reduce partial outputs. In MoE, each token must reach the GPU that holds its assigned experts. This requires a data-dependent routing communication step.

The dispatch/combine pattern

Dispatch (before expert compute)

Let \(B\) be the total number of input tokens in one EP group's dispatch, not a sequence batch size. With equal input partitioning, each rank starts with \(B_\text{local}=B/EP\) tokens. The router assigns each token to \(K\) experts. An AlltoAll redistributes tokens to the ranks that hold their target experts. Each rank receives the tokens assigned to its experts and sends away tokens bound for other ranks.

Expert compute (local)

Each rank runs its \(E/EP\) expert FFNs on the dispatched tokens. Computation is local in the baseline with whole experts per GPU; expert TP adds its own collectives.

Combine (after expert compute)

A second AlltoAll routes expert outputs back to the ranks that originally held each token, where they are aggregated (typically summed with per-expert learned weights) to produce the layer output.

Why AlltoAll, not AllReduce

An AllReduce reduces — it aggregates partial sums from all ranks into a full result. The dense TP AllReduce is needed because every rank computed a partial sum of the same output token, and those partial sums must be added together.

Expert dispatch is a replication-and-permutation, not a reduction: each token produces \(K\) assignments, each targeting one expert. AlltoAll exchanges the destination-specific chunks. Combine returns the expert results and reduces them with the routing weights; implementations can fuse or deduplicate parts of these exchanges.

Logical activation payload, across one EP group
\[ V_\text{dispatch}=BKDb,\qquad V_\text{dispatch+combine}=2BKDb \] Here \(b\) is bytes per activation value, \(K\) is top-K, and \(D\) is hidden width. BF16 uses \(b=2\). This counts one full-width vector per assignment, including local assignments; it excludes metadata, padding, and backward traffic.

Logical payload is not wire traffic. If a fraction \(r\) of assignments leaves its origin rank, average dispatch bytes sent per rank are \(rBKDb/EP\), assuming balanced input and routing and no deduplication. For uniformly placed experts, the expected off-rank fraction is \(r=1-1/EP\). Inter-node traffic needs the fraction crossing a node, not merely a rank. Skew, shared destinations, hierarchical dispatch, and padding alter actual traffic.

Compare collectives with the same token-count and traffic convention. For a TP AllReduce on \(B\) token vectors, the tensor payload per rank is \(BDb\). A ring on \(p\) ranks sends \(2(p-1)BDb/p\) bytes per rank, with a matching receive volume; other algorithms have different cost models. If \(B\) already counts tokens, do not multiply it by sequence length again. There is no general “\(K\ll\text{sequence length}\), therefore AlltoAll is cheaper” rule.

Fan-out — the term the volume formula misses

Bytes are not the whole cost. What the payload formula hides is how many distinct peers each token's copy must reach. A token routed to experts on \(K\) different nodes has \(K\) destinations, though dispatchers batch many tokens into messages. Logical assignment payload alone does not capture fan-out, message sizes, or the slowest-link time.

This is a mild issue at \(K = 2\) and a serious one for fine-grained MoE, where \(K = 6\) or 8 is normal (see MoE Routing §8). DeepSeek-V2's answer is device-limited routing: before running top-\(K\), first select the \(M\) devices holding the highest-affinity experts, then run top-\(K\) only among experts on those devices.

Device-limited routing
\[ \text{devices touched per token} \;\le\; M \quad \text{regardless of } K \]
DeepSeek-V2: \(M = 3\) with \(D = 8\) device groups and \(K = 6\). The paper reports that \(M \ge 3\) matches unrestricted top-\(K\) quality — so the constraint is nearly free.

The effect is to decouple communication fan-out from routing multiplicity: you can keep raising \(K\) for specialization while capping destinations per token. If dispatch deduplicates tokens per destination device, at most \(M B_\text{local}\) distinct token-device vectors are needed from one origin rank. Without that optimization, multiple assignments can still send duplicate vectors. The communication balance loss complements this sending-side constraint by discouraging overloaded receivers.

3 · Expert Parallelism — what it shards and why

Expert Parallelism assigns each EP rank a disjoint subset of the \(E\) experts: rank \(r\) holds experts \([r \times E/EP,\ (r+1) \times E/EP)\). The expert weights for those experts live only on that rank within this group — no expert TP in the baseline. Another data-parallel replica may hold a copy of the same expert pool.

EP group, EP rank, and local expert group are different

An EP group is a communication group of worker processes that jointly hold an expert pool and exchange its tokens. An EP rank is one member of that group, usually one GPU process. With eight experts and two ranks: 

EP communication group: {GPU 0, GPU 1}
|
+-- EP rank 0 / GPU 0 owns E0-E3
|   +-- Local expert group A: {E0, E1}
|   +-- Local expert group B: {E2, E3}
|
+-- EP rank 1 / GPU 1 owns E4-E7
    +-- Local expert group C: {E4, E5}
    +-- Local expert group D: {E6, E7}

The local groups A-D illustrate MAI-style scheduling inside a rank; they are not additional EP process groups. A token on GPU 0 selecting E6 travels within the EP group to GPU 1; group D schedules E6's work. The exact group sizes here are illustrative, not MAI's disclosed configuration.

EP membership is chosen by software, not defined by node boundaries. A group can fit within one node, span nodes inside a rack-scale NVLink domain, or cross the scale-out network. A larger NVLink domain permits wider EP on the fast fabric; it does not prescribe an EP degree or turn remote memory into local HBM.

TP on expert weights vs. EP — arithmetic intensity argument
TP within expert FFN

Each expert's matrices are split across a TP group. Column-parallel up/gate projections can feed a row-parallel down projection, followed by reduction of partial outputs. Implementations can batch expert communication; one AllReduce per expert GEMM is not a requirement.

TP saves weight memory and can accelerate sufficiently large GEMMs, but pays for collectives. Small token counts per expert can make launch, weight-bandwidth, and communication costs dominate. Measure the actual expert shapes instead of assuming all training GEMMs are memory-bound.

EP — shard the experts, move the tokens

Each GPU holds \(E/EP\) complete experts in the baseline. A forward dispatch and combine have logical payload \(2BKDb\) across the group. Actual wire traffic depends on placement and the dispatcher; pipelined schedules may use multiple rounds.

EP keeps expert weights local and moves the tokens instead. Tokens are small (\(D\) floats each); weight matrices are large (\(D \times D_e\)). Moving small things to large things is cheaper than moving large things.

The EP principle
EP assigns different experts to different workers and moves token activations to them. TP splits each expert's matrices. They solve different placement problems and can be combined; their benefit depends on resident state, token counts, kernel efficiency, and topology.

4 · EP degree tradeoffs

Memory savings

With EP degree \(EP\), each rank holds \(E/EP\) expert weight matrices. For a 64-expert MoE with each expert having dimension \(D=2048,\ D_e=1024\) in bf16:

\[ \text{expert weights per rank} = \frac{E}{EP} \times 2 \times D \times D_e \times 2 \text{ bytes} = \frac{64}{EP} \times 2 \times 2048 \times 1024 \times 2 = \frac{512 \text{ MiB}}{EP} \]

Doubling EP halves the per-GPU expert weight memory. This is the main motivation for large EP: the total expert parameter count scales with \(E\), so even moderate \(E\) quickly exceeds single-GPU HBM at reasonable dimensions.

Fixed logical payload does not imply fixed network cost

At fixed group-wide \(B,K,D,b\), logical dispatch payload \(BKDb\) does not depend on the number of experts or ranks. Increasing EP can nevertheless change the remote fraction, message sizes, fan-out, contention, and achieved bandwidth. Holding tokens per rank fixed instead grows group-wide \(B\), so even logical payload grows.

Load imbalance can expose stragglers

Under equal expert costs and hardware, \(BK/EP\) assignments per rank is the balanced target. Skewed expert loads can create a slow rank. A bulk-synchronous dispatch/compute/combine schedule exposes that straggler; chunked schedules may overlap some work but do not erase it.

Load imbalance effect on throughput
\[ \text{expert-compute throughput} \approx \frac{1}{\lambda} \times \text{balanced throughput}, \quad \lambda = \frac{\max_r(\text{tokens dispatched to rank } r)}{\text{avg tokens per rank}} \] This is a linear-work, compute-only approximation, not an end-to-end law. Different expert shapes, communication, and kernel efficiencies change the result.

An auxiliary loss can discourage hot experts, but gives no universal bound on \(\lambda\). Its aggregation scope matters: globally balanced counts can hide opposite imbalances in separate EP groups. Mistral balances expert inbound tokens over each EP group. A runtime capacity policy is separate: it decides how to execute or drop assignments after routing.

Dropless execution with bounded memory

Capacity need not mean dropping tokens or allocating for the worst possible imbalance. Microsoft's MAI-Base-2 implementation groups the experts on each EP rank and gives each expert a fixed token capacity. An overloaded expert can borrow unused capacity from others in its group; tokens still left over are processed in additional dispatch → compute → collect rounds. Backward uses a similar multi-round schedule with fine-grained recomputation per expert group.

Bound memory, not execution time. More capacity consumes more memory; less capacity can require more rounds and scheduling/communication overhead. All routed tokens are processed, but a skewed load can still take longer. Microsoft configures capacity for one round in steady state; the extra rounds handle the tail without growing the expert buffers.

In local group A above, suppose E0 and E1 each have nominal capacity 100 assignments per round. Loads of 150 and 50 fit the pooled capacity of 200 by borrowing E1's unused slots. E0 still computes its 150 assignments using E0's weights; this is buffer borrowing, not rerouting tokens to E1. Loads of 250 and 50 exceed the pooled capacity and require additional rounds. Counts refer to token-expert assignments, so a top-\(K\) token can contribute more than one assignment.

  • Pipeline groups and rounds. Dispatch and collect overlap expert compute, except the first dispatch and last collect. In the reported forward schedule, weight quantization and shared-expert work overlap the exposed communication. In backward, input dispatch overlaps same-layer recomputation and gradient collect overlaps weight-gradient computation, hiding all expert communication in that implementation.
  • Amortize fine-grained experts. Grouped GEMMs and communication reduce launch overhead and tails. GPU-resident routing metadata and GPU-initiated all-to-all avoid host/device synchronization; symmetric-memory NVLink exchange avoids staging copies and reduces HBM contention with concurrent GEMMs.
  • Batch the balancing reductions. Combine load-balancing losses across layers into one batched reduction instead of a separate all-reduce per layer.

Together these changes raised reported MoE-layer MFU from 24% to 35%, making MoE in every layer preferable in wall-clock time, not just FLOPs. This is a layer-level measurement, not the full run's MFU, and overlap is schedule-dependent rather than guaranteed by EP itself. See the model–systems co-design case and the distinct efficiency denominators.

Size EP from assignments and placement, not \(E/K\)

For \(B\) group-wide tokens and top-\(K\) routing, uniform routing gives:

\[ \mathbb E[\text{assignments per expert}]=\frac{BK}{E}, \qquad \mathbb E[\text{assignments per rank}]=\frac{BK}{EP}. \] These are averages, not occupancy guarantees.

For \(B=8192,E=128,K=4,EP=128\), each rank holds one whole expert and receives 256 assignments on average. This is valid even though \(EP>E/K=32\). With whole, unreplicated experts, \(EP\le E\) avoids ranks with no assigned experts; equal placement also needs an appropriate divisibility plan. Whether it is fast depends on the actual distribution, expert shapes, and fabric. Expert TP or replication changes the placement constraints.

5 · Where TP applies in MoE models

TP can shard the dense attention layers. The argument from Tensor Parallelism carries over unchanged: QKV projections and output projections are split column/row-parallel across the TP group (NVLink), and multi-head attention is split across heads. In the conventional column/row-parallel pattern, the forward attention output projection needs one reduction; backward introduces another. SP and alternative schedules change the collective pattern.

Expert TP and EP can coexist. Each collective's process group contains actual processes, not another process group as a single rank. In an orthogonal mesh, hold the TP coordinate fixed to identify EP peers, and hold the EP coordinate fixed to identify expert-TP peers. Other frameworks fold the axes differently. Neither axis is inherently intra-node or inter-node; the layout must specify membership and topology.

Expert TP can be useful for memory capacity or large GEMMs, but its extra communication can hurt small expert batches. \(D_e\) is model-specific: granularity four relative to a \(4D\) dense FFN means \(D_e=D\), not \(D/4\). See the shape example.

The counterexample: a 236B model with no TP at all

"Attention is dense, so shard it with TP" is the default, not a law. DeepSeek-V2 — 236B total parameters — was trained with no tensor parallelism anywhere: 16-way pipeline parallelism, 8-way expert parallelism, and ZeRO-1 data parallelism, with a portion of operators recomputed rather than stored.

The general trade-off is memory and computation saved versus additional collectives. DeepSeek-V2 activates 21B parameters per token, but resident memory still includes all locally assigned experts, not only the selected ones. EP/PP placement and selective recomputation can make the state fit without TP. Once it fits, TP must justify its communication through an actual step-time improvement; sparsity alone does not prove that it will.

When to suspect you don't need TP
  • Resident weights after EP/PP placement, optimizer state, and peak activations fit without TP; active parameters alone are not a memory budget.
  • EP is already sharding the bulk of the weights — in a fine-grained MoE the experts are the model.
  • Recomputation is acceptable: you are trading FLOPs for memory more cheaply than TP trades bandwidth for it.
  • Pipeline depth is available and the schedule is good enough to keep the bubble small (DeepSeek-V2 used a zero-bubble schedule — see Pipeline Parallelism).

Shared experts as an overlap opportunity

One more structural detail: architectures with shared always-on experts get a natural latency-hiding opportunity. If shared experts are replicated on token-origin ranks, their forward computation needs no EP dispatch and can overlap routed-expert communication. Sharded shared experts may still need TP collectives. This is not free compute: overlap depends on dependencies, placement, and available GPU resources.

6 · Data Parallelism interaction

In the explicit Cartesian layout below, DP replicates the TP × EP configuration. Each replica processes a different micro-batch and synchronizes gradients with peers owning the same parameter shard. Frameworks may instead fold axes or use different replication groups for dense and expert parameters. For the explicit layout:

  • Expert weight gradients accumulate from the tokens dispatched to each expert. Since each DP replica has different tokens, their expert gradients differ and must be reduced across DP. Reductions must use the corresponding expert-data-parallel group, not mix gradients from different expert IDs. Dense and expert parameters need not have identical groups.
  • AlltoAll dispatch happens within each DP replica's EP group independently. The EP communication is not synchronized across DP replicas — each replica dispatches its own tokens to its own EP-rank peers.
  • ZeRO-3 + EP: with parameter sharding across DP replicas, each DP rank holds \(1/DP\) of each expert shard's parameters. The ZeRO AllGather before expert GEMMs gathers full expert weights for computation, then shards them back. This stacks with EP: each rank holds \((E/EP)/DP\) worth of expert parameters in its ZeRO partition.
\[ \text{tokens per optimizer step} = B \times DP \times \text{gradient-accumulation steps}. \]

\(B\) counts distinct tokens per replica, not TP copies or top-\(K\) assignments. Scaling the batch does not guarantee linear throughput or unchanged optimization.

7 · Worked example — EP=4, expert DP=2 on 8 GPUs

This is an illustrative placement, not a verified framework launch recipe: two nodes with four GPUs each, \(E=64\), \(K=2\), \(D=2048\), and no TP or PP. Each node contains a complete expert pool, with 16 whole experts per GPU. Each group processes \(B=8192\) distinct tokens, initially 2048 per GPU.

Step 1 — EP groups exchange tokens within each node

Node 0 / EP group A: {GPU 0, GPU 1, GPU 2, GPU 3}
                      E0-15  E16-31 E32-47 E48-63
Node 1 / EP group B: {GPU 4, GPU 5, GPU 6, GPU 7}
                      E0-15  E16-31 E32-47 E48-63

Assume each node's GPUs share NVLink. Dispatch/combine stays inside that domain. A rank number is relative to its process group: GPU 4 is EP rank 0 in group B.

Step 2 — corresponding experts synchronize across replicas

Expert-data-parallel groups:
  {GPU 0, GPU 4}: replicas of E0-15
  {GPU 1, GPU 5}: replicas of E16-31
  {GPU 2, GPU 6}: replicas of E32-47
  {GPU 3, GPU 7}: replicas of E48-63

Expert gradients synchronize across nodes between matching owners, not between different experts in an EP group. Dense attention weights are replicated on all eight GPUs here; because every GPU starts with different tokens, their gradients synchronize across all eight. This illustrates why dense DP and expert DP need not have the same size.

Step 3 — count assignments and transmitted bytes separately

Each group produces \(BK=16384\) assignments: 256 per expert and 4096 per rank on average. With uniform routing and BF16, logical dispatch payload is \(8192\times2\times2048\times2=64\) MiB across the group. Three quarters of assignments are off-rank, giving 48 MiB sent across the group, or 12 MiB sent per GPU. Each GPU also receives 12 MiB on average; do not add sent and received bytes unless reporting bidirectional endpoint traffic.

8 · MoE-aware throughput ceiling

FLOPs formula

The MFU page derives the 6N FLOPs/token rule. For MoE, \(N\) is the activated parameter count per token — not the total. With \(K\) of \(E\) experts active:

\[ \text{FLOPs/token (MoE)} = 6 \times N_\text{activated} + 12 \times L \times D \times T \] \[ N_\text{activated} = N_\text{dense} + N_\text{shared} + \frac{K}{E}N_\text{routed} \] \(N_\text{routed}\) counts equal-sized routed experts; dense and shared weights are always active in this approximation. Here \(L,D,T\) are layer count, hidden width, and sequence length for the full-attention FLOP term. Sparse attention requires its own accounting.

When AlltoAll is on the critical path

In a bulk-synchronous forward, dispatch, expert computation, and combine add to step time. A token's computation needs its input, but that does not prevent pipelining different expert groups or chunks, as in MAI's schedule.

A simplified balanced, whole-expert, two-projection forward model uses:

  • \(\tau_\text{GEMM}\approx 4(B/EP)KDD_e/F_\text{eff}\), where \(F_\text{eff}\) is achieved expert-matrix FLOP/s.
  • \(\tau_\text{dispatch}\approx\ell+r(B/EP)KDb/W_\text{eff}\), where \(\ell\) is exchange startup/scheduling cost and \(W_\text{eff}\) is effective one-way bandwidth.
  • Combine has a similar payload in this uncombined-assignment model; SwiGLU changes the GEMM coefficient from 4 to 6.

If startup is ignored and achieved rates are treated as constants, the bandwidth-only ratio for dispatch plus combine is:

\[ \frac{\tau_\text{dispatch}+\tau_\text{combine}}{\tau_\text{GEMM}} \approx \frac{rbF_\text{eff}}{2D_eW_\text{eff}}. \] \(B\) cancels. This model does not yield a universal crossover batch size.

Real batch-size effects come from startup, expert load distribution, GEMM shapes, weight-memory traffic, and changing achieved bandwidth. Increasing batch size can amortize overhead and improve arithmetic intensity, but the crossover must be measured or modeled with those terms. A communication bottleneck does not prove that the GEMMs themselves are memory-bandwidth-bound.

Profile the slowest rank and the exposed critical path, not just aggregate bytes. Compare peak memory, tokens per expert, dispatch/combine durations, achieved GEMM throughput, and overlap under the intended topology and capacity policy.

9 · Framework support — where EP × TP actually runs

Everything above is framework-agnostic; support for it is not. The EP axis needs three things managed as first-class state: expert-sharded parameters with their own process groups, the dispatch/combine AlltoAll wired into the layer's forward and backward, and an optimizer + checkpoint layout that understands a parameter existing on only one EP rank.

Megatron-family vs. FSDP-family on the EP axis
Megatron-LM / Megatron-Core

The stack manages EP process groups, grouped-GEMM expert execution, token dispatch, and expert-aware distributed checkpointing. Attention TP, expert TP, EP, and expert DP degrees must be read from the actual configuration; §7 is an illustration, not a universal shipped layout.

FSDP / FSDP2

FSDP is a DP-family sharder — the API itself has no EP concept: no expert process groups, no dispatch AlltoAll, no expert-sharded optimizer state. Wrapped around a stock MoE model, it shards expert weights over DP and every rank all-gathers the full expert table to compute its local tokens — the §3 arithmetic-intensity win never materializes, and AllGather traffic scales with total (not activated) expert parameters.

EP can be assembled around FSDP: torchtitan composes an EP mesh axis (DTensor) with FSDP2 and TP — the DeepSeek-V3 pre-training recipe — and MegaBlocks-style expert layers compose with FSDP/HSDP via DeviceMesh (the DBRX lineage); DeepSpeed-MoE ships its own ep_size axis. In every such case the EP axis comes from the MoE layer implementation plus an explicit mesh plan — never from FSDP itself.

Hybrid architectures sharpen the gap: a model interleaving MoE FFN blocks with linear-attention layers wants different sharding per layer family — EP for the experts, TP or plain DP for the linear-attention state. That is a heterogeneous device mesh: natural to express in Megatron-Core's per-layer specs, and outside what FSDP's wrap-and-shard model was designed to say.
Practical consequence
If a profile of a stock FSDP fine-tune stack (e.g. a Transformers MoE model wrapped in FSDP) says the fix is EP=8, TP=1–2, the lever is not a config change — it is a migration to an EP-native stack: Megatron-Core (the most integrated EP × TP × PP planner), torchtitan, DeepSpeed-MoE, or a MegaBlocks-style integration. Which one is a stack decision to plan as the prerequisite, not an optimization inside the current run.

10 · Summary

The MoE change

Sparse activation: only \(K\) of \(E\) experts fire per token. Expert weights scale as \(O(E)\), demanding a new sharding axis. Per-token compute stays fixed at \(K\) expert FLOPs.

AlltoAll dispatch

Replicate/permutate assignments, compute, return and combine. Logical payload is \(BKDb\) each way across the group; remote fraction, topology, and dispatcher determine wire traffic.

EP versus expert TP

EP distributes experts; TP splits their matrices. They can coexist. Evaluate resident state, token counts, kernel efficiency, and communication rather than assuming a universal bottleneck.

EP tradeoffs

More EP reduces local expert storage but can increase fan-out and expose skew. Expected assignments are \(BK/E\) per expert and \(BK/EP\) per rank; \(EP\le E/K\) is not a general requirement.

Two meanings of group

An EP group contains workers exchanging tokens. MAI local expert groups contain experts on one worker sharing a bounded execution budget. Capacity borrowing does not change expert identity.

Framework support

EP comes from the MoE stack, not the sharder: first-class in Megatron-Core, DeepSpeed-MoE, torchtitan (EP + FSDP2 + TP on DTensor), MegaBlocks. Plain FSDP has no EP axis — reaching EP on a stock FSDP run is a stack migration, not a config change.

Throughput ceiling

Model FLOPs use activated parameters, including shared experts. Memory uses resident state. In the constant-rate bandwidth-only model, batch size cancels; startup, kernel efficiency, skew, and overlap determine real crossovers.
