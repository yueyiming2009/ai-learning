MoE Parallelism — EP, TP, and Throughput Tradeoffs

Mixture-of-Experts models replace the dense FFN with a data-dependent expert dispatch, demanding a new parallelism axis. This page derives the AlltoAll cost model, the arithmetic-intensity argument for Expert Parallelism over TP on FFN weights, and how to reason about TP × EP × DP degrees for throughput.

Prerequisites: MoE Routing → (gating network, top-K, auxiliary loss), Tensor Parallelism →, Data Parallelism & ZeRO →, Pipeline Parallelism →, Sequence Parallelism →, and Sharding & Collectives → (AlltoAll). For a concrete training step using EP, see PPO in slime/Miles →.

1 · How MoE changes the compute picture

A standard transformer FFN is a dense two-projection block: every token passes through the same \(W_\text{up}[D, 4D]\) and \(W_\text{down}[4D, D]\). All \(4D^2\) parameters are active for every token.

A Mixture-of-Experts FFN replaces this with \(E\) independent expert FFNs plus a learned router. The router maps each input token to a probability distribution over experts and selects the top-\(K\) experts to process that token. Only those \(K\) experts activate; the remaining \(E-K\) are skipped.

PropertyDense FFNMoE FFN (\(E\) experts, top-\(K\))
Active params per token\(2 \times D \times 4D = 8D^2\)\(K \times 2 \times D \times D_e\) (where \(D_e\) is per-expert width)
Total params (FFN)\(8D^2\)\(E \times 2 \times D \times D_e\)
FLOPs per token\(16D^2\)\(K \times 4 \times D \times D_e\)
Weight memory\(8D^2\) params\(E \times 2 \times D \times D_e\) params (much larger)
CommunicationAllReduce (with TP)AlltoAll dispatch + AlltoAll combine

The MoE tradeoff: you multiply total parameters by \(E/K\) relative to a dense FFN of the same activated compute, gaining model capacity at the cost of weight memory and a new communication pattern. Typical values: \(E = 64,\ K = 2\), so weight memory is \(32\times\) a dense equivalent at the same FLOPs/token.

The MoE constraint
Expert weights scale as \(O(E)\). They must either be replicated across GPUs (memory-prohibitive at large \(E\)) or sharded across a new parallelism axis — Expert Parallelism.

2 · AlltoAll dispatch — the cost model

In a dense model with TP, each GPU applies the same FFN to its local tokens and reduces partial sums with an AllReduce. In MoE, each token must reach the GPU that holds its assigned experts. This requires a data-dependent routing communication step.

The dispatch/combine pattern

Dispatch (before expert compute)

Each rank holds \(B_\text{local}\) tokens. The router assigns each token to \(K\) experts. An AlltoAll redistributes tokens to the ranks that hold their target experts. Each rank receives the tokens assigned to its experts and sends away tokens bound for other ranks.

Expert compute (local)

Each rank runs its \(E/EP\) expert FFNs on the dispatched tokens. Fully local — no communication.

Combine (after expert compute)

A second AlltoAll routes expert outputs back to the ranks that originally held each token, where they are aggregated (typically summed with per-expert learned weights) to produce the layer output.

Why AlltoAll, not AllReduce

An AllReduce reduces — it aggregates partial sums from all ranks into a full result. The dense TP AllReduce is needed because every rank computed a partial sum of the same output token, and those partial sums must be added together.

Expert dispatch is a permutation, not a reduction: each token goes to exactly one expert (per selection), is processed there, and comes back. There are no partial sums to accumulate across ranks at dispatch time. AlltoAll is exactly the right primitive — it is a full-to-full exchange where each rank sends a distinct chunk to each other rank.

AlltoAll dispatch volume per MoE layer
\[ V_\text{dispatch} = B \times K \times D \text{ values} \quad (= 2BKD \text{ bytes in bf16}) \] where \(B\) = tokens in this batch (not sequences), \(K\) = top-K, \(D\) = hidden dim. Same for combine.
Total per-layer: \(2 \times 2BKD\) bytes (one AlltoAll each way).

Compare this to the TP AllReduce for a dense FFN of the same \(D\): volume per AllReduce = \(2BTD\) bytes (for \(T\) tokens in the sequence). They differ in the token count: the AlltoAll sends \(BK\) tokens (total dispatched per layer) vs. the AllReduce's \(BT\) tokens. At \(K \ll T\) the AlltoAll is cheaper; but \(K\) is typically 2 while \(T\) can be 4096+, so the AlltoAll is often over an order of magnitude smaller in volume.

The AlltoAll payload is independent of \(E\) and \(EP\). Adding more experts or more EP ranks does not change the total bytes moved — it only changes how many ranks participate in the exchange. (A permutation's total data volume equals the number of elements being permuted.)

Fan-out — the term the volume formula misses

Bytes are not the whole cost. What the payload formula hides is how many distinct peers each token's copy must reach: a token routed to \(K\) experts scattered across \(K\) different nodes generates \(K\) separate inter-node messages, each with its own latency and its own place in the slowest-link calculation. Total volume is unchanged; wall-clock is not.

This is a mild issue at \(K = 2\) and a serious one for fine-grained MoE, where \(K = 6\) or 8 is normal (see MoE Routing §8). DeepSeek-V2's answer is device-limited routing: before running top-\(K\), first select the \(M\) devices holding the highest-affinity experts, then run top-\(K\) only among experts on those devices.

Device-limited routing
\[ \text{devices touched per token} \;\le\; M \quad \text{regardless of } K \]
DeepSeek-V2: \(M = 3\) with \(D = 8\) device groups and \(K = 6\). The paper reports that \(M \ge 3\) matches unrestricted top-\(K\) quality — so the constraint is nearly free.

The effect is to decouple communication fan-out from routing multiplicity: you can keep raising \(K\) for specialization without the message count following it. It also gives a hard bound to build on — each device sends at most \(MT\) hidden states — which is what the communication balance loss on the routing page then complements from the receiving side.

3 · Expert Parallelism — what it shards and why

Expert Parallelism assigns each EP rank a disjoint subset of the \(E\) experts: rank \(r\) holds experts \([r \times E/EP,\ (r+1) \times E/EP)\). The expert weights for those experts live only on that rank — no replication, no TP sharding within them (in the baseline configuration).

TP on expert weights vs. EP — arithmetic intensity argument
TP within expert FFN

Each GPU holds half of each expert's weight matrix. After every expert GEMM, an AllReduce sums partial outputs. With \(E\) experts active: \(E\) AllReduces per layer.

The expert GEMMs at training batch sizes are memory-bandwidth-bound (few tokens per expert → low arithmetic intensity). TP adds communication without improving the memory bottleneck — the arithmetic intensity of the GEMM doesn't increase, but AllReduce latency is added on the critical path.

EP — shard the experts, move the tokens

Each GPU holds \(E/EP\) complete expert weight matrices. Expert GEMMs are fully local. Only two AlltoAll operations per layer (dispatch + combine), total volume \(4BKD\) bytes — independent of \(E\).

EP keeps expert weights local and moves the tokens instead. Tokens are small (\(D\) floats each); weight matrices are large (\(D \times D_e\)). Moving small things to large things is cheaper than moving large things.

The EP principle
At the batch sizes typical in training, expert FFNs are memory-bandwidth-bound. TP on expert weights adds AllReduce communication without improving arithmetic intensity. EP avoids this by keeping each expert local and routing tokens via AlltoAll — whose volume is proportional to tokens, not parameters.

4 · EP degree tradeoffs

Memory savings

With EP degree \(EP\), each rank holds \(E/EP\) expert weight matrices. For a 64-expert MoE with each expert having dimension \(D=2048,\ D_e=1024\) in bf16:

\[ \text{expert weights per rank} = \frac{E}{EP} \times 2 \times D \times D_e \times 2 \text{ bytes} = \frac{64}{EP} \times 2 \times 2048 \times 1024 \times 2 \approx \frac{512 \text{ MB}}{EP} \]

Doubling EP halves the per-GPU expert weight memory. This is the main motivation for large EP: the total expert parameter count scales with \(E\), so even moderate \(E\) quickly exceeds single-GPU HBM at reasonable dimensions.

Communication volume stays constant

Unlike TP (where AllReduce volume scales with the tensor being reduced), the AlltoAll dispatch volume \(2BKD\) is independent of EP degree. It's a permutation of a fixed number of tokens — more EP ranks just means smaller chunks per rank, not more total bytes. The alltoall latency may increase slightly (more ranks in the collective) but bandwidth is unaffected.

Load imbalance is the EP ceiling

The one cost that grows with EP is the exposure of expert load imbalance. If all EP ranks had exactly \(BK/EP\) tokens dispatched to them, all expert GEMMs would finish simultaneously. In practice, the router assigns tokens non-uniformly: one expert might receive \(2\times\) the average. All EP ranks must wait for the slowest one to finish before the combine AlltoAll can proceed.

Load imbalance effect on throughput
\[ \text{effective throughput} = \frac{1}{\lambda} \times \text{balanced throughput}, \quad \lambda = \frac{\max_r(\text{tokens dispatched to rank } r)}{\text{avg tokens per rank}} \] A 2× load spike (\(\lambda = 2\)) halves expert-layer throughput. More EP ranks → smaller denominator → higher relative variance → larger expected \(\lambda\).

Training uses an auxiliary load-balancing loss that penalizes routers for concentrating tokens on a few experts. This typically keeps \(\lambda \le 1.3\) in practice. Some implementations also cap the number of tokens a single expert can receive (expert capacity), dropping or buffering excess tokens rather than stalling the pipeline.

Practical EP ceiling

Each expert must receive at least one token on average per step; otherwise some ranks compute nothing and the dispatch overhead isn't amortized. This gives:

\[ EP_\text{max} \le \frac{B \times K}{1} = BK \quad \text{(one token per expert per step on average)} \] In practice: \(EP \le E/K\) ensures each rank handles at least \(E/(EP) \ge K\) experts, giving a meaningful local workload.

5 · Where TP applies in MoE models

TP remains the right axis for the attention layers, which are dense. The argument from Tensor Parallelism carries over unchanged: QKV projections and output projections are split column/row-parallel across the TP group (NVLink), and multi-head attention is split across heads. Two AllReduces per layer, volume \(2BTD\).

For the expert FFN layers: EP replaces TP as the sharding axis. The two approaches use separate process groups — the TP group contains the GPUs within one node; the EP group contains one GPU (or one TP sub-group) per node.

TP-within-expert is possible: shard each expert's weight matrix column/row-parallel across the TP group, adding an AllReduce after each expert GEMM. This is only beneficial when a single expert is large enough to be compute-bound at high batch size — rare in standard MoE configurations (\(D_e \approx D/4\)). In practice, use EP for experts and TP for attention.

The counterexample: a 236B model with no TP at all

"Attention is dense, so shard it with TP" is the default, not a law. DeepSeek-V2 — 236B total parameters — was trained with no tensor parallelism anywhere: 16-way pipeline parallelism, 8-way expert parallelism, and ZeRO-1 data parallelism, with a portion of operators recomputed rather than stored.

The reasoning is worth extracting, because it generalizes. TP buys memory relief and pays for it with two AllReduces per layer on the critical path. What makes that trade good is a large activated parameter count that will not otherwise fit. A sparse model inverts the premise: only 21B parameters are activated per token, so the per-layer working set is small, and selective recomputation covers the remaining activation pressure. With the memory problem solved more cheaply elsewhere, TP is left contributing nothing but communication — so it was dropped.

When to suspect you don't need TP
  • Activated (not total) parameters per token are small relative to device memory.
  • EP is already sharding the bulk of the weights — in a fine-grained MoE the experts are the model.
  • Recomputation is acceptable: you are trading FLOPs for memory more cheaply than TP trades bandwidth for it.
  • Pipeline depth is available and the schedule is good enough to keep the bubble small (DeepSeek-V2 used a zero-bubble schedule — see Pipeline Parallelism).

Shared experts as free overlap

One more structural detail: architectures with shared always-on experts get a natural latency hiding opportunity. Shared experts run for every token, so they need no dispatch and no combine — their input is already resident on the rank that holds the token. That makes their FLOPs the ideal thing to schedule during the routed experts' AlltoAll, which is exactly what DeepSeek-V2 does. It is the rare overlap that requires no restructuring: the work was already local.

6 · Data Parallelism interaction

DP is orthogonal to both TP and EP. Each DP replica runs an independent forward and backward pass on a different micro-batch, then synchronizes gradients. For MoE:

  • Expert weight gradients accumulate from the tokens dispatched to each expert. Since each DP replica has different tokens, their expert gradients differ and must be reduced across DP. The reduction (ReduceScatter with ZeRO-3) is identical to the dense case — expert weights are just parameters, and all-parameter gradient sync applies uniformly.
  • AlltoAll dispatch happens within each DP replica's EP group independently. The EP communication is not synchronized across DP replicas — each replica dispatches its own tokens to its own EP-rank peers.
  • ZeRO-3 + EP: with parameter sharding across DP replicas, each DP rank holds \(1/DP\) of each expert shard's parameters. The ZeRO AllGather before expert GEMMs gathers full expert weights for computation, then shards them back. This stacks with EP: each rank holds \((E/EP)/DP\) worth of expert parameters in its ZeRO partition.
\[ \text{global batch} = B_\text{local} \times DP \quad \Rightarrow \quad \text{throughput scales linearly with DP until communication dominates} \]

7 · Worked example — TP=2, EP=2, DP=2 on 8 GPUs

The slime/Miles PPO walkthrough uses this configuration for a 30B MoE model with 64 experts, top-2 routing, \(D = 2048\), on 2 nodes × 4 GPUs/node. Here we derive why those degrees were chosen.

Step 1 — TP for attention (NVLink, intra-node)

TP must stay within one NVLink island. Each node has 4 GPUs. We want TP to cover attention efficiently. TP=2 is chosen (not TP=4) to keep the AllReduce payload small and leave room for the EP axis within the node: 

Node 0: GPU 0, GPU 1  ← TP group 0 (NVLink, AllReduce for attention)
         GPU 2, GPU 3  ← TP group 1
Node 1: GPU 4, GPU 5  ← TP group 2
         GPU 6, GPU 7  ← TP group 3

Step 2 — EP for experts (InfiniBand, inter-node)

EP=2 across the two nodes. Each EP rank is one TP group: GPU 0+1 (node 0) vs. GPU 4+5 (node 1). Each EP rank holds \(64/2 = 32\) experts. 

EP group A: TP group 0  (GPUs 0,1, node 0) ↔ TP group 2  (GPUs 4,5, node 1)
EP group B: TP group 1  (GPUs 2,3, node 0) ↔ TP group 3  (GPUs 6,7, node 1)

The AlltoAll for expert dispatch crosses InfiniBand (node 0 ↔ node 1). With \(B = 8192\) tokens, \(K = 2\), \(D = 2048\), bf16: AlltoAll volume per GPU ≈ \(8192 \times 2 \times 2048 \times 2 / 2 \approx 32\) MB. (Half the tokens go to the remote EP rank; the other half stay local.)

Step 3 — DP fills remaining replicas

With TP=2 and EP=2, each EP group uses 2 GPUs per node × 2 nodes = 4 GPUs. We have 8 GPUs total, so DP=2 replicates the whole (TP=2, EP=2) configuration twice: 

DP rank 0: EP group A  (GPUs 0,1,4,5)
DP rank 1: EP group B  (GPUs 2,3,6,7)

Per-layer communication breakdown

OperationPrimitiveVolume / GPUFabric
Attention (fwd) 2× AllReduce (TP) \(2 \times 2 \times BT \times D\) bf16 ≈ 2× 34 MB NVLink
Expert dispatch (fwd) AlltoAll (EP) ≈ 32 MB (half tokens cross node) InfiniBand
Expert combine (fwd) AlltoAll (EP) ≈ 32 MB InfiniBand
Gradient sync (bwd) ReduceScatter + AllGather (DP) Proportional to expert weight size InfiniBand

The TP AllReduce uses NVLink (fast, low latency, on the critical path). The EP AlltoAll uses InfiniBand (slower, but its volume — \(\approx 32\) MB at these settings — is small relative to expert GEMM time at this batch size, so it stays mostly hidden).

8 · MoE-aware throughput ceiling

FLOPs formula

The MFU page derives the 6N FLOPs/token rule. For MoE, \(N\) is the activated parameter count per token — not the total. With \(K\) of \(E\) experts active:

\[ \text{FLOPs/token (MoE)} = 6 \times N_\text{activated} + 12 \times L \times D \times T \] \[ N_\text{activated} = N_\text{attn} + \frac{K}{E} \times N_\text{FFN} \] where \(N_\text{attn}\) = attention parameter count (dense, replicated), \(N_\text{FFN}\) = total expert FFN params.

When AlltoAll is on the critical path

The expert compute and the AlltoAll dispatch happen sequentially (dispatch must complete before expert GEMMs begin). The effective throughput depends on which is slower.

Define:

  • \(\tau_\text{GEMM}\) = time for expert GEMMs on one EP rank = \(\frac{(B/EP) \times K \times 4 \times D \times D_e}{\text{FLOP/s}_\text{device}}\)
  • \(\tau_\text{A2A}\) = AlltoAll latency = \(\frac{2 \times (B/EP) \times K \times D \times 2}{\text{IB bandwidth}}\)

When \(\tau_\text{A2A} > \tau_\text{GEMM}\), the AlltoAll is on the critical path and EP is the throughput bottleneck. Setting \(\tau_\text{A2A} = \tau_\text{GEMM}\) gives the cross-over batch size:

\[ B^* = \frac{2 \times \text{FLOP/s}_\text{device} \times D_e}{\text{IB bandwidth} \times 2} = \frac{\text{FLOP/s}_\text{device} \times D_e}{\text{IB bandwidth}} \] Below \(B^*\) tokens per EP rank: AlltoAll dominates. Above \(B^*\): expert GEMMs dominate.

For an H100 at 1 PFLOP/s (bf16 dense), IB at 50 GB/s, \(D_e = 1024\): \(B^* \approx 1{,}000{,}000 \times 1024 / 50{,}000{,}000{,}000 \approx 20{,}000\) tokens per EP rank. At training batch sizes of 8,192 tokens per rank, most MoE training runs sit below \(B^*\) — the AlltoAll is the bottleneck, not the expert GEMMs. This is why expert GEMMs are memory-bandwidth-bound and why TP (which adds more AllReduce communication) makes things worse.

The cross-over batch size \(B^*\) grows with \(D_e\) and device FLOP/s. As models get larger experts or are run at larger batch sizes, compute becomes the bottleneck. But for standard MoE configurations in RL fine-tuning (small rollout batches), AlltoAll latency is almost always the binding constraint.

9 · Framework support — where EP × TP actually runs

Everything above is framework-agnostic; support for it is not. The EP axis needs three things managed as first-class state: expert-sharded parameters with their own process groups, the dispatch/combine AlltoAll wired into the layer's forward and backward, and an optimizer + checkpoint layout that understands a parameter existing on only one EP rank.

Megatron-family vs. FSDP-family on the EP axis
Megatron-LM / Megatron-Core

EP is a first-class mesh axis: EP × TP × DP × PP configured together, grouped-GEMM expert execution, token dispatch built into the MoE layer, expert-aware distributed checkpointing. The TP-intra-node / EP-across-TP-groups layout of §7 is the shipped default, not an integration project.

FSDP / FSDP2

FSDP is a DP-family sharder — the API itself has no EP concept: no expert process groups, no dispatch AlltoAll, no expert-sharded optimizer state. Wrapped around a stock MoE model, it shards expert weights over DP and every rank all-gathers the full expert table to compute its local tokens — the §3 arithmetic-intensity win never materializes, and AllGather traffic scales with total (not activated) expert parameters.

EP can be assembled around FSDP: torchtitan composes an EP mesh axis (DTensor) with FSDP2 and TP — the DeepSeek-V3 pre-training recipe — and MegaBlocks-style expert layers compose with FSDP/HSDP via DeviceMesh (the DBRX lineage); DeepSpeed-MoE ships its own ep_size axis. In every such case the EP axis comes from the MoE layer implementation plus an explicit mesh plan — never from FSDP itself.

Hybrid architectures sharpen the gap: a model interleaving MoE FFN blocks with linear-attention layers wants different sharding per layer family — EP for the experts, TP or plain DP for the linear-attention state. That is a heterogeneous device mesh: natural to express in Megatron-Core's per-layer specs, and outside what FSDP's wrap-and-shard model was designed to say.
Practical consequence
If a profile of a stock FSDP fine-tune stack (e.g. a Transformers MoE model wrapped in FSDP) says the fix is EP=8, TP=1–2, the lever is not a config change — it is a migration to an EP-native stack: Megatron-Core (the most integrated EP × TP × PP planner), torchtitan, DeepSpeed-MoE, or a MegaBlocks-style integration. Which one is a stack decision to plan as the prerequisite, not an optimization inside the current run.

10 · Summary

The MoE change

Sparse activation: only \(K\) of \(E\) experts fire per token. Expert weights scale as \(O(E)\), demanding a new sharding axis. Per-token compute stays fixed at \(K\) expert FLOPs.

AlltoAll dispatch

Permute tokens to the ranks holding their experts, compute locally, permute back. Volume = \(2BKD\) bytes per AlltoAll — independent of \(E\) and \(EP\). Not a reduction.

Why EP, not TP

Expert GEMMs are memory-bandwidth-bound at training batch sizes (low arithmetic intensity). TP adds AllReduce comm without fixing the bottleneck. EP keeps experts local and moves the smaller tokens.

EP tradeoffs

More EP → less weight memory per GPU. AlltoAll volume unchanged. Load imbalance (\(\lambda\)) is the ceiling: throughput ≤ \(1/\lambda\) of balanced. Use auxiliary loss to keep \(\lambda \le 1.3\).

TP in MoE

TP still handles dense attention layers (unchanged from the dense case). For experts: EP, not TP. TP-within-expert only if a single expert exceeds NVLink capacity — rare.

Framework support

EP comes from the MoE stack, not the sharder: first-class in Megatron-Core, DeepSpeed-MoE, torchtitan (EP + FSDP2 + TP on DTensor), MegaBlocks. Plain FSDP has no EP axis — reaching EP on a stock FSDP run is a stack migration, not a config change.

Throughput ceiling

MoE FLOPs use activated params. Cross-over batch size \(B^* = \text{FLOP/s} \times D_e / \text{IB BW}\). Below \(B^*\): AlltoAll-bound. Most training runs fall here.
