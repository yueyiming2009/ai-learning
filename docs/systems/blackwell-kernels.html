GPU Kernels · Blackwell / sm_100

The Blackwell Kernel Model

What changes when you write kernels for sm_100: the MMA becomes a single-thread-issued asynchronous engine, accumulators move into Tensor Memory, two SMs gang up on one multiply, and 4-bit block-scaled formats enter the mainloop.

Pre-reading: the Hopper warp-specialized mainloop — this page is a diff against it; GPU Generations for the chip-level changes (dual-die, HBM3e, NVL72) that are deliberately not repeated here; and CUDA for warps and occupancy. The FlashAttention-4 section is the flagship application of everything below.

The trajectory completes: the MMA becomes an engine

Each tensor-core generation has moved the MMA further away from being "an instruction some threads execute" and closer to being an independent machine the kernel programs. Ampere's mma.sync is executed by a warp in lockstep, operands and results in that warp's registers. Hopper's wgmma widened issue to a 128-thread warpgroup, made execution asynchronous, and let operands come straight from shared memory — but accumulators still occupied the issuing threads' registers, chaining the compute warps to the output. Blackwell's fifth-generation instruction family, tcgen05, severs the last link: one thread issues the MMA, operands are described separately, and the accumulator lives in a new dedicated on-chip memory — TMEM — rather than the issuing threads' registers. Epilogue warps later load its values into registers for postprocessing. NVIDIA's own docs call the operation UMMA; completion is reported asynchronously through an mbarrier, exactly like a TMA copy. The tensor core is now, architecturally, a peer of the copy engine: you enqueue work, you get a signal when it's done.

Three generations, one direction: decouple the MMA from threads. The issue width collapses (32 → 128 → 1 threads) while the matrix tile covered by one instruction grows (16×8×16 → 64×N×16 → up to 128×256×16 in Blackwell's single-CTA mode, for FP16/BF16), and the accumulator migrates out of the register file entirely. The worked example below separates tile size from thread count.

What “the instruction grows” means: the same tile in 256 → 2 → 1 MMAs

An MMA (matrix multiply-accumulate) with shape \(M \times N \times K\) performs:

\[ D_{M \times N} = A_{M \times K}\,B_{K \times N} + C_{M \times N}. \]

\(M \times N\) is the output tile; \(K\) is the reduction depth per instruction. A \(16 \times 8 \times 16\) MMA multiplies a \(16 \times 16\) A tile by a \(16 \times 8\) B tile, updating 128 output values with a length-16 dot product each. “Grows” refers to this matrix work, not the instruction's encoded size or the number of issuing threads. In the FP16/BF16 comparison above, the output footprint grows while the reduction depth stays 16.

Hold the work fixed: update one \(128 \times 256\) output tile using one \(K=16\) slice. Choose Hopper's \(N=256\) variant and Blackwell's large single-CTA shape:

InstructionM × N × K per MMALogical MMAs for this sliceIssue threads per MMA
Ampere mma.sync16 × 8 × 16\((128/16)(256/8) = 256\)32 (one warp)
Hopper wgmma64 × 256 × 16\((128/64)(256/256) = 2\)128 (four warps)
Blackwell tcgen05.mma128 × 256 × 16\((128/128)(256/256) = 1\)1

Each row updates the same 32,768 output values. The counts are logical MMA operations across the output tile, not per-thread counts or a prescription for assigning warps. Hopper's \(N\) is a supported instruction-selected width, not an arbitrary runtime dimension; Blackwell also supports smaller shapes. Its single issuing thread submits the operation to the tensor-core hardware, which computes and accumulates asynchronously in TMEM — the thread does not calculate all those values itself.

256 → 2 → 1 instructions is not a 256× speedup. A larger instruction can occupy the tensor-core hardware over multiple cycles; throughput, data movement, and scheduling still determine runtime. These counts exclude operand loads, synchronization, and the epilogue.

One slice is not the full GEMM. For a full reduction dimension of 1024, these shapes need \(1024/16 = 64\) successive accumulation steps. And “per CTA” here means cta_group::1, not one instruction for the CTA's entire kernel: the 2-SM / CTA-pair mode instead lets two CTAs cooperate on an effective \(256 \times N\) output tile.

Why force this on kernel authors? Because Hopper's design had hit two walls. Registers: a warpgroup holding a large fp32 accumulator spends most of its register budget on it, capping how many roles (softmax, correction, epilogue) a kernel can staff — the constraint that shaped FA-3. Issue overhead: warp-wide issue burns instruction bandwidth that single-thread issue doesn't. Moving accumulation into dedicated storage with its own high-bandwidth datapath frees both — at the price of a new memory space you must explicitly manage.

TMEM: the accumulator gets its own address space

Tensor Memory is 256 KiB per SM, physically organized as a 2-D array of 128 lanes × 512 columns of 32-bit cells (a TMEM address encodes lane in its upper half, column in its lower). It is not a cache and not shared memory — it is scratchpad wired into the tensor core's datapath, and it comes with unusually explicit rules:

  • You allocate it yourself, at runtime, with tcgen05.alloc — in units of whole columns, a power of two, minimum 32 columns — and free it with tcgen05.dealloc. Forgetting to free is a real bug class: the SM cannot schedule new work needing TMEM until it's released. CUTLASS wraps this in a TmemAllocator; the CuTe DSL exposes the same object.
  • The MMA writes it; warps read it in quarters. Accumulators land in TMEM as (row of the tile → lane, column of the tile → columns). Threads access it only through dedicated copies (tcgen05.ld/st), and each warp of an epilogue warpgroup can touch only its own 32 of the 128 lanes — so draining a tile is inherently a 4-warp job, one warp per lane-quarter.
  • It is the new occupancy axis. A 128×256 fp32 accumulator occupies 256 columns — half of TMEM. Sizing accumulators, ping-pong buffers, and scale-factor storage against the 512-column budget is to Blackwell what register/smem budgeting is on Hopper.

Allocate vertically; pipeline horizontally. Each tile spans all 128 lanes but only N columns. Each grid block groups 32 lanes × 32 columns, not one cell; one physical cell is 32 bits (4 bytes), so \(128 \times 512 \times 4 = 256\) KiB. W0–W3 are warp indices within a warpgroup; highlighting one reader does not change the allocation or stop the other warps. Snapshots illustrate ordering, not cycle-accurate timing. The epilogue walkthrough unpacks the read path.

Reading a coordinate: in this FP32 layout, TMEM[40, 300] is row 40, column 300 — T1's local column 44 when \(N=256\), in warp 1's accessible lane band. Its address is (40 << 16) | 300 = 0x0028012c, a lane/column encoding, not a linear byte offset. Other MMA shapes and packed dtypes have their own layouts; this illustration deliberately uses the simple 128-row FP32 case. See NVIDIA's TMEM addressing and warp access restrictions.

The payoff for this bookkeeping is what it evicts: with accumulators gone, the register file returns to the rest of the kernel. Softmax scratch, dequant tables, multiple concurrent roles per CTA — the things Hopper kernels rationed registers for — get their budget back. That, more than raw FLOPs, is what "deeper warp specialization" means on this architecture.

tcgen05.mma: one thread programs the matrix engine

The instruction reads as a command packet, not arithmetic: a single thread presents an instruction descriptor (shape, dtypes, majorness) plus operand descriptors — A from shared memory or TMEM, B from shared memory, D an address in TMEM — and the hardware runs a \(128 \times N \times 16\) multiply (N up to 256 for 16-bit inputs; K deepens as dtypes narrow) entirely out-of-band. The issuing thread immediately moves on; a later tcgen05.commit binds all outstanding MMAs to an mbarrier that consumers wait on.

The structural consequence is easy to miss and defines the whole kernel: since one thread suffices, real kernels dedicate a single MMA warp — one warp, effectively one active thread — that does nothing but wait on "operands staged" barriers and enqueue MMAs. Compute issue, which on every prior architecture was the job of most of the CTA, is now a control loop the size of a rounding error. Everyone else moves data.

CTA pairs: two SMs, one MMA

Every tcgen05.mma carries a cta_group::1 or ::2 modifier. In the 2-CTA mode, two adjacent CTAs of a cluster (a "CTA pair," even rank leading) cooperate on a single MMA: the leader issues it, and the instruction reads operands from both CTAs' shared memories and writes both CTAs' TMEM — reaching an effective \(256 \times N\) tile spanning two SMs.

The win is not the bigger number — it's the traffic. With operand tiles split across the pair's shared memories, each tile is loaded from HBM and staged in smem once per pair instead of once per CTA: shared-memory capacity and bandwidth per output element are halved. That matters precisely where smem bandwidth is the binding constraint — the FA-4 backward pass, bound by smem rather than tensor cores, takes its decisive win from exactly this mode; dense-GEMM kernels ship in both flavors (CUTLASS's …1Sm…/…2Sm… dispatch policies, cuTile's num_ctas=ct.ByTarget(sm_100=2)).

The sm_100 kernel shape: everyone moves data

Put the pieces together and the Hopper producer/consumer picture reorganizes. Consumers no longer exist in the old sense — a compute warpgroup need not hold the long-lived MMA accumulator in registers. The CTA becomes a set of small specialized crews around two asynchronous engines (TMA and the tensor core), with epilogue warps loading register fragments for the final scalar/vector work:

MMA issue is control work; epilogue warps still compute. A load warp drives TMA; the MMA warp's single thread enqueues UMMAs against smem-stage barriers; a 4-warp epilogue warpgroup (one warp per TMEM lane-quarter) transforms and stores the previous tile's accumulator while the current one fills — the TMEM ping-pong from the figure above. Persistent kernels add a scheduler warp fetching the next tile assignment. Compare the Hopper timeline on the CUTLASS page: same choreography, but the "consumer" role has split into a one-thread issuer and an epilogue that performs both data movement and postprocessing.

Inside the epilogue: load, wait, transform, convert, store

Use the CUTLASS running example: scale the accumulator, add the scaled residual and per-column bias in FP32, apply ReLU, then round to BF16. The matrix product is complete in TMEM; it is not yet the final stored tensor. For one completed 128×N tile, the path is:

Why stage in shared memory if the result is already in registers? A TMEM load layout and a good global-store layout need not assign the same values to neighboring threads. A shared-memory exchange can change that distribution, and a TMA store takes its source from shared memory. A direct register-store path can avoid this stage when its mapping is already suitable. Neither choice changes the epilogue's mathematical expression; see the CuTe layout view.

Two different reuse points. A TMEM slot may be overwritten once all consumers have finished the TMEM loads they need and the kernel signals that handoff — even if they are still computing or storing from register copies. Shared-memory output staging has its own later reuse point: an asynchronous store must no longer be reading it. A single warp finishing is not permission to recycle a slot that other warps still need.

The tradeoff is therefore not “epilogues are free.” Bias/residual reads, conversion instructions, register pressure, and optional smem traffic can become the bottleneck next to fast tensor cores. Fusion removes the global accumulator temporary, not these costs; the fused-versus-unfused traffic model counts exactly what disappears.

Two habits of thought carry over anyway: the pipeline is still governed by mbarriers around smem stages, and occupancy is still a budget game — just with TMEM columns joining registers and shared memory as the resources being rationed (deep-pipeline, one-or-two-CTA-per-SM configurations are the norm). And note what got harder: with tensor-core FLOPs doubled but smem bandwidth and SFU throughput not, the surrounding scalar work — softmax being the canonical case — is now the part most likely to be your bottleneck. That asymmetry, and the FMA-pipe exponential trick it forced, is the subject of the FA-4 section.

Block-scaled MMA: quantization enters the instruction

Blackwell's second headline is that block quantization stops being epilogue/prologue software and becomes an operand semantics of the MMA. The block_scale instruction kinds compute

\[ D = C + (A \cdot SF_A)\,(B \cdot SF_B), \]

where the scale-factor tensors assign one FP8-type scale to every 16 or 32 elements of \(A\) and \(B\) along K, applied by the hardware inside the multiply. The supported formats:

FormatElementScale dtypeBlock size (K)Notes
MXFP8 / MXFP6 / MXFP4E4M3/E5M2 · FP6 · E2M1UE8M0 (power of two)32OCP Microscaling standard; mixable per operand (e.g. MXFP8 acts × MXFP4 weights)
NVFP4E2M1UE4M3 (fractional)16NVIDIA's format: finer blocks + a per-tensor FP32 scale — the 4-bit pretraining recipe

For the kernel author, block scaling adds one genuinely new duty: the scale-factor tensors are operands living in TMEM, with their own prescribed layouts — so the mainloop grows a second data path (TMA scale factors to smem, copy into TMEM alongside the accumulator budget) and the epilogue typically grows the reverse: computing per-block amax and quantizing the output so the next GEMM can consume it. CUTLASS's CollectiveBuilder generates all of this from a dtype choice (nv_float4_t, mx_float8_t…); cublasLt exposes the same paths as block-scaled matmul APIs. The 4× rate over Hopper FP8 is why every 2025-26 frontier stack — NVFP4 pretraining, MXFP4 serving — is racing down this path.

The one-paragraph takeaway

A Blackwell kernel is a small control program coordinating two asynchronous engines through barriers: TMA feeds shared memory, one thread feeds the tensor core, accumulators live in a 512-column scratchpad you allocate yourself, two SMs can pool their staging for one multiply, and quantization scales ride inside the MMA. The SIMT machinery is still there — but in the mainloop of a peak kernel, threads have become the I/O system of the tensor core, which is the logical endpoint of the trajectory this whole shelf has been tracing.
