Systems · Cross-operator execution

Megakernels

From GPU-resident task runtimes to TPU whole-decoder pipelines: keep useful work moving across operator boundaries, while taking ownership of dependencies, memory lifetimes, and scheduling.

Evidence reviewed November 15, 2026. A curated, dated landscape—not an exhaustive survey or a continuously updated leaderboard. Results below are author-reported, not reproduced here; the interactive model is illustrative.

Prerequisites: CUDA Graphs explains launch replay; CUTLASS scheduling explains persistent tiles and partial waves; MoE parallelism explains dispatch, experts, and combine. This page owns what changes when those operations share an execution runtime. For training, start with the backward graph, memory ledger, and FSDP integration.

1 · Start with the 2026 developments

The field has moved beyond the 2025 single-sequence Llama demonstration. The strongest recent lessons are serving integration, training-scale communication overlap, hardware-specific scheduling, and rapid optimization. They do not converge on one universal interpreter or memory allocator.

2 · What “megakernel” means

A megakernel keeps a substantial multi-operator computation inside one device program, so scheduling and data movement can cross boundaries that would otherwise separate kernels. On GPUs, this often means persistent thread blocks executing a task graph. On TPU, it can instead mean a sequential Pallas program with explicitly overlapped DMA. The shared idea is cross-operator control, not a particular GPU interpreter.

TechniqueUnit being optimizedBoundary that remains
Ordinary fusionA small operator group, such as GEMM plus activation.Other operators remain separate; the main gain may be avoided intermediate reads/writes.
CUDA GraphsSubmission/replay of a recorded graph.Kernel nodes remain kernels. Graph replay does not itself create tile-level producer/consumer synchronization.
Persistent GEMMTiles of one matrix operation or grouped operation.Persistence alone does not imply a multi-operator runtime.
MegakernelA decoder, forward pass, MoE block, or other substantial multi-operator region.Explicit internal dependencies, buffers, and host/application boundaries still exist.
Persistent serving engineWorker/process/model-state lifetime across requests or experiments.Its forward pass may execute many kernels; engine persistence is not kernel persistence.

“One launch” is scoped: per participating device and per selected region. A decode megakernel need not include prefill, sampling, or the whole autoregressive loop. A training megakernel need not include routing setup, every model layer, weight quantization, optimizer updates, or checkpointing.

Also avoid a false dichotomy: independent kernels can overlap on streams, and programmatic dependent launch can overlap preparation of dependent kernels. The target is unnecessary synchronization and pipeline gaps in the actual execution graph—not a claim that CUDA always serializes every kernel on the device.

3 · Replace operator barriers with actual dependencies

Suppose a GEMM produces tiles \(Y_i\), followed by an all-reduce. A coarse schedule waits for the entire GEMM. A finer schedule can start reducing tile \(i\) once every participating rank has produced its required contribution, while other tiles are still computing. Reducing synchronization scope does not remove the mathematical dependency.

1. Lower

Split operators into tasks with explicit input/output regions and dependencies.

2. Place

Assign predictable work; reserve queues for runtime-dependent attention or routing.

3. Execute

Prefetch independent weights, wait for valid activations, compute, and finish stores.

4. Publish

Signal completed regions with the required visibility; release buffers and successors.

This exposes three opportunities: fill a partially idle wave with other ready work; prefetch the next operation's immutable weights before its activations arrive; and overlap computation with communication at a smaller granularity. None is automatic if the next task is not ready or all tasks contend for the same saturated resource.

Conceptual worker protocol — not executable CUDA:

task = select_ready_task_or_prefetchable_candidate()
reserve_buffers(task)
start_independent_weight_copies(task)
wait_for_required_input_regions(task, current_epoch)
wait_for_copy_completion(task)
compute(task)
complete_output_stores(task)
publish_output_readiness(task, required_memory_scope)
release_buffers_after_all_users_and_async_operations_finish(task)

The host can prepare a schedule ahead of time; GPU-resident execution does not require every scheduling decision to happen dynamically on the GPU. Likewise, one kernel does not keep all intermediate tensors in registers or SRAM: global-memory activations and readiness counters remain important in the HazyResearch and Cohere designs.

4 · Current designs disagree in useful ways

Cohere: a task ABI plus a real serving boundary

The September serving-engine report uses a common task calling convention: fixed-size descriptors, a common block shape, and producer/consumer/storer roles. Static waves fix most placement; attention and MoE claimers steal from stage-specific queues because live sequence lengths and routing change task counts.

North Mini Code's parallel attention and FFN branches offer unusually strong opportunities to fill idle SMs with ready work. That is a model-architecture advantage, not a dependency pattern to assume in a sequential attention-then-MLP transformer.

A revision to the foundational recipe: Cohere reports rejecting shared-memory paging because its bookkeeping and bugs outweighed the gains. It instead uses per-op static shared-memory layouts, carries pipeline state across same-type GEMM tiles, and prefetches immutable weights before activation waits. Paging is a design option, not a megakernel requirement.

The serving boundary is equally important. Python admits requests and runs prefill; a native C++ thread drives decode. Python parks decode before changing batch/KV state, then resumes it with a matching schedule. The pinned launch ABI carries separate instruction buffers, context variants, dynamic queue metadata, and barrier pointers. An OpenAI-compatible endpoint does not make this a general-purpose replacement: the release is model-specific, H100/BF16-only, and tuned for batches 1–8.

Mixture-of-Kittens: training and communication are first-class

MoK's September paper targets scale-up NVLink domains, not just launch-bound inference. Its MoE forward/backward designs coordinate shared and routed expert computation with token transfers. A reusable device-generated schedule supports pull-based dispatch and push-based combine, with corresponding reverse operations during backward.

Two sizes have different jobs: a minibatch sets computation/communication overlap granularity; a macrobatch ring buffer bounds token-buffer storage. Slot reuse must wait for all consumers; backward may recompute forward intermediates overwritten by ring reuse. This addresses data-dependent token counts without a host round-trip to allocate an exact-sized token buffer.

Compute and communication get tunable SM allocations. The implementation report also describes Blackwell Cluster Launch Control so work can yield to higher-priority kernels needed for inter-rack communication. A permanently resident grid that monopolizes resources can lose end-to-end even when its isolated MoE timing improves.

Keep the API scope honest: schedule construction and optional weight prequantization are separate from the fused forward/backward paths. The reported 1.41× production throughput improvement includes an entire training stack; the 2.37× figure is a layer-level MXFP8 forward result. Neither proves equal gains on another topology, routing distribution, or model.

TPU: the concept does not require SM task queues

Inferact's Pallas design expresses the decoder as a grid-less program, using scoped VMEM allocations and explicit asynchronous HBM-to-VMEM copies across layer boundaries. On the targeted TPU v7 hardware, each TensorCore has a 64 MiB software-managed VMEM pool. Activations can remain resident while upcoming weight transfers are staged; collectives and buffer lifetimes are part of the same program.

For the reported Kimi K3 setup, 16 physical chips expose 32 TensorCore device ranks; the repository's 32-device launch is not a 32-chip result. The topology and attention/expert partitioning are tuned together. The current October 15 source snapshot also includes Qwen3.8 and Muse-Spark-Open paths; their supported modes should not be inferred from the original Kimi benchmark.

The 709-token/s result includes DSpark speculation at a declared acceptance length. The reported roughly 1.4–2× non-speculative decode advantage also compares different accelerators and software stacks. Neither number isolates the causal contribution of megakernel fusion. A CPU interpreter can check equations, but cannot validate TPU DMA ordering, VMEM capacity, lowering, or hardware speed.

MPK: compiler-generated graphs with hybrid dispatch

The June 2026 revision lowers operators to SM-level tasks and events, fuses redundant events, and normalizes/linearizes the task graph for cheap dispatch. Predictable tasks can be queued ahead of time; variable-duration work uses just-in-time dispatch. Workers prefer ready JIT tasks over blocked AOT work, balancing dispatch cost against load imbalance.

Unlike the June 2025 announcement's roadmap, the revised paper describes MoE support, continuous batching, paged attention, and batch-specialized graphs selected at runtime. Its evaluation still uses controlled offline traffic. Capability descriptions and benchmark coverage are different kinds of evidence.

Fleet: “any free worker” can ignore the memory hierarchy

The Fleet preprint adds chiplet-scoped tasks and per-chiplet scheduling on AMD MI350. Workers within an XCD cooperate on tiles with shared weight locality, while hierarchical signaling distinguishes local coordination from cross-chiplet visibility. This improves cache reuse within the working set; it does not imply that a model's weights fit permanently in chiplet L2.

The general lesson is to match task placement and synchronization scope to the actual memory hierarchy. Do not transfer an H100 round-robin policy, AMD fence sequence, or TPU collective topology unchanged to another device. Treat Fleet as a 2026 preprint; a repository's future conference citation is not evidence of an accepted publication.

5 · Training: backward is a different dependency graph

Small-batch decode primarily exposes weight-streaming and boundary costs. Training adds saved activations, input and parameter gradients, gradient accumulation, distributed reductions, and optimizer state. Large dense GEMMs can already be compute-efficient; fine-grained MoE can still be IO-, communication-, or scheduling-bound. The opportunity is to shorten the training critical path, not simply to reduce the kernel count.

A practical scope is one distributed layer or operator region, with separate forward and backward implementations. Attention, router setup, loss, optimizer updates, and checkpointing can remain outside that region. A forward-only fused MoE implementation is not a training backend until its backward, saved-state contract, and distributed integration exist.

Backward branches: dgrad is not wgrad

Consider one bias-free SwiGLU expert, or a dense FFN, using row-major activations. Let \(X\in\mathbb{R}^{T\times D}\), \(W_u,W_g\in\mathbb{R}^{D\times I}\), and \(W_d\in\mathbb{R}^{I\times D}\). Here \(T\) is the number of tokens assigned to this expert; in MoE it varies at runtime. With \(s=\mathrm{SiLU}\):

\[ U=XW_u,\quad V=XW_g,\quad H=s(V)\odot U,\quad Y=HW_d. \] \[ G=\frac{\partial L}{\partial Y},\qquad dH=GW_d^\top,\qquad dW_d=H^\top G, \] \[ dU=dH\odot s(V),\qquad dV=dH\odot U\odot s'(V), \] \[ dX=dU\,W_u^\top+dV\,W_g^\top,\qquad dW_u=X^\top dU,\qquad dW_g=X^\top dV. \]

Dgrad means the input/activation gradients that continue backward through the model; wgrad means parameter gradients consumed by accumulation, reduction, and the optimizer. The equations create branches, not one mandatory order in which every wgrad finishes before dgrad can continue.

BranchNeedsWhat completion makes possible
\(G\rightarrow dH\rightarrow(dU,dV)\rightarrow dX\)Forward-version weights and saved or reconstructed gate/up activations.Return token gradients to their source ranks; continue earlier-layer backward when the surrounding runtime exposes readiness.
\((H,G)\rightarrow dW_d\)Gated activations and this expert's output gradient.Accumulate the down-projection parameter gradient. It does not depend on completing \(dX\).
\((X,dU,dV)\rightarrow(dW_u,dW_g)\)Original expert inputs and gate/up gradients.Accumulate the remaining parameter gradients; release saved inputs only after their final reader.

Ignoring elementwise work, the three forward GEMMs cost about \(6TDI\) FLOPs; the six backward GEMMs cost about \(12TDI\). Forward/dgrad GEMMs vary along the token/output-row dimension, whereas wgrad reduces over tokens. A forward tile size, queue order, or compute/communication SM split is therefore not automatically a good backward configuration.

In the MoK backward schedule, reverse-combine supplies output gradients, dgrad produces expert input gradients, and reverse-dispatch returns them. Wgrad can overlap the final reverse-dispatch because the token-gradient transfer does not depend on it. MoK delays weight-gradient GEMMs until dgrads for the minibatches are ready, also preserving a larger token reduction for numerical behavior. This is a particular schedule, not a universal instruction to defer all wgrads: doing so can delay FSDP reduce-scatter and lengthen the final training tail.

Mathematical readiness is not framework readiness. A monolithic custom autograd backward that returns all gradients together does not automatically let PyTorch schedule the preceding layer as soon as an internal \(dX\) tile is ready. Cross-layer overlap requires an execution interface that exposes the relevant completion events. Intra-kernel reverse-dispatch overlap alone does not demonstrate that capability.

Activation lifetime is a scheduling constraint

Fusion may remove temporary IO while leaving long-lived saved state untouched. For \(N\) original tokens, top-\(K\) routing, and width \(D\), one materialized BF16 expert-expanded tensor costs \(2NKD\) bytes. An illustrative \(N=8192,\ K=8,\ D=4096\) tensor is 512 MiB, before counting other layers or gradients. Avoiding a retained copy and bounding a transient buffer solve different problems.

Memory classLifetime / release conditionOptimization and its cost
Inputs and routing metadataRetain until all backward gathers, wgrads, and any replay have consumed them.Gather directly from original inputs rather than save repeated expert-expanded inputs. Preserve forward routing and any stochastic state needed for equivalent replay.
Gate/up preactivations and gated outputNeeded by activation derivatives and parameter gradients.Save selected intermediates; reconstruct cheap elementwise results or replay missing GEMMs. Replay saves memory but can add FLOPs, weight reads, and distributed parameter materialization.
Dispatch/combine ring and scratchA slot cannot be reused until every local/remote consumer and asynchronous transfer is done.Fixed capacity bounds transient token storage. It does not bound all saved activations, gradients, or optimizer state.
Unsharded/prefetched parametersValid from all-gather completion through the last compute or asynchronous reader.Earlier prefetch increases overlap and peak memory. Resharding saves memory but may require another all-gather for backward/replay.
Gradients and optimizer statePersist through required accumulation/reduction and the update.Shard and reduce at the intended boundaries; kernel fusion does not itself eliminate these allocations.

Two distinct solutions: MoK uses ring-aware replay inside backward to reconstruct intermediates overwritten by forward's ring reuse. SonicMoE instead demonstrates how algebra and IO-aware kernels reduce saved state without replaying the forward GEMMs: retain original inputs and up/gate preactivations, regenerate the gated activation during backward, and avoid retaining every expert's full-width output for router gradients.

The router-gradient identity makes the latter concrete. For one token, let \(y_e=h_eW_{d,e}\), combined output \(o=\sum_e a_e y_e\), and \(g=\partial L/\partial o\). Then:

\[ \frac{\partial L}{\partial a_e} =\langle g,y_e\rangle =\langle gW_{d,e}^{\top},h_e\rangle. \]

This avoids retaining \(y_e\) solely for that gradient. Use the unweighted projection \(gW_{d,e}^{\top}\); the expert activation gradient contains the additional factor \(a_e\), so substituting it directly gives the wrong result. Chain the coefficient gradient through router normalization/projection separately. No division by a potentially zero routing weight is necessary.

SonicMoE's described computation still uses three forward and five backward kernels. Its reported 45% activation-memory reduction is a scoped MoE result, not proof that fewer kernels or one megakernel is necessary for memory efficiency. Its token-rounding proposal is a separate routing change; do not count it as a semantics-preserving scheduling optimization.

FSDP overlap must survive the fused region

Expert-parallel dispatch exchanges tokens within an EP group. FSDP exchanges parameter shards and gradients across the relevant data-parallel/sharding group. These groups and fabrics need not coincide. A faster intra-rack MoE region can still slow training if it prevents inter-rack parameter or gradient communication from progressing.

The PyTorch 2.15 FSDP2 contract provides the outer schedule: all-gather a parameter group before use; optionally reshard after forward; re-gather for backward when needed; and reduce-scatter completed gradients. Each fully_shard application determines a communication group. Per-block grouping exposes overlap; grouping the entire model into one unit delays those opportunities. See TorchTitan's FSDP2 integration for the surrounding model structure.

Illustrative backward dependencies — not a measured timeline:

compute:    [backward B3]  [backward B2]  [backward B1]
weight AG:  [prefetch B2]  [prefetch B1]
grad RS:    start RS(B3) when its group gradients are ready,
            then RS(B2), then RS(B1), respecting collective order

AG completion  -> first read of gathered weights
last reader    -> release gathered storage
wgrad completion + accumulation policy -> reduce-scatter
reduction/update prerequisites         -> optimizer step

Three integration requirements follow:

  1. Preserve parameter and hook boundaries. Call through the framework's supported module/unshard interface; do not silently run a cached whole-model pointer schedule across multiple FSDP groups whose weights may be reshaped, freed, or re-gathered. Keep the forward parameter version valid for backward.
  2. Leave communication resources and scheduling opportunities. A separate CUDA stream does not reserve SMs or guarantee overlap. MoK uses Blackwell CLC to yield work to higher-priority communication kernels. Other hardware needs an explicit supported strategy; stream priority alone is not a universal preemption mechanism.
  3. Honor gradient readiness and accumulation policy. Delayed wgrads postpone reduce-scatter; earlier all-gathers extend parameter lifetimes. Accumulating microbatches or suppressing intermediate synchronization changes reduction timing and memory. Do not expose partial gradients as complete or update weights while old-version reads remain outstanding.

A useful starting boundary is one FSDP-managed block containing a fused MoE region, leaving inter-block all-gather/reduce-scatter scheduling to the framework. It is a design starting point, not a claim that an arbitrary custom kernel can be dropped into FSDP without verifying hooks, streams, aliases, and completion ordering.

For a normalized baseline step, if fraction \(f\) improves by factor \(s\) and the change adds unhidden overhead \(r\), a simple Amdahl model gives:

\[S_{\mathrm{step}}=\frac{1}{(1-f)+f/s+r}.\]

For example, doubling a region that occupies half the step gives only \(1.33\times\) whole-step speedup when \(r=0\). This is an illustrative serial-fraction model; real overlap changes the critical path. Do not plug a forward-only speedup into the whole forward-plus-backward fraction.

6 · Finer tasks are not always faster

Consider a deliberately simplified two-stage pipeline: total compute time \(C\), total communication time \(D\), and \(n\) equal chunks. Assume the two stages can overlap without bandwidth/resource contention, and each chunk adds an unhidden coordination cost \(h\). Then:

\[ T_{\mathrm{serial}} = C+D,\qquad T_{\mathrm{pipe}}(n) = \frac{C+D}{n} +(n-1)\frac{\max(C,D)}{n}+nh = \max(C,D)+\frac{\min(C,D)}{n}+nh. \] \[ n^*_{\mathrm{continuous}}=\sqrt{\frac{\min(C,D)}{h}}\quad(h>0). \]

Smaller chunks shorten ramp/drain, but add more coordination. Choose an integer near \(n^*\) within the allowed range. When \(h=0\), the toy model improves toward the bottleneck-stage limit as chunks increase. Real kernels add partial waves, smaller GEMMs, queue contention, routing skew, and buffer constraints, so this is a reasoning aid—not an autotuner or an estimate of a named system.

Pipeline latency equals max(C,D) + min(C,D)/n + n times coordination overhead.
Pipelined + coordination Serialized C + D

Removing boundaries moves the optimization problem; it does not remove overhead. Compute is fixed at 800 µs. The curve relaxes chunk count continuously; the readout searches integer counts 1–64. Common launch costs are omitted. The serial reference has no per-chunk coordination, so one pipelined chunk is slower by \(h\). These are synthetic numbers, not GPU/TPU benchmarks.

MoK provides a practical counterpart: communication that is too fine-grained repeatedly interrupts efficient Tensor Core work, while overly coarse transfer batches delay the first compute and final combine. Tune task/transfer size with the compute/communication SM split, not as independent constants.

8 · Evaluate the whole system, not the slogan

Start with a profile that distinguishes host submission, kernel-switch/pipeline gaps, low occupancy, memory bandwidth, and exposed collectives. Megakernels are promising when those boundaries leave useful resources idle; fewer launches do not repair slow GEMMs or remove irreducible memory traffic.

  1. Freeze the comparison: source revisions, checkpoint, precision, hardware count and topology, backend versions, prompt/output distributions, routing skew, concurrency, and sampling/speculation policy.
  2. Separate metrics: kernel/forward time, per-user inter-token latency, aggregate accepted tokens/s, prefill/TTFT, tail latency under arrivals, peak memory, and end-to-end training throughput. Include schedule/reset/sampling work where the claimed scope requires it.
  3. Isolate changes: use graph-enabled and tuned baselines; ablate scheduling, communication, fusion, quantization, and parallelism rather than attributing their combined gain to one mechanism.
  4. Exercise boundaries: ragged sequences, skewed experts, empty/finished slots, graph/batch transitions, ring wraparound, and intended multi-device communication. Compare numerical outputs and gradients at declared tolerances.
  5. Measure integration: whether prefill blocks decode, whether the kernel prevents other communication from progressing, and whether compilation/tuning cost amortizes before traffic changes again.

Cohere makes the scope issue concrete: the 1.58× decode benchmark disables prefill and uses a synthetic KV cache; the real-prompt serving runs include prefill and report smaller gains. Generated token counts differ between engines, so throughput ratios are not automatically ratios of time to complete identical outputs.

The newest connection: optimizing the optimizer's turnaround

Together Compiler retains an engine while agents replace candidate forward passes, using few-layer screening and more representative many-layer measurements. Engine hot reload still entails graph recapture; it is not replaying an unchanged graph with magically replaced code.

This connects two distinct time scales: megakernel design improves execution, while persistent experiment infrastructure improves how rapidly useful designs can be found. TKCC's reported 252× experiment throughput, up-to-2.6× frontier-model TPS, and up-to-1.7× result against Llama-1B megakernels are different measurements. None should be multiplied together.

Inferact separately reports sub-90-second cold compilation for its hand-scheduled TPU decoder versus 30-plus-minute compilation that large XLA model programs can incur. That is a development-loop observation with different programs, not a serving speedup or a universal Pallas/XLA benchmark.

Current decision rule: retain competitive operator implementations, identify specific cross-operator waste, then choose the least complex runtime that removes it. Static waves plus local queues, a compiler-generated graph, chiplet cooperation, and a sequential TPU pipeline are alternatives—not successive levels of an inevitable single design.
