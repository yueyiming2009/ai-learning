CUTLASS — The GEMM Factory

NVIDIA's open C++ template library that decomposes matrix multiply into composable, compile-time pieces — the tiling hierarchy, collectives and warp specialization, stream-K scheduling, and epilogue fusion that define what "peak GEMM" means.

Pre-reading: CUDA — The SIMT Programming Model, whose shared-memory tiled matmul is the seed this entire library grows from. GPU Kernels in CuTe DSL covers the layout algebra that became CUTLASS's foundation in 3.x — this page covers the library built on it: the GEMM decomposition, the kernel architecture, and the machinery around a single tile's multiply.

Why CUTLASS exists: an open, decomposable cuBLAS

cuBLAS gives you peak GEMM as a sealed box: one call, no visibility, no extension points. That's fine until you need what a closed box can't do — fuse your epilogue into the kernel tail instead of paying another HBM round-trip, run a dtype or layout combination cuBLAS hasn't shipped, batch thousands of small expert GEMMs for MoE, or simply see how peak is achieved. CUTLASS (CUDA Templates for Linear Algebra Subroutines, open-sourced December 2017) is NVIDIA's answer: the same performance ambition, delivered as a hierarchy of composable C++ templates that you can instantiate, customize, and read. On mainstream shapes it lands within a few percent of cuBLAS — occasionally ahead on shapes cuBLAS hasn't prioritized — while remaining a construction kit rather than a product.

Its role in the ecosystem has steadily grown: it is the reference implementation of "how NVIDIA intends this hardware to be programmed," the substrate under FlashAttention-3, TensorRT-LLM, vLLM's FP8 GEMMs and much of PyTorch's specialized-op inventory — and, since 3.0, the home of the CuTe abstractions that reorganized the whole library.

The one idea: a hierarchy of tiles, each matched to a hardware level

The CUDA page's tiled matmul tiles once: block-sized tiles staged in shared memory. CUTLASS's founding observation is that peak GEMM is that same idea applied at every level of the machine, with the tile sizes chosen so each level's data reuse saturates the corresponding storage:

Problem

M × N × K

Carved into a grid of output tiles; a tile scheduler assigns tiles to CTAs — in HBM.

→

CTA tile

e.g. 128×128 ×(K/32)

One block's output; K marched in slices staged through shared memory, multi-stage pipelined.

→

Warp tile

e.g. 64×64

One warp('s group)'s slab of the CTA tile; accumulators live in registers (TMEM on Blackwell).

→

Instruction

mma 16×8×16 · wgmma 64×N×16

One tensor-core op — the only level that does arithmetic. Everything left of here exists to feed it.

Every level is the same trick at a different radius. Each tiling multiplies data reuse by its tile width, buying enough arithmetic intensity to hide the next-slower memory: HBM → smem → registers → tensor core. CUTLASS is, at heart, a library of these nested loops with every tile size exposed as a template parameter — plus everything required to keep the pipeline full.

Getting the sizes right is a resource-budget puzzle — the CTA tile bounded by shared memory, the warp tile by registers, all of it by occupancy — which is why "a GEMM" in CUTLASS is not one kernel but a family of thousands of instantiations, and why the library ships a profiler to search them.

Two eras of the same library

CUTLASS 2.x organized the code the way the figure reads: nested threadblock:: / warp:: / thread:: templates, one per level. The public API is disarmingly simple — a GEMM is a type, and running one looks like this (from examples/00_basic_gemm):

using ColumnMajor = cutlass::layout::ColumnMajor;
using CutlassGemm = cutlass::gemm::device::Gemm<
    float, ColumnMajor,     // A: dtype, layout
    float, ColumnMajor,     // B
    float, ColumnMajor>;    // C  (tile sizes, stages: sensible defaults)

CutlassGemm gemm_op;
CutlassGemm::Arguments args({M, N, K},          // problem size
                            {A, lda}, {B, ldb}, // sources
                            {C, ldc}, {C, ldc}, // C in, D out
                            {alpha, beta});     // epilogue: D = αAB + βC
cutlass::Status status = gemm_op(args);         // launches the kernel

CUTLASS 3.x (2023) rewrote the internals around CuTe: the ad-hoc index math at every level became layouts and atoms, and the level hierarchy was regrouped into a cleaner set of concepts built for Hopper's asynchronous hardware. The 2.x-style API remains; underneath it, the machinery changed completely. CUTLASS 4.x (2025) then added the Python face — the CuTe DSL — over the same concepts; this page stays on the C++ side.

The 3.x architecture: four layers, and kernels as types

LayerType (canonical)Owns
Devicedevice::GemmUniversalAdapterHost-side API: argument checking, workspace, launch.
Kernelkernel::GemmUniversalThe grid: composes a mainloop + an epilogue with a tile scheduler (which CTA gets which tile — persistent, stream-K).
Collectivecollective::CollectiveMma, CollectiveEpilogueEverything one CTA(-cluster) does: the smem-pipelined mainloop, the epilogue. The unit of reuse and of architecture specialization, selected by dispatch policies.
CuTetiled MMA / tiled copy over atomsThread↔data layouts and the actual instructions — the atom table.

Because assembling four layers of templates by hand is brutal, 3.x's front door is the CollectiveBuilder: name the architecture, dtypes, tile and cluster shapes, and let Auto policies pick stages and schedule (from examples/48_hopper_warp_specialized_gemm, lightly trimmed):

using ArchTag       = cutlass::arch::Sm90;          // Hopper
using OperatorClass = cutlass::arch::OpClassTensorOp;
using TileShape     = Shape<_128,_128,_32>;         // CTA tile (M, N, K)
using ClusterShape  = Shape<_4,_2,_1>;              // CTAs per cluster (TMA multicast)

using CollectiveEpilogue = typename cutlass::epilogue::collective::CollectiveBuilder<
    ArchTag, OperatorClass, TileShape, ClusterShape,
    cutlass::epilogue::collective::EpilogueTileAuto,
    ElementAccumulator, ElementAccumulator,
    ElementC, LayoutC, AlignmentC,                  // C: source
    ElementC, LayoutC, AlignmentC,                  // D: destination
    cutlass::epilogue::collective::EpilogueScheduleAuto>::CollectiveOp;

using CollectiveMainloop = typename cutlass::gemm::collective::CollectiveBuilder<
    ArchTag, OperatorClass,
    ElementA, LayoutA, AlignmentA,
    ElementB, LayoutB, AlignmentB,
    ElementAccumulator,
    TileShape, ClusterShape,
    cutlass::gemm::collective::StageCountAutoCarveout<   // smem stages = what's
      static_cast<int>(sizeof(typename CollectiveEpilogue::SharedStorage))>, // left
    cutlass::gemm::collective::KernelScheduleAuto>::CollectiveOp;

using GemmKernel = cutlass::gemm::kernel::GemmUniversal<
    Shape<int,int,int>,                             // runtime problem shape
    CollectiveMainloop, CollectiveEpilogue>;

using Gemm = cutlass::gemm::device::GemmUniversalAdapter<GemmKernel>;

Running it is a fixed four-step ritual: build an Arguments struct (shape, pointers, strides, epilogue scalars), can_implement(args), initialize(args, workspace), run(). The thing to absorb is that everything above Arguments is a type: tile sizes, stage counts, schedules, dtypes are compile-time, so the composed kernel has zero runtime dispatch — and each distinct configuration is a separate compilation. Both of the library's signatures follow from this one choice: its performance, and its build times.

Inside a Hopper collective: warp specialization

What the builder actually selects on Hopper is a warp-specialized mainloop — the design that asynchronous hardware forced. TMA moves descriptor-addressed tiles and signals transaction barriers; wgmma multiplies from shared memory asynchronously. So the collective splits the CTA into roles: producer warps that only issue TMA copies, and consumer warpgroups that only run MMAs, handing buffers around a multi-stage shared-memory ring guarded by barriers — a hardware-enforced producer/consumer queue:

The mainloop as an assembly line. Producer warps stream K-slices into a ring of shared-memory stages while consumer warpgroups drain them into accumulators; after the ramp-up stage, loads and MMAs fully overlap. The pingpong schedule sharpens this further: two consumer warpgroups alternate tiles, so one's epilogue (the seg-epi tail) hides under the other's mainloop. This diagram is what the CUDA page's load→__syncthreads()→compute rhythm becomes when both sides go asynchronous.

The ClusterShape plugs in here too: CTAs in a cluster share A- and B-tiles via TMA multicast, cutting HBM traffic by the cluster width. On Blackwell the same collective concept re-specializes again — tcgen05 MMAs accumulate in dedicated tensor memory (TMEM), CTA pairs cooperate on one MMA, and block-scaled dtypes (NVFP4/MXFP8) enter the mainloop — new dispatch policies, same architecture. That is precisely the churn the collective layer exists to absorb, and the reason Tile IR makes the same bet one level higher.

Schedulers: split-K, stream-K, and the tail problem

One CTA per output tile is only load-balanced when the tile count comfortably exceeds (and divides into) the SM count. Real shapes betray you twice: skinny-K problems yield too few tiles to fill the GPU, and any tile count that isn't a multiple of the SM count leaves a partially idle final wave — the quantization tail, ruinous when there are only a few waves. The kernel layer's tile scheduler is the pluggable fix:

  • Split-K: split the K-reduction across several CTAs per output tile; partial accumulators combine through workspace (or atomics). More parallelism, at the cost of a reduction pass.
  • Stream-K: abandon tile-per-CTA entirely — launch exactly as many persistent CTAs as SMs and hand each an equal span of MMA work, wherever tile boundaries fall; CTAs sharing a tile reconcile partials. The tail wave disappears by construction, and one kernel covers the shape space that previously needed a zoo of heuristics.

Persistent scheduling is also what the cuTile persistent matmul and Triton's persistent kernels imitate at their altitude — CUTLASS is where the pattern was industrialized.

Epilogues: the free real estate at the end of a GEMM

When the mainloop finishes, the result is sitting in registers — and anything you compute now is free of HBM traffic, while anything you defer to a separate kernel costs a full round-trip of the output. That makes the epilogue the single most valuable fusion site in deep learning: bias add, activation, residual add, per-channel scales, and the quantize-to-FP8-plus-amax pattern of low-precision serving all belong there.

CUTLASS grew from fixed epilogues (LinearCombination: \(D = \alpha AB + \beta C\)) to the Epilogue Visitor Tree (EVT): you describe the post-GEMM computation as a small expression tree over named nodes — accumulator in, auxiliary tensor loads, elementwise ops, reductions, stores out — and the epilogue collective compiles the tree into the kernel tail, with its own tiling and smem staging. It is a compiler for kernel tails, and it's how one GEMM instantiation serves the dozens of fusion variants an inference stack needs. Beyond epilogues, the same library machinery covers grouped GEMM (one launch, thousands of differently-shaped expert GEMMs — the MoE workhorse), convolution as implicit GEMM, and 2:4 structured sparsity.

In practice: the profiler, the build times, and when to reach for it

Since every configuration is a type, finding your kernel is a search problem. The library embraces this: cutlass_profiler enumerates instantiations (filtered at CMake time — building broadly means thousands of kernels and very long compiles), benchmarks them against your shapes, and reports the winners; frameworks then codegen exactly those. The famous costs are real: template-heavy compiles measured in minutes and error messages measured in pages — the pain that CuTe DSL exists to remove while keeping the concepts.

Use cuBLAS when

A stock GEMM at a stock dtype is the whole job. It's one call and it's already tuned.

Use CUTLASS when

You need fused epilogues, exotic dtypes/layouts, grouped/streamed scheduling, or a peak-performance template to build a product on.

Use the DSLs when

You're writing a new kernel: Triton/cuTile for tile-level productivity, CuTe DSL for CUTLASS-class control in Python.

CUTLASS's real product

Not any single kernel, but the decomposition: problem → scheduled tiles → pipelined collectives → tiled MMAs → atoms. Every serious GPU kernel effort of the last few years — FlashAttention-3, the DSLs, vendor inference stacks — is some subset of this hierarchy, reimplemented at a chosen altitude. Learn the decomposition once and every one of them becomes legible.
