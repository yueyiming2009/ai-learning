CUDA Graphs

Capture a repeated GPU workflow once, instantiate its launch plan, and replay the whole dependency graph with one host call. The kernels do the same work at the same addresses; the CPU stops rebuilding and submitting every launch.

Where this sits: read The PyTorch Execution Model for why eager operator dispatch becomes launch-bound, and CUDA streams for the queue that capture records. CUDA Graphs optimize submission; they are not the autograd graph and they do not fuse kernels like torch.compile.

The problem: the GPU finishes before the CPU can feed it

A CUDA kernel launch is asynchronous, but it is not free. Before a kernel appears in a GPU stream, Python, the framework dispatcher, the CUDA runtime, and the driver may all do setup work. A few microseconds of host overhead is easy to hide behind a 2 ms GEMM. It is impossible to hide behind a 2 µs pointwise kernel when the next launch is not ready yet.

Repeated workloads make this especially visible. One transformer decode step may issue hundreds of kernels, then execute nearly the same sequence again for the next token. Eager submission asks the CPU to rediscover and resubmit that sequence every time. A CUDA Graph moves that repeated setup out of the hot path:

Capture once

Record kernels, copies, arguments, and dependencies from one representative execution.

Instantiate once

Validate the graph and prepare an executable launch plan ahead of time.

Replay many times

Submit the entire workflow with one cudaGraphLaunch instead of \(K\) host launches.

Keep addresses stable

Change the values in long-lived buffers; do not change the pointers burned into the graph.

“Graph” means three different things in a PyTorch stack

GraphWhat its nodes meanWhat it is for

CUDA GraphAlready-chosen kernels, memory operations, and dependenciesReplay the same GPU submission plan with low CPU overhead.
The essential distinction

A CUDA Graph does not turn many kernels into one kernel. The GPU still runs the captured kernels and they still move the same bytes. What disappears is the repeated host-side setup and the launch gaps it caused.

Anatomy: template, executable, replay

A graph is a directed acyclic graph (DAG). Operations are nodes; ordering constraints are edges. A node becomes runnable when its dependencies are satisfied, leaving CUDA free to schedule independent work while preserving the recorded dependency relation.

copy input → projection GEMM → RMSNorm → logits + sample → write token
1

Warm up

Run eager iterations so libraries initialize, kernels load, allocators settle, and autotuners finish.

2

Define / capture

Create a cudaGraph_t explicitly, or record existing stream work with stream capture.

3

Instantiate

Turn the template into a validated cudaGraphExec_t optimized for launch.

4

Replay

Refresh values in static buffers, then launch the executable graph as often as needed.

CUDA offers two ways to define the template. The explicit Graph API adds nodes and edges directly, which is useful when a runtime owns the schedule and wants to update node parameters. Stream capture brackets ordinary stream-based code; launches that would have entered the stream are recorded instead. ML frameworks favor stream capture because cuBLAS, cuDNN, NCCL, and custom kernels already speak the stream API.

Definition is separate from execution

Capture does not run the workload. It records what would have been submitted. Instantiation may be expensive, and the first replay may be colder than later ones. The payoff only appears after enough hot replays amortize those one-time costs.

The speedup: removing the launch-limited regime

Consider \(K\) identical kernels in one serial stream. Let each kernel take \(t\) microseconds on the GPU and let the CPU need \(L\) microseconds to prepare each launch. The CPU can prepare launch \(i+1\) while kernel \(i\) runs, so a useful toy model is

\[ T_{\text{eager}} \approx L + t + (K-1)\max(L,t), \qquad T_{\text{graph}} \approx L_g + Kt \]

When \(t \ge L\), each kernel is long enough to hide preparation of the next launch and the curves meet. When \(t < L\), the GPU repeatedly drains its queue and waits for the CPU; graph replay replaces those \(K\) preparation intervals with one graph launch \(L_g\). Drag the controls to see the crossover.

Eager: one host launch per kernel CUDA Graph: one host launch per step Illustrative launch cost \(L=5\) µs

One graph removes gaps, not work. On the left, short kernels expose host launch latency and replay can be much faster. Past the 5 µs crossover, ordinary asynchronous launching already keeps the stream fed, so the graph and eager curves converge. Real launch costs and graph-launch costs vary by stack; the regime change is the point.

Graph capture also has a one-time cost \(C\). Across \(R\) repetitions, use a graph only if the accumulated per-step saving exceeds it:

\[ R\left(T_{\text{eager}}-T_{\text{graph}}\right) > C \]

This is why decode loops, fixed-shape training steps, iterative solvers, and simulations are natural targets, while a one-off large GEMM is not.

Native CUDA: capture an existing stream workflow

The condensed C++ pattern is warm up → begin capture → issue normal stream work → end capture → instantiate → replay. The graph below reads a fixed static_input address on every replay. New batches are copied into that address before launch.

cudaStream_t stream;
cudaGraph_t graph;
cudaGraphExec_t graph_exec;

cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking);

// Warm up lazy library initialization, module loading, and allocations.
for (int i = 0; i < 3; ++i) {
    model_step(static_input, static_output, stream);
}
cudaStreamSynchronize(stream);

// Work issued here is recorded, not executed.
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
model_step(static_input, static_output, stream);
cudaStreamEndCapture(stream, &graph);

// Pay validation and launch-plan setup once.
cudaGraphInstantiate(&graph_exec, graph, 0);

for (Batch batch : batches) {
    // The source may change; the graph's destination pointer stays fixed.
    cudaMemcpyAsync(static_input, batch.device_ptr, bytes,
                    cudaMemcpyDeviceToDevice, stream);
    cudaGraphLaunch(graph_exec, stream);
    consume(static_output, stream);
}

The copy above is outside the graph because batch.device_ptr may change. If both source and destination addresses are stable, the copy can itself be captured as a memcpy node. The same rule applies to kernel scalar arguments: captured values are fixed unless the application updates the executable graph or places changing values in device memory that the captured kernel reads.

Stream capture is dependency capture

One stream is straightforward: program order becomes a chain of edges. Multiple streams are legal, but every captured side stream must fork from the origin stream through an event dependency and rejoin it before capture ends. CUDA records the dependency DAG, not a promise to reproduce the exact stream assignment during replay.

Advanced alternative — update an executable graph

Native CUDA can update kernel parameters, memory addresses, and other node parameters without rebuilding everything when graph topology remains compatible. Use cudaGraphExecUpdate or node-specific update APIs when copying into static buffers is too expensive. Structural changes still require a new graph or re-instantiation.

PyTorch: static buffers around torch.cuda.CUDAGraph

PyTorch’s low-level wrapper uses the same stream-capture mechanism while integrating with the caching allocator. The canonical inference pattern keeps placeholder inputs and captured outputs alive for the graph’s entire lifetime:

import torch

model = model.cuda().eval()
static_x = torch.empty((batch, hidden), device="cuda")
graph = torch.cuda.CUDAGraph()

# Warm up on a side stream. This triggers lazy setup before capture.
warmup = torch.cuda.Stream()
warmup.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(warmup), torch.inference_mode():
    for _ in range(3):
        static_y = model(static_x)
torch.cuda.current_stream().wait_stream(warmup)

# torch.cuda.graph selects a capture side stream and instantiates on exit.
with torch.inference_mode(), torch.cuda.graph(graph):
    static_y = model(static_x)

def run(new_x):
    static_x.copy_(new_x)  # change values, not the captured address
    graph.replay()
    return static_y.clone()  # retain this result across the next replay

static_y aliases graph-owned storage and is overwritten by the next replay. The clone() makes the example safe for callers that retain outputs, but it adds an eager allocation and copy. A tightly pipelined runtime instead consumes static_y before replaying again, or feeds that fixed-address output directly into another captured graph.

Warmup belongs on a side stream. It lets cuBLAS/cuDNN initialize, autotuners choose algorithms, JIT kernels load, and ordinary allocations occur before capture. Capturing a first-ever call is a common way to encounter an unsupported allocation or hidden synchronization.

mode="reduce-overhead" is not a guarantee that every call becomes a CUDA Graph. TorchInductor may skip unsafe regions, record new paths, or create a separate recording for a new shape. The compiler route is still attractive because it can combine kernel fusion with low-overhead replay: fusion reduces GPU work and memory traffic; CUDA Graphs reduce host submission work.

The capture contract

Replay is cheap because decisions are frozen. Manual capture is correct only while the live workload obeys the contract represented by the recorded graph.

ConstraintWhy it existsUsual response
Same operation topologyReplay launches the recorded nodes and edges; Python does not run again.Capture one stable path, use partial capture, or keep dynamic branches eager.
Same device addressesKernel pointer arguments are embedded in the graph.Keep static buffers alive and copy new values into them.
Same shapes and layoutsGrid sizes, strides, workspace, and library algorithms were chosen for the captured metadata.Bucket/pad shapes or maintain one graph per common shape.
No CPU–GPU synchronizationCaptured work is not executing, so calls such as .item() have nothing valid to wait for.Move scalar reads, logging, and host decisions outside the captured region.
No essential CPU side effectsOrdinary Python/C++ host code is not replayed with the device graph.Keep bookkeeping eager or express the decision as supported device control flow.
Capture isolationUncaptured work or unsafe allocation on another thread can create dependencies the capture cannot represent.Quiesce other CUDA work and use the default strict capture mode.
Valid multi-stream fork/joinThe captured DAG must begin and end at the origin stream.Use events or stream waits to branch and rejoin before capture ends.
Stable output lifetimeThe next replay writes the same output addresses again.Consume immediately or clone values that must survive another replay.

CUDA random-number operations are graphable, but custom torch.Generator instances must use graph-safe state handling and be registered with the graph. Data-dependent control flow is generally a graph boundary; modern CUDA/PyTorch can represent some device-side branches through conditional graph nodes and torch.cond, but arbitrary Python branching still does not replay.

Memory addresses are the deepest constraint

PyTorch services allocations made during capture from a graph-private memory pool. The pool reserves those virtual addresses until the graph and captured tensors die. This prevents eager allocations from reusing an address that a later replay will write, but it can raise peak memory when many graphs or shape variants coexist.

Graphs may share a private pool only when their replay order and liveness make reuse safe—typically they execute in the same known order and never concurrently. Sharing saves memory, but replaying one graph can overwrite another graph’s outputs. Treat pool sharing as memory planning, not a free flag.

Dynamic workloads: make repetition explicit

Real ML workloads are not perfectly static. The practical question is not “is the whole program static?” but “where does it repeat, and how many stable variants are worth caching?”

Shape buckets

Capture common batch/sequence sizes, pad each request to the nearest bucket, and fall back to eager for outliers.

Partial capture

Leave data-dependent routing, CPU decisions, and irregular preprocessing eager; graph the stable GPU islands.

Graph updates

In native CUDA, update parameters when the topology is unchanged instead of recording a new graph.

CUDAGraph Trees

Let torch.compile record compatible paths/shapes while sharing one managed memory pool.

Why inference servers capture several graphs

Autoregressive decode repeats the same layer stack every token, but active batch size changes as requests arrive and finish. Servers such as vLLM therefore capture a ladder of batch-size or token-count buckets. At runtime they select a compatible graph, pad inactive slots, copy request state into static buffers, replay, and mask unused outputs. The padding wastes some GPU work; avoiding hundreds of host launches can still win.

Too many variants reverse the tradeoff: each recording costs startup time and private-pool memory. If shape changes are nearly unique, use eager or compiled execution without graphs. If there are only a handful of hot shapes, cache them.

Training and distributed capture

A training graph may include forward, loss, backward, and the optimizer step. Before capture, call optimizer.zero_grad(set_to_none=True) so backward allocates persistent .grad buffers from the graph’s private pool. On replay, backward refills those addresses and a captured optimizer updates the same parameter addresses in place.

Capture only the graph-safe portion when mixed-precision loss scaling or optimizer logic performs a host sync. Distributed collectives can be captured on modern NCCL/CUDA stacks, but every rank must replay a compatible collective sequence in the same order. Warm up the distributed path thoroughly and treat rank divergence as a correctness bug, not merely a performance miss. See NCCL and PyTorch distributed training for the communication layer around the graph.

Debugging: prove the workload is graph-shaped

Start with a profiler, not an API. In Nsight Systems, a good candidate has many short GPU kernels, visible idle gaps, and a CPU thread issuing launch calls on the critical path. After graphing, the CPU row should show one graph launch per step while the GPU row still shows the individual kernels packed more tightly.

CUDA can emit a graph as DOT with cudaGraphDebugDotPrint. PyTorch’s CUDAGraph also exposes debug-dump and graph-data helpers in current releases. These are useful when a profiler shows unexpected serialization: inspect whether an edge is a true captured dependency before trying to “fix” stream placement.

Decision rule

Use CUDA Graphs when a GPU-only region repeats many times, uses a small set of shapes and memory addresses, and spends meaningful time waiting for host submission. Use fusion or better kernels when the GPU work itself is the bottleneck. Often the best stack does both.
