A Blackwell GEMM, End to End

A source-pinned BF16 experiment for SM100 and SM103: select the native target, build the tensor views, compile a real tcgen05 kernel, follow TMA and TMEM through its pipeline, check the answer, and tune from evidence.

Read first: CuTe DSL layouts and partitions and the Blackwell kernel model. This lab is the executable bridge, not another architecture overview. Keep cuBLAS as the baseline and CUDA synchronization as the vocabulary.
Evidence boundary: the runner and source trace target NVIDIA CUTLASS v4.8.1, commit 2c85f497547eb441f0fe80bfb0fb2e6f9add1719. APIs, shared BF16 MMA support, and SM100/SM103 target selection were checked against source; this page does not claim GPU execution on B200/GB200 or B300/GB300, or measured performance. The browser plot below is an analytical model. Pass the GPU gates independently on each architecture before treating a configuration as working or fast.

1 · Start with a bounded, reviewed environment

The first experiment is deliberately narrow: one GPU, one batch, BF16 inputs/output, FP32 accumulation, and \(C=AB\). The optional ReLU is an elementwise epilogue, not a residual/bias fusion. The implementation is NVIDIA's complete DenseGemmKernel; the downloadable lab runner owns tensor setup, verification, timing, and profiling. It imports the reviewed kernel rather than duplicating its implementation.

Native targets: B300 and GB300 are SM103, not SM100

The NVIDIA compute-capability table maps B200/GB200 to 10.0 and B300/GB300 to 10.3. The same BF16 reference kernel uses shared Blackwell MMA, TMA, and TMEM machinery on these two architectures. The pinned CuTe MMA implementation admits the SM100 family, including SM103; its source name is not a B200-only hardware restriction.

capability = torch.cuda.get_device_capability(device)
gpu_arch = target_for_capability(capability)
# (10,0) -> "sm_100a"; (10,3) -> "sm_103a"; all other values raise.
compiled = cute.compile(
    gemm, *views, stream, epilogue_op,
    options=f"--gpu-arch={gpu_arch}",
)

This is per-device JIT compilation, not a promise that one architecture-specific cubin runs on both GPUs. NVIDIA's compiler-target rules distinguish exact-capability a targets from shared-family f targets: sm_100a artifacts are not automatically SM103-compatible. A supported sm_100f target can cover common family features, but not every SM103-specific enhancement. This runner deliberately compiles for the installed device's native a target and records it as compilation_target. Do not force CUTE_DSL_ARCH=sm_100a in a B300 environment or reuse B200 architecture-specific artifacts.

On B300/GB300, use the same commands below. No new dtype, shape, or CTA-pair flag is required for this BF16 lab. Startup should report (10,3) and sm_103a; on B200/GB200 it should report (10,0) and sm_100a. An old wheel, unsupported compiler target, or failed source check is a blocker to resolve, not a reason to remove the guard. Run the numerical, tail, sanitizer, generated-code, and timing gates on the actual device.

What changes on Blackwell Ultra?

The NVIDIA Blackwell Ultra architecture description separates common kernel machinery from new performance capabilities:

2 · The host contract: B has two different views

PyTorch writes \(A[M,K]B[K,N]\). This CuTe kernel expects A[M,K,L], B[N,K,L], and C[M,N,L]. Both refer to the same mathematical multiply: \(C_{mnl}=\sum_k A_{mkl}B_{nkl}\). B's view changes its coordinate convention, not the weights or the GEMM equation.

# Excerpt from the downloadable runner; L = 1.
a_storage = torch.randn((1, M, K), device=device, dtype=torch.bfloat16)
b_storage = torch.randn((1, K, N), device=device, dtype=torch.bfloat16)
c_storage = torch.full((1, M, N), float("nan"),
                       device=device, dtype=torch.bfloat16)

a = a_storage.permute(1, 2, 0)  # (M,K,1), strides (K,1,M*K)
b = b_storage.permute(2, 1, 0)  # (N,K,1), strides (1,N,K*N)
c = c_storage.permute(1, 2, 0)  # (M,N,1), strides (N,1,M*N)
views = tuple(from_dlpack(t, assumed_align=16) for t in (a, b, c))
stream = cuda.CUstream(torch.cuda.current_stream().cuda_stream)

DLPack conversion is a zero-copy view. The BF16 contiguous dimensions N/K must be multiples of 8 so the packed rows retain 16-byte alignment; assumed_align=16 is a promise about real addresses, not a request to fix them. A sliced/offset tensor needs its own alignment checks. These static views specialize the compiled experiment to its shape/layout. Keep the storage, views, and stream alive until all launches finish.

gemm = DenseGemmKernel(
    acc_dtype=cutlass.Float32,
    use_2cta_instrs=False,
    mma_tiler_mn=(128, 128),
    cluster_shape_mn=(1, 1),
    use_tma_store=True,
)
if not gemm.can_implement(*views):
    raise ValueError("Unsupported configuration")
compiled = cute.compile(
    gemm, *views, stream, lambda x: x, options=f"--gpu-arch={gpu_arch}"
)
compiled(*views, stream)

The runner uses the PyTorch current stream for both implementations and their CUDA events. Compilation is outside timing. Launching queues GPU work; stream ordering is not a host completion guarantee, so correctness checks and profiling boundaries explicitly synchronize. This is inference-only code: no autograd or backward registration.

3 · Trace the actual kernel, not a hypothetical skeleton

Open the pinned host setup, then walk through these device stages. All names below are source navigation landmarks, not standalone pseudocode presented as a runnable kernel.

Stage / sourceWhat to inspectInvariant to preserve
Shapes and stagingmake_trivial_tiled_mma, staged/swizzled A/B SMEM layouts, and make_tiled_tma_atom_A/B. BF16's K=16 instruction is tiled four times: the mainloop stage advances K by 64.A/B descriptors, strides, major modes, and SMEM swizzles must match the MMA's operand layouts. Changing a tile is not just changing loop bounds.
Initialize pipelinesPipelineTmaUmma owns the A/B stage handoff; PipelineUmmaAsync owns accumulator completion. TMA transaction counts describe the actual A+B bytes.Initialize barriers before asynchronous producers use them. Preserve participant counts, stage indices, and phase progression.

The first K block initializes the accumulator; later blocks enable tcgen05.Field.ACCUMULATE.Release the A/B stage through the UMMA completion protocol, not when issue returns. PipelineTmaStore protects staging reuse.TMEM loads, output-layout exchange, and TMA stores have distinct completion/visibility requirements. FinishThe CTA synchronizes before tmem.free; the A/B producer tail drains pending stage obligations.No consumer may retain a TMEM load obligation after free. Output staging must remain valid while an asynchronous store reads it.
This baseline is not the full warp-specialized persistent design. It has 128 threads per CTA, one accumulator stage, and warp 0 drives the TMA/MMA control loop. All threads participate in the epilogue. There is no two-output TMEM ping-pong or separate persistent scheduler warp here. Learn this protocol first; use the linked architecture diagram and NVIDIA's persistent variants as the next step, not as a claim about this source.

For the default 128×128 FP32 accumulator, the simple full-row storage footprint is \(128\cdot128\cdot4=64\) KiB, or 128 TMEM columns. A raw BF16 A+B stage at K=64 contains \(2(128\cdot64+128\cdot64)=32\) KiB. Neither number is the whole resource budget: barriers, padded/swizzled layouts, and output staging matter. The runner prints the reference's actual stage count and TMEM allocation after compilation; do not force an arbitrary stage count without recomputing its storage layouts.

A first edit: fuse ReLU without changing the contract

def relu(x):
    return cute.where(x > 0, x, cute.full_like(x, 0))

compiled = cute.compile(
    gemm, *views, stream, relu, options=f"--gpu-arch={gpu_arch}"
)
# Runtime arguments do not include the compile-time epilogue callback.
compiled(*views, stream)

--relu selects this already-wired experiment. Importantly, this pinned reference calls the callback after conversion to the output dtype. For the finite BF16 values used here, the reference is relu(BF16(FP32_AB)). It is not a general FP32 residual+bias+activation epilogue, and it does not define a NaN/Inf contract. Adding scalars, bias tensors, or reductions requires changing the reference's signature, partitioned loads, predicates, and possibly staging; an elementwise lambda alone does not supply those duties.

For a source edit beyond the supplied configurations, use a separately reviewed copy and a new source pin. The runner intentionally rejects edits to its reference file. Never bypass a checksum failure merely to make an experiment run.

4 · Pass correctness gates before recording speed

The runner compares both the CuTe output and the BF16 library output against a separate FP32 PyTorch multiply of the actual BF16 operands, followed by BF16 rounding and optional ReLU. TF32 and reduced-precision BF16 reductions are disabled. Random A is scaled by \(1/\sqrt K\), so output magnitudes stay roughly stable as K changes. This avoids making a fixed absolute tolerance meaningless just by increasing K.

Random inputs use atol=0.01, rtol=0.02, with maximum absolute error printed. These are declared lab tolerances, not a universal BF16 guarantee. Zeros and the rectangular identity pattern require exact equality; identity means \(A_{ik}=1\) only for \(i=k\), so it also works for non-square shapes. Outputs start as NaNs to expose unwritten cells, and assert_close does not accept matching NaNs.

# Accumulation, output initialization, and coordinate ownership:
for pattern in random zeros identity; do
  python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
    --pattern "$pattern"
done

# Aligned but partial output/K tiles: retain TMA stores.
python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 1032 --n 520 --k 264

# Epilogue and a different reduction depth:
python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 512 --n 1024 --k 4096 --relu

# This MUST fail before launch: N is not a legal 16-byte BF16 stride.
python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" --n 513

The reference's TMA output path supports boundary tiles, while its direct register-store path has no output predication. The runner rejects --direct-store unless M and N completely cover each 128×tile-N CTA output tile. This is a supported-example constraint, not evidence that all CuTe kernels handle tails automatically. Repeat the partial-tile gate for every 2-CTA configuration you plan to use, independently on SM100 and SM103.

compute-sanitizer --tool memcheck --error-exitcode 1 \
  python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 1032 --n 520 --k 264

compute-sanitizer --tool synccheck --error-exitcode 1 \
  python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT"

Use a tool release that understands the installed GPU, including SM103 on B300/GB300, and the generated instructions. Numerical success plus a clean sanitizer run is stronger evidence than either alone; it still does not prove an asynchronous protocol correct. Tool coverage for TMA/TMEM and races is version-dependent. Diagnose unsupported-instruction/tool errors instead of suppressing them, and inspect the pipeline invariants when a kernel hangs.

5 · Compare the same work, outside compilation

The baseline is CUDA torch.mm on the same BF16 A/B storage with a preallocated BF16 output, dispatched through PyTorch's BLAS backend. The runner reports the backend preference; inspect the actual kernels in a profile rather than assuming a particular cuBLASLt algorithm. With --relu, the baseline includes a separate in-place ReLU kernel; the CuTe callback is fused. This is then a fused-vs-unfused comparison, not GEMM-only throughput.

python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 4096 --n 4096 --k 4096 --iterations 100 --trials 5

python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 4096 --n 4096 --k 4096 --iterations 100 --trials 5 --relu

After correctness, both implementations receive 10 warmup launches. Each trial averages 100 launches between CUDA events on the same stream; the runner alternates implementation order and reports all trial samples plus their median. Compile time is reported separately. Allocation, DLPack conversion, FP32 reference calculation, and result copies are outside the timed batches.

\[ \mathrm{TFLOP/s} = \frac{2MNK}{t_{\mathrm{ms}}\cdot10^9}, \qquad \mathrm{time\ ratio} = \frac{t_{\mathrm{PyTorch}}}{t_{\mathrm{CuTe}}}. \]

The numerator counts GEMM arithmetic only, even when ReLU is included in elapsed time. A ratio above 1 means CuTe was faster for that measured configuration. The page supplies no expected TFLOP/s or claimed speedup. Preserve correctness/error outputs beside the samples; rejecting a failing candidate is part of tuning, not an inconvenient outlier.

Declare the timing regime. These are warm, repeated same-buffer, non-graph launches, not cold-HBM measurements. Reuse can hit L2. Short kernels can be starved by Python launch overhead; CUDA-event batches then include GPU idle gaps. Nsight Systems tells you when to switch to matched graph-replay measurements. Do not graph only one side, flush only one side's cache, or use profiler-replay duration as an ordinary benchmark.

Before tuning, predict which resource could matter

For an ideal cold-input BF16 GEMM with every matrix transferred once, compare a compute bound, a global-memory traffic bound, and a chosen launch floor:

\[ t_{\mathrm{compute}}=\frac{2MNK}{P},\quad t_{\mathrm{memory}}=\frac{2(MK+KN+MN)}{B},\quad t_{\mathrm{model}}=\max(t_{\mathrm{compute}},t_{\mathrm{memory}},t_{\mathrm{launch}}). \]

For M=N=2048, P=1000 TFLOP/s, B=4 TB/s, and a 5 µs floor, the model is launch-limited at K=128 and compute-limited at K=8192. This is not a GPU benchmark.

6 · Isolate one validated launch, then read the generated code

nsys profile --trace=cuda,nvtx --capture-range=cudaProfilerApi \
  --capture-range-end=stop --output=blackwell-timeline \
  python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 4096 --n 4096 --k 4096 --profile

ncu --profile-from-start off --set full --export blackwell-kernel \
  python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \

For launch-starvation diagnosis, also capture the ordinary benchmark with Nsight Systems and no capture-range restriction; the isolated profile above intentionally removes repeated host launches. Match the profiler version, GPU permissions, and available section names to your environment. A profiling-permission failure is not a slow-kernel result.

7 · Change one supported configuration at a time

# Same problem and timing regime; each candidate checks correctness first.
for tile_n in 64 128 256; do
  python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
    --m 4096 --n 4096 --k 4096 --tile-n "$tile_n"
done

# Same 128x128 per-CTA output, but 256x128 logical MMA across a CTA pair:
python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 4096 --n 4096 --k 4096 --tile-n 128 --two-cta

# Complete tiles only: compare output-store choreography.
python blackwell-gemm-lab.py --cutlass-root "$CUTLASS_ROOT" \
  --m 4096 --n 4096 --k 4096 --tile-n 128 --direct-store

A larger N tile increases reuse but also accumulator footprint, output staging, and often register pressure. --two-cta changes both the MMA tiler to (256,N) and the cluster to (2,1); each CTA still owns 128×N output values. Keeping only the old cluster while enabling a pair violates the source's constraints. Two CTAs cooperate through an architecture-specific protocol; this is not simply doubling block count.

Record candidate, GPU/versions, compilation_target, shape, actual A/B stages and TMEM columns, correctness/error values, timing samples, and the profiler evidence that motivated it. Recheck the winner on different K values and the partial-tile gate, not only the square shape used for tuning. Retune after moving from B200/GB200 to B300/GB300; do not inherit the old winner without evidence. Close candidates need repeated runs under matched clocks, power limits, and competing workload; do not declare a win from one noisy median.

Completion gate: a configuration is ready only after its declared input/layout domain passes numerical checks and applicable sanitizer checks, its generated target/instructions are inspected, and its speed is measured against the same-work baseline under a declared timing regime. Until those GPU checks are recorded, this remains a source-verified lab, not an execution-validated performance claim.

8 · Where to extend the kernel

Persistent/warp-specialized GEMM: start from the pinned persistent source after the baseline protocol is understood. Scheduler state, warp roles, and overlapping output lifetimes require a different kernel; the runner does not pretend to expose them as a stage-count knob.

Block-scaled operands: use the separate SM100 block-scaled reference or the experimental SM103 FP4 Ultra reference for B300/GB300. Add packed payloads, scale tensors with prescribed layouts, scale staging/TMEM budget, and a reference computed from the quantized-and-dequantized inputs. These are different experiments with different constraints; replacing BF16 with an FP4 dtype or relabeling the target does not establish those contracts. Read block-scaled MMA and quantization before porting the experiment.

Attention: FlashAttention-4 adds two matmuls, online-softmax/correction work, different dominant resources, and more overlapping crews. Its B200 bottleneck discussion needs the Ultra SFU caveat on B300/GB300. The reusable lesson is the experiment loop: declare the contract → preserve ownership and completion → prove the answer → profile → change one hypothesis.
