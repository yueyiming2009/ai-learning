Megatron-LM — Vertically Integrated Model Parallelism

Megatron's bargain: express your model in its transformer blocks, and in exchange every layer of the stack is co-designed — the parallelism knows the model, the kernels know the parallelism, and the communication schedule knows both. This page is the deep dive: the 5-D strategy layer, the fused-kernel and overlap engineering that make it fast even at TP = 1, FP8 via Transformer Engine, and what the bargain costs.

One of three framework deep dives — the others are DeepSpeed → and TorchTitan →; the cross-framework comparison, throughput crossover, and decision guide live on Training Frameworks →. The parallelism math itself is on TP →, SP →, PP →, EP →, and the ZeRO ladder →.

1 · What "Megatron" names — four layers of one NVIDIA stack

Megatron began as the 2019 NVIDIA paper (Shoeybi et al.) that introduced intra-layer model parallelism — what everyone now calls tensor parallelism — for transformers, demonstrated on an 8.3B GPT-2 when "large" meant 1.5B. Since then it has accreted the rest of the modern parallelism toolbox and split into a small family of names worth keeping straight:

NameWhat it is
Megatron-Core The library: parallelism engine (TP/SP/PP/CP/EP process groups and schedules), transformer building blocks, the distributed optimizer, distributed checkpointing, and dataset/dataloader utilities. This is what other systems build on — NVIDIA's NeMo, and verl's Megatron backend.
Megatron-LM The reference pretraining scripts on top of Megatron-Core — the pretrain_gpt.py entry point, argument parsing, training loop. What most people mean by "training with Megatron."
Transformer Engine (TE) The kernel layer underneath: fused attention, fused norms, and above all FP8/MXFP8 GEMMs with scaling management (§5). Usable independently, but co-designed with Megatron-Core.
NeMo The enterprise wrapper: Megatron-Core plus recipes, data curation, checkpoint conversion (Megatron-Bridge for the Hugging Face boundary — elaborated in §8), and deployment tooling.

The design philosophy across all four layers is vertical integration on NVIDIA hardware. The model must be expressed in Megatron's own transformer blocks — you don't bring an arbitrary nn.Module — and in exchange the whole stack is co-designed top to bottom. That bargain is exactly what a compiler can't yet give you across TP/PP boundaries, and it is the source of both everything in §3–5 and everything in §7.

2 · The strategy layer — 5-D parallelism + distributed optimizer

Strategy-wise, Megatron is the reference implementation of everything on the parallelism pages, composed out of the box with the process-group bookkeeping done for you:

AxisMegatron's implementationPlacement logic
TP → --tensor-model-parallel-size; column→row sandwich per attention/MLP Intra-node, on NVLink — its all-reduces sit on the critical path of every layer
SP → --sequence-parallel; shards the norms/dropouts TP leaves replicated, turning TP's all-reduces into all-gather + reduce-scatter pairs Rides the TP group; enables selective activation recomputation
PP → --pipeline-model-parallel-size + --num-layers-per-virtual-pipeline-stage; interleaved 1F1B Across nodes — only skinny activations cross the slow links
CP --context-parallel-size; ring-attention sharding of the sequence dim for long context Between TP and DP in the hierarchy
EP → --expert-model-parallel-size; token dispatch + grouped GEMM (§6) Orthogonal to TP for expert weights; all-to-all across the EP group
DP + dist-opt → --use-distributed-optimizer; optimizer state and fp32 master weights sharded over the DP group — ZeRO-1 in Megatron's dialect Outermost; gradient buckets reduce-scatter, parameters all-gather (§4)

What makes it "Megatron" is not any one axis but that all of them compose — the canonical frontier recipe (TP×SP intra-node, PP across nodes, CP for long context, EP for MoE, sharded DP outermost) is a command-line flag combination, not an integration project.

3 · Fusion — why it's fast even at TP = 1

Run Megatron-LM with --tensor-model-parallel-size 1 — pure data parallelism — and it can still beat a naive PyTorch loop on the same model. That advantage is the step-implementation layer: hand-written kernels that starve the memory bus. A transformer step is matmuls interleaved with bandwidth-bound pointwise ops, each of which normally costs a full HBM read + write of an activation tensor; Megatron fuses the standard chains:

The fusion inventory
  • Bias + activation (GeLU / SwiGLU) in the MLP — one kernel forward, one backward.
  • Bias + dropout + residual-add after attention and MLP — three ops, one kernel.
  • Persistent LayerNorm/RMSNorm — the row stays in registers/shared memory across the whole reduction.
  • Scaled masked softmax — scaling, implicit causal masking (the triangular kernel never materializes a mask tensor), and the max-subtraction trick fused, in fp16/bf16 end-to-end. Superseded by FlashAttention / TE fused attention, which Megatron selects automatically — see FlashAttention.
  • Fused RoPE and a vocab-parallel fused cross-entropy that never materializes the full softmax over the vocabulary — the largest single activation in a small model.
  • Gradient-accumulation fusion: the weight-gradient GEMM accumulates directly into the persistent fp32 main-grad buffer via the GEMM epilogue (see cublasLt epilogues), instead of emitting a bf16 gradient and launching a separate cast-and-add. With gradient accumulation this saves a full read+write of every weight gradient per micro-batch.
  • Fused optimizer + multi-tensor apply: Adam updates, grad-norm computation, and clipping batched across all parameter tensors into a handful of launches — thousands of small kernels removed per step, which matters most precisely when the model is small.

Note what this list is: each item is something torch.compile can now produce for an eager model (the TorchTitan bet), but Megatron had them years earlier and still holds the edge where fusion must cross a collective — which is the subject of the next section.

4 · Overlap — never let a collective idle the SMs

The second half of the implementation layer is hiding communication behind compute. Each flag attacks a different exposure:

MechanismWhat it hides
--overlap-grad-reduce DP gradient communication: gradients live in one contiguous, bucketed buffer; each bucket's reduce-scatter launches the moment backward fills it, hiding the reduction behind the rest of backward.
--overlap-param-gather The distributed optimizer's parameter all-gather: updated parameters for layer \(n{+}1\) prefetch while layer \(n\) computes forward.
--tp-comm-overlap The one that attacks TP's intrinsic critical-path cost: GEMMs are split into chunks and the TP all-gather/reduce-scatter ring-pipelines against the compute chunks — "userbuffers," direct NVLink writes bypassing NCCL's staging. TorchTitan's async TP is the compiler-generated version of this idea.
Interleaved 1F1B The pipeline bubble: the virtual-pipeline schedule shrinks it by the interleave factor — see Pipeline Parallelism.

5 · Transformer Engine — turnkey FP8

On top of the fusion/overlap layer sits Transformer Engine: FP8 GEMMs on Hopper and Blackwell with the numerics managed for you. The hard part of FP8 training is not the GEMM — it is scaling: e4m3/e5m2 have so little range that every tensor needs a scale factor, tracked and updated as magnitudes drift during training. TE owns that bookkeeping (delayed scaling from an amax history on Hopper; per-block scaling in the MXFP8 formats on Blackwell — see the Blackwell kernel model), keeps the accumulations and master weights in higher precision, and exposes the result as drop-in transformer modules.

Why it matters
For large-model pretraining FP8 is routinely another 1.3–1.6× step-time win —
and for a long time Megatron was the only stack where it was turnkey.

That exclusivity has eroded — torchao float8 gives the PyTorch-native stack the same GEMMs — but TE still moves first on each hardware generation's formats and keeps the deepest integration with Megatron's fused kernels (the FP8 cast fuses into adjacent operations rather than costing its own memory pass).

6 · MoE — the most battle-hardened EP planner

Megatron-Core is the reference for large-scale MoE training (the full math is on MoE Parallelism). The pieces it owns:

  • An explicit EP axis (--expert-model-parallel-size) composed with TP, PP, CP, and DP in one planner — expert weights can be simultaneously expert-parallel and tensor-parallel, with separate process groups for each.
  • Token dispatchers — all-gather-based for small EP degrees, all-to-all for large; the permute/unpermute machinery that routes each token to its experts and restores order afterward, with DeepEP-style kernels available for the all-to-all at scale.
  • Grouped GEMM expert compute, so E experts' small matmuls run as one batched kernel instead of E launches — the difference between an MoE layer that is bandwidth-bound and one that isn't.
  • The operational toolbox: aux-loss and aux-free load balancing, capacity factors and token dropping (or dropless), and upcycling dense checkpoints into MoE.

This is the corner of the landscape where Megatron's lead is largest: EP-native alternatives exist (TorchTitan's dp2ep, DeepSpeed-MoE, MegaBlocks), but the EP × TP × PP composition at frontier scale is Megatron's home turf.

7 · The costs — the mirror image of the benefits

  • NVIDIA-only in practice. The kernel layer and TE are CUDA; the ROCm forks trail. The vertical integration that buys the MFU is an integration with one vendor's hardware.
  • A rigid model zoo. Anything that isn't a Megatron transformer block is a porting project — new attention variants, novel layer types, or research architectures mean writing Megatron-dialect modules, not just an eager nn.Module.
  • Checkpoint friction. Its own distributed checkpoint format; conversion to/from Hugging Face is a perennial friction point that dedicated bridge tooling (Megatron-Bridge, §8, verl's model merger) exists to paper over.
  • A large, research-hostile codebase. The price of hand-written layer 3: the code that makes it fast is the code that makes it hard to modify. This is the single strongest argument that routes researchers to TorchTitan and fine-tuners to DeepSpeed/FSDP.

8 · Ecosystem — where you meet Megatron

Directly, in frontier pretraining: it is the default engine for dense and MoE pretraining at ≳10B on NVIDIA clusters, chasing MFU. Indirectly, in two places: NeMo, which packages Megatron-Core for enterprise training; and RL post-training, where verl exposes a Megatron-Core backend for the actor/critic's training half — the standard choice once the policy model outgrows the FSDP backend (see verl). In both cases what's being reused is Megatron-Core the library, not the pretraining scripts — the four-layer split of §1 doing its job.

The Hugging Face boundary — Megatron-Bridge

Almost every real Megatron run touches the Hugging Face ecosystem on one side or the other: post-training and continued pretraining start from an HF checkpoint, and whatever you train has to come back out as an HF checkpoint before vLLM, SGLang, or anyone else downstream can serve it. That boundary is harder than "rename some tensors," for three stacked reasons:

  • The formats disagree. An HF checkpoint is a set of safetensors files describing one logical model, one named tensor at a time. A Megatron distributed checkpoint is sharded the way the training job was sharded — a weight may be split column-wise across the TP group, live on one PP stage's ranks, and (for experts) belong to one EP rank.
  • The layouts disagree. Megatron fuses and rearranges weights for kernel efficiency: QKV projections stored as one interleaved matrix, SwiGLU's gate and up projections concatenated, embeddings padded to a vocab size divisible by the TP degree. Conversion has to un-fuse, de-interleave, and un-pad — per architecture, and wrong-but-plausible layouts fail silently as a model that trains but is subtly broken.
  • The scale forbids the naive fix. The obvious script — gather everything to rank 0, fix it up, save — needs the whole model in one host's memory. At the ≳10B sizes where Megatron is the right tool, that is exactly what you can't do.

Megatron-Bridge (the NVIDIA-NeMo/Megatron-Bridge library) is NVIDIA's official answer, replacing the ad-hoc conversion scripts that used to circulate. Its AutoBridge API detects the architecture from the HF config and converts in both directions — AutoBridge.from_hf_pretrained(...) to materialize a Megatron-Core model from HF weights, bridge.save_hf_pretrained(model, ...) to export back, emitting the full HF folder (weights, config, tokenizer). The design points target exactly the three problems above:

  • Parallelism-aware: conversion runs against the live sharded model, aware of TP/PP/VPP/CP/EP layouts, so each rank contributes only its shard — no gather-to-rank-0 step.
  • Streaming, per-parameter: tensors are imported/exported one at a time with no intermediate full checkpoint on disk or in memory, so conversion cost stays flat as the model grows.
  • A per-architecture bridge registry: the fuse/unfuse/rename rules live in maintained per-model-family bridges (30+ families — Llama, Qwen dense and MoE, DeepSeek, Gemma, Mistral, and others) rather than in everyone's private conversion script, and conversions can be round-trip verified.

Two footnotes complete the picture. First, Megatron-Bridge has outgrown the converter role: it is the refactor of NeMo's training stack, wrapping Megatron-Core in a PyTorch-native training loop with pretraining/SFT/LoRA recipes — so "NeMo" in the §1 table increasingly means this library. Second, the same boundary is why RL infrastructure grows equivalent machinery: in a verl run with a Megatron backend, the actor's weights must reach the vLLM rollout engine (which speaks HF layouts) every step, so the resharding problem Megatron-Bridge solves at checkpoint granularity reappears as the weight-sync path — see verl's architecture.

The one-paragraph verdict
Choose Megatron when
Pretraining dense or MoE models ≳10B on NVIDIA clusters where the last 10–20% of MFU pays for itself; MoE at large EP degrees; FP8/MXFP8 on the newest hardware; or scaling verl RL training past what FSDP handles.
Look elsewhere when
The model doesn't fit Megatron's blocks and porting isn't worth it (→ DeepSpeed, FSDP); you need to modify the training system itself (→ TorchTitan); or the run is a fine-tune where framework overhead dwarfs kernel wins (→ HF Trainer/Accelerate).

Summary

The bargain

Express the model in Megatron's blocks; get a co-designed stack (Core → LM → TE → NeMo) where parallelism, kernels, and schedules know each other. Vertical integration on NVIDIA hardware.

Strategy layer

TP + SP + interleaved-1F1B PP + CP + EP + distributed-optimizer DP (ZeRO-1), all first-class and composable by flag — the reference implementation of the parallelism pages.

Implementation layer

Hand-fused kernels (norms, softmax, cross-entropy, grad-accumulation epilogues) plus overlap everywhere (bucketed grad reduce, param prefetch, TP userbuffers) — fast even at TP=1; FP8 turnkey via TE.

The price

NVIDIA-only, a rigid model zoo, checkpoint-format friction, and a codebase that resists modification — the exact trade TorchTitan and DeepSpeed exist to refuse.
