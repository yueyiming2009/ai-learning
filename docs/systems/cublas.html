cuBLAS — Calling Peak GEMM

The most-executed library in deep learning: the BLAS levels and why only GEMM escapes the bandwidth ceiling, the column-major legacy, batched matmuls, cublasLt's epilogues and heuristics, and what determinism costs.

Pre-reading: GPU Hardware for ML for the roofline model this page leans on, and MFU for the whole-run accounting. CUTLASS is this library's open twin — read together, they are the closed box and its blueprints.

The most-executed library in deep learning

Every nn.Linear, every attention projection, every LM head — when PyTorch multiplies matrices on an NVIDIA GPU, the call bottoms out in cuBLAS. It has shipped with CUDA since the first toolkit (2007), implementing the BLAS interface — the 1979-vintage Fortran API that scientific computing standardized on — plus a modern extension layer (cublasLt) that grew up specifically to serve deep learning. By instruction count and by joules, it is plausibly the most-executed numerical library on earth right now.

Its contract is the inverse of everything else on the kernel shelf: zero programmability, maximum performance-per-effort. One function call gets you the tensor cores at somewhere near peak, tuned per architecture by the people who designed the silicon. The rest of this page is about what that call actually is, what the box does inside, and where its edges are — the edges being exactly where Triton, CUTLASS, and friends take over.

The BLAS levels — and why GEMM is the only one that matters

BLAS organizes its routines into three levels, and the split is really about arithmetic intensity — FLOPs per byte of memory traffic:

LevelShapeCanonical routineFLOPs : dataIntensity (BF16)
1 — vector\(y \leftarrow \alpha x + y\)axpy, dot\(O(N) : O(N)\)~0.3 FLOPs/B, constant
2 — matrix·vector\(y \leftarrow Ax\)gemv\(O(N^2) : O(N^2)\)~1 FLOP/B, constant
3 — matrix·matrix\(C \leftarrow \alpha\,\text{op}(A)\text{op}(B) + \beta C\)gemm\(O(N^3) : O(N^2)\)~N/3 FLOPs/B — grows with size

Levels 1 and 2 touch each operand once per FLOP-pair: no tiling, no cleverness, no library can save them — they are bandwidth, full stop. Level 3 is the only routine whose intensity grows with problem size, because each element of \(A\) and \(B\) participates in \(N\) multiply-adds. That single asymptotic fact is why tensor cores exist, why the CUTLASS tiling hierarchy exists, and why "is it GEMM-shaped?" is the first question of GPU performance:

GEMM \(N{\times}N{\times}N\): \(N/3\) GEMV: ≈1 AXPY: ≈0.33 H100 ridge ≈ 295 FLOPs/B

Only Level 3 can climb out of the bandwidth regime. Arithmetic intensity (BF16 FLOPs per byte of unavoidable HBM traffic) versus size, log–log, against an H100 SXM's ridge point (989 TF/s ÷ 3.35 TB/s ≈ 295). AXPY and GEMV are flat lines a decade below the ridge — perfect implementations of them are still ~1% of peak FLOP/s. Square GEMM crosses the ridge near \(N \approx 900\): below that, even cuBLAS is bandwidth-bound; above it, tensor cores can be fed. Note where inference decode lives: batch-1 matmuls are GEMV-shaped — the teal line — which is the arithmetic behind the memory-bound decode story.

Anatomy of the call — and the column-major legacy

The classic API is a stateful handle plus per-routine calls. Everything is asynchronous on the handle's stream:

cublasHandle_t handle;
cublasCreate(&handle);                          // heavyweight: create once, reuse
cublasSetStream(handle, stream);

const float alpha = 1.0f, beta = 0.0f;
cublasSgemm(handle,
            CUBLAS_OP_N, CUBLAS_OP_N,           // op(A), op(B): N, T, or C
            m, n, k,                            // C is m×n, op(A) m×k, op(B) k×n
            &alpha,
            A, lda,                             // lda: leading dimension —
            B, ldb,                             //   column stride, allows submatrices
            &beta,
            C, ldc);                            // C = α·op(A)·op(B) + β·C

The trap every framework author has met: BLAS is column-major, inherited from Fortran, while C/C++/PyTorch tensors are row-major. Nobody transposes anything to cope — they use an identity instead. A row-major matrix reinterpreted as column-major is its transpose, and \(C^\top = B^\top A^\top\). So to compute row-major \(C = AB\), you call cuBLAS with the operands swapped — asking for what it thinks is \(C^\top = B^\top A^\top\), all in its column-major world — and the row-major result comes out right, zero copies made:

// row-major C[m×n] = A[m×k] · B[k×n]: swap operands, swap m↔n
cublasSgemm(handle, CUBLAS_OP_N, CUBLAS_OP_N,
            n, m, k,                     // note: n first
            &alpha, B, n, A, k,          // note: B first
            &beta,  C, n);

Mixed precision arrived as cublasGemmEx: storage dtypes and the compute type become arguments, decoupling "what the matrices are" from "what the tensor cores accumulate" — CUBLAS_COMPUTE_32F with FP16/BF16 inputs is the standard training configuration; the FP32-storage variants can be silently accelerated with TF32 when the math mode allows it (see numerics).

Batched GEMM: the transformer's actual workload

A transformer rarely runs one big GEMM; it runs stacks of them — the attention scores \(QK^\top\) and \(PV\) are a matmul per head per sequence, each too small to fill the GPU alone. Launching them one by one dies of launch overhead and low occupancy, so cuBLAS provides one-launch batch families:

  • cublasGemmBatchedEx — takes arrays of pointers: each problem anywhere in memory (same shape). What ragged workloads use.
  • cublasGemmStridedBatchedEx — one base pointer per operand plus a fixed stride between problems: exactly the layout of a contiguous [B, H, S, d] tensor. This is what torch.matmul on 4-D tensors becomes, and it's the fast path — no pointer-array indirection.

The mental model: batching turns many small GEMMs into one grid-level workload, recovering occupancy — but each problem is still tiled independently, so tiny matmuls (small \(d\), short sequences) remain inefficient inside the batch. That inefficiency, plus the unfusable softmax sitting between the two attention GEMMs, is precisely why attention left cuBLAS for FlashAttention; and the MoE variant of the problem — thousands of expert GEMMs with different shapes — is why grouped GEMM lives in CUTLASS.

cublasLt: the API deep learning actually calls

By 2019 the classic API was drowning: dtype combinations × layouts × tensor-core generations × the epilogue fusions every network wants. cublasLt (CUDA 10.1) restructured matmul as a configured object rather than a function name — and it is what PyTorch calls for your Linear layers:

// 1 · describe the operation: compute type + epilogue
cublasLtMatmulDesc_t op;
cublasLtMatmulDescCreate(&op, CUBLAS_COMPUTE_32F, CUDA_R_32F);
cublasLtEpilogue_t epi = CUBLASLT_EPILOGUE_BIAS;          // or RELU_BIAS, GELU_BIAS…
cublasLtMatmulDescSetAttribute(op, CUBLASLT_MATMUL_DESC_EPILOGUE, &epi, sizeof(epi));
cublasLtMatmulDescSetAttribute(op, CUBLASLT_MATMUL_DESC_BIAS_POINTER, &bias, sizeof(bias));

// 2 · describe the matrices: dtype, shape, ld — row-major is now a legal order
cublasLtMatrixLayout_t La, Lb, Lc;
cublasLtMatrixLayoutCreate(&La, CUDA_R_16F, m, k, lda);   // …order attribute settable

// 3 · ask the heuristic for kernels, then run the best one
cublasLtMatmulHeuristicResult_t algos[8]; int found;
cublasLtMatmulAlgoGetHeuristic(lt, op, La, Lb, Lc, Lc, pref, 8, algos, &found);
cublasLtMatmul(lt, op, &alpha, A, La, B, Lb, &beta, C, Lc, D, Lc,
               &algos[0].algo, workspace, ws_size, stream);

Three ideas matter more than the boilerplate:

  • Epilogues as attributes. Bias add, ReLU/GELU (with auxiliary output for the backward pass), and scaling ride inside the GEMM's register tail instead of costing an extra kernel and an HBM round-trip of the output — the sealed-box version of CUTLASS's EVT, limited to the menu NVIDIA ships. PyTorch's addmm (Linear with bias) maps straight onto CUBLASLT_EPILOGUE_BIAS.
  • The heuristic is a query, not an oracle. GetHeuristic returns candidates; serious users (TensorRT, inference stacks) benchmark the top few on their real shapes and cache the winner. That's autotuning re-entering through the API's front door.
  • FP8 lives here. Hopper/Blackwell FP8 GEMM is a cublasLt exclusive: E4M3/E5M2 inputs with per-tensor scale pointers, higher-precision accumulate, an amax output for computing the next iteration's scales — the primitive under FP8 serving and FP8 training recipes. Workspace (a few MB) stops being optional if you want the fast algorithms.

Inside the box: a dispatcher over a kernel zoo

A cuBLAS call does no code generation. The library ships thousands of pre-compiled kernels — the CUTLASS-style decomposition instantiated across tile shapes, stage counts, dtypes, and architectures — plus a heuristic that maps your (shape, dtype, layout, arch) onto one of them. That design explains its observable behavior:

Why it's fast

For the shapes deep learning actually runs — the dense square-ish GEMMs of transformer blocks — the mapping is exhaustively tuned per architecture.

Why it has cliffs

Performance vs. shape is piecewise: tile-quantization sawtooth (a dimension one past a tile boundary wastes a whole extra tile) and wave quantization show through the abstraction.

Why it's beatable

Odd shapes (skinny K, weird aspect ratios, tiny batched problems) can fall between tuned kernels — where a CUTLASS profiler search or a custom kernel finds 1.2–2×.

The practical upshot: treat cuBLAS performance as an empirical surface, not a constant. The same reasoning that sizes CUTLASS tiles tells you which of your shapes sit badly on it — and shape hygiene (dimensions divisible by 16, padded vocab sizes) is usually cheaper than replacing the kernel.

Numerics and determinism: the knobs frameworks argue about

  • TF32 — on Ampere+, FP32-typed GEMMs can run on tensor cores with 10-bit mantissas: ~8× faster, ~3 decimal digits. cuBLAS exposes it as a math mode / compute type; PyTorch surfaces it as torch.backends.cuda.matmul.allow_tf32 (default off for matmul, on for cuDNN convs) and torch.set_float32_matmul_precision("high") — the switch the cuTile sample flips before checking correctness against torch.
  • Reduced-precision accumulate — FP16 storage with FP16 accumulate is faster on some parts and quietly dangerous at large \(K\); training recipes accumulate in FP32. cublasLt makes the choice explicit per-call via the compute type.
  • Determinism — cuBLAS is bitwise run-to-run reproducible for the same version, architecture, and shape, except for algorithms that reduce via atomics (some split-K and batched paths), where floating-point addition order varies. torch.use_deterministic_algorithms(True) therefore demands CUBLAS_WORKSPACE_CONFIG=:4096:8 (or :16:8) — pinning workspace so only order-stable algorithms run. Across versions or GPUs, no promise: heuristics change, tiles change, sums reorder. Loss-curve archaeology should never assume otherwise.

Where the box ends

The family tree, for completeness: cublasLt is the DL workhorse; classic cublas wraps it for BLAS compatibility; cublasXt does out-of-core multi-GPU GEMM with host pointers (HPC, not DL); cuBLASDx is a device-side header library for calling BLAS inside your own kernel — the fusion escape hatch, adjacent to writing CUTLASS directly.

Rule of thumb — completing the ladder

Start here: if your operation is a dense matmul (± the stock epilogues) on healthy shapes, cuBLAS/cublasLt is one call away from peak, and nothing on this shelf will beat it by enough to matter. Leave when one of three things is true: you need a fusion it doesn't offer (→ Triton/cuTile, or FlashAttention's fate), your shapes sit in its cliffs (→ CUTLASS search or grouped GEMM), or the op isn't a matmul at all (→ the whole SIMT toolbox). The kernel-programming ladder on this site is, in effect, a taxonomy of reasons to leave this library.
