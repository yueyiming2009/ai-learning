GPU Kernels in cuTile

CUDA's native tile programming model — write kernels as operations on whole tiles, let the compiler own threads, shared memory, and tensor cores, and compile through Tile IR, a new virtual ISA built for forward compatibility.

Pre-reading: GPU Kernels in Triton — cuTile lives at the same block-level altitude, and this page constantly compares the two. GPU Kernels in CuTe DSL covers NVIDIA's thread-level DSL, the other end of the control spectrum. GPU Hardware for ML for the memory hierarchy and tensor cores everything here is compiled onto.

What cuTile is: tiles become a first-class CUDA citizen

For eighteen years CUDA offered exactly one programming model: SIMT — you decide what every thread does, and all structure above the thread (warps, tiles, staging through shared memory) is convention you build by hand. Triton demonstrated that for most deep-learning kernels a tile-level model is the right altitude: describe operations on blocks of data, let a compiler assign threads. With CUDA 13.1 (December 2025), NVIDIA adopted that conclusion into CUDA itself: CUDA Tile is a new tile-based programming model alongside SIMT, and cuTile Python (pip install cuda-tile) is its first DSL — with a C++ implementation announced to follow.

Two design decisions distinguish it from "NVIDIA's Triton clone":

  • A virtual ISA underneath. cuTile kernels compile to Tile IR, a documented tile-level instruction set that the driver's tileiras compiler lowers to each GPU generation. Tensor cores, TMA, and whatever replaces them are targets of the IR, not features of your source: the promise is that tile code written today recompiles onto future architectures at full speed, the way PTX carried SIMT code forward. Other languages can target the same IR — a Julia frontend (cuTile.jl) already exists.
  • Arrays and tile indices instead of pointers and masks. Kernels receive real arrays (a PyTorch/CuPy tensor passes straight through via DLPack, shape and strides included) and load tile number k of a declared tile shape. Out-of-bounds handling is a padding_mode argument, not eight lines of offset-and-mask arithmetic.

Three altitudes for the same hardware. The line that moves is who owns the thread↔data mapping. cuTile and Triton sit at the same altitude; cuTile's bet is that owning the whole stack — language, IR, and the tileiras compiler that knows each architecture's tensor cores natively — closes the performance gap while keeping the tile model's economy of expression.

The supported-hardware matrix is the one genuinely surprising fact: at launch, Tile IR compiles for Ampere, Ada, and Blackwell (compute capability 8.x, 10.x–12.x) — not Hopper. Hopper support (9.x) is listed as coming in a future version. Running it needs CUDA Toolkit 13.1+ and driver r580+.

The execution model: blocks compute, tiles are values

The abstract machine is small enough to state completely. A kernel is executed by a 1-/2-/3-D grid of logical blocks. Each block runs the whole kernel body: scalar operations execute serially (conceptually on one thread), and tile operations execute collectively across the block's execution resources. That is the entire parallelism story you're shown — individual threads are not exposed at all, and explicit synchronization within a block is not just unnecessary but disallowed. Coordination between blocks remains your job, via atomics (the LayerNorm sample serializes cross-block gradient accumulation with an atomic_cas spin-lock and acquire/release memory orders).

Block — unit of execution

Runs the kernel body. Tile ops parallelize across it; scalars are serial. No thread IDs, no __syncthreads.

Tile — unit of data

An immutable value with no defined storage — registers, shared memory, TMEM: the compiler's call. Shapes are compile-time constants, powers of two.

Array — the data at rest

A global-memory view with runtime shape/strides (your PyTorch tensor). Mutable through loads/stores; must not alias other array arguments.

Two consequences are worth pausing on. First, because tiles have no storage, the register-vs-shared-memory question — the central obsession of the thread-level style — simply is not in the language; the compiler places data per target. Second, everything in tile code is immutable: an operation that "modifies" a tile returns a new one. That functional flavor is what gives the compiler freedom to reorder, fuse, and pipeline tile operations, and it makes kernels read like NumPy rather than like CUDA.

Kernel parameters annotated ct.Constant[...] are constant-embedded: the kernel is specialized and compiled per unique value, exactly like a C++ template parameter or Triton's tl.constexpr — this is how tile shapes meet their compile-time-constant requirement while remaining ordinary function arguments.

First kernel: vector add, with no pointers in sight

import cuda.tile as ct
import torch

TILE = 256

@ct.kernel
def vector_add(a, b, c):
    bid = ct.bid(0)                                  # which tile am I?
    ta = ct.load(a, index=(bid,), shape=(TILE,),
                 padding_mode=ct.PaddingMode.ZERO)   # tile #bid, OOB reads 0
    tb = ct.load(b, index=(bid,), shape=(TILE,),
                 padding_mode=ct.PaddingMode.ZERO)
    ct.store(c, index=(bid,), tile=ta + tb)          # edge tiles clipped automatically

a = torch.randn(1_000_000, device="cuda")
b = torch.randn(1_000_000, device="cuda")
c = torch.empty_like(a)

grid = (ct.cdiv(a.shape[0], TILE), 1, 1)
ct.launch(torch.cuda.current_stream(), grid, vector_add, (a, b, c))

Structurally this is the Triton vector add — one block per tile, a grid of cdiv(N, TILE) blocks — but the addressing model is where the two languages part ways:

Triton: pointers + masks

offs = pid * BS + tl.arange(0, BS)
mask = offs < n
x = tl.load(x_ptr + offs, mask=mask)

You reconstruct the array from a raw pointer, and every edge case is your mask. Flexible — and the source of most first-week Triton bugs.

cuTile: arrays + tile indices

x = ct.load(arr, index=(pid,),
            shape=(BS,),
            padding_mode=ZERO)

The array keeps its shape and strides; you name a tile by index. Bounds, padding, and (on edge stores) clipping are the runtime's problem.

Because tile shapes are compile-time constants, TILE can be a captured Python global (as here), a ct.Constant[int] parameter, or any constant expression — and each distinct value produces its own compiled specialization.

A real kernel: tiled matmul on tensor cores

This is the shipped samples/MatMul.py kernel, lightly simplified to a 2-D grid (the original linearizes the grid and applies a group swizzle for L2 reuse, exactly like Triton's canonical matmul). Each block owns one \((t_m, t_n)\) tile of \(C\) and marches over \(K\):

ConstInt = ct.Constant[int]

@ct.kernel(num_ctas=ct.ByTarget(sm_100=2))       # 2 cooperating CTAs on Blackwell
def matmul_kernel(A, B, C, tm: ConstInt, tn: ConstInt, tk: ConstInt):
    bidx, bidy = ct.bid(0), ct.bid(1)
    num_k = ct.num_tiles(A, axis=1, shape=(tm, tk))   # K-extent in tiles

    acc = ct.full((tm, tn), 0, dtype=ct.float32)      # fp32 accumulator
    dtype = ct.tfloat32 if A.dtype == ct.float32 else A.dtype  # tf32 → tensor cores

    for k in range(num_k):
        a = ct.load(A, index=(bidx, k), shape=(tm, tk),
                    padding_mode=ct.PaddingMode.ZERO).astype(dtype)
        b = ct.load(B, index=(k, bidy), shape=(tk, tn),
                    padding_mode=ct.PaddingMode.ZERO).astype(dtype)
        acc = ct.mma(a, b, acc)                       # tile × tile + acc

    ct.store(C, index=(bidx, bidy), tile=ct.astype(acc, C.dtype))

Now compare this against the CuTe DSL GEMM skeleton and notice everything that is absent: no shared-memory tensors, no cp.async/TMA copy atoms, no ldmatrix, no swizzled smem layouts, no pipeline stages, no barrier choreography. All of it still happens — the tileiras compiler stages tiles through shared memory, drives TMA, selects mma.sync on Ampere or tcgen05 on Blackwell, and software-pipelines the K-loop — but it happens below the IR, per target. The one hardware-generation fact in the source is a tuning annotation, not code: num_ctas=ct.ByTarget(sm_100=2) requests Blackwell's paired-CTA mode, and is ignored where it doesn't apply.

Beyond matmul: the op vocabulary

Tiles support NumPy-style elementwise math and broadcasting, ct.sum/reductions and scans along axes, ct.where, ct.arange, ct.transpose, type casts, and atomics with explicit memory orders. The samples directory covers the practical span: LayerNorm (cross-tile reduction loops), FMHA (attention), batched and block-scaled matmul, MoE, FFT, and a distributed all-gather+matmul — plus NVIDIA's TileGym repo with more. A persistent-kernel variant is idiomatic: launch min(num_SMs, num_tiles) blocks and stride tiles by ct.num_blocks(0).

Tile IR: the part that isn't a DSL

Everything above could be (and in Triton, is) implemented as a compiler bolted onto the side of CUDA. The structural novelty is that NVIDIA specified the tile machine as an ISA. The stack:

LayerArtifactAnalogue in SIMT CUDA
cuTile Python (today), C++ (announced), cuTile.jlPython source, traced per launchCUDA C++
Tile IR — documented virtual ISA for tile programsportable bytecodePTX
tileiras (in the driver / toolkit)per-architecture SASSptxas

The compilation flow follows: ct.launch specializes the kernel for its concrete arguments (dtypes, constant-embedded values) and JIT-compiles with caching; cuda.tile.compilation.export_kernel does it ahead of time instead, emitting either a cubin for a specific GPU or Tile IR bytecode that the driver finishes compiling on whatever GPU it meets — the forward-compatibility path. AOT export requires spelling out the parameter constraints (alignments, divisibility, constants) that JIT would have inferred from example arguments.

The strategic read

PTX made SIMT programs outlive their hardware; Tile IR is the same bet one level up. Tensor-core generations have been churning (mma.sync → wgmma → tcgen05 in three architectures — the reason the CuTe atom table exists), and NVIDIA's answer is to make the tile op the stable contract and absorb that churn inside the compiler. Kernels that must exploit a generation's quirks by hand keep CuTe; kernels that express an algorithm keep recompiling.

Tuning without touching threads

You can't reorder warps or resize a shared-memory buffer — so performance work happens through declared knobs and hints, all of which are semantically optional:

KnobWhat it does
tm/tn/tk tile shapesThe dominant lever, exactly as in Triton — passed as ct.Constant parameters, one compiled specialization per value.
ct.ByTarget(...)Per-architecture values for kernel config — num_ctas, occupancy, opt_level — e.g. paired CTAs only on sm_100.
latency=1..10 on load/storeDeclares how DRAM-heavy the access is; guides prefetch depth in the generated pipeline.
allow_tma=True/FalsePermits or forbids lowering a load/store to TMA (allowed by default where supported).
ct.assume_divisible_by(n, 16)Unchecked divisibility promise on a runtime scalar; propagates through derived indices so dynamic slices still get aligned, wide memory ops.
ct.tune.exhaustive_searchBuilt-in autotuner: benchmark a config space, keep the winner.

The pattern to notice: every knob is a declaration about the problem (this scalar is aligned; this access is heavy; this target has CTA pairs), never an instruction about the machine. That's what keeps the source portable across the IR's targets.

Rule of thumb

Reading the three as one landscape: Triton is the portable incumbent with the ecosystem; cuTile is the same programming model with a cleaner addressing story and NVIDIA's compiler underneath — the natural choice when you're NVIDIA-only and want tile code that survives architecture churn; CuTe DSL is for the kernels where the compiler's choices are the bottleneck and you need to place every value yourself. The realistic 2026 stack uses Triton/cuTile for the long tail of fused kernels and CuTe for the handful of GEMM/attention kernels where the last 20% lives.
