Sharding & Collectives — The Communication Math

Every flavor of parallelism is the same matmuls and norms you already know, split across devices and stitched back with a handful of collective operations. This page builds the notation and the cost model: how a sharded array is described, what communication a sharded matmul forces, and exactly how much each collective costs.

Training a large model on ten thousand accelerators looks, abstractly, identical to training on one: the same matmuls, the same nonlinearities, the same backward pass. The only new thing is that the arrays no longer fit in the memory of a single device, so we split them up — we shard (or partition) them across a mesh of devices. The moment a computation needs to reduce or contract along a dimension that has been split, the devices must talk, and that conversation is a collective.

This is the foundation page for the whole parallelism series. Tensor, data, pipeline, sequence, and expert parallelism are all just different choices of which array dimensions to shard — and the bill always comes due in the four collectives priced below (plus, for pipeline stages, plain point-to-point sends). The hardware these prices stand on lives one page down, in GPU Interconnect → and TPU Hardware →; the engine that actually runs them lives in NCCL →. Get this page right and the rest is bookkeeping.

The sharding notation follows “How to Scale Your Model” (Google DeepMind) — it is the clearest tool there is for reading communication off a matmul.

1 · Why we shard

A 70B-parameter model in bf16 is 140 GB of weights alone. Training it under mixed-precision AdamW costs 16 bytes per parameter — weights, gradients, fp32 master copy, and the two Adam moments — so the resident state is \(70\times10^9 \times 16 \approx 1.1\) TB before a single activation is stored. No accelerator has that much high-bandwidth memory (HBM is \(O(10\!-\!100)\) GB per chip). So we cut each array into blocks and scatter them across many devices.

A sharded array has two shapes:

  • a global (logical) shape — what the math sees, e.g. a weight matrix \([D, F]\);
  • a device-local shape — the block that physically lives on one device, e.g. \([D, F/|X|]\) if the second axis is split across \(|X|\) devices.

The art is choosing shardings so that as much arithmetic as possible stays local (no communication), and so that the communication you cannot avoid is the cheap kind.

2 · A notation for sharding

Picture the devices arranged in a grid — a device mesh — whose axes are given names \(X, Y, Z\). The mesh axis \(X\) has \(|X|\) devices along it. We then describe a sharding by writing, next to each logical array axis, which mesh axis it is split over, as a subscript.

Reading the notation
  • A[IX, JY] — the array \(A\) with its first axis \(I\) split across mesh axis \(X\) and its second axis \(J\) split across \(Y\). Each device holds \(1/(|X|\,|Y|)\) of the tensor.
  • No subscript ⇒ replicated. A[I, JX] means \(I\) is fully present on every device; only \(J\) is split.
  • A[IXY, J] — axis \(I\) split across the flattened \(X\!\times\!Y\) mesh (all \(|X||Y|\) devices). Subscript order sets the traversal order across the grid.
  • Rule: a given mesh axis may appear at most once across a tensor — you cannot shard two logical axes onto the same physical axis (there aren’t enough devices to be in two places at once).

The unreduced marker \(\{U_X\}\)

There is one more state an array can be in, and it is the crux of the whole subject. Suppose two operands are each split along a contracting dimension. Every device can multiply its local blocks, but the product it gets is only a partial sum — the piece of the dot product that used the data it happened to hold. The full result is the sum of these partials across the mesh. We mark that “sum still owed” state as

Unreduced along X
C[I, K] {UX}  —  “each device on \(X\) holds a different partial sum; a reduction along \(X\) is pending.”

\(\{U_X\}\) is not a sharding (every device has a full-shape \([I,K]\) array) and it is not replication (the arrays disagree). It is an obligation. Resolving it — turning partial sums into the true sum — is exactly what the reducing collectives do.

3 · What a collective costs

A GPU communicates by pushing bytes through its links — NVLink into the node’s NVSwitch, a NIC into the cluster fabric. GPU Interconnect §1–2 builds that machinery in detail; the one property we need here is the headline: the NVSwitch is a non-blocking crossbar, so every GPU can drive its full link bandwidth to every other GPU at the same time, with no shared bottleneck and no notion of distance. That collapses the whole topology into one number per GPU: \(W\), the bandwidth it has into the fabric.

With that, the cost of a collective is just how many bytes each GPU must move through its links, divided by \(W\) — and because the crossbar is non-blocking, every GPU does this concurrently, so the slowest GPU sets the time. Take an array of \(V\) bytes spread as \(V/N\) shards across \(N\) GPUs and count the bytes for an AllGather: each GPU already holds its own \(V/N\), so it only needs to take in the other \(N-1\) shards — \(V\,(N-1)/N\) bytes across its link. Hence:

Bandwidth-bound collective time
\[ T \;=\; \frac{V}{W}\cdot\frac{N-1}{N} \;\xrightarrow[\;N\ \text{large}\;]{}\; \frac{V}{W}. \]

Two facts fall out, and they drive every parallelism decision in the series:

  1. The cost barely depends on \(N\). The factor \((N-1)/N\) is “you don’t pay to move the shard you already have”; it is within 25% of 1 by \(N=4\) and \(\to 1\) after. The crossbar is non-blocking, so adding GPUs adds no contention — the price is set by one GPU’s link speed, not the device count.
  2. The cost scales with the array size \(V\), not the mesh. The lever you actually control is how big the communicated tensors are — which is exactly what each parallelism scheme trades against.
This is the number you measure. NCCL reports exactly this quantity as bus bandwidth (busbw in nccl-tests): bytes-moved-per-GPU ÷ time. It applies a per-collective multiplier — \((N-1)/N\) for AllGather/ReduceScatter, \(2(N-1)/N\) for AllReduce — precisely so the figure approximates peak link bandwidth and is comparable across collectives and GPU counts. When busbw nears your NVLink/NIC bandwidth, the collective is running optimally.

The one fact that shapes everything: bandwidth comes in two tiers

\(W\) is not a single number. Recapping GPU Interconnect §2: it drops by an order of magnitude at the edge of the NVLink domain —

LinkScopePer-GPU bandwidth \(W\)
NVLink + NVSwitchwithin one node (≤8 GPUs)~450 GB/s each way (H100)
InfiniBand / Ethernet NICacross nodes~50 GB/s (one 400 Gb/s NIC/GPU)

That ~10× cliff is the reason the parallelism schemes are layered the way they are. A collective that fires often and on the critical path — like the per-block AllReduce of tensor parallelism — must stay on NVLink, which caps it to a single node. A collective that is rare (a once-per-step gradient AllReduce in data parallelism) or point-to-point and overlappable (pipeline-stage activations) can afford to cross the slow network. Every later page is, at heart, a decision about which tier each collective lands on.

Small messages: the latency floor

Bandwidth isn’t the whole story for tiny transfers. Every collective also pays a fixed start-up/latency term \(L\) — propagation and per-step overhead that a few bytes can’t amortize. The realistic cost is the larger of the two regimes:

\[ T \;=\; \max\!\Big(\; \underbrace{L}_{\text{latency-bound}}\;,\; \underbrace{\tfrac{V}{W}\cdot\tfrac{N-1}{N}}_{\text{bandwidth-bound}} \;\Big). \]

How small \(L\) can be made is a scheduling question — ring schedules pay \(O(N)\) latency, tree schedules \(O(\log N)\), and NCCL picks per message size — and the whole story lives in NCCL →. For training it rarely matters: gradients and activations are megabytes to gigabytes, firmly bandwidth-bound. At inference/sampling time, where a step may reduce only a few kilobytes, the latency term is the one you feel. (On a TPU the same two-regime formula holds, but the ring is physical — chips are wired as a nearest-neighbor torus — so the \(O(N)\) latency is baked into the hardware rather than a scheduling choice.)

4 · AllGather — undo a sharding

The first primitive removes a subscript: it reassembles a split axis so every device ends up with the full, un-sharded array along that axis.

AllGather over X
A[I, JX]  →  A[I, J]

Counting bytes: every GPU is missing \(N-1\) of the \(N\) shards, so it must take in \(V\,(N-1)/N\) bytes (equivalently, it broadcasts its own \(V/N\) shard out to the \(N-1\) others). On the crossbar all of those transfers run at once, so the time is just that per-GPU volume over the link bandwidth:

AllGather cost
\[ T_\text{AG} \;=\; \frac{V}{W}\cdot\frac{|X|-1}{|X|}\;\approx\;\frac{V}{W}, \qquad V = \text{bytes of the full (gathered) array.} \]

AllGather does not have to remove all sharding — it can collapse one mesh axis while leaving others — and, in a matmul, you are free to do it before or after the local multiply, whichever keeps the moved tensor smaller. The widget in §6 animates it (first tab), alongside the two reducing collectives it composes into.

5 · ReduceScatter — reduce, but stay split

ReduceScatter resolves an unreduced axis and leaves the result sharded. Picture the \(\{U_X\}\) state concretely: every GPU holds a full-shape array of partial sums. Designate GPU \(d\) the owner of slice \(d\) of the output. Then each GPU keeps its own slice’s partial, ships the other \(N-1\) partial slices to their owners, and adds up the \(N-1\) foreign partials that arrive for the slice it owns. Each GPU walks away with the fully-summed value of exactly one slice — the array is reduced and a new subscript has appeared:

ReduceScatter over X, sharding the J axis
A[I, J] {UX}  →  A[I, JX]

The traffic is the mirror image of an AllGather — sends where AllGather had receives — so each GPU pushes the same \(V\,(N-1)/N\) bytes through its link, and it costs the same:

\[ T_\text{RS} \;=\; \frac{V}{W}\cdot\frac{|X|-1}{|X|}\;\approx\;\frac{V}{W}. \]

Note the freedom: a ReduceScatter introduces a new sharded dimension, and you get to pick which one. Resolving \(\{U_X\}\) on a \([I,K]\) array, you may land on either A[IX, K] or A[I, KX] — the modeling context usually forces the choice, which is why we write the target axis explicitly, e.g. ReduceScatterX,K.

6 · AllReduce — reduce and replicate

The most familiar collective (it is what vanilla data-parallel training calls on its gradients) resolves an unreduced axis and leaves the true sum replicated on every device.

AllReduce over X
C[I, K] {UX}  →  C[I, K]

But notice what it is: first sum the partials and scatter (ReduceScatter), then gather the scattered sums back to everyone (AllGather). Each GPU therefore both sends and receives ~\(V(N-1)/N\) — twice the byte movement of either half.

AllReduce = ReduceScatter ∘ AllGather
\[ T_\text{AR} \;=\; T_\text{RS} + T_\text{AG} \;=\; 2\cdot\frac{V}{W}\cdot\frac{|X|-1}{|X|}\;\approx\;\frac{2V}{W}. \]
AllReduce is twice the price of the others. Whenever the downstream computation can live with a sharded result, prefer a ReduceScatter and skip the gather — you only pay to re-replicate when you actually need the full array on every device. Half the comm volume of a layer can hinge on this single choice.

Why \(2V/W\) is the floor

RS ∘ AG is not just a way to do an AllReduce — it is bandwidth-optimal, and the counting argument is short. Track a single byte-position of the output. Its final value is the sum of \(N\) partials, one per GPU, and at the end every GPU must hold it. Two costs are unavoidable:

  • Reducing. An addition can only happen where both operands sit on the same device, so at least \(N-1\) of the \(N\) partials must cross the fabric to get folded in: \(N-1\) transmissions.
  • Distributing. Once fully summed, the value lives on whichever GPU finished the sum; the \(N-1\) others must each receive it (or a contribution that lets them finish it — either way a transmission): \(N-1\) more.

So every byte-position forces at least \(2(N-1)\) crossings — \(2V(N-1)\) bytes of total fabric traffic — and all of it must leave through just \(N\) egress links. The best any schedule can possibly do is spread that traffic perfectly evenly:

AllReduce bandwidth lower bound
\[ T_\text{AR} \;\ge\; 2\cdot\frac{V}{W}\cdot\frac{|X|-1}{|X|} \]

— exactly the cost above, with zero slack. The decomposition meets the bound because each half wastes nothing: ReduceScatter pays only the \(N-1\) reduction crossings per position (each partial travels once and is consumed by an add), AllGather pays only the \(N-1\) deliveries (finished bytes, no more math), and both keep every link uniformly busy. The trick is the intermediate state — each output slice fully summed on exactly one owner — which is the cheapest possible halfway point: the reduce phase builds one copy of each sum, not \(N\), and the gather phase only copies.

The naive alternative shows what the bound protects you from. Reduce everything to one root, then broadcast: the mandatory bytes are the same, but they all crowd one port — the root takes in \(V(N-1)\) and pushes out \(V(N-1)\) while the other \(N-1\) links sit mostly idle. That is ≈\(N\times\) the optimum. The lower bound is a per-link statement, so hitting it is entirely about balance.

7 · AllToAll — move a subscript sideways

The fourth primitive is a resharding / transpose: it takes an axis that is split and replicates it, while splitting a different axis along the same mesh dimension. It is how a computation hands off between two regions that want incompatible layouts — most notably the token routing around a Mixture-of-Experts block.

AllToAll over X
A[IX, J]  →  A[I, JX]

Count the bytes carefully, because they are not the same as an AllGather’s. The array stays sharded throughout — no device ever materializes the full \(V\) bytes. Each GPU holds a \(V/N\) block, carved into \(N\) pieces of \(V/N^2\): it keeps the piece destined for itself, sends the other \(N-1\) pieces to their owners (one each, all in parallel through the switch), and receives \(N-1\) pieces in exchange. Per-GPU traffic:

AllToAll cost
\[ T_\text{A2A} \;=\; \frac{V}{N\,W}\cdot\frac{N-1}{N}\;\approx\;\frac{V}{N\,W} \;=\;\frac{T_\text{AG}}{N}. \]

So an AllToAll is roughly \(N\times\) cheaper than an AllGather of the same logical array. The intuition: AllGather amplifies data — every shard must end up on every device, so the fabric carries \(N\) copies. AllToAll only rearranges it — each byte has exactly one destination. Resharding is cheap; replicating is what costs.

On a TPU torus the discount is smaller. There, pieces must hop through intermediate chips, and the byte-hop accounting works out to ≈\(\tfrac14\) of an AllGather (the scaling-book figure) rather than \(1/N\). Either way the ranking holds: AllToAll < AllGather/ReduceScatter < AllReduce.

8 · What a sharded matmul forces

Now the payoff. Take any matmul \(A \cdot B \to C\) contracting over a shared axis \(J\). Whether it needs communication — and which collective — is decided entirely by how the contracting axis \(J\) is sharded. Three cases cover everything.

Case 1 — contracting axis not sharded → free

A[IX, J] · B[J, KY] → C[IX, KY]
Each device holds whole rows and whole columns of the contraction, so the local block product is already a correct shard of the output. No communication. The output simply inherits the input shardings on the non-contracting axes.

Case 2 — one operand sharded on the contraction → AllGather

A[I, JX] · B[J, K] → C[I, K]
\(A\) is missing the rest of its contracting axis. AllGather it first, then multiply locally:
AllGatherX: A[I, JX] → A[I, J], then A[I, J] · B[J, K] → C[I, K]. Cost = one AllGather.

Case 3 — both operands sharded on the contraction → AllReduce or ReduceScatter

A[I, JX] · B[JX, K] → C[I, K] {UX}
Local block products are valid partial sums — the output is born unreduced. Resolve it:

  • need the full result everywhere → AllReduceX (cost \(2V/W\)); or
  • happy to keep it split → ReduceScatterX → C[I, KX] (cost \(V/W\), half as much).

Non-contracting dimensions never force communication — they pass their sharding straight from inputs to output. And a sharding that puts the same mesh axis on two axes of one tensor, e.g. A[IX, J] · B[J, KX] → C[IX, KX], is simply illegal (\(X\) can’t appear twice); you fix it by AllGathering one of the axes before the multiply.

The one-sentence summary of Section 8

A sharded matmul is free unless its contracting axis is split — in which case you pay one AllGather (if one operand is split) or one AllReduce / ReduceScatter (if both are). Every parallelism scheme in this series is a way of arranging matmuls to land in Case 1 as often as possible, and to make the unavoidable Case 3 reductions small.

9 · Forward/backward duality

A convenient theorem ties the collectives together under autodiff: the backward pass of an AllGather is a ReduceScatter, the backward of a ReduceScatter is an AllGather — and the backward of an AllReduce is another AllReduce. None of this needs to be memorized; it falls out of three small observations.

Observation 1 — backprop through a linear op applies its transpose

A collective only copies and adds numbers — it is a linear map \(A\) on the stacked per-device data. Backprop through any linear map \(y = Ax\) multiplies the incoming gradient by the transpose: \(\partial L/\partial x = A^\top \,\partial L/\partial y\). So the question “what is the backward of this collective?” is really “what communication pattern is \(A^\top\)?”

Observation 2 — copy and sum are transposes of each other

The classic autodiff duality: a fan-out in the forward becomes a fan-in in the backward. Run the §6 widget in your head, in reverse:

  • AllGather forward: GPU 0 ships copies of its shard to GPUs 1–3. In the backward pass each of those GPUs holds its own gradient w.r.t. its copy — and since all copies are the same variable, those gradients must be summed into shard 0’s gradient. Ship foreign partials to the owner, add on arrival: that is exactly ReduceScatter’s send-and-sum, running the same wires in reverse. Hence AllGatherX⊤ = ReduceScatterX.
  • ReduceScatter forward: contributions are summed, and GPU 0 keeps only slice 0. The backward of a sum is a broadcast — \(\partial(\textstyle\sum_i x_i)/\partial x_i = 1\), so every contributor receives the output’s gradient unchanged — and every GPU contributed to every slice, so each GPU needs the gradient of all \(N\) slices, each fetched from its owner. Everyone gathers every slice: ReduceScatterX⊤ = AllGatherX.
Observation 3 — transposing a composition flips each factor and reverses the order

Now apply both to the §6 decomposition AllReduce = AllGather ∘ ReduceScatter:

\[ \text{AR}^\top \;=\; (\text{AG}\circ\text{RS})^\top \;=\; \text{RS}^\top \circ\, \text{AG}^\top \;=\; \text{AG}\circ\text{RS} \;=\; \text{AR}. \]

The order reversal swaps the two halves; transposing each half swaps them back. The two flips cancel — AllReduce is self-adjoint.

Adjoint pairs
AllGatherX (fwd)  ⟺  ReduceScatterX (bwd)
ReduceScatterX (fwd)  ⟺  AllGatherX (bwd)
AllReduceX (fwd)  ⟺  AllReduceX (bwd, self-adjoint)
AllToAllX (fwd)  ⟺  AllToAllX (bwd, the inverse permutation)

The AllReduce case can also be seen directly, without the decomposition. Forward, it computes \(y = \sum_i x_i\) and replicates it, so every input touches every replica with coefficient 1. By symmetry, \(\partial L/\partial x_i = \sum_d \partial L/\partial y_d\) for every \(i\): sum the per-device cotangents, hand everyone the result — which is the definition of an AllReduce on the gradients. (In matrix form an AllReduce is \((\mathbf{1}\mathbf{1}^\top)\otimes I\), and \(\mathbf{1}\mathbf{1}^\top\) is symmetric.)

The fine print: “backward = AllReduce” assumes the incoming gradients are partials. The transpose rule treats the per-device cotangents as genuine partial sums (the {UX} state) — each device’s replica feeding a different downstream computation. In Megatron-style tensor parallelism the computation after the forward AllReduce is replicated instead, so in the backward pass every device already holds the complete, fully-reduced gradient — AllReducing those identical copies would overcount by \(N\times\). That is why Megatron’s conjugate operators read \(g\) = (AllReduce fwd, identity bwd) and \(f\) = (identity fwd, AllReduce bwd): the block still pays one AllReduce per leg, but the backward one comes from \(f\) at the block’s input — where a replicated activation fed two sharded branches, whose gradient contributions really are partials that need summing — not from re-running \(g\)’s.

The accounting corollary: counting communication for a forward pass immediately gives the backward cost. Replace each collective with its dual — same price, since AllGather and ReduceScatter cost the same and the other two are self-dual. In particular, whatever AllReduce traffic a layer pays forward, it pays again backward: the \(2V/W\) shows up on both legs.

10 · The same four, in code

The notation on this page is the analysis tool; in a real training script the collectives go by their API names. The mapping is one-to-one — keep it handy when crossing into torch.distributed →:

This pagetorch.distributedNCCL verbJAX (lax)
AllGatherX all_gather_into_tensor ncclAllGather all_gather
ReduceScatterX reduce_scatter_tensor ncclReduceScatter psum_scatter
AllReduceX all_reduce ncclAllReduce psum
AllToAllX all_to_all_single grouped ncclSend/ncclRecv all_to_all

Two footnotes. The “All” in each name means every rank both contributes and receives; each has a cheaper one-rooted relative (broadcast, reduce, gather, scatter) that occasionally appears in checkpointing or logging paths. And point-to-point send/recv is the one primitive here that is not a collective at all — it is how pipeline parallelism passes activations between stages, and it prices by the same \(V/W\) logic with \(N=2\).

11 · Summary

CollectiveWhat it doesSharding changeBytes/GPU ÷ \(W\)
AllGather Reassemble a split axis; remove a subscript. A[JX] → A[J] \(\frac{V}{W}\cdot\frac{N-1}{N}\)
ReduceScatter Sum a partial axis and re-split along another; add a subscript. A{UX} → A[JX] same as AllGather
AllReduce Sum a partial axis; replicate the result. Removes a \(\{U_X\}\). A{UX} → A \(2\times\) AllGather
AllToAll Replicate one axis while splitting another on the same mesh axis (resharding / transpose). A[IX] → A[JX] \(\approx \frac{V}{N\,W}\) — \(\tfrac{1}{N}\) of AllGather
Sharding

A mesh names physical axes \(X,Y\); a sharding maps logical array axes onto them. No subscript = replicated; \(\{U_X\}\) = a sum still owed.

When comm happens

Only when you reduce/contract along a sharded axis. Element-wise ops on sharded arrays are always free.

The cost law

\(T \approx V/W\): bytes each GPU pushes through its links ÷ link bandwidth \(W\) — almost independent of device count.

Two-tier \(W\)

NVLink inside a node (~450 GB/s) vs network across nodes (~50 GB/s). Keep chatty collectives on NVLink — this is why TP stays in one node.

Cheapest first

Reshard (AllToAll, \(V/NW\)) < reduce sharded (ReduceScatter, \(V/W\)) < reduce replicated (AllReduce, \(2V/W\)). Pay to replicate only when you must.
