CUDA — The SIMT Programming Model

The layer under everything: threads, warps, blocks and grids, memory and coalescing, the barrier/fence hierarchy, and two canonical kernels — the substrate that Triton, CuTe DSL, and cuTile all compile down to.

Pre-reading: GPU Hardware for ML — this page is the software contract over that hardware (SMs, HBM, SRAM, tensor cores), and assumes you've seen the physical side. The PyTorch Execution Model shows where kernel launches come from in an ML program. The DSL pages — Triton, CuTe DSL, cuTile — all define themselves against what's on this page.

The contract: scalar code, executed thirty-two at a time

CUDA (2006) is built on one idea: you write an ordinary-looking scalar function — the kernel — describing what a single thread does, and you launch it across tens of thousands of threads at once. Each thread discovers who it is from built-in index variables and uses that identity to pick its slice of the data. That's the whole model; everything else on this page is the fine print.

The execution style is called SIMT — single instruction, multiple threads. It sits deliberately between two older ideas. Unlike SIMD, you never write vector instructions: each thread has its own registers, its own control flow, its own addresses. Unlike true independent threads, the hardware executes them in groups of 32 called warps, one shared instruction at a time. The programming model sells you the scalar-thread illusion; the performance model is about knowing where the illusion ends — warps are where coalescing, divergence, and occupancy live.

A CUDA program is heterogeneous: host (CPU) code allocates memory, moves data, and launches kernels; device (GPU) code is the kernels themselves. Function qualifiers mark the boundary — __global__ for kernels (called from host, run on device), __device__ for device-side helpers — and the triple-chevron syntax kernel<<<grid, block>>>(args) is a kernel launch: an asynchronous request to run grid × block threads.

The thread hierarchy, and what each level buys you

Threads are organized in a two-level hierarchy, and the levels are not administrative — each one is a capability boundary:

Grid

one kernel launch

Blocks, independently schedulable in any order onto any SM. No sync between them within a kernel — independence is what makes the grid scale across 1 SM or 132.

→

Block (CTA)

≤ 1024 threads, lives on one SM

The cooperation unit: threads in a block share shared memory and can barrier at __syncthreads(). Sliced into warps of 32.

→

Warp

32 lanes, one instruction

The hardware execution unit — invisible in the syntax, decisive for performance. Lanes exchange registers directly via shuffles.

Each level is a capability boundary. Grid: scalability through independence. Block: cooperation through shared memory and barriers. Warp: lockstep execution and register-level communication. The launch configuration <<<grid, block>>> chooses the first two sizes; the warp's size (32) is the one number you don't choose.

Inside a kernel, four built-ins locate a thread: threadIdx (position in its block), blockIdx (block's position in the grid), blockDim and gridDim (the sizes). All are 3-component vectors — the 1/2/3-D shapes are pure convenience for indexing images and matrices; the hardware only sees flat blocks.

First kernel: vector add, with everything visible

The same kernel that opens the Triton, CuTe DSL, and cuTile pages, at the bottom of the stack — nothing abstracted:

__global__ void vector_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // who am I?
    if (i < n)                                       // last block may overhang
        c[i] = a[i] + b[i];                          // my one element
}

And the host side — the part every DSL hides but every framework still executes underneath:

float *a, *b, *c;
cudaMalloc(&a, n * sizeof(float));                  // device (HBM) allocations
cudaMalloc(&b, n * sizeof(float));
cudaMalloc(&c, n * sizeof(float));
cudaMemcpy(a, host_a, n * sizeof(float), cudaMemcpyHostToDevice);
cudaMemcpy(b, host_b, n * sizeof(float), cudaMemcpyHostToDevice);

int threads = 256;                                  // block size: multiple of 32
int blocks  = (n + threads - 1) / threads;          // ceil(n / threads)
vector_add<<<blocks, threads>>>(a, b, c, n);        // async: returns immediately

cudaMemcpy(host_c, c, n * sizeof(float), cudaMemcpyDeviceToHost);  // implicit sync

Three things to internalize, because every page above this one refers back to them:

  • The index formula blockIdx.x * blockDim.x + threadIdx.x is the SIMT primitive that Triton wraps as pid * BLOCK_SIZE + tl.arange(...), CuTe generalizes into layouts, and cuTile replaces with tile indices. It is the thread↔data mapping, written by hand, one thread at a time.
  • The bounds check if (i < n) is the ancestor of Triton's mask=, CuTe's coordinate-tensor predication, and cuTile's padding_mode.
  • Launches are asynchronous — the CPU queues the kernel (a few µs of overhead) and moves on. This is the fact the PyTorch execution model is built around, for better (overlap) and worse (launch-bound small ops).

When the grid can't cover the data, or you want fewer, longer-lived blocks, the idiom is the grid-stride loop — each thread strides by the total thread count (for (int i = tid; i < n; i += gridDim.x * blockDim.x)), the raw form of the persistent-kernel pattern in the cuTile matmul.

Coalescing: the warp is the unit of memory access

When a warp executes a load, the hardware collects all 32 addresses and fetches the set of 32-byte sectors they touch. The instruction costs the same either way — what varies is how many sectors move across the bus. Thirty-two consecutive floats live in four sectors; thirty-two column-strided floats can live in thirty-two. Same instruction, 8× the traffic, and on a memory-bound kernel that ratio is your slowdown:

warp lane (thread) 32 B sector fetched lane → address

One warp load, four ways. Top: the 32 lanes of a warp, each loading one 4-byte float at a[stride·i]. Bottom: the 32-byte sectors the memory system must fetch. The useful payload is always 128 bytes; the fetched traffic grows with stride until every lane drags its own sector (12.5% efficiency, the floor for 4-byte words). This is why "adjacent threads read adjacent addresses" is the first law of CUDA — and why accessing a row-major matrix down a column (stride = row length) is the classic way to break it.

Every abstraction upstream is arranged around this rule: Triton's contiguous tl.arange blocks, CuTe's insistence that the value-layout's major mode match the data's, cuTile's compiler choosing the mapping for you. Shared memory has an analogous rule — 32 banks, 4 bytes wide; threads hitting the same bank at different addresses serialize — which is why you'll see padding ([TILE][TILE+1]) and swizzled layouts in hand-tuned kernels.

Warp-level reality: divergence, shuffles, occupancy

Divergence

A warp has one instruction stream. When threads in a warp branch differently, the hardware runs both paths, masking off the inactive lanes — an if/else split down the middle of a warp costs the sum of both sides. Divergence between warps is free; it's intra-warp divergence that serializes. The compiler converts short branches into predication, and well-designed kernels arrange conditions to be uniform per warp (the vector-add bounds check diverges only in the single boundary warp — harmless).

Warp shuffles: registers as the fastest shared memory

Lanes of a warp can read each other's registers directly, no memory involved. The canonical use is the warp reduction — the building block of every sum, max, softmax denominator, and norm on the GPU:

// each of the 32 lanes holds one float v; after the loop, lane 0 holds the warp's sum
for (int offset = 16; offset > 0; offset >>= 1)
    v += __shfl_down_sync(0xffffffff, v, offset);   // add lane i+offset's v into lane i

Five instructions, no shared memory, no barriers. A block-wide reduction is then: shuffle within warps → one partial per warp to shared memory → __syncthreads() → first warp shuffles the partials. This composition of warp primitives + smem + barrier is what tl.sum and ct.sum generate for you.

Occupancy: parallelism as latency-hiding

GPUs don't hide HBM latency with big caches and speculation — they hide it with other warps. Each SM holds up to 64 resident warps; every cycle, its schedulers issue from whichever warps aren't stalled. A memory stall of ~400–800 cycles disappears if enough other warps have work. Occupancy — resident warps as a fraction of the maximum — is set by how much of the SM's fixed budget each block consumes: registers per thread, shared memory per block, threads per block. Ask for 200 registers per thread and occupancy caps at a fraction of maximum; sometimes that trade is right (more state per thread, less traffic — the CuTe GEMM lives there), but launch-config choices like "256 threads per block" exist to keep this arithmetic healthy. cudaOccupancyMaxActiveBlocksPerMultiprocessor does the bookkeeping; profilers (Nsight Compute) report it directly.

Second kernel: shared-memory tiled matmul

The canonical CUDA teaching kernel — and, on this site, the Rosetta stone: it is by hand what the cuTile matmul asks the compiler to do and what the CuTe skeleton spells out with atoms. Naively, computing one element of \(C = AB\) reads a full row of \(A\) and column of \(B\) from HBM: \(2K\) loads for \(2K\) FLOPs — hopelessly memory-bound. Tiling fixes the ratio: stage a TILE×TILE tile of each input into shared memory once, and every element in it gets reused TILE times.

#define TILE 32

__global__ void matmul(const float* A, const float* B, float* C,
                       int M, int N, int K) {
    __shared__ float As[TILE][TILE];        // block-visible SRAM
    __shared__ float Bs[TILE][TILE];

    int row = blockIdx.y * TILE + threadIdx.y;   // this thread's C element
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.f;

    for (int k0 = 0; k0 < K; k0 += TILE) {   // march over K, one tile at a time
        // stage: each thread carries one element of each tile.
        // adjacent threadIdx.x → adjacent addresses: both loads coalesce.
        As[threadIdx.y][threadIdx.x] = (row < M && k0 + threadIdx.x < K)
                                     ? A[row * K + k0 + threadIdx.x] : 0.f;
        Bs[threadIdx.y][threadIdx.x] = (k0 + threadIdx.y < K && col < N)
                                     ? B[(k0 + threadIdx.y) * N + col] : 0.f;
        __syncthreads();                     // tile fully staged before anyone reads

        for (int k = 0; k < TILE; ++k)       // compute entirely from SRAM
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
        __syncthreads();                     // everyone done before next overwrite
    }
    if (row < M && col < N)
        C[row * N + col] = acc;
}
Reading the kernel as a checklist of everything so far
  • Index math: 2-D block/thread indices pick each thread's output element — the hand-written layout.
  • Coalescing: in both staged loads, threadIdx.x is the fastest-moving index and multiplies nothing — adjacent lanes, adjacent addresses.
  • Shared memory + barriers: the load→__syncthreads()→compute→__syncthreads() rhythm is the manual version of the pipeline every DSL generates. Miss the second barrier and fast threads corrupt the tile mid-read — the classic CUDA bug.
  • Arithmetic intensity: HBM traffic drops by a factor of TILE (32) versus naive; the kernel crosses from memory-bound toward compute-bound, which is the entire point of tiling.

And the honest coda: this classic kernel, the peak of introductory CUDA, reaches only a modest fraction of a modern GPU's throughput — it runs on plain FMA units. Tensor cores are reached through warp-level MMA instructions (mma.sync, wgmma, tcgen05) with elaborate operand layouts, plus async copies (cp.async, TMA) to keep them fed — exactly the machinery the CuTe atom table catalogs. The gap between this page's matmul and those kernels is the reason the rest of the shelf exists.

Synchronization: barriers, fences, scopes, and phases

A parallel algorithm is correct only if a consumer cannot outrun its producer. CUDA exposes several synchronization tools, but they solve different problems. A barrier names a group of threads, waits for the required participants, and establishes memory visibility across the synchronization point. A fence orders one thread’s memory operations at a chosen scope but does not make another thread wait. Confusing the two is a classic source of races.

The barrier contract

For participating threads, writes completed before arrival become visible to reads after the matching wait. The barrier answers both “has everyone reached the handoff?” and “may I safely observe what they wrote?”

A fence is not a notification. __threadfence() can ensure payload writes are ordered before a later flag write, but another thread still needs an atomic/flag protocol to learn that the payload is ready. Likewise, an atomic counter does not automatically make unrelated data visible unless the surrounding memory-order protocol does.

A correct publication protocol combines an ordered payload write with a separately synchronized flag—normally an atomic store/release paired with an atomic load/acquire.

At PTX level, the ordinary whole-CTA rendezvous generally becomes a bar.sync operation. PTX also exposes a small fixed set of named barriers and optional arrival counts, but CUDA C++ and Cooperative Groups should express ordinary group synchronization unless a hand-written PTX protocol is truly required.

The performance rule follows the correctness hierarchy: prefer a warp barrier over a CTA barrier when only one warp communicates; prefer a CTA barrier over a cluster or grid barrier when the data is local. Wider barriers coordinate more execution resources and are harder to schedule.

__syncthreads(): the whole-block rendezvous

__syncthreads() waits until every non-exited thread in the CTA reaches the same dynamic barrier. It also makes prior shared- and global-memory accesses by those threads visible to the block after the barrier. The two calls in the tiled matmul above protect different hazards:

  1. The first prevents a consumer from reading As/Bs before another thread has written its element.
  2. The second prevents a fast thread from overwriting the shared-memory stage for tile \(k+1\) while a slow thread still reads tile \(k\).

CUDA also provides voting variants that perform the same full-block barrier and return a reduction of a predicate:

IntrinsicReturned value after all threads arrive
__syncthreads_count(p)Number of block threads for which \(p\ne0\).
__syncthreads_and(p)Nonzero iff \(p\) is nonzero for every block thread.
__syncthreads_or(p)Nonzero iff \(p\) is nonzero for at least one block thread.

The deadlock rule: participation must be uniform

A block-wide barrier may appear in a branch only when the condition evaluates identically for the whole block. A partial final block makes this tempting code invalid:

// WRONG: divergent barrier participation is undefined and can deadlock.
if (global_i < n) {
    smem[threadIdx.x] = input[global_i];
    __syncthreads();
    consume(smem);
}

// RIGHT: predicate the work, not the whole-block rendezvous.
bool active = global_i < n;
smem[threadIdx.x] = active ? input[global_i] : 0.f;
__syncthreads();
if (active)
    consume(smem);

A helper called by only half the block or a loop whose trip count differs across live threads can hide the same invalid participation. Exited threads are excluded from __syncthreads(), but an early return can still omit data that peers need. Explicitly counted cuda::barrier arrivals are different: a departing participant must satisfy or adjust its arrival obligation, usually with arrive_and_drop(). Cooperative Groups makes the intended participant set explicit in collective helpers.

Warp synchronization: do not rely on accidental lockstep

__syncwarp(mask) waits for the non-exited lanes named in mask and orders memory among those lanes. Each caller must name itself, and all named lanes must execute a corresponding call with the same mask. This matters on modern GPUs with independent thread scheduling: warp lanes often execute together, but “the warp is lockstep” is not a substitute for synchronization when lanes exchange data through shared or global memory.

For a full warp where all 32 lanes reach the ballot before branching, let 1 <= active_lanes <= 32 and give that warp its own shared-memory scratch slice:

unsigned mask = __ballot_sync(0xffffffffu, lane < active_lanes);

if (lane < active_lanes) {
    scratch[lane] = value;
    __syncwarp(mask);
    if (lane + 1 < active_lanes)
        value += scratch[lane + 1];
}

Do not use an __activemask() snapshot to infer the complete logical participant set: independently scheduled lanes may reach it in different subsets. Compute the mask at a collective point with a known valid membership mask. If the scratch slice is reused in a loop, add a matching barrier after the reads and before the next overwrite.

Register shuffles such as __shfl_down_sync(mask, ...) already name their participating lanes and synchronize that exchange. Use __syncwarp when the handoff happens through memory or separate instructions.

Cooperative Groups: make the participant set part of the API

Cooperative Groups replaces an implicit assumption (“surely the whole block called this function”) with an explicit group object:

namespace cg = cooperative_groups;

auto block = cg::this_thread_block();
auto warp  = cg::tiled_partition<32>(block);

block.sync();  // equivalent participant set to __syncthreads()
warp.sync();   // only this 32-thread tile

Hopper adds a cluster_group. Its CTAs are guaranteed to be co-scheduled, so cluster.sync() can protect accesses to distributed shared memory. The cluster interface also has split barrier_arrive()/barrier_wait(token) operations. A grid_group offers the same shape across a whole grid, but grid.sync() is legal only for a cooperative launch sized so every block can reside concurrently; ordinary kernels still synchronize independent CTAs by ending the kernel and launching the next one.

cuda::barrier: split arrival from waiting

__syncthreads() combines arrival and waiting in one call. cuda::barrier separates them, allowing a thread to announce “my writes are published” and do independent work before it actually needs its peers’ data:

#include <cuda/barrier>
#include <cooperative_groups.h>
#include <utility>

using BlockBarrier = cuda::barrier<cuda::thread_scope_block>;

__global__ void split_phase(float* data) {
    __shared__ BlockBarrier ready;
    auto block = cooperative_groups::this_thread_block();

    if (block.thread_rank() == 0)
        init(&ready, block.size());        // expected arrivals per phase
    block.sync();                          // bootstrap initialization

    publish_my_piece(data);
    auto token = ready.arrive();          // nonblocking + memory fence
    do_work_that_needs_no_peer_data();
    ready.wait(std::move(token));          // wait for this phase to advance
    consume_everyones_pieces(data);
}
Expected arrivals

init sets the number of arrivals needed to complete each reusable phase. It need not equal the full block size.

Arrival token

arrive() returns a token tied to the current phase; wait(token) blocks only while that phase remains current.

Automatic reset

Once all required arrivals and any attached asynchronous work complete, the phase advances and the pending count resets for the next use.

Early departure

arrive_and_drop() arrives now and reduces the expected participant count for future phases.

arrive_and_wait() is the combined convenience operation. A phase token may only be used for its phase or the immediately preceding one, and a thread must observe phase completion before racing ahead into a later reuse. If all threads in a block or warp simply need a rendezvous, NVIDIA recommends __syncthreads() or __syncwarp(); the explicit barrier earns its complexity when participation is selective or arrival can overlap useful work.

mbarrier: the shared-memory state machine underneath async pipelines

Starting with Ampere (compute capability 8.0), block-scoped cuda::barrier operations can use hardware acceleration from the PTX mbarrier family. An mbarrier is an opaque 8-byte, 8-byte-aligned object in shared memory. Unlike the small fixed set of CTA bar.sync slots, mbarrier objects are allocated by the program and are limited primarily by shared-memory capacity. Hopper (compute capability 9.0) adds the transaction-count mechanism used by TMA below.

Each phase tracks more than “how many threads arrived”:

Ordinary mbarrier primary-phase completion
\[ \text{phase complete} \iff \text{pending arrivals}=0 \;\land\; \text{transaction count}=0. \]

PTX 9.3 adds .layout::v1 barriers with payload reports and a conditional phase for fabric operations. The ordinary .layout::v0 TMA example here only needs the core arrival/transaction-count model.

PTX operationRole in the state machine
mbarrier.initInitialize the object and expected arrival count before any participant uses it.
mbarrier.arriveDecrement pending arrivals and return state associated with the current phase.
mbarrier.arrive_dropArrive in this phase and reduce the expected arrival count for subsequent phases.
mbarrier.expect_tx / arrive.expect_txAdd asynchronous work—often TMA bytes—to the phase’s transaction count.
mbarrier.complete_txIssued by the completing async operation to subtract finished transactions.
mbarrier.test_wait / try_waitTest phase completion using state or parity; higher-level waits repeat until it succeeds.

Schematic PTX for one TMA load phase on Hopper or newer looks like this. One thread owns initialization, arrival, waiting, consumption, and invalidation in this example; dst is a suitably aligned shared-memory tile and map is an already-published tensor map:

// Shared storage is a .b64 object aligned to 8 bytes.
mbarrier.init.shared::cta.b64              [bar], 1;
fence.proxy.async.shared::cta;            // publish initialization to TMA
mbarrier.arrive.expect_tx.shared::cta.b64  state, [bar], bytes;

// An async engine later performs complete_tx as work finishes.
cp.async.bulk.tensor.2d.shared::cluster.global
    .mbarrier::complete_tx::bytes [dst], [map, {x, y}], [bar];

wait_ready:
mbarrier.try_wait.shared::cta.b64          ready, [bar], state;
@!ready bra wait_ready;
// ...consume the loaded tile; after the final phase...
mbarrier.inval.shared::cta.b64             [bar];

The proxy fence makes the initialized barrier visible to the asynchronous copy engine; waiting once without checking the predicate is not sufficient. With multiple threads, also publish initialization to every participant before first use, have each consumer observe the full phase before reading, and ensure all users are finished before invalidation or buffer reuse.

The object automatically advances and resets when both counters reach zero. Before an arrival in the following phase, at least one waiter must have observed successful completion of the previous phase. That rule prevents a fast producer from lapping a slow consumer and confusing a reused parity token.

Conceptually, arrival publishes prior writes and a successful wait acquires them for the consumer. Asynchronous engines introduce an additional memory proxy: when ordinary threads produce shared-memory data for TMA to store, a proxy fence is still required before the engine reads it. Correct barrier counts cannot repair missing memory-order edges.

Cluster barriers are directional. A thread may signal an mbarrier in another CTA’s distributed shared memory with supported arrive/transaction operations, but waiting is performed by threads that own the barrier’s local shared-memory address. TMA multicast uses this one-way signaling to complete barriers in several destination CTAs.

Producer/consumer pipelines need “full” and “empty” handoffs

A ring-buffer stage has two ownership transitions. The producer must wait until consumers release the stage as empty; after filling it—possibly through TMA—it signals full. Consumers wait for full, compute, then signal empty. Double buffering needs both transitions for both buffers; otherwise a producer can overwrite a tile still in use even if the initial load barrier is correct.

Producer acquire

Wait for the empty phase before writing or launching an asynchronous load into the stage.

Producer commit

Publish ordinary writes or attach TMA transaction bytes to the stage’s full barrier.

Consumer wait

Observe the full phase before WGMMA or scalar code reads the staged tile.

Consumer release

Signal that all reads are finished before the ring slot wraps around to the producer.

This is the primitive beneath TMA’s transaction-barrier protocol, the CUTLASS producer/consumer mainloop, and the barrier choreography hidden by cuTile. CUDA C++ libraries package the phase arithmetic because one wrong expected count or one skipped release becomes a silent race or a kernel-wide deadlock.

The machinery: streams, and what a kernel compiles to

Streams: the asynchrony model

All device work — kernels, copies — is issued into streams: ordering domains whose commands execute FIFO. Different streams are otherwise unordered and may run concurrently when the hardware has resources; cudaEvents add precise cross-stream dependencies without blocking the host. Synchronization is the separate act of making the CPU wait. The dedicated CUDA Streams & Events page develops that model through default-stream semantics, pinned-memory copy/compute overlap, timing, asynchronous errors, and PyTorch's stream-aware allocator lifetime. Repeated host launch overhead into these queues is what CUDA Graphs exist to amortize.

PTX, cubin, and SASS: follow one kernel through compilation

nvcc is a compiler driver: it sends host code to a C++ compiler and drives a separate device-code pipeline. PTX is the virtual instruction set; SASS is the native GPU instruction set; cubin is a binary container. They are not three interchangeable names for assembly.

The native targets below are A100 (sm_80) and H100 (sm_90), with ordinary compute_80 PTX as a fallback. Use a scratch directory for the generated files.
1 · Give the compiler a complete program

Save this as vector_add.cu. It is the same vector-add kernel, now with a small checked host program. extern "C" keeps the kernel's symbol readable in the dumps. Managed memory keeps setup short; this is a compilation exercise, not a memory-transfer benchmark.

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

extern "C" __global__
void vector_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

void check(cudaError_t status) {
    if (status != cudaSuccess) {
        std::fprintf(stderr, "CUDA: %s\n", cudaGetErrorString(status));
        std::exit(EXIT_FAILURE);
    }
}

int main() {
    constexpr int n = 8;
    float* data = nullptr;
    check(cudaMallocManaged(&data, 3 * n * sizeof(float)));
    for (int i = 0; i < n; ++i) {
        data[i] = float(i);
        data[n + i] = float(2 * i);
    }
    vector_add<<<1, 32>>>(data, data + n, data + 2 * n, n);
    check(cudaGetLastError());
    check(cudaDeviceSynchronize());
    bool ok = true;
    for (int i = 0; i < n; ++i) {
        if (data[2 * n + i] != float(3 * i)) {
            std::fprintf(stderr, "Mismatch at %d: got %g, expected %g\n",
                         i, data[2 * n + i], double(3 * i));
            ok = false;
        }
    }
    check(cudaFree(data));
    std::printf("%s: %d elements\n", ok ? "PASS" : "FAIL", n);
    return ok ? EXIT_SUCCESS : EXIT_FAILURE;
}
2 · Stop at PTX: the virtual program
nvcc -O3 -lineinfo --ptx -arch=compute_80 vector_add.cu -o vector_add.ptx
sed -n '1,100p' vector_add.ptx

--ptx stops before native code generation: this file is device code, not a host executable. Look for .version (PTX language version), .target sm_80 (required target features, despite the sm_ spelling), and the .entry vector_add kernel. The command's compute_80 selects the virtual architecture; it does not mean this text is already A100 machine code.

Trace the kernel's operations using these landmarks. Register names and exact instruction choices vary by toolkit and optimization; this is a reading guide, not a byte-for-byte expected dump:

3 · Assemble a cubin, then read its SASS
ptxas -arch=sm_80 -lineinfo -v vector_add.ptx -o vector_add.sm80.cubin
nvdisasm -g vector_add.sm80.cubin > vector_add.sm80.sass
cuobjdump --dump-resource-usage vector_add.sm80.cubin
sed -n '1,160p' vector_add.sm80.sass

ptxas does target-specific optimization, instruction selection, scheduling, and register allocation — not just text-to-byte translation. Its -v output reports resources such as registers and spills. The resulting cubin is an ELF file containing native code and supporting metadata; it is not a CPU executable, so do not try to run ./vector_add.sm80.cubin.

nvdisasm decodes those instruction bytes into SASS; -g includes source-line information when available from -lineinfo. In the kernel's code section, look for thread/block ID reads such as S2R, integer address arithmetic such as IMAD, global loads/stores such as LDG/STG, and FADD for the addition. Native registers such as R0 and predicates such as P0 are no longer PTX's virtual names. Instruction suffixes, ordering, and register counts depend on the target and compiler.

Tool boundary: nvdisasm takes a standalone cubin and offers richer disassembly. cuobjdump can also inspect cubins, but can additionally find device code embedded in executables, objects, libraries, and fatbinary files. The resource report here is the compiled kernel's register/local/shared-memory usage, not the host program's managed-memory allocation.

4 · Package native images and a PTX fallback
nvcc -O3 -lineinfo vector_add.cu -o vector_add \
  -gencode arch=compute_80,code=sm_80 \
  -gencode arch=compute_90,code=sm_90 \
  -gencode arch=compute_80,code=compute_80

cuobjdump --list-elf ./vector_add
cuobjdump --list-ptx ./vector_add
cuobjdump --dump-ptx ./vector_add
cuobjdump --dump-sass ./vector_add

This rebuilds from the source; it does not consume the earlier standalone .ptx or .cubin files. The output is a host executable with a fatbinary of device alternatives: an sm_80 cubin, an sm_90 cubin, and retained compute_80 PTX. Look for both native targets in --list-elf and the PTX entry in --list-ptx; file names and metadata vary by toolkit.

In each -gencode, arch=compute_XX selects the frontend's virtual feature set; code=sm_XX emits native code, while code=compute_XX retains PTX for later compilation. Only the third line above requests retained PTX. A transient PTX intermediate during a native build is not proof that PTX shipped. Conversely, PTX-only packaging need not include any native cubin. Using --fatbin instead of building an executable emits a standalone device-only fatbinary, without main().

Inspect what shipped, not what you assume shipped. cuobjdump --dump-sass shows embedded native images, not the machine code the driver might later JIT for a different GPU.
5 · Observe native loading versus driver JIT

Under normal settings, the driver uses a compatible native cubin when available; otherwise it can compile compatible embedded PTX for the installed GPU. If neither path is usable, loading/launching the kernel fails. For the build above:

GPUNormal path for this executable
A100 · sm_80Load the embedded sm_80 cubin
H100 · sm_90Load the embedded sm_90 cubin
B200 · sm_100No compatible native image in this build: JIT the retained PTX, or reuse its driver-cache result

On a CUDA-equipped machine, start with no conflicting JIT environment overrides and run these separately. Each assignment applies only to that command:

./vector_add
CUDA_FORCE_PTX_JIT=1 CUDA_CACHE_DISABLE=1 ./vector_add
CUDA_DISABLE_PTX_JIT=1 ./vector_add

The first run should print PASS: 8 elements on each GPU above with a suitable driver. The second ignores embedded cubins and disables the on-disk compilation cache, exercising PTX compilation rather than a cached result; it should also pass. The third forbids PTX JIT: it should pass on A100/H100, but fail on B200 for this particular build. That failure is an intentional check for missing compatible native code, not a numerical bug.

Normally the driver caches JIT results across runs, so “PTX fallback” does not mean recompiling on every launch. First-use latency and steady-state execution are different measurements; this tiny program demonstrates selection, not performance.

Forward compatibility has conditions. The GPU must satisfy the PTX target's feature requirements, and the driver must understand the emitted PTX language version. A new toolkit can emit a PTX version an older driver cannot parse even with compute_80. Native cubin compatibility follows compute-capability rules, not arbitrary cross-generation portability; architecture-specific targets such as sm_90a also have stricter rules than the ordinary targets used here.

Connect this back to Blackwell: tcgen05.mma is a PTX-level operation, so the 256 → 2 → 1 MMA comparison describes logical instruction work, not a measured native instruction count or cycle ratio. SASS reveals the target-specific lowering; profiling reveals its cost. JIT-compiling this old-feature-set vector add on Blackwell does not turn it into a TMEM/2-SM tensor-core kernel. That distinction is also why Tile IR makes its portability promise at the higher tile-operation level.

Why the model still matters

Almost nobody ships hand-rolled CUDA C++ kernels for ML anymore — but every abstraction above it leaks in SIMT terms. Triton's block sizes are occupancy decisions; CuTe's layouts are coalescing decisions; cuTile's tuning hints are warp-scheduling decisions; every profiler trace is warps, sectors, and stalls. SIMT is the vocabulary of GPU performance even when it's no longer the syntax.
