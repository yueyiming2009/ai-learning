TVM & FFI

How an ML computation becomes machine code, how Python calls that code, and why sharing a tensor buffer is not the same as understanding its computation.

The one-sentence model: TVM transforms ML programs into executable artifacts; TVM-FFI supplies a common cross-language calling and object interface; DLPack describes tensors so libraries can share their storage.

Start here: read the map, run the scalar and CPU-tensor lessons, then learn the GPU contract. You do not need CUDA or the full TVM compiler to learn TVM-FFI.

Based on the Apache TVM-FFI documentation and TVM architecture docs, read October 31, 2026. These are rolling docs, not a pinned release. The examples below are source-checked learning examples, not locally execution-validated TVM installations.

1. Separate the four layers

Suppose you have a PyTorch tensor and a fast C++ or CUDA implementation. There are two different problems: how to produce fast code, and how to invoke it safely from another language or framework. TVM and TVM-FFI address different parts of that story.

LayerQuestion it answersWhat it is not
Apache TVM compilerHow can a model or tensor program be transformed, scheduled, and lowered for a target CPU/GPU?Just a Python binding library.
TVM execution runtimeHow do we load compiled artifacts, manage target-specific execution, and run a model or kernel?The full optimization toolchain; deployment need not ship all compiler passes.
TVM-FFIHow do languages agree on values, function calls, modules, ownership, and errors?A kernel optimizer, tensor-math library, or autograd engine.
DLPackWhere is this tensor's data, what is its layout, and how is its lifetime transferred/shared?A compiler, an operation registry, or a CPU-to-GPU copy mechanism.

FFI means foreign function interface: code in one language calls code implemented in another. Python calling a native function stays in the same process; this is not HTTP, RPC, or a network serialization format.

TVM-FFI is standalone. The Python distribution is apache-tvm-ffi, imported as tvm_ffi; the compiler is imported as tvm. You can write a kernel using ordinary C++, CUDA, or another compiler and expose it through TVM-FFI without running any TVM compiler pass.

Path A: compile a model

Model / tensor program → TVM transformations and code generation → compiled artifact.

Path B: author a kernel

Handwritten C++ / CUDA or a kernel DSL → its own compiler → exported FFI function.

Common call boundary

Python / C++ / another binding → TVM-FFI function → native implementation using tensor descriptors.

2. What TVM actually compiles

Use \(Y=\max(AB+b,0)\) as the running example. A framework describes the computation; a target needs loops, memory accesses, parallel work assignment, and instructions. TVM's intermediate representations let you optimize at more than one level.

ConceptWhat you should pictureA decision for this example
IRModuleA compiler-side collection of program functions, not a loaded shared library.Keep graph-level functions and low-level tensor functions in one compilation unit.
RelaxHigh-level computation, tensor shapes, dataflow, and control flow.Eliminate redundant work, fuse suitable operators, or dispatch a subgraph to an external library.
TensorIR / low-level tensor IRLoop nests, buffers, reductions, memory scopes, and parallelism.Tile the matrix multiplication, reuse data, vectorize CPU work, or bind GPU work to threads.
ScheduleA choice of how to execute the computation while preserving its intended semantics.Choose tile sizes, loop order, cache placement, and parallel work mapping.
Lowering + code generationTurn high-level constructs into target-specific executable code, often through downstream tools such as LLVM or CUDA compilers.Produce CPU machine code or host launch code plus GPU code.
Runtime Module / FunctionA loadable collection of callable functions. A model may also need the Relax VM and target-specific runtime modules.Load an artifact, look up an entry point, and pass inputs.

From “what” to “how”

# Conceptual pseudocode, not a TVM API example.
# Graph view:
Y = relu(matmul(A, B) + bias)

# One possible fused loop view:
for i in range(M):
    for j in range(N):
        acc = 0
        for k in range(K):
            acc += A[i, k] * B[k, j]
        Y[i, j] = max(acc + bias[j], 0)

# A scheduled implementation might tile i/j/k, reuse tiles,
# and map independent output tiles to CPU workers or GPU blocks.

Fusing the bias and ReLU into the matmul epilogue can avoid writing and rereading intermediate tensors. Scheduling can improve locality and hardware utilization. Neither change comes from FFI: FFI does not inspect your loop and make it faster. Fusion is not always profitable or supported; using a tuned library can be the better choice.

The reduction over \(k\) is not just another freely parallel loop: partial sums must be combined correctly. Floating-point reordering can change rounding. “Equivalent computation” needs the appropriate numerical tolerance, and deliberately approximate transformations such as quantization need their own accuracy checks.

Avoid the tutorial-version trap. Older material uses Relay, tvm.tir, tvm._ffi, and PackedFunc. The current architecture and creation pages include Relax, tirx/tvm_tirx, tvm.s_tir, and standalone tvm_ffi. Do not mix imports from different generations. Match the tutorial to the installed compiler release.

First compiler exercise: follow the official TensorIR creation tutorial using its matching environment. Inspect the IR, compile its CPU example, compare against NumPy, then follow the transformation tutorial. Change one schedule decision and compare both correctness and warmed-up runtime. The goal is to see the program representation change, not merely to obtain a number from a library.

3. How one Python call crosses into C++

An API is the source-level interface you program against. An ABI, or application binary interface, is the agreement compiled code uses: argument layout, calling convention, symbols, and ownership. C++ templates and Python objects are not themselves a universal binary contract.

TVM-FFI uses a stable C ABI with a uniform packed function signature. “Packed” means the arguments are collected into an array of tagged values, not that a tensor's entire data buffer is serialized.

int exported_call(
    void* handle,
    const TVMFFIAny* args,
    int32_t num_args,
    TVMFFIAny* result
);

At this boundary, TVMFFIAny is a 16-byte tagged value: small values such as integers live inline; tensors and other objects are represented by pointers/references. The input arguments are borrowed views. The result is owning and must be zero-initialized by a raw C caller. The C return value is a status code: 0 for success, -1 for an error—not the function's mathematical result.

1 · Convert

Python values become tagged ABI arguments. A supported tensor supplies its descriptor without copying its elements.

2 · Invoke

The exported wrapper unpacks and checks argument types, calls the typed C++ function, and translates exceptions into the ABI error channel.

3 · Return

The binding converts the result back to Python, or raises an exception. A GPU launch can return before the GPU finishes.

Most users should not implement that C wrapper manually. Export a typed C++ function with TVM_FFI_DLL_EXPORT_TYPED_FUNC, or let the inline build helper generate the export. The wrapper checks the argument type; it cannot infer your kernel's required dtype, layout, shape, or aliasing contract.

Three names you will meet

InterfaceUse it forImportant distinction
Module + exported symbolsLoading a kernel library with tvm_ffi.load_module(path) and calling mod.scale(...).A runtime module is not an IRModule or a Python source module.
Global function registryNamed application APIs or callbacks via register_global_func / get_global_func.Registering a Python function does not compile its body into native code. A C++ registration exists only after its library is loaded.
Object + reflectionSharing structured state, fields, and methods across languages.Explicit object registration and reference-counted lifetime, not arbitrary C++ objects becoming magically portable.

4. CPU lab: first a value, then a tensor

Use a disposable, approved development environment with a C++17-capable compiler and the official apache-tvm-ffi package. The tensor lesson also uses NumPy with DLPack support. Follow the official prerequisites and your organization's package policy. No full TVM compiler, PyTorch, or GPU is needed for these two lessons.

These snippets compile local C++ and load the resulting native library into Python. Review the source before running; loading native code is not sandboxing. No packages are installed by this page.

Lesson A · Cross the boundary with one integer

from tvm_ffi.cpp import load_inline

scalar = load_inline(
    name="ffi_integer_lesson",
    cpp_sources=r"""
#include <tvm/ffi/tvm_ffi.h>

int64_t add_two(int64_t x) {
    return x + 2;
}
""",
    functions=["add_two"],
)

assert scalar.add_two(40) == 42
print(scalar.add_two(40))  # 42

load_inline invokes the host C++ toolchain, builds and caches a shared library, and returns a loaded tvm_ffi.Module. It is a convenience build helper, not the TVM tensor compiler. The first call to the helper may take compilation time; repeated native function calls are a different cost.

The functions argument generates the equivalent of this export in the translation unit:

TVM_FFI_DLL_EXPORT_TYPED_FUNC(add_two, add_two)

That exposes a symbol named __tvm_ffi_add_two. Use either automatic export or the manual macro for the same function, not both. For an already-built compatible library, use tvm_ffi.load_module(path) instead of rebuilding it.

Lesson B · Scale an existing NumPy buffer in C++

The next function computes \(y_i=\alpha x_i\). Its contract is deliberately small: 1-D, contiguous, CPU, float32 tensors of equal length. The caller supplies a fresh writable output buffer, so there is no partial input/output overlap.

import numpy as np
from tvm_ffi.cpp import load_inline

kernels = load_inline(
    name="ffi_tensor_lesson",
    cpp_sources=r"""
#include <tvm/ffi/tvm_ffi.h>

void scale(tvm::ffi::TensorView x,
           tvm::ffi::TensorView y,
           double factor) {
    TVM_FFI_CHECK(x.device().device_type == kDLCPU &&
                  y.device().device_type == kDLCPU, ValueError)
        << "Expected CPU tensors";
    TVM_FFI_CHECK(x.ndim() == 1 && y.ndim() == 1, ValueError)
        << "Expected 1-D tensors";
    DLDataType f32{kDLFloat, 32, 1};
    TVM_FFI_CHECK(x.dtype() == f32 && y.dtype() == f32, TypeError)
        << "Expected float32 tensors";
    TVM_FFI_CHECK(x.IsContiguous() && y.IsContiguous(), ValueError)
        << "Expected contiguous tensors";
    TVM_FFI_CHECK(x.size(0) == y.size(0), ValueError)
        << "Expected equal lengths";

    const auto* in = static_cast<const float*>(x.data_ptr());
    auto* out = static_cast<float*>(y.data_ptr());
    const float alpha = static_cast<float>(factor);
    for (int64_t i = 0; i < x.size(0); ++i) {
        out[i] = alpha * in[i];
    }
}
""",
    functions=["scale"],
)

x = np.array([1, 2, 3, 4], dtype=np.float32)
y = np.empty_like(x)
kernels.scale(x, y, 2.0)
np.testing.assert_allclose(y, x * 2.0)
print(y)  # [2. 4. 6. 8.]

The C++ function returns void (Python sees None), but y changes. It writes into the output's existing allocation: no tensor result has to be copied back. This is often called a destination-passing interface. The ordinary C++ loop is just a teaching kernel, not a claim of beating NumPy's optimized implementations.

Make the contract fail before trusting it

# Continue in the same script after Lesson B.
bad_inputs = [
    x.astype(np.float64),  # Wrong dtype
    x[::2],               # Non-contiguous view
    x.reshape(2, 2),      # Wrong rank
    x[:-1],               # Length differs from y
]
for bad in bad_inputs:
    try:
        kernels.scale(bad, y, 2.0)
    except (TypeError, ValueError) as exc:
        print(type(exc).__name__, str(exc))
    else:
        raise AssertionError("Invalid input was accepted")

empty = np.empty(0, dtype=np.float32)
kernels.scale(empty, np.empty_like(empty), 2.0)  # Zero iterations

A raw pointer cannot tell you whether writing is allowed or whether another argument overlaps its storage. This lab avoids those problems by construction. A general public API must define and enforce its writable-output and aliasing rules rather than relying only on the checks above.

5. Zero-copy means shared storage, not zero responsibility

To interpret a tensor, the callee needs more than float*. A DLPack descriptor carries a data pointer, device, rank, dtype, shape, strides, and byte offset. Strides are measured in elements; the offset is measured in bytes.

For an ordinary byte-addressable dtype:
address(i0, ..., in) =
    data + byte_offset
         + element_size_in_bytes * sum(ij * stride[j])

Python framework tensor ─┐
FFI tensor descriptor  ──┼──> one underlying allocation
Another framework view ─┘

For a 2-D contiguous array of shape (3, 4), strides are (4, 1). Its transpose can share storage while having shape (4, 3) and strides (1, 4). A kernel that assumes flat contiguous indexing must reject or explicitly handle that layout. “Make contiguous” can allocate and copy; it is not a free part of FFI conversion.

TypeOwnershipWhen to use
DLTensor / TensorViewBorrowed descriptor; no ownership of the data allocation.Inspect and use a caller's tensor during a kernel call. Do not store a borrowed view for later use.
DLManagedTensorVersionedDescriptor plus a producer-managed cleanup callback and context.Managed interchange: the consumer releases its ownership through the agreed deleter.
tvm::ffi::Tensor / Python tvm_ffi.TensorManaged tensor reference that keeps the backing storage alive through its ownership mechanism.Return a tensor or retain one in long-lived state; it need not own a new allocation.
AnyView / AnyThe corresponding borrowed / owning distinction for general ABI values.Borrow arguments; manage the lifetime of object-valued results.

Optional PyTorch experiment · Observe aliasing directly

import torch
import tvm_ffi

x = torch.arange(4, dtype=torch.float32)  # CPU; no autograd
shared = tvm_ffi.from_dlpack(x, require_contiguous=True)
again = torch.from_dlpack(shared)

assert again.data_ptr() == x.data_ptr()
again[0] = 99
assert x[0].item() == 99

This experiment shares data; it does not preserve a PyTorch autograd graph through the foreign code. Use only a supported PyTorch/FFI combination; the current installation page calls out an additional compatibility package for PyTorch ≤ 2.9. Check your installed versions before adding dependencies.

Zero-copy is not a device transfer. A CUDA tensor stays on its CUDA device. A host CPU loop must not dereference that pointer. It also does not mean “no work”: descriptor conversion, reference management, and stream coordination can still cost time.

Same storage is not independent data. Mutations can be visible through every alias. DLPack does not supply gradient rules, operator semantics, or permission to mutate an otherwise immutable framework value.

Source: Tensor and DLPack.

6. Moving from a CPU call to a GPU launch

On the CPU, the loop finishes before the function returns. On CUDA, the host function typically enqueues a kernel and returns while the GPU is still working. A correct signature is only the beginning.

  1. Validate both inputs and outputs. Check CUDA device type, matching device IDs, dtype, shape, layout, writable output, and supported aliasing.
  2. Select the device. Use the appropriate device guard; the caller's current device need not match the tensor's device.
  3. Use the caller's stream. Obtain the environment stream for that device, not an assumed stream 0.
  4. Launch safely. Handle zero elements, guard out-of-range threads, and check CUDA launch errors. Keep allocations valid until the GPU has finished using them.
// Schematic fragment inside a validated CUDA host wrapper.
// Not a complete compilable kernel.
auto device = x.device();
tvm::ffi::CUDADeviceGuard guard(device.device_id);
auto stream = static_cast<cudaStream_t>(
    TVMFFIEnvGetStream(device.device_type, device.device_id));

// Compute the launch dimensions; skip the launch for n == 0.
// ScaleKernel<<<blocks, threads, 0, stream>>>(...);
// Check launch errors using the CUDA runtime API.

Supported framework conversions can capture the current framework stream. There are also explicit tvm_ffi.use_torch_stream and tvm_ffi.use_raw_stream contexts when automatic detection is insufficient. The native kernel still needs to use the stream it obtains.

Two different lifetime questions: the borrowed descriptor must be valid while host code reads it, and the backing allocation must remain valid through asynchronous device use. Reference counting alone is not proof of GPU completion. If you use another stream, establish execution dependencies and satisfy the framework allocator's lifetime rules.

Two different integration questions: an eager FFI call can work while torch.compile, autograd, vmap, or graph capture still needs additional integration. Supply framework-specific operator registration, shape/meta information, mutation/alias declarations, and gradient or batching rules as applicable. A portable call ABI does not make an opaque function automatically understood by every graph compiler.

For JAX, the official quick start uses a dedicated adapter and registration through JAX's FFI mechanism; it is not simply the PyTorch call pasted into a JIT-compiled JAX function.

Sources: complete CUDA kernel-library patterns; stream and lifetime interfaces; JAX integration. Related notes: CUDA streams, CUDA Graphs, and PyTorch execution.

7. When does call overhead matter?

A tiny native function can spend more time crossing the language boundary than doing useful work. For a larger kernel, the same fixed cost can become negligible. That is a statement about granularity, not a guaranteed speedup from choosing one binding library.

For a simple serialized model, let \(h\) be the per-call boundary overhead, \(c\) useful work per item, and \(B\) the number of items processed inside one native call:

\[ t_{\text{item}}(B)=c+\frac{h}{B}, \qquad \text{overhead fraction}=\frac{h}{h+Bc}. \]

x: items per native call B · y: amortized µs/item · all values are hypothetical

With h = 2 and c = 0.5 microseconds, one item costs 2.5 microseconds; at 16 items per call the amortized cost is 0.625 microseconds per item.
B items in one native call One native call per item Useful-work floor c

At B = 16: 0.625 µs/item versus 2.500 µs/item; 4.00× modeled throughput ratio; 20.0% boundary overhead.

Amortize the boundary, not the explanation away. Move the sliders to see when batching matters. This is not a TVM-FFI benchmark or a GPU throughput predictor: it excludes overlap, occupancy changes, launch costs, memory traffic, and time waiting to form a batch. It assumes the native function actually processes B items per call.

With \(h=2\) µs and \(c=0.5\) µs, overhead is 80% at \(B=1\), but 20% at \(B=16\). To keep the boundary fraction at or below 10%, the model requires \(B\geq9h/c\), or at least 36 items for those defaults.

Measure the right thing. Separate build/load time from warmed-up calls. For GPU execution, host wall time around an asynchronous call is not kernel completion time. Use CUDA events for device work and appropriate synchronization at the boundaries of an end-to-end timing interval. Do not insert a synchronization into every production call just to make timing easy.

TVM scheduling changes the implementation of useful work. Fusion can reduce intermediate memory traffic and kernel launches. FFI targets the language boundary and interoperability. CUDA Graphs target repeated host submission overhead. These techniques can complement each other; none makes the others redundant.

8. What should you choose for a real project?

Your problemStart withWhy
Optimize and deploy an ML model across targets.TVM's compiler and deployment tutorials.You need graph/tensor transformations, target code generation, and runtime integration.
Expose an existing tensor kernel to several languages/frameworks.TVM-FFI + DLPack.A common native boundary avoids coupling the kernel directly to every framework's C++ tensor API.
Bind a general C++ library tightly to Python.Compare pybind11 / nanobind with TVM-FFI.Python-oriented binding ergonomics versus an ML-oriented, language-neutral ABI; choose by integration needs, not assumed speed.
Call a small existing C API.Consider ctypes or cffi.A narrow C interface may not need a new object/module system.
Make a kernel participate in PyTorch autograd/compilation.PyTorch's operator integration APIs, with the native binding of your choice underneath.Calling the kernel and teaching the framework its semantics are separate jobs.
Write or tune the GPU computation itself.Triton, CuTe DSL, CUDA, or TVM's low-level programming tools.These describe or generate the computation; FFI is the boundary around it.

“One library” has a scope. Avoiding CPython-version and framework-specific bindings does not make a native binary universal across operating systems, CPU architectures, C/C++ runtime dependencies, or GPU instruction sets and drivers. Compatible FFI runtime support and any kernel-specific dependencies still need to be present. Shipping an FFI-only kernel is also different from deploying a full TVM model with its required execution runtime.

9. Check your mental model

I wrapped my slow matmul with TVM-FFI. Why is it still slow?

The wrapper changes how callers reach the code, not the matmul algorithm, tiling, memory reuse, or instructions. Optimize the kernel or choose a better implementation. Measure boundary overhead separately.

Why can the CPU lesson accept a NumPy array without copying it?

The binding obtains a compatible tensor descriptor through the interchange protocol. C++ reads/writes the existing CPU allocation. Dtype, layout, lifetime, and mutability still have to satisfy the kernel's contract.

Can I save a TensorView in a global variable for a later call?

Not by itself. It is borrowed and does not keep the producer's tensor alive. Retain an appropriate managed tensor/owner for long-lived state, and separately honor asynchronous device-use lifetime rules.

The kernel works on stream 0 but fails with other work. What is missing?

Check the selected device, caller's current stream, execution dependencies between streams, and backing-allocation lifetime. A valid pointer and a matching dtype are not enough to establish correct ordering.

Does a successful eager call prove that gradients and torch.compile work?

No. The framework needs the operation's graph-level contract and, where applicable, gradient, batching, mutation/aliasing, and shape rules. FFI and DLPack do not derive them from machine code.

Is load_inline secretly compiling a TVM IRModule?

No. It builds the C++/CUDA source you supply using the native toolchain. In this guide there is no TVM IRModule at all. The returned object is a loaded runtime Module.

A practical next-hour learning path

  1. Boundary: run the scalar lesson, change the C++ result, and identify where export, compilation, loading, and calling happen.
  2. Tensors: run the scale lesson and its invalid-input cases. Explain why the empty input is safe and why a strided input is rejected.
  3. Compiler: work through a version-matched TVM TensorIR example. Inspect the original and transformed program before comparing numerical results.
  4. GPU, when available: follow the official kernel-library guide. Verify a non-default stream and a nonzero device ID where supported before benchmarking.

You understand the stack when you can answer independently: who generates the code, who owns the allocation, who chooses the execution stream, and who knows the operation's mathematical semantics?
