GPU Kernels in CuTe DSL

CUTLASS 4's Python-native kernel language — layouts as functions, the algebra that turns tiling into arithmetic, thread–value partitioning, and hardware atoms down to the tensor-core instruction.

Pre-reading: GPU Hardware for ML for the memory hierarchy (HBM → L2 → shared memory → registers) and tensor cores; The PyTorch Execution Model for why hand-written kernels exist at all; and GPU Kernels in Triton for the block-level DSL this page contrasts against — CuTe DSL sits one level of control below Triton.

Why another kernel DSL?

The hard part of a high-performance GPU kernel is not the arithmetic. It is the bookkeeping: which thread holds which element, in which memory space, at which pipeline stage — and whether the resulting access pattern is coalesced in global memory, bank-conflict-free in shared memory, and shaped exactly the way the tensor-core instruction demands. In raw CUDA C++ this bookkeeping is hand-rolled index arithmetic, and it is where the bugs and the lost bandwidth live.

CuTe (the core abstraction layer of CUTLASS since 3.0) makes that bookkeeping a first-class mathematical object: the layout, a function from logical coordinates to memory offsets, with an algebra for composing, tiling, and partitioning layouts. The catch was the packaging — C++ template metaprogramming, with minutes-long compiles per instantiation and error messages measured in screens.

CuTe DSL (CUTLASS 4.x, 2025, pip install nvidia-cutlass-dsl) lifts the same abstractions into Python. Kernels are Python functions that JIT-compile through MLIR to native GPU code in seconds instead of minutes, interoperate zero-copy with PyTorch via DLPack, and keep full thread-level control — including the newest hardware instructions (TMA, wgmma, Blackwell's tcgen05) that block-level compilers take time to learn. Because the abstractions match C++ CuTe one-for-one, kernels port between the two almost line-by-line.

Adoption made the case quickly: FlashAttention-4 — the Blackwell rewrite — is written in CuTe DSL Python rather than C++; Tri Dao's QuACK library ships memory-bound kernels (RMSNorm, softmax, cross-entropy) in pure CuTe DSL that reach near-peak HBM bandwidth on H100; and the Blackwell GEMM / MLA kernels behind vLLM and SGLang increasingly come from this stack.

What CuTe DSL hides

C++ templates, index arithmetic (folded away by the layout algebra at compile time), PTX spelling of copy/MMA instructions.

What you still control

Everything Triton decides for you: per-thread data assignment, vector widths, shared-memory staging and swizzles, pipeline depth, which hardware instruction executes each copy and each MMA.

The price

You must think in layouts. This page is mostly about learning to do that.

The core abstraction: Layout = Shape : Stride

A layout is a pair written Shape:Stride, and it is a function — it maps a logical coordinate to a linear memory offset by a dot product with the strides:

\[ L = (s_0, s_1, \dots) : (d_0, d_1, \dots), \qquad L(c_0, c_1, \dots) = \sum_i c_i \, d_i . \]

A 4×8 matrix stored column-major is (4,8):(1,4): moving down a column steps 1 element in memory, moving across a row steps 4. Row-major is (4,8):(8,1). CuTe's default (cute.make_layout((4,8))) is compact column-major — "LayoutLeft," with the leftmost mode fastest — the opposite of PyTorch's row-major convention, which is why the worked kernel below builds its layouts with an explicit order.

Two things make this more than a strided-tensor rerun. First, shapes can be hierarchical: any mode can itself be a (shape, stride) pair. The notation is dense on first sight, so build the tiled layout ((2,2),(2,4)):((1,4),(2,8)) up in two moves — it is still the same 4×8 matrix, just counted differently:

  1. Split each flat mode in two. The 4 rows become (2,2): a counter i₀ for the row inside a 2×2 tile and a counter i₁ for which tile-row. The 8 columns become (2,4): j₀ inside the tile, j₁ across the four tile-columns. Nothing has moved in memory — the same 32 cells are now addressed by four small counters instead of two, with m = i₀ + 2·i₁ and n = j₀ + 2·j₁.
  2. Give each sub-mode its own stride. The within-tile counters get small strides (1 and 2), so a tile's four cells sit at consecutive offsets; the across-tile counters get large ones (4 and 8), so each tile begins where the previous one ends. The offset is the same stride dot product as before — just with four terms.

That is the whole trick: memory now fills one 2×2 tile completely before moving to the next — the blocking every GEMM diagram draws, expressed inside the type instead of as loop bounds. Decoded sub-mode by sub-mode:

shape((2,2),(2,4)) : stride((1,4),(2,8))
i₀size 2 · stride 1

row inside a tile — the cell below is the very next offset

i₁size 2 · stride 4

which tile-row — the tile below starts one whole tile (4 cells) later

j₀size 2 · stride 2

column inside a tile — a step right skips the tile's 2-cell column

j₁size 4 · stride 8

which tile-column — the next one starts 8 cells later (a stack of two tiles)

offset = i₀·1 + i₁·4 + j₀·2 + j₁·8. Try (m,n) = (3,5): m = 3 → i = (1,1), n = 5 → j = (1,2), so offset = 1·1 + 1·4 + 1·2 + 2·8 = 23 — hover that cell in the tiled preset below and the same arithmetic appears.

Second, strides are unconstrained: overlapping, padded, and repeating layouts are all legal functions, which is exactly what broadcasting, leading-dimension padding, and swizzled shared-memory patterns need.

offset 0 highest offset memory-order walk 2×2 tile boundary (tiled preset)

A layout is a function, not a storage format. The same 4×8 logical grid under four coordinate→offset functions; each cell shows its offset \(L(m,n)\), and the line walks linear memory in order. Column-major snakes down columns; the tiled layout fills each blue-outlined 2×2 tile before moving to the next — the shape a per-thread value fragment or a swizzled shared-memory tile wants; the padded layout (leading dimension 8 for 4 rows) leaves holes at offsets 4–7 of every column. Hover any cell to see its offset computed as the stride dot product.

In code, layouts are ordinary Python objects — buildable, printable, callable:

a = cute.make_layout((4, 8))                      # (4,8):(1,4) — compact column-major
b = cute.make_layout((4, 8), stride=(8, 1))       # (4,8):(8,1) — row-major, spelled out
c = cute.make_ordered_layout((4, 8), order=(1, 0)) # row-major via mode order (rightmost fastest)
d = cute.make_layout(((2, 2), (2, 4)),
                     stride=((1, 4), (2, 8)))      # the tiled layout from the figure

a((2, 3))          # 14 = 2·1 + 3·4 — layouts are functions of coordinates
cute.size(a)       # 32 — number of logical elements
cute.cosize(a)     # 32 — highest offset + 1 (60 for the padded layout: holes count)
Why this wins at compile time

Layout shapes and strides are static by default. Every dot product, tile slice, and partition below is evaluated during compilation and folds into immediate offsets in the generated SASS — the elaborate algebra costs zero instructions at runtime.

The layout algebra: tiling as arithmetic

Because layouts are functions, they compose — and CuTe builds its entire tiling vocabulary out of a handful of operations on them. These four are the load-bearing ones:

Composition: gather one layout through another

composition(A, B) is function composition \((A \circ B)(c) = A(B(c))\): B selects which of A's elements, in B's order; A supplies the addresses.

A = cute.make_layout(20, stride=2)     # 20:2 — every 2nd element
B = cute.make_layout(5,  stride=4)     # 5:4  — every 4th index
cute.composition(A, B)                 # 5:8  — every 4th of every 2nd

Complement: everything the tile doesn't cover

complement(B, n) builds the layout of "the rest": the elements of a size-n space that B does not touch, arranged to tile it. For a tile 4:1 inside 24 elements, the complement is 6:4 — six tile-starting-points, 4 apart. Complement is the piece that turns a tile shape into a partitioning of the whole space.

Divide: split into (within-tile, across-tiles)

logical_divide(A, B) = composition(A, (B, complement(B))) — it reshapes A into two groups of modes: coordinates inside one tile, and the index of which tile.

A = cute.make_layout(24)                      # 24:1
cute.logical_divide(A, cute.make_layout(4))   # (4,6):(1,4) — (elem-in-tile, tile-idx)

# the 2-D workhorse: tile a matrix by (bM, bN)
M = cute.make_layout((16, 256), stride=(1, 16))
cute.zipped_divide(M, (4, 32))   # ((4,32),(4,8)) : ((1,16),(4,512))
                                 # mode 0 = coords in one 4×32 tile
                                 # mode 1 = which of the 4×8 tiles

zipped_divide is logical_divide with the modes regrouped into exactly two: ((TileM,TileN), (RestM,RestN)). Index it with a tile coordinate and you hold that tile; this is how a CTA grabs its piece of the problem — indexing, not pointer arithmetic. Its inverse, logical_product, stamps a tile across a grid of repetitions; its blocked_/raked_ variants are precisely the two thread-assignment pictures in the figure further down.

The tiled layout in the figure is a divide

Preset 3 above, ((2,2),(2,4)):((1,4),(2,8)), is exactly zipped_divide of the column-major 4×8 layout by a (2,2) tiler: mode 0 walks one 2×2 tile, mode 1 walks the 2×4 grid of tiles. What reads as "blocking to fit tensor cores / shared memory" in a paper is one call in the algebra — and since it's all static, it compiles to nothing.

Tensors: a pointer with a layout

A CuTe tensor is an engine (pointer, or register storage) paired with a layout: make_tensor(ptr, layout). Every algebra operation on layouts lifts to tensors — zipped_divide on a tensor tiles its view, slicing with a partial coordinate peels off modes:

gA = cute.zipped_divide(mA, (16, 128))   # ((16,128), (M/16, N/128)) view of A
blkA = gA[((None, None), bidx)]          # keep mode 0, fix tile = bidx → (16,128)

The Nones work like NumPy's : — keep that mode. Three tensor species matter in practice, one per level of the memory hierarchy:

  • Global-memory tensors — a view of HBM, created on the host from PyTorch arrays via DLPack (from_dlpack(t)), zero-copy.
  • Shared-memory tensors — a shared-memory pointer plus a (often swizzled) layout; same algebra, different engine.
  • Fragments — per-thread arrays living in the SM's register file, usually built to mirror a partition: make_fragment_like(thrA). Loading a fragment gives a TensorSSA value supporting vectorized elementwise math (frgA.load() + frgB.load()).

One more tensor deserves a name: the identity tensor, make_identity_tensor(shape), whose value at coordinate \((m,n)\) is the coordinate itself. Tile and partition it alongside the data and every thread ends up holding the logical coordinates of its values — compare them against the true extent (elem_less(coord, shape)) and you have out-of-bounds predication that survives every layout transformation. This is CuTe's answer to Triton's mask=.

The DSL machinery: Python that compiles away

Two decorators split a program: @cute.jit marks host-side functions (set up layouts, tile tensors, launch), @cute.kernel marks device kernels. Calling the kernel object inside a jit function and chaining .launch(grid=…, block=…) issues the launch.

import torch
import cutlass
import cutlass.cute as cute
from cutlass.cute.runtime import from_dlpack

a = torch.randn(2048, 2048, device="cuda")
b = torch.randn(2048, 2048, device="cuda")
c = torch.zeros_like(a)

# zero-copy views: DLPack pointer + a CuTe layout read off shape/stride
mA = from_dlpack(a).mark_layout_dynamic()   # dynamic layout: one compile, any size
mB = from_dlpack(b).mark_layout_dynamic()
mC = from_dlpack(c).mark_layout_dynamic()

elementwise_add(mA, mB, mC)      # first call: trace → MLIR → PTX (~a second)

add = cute.compile(elementwise_add, mA, mB, mC)   # or compile explicitly once…
add(mA, mB, mC)                  # …then launch with microseconds of Python overhead

The semantics to internalize: the Python body runs once, at trace time. Layout algebra, plain print, Python for loops over static ranges — all execute during compilation (loops unroll; print shows you the inferred types and layouts, which is the standard way to debug partitioning). Only operations on runtime values — tensor elements, thread indices — become GPU instructions; for runtime inspection there are cute.printf and cute.print_tensor. Parameters annotated cutlass.Constexpr are compile-time constants, so a Python int like a vector width specializes the kernel the way a C++ template parameter would.

Worked kernel: vectorized elementwise add

The canonical first CuTe DSL kernel (this section follows examples/python/CuTeDSL in the CUTLASS repo, lightly trimmed). The job: \(C = A + B\) over row-major fp32 matrices, saturating HBM bandwidth. The interesting part is not the add — it's the thread–value (TV) layout, the layout that answers "which thread holds which elements of a tile."

The TV layout: choosing who holds what

Pick a tile of 16×128 elements for a 128-thread CTA. Arrange the threads as (4,32) row-major — 32 threads spanning a row, matching the row-major data — and give each thread a (4,4) row-major patch of values. Each thread's row of 4 fp32 values is 16 contiguous bytes: one 128-bit load. Adjacent threads hold adjacent 16-byte chunks, so a warp's loads merge into full-width coalesced transactions. Both properties are choices encoded in two small layouts:

thr_layout = cute.make_ordered_layout((4, 32), order=(1, 0))  # 128 threads, row-major
val_layout = cute.make_ordered_layout((4, 4),  order=(1, 0))  # 4×4 values per thread
tiler_mn, tv_layout = cute.make_layout_tv(thr_layout, val_layout) # tile = (16, 128)

✓ value-major matches data-major → vectorized

Toy version (4×16 tile, 8 threads, 8 values each): every thread's row-chunk is contiguous → one 128-bit load per row.

✗ values raked across columns → scalar loads

Same elements per thread, but strided in the major dimension → eight separate 32-bit loads.

The TV layout is a performance decision, stated as data. Each cell is one tile element, colored by the thread that owns it. Both assignments are legal and touch identical bytes; only the left one lets each thread issue 128-bit vectorized loads (its values are contiguous in the tensor's major dimension), which is the difference between saturating HBM and being instruction-issue-bound. In CuTe you write this choice down as val_layout; in Triton the compiler makes it for you.

Host side: tile the problem

@cute.jit
def elementwise_add(mA, mB, mC, copy_bits: cutlass.Constexpr = 128):
    vector_size = copy_bits // mA.element_type.width          # 4 fp32 per 128-bit load

    thr_layout = cute.make_ordered_layout((4, 32), order=(1, 0))
    val_layout = cute.make_ordered_layout((4, vector_size), order=(1, 0))
    tiler_mn, tv_layout = cute.make_layout_tv(thr_layout, val_layout)

    gA = cute.zipped_divide(mA, tiler_mn)   # ((TileM,TileN), (RestM,RestN))
    gB = cute.zipped_divide(mB, tiler_mn)
    gC = cute.zipped_divide(mC, tiler_mn)

    # identity tensor, tiled identically: each value is its own (m, n) coordinate
    cC = cute.zipped_divide(cute.make_identity_tensor(mC.shape), tiler=tiler_mn)

    elementwise_add_kernel(gA, gB, gC, cC, mC.shape, thr_layout, val_layout).launch(
        grid=[cute.size(gC, mode=[1]), 1, 1],           # one CTA per tile
        block=[cute.size(tv_layout, mode=[0]), 1, 1],   # 128 threads
    )

Device side: slice, partition, copy, add

@cute.kernel
def elementwise_add_kernel(
    gA: cute.Tensor, gB: cute.Tensor, gC: cute.Tensor,
    cC: cute.Tensor,            # coordinate tensor for predication
    shape: cute.Shape,          # true (M, N)
    thr_layout: cute.Layout, val_layout: cute.Layout,
):
    tidx, _, _ = cute.arch.thread_idx()
    bidx, _, _ = cute.arch.block_idx()

    # 1 · CTA level: index out this block's (TileM, TileN) tile
    blk_coord = ((None, None), bidx)
    blkA, blkB, blkC = gA[blk_coord], gB[blk_coord], gC[blk_coord]
    blkCrd = cC[blk_coord]

    # 2 · thread level: a tiled copy built from a 128-bit copy atom + the TV layout
    atom = cute.make_copy_atom(cute.nvgpu.CopyUniversalOp(), gA.element_type)
    tiled_copy = cute.make_tiled_copy_tv(atom, thr_layout, val_layout)
    thr_copy = tiled_copy.get_slice(tidx)

    thrA = thr_copy.partition_S(blkA)     # this thread's slice of the tile
    thrB = thr_copy.partition_S(blkB)
    thrC = thr_copy.partition_S(blkC)
    thrCrd = thr_copy.partition_S(blkCrd)

    # 3 · registers shaped like the per-thread slice
    frgA = cute.make_fragment_like(thrA)
    frgB = cute.make_fragment_like(thrB)
    frgC = cute.make_fragment_like(thrC)

    # 4 · predication: is each of my coordinates inside the real (M, N)?
    frgPred = cute.make_rmem_tensor(thrCrd.shape, cutlass.Boolean)
    for i in range(cute.size(frgPred)):          # unrolls at compile time
        frgPred[i] = cute.elem_less(thrCrd[i], shape)

    # 5 · gmem → registers (vectorized), add, registers → gmem
    cute.copy(atom, thrA, frgA, pred=frgPred)
    cute.copy(atom, thrB, frgB, pred=frgPred)
    frgC.store(frgA.load() + frgB.load())
    cute.copy(atom, frgC, thrC, pred=frgPred)
The partitioning cascade — the pattern every CuTe kernel follows
  1. Problem → CTA tiles: zipped_divide on the host; the kernel indexes its tile with bidx. No pointer arithmetic anywhere.
  2. Tile → per-thread slices: a copy (or MMA) atom plus the TV layout builds a tiled operation; get_slice(tidx).partition_S(...) hands each thread a tensor view of exactly its values.
  3. Slices → registers: fragments mirror the slice shape; cute.copy with the atom becomes vectorized (here 128-bit) load/store instructions.

Note what is absent: no index arithmetic, no bounds if-statements (the predicate fragment rides along through the same partitioning as the data), and no explicit vectorization — the 128-bit width lives in the copy atom and the val layout's contiguity makes it legal. Run with --benchmark and this kernel reports HBM-bandwidth-limited throughput, matching torch.add — the same "nothing to fuse" ceiling as the Triton vector add, reached from one level of abstraction lower.

Scaling up: the GEMM pattern and hardware atoms

Elementwise kernels use one memory space. Real kernels — GEMM, attention — stage tiles through the whole hierarchy, and the same cascade simply repeats per level with an atom at each step. An atom wraps one hardware instruction together with the layout it imposes on the threads and values that execute it; the algebra then tiles that atom across a CTA:

GenerationCopy atomsMMA atomsWhat changed
Ampere (sm_80)cp.async gmem→smem, ldmatrix smem→regmma.sync — warp-wide, e.g. 16×8×16 fp16async global loads; operands in registers
Hopper (sm_90)TMA — bulk tensor copies from a descriptorwgmma — warpgroup (128 threads), async, reads smemcopies and MMAs both become async engines
Blackwell (sm_100)TMA (+ cluster multicast)tcgen05.mma — accumulates in dedicated tensor memory (TMEM)accumulators leave the register file

This table is the practical argument for thread-level control: each generation's flagship instruction imposes stranger layouts (wgmma's smem operand descriptors, TMEM accumulators), and the layout algebra is the tool that keeps them composable. The canonical GEMM skeleton, condensed from the CUTLASS examples (sgemm.py shows the full Ampere version):

# one CTA owns tile (bidx, bidy) of C and marches over K — shapes in comments
gA = cute.local_tile(mA, (bM, bK), (bidx, None))    # (bM, bK, K/bK)
gB = cute.local_tile(mB, (bN, bK), (bidy, None))    # (bN, bK, K/bK)
gC = cute.local_tile(mC, (bM, bN), (bidx, bidy))    # (bM, bN)

# stage tiles through shared memory with a gmem→smem tiled copy (cp.async / TMA atom)
thr_g2s = tiled_copy_g2s.get_slice(tidx)
tAgA = thr_g2s.partition_S(gA)                      # source: this thread's gmem pieces
tAsA = thr_g2s.partition_D(sA)                      # dest:   its smem pieces (swizzled layout)

# partition smem across the tiled MMA; accumulate in registers
thr_mma = tiled_mma.get_slice(tidx)
tCsA = thr_mma.partition_A(sA)
tCrA = thr_mma.make_fragment_A(tCsA)                # register operands, MMA-shaped
acc  = thr_mma.make_fragment_C(thr_mma.partition_C(gC))

for k in cutlass.range(num_k_tiles):                # the mainloop
    cute.copy(atom_g2s, tAgA[None, k], tAsA[None, k % STAGES])  # prefetch next stage
    ...                                              # commit / wait async group, barrier
    cute.copy(atom_s2r, tCsA_k, tCrA)                # smem → registers (ldmatrix)
    cute.gemm(tiled_mma, acc, tCrA, tCrB, acc)       # tensor-core MMAs

Every arrow in the dataflow — gmem→smem, smem→reg, reg→tensor core — is the same three-step cascade as the elementwise kernel with a different atom plugged in, and multi-stage pipelining is just a STAGES-deep smem layout plus an async-copy schedule. FlashAttention in CuTe DSL is this skeleton with two MMAs, an online-softmax rescale between them, and the tiling logic expressed as — of course — layouts.

Rule of thumb

Fusing memory-bound chains (softmax, norms, activations, dequant epilogues): Triton — the compiler's choices are close enough to optimal and you ship the same day. Peak tensor-core throughput on current-generation silicon, exact control of shared memory and pipelines, or an instruction the compiler doesn't emit yet: CuTe DSL — the control of CUDA C++ with compile times and ergonomics that make iteration feel like Triton. The two coexist in most serious stacks.
