TorchTitan — PyTorch-Native Pretraining, Inside Out

TorchTitan is PyTorch's answer to "what if the whole Megatron feature list were rebuilt from composable, native primitives?" This page walks the stack from the inside: the DTensor/DeviceMesh substrate, each parallelism axis as Titan actually applies it, the wrapping order that makes them compose, and the compiler + production layers on top.

One of three framework deep dives — the others are Megatron-LM → and DeepSpeed →; the cross-framework comparison, throughput crossover, and decision guide live on Training Frameworks →. It leans on the strategy pages — Data Parallelism & ZeRO →, Tensor Parallelism →, Sequence Parallelism →, Pipeline Parallelism →, and MoE Parallelism → — for the math of each axis; here the subject is how one codebase composes all of them.

1 · What TorchTitan actually is

TorchTitan (pytorch/torchtitan, the 2024 paper "TorchTitan: One-stop PyTorch native solution for production ready LLM pre-training") is PyTorch's reference pretraining stack — and, just as importantly, the forcing function for PyTorch's distributed APIs. Every feature it ships must be expressible in public torch.distributed primitives; when it can't be, the primitive gets built (FSDP2, async TP, zero-bubble pipeline schedules, and DTensor itself all matured this way). Three design commitments follow:

  • The model is a plain nn.Module. Llama-style transformers written in ordinary eager PyTorch, with no parallelism awareness inside the modeling code. Every distribution decision is applied from outside, after construction — the opposite of Megatron, whose blocks are born parallel.
  • Every parallelism is a DTensor layout on one device mesh. FSDP, TP, PP, CP, and EP are not five subsystems; they are five ways of assigning shardings to tensors over axes of a single DeviceMesh. Composition is mesh algebra, not glue code.
  • Small and legible. The core is on the order of ten thousand lines. It is meant to be read, forked, and benchmarked against — a reference implementation in the literal sense, with production runs (Llama 3.1 8B→405B-class, and MoE recipes for DeepSeek-V3-style models) as the proof it isn't a toy.

A run looks like this — a TOML config selecting a model recipe and parallelism degrees, launched with torchrun under the hood: 

NGPU=64 CONFIG_FILE=./torchtitan/models/llama3/train_configs/llama3_70b.toml \
  ./run_train.sh \
  --parallelism.tensor_parallel_degree 8 \
  --parallelism.pipeline_parallel_degree 2

2 · The substrate — one DeviceMesh, DTensor everywhere

Titan's first act at startup is to fold every parallelism degree into a single world mesh — an n-dimensional view of the ranks, ordered outermost → innermost roughly as:

The world mesh
["pp", "dp_replicate", "dp_shard", "cp", "tp"]
product of degrees = world size; each named axis is a communicator; EP for MoE layers is carved out of the dp_shard × cp ranks (§6)

The ordering encodes the network hierarchy from the parallelism pages: tp innermost so its latency-critical collectives stay on NVLink within a node; pp outermost so only skinny activations cross the slowest links; the data-parallel axes in between, split into dp_replicate (DDP-style replication) and dp_shard (FSDP-style sharding) so that HSDP — shard within a group, replicate across groups — is just "both axes > 1" rather than a separate mode.

On this mesh, DTensor is the common currency. A DTensor is a global logical tensor plus a placement per mesh axis — Shard(dim), Replicate(), or Partial() (values that still need a reduction, e.g. a matmul's unsummed partial products). The DTensor dispatcher knows, for each ATen op, what communication converts input placements into valid output placements — so "run this layer under TP" becomes "declare its weights Shard(0) on the tp axis" and the all-gathers/reduce-scatters follow from the placement rules rather than from hand-inserted collective calls. One type system carries every axis, which is exactly why the axes compose: a single weight can simultaneously be Shard(0) on dp_shard (FSDP) and Shard(0) on tp (column parallel), and checkpointing (§9) can reason about the global tensor behind any such layout.

3 · The DP axis — FSDP2, per-parameter sharding

The data-parallel workhorse is FSDP2 (fully_shard), whose ZeRO-3 math is derived in the ZeRO ladder page. What Titan showcases is the second-generation representation: instead of FSDP1's flat-parameter monolith, every parameter is individually a DTensor sharded Shard(0) over dp_shard. Titan applies it bottom-up, one transformer block at a time, then to the root: 

for block in model.layers:
    fully_shard(block, mesh=dp_mesh, mp_policy=MixedPrecisionPolicy(
        param_dtype=torch.bfloat16, reduce_dtype=torch.float32))
fully_shard(model, mesh=dp_mesh)   # root: embeddings, norm, output head

Each fully_shard call defines one communication group: the unit whose parameters all-gather together before compute and reshard after. Blockwise wrapping is the standard bandwidth/memory compromise — big enough gathers to saturate the interconnect, small enough that only ~one block's full parameters are ever resident. Around that structure FSDP2 runs the classic overlap schedule: implicit prefetch (all-gather block \(n{+}1\) while block \(n\) computes), gradient reduce-scatter issued as soon as each block's backward completes, and fp32 gradient reduction under bf16 compute via the mixed-precision policy. Two knobs recur in Titan configs:

  • reshard_after_forward — freeing gathered parameters after forward (true ZeRO-3) re-gathers them in backward; keeping them (ZeRO-2-like) spends memory to halve parameter communication. Titan sets this per-block, e.g. not resharding the last block since backward begins there immediately.
  • HSDP — with dp_replicate > 1, sharding stays inside a replica group (typically ≤ a few nodes) and gradients all-reduce across groups, capping the all-gather ring size that pure FSDP would otherwise stretch across the whole cluster.

4 · The TP/SP axis — a parallelism plan, not a parallel model

Tensor parallelism in Titan is a dictionary. The model stays untouched; a plan maps submodule names to DTensor layouts, and parallelize_module rewrites the weights in place: 

parallelize_module(block, tp_mesh, {
    "attention_norm": SequenceParallel(),
    "attention.wq":   ColwiseParallel(),
    "attention.wk":   ColwiseParallel(),
    "attention.wv":   ColwiseParallel(),
    "attention.wo":   RowwiseParallel(output_layouts=Shard(1)),
    "ffn_norm":       SequenceParallel(),
    "feed_forward.w1": ColwiseParallel(),
    "feed_forward.w2": RowwiseParallel(output_layouts=Shard(1)),
    "feed_forward.w3": ColwiseParallel(),
})

This is exactly the Megatron sandwich from Tensor Parallelism — column-split into row-split with one reduction per sandwich — plus sequence parallelism on the norms, expressed declaratively: SequenceParallel() means "activations are Shard(1) (sequence dim) here," and the placement rules turn the SP↔TP boundary into the all-gather / reduce-scatter pair automatically. Two refinements matter in practice:

  • Loss parallel. The output projection stays ColwiseParallel — logits remain vocab-sharded — and cross-entropy is computed directly on the shards, never materializing the full \([T \times V]\) logits tensor. For a 128k vocabulary this is one of the largest single activations in the step; Megatron hand-writes a fused vocab-parallel loss kernel for the same reason.
  • Async TP (§8) attacks the sandwich's critical-path collectives by micro-pipelining them against the GEMMs — the compiler-era version of Megatron's userbuffers.

5 · The PP axis — torch.distributed.pipelining

Pipeline parallelism is the one axis that can't be a per-tensor layout — it partitions the module graph and needs a runtime schedule (see Pipeline Parallelism for the bubble math). Titan splits the model structurally: each pipeline rank instantiates the full model skeleton with meta tensors, deletes the layers it doesn't own, and wraps the remainder as one or more PipelineStages. The schedule is then a config choice from torch.distributed.pipelining: GPipe, 1F1B, interleaved 1F1B (multiple stages per rank to divide the bubble), and the zero-bubble family (splitting weight-gradient from input-gradient backward to fill the bubble, including the V-schedule variant). Because schedules consume stages through a generic interface, a new schedule is a new class, not a new fork of the training loop — Titan even accepts schedules described in a CSV of per-rank actions for research on custom ones.

The consequence of splitting first: everything downstream (§3–4, §7–8) is applied per stage. Each stage's submodule is independently TP-planned, checkpointed, compiled, and FSDP-wrapped — PP is the outermost factorization, and the SPMD axes operate inside it.

6 · The long-context and MoE axes — CP and EP

Context parallelism shards the sequence dimension across the cp mesh axis for the entire step, so a million-token context's activations never sit on one GPU. Feed-forward and norms are embarrassingly parallel over tokens; attention is the hard part — every query must see all keys/values — and is handled ring-style: KV shards rotate around the cp group while each rank accumulates partial attention with online-softmax corrections (the same trick that makes FlashAttention tile-able). Titan wraps this as a context manager over SDPA, with load-balancing that deals shard pairs from both ends of the sequence so causal masking doesn't starve the ranks holding early tokens.

Expert parallelism arrived with the MoE recipes (DeepSeek-V3-style models, Llama 4). Titan's design is dp2ep: expert layers borrow their parallelism from ranks the dense layers already use for dp_shard × cp — dense weights stay fully sharded over that whole axis, while each expert lives whole (or TP-sharded) on a slice of it, with token all-to-alls routing between slices. It is the EP × FSDP × TP composition on one DeviceMesh described in MoE Parallelism, plus grouped-GEMM expert kernels; the B200-generation recipes add MXFP8 grouped GEMMs and DeepEP-style all-to-all optimizations. The notable fact is architectural: EP required no new framework machinery — it is one more set of DTensor placements plus a routing layer.

7 · The wrapping order — why it composes

The heart of the codebase is one function per model family (e.g. parallelize_llama) that applies the axes in a fixed order. The order is not stylistic — each layer must see the form of the model the previous layer produced:

0 · Pipeline split — before everything
partition the module graph into stages; all following steps run per stage
4 · fully_shard (FSDP2 / HSDP) — outermost
per-parameter Shard(0) on dp_shard; must wrap last so it governs the final parameters and hooks
3 · torch.compile — per TransformerBlock
regional compilation: one graph per block, reused across layers
2 · Activation checkpointing
full or selective (per-op / every-k-blocks) recompute policy
1 · TP / SP plan — innermost
parallelize_module swaps weights to DTensor layouts on the tp axis
plain eager TransformerBlock — attention + FFN, no parallelism awareness

Titan's composition onion. The pipeline split happens first (it changes which modules exist on this rank); then, innermost to outermost per block: TP/SP layouts, activation checkpointing, regional torch.compile, and FSDP2. Each wrapper only has to understand the interface of the layer beneath it — DTensor is what makes that true.

  • TP before AC/compile: the checkpointing wrapper and the compiler should see the already-sharded module, so recompute and the captured graph operate on local shards (smaller, and correct under the placement rules).
  • Compile before FSDP: FSDP2's all-gather/reshard machinery lives in pre/post-forward hooks around each block; compiling the block's interior keeps the graph free of communication runtime, while the hooks fire between compiled regions. (Whole-model compilation with communication inside the graph is the SimpleFSDP experiment — see §8.)
  • FSDP outermost: it must own the final parameter storage to shard it, and its hooks must be the outermost so prefetch/reshard bracket everything else the block does.
The one-line thesis
Parallelisms compose when they are data layouts, not module rewrites —
Titan's job is mostly to apply five layout systems to one eager model in the right order.

8 · The compiler layer — where Megatron's kernels come from

Titan ships almost no custom CUDA. The fused kernels Megatron hand-writes (see Megatron's fusion inventory) are expected to come from the compiler stack:

PieceWhat it replaces
Regional torch.compile Pointwise-chain fusion (bias+activation, residual+norm chains) via Inductor. Compiling per-block instead of whole-model means one graph compiled once and reused for every layer — near-full-model speedup at a fraction of the compile time, and no graph breaks at FSDP hook boundaries. (See the PyTorch execution model for how capture works.)
SDPA / FlexAttention Fused attention — FlashAttention through a stock API, with FlexAttention generating fused kernels for attention variants (document masking, soft-capping) that would otherwise need hand-written CUDA.
Float8 via torchao Transformer Engine's FP8 GEMMs: linear layers swapped for float8 modules (tensorwise or rowwise scaling), composing with FSDP2 so parameters all-gather already in fp8 — halving parameter comm bytes, not just speeding GEMMs. MX formats (MXFP8) follow on Blackwell.
Async TP Megatron's userbuffers: the compiler decomposes each TP collective into chunks micro-pipelined against the matching GEMM chunks, over SymmetricMemory (direct-mapped peer NVLink buffers) — hiding the TP sandwich's critical-path communication.
Fused optimizer Megatron's multi-tensor Adam: torch.optim.AdamW(fused=True, foreach=…).

The frontier of this bet lives in Titan's experiments/ folder: SimpleFSDP re-expresses FSDP itself as a few hundred lines of DTensor redistributions inside a whole-model torch.compile graph, letting the compiler — not hand-scheduled hooks — reorder, bucket, and overlap the collectives. That is the fully-compiled endpoint (the XLA/GSPMD position) approached incrementally from eager PyTorch.

9 · The production ring — checkpointing, fault tolerance, config

9.1 Distributed checkpointing (DCP)

Because every parameter is a DTensor with a known global shape and placement, checkpointing is layout-independent: each rank saves its shards plus metadata, and load-time resharding lets a checkpoint written on one parallelism layout (say FSDP×TP = 16×8) restore onto another (say 64×2) — the saved unit is the global tensor, not any rank's view of it. On top, Titan runs async checkpointing: the step blocks only to copy state to host memory (seconds), while serialization and upload proceed on background threads under the next steps' compute. Conversion tooling bridges DCP ↔ Hugging Face safetensors at the edges of the run.

9.2 Fault tolerance

For debugging collective hangs there is Flight Recorder integration (a flight log of recent NCCL ops — see NCCL); for surviving failures, torchft integration replicates the run at the dp_replicate axis and reconciles optimizer steps across replica groups with a lighthouse server, so losing a replica group costs its in-flight step rather than a cluster-wide restart-from-checkpoint.

9.3 Config and codebase shape

One TOML file per recipe, every field overridable from the CLI. The layout mirrors the concepts of this page — which is the real sense in which Titan is "readable": the file names are the architecture. 

torchtitan/
  train.py                     # the training loop (~500 lines, readable top to bottom)
  distributed/                 # ParallelDims → world mesh; utils for each axis
  components/                  # checkpoint, float8, optimizer, lr scheduler, loss
  models/llama3/
    model/                     # plain eager nn.Module
    infra/parallelize.py       # the wrapping order of §7 for this family
    infra/pipeline.py          # stage splitting
    train_configs/*.toml       # 8B / 70B / 405B recipes
  experiments/                 # SimpleFSDP, flux, ...

A new model family registers a TrainSpec — model class + its parallelize and pipeline functions + component builders — and inherits the whole stack. That is the practical payoff of §7's discipline: supporting a new architecture means writing its eager module and its plan, not porting it into a framework dialect.

Where this leaves Titan vs. Megatron — one paragraph, not a rematch
What the composition buys
Any eager model, ~10k readable lines, checkpoint resharding across layouts, compiler-supplied kernels, and new axes (EP, CP) arriving as layouts rather than rewrites. The stack of choice when you need to modify the training system — research forks, and verl's FSDP backend lineage.
What vertical integration still buys
Megatron's co-designed kernels + schedules keep the last few MFU points at frontier scale, and its EP × TP × PP MoE planner is more battle-hardened. The full comparison — including where the crossover sits — is on Training Frameworks →.

Summary

One substrate

A single DeviceMesh (pp, dp_replicate, dp_shard, cp, tp) and DTensor placements (Shard/Replicate/Partial) carry every axis; composition is mesh algebra.

One order

Pipeline-split first; then per block, inside-out: TP/SP plan → activation checkpointing → regional torch.compile → fully_shard. Each wrapper sees only the layer beneath it.

Kernels from the compiler

Inductor fuses the pointwise chains, SDPA/FlexAttention covers attention, torchao float8 halves GEMM and comm bytes, async TP micro-pipelines the sandwich — Megatron's §2.2 list, without custom CUDA.

Production by construction

DTensor metadata makes checkpoints reshardable across parallelism layouts; async DCP hides save latency; torchft turns dp_replicate into a fault-tolerance boundary.
