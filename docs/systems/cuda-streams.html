CUDA Streams & Events

Order GPU work without stopping the CPU: one stream gives FIFO semantics, multiple streams expose independent work, events connect them with device-side dependencies, and synchronization marks the rare points where the host truly must wait.

Where this sits: CUDA explains the threads and memory that execute a kernel, including the in-kernel barrier and fence hierarchy; this page explains how kernels and copies are submitted around them. CUDA Graphs records this stream dependency model for replay, while the PyTorch execution model shows why frameworks rely on asynchronous submission.

A CUDA stream is often introduced as a queue, which is correct but incomplete. It is an ordering domain: commands submitted to one stream execute in issue order, while commands in different streams have no ordering unless you add one. The host normally keeps running after submission. The device scheduler starts any command whose dependencies are satisfied and whose required engines and resources are available.

Same stream

FIFO. A later command cannot pass an earlier command in that stream.

Different streams

Potentially concurrent and otherwise unordered. Correctness needs an explicit dependency.

Event wait

Orders device work across streams without blocking the host thread.

Synchronization

Blocks the host until a stream, event, or the whole device reaches a boundary.

The central rule

Streams grant permission to overlap; they do not guarantee overlap. Hardware engines, data dependencies, kernel resource usage, memory type, and hidden synchronization still decide what actually runs together.

1. Three clocks: host submission, stream order, device execution

Host thread

Calls runtime and library APIs. Asynchronous calls usually return after enqueueing, not after completion.

→

Stream queues

Preserve program order per stream and carry event dependencies between streams.

→

GPU engines

Compute engines and copy engines select ready work subject to available resources.

These clocks are deliberately decoupled. A launch such as kernel<<<grid, block, 0, stream>>>(...) can return while older work is still executing. The host may enqueue a long future schedule before the GPU reaches it. That decoupling hides launch latency and lets the CPU prepare the next batch, but it also explains two common surprises:

  • A CPU timer around a launch measures submission, not kernel runtime.
  • An illegal memory access may be reported by a later synchronization call, not by the launch that caused it.
A stream is not a reserved execution lane

Creating eight streams does not divide the GPU into eight pieces. Streams describe readiness and ordering. The scheduler may interleave their thread blocks, run one command first, or serialize everything when a kernel consumes all SM, register, or shared-memory capacity.

2. The ordering rules

RelationshipWhat CUDA guaranteesWhat it does not guarantee
Commands A then B in one streamB begins only after the required effects of A are complete.Host-side completion: an asynchronous submission can return before either command finishes.
Commands in two ordinary streamsNo order unless an event, external semaphore, or host action adds one.They will overlap, start in issue order, or make equal progress.
cudaStreamWaitEventFuture work in the waiting stream stays pending until the recorded event completes; the host only enqueues the wait.Host-side completion of the event.
cudaStreamSynchronizeThe host returns only after previously submitted work in that stream completes.Completion of unrelated streams.
cudaDeviceSynchronizeThe host returns after previously submitted work on the device completes.Good hot-path performance; this is the broadest host-side completion wait, not an in-kernel thread barrier.

Within one stream, this is enough to express a producer-consumer chain: copy input, run a kernel, copy output. Across streams, correctness must be made explicit. Host submission order alone is not a dependency:

// Wrong assumption: launch order across streams is not execution order.
produce<<<grid, block, 0, producer_stream>>>(buffer);
consume<<<grid, block, 0, consumer_stream>>>(buffer);

The consumer is legal only after an event wait, a host synchronization, or another supported cross-stream primitive connects it to the producer.

3. Events: dependencies without a host round trip

An event is a marker inserted into a stream. Recording it says, "this event becomes complete after all earlier work in this stream." Waiting on it from another stream says, "do not begin later work here until that marker is complete." The CPU only enqueues those instructions and continues.

Enqueue the record before the wait. A stream wait captures the event's most recent recording at the time of the call; recording it again later does not retarget that wait. Waiting on an event that has never been recorded is a no-op, not a promise to wait for a future recording.

cudaStream_t copy_stream, compute_stream;
cudaEvent_t input_ready, kernel_done;

cudaStreamCreateWithFlags(&copy_stream, cudaStreamNonBlocking);
cudaStreamCreateWithFlags(&compute_stream, cudaStreamNonBlocking);
cudaEventCreateWithFlags(&input_ready, cudaEventDisableTiming);
cudaEventCreateWithFlags(&kernel_done, cudaEventDisableTiming);

cudaMemcpyAsync(d_x, h_x, bytes, cudaMemcpyHostToDevice, copy_stream);
cudaEventRecord(input_ready, copy_stream);

// Device-side dependency: the host does not block here.
cudaStreamWaitEvent(compute_stream, input_ready, 0);
kernel<<<grid, block, 0, compute_stream>>>(d_x, d_y);
cudaEventRecord(kernel_done, compute_stream);

do_independent_cpu_work();
cudaEventSynchronize(kernel_done);  // Wait only when the result is needed.
Read the dependency, not the API sequence

input_ready creates the edge copy → kernel. kernel_done creates a narrow host-consumption boundary. Replacing either event with cudaDeviceSynchronize() would be correct but would erase unrelated concurrency.

Use events created with cudaEventDisableTiming when they exist only for ordering. Use timing-enabled events when you need device elapsed time. Events can also bridge library calls because cuBLAS, cuDNN, NCCL, and framework kernels all participate in the same stream ordering model when their handles or calls use the intended stream.

Completion does not copy d_y into host memory: enqueue a dependent D2H transfer and wait for that transfer before reading its host destination. These snippets focus on ordering; production code must check CUDA return values and launch errors, and release streams, events, and buffers when no longer needed.

4. Copy/compute overlap and the pipeline it creates

Suppose each of \(N\) chunks needs an H2D copy taking \(C\) and a kernel taking \(K\). One stream serializes every stage:

\[ T_{\text{serial}} = N(C+K). \]

With pinned host memory, independent buffers, a copy engine, and at least two streams, chunk \(i+1\) can copy while chunk \(i\) computes. Ignoring launch overhead, the ideal two-stage pipeline is

\[ T_{\text{pipeline}} \approx C + K + (N-1)\max(C,K). \]
H2D copy kernel dependency-ready point

Overlap removes idle slots, not work. This idealized model uses one H2D engine, one compute lane, and two reusable input buffers, with no launch overhead or bandwidth contention. Its steady-state throughput is limited by the slower stage, \(\max(C,K)\), after paying one fill and one drain. Green markers show copy completion; a kernel may still wait for the compute lane.

A compact double-buffer pattern alternates two non-blocking streams and two device input buffers. Assume both streams and buffers are already created, every host_chunk[i] is pinned, and every output[i] names distinct device output storage. Reusing a stream every other chunk automatically prevents that stream's input buffer from being overwritten before its previous kernel finishes:

for (int i = 0; i < chunks; ++i) {
    int slot = i % 2;
    cudaStream_t s = streams[slot];

    cudaMemcpyAsync(device_buffer[slot], host_chunk[i], bytes,
                    cudaMemcpyHostToDevice, s);
    kernel<<<grid, block, 0, s>>>(device_buffer[slot], output[i]);
}

Keep each host source unchanged until its copy completes. After enqueueing, synchronize both streams before freeing their buffers, or record a completion event in each and make the next consumer wait on both. The snippet schedules work; returning from the loop is not a completion boundary.

The four conditions for real overlap

ConditionWhy it mattersTypical failure
Pinned host memoryDMA can access it directly; use cudaMallocHost/cudaHostAlloc or a framework pinned allocator.Pageable memory forces staging and may make an "async" copy block or serialize.
Separate streams and buffersOne stream is FIFO, and one buffer cannot be overwritten while its consumer still reads it.All stages use the default stream or reuse one allocation too early.
Available enginesThe device needs an asynchronous copy engine, and direction-specific engines determine H2D/D2H concurrency.The hardware or transfer direction cannot overlap as assumed.
No hidden serializationHost waits, legacy-default-stream dependencies, and shared bandwidth can remove the expected overlap or its speedup.A synchronization between chunks drains the pipeline, or copy/kernel bandwidth contention lengthens both stages.

Overlapping two kernels additionally needs spare blocks, registers, shared memory, and scheduler capacity. Copy/compute overlap is different: a DMA copy can run on a copy engine while a kernel occupies all SMs, though they may still contend for memory bandwidth.

Host-buffer lifetime is part of correctness. The source of an asynchronous H2D copy must remain valid and unchanged until that copy completes. Pinned memory makes overlap possible; it does not make early reuse safe.

Stream priorities, created with cudaStreamCreateWithPriority, influence which pending work the scheduler prefers. They are hints, not hard reservations or guaranteed preemption. A long-running kernel may still delay urgent work depending on the architecture and its scheduling granularity.

5. The default stream can add ordering you did not write

CUDA has two default-stream modes. Confusing them is a classic source of "why did this serialize?" bugs, especially when code from several libraries meets in one process.

ModeSemanticsPractical guidance
Legacy default stream
0 / cudaStreamLegacy		Acts as a synchronizing stream with other blocking streams in the same context. Work can acquire implicit edges that are absent from the source.Do not rely on it as an accidental global barrier. Explicit events state intent better.
Per-thread default stream
cudaStreamPerThread		Each host thread gets a default stream that behaves like an ordinary stream rather than the legacy null stream.Know how every translation unit was compiled; mixed assumptions are difficult to reason about.
Explicit non-blocking stream
cudaStreamNonBlocking		Does not synchronize with the legacy default stream merely because it is the default.Prefer explicit streams and explicit dependencies in reusable runtime code.

Libraries add one more layer: a cuBLAS or cuDNN handle has an associated stream, and NCCL collectives are enqueued into the stream passed to the call. If a handle silently remains on stream 0, a carefully designed side-stream pipeline can collapse back into serialization or race with work that was expected to precede it.

6. PyTorch: current streams, waits, and allocator lifetime

PyTorch enqueues CUDA operators on the current stream for that device. Most user code stays on the default stream, so ordinary operator order appears synchronous even though the CPU is running ahead. Side streams require both execution ordering and storage-lifetime bookkeeping:

import torch

default = torch.cuda.current_stream()
side = torch.cuda.Stream()

# Side-stream work must wait for x's prior producers.
side.wait_stream(default)
with torch.cuda.stream(side):
    y = stage1(x)
    x.record_stream(side)       # Keep x's storage alive through this use.

# Future default-stream work waits without blocking Python.
default.wait_stream(side)
z = stage2(y)
y.record_stream(default)        # Keep y alive through the consumer work.
Two different problems, two different tools
  • wait_stream / wait_event protects data dependencies: a consumer must not execute before its producer.
  • record_stream protects allocator lifetime: PyTorch's caching allocator must not recycle a tensor's storage while another stream may still touch it.

For input pipelines, pinned DataLoader memory plus tensor.to("cuda", non_blocking=True) permits H2D copies to overlap with useful work. The flag alone is not a guarantee: pageable input, immediate consumption on the same stream, or a later host read can still remove the overlap.

Operations that return a CUDA value to Python synchronize. Common examples include .item(), many .cpu() paths, and printing values that must be materialized. Keep scalar decisions on-device or move them outside the hot region when possible.

7. Timing and asynchronous errors

Use events for device time

cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

cudaEventRecord(start, stream);
kernel<<<grid, block, 0, stream>>>(x);
cudaEventRecord(stop, stream);

cudaEventSynchronize(stop);
float milliseconds = 0.0f;
cudaEventElapsedTime(&milliseconds, start, stop);

Events are timestamped in the device timeline, so this measures queued GPU work between the markers rather than the few microseconds the CPU spent issuing it. Warm up first, repeat enough times to reduce noise, and keep the endpoints in a dependency chain that actually brackets the work you mean to measure.

Errors can surface later

A launch can fail in two phases. Configuration errors such as an invalid grid can be reported immediately by cudaGetLastError() or cudaPeekAtLastError(). Execution faults such as an illegal device address happen asynchronously and are commonly reported by a later event/stream/device synchronization or blocking transfer.

Debug mode is not benchmark mode

A synchronization after every launch is useful while isolating a fault, and CUDA_LAUNCH_BLOCKING=1 makes framework stack traces easier to attribute. Both destroy the asynchronous schedule. Remove them before measuring performance.

BoundaryHost behaviorScope
Kernel launch / most async APIsReturns after submissionNo completion boundary
cudaEventSynchronize(event)BlocksWork needed to complete that event
cudaStreamSynchronize(stream)BlocksPreviously queued work in one stream
cudaDeviceSynchronize()BlocksPreviously queued work on the device
Blocking D2H copy / host value readBlocksDependencies needed to make host-visible data valid

Allocations can also be scheduling boundaries. Traditional cudaMalloc/cudaFree are poor choices in a hot asynchronous path because allocation management may synchronize. Stream-ordered pools and cudaMallocAsync/cudaFreeAsync attach allocation lifetime to stream order, which is the same idea PyTorch's caching allocator implements at framework level.

8. Read the profiler as a dependency graph

Nsight Systems is the first tool for streams: it shows CPU launch calls, CUDA API time, stream lanes, copy engines, kernels, events, and gaps on one timeline. Nsight Compute answers the next question: if streams are independent but kernels still serialize, does one kernel consume all the resources needed for concurrency?

A reliable design sequence

First draw the true producer-consumer DAG. Put naturally ordered chains in one stream. Add events only at cross-stream edges. Add host waits only where the CPU consumes a result. Then profile to see whether the hardware can exploit the concurrency you exposed.
