Pipeline Parallelism — Stages, Schedules, and the Bubble

When the model overflows one NVLink node, split it vertically across nodes. This page derives the three schedules — GPipe, 1F1B, and interleaved 1F1B — through their bubble and memory formulas, and shows when PP is the right axis to reach for.

Prerequisites: Sharding & Collectives → (point-to-point send/recv) and Tensor Parallelism → (why TP is bounded to one node). Pipeline parallelism picks up where TP stops.

1 · Why pipeline parallelism

Tensor parallelism shards operators across the \(|X|\) GPUs in a NVLink island, typically \(|X| \le 8\). At 80 GB each that gives 640 GB of HBM — enough for models up to roughly 100B parameters in bf16 with optimizer state. Larger models must span multiple nodes, and the cross-node fabric (InfiniBand, RoCE) is an order of magnitude slower than NVLink. That rules out TP: its AllReduce is on the critical path of every layer, so it must stay inside one node.

Pipeline parallelism (PP) takes a different cut: it splits the depth of the model rather than the width of its layers. The \(L\) transformer layers are partitioned into \(PP\) equal stages; stage \(i\) lives on one node and owns \(L/PP\) consecutive layers. Stages communicate only at boundaries — passing activations forward and gradients backward — using cheap point-to-point send/recv rather than AllReduce.

The PP contract
Each stage holds \(L/PP\) layers. The only cross-node traffic is the activation tensor at each stage boundary: \(B \times T \times D\) values in each direction per micro-batch, one send and one recv.

The cost: stages can't all run simultaneously, because stage 2 can't start until stage 1 finishes. The idle time this forces is called the pipeline bubble, and minimizing it is the central engineering challenge of pipeline parallelism.

2 · Naive GPipe — the simple schedule

GPipe introduced the simplest pipeline schedule: split the global batch into \(m\) equal micro-batches, run all \(m\) forward passes first, then all \(m\) backward passes.

Stage t=1t=2t=3t=4 t=5t=6t=7t=8 t=9t=10t=11t=12
1 F1F2F3F4 B4B3B2B1 ————
2 —F1F2F3 F4B4B3B2 B1———
3 ——F1F2 F3F4B4B3 B2B1——
4 ———F1 F2F3F4B4 B3B2B1—

F = forward   B = backward   — = idle (bubble). PP=4, m=4 micro-batches.

Bubble fraction

Stage 1 must wait for stages 2–4 to finish all their forward passes before it can begin its backward. That wait is \(PP - 1\) forward-pass slots. The total useful work is \(2m\) slots (m forward + m backward) per stage. So:

\[ \text{bubble fraction (GPipe)} = \frac{PP - 1}{m + PP - 1} \]

For \(PP = 4,\ m = 4\): bubble = \(3/7 \approx 43\%\). Nearly half the cluster sits idle. The only fix is to increase \(m\), but GPipe has a second problem that limits how large you can make \(m\).

Activation memory

GPipe stores activations for all \(m\) micro-batches simultaneously before starting any backward pass. If each micro-batch's activations across \(L/PP\) layers cost \(A\) bytes, the peak activation memory per stage is \(m \times A\). Making \(m\) large to reduce the bubble directly inflates activation memory — a hard tradeoff.

GPipe's activation memory scales with the number of micro-batches \(m\). Choosing \(m\) large enough to get a small bubble (\(m \gg PP\)) quickly OOMs for non-trivial stage sizes.

3 · 1F1B — one forward, one backward

Megatron-LM's 1F1B schedule breaks the all-forward-then-all-backward barrier by interleaving one forward and one backward pass per stage. The key insight: as soon as stage 4 finishes forward for micro-batch 1, it can immediately start backward for micro-batch 1 — freeing stage 3 to continue without waiting for all micro-batches to flood the pipeline.

Stage t=1t=2t=3t=4t=5t=6 t=7t=8t=9t=10t=11
1 F1F2F3F4 B1F5B2F6 B3B4B5
2 —F1F2F3 F4B1F5B2 F6B3B4
3 ——F1F2 F3F4B1F5 B2F6B3
4 ———F1 F2F3F4B1 F5B2F6

1F1B schedule: PP=4, m=6 micro-batches. Bubble (gray) only at startup and drain.

The bubble only occurs during the startup phase (PP-1 forward passes filling the pipe) and the drain phase (PP-1 backward passes flushing it). In steady state every stage alternates F and B.

\[ \text{bubble fraction (1F1B)} = \frac{PP - 1}{m + PP - 1} \]

Same formula as GPipe — but now the memory profile is fundamentally different.

Why memory is better

In steady state, each stage at most holds activations for \(PP\) in-flight micro-batches (the ones currently in the startup phase). Once backward for micro-batch 1 completes at stage 1, its activations are freed before micro-batch 5 arrives. Peak memory per stage is bounded by \(PP\), not by \(m\).

GPipe vs 1F1B — memory at PP=4, m=16
GPipe

All 16 micro-batch activations in memory simultaneously. Peak = \(16 \times A\) per stage. Making \(m\) large enough to hide the bubble OOMs.

1F1B

At most \(PP = 4\) micro-batches in flight. Peak = \(4 \times A\) per stage, regardless of \(m\). Large \(m\) is cheap to achieve.

4 · Interleaved 1F1B — virtual stages

The 1F1B bubble fraction \((PP-1)/(m+PP-1)\) still grows with \(PP\). At \(PP = 16\) and \(m = 32\) it is \(15/47 \approx 32\%\). Interleaved 1F1B halves (or further reduces) the bubble by assigning each device \(v \gt 1\) virtual stages — non-contiguous chunks of layers — instead of one contiguous block.

Example: PP=4, v=2 virtual stages

With 32 layers: device 0 owns layers 0–3 and 16–19; device 1 owns layers 4–7 and 20–23; etc. Each forward or backward pass visits \(PP\) devices twice — one pass per virtual stage — with a P2P send at each virtual-stage boundary.

\[ \text{bubble fraction (interleaved, } v \text{ virtual stages)} = \frac{1}{v}\cdot\frac{PP - 1}{m + PP - 1} \]

The bubble shrinks by \(1/v\). At \(v = 2\), the example above drops from 32% to 16%.

The cost of virtual stages

Every virtual-stage boundary requires a P2P send/recv, so a single micro-batch now generates \(2(v-1)\) extra cross-node P2P sends per forward and per backward. With InfiniBand at ~25 GB/s and activations of \(B \times T \times D\) bytes, even \(v = 2\) adds measurable latency per step. In practice \(v = 2\) is the most common choice — enough to cut the bubble materially without overwhelming the network.

The tradeoff: more virtual stages reduce the bubble but increase P2P traffic and raise peak activation memory (now \(v \times PP\) stages' worth per device). Usually \(v \le 4\).

5 · Zero bubble — splitting the backward pass

Everything so far treats the backward pass for a micro-batch as one indivisible unit \(B\) that must run on stage \(p\) before stage \(p-1\) can start its own. That dependency is what forces the bubble. But it is only half true — and the half that is false is where the remaining bubble lives.

Two backwards, not one

A layer's backward pass computes two different things:

  • \(B\) — the gradient with respect to the layer's inputs. The previous stage cannot start its backward without this. It is on the critical path.
  • \(W\) — the gradient with respect to the layer's weights. Nobody is waiting for it. It must merely finish before the optimizer step at the end of the iteration.

Standard 1F1B computes both together, which means work that nothing depends on is being executed while a downstream device sits idle. Zero Bubble (Qi et al., 2023) splits them into separately schedulable units \(B\) and \(W\), then uses the \(W\) chunks as filler — pushing them into precisely the slots that would otherwise be bubble.

The scheduling insight
\[ \underbrace{B}_{\text{blocks the previous stage}} \;+\; \underbrace{W}_{\text{blocks nothing until the step}} \]
Roughly \(1/3\) of backward FLOPs are weight-gradient work with no downstream dependency — enough filler to cover a large share of a 1F1B warm-up/cool-down bubble.

The handwave in the name is worth being precise about: the schedule that reaches a literally empty bubble also has to relax the optimizer-step synchronization at the iteration boundary (the zero-bubble paper bypasses the usual synchronized gradient-clipping/step barrier). The variant most systems actually deploy keeps the synchronization and takes a bubble that is much smaller than 1F1B's without being exactly zero.

Where this matters

The bubble fraction \((PP-1)/(m+PP-1)\) is worst when \(PP\) is large relative to \(m\) — exactly the regime you are pushed into when you drop tensor parallelism and lean on pipeline depth instead. DeepSeek-V2 is the production example: 16-way zero-bubble PP, 8-way expert parallelism, ZeRO-1, and no TP at all for a 236B model (see MoE Parallelism §5). At \(PP = 16\) a 1F1B schedule would be giving up ~32% at \(m = 32\); that is the cost the split backward is buying back.

Zero-bubble composes with interleaving rather than replacing it — \(v\) virtual stages reduce the bubble to be filled, and \(W\)-splitting fills what remains. It also interacts with §6: \(W\) chunks deferred to late in the iteration keep their activations alive longer, so the schedule trades some peak activation memory for the bubble it removes.

6 · Activation memory at stage boundaries

The activations stored at each stage boundary have the shape \([B_\mu, T, D]\) where \(B_\mu = B / m\) is the micro-batch size. In bf16 that is:

\[ \text{per-boundary activation} = 2 \cdot B_\mu \cdot T \cdot D \text{ bytes} \]

For \(B_\mu = 4,\ T = 4096,\ D = 8192\): each boundary stores \(2 \times 4 \times 4096 \times 8192 \approx 268\) MB. With \(PP\) in-flight micro-batches and \(v\) virtual stages, peak boundary activation memory per device is \(\approx v \times PP \times 268\) MB — separate from the within-stage activations used for backprop.

Gradient checkpointing

Within-stage activations (the outputs of each layer needed for the backward pass) can dwarf boundary activations for deep stages. Gradient checkpointing (also called activation recomputation) trades compute for memory: discard all intermediate activations during the forward pass, then recompute them during backward by re-running the forward through each checkpointed segment.

Full recomputation adds one extra forward pass per backward, increasing compute by ~33%. Selective recomputation saves only the "cheap but large" activations (e.g., attention softmax outputs) and recomputes only the cheap-to-recompute ops — a useful middle ground. Most frontier training runs use selective recomputation to keep each stage's activation memory within the HBM budget without the full 33% overhead.

7 · Choosing the PP degree

The central rule: use PP when TP at maximum node-width still doesn't fit the model in memory. Beyond that, the key variables are:

VariableEffect on PP choice
Micro-batch count \(m\) Bubble = \((PP-1)/(m+PP-1)\). Need \(m \gg PP\) to keep bubble below 5–10%. Common target: \(m \ge 4 \times PP\).
Global batch size \(B\) \(m = B / (B_\mu \times DP)\). If \(B\) is fixed and \(DP\) is large, \(m\) may be too small to hide the bubble — push \(PP\) down or tolerate a larger bubble.
Layer count \(L\) Each stage needs \(L/PP\) layers. At small \(PP\) each stage has many layers (good: more compute per step, amortizes P2P). At large \(PP\) stages get thin — inter-node P2P becomes the bottleneck.
Inter-node bandwidth P2P activation sends at stage boundaries use InfiniBand/RoCE. Each send is \(2 B_\mu T D\) bytes; this must be ≪ stage compute time. At 400 Gb/s IB and \(D = 8192,\ T = 4096,\ B_\mu = 4\): ~268 MB / 50 GB/s ≈ 5 ms per send.
Typical frontier configuration
TP=8 (one node), PP=4–16 (across nodes), DP fills remaining GPUs, \(m \approx 4 \times PP\), interleaved 1F1B with \(v = 2\).

At very large scale (e.g., \(PP = 16,\ DP = 64\)), minimizing the bubble requires large \(m\), which means large global batch sizes. This is why frontier training runs use batch sizes in the millions of tokens per step — not only for statistical efficiency but to keep the pipeline full.

8 · Summary

The cut

PP splits the model by depth (consecutive layers per stage). Stages communicate via P2P send/recv — not AllReduce — so cross-node bandwidth is used only at stage boundaries.

GPipe

All-forward-then-all-backward. Bubble = \((PP-1)/(m+PP-1)\). Memory = \(m \times A\) per stage. Simple but memory-expensive at large \(m\).

1F1B

Interleaved forward/backward. Same bubble formula but memory = \(PP \times A\) per stage — independent of \(m\). Enables large \(m\) without OOM.

Interleaved 1F1B

Virtual stages: \(v\) non-contiguous layer chunks per device. Bubble shrinks to \(\frac{1}{v}(PP-1)/(m+PP-1)\) at the cost of \(v\) extra P2P sends per step.

Zero bubble

Split backward into \(B\) (input grads, on the critical path) and \(W\) (weight grads, blocking nothing until the step), then schedule \(W\) into the bubble. DeepSeek-V2 ran 16-way ZB-PP with no TP.

Memory

Stage boundary activations: \(2 B_\mu T D\) bytes each, \(v \times PP\) in flight. Within-stage activations dominate; use gradient checkpointing to trade ~33% compute for memory.

The rule

Use PP when model exceeds one-node TP capacity. Keep \(m \ge 4 \times PP\) to hold the bubble below ~20%. Use \(v = 2\) virtual stages unless P2P is the bottleneck.
