verl Architecture — The HybridFlow Controller Model

How verl expresses an RLHF dataflow as ordinary single-process Python while every line fans out to a distributed cluster — the hybrid single/multi-controller model, the WorkerGroup and DataProto abstractions, the trainer control loop, and the pluggable training and rollout backends.

verl (Volcano Engine Reinforcement Learning) is the open-source implementation of HybridFlow (ByteDance, arXiv:2409.19256). This page is the architectural map: how the framework is put together. For the GPU-allocation decisions on top of it see Resource Pool Placement; for a step-by-step tensor trace see the PPO and GRPO walkthroughs.

1. The Problem: RL Post-Training Is a Dataflow of Mismatched Workloads

A single RLHF/GRPO step chains together workloads that want completely different execution models:

StageWorkloadWants to run as…
GenerationAutoregressive decoding of long responsesAn inference engine (vLLM/SGLang) with its own TP layout, paged KV cache, continuous batching
Experience prepold/ref log-probs, value estimates, rewardsBatched forward passes — often a different sharding than training
TrainingActor + critic forward/backward/optimizerAn SPMD distributed-training job (FSDP or Megatron TP/PP/EP)
Advantage / lossGAE or group-relative normalizationLight, mostly-sequential array math on the gathered batch

The hard part is not any one stage — it is orchestrating the dataflow between them: data has to move from an inference engine's layout into a training engine's layout, weights have to move the other way, and the whole thing has to be expressed in code a researcher can read and modify. Two naive designs each fail at one end:

Single-controller everywhere

  • One driver issues every op to every GPU (à la classic Ray / RPC-per-op).
  • Easy to express — the dataflow is just Python.
  • Too slow for training — per-op control + data dispatch overhead across thousands of micro-ops crushes throughput.

Multi-controller everywhere (pure SPMD)

  • Every rank runs the same program; collectives coordinate them (à la Megatron / DeepSpeed launch).
  • Fast — no central bottleneck inside a stage.
  • Rigid to express — cross-stage dataflow and resharding become tangled rank-aware code; hard to prototype a new algorithm.

HybridFlow's thesis: use each model where it is strong. Orchestrate the dataflow between stages with a single controller, and run the heavy compute inside each stage as multi-controller SPMD. verl is that idea made concrete.

2. The Hybrid Single/Multi-Controller Model

verl splits the program into two planes:

Single-controller plane — one driver process
RayPPOTrainer.fit() — the RL algorithm written as sequential Python over the whole batch.
generate_sequences() compute_log_prob() compute_values() compute_advantage() ·driver-side update_actor()
Bridge — @register(dispatch_mode=…) + DataProto
Each driver call is intercepted: the batch is scattered to workers, the method runs SPMD, results are gathered back into one DataProto.
Multi-controller plane — WorkerGroups (SPMD over GPUs)
ActorRollout WorkerGroup
(FSDP/Megatron + vLLM/SGLang) Critic WorkerGroup Reference WorkerGroup RewardModel WorkerGroup

The driver never touches an individual GPU rank. It calls a method on a WorkerGroup as if it were a single object; the bridge turns that one call into an SPMD invocation across all the group's ranks and reassembles the output. That is the whole trick — and it is what lets the body of fit() read like a NumPy script while executing on hundreds of GPUs.

The dispatch/collect bridge

A worker method becomes driver-callable by decorating it with @register, which declares how the driver's single call maps onto the ranks:

from verl.single_controller.base.decorator import register, Dispatch

class CriticWorker(Worker):

    @register(dispatch_mode=Dispatch.DP_COMPUTE_PROTO)
    def compute_values(self, data: DataProto) -> DataProto:
        # runs on every rank; `data` is already this rank's shard
        values = self.critic_model(data.batch['input_ids'])
        return DataProto.from_dict({'values': values})

The dispatch_mode picks the scatter/gather strategy:

Dispatch modeScatterGatherUsed for
ONE_TO_ALLBroadcast same args to every rank—Lifecycle: init_model, save_checkpoint
DP_COMPUTE_PROTOSplit the DataProto into N equal chunks, one per DP rankConcatenate the N returned DataProtosThe workhorse: log-probs, values, generation, updates
MEGATRON_COMPUTE_PROTODP-chunk, but broadcast within each TP/PP groupCollect only from the rank that owns the outputMegatron-backed workers

With DP_COMPUTE_PROTO, the driver hands the bridge one batch of, say, 1024 sequences; the bridge chunk()s it into 8 shards for an 8-way data-parallel group, calls compute_values on each rank with its shard, then concat()s the 8 results back into one 1024-row DataProto for the next line of fit(). The padding to make the batch divisible by the DP size, the scatter, and the gather are all handled by the decorator — invisible in the algorithm code.

3. The Four Core Abstractions

Worker & WorkerGroup

A Worker is a Ray actor pinned to a GPU. A WorkerGroup (concretely RayWorkerGroup) is the set of workers that run one role SPMD-style. The driver holds one handle per group — actor_rollout_wg, critic_wg, ref_policy_wg, rm_wg — and the registered methods of the underlying worker class appear as methods on that handle.

from verl.single_controller.ray import RayWorkerGroup, RayClassWithInitArgs

actor_rollout_wg = RayWorkerGroup(
    resource_pool = actor_pool,                       # which GPUs (see Placement page)
    ray_cls_with_init = RayClassWithInitArgs(
        cls = ActorRolloutRefWorker, config = config.actor_rollout_ref),
)
actor_rollout_wg.init_model()                         # ONE_TO_ALL → runs on all ranks

ResourcePool — which GPUs a group lives on

A ResourcePool is a named set of GPUs; the ResourcePoolManager maps each worker class to a pool. Two groups in the same pool are colocated (they share VRAM and take turns); groups in different pools run on disjoint GPUs and can overlap. This is the single most consequential knob for throughput and memory — it gets its own page: Resource Pool Placement in VeRL.

DataProto — the universal batch container

Every method on the driver↔worker boundary speaks DataProto: a wrapper around a TensorDict (.batch, the GPU tensors) plus a dict of NumPy/object arrays (.non_tensor_batch, e.g. raw prompts) and a free-form .meta_info. It is the lingua franca that makes the bridge generic — scatter/gather only has to know how to split and join DataProtos, not every method's bespoke arguments.

data = DataProto.from_dict({'input_ids': ids, 'attention_mask': mask})
shards = data.chunk(8)                 # what DP_COMPUTE_PROTO does to scatter
merged = DataProto.concat(shards)      # …and to gather
batch  = batch.union(gen_output)       # glue generation outputs onto the prompts
group  = batch.repeat(n_samples)       # GRPO: n responses per prompt

Because resharding the batch is just chunk/concat/union on a DataProto, the same algorithm code runs whether the actor is 8-way FSDP or a Megatron TP×PP×DP mesh — only the dispatch mode changes.

The HybridEngine — training and generation on one GPU set

The ActorRolloutRefWorker is special: it hosts both the training engine (FSDP/Megatron) and the rollout engine (vLLM/SGLang) on the same GPUs, switching modes within a step. This colocation — the "HybridEngine" — is why a default verl run needs only one pool. The memory choreography of that switch (all-gather weights → load into vLLM → free → generate → tear down → resume FSDP) is detailed on the Placement page.

4. The Control Loop — RayPPOTrainer.fit()

Here is the entire RL algorithm, stripped to its skeleton. Read it as ordinary single-process code; remember that every *_wg.* call silently scatters to a cluster and gathers back. This single function is the whole point of the architecture:

for batch in dataloader:                                  # prompts
    # ── 1. Generation (rollout engine inside the ActorRollout group) ──
    gen = actor_rollout_wg.generate_sequences(batch)       # DP_COMPUTE_PROTO
    batch = batch.union(gen)                                # prompts + responses

    # ── 2. Experience: recompute log-probs, ref, values, rewards ──
    batch = batch.union(actor_rollout_wg.compute_log_prob(batch))   # old π logprob
    batch = batch.union(ref_policy_wg.compute_ref_log_prob(batch))  # KL reference
    batch = batch.union(critic_wg.compute_values(batch))           # PPO only
    batch = batch.union(rm_wg.compute_rm_score(batch))            # or a rule fn

    # ── 3. Advantage — driver-side array math, no GPU group needed ──
    batch = compute_advantage(batch, estimator=config.algorithm.adv_estimator)
            # GAE for PPO · group-relative z-score for GRPO

    # ── 4. Update ──
    critic_wg.update_critic(batch)                          # PPO only
    actor_rollout_wg.update_actor(batch)                    # clipped PG step

    # ── 5. Sync fresh weights into the rollout engine ──
    #     (implicit in HybridEngine; explicit + async in disaggregated mode)

Two things to notice. First, advantage estimation runs on the driver — it is light array math over the already-gathered batch, so there is no reason to pay dispatch overhead for it; swapping PPO's GAE for GRPO's group-relative baseline is a one-line change here, not a distributed-systems change. Second, which groups exist is algorithm-dependent: GRPO simply never constructs critic_wg, and the corresponding lines vanish. The walkthroughs trace exactly what each line does to the tensors — PPO (with critic, GAE) and GRPO (no critic, group baseline).

5. Pluggable Backends

The roles above are interfaces; verl ships interchangeable implementations. You pick a training backend and a rollout backend in config, and the control loop is unchanged.

Training backend — FSDP vs Megatron

FSDP / FSDP2 (default)

  • ZeRO-3 parameter + grad + optimizer sharding across the DP group.
  • Almost no model-code changes — wraps a HuggingFace model directly.
  • Best for prototyping and up to ~70B; the easy on-ramp.
  • Dispatch: DP_COMPUTE_PROTO.

Megatron-LM

  • Full 4-D parallelism: tensor (TP), pipeline (PP), expert (EP), context (CP).
  • Needed for very large dense models and large MoE (expert parallelism).
  • Requires a Megatron model definition / weight conversion.
  • Dispatch: MEGATRON_COMPUTE_PROTO.

Rollout backend — vLLM vs SGLang

Generation is delegated to a production inference engine: vLLM or SGLang, both with paged KV cache and continuous batching. verl drives the engine for generation and, in async/disaggregated mode, runs it as a standing server. The choice is a config string (actor_rollout_ref.rollout.name: vllm | sglang); the slime / Miles walkthrough shows the contrasting SGLang-HTTP-server design used by another framework.

The pluggability invariant

Training backend, rollout backend, and RL algorithm vary independently. FSDP+vLLM+GRPO, Megatron+SGLang+PPO, and everything between reuse the same fit() loop — because every combination communicates only through DataProto across the dispatch bridge.

6. Weight Resharding — The Crux Between Train and Generate

The actor's weights live in two different layouts: the training engine's (FSDP shards, or a Megatron TP×PP mesh) and the inference engine's (vLLM/SGLang TP layout). After every actor update the fresh weights must move from the first into the second before the next rollout. verl handles this with a per-backend sharding manager that knows both layouts and performs the resharding — gathering/regrouping parameters and loading them into the running inference engine in place, without a checkpoint round-trip.

  • Colocated (HybridEngine): resharding is a same-GPU memory operation each step — all-gather the FSDP shard (or regroup the Megatron mesh) into the inference TP layout, hand it to vLLM/SGLang, free the training copy. Cheap, but it is the memory peak of the step.
  • Disaggregated / async: training and rollout pools are different GPUs, so resharding becomes a cross-pool weight transfer over NCCL on a cadence (trigger_parameter_sync_step). The rollout engine then runs slightly stale weights between syncs — which is exactly the policy-lag problem.
Async weight sync is what makes rollouts off-policy, and it is why disaggregated verl needs importance-sampling correction. The math of that lag and its fixes (TIS/GSPO, MILES-style elimination) is on Async RL — Policy Lag, IS Correction, and TIM; the cadence/staleness knobs and the cross-interconnect cost are on Placement.

8. Launching a Run — How the Pieces Assemble

A verl job is a Hydra-configured entrypoint. The driver builds the resource pools, constructs the WorkerGroups onto them, then calls fit():

# entrypoint: python -m verl.trainer.main_ppo --config-name ppo_trainer \
#     algorithm.adv_estimator=grpo \
#     actor_rollout_ref.model.path=Qwen/Qwen2.5-7B \
#     actor_rollout_ref.rollout.name=vllm \
#     actor_rollout_ref.actor.strategy=fsdp \
#     trainer.n_gpus_per_node=8 trainer.nnodes=1

# main_ppo.py (sketch)
ray.init()
role_worker_mapping = {
    Role.ActorRollout: ActorRolloutRefWorker,   # FSDP/Megatron + vLLM/SGLang
    Role.Critic:       CriticWorker,            # omitted when adv_estimator=grpo
    Role.RefPolicy:    ActorRolloutRefWorker,
    Role.RewardModel:  RewardModelWorker,       # or a rule-based reward fn
}
resource_pool_manager = ResourcePoolManager(resource_pool_spec, mapping)

trainer = RayPPOTrainer(config, role_worker_mapping, resource_pool_manager, ...)
trainer.init_workers()    # build the WorkerGroups on their pools
trainer.fit()             # the §4 loop

Everything you tune day-to-day is a Hydra override on this command: the algorithm (adv_estimator), the model, the two backends, the parallel degrees, the placement, and the optimization knobs. The architecture is what makes that flat config surface possible — each override flips an implementation behind a stable interface, and the fit() loop never notices.

The one-paragraph mental model

verl writes the RL algorithm as single-controller Python over whole batches of DataProto. Each call to a role's WorkerGroup is intercepted by an @register dispatch mode that scatters the batch to SPMD multi-controller workers and gathers the result. Roles run on ResourcePools of GPUs; the actor colocates training and generation in the HybridEngine, and a sharding manager moves fresh weights from the training layout into the inference layout each step. Backends (FSDP/Megatron, vLLM/SGLang) and algorithms (PPO/GRPO) swap underneath an unchanged control loop.
