Practical Agentic RL Training

One code-task experiment, from a dataset row to a defensible learning result: prepare the environment, establish a baseline, audit the trajectory, train small, and evaluate held out.

Evidence status — October 4, 2026: source-checked, not execution-validated.

The MiMo release, pinned launcher, runner, and verifier were inspected. No task container, GPU training job, checkpoint restore, or learning gain has been reproduced for this guide. Commands below are a proposed diagnostic configuration, not a tested quickstart or minimum-hardware claim. Run third-party code and images only after review and approval in an isolated training environment.

1. Define the experiment, not just the training command

The example is the code configuration of MiMo-V2.6-RL-oss: 2,698 task records, each describing a repository problem, an execution image, and a test-based verifier. It is not a corpus of successful demonstrations. The policy must produce fresh trajectories. The other four configurations use different environments or graders; they are not interchangeable inputs to this recipe.

Task row → dataset adapter → Uni-Agent session/gateway → mimoagent harness → task pod → test verdict → captured tokens + masks + logprobs + reward → VeRL policy update

Proposed first experiment: an approved local snapshot of the release's linked 9B distilled model, 32 training tasks, 64 development tasks, and 64 locked final-test tasks. Use two explicit harness profiles, fixed task-to-harness assignment, four training attempts per prompt, and a 20-update diagnostic run. These sizes are teaching choices, not Xiaomi's recipe or a promise of statistical power.

Success is better held-out task completion at the same harness and inference budget, with infrastructure reliability reported separately. A working launch, one nonzero reward, or overfitting 32 tasks is useful evidence, but none is that result.

Use a reviewed Linux training runtime compatible with this fork's Megatron/mbridge, SGLang, Ray, and TransferQueue paths. A generic current pip install verl is not a substitute. The launcher expects an existing Ray cluster and Kubernetes access for disposable task pods. Defaults are not a small experiment.

Read resolved_config.yaml, not whichever file you saw first. The one-node/eight-GPU profile below is an unmeasured topology proposal; memory fit depends on the checkpoint, accelerator, context budget, and runtime.

Gate: approved artifacts, declared resource limits, an accessible Ray/Kubernetes environment, and a complete identity manifest. Missing runtime compatibility or image approval blocks execution; do not work around it by disabling prechecks.

3. Turn task records into executable inputs

A sampled assignment asks the agent to make an action's secrets parameter optional while preserving token export. Its row contains the user prompt and a JSON string under extra_info.instance_json. The dataset adapter decodes that string at rollout time into tools_kwargs.instance. Preserve the JSON-string representation in Parquet rather than inventing a new nested schema.

Instance fieldsWhat to check
dataset_type, instance_idType is opensource-code; identity is stable and unique.
docker_image, cwdApproved, pullable image digest; absolute repository path inside that image.
problem_statementMatches the intended task in prompt; no hidden verifier material is sent to the model.
test_patch, test_command, verifier_timeout_secTests and runner are supplied at grading time; command/path/toolchain agree; timeout is positive.

Resolve image names before launching. Rows can contain bare names such as format-code-task-001457:latest, while the environment contract expects a fully qualified image. Use the release's image-mapping.jsonl to find the public tag, then a reviewed registry process to resolve or mirror it to an immutable digest. Do not assume the runner loads the mapping for you.

Split before looking at outcomes. Curate split_ids.json with train, dev, and test arrays. Group related repository/issue variants using provenance, not just random row indices. If that provenance is unavailable, describe the split as task-ID-held-out, not repository-held-out. The release lists only training splits; it does not supply an independent evaluation protocol. Keep final-test material out of policy-accessible mounts and all task-selection or tuning decisions.

Offline preparation example: preserve rows, resolve images, enforce disjoint selections

Run in a reviewed data-preparation environment with PyArrow already available, in a directory containing the pinned code.parquet, image-mapping.jsonl, your curated split_ids.json, and approved_image_digests.json. The last file maps public image tags to approved fully qualified registry/path@sha256:... references. This transforms data only; it does not execute task code or pull images.

import json
import re
from pathlib import Path

import pyarrow as pa
import pyarrow.parquet as pq

table = pq.read_table("code.parquet")
rows = table.to_pylist()
by_id = {row["extra_info"]["instance_id"]: row for row in rows}
if len(by_id) != len(rows):
    raise ValueError("Duplicate instance IDs in source data")

mapping_rows = [
    json.loads(line)
    for line in Path("image-mapping.jsonl").read_text().splitlines()
    if line.strip()
]
mapping = {r["dataset_image"]: r["dockerhub_image"] for r in mapping_rows}
if len(mapping) != len(mapping_rows):
    raise ValueError("Duplicate dataset image mappings")
approved = json.loads(Path("approved_image_digests.json").read_text())
splits = json.loads(Path("split_ids.json").read_text())
sizes = {"train": 32, "dev": 64, "test": 64}
if set(splits) != set(sizes):
    raise ValueError("Expected exactly train, dev, test selections")
if any(not isinstance(splits[k], list) or len(splits[k]) != n
       for k, n in sizes.items()):
    raise ValueError("Selection sizes do not match the declared experiment")
all_ids = [uid for name in sizes for uid in splits[name]]
if len(set(all_ids)) != len(all_ids) or not set(all_ids).issubset(by_id):
    raise ValueError("Selections overlap, contain duplicates, or name missing tasks")

required = {
    "dataset_type", "instance_id", "docker_image", "cwd",
    "problem_statement", "test_patch", "test_command", "verifier_timeout_sec",
}
prepared = {}
for name in sizes:
    selected = []
    for uid in splits[name]:
        row = by_id[uid]
        extra = dict(row["extra_info"])
        inst = json.loads(extra["instance_json"])
        if not required.issubset(inst) or any(not inst[k] for k in required):
            raise ValueError(f"{uid}: incomplete instance")
        if (inst["dataset_type"] != "opensource-code"
                or extra["dataset_type"] != "opensource-code"
                or inst["instance_id"] != uid
                or not inst["cwd"].startswith("/")
                or float(inst["verifier_timeout_sec"]) <= 0):
            raise ValueError(f"{uid}: invalid task contract")
        public_image = mapping[inst["docker_image"]]
        digest_image = approved[public_image]
        if not re.fullmatch(r"[^@\s]+/[^@\s]+@sha256:[0-9a-f]{64}", digest_image):
            raise ValueError(f"{uid}: expected an approved immutable image")
        inst["docker_image"] = digest_image
        extra["instance_json"] = json.dumps(inst, ensure_ascii=False)
        selected.append({**row, "extra_info": extra})
    prepared[name] = pa.Table.from_pylist(selected, schema=table.schema)
prepared["smoke"] = prepared["train"].slice(0, 1)
if any(Path(f"{name}.parquet").exists() for name in prepared):
    raise FileExistsError("Refusing to overwrite prepared experiment data")
for name, output in prepared.items():
    pq.write_table(output, f"{name}.parquet")

The identity checks do not prove semantic decontamination or image safety. Record hashes of inputs and outputs, retain the image-rewrite map, and audit the split provenance separately. Preserve evaluation row order: the fixed harness assignment below uses dataset indices.

Verify the verifier before optimizing against it

The code environment captures the base commit, resets the paths touched by the test patch, applies that patch, and runs the test command. A zero exit code yields reward 1; otherwise reward 0. Reset/apply failures carry an error category and must not be mistaken for an incorrect solution.

The tests arrive after the rollout, but agent and grader share a pod/filesystem. This is not an independently isolated verifier. Check image history and residue, credentials, network policy, test-runner integrity, and cleanup; the cheap history assertion is not a complete image audit. Keep the row's verifier payload inaccessible to the policy. See reward-integrity boundaries.

Gate: for a disposable training task, preserve evidence that the untouched/broken state fails and an independently reviewed correct change passes through the same grading path. The release does not supply that positive-control solution in these rows. Also verify that an image/setup or test-patch failure is classified separately from policy failure.

4. Freeze a supported harness and resource configuration

Pinned-source inconsistency: one harness is rejected.

Comments say a one-entry spec implements a single-harness run, but _mixed_harness_specs() rejects fewer than two entries. Use two genuine profiles here, mini-mimocode and mini-bash; do not disguise one profile under duplicate labels. A real single-harness experiment needs a separately reviewed upstream fix.

Copy those two pinned profiles into a shared experiment directory and create two-arm.yaml beside them:

harnesses:
  - label: mini-mimocode
    config: ./mini-mimocode.yaml
  - label: mini-bash
    config: ./mini-bash.yaml

For both copied profiles, set agent.step_limit: 30 and add max_tokens: 8192, timeout: 300, and max_retries: 0 under model.model_kwargs, keeping the existing temperature and other settings. These are proposed bounded-experiment limits, not the release's defaults. Customize and review the Kubernetes placement/resource settings. The wrapper only rewrites token/time limits for its default four-arm spec; a custom spec must carry its own limits.

Set MIXED_HARNESS_MODE=prompt with seed 0. The pinned runner chooses (seed + dataset_index) % number_of_harnesses, so each task keeps one harness within an unchanged data order. This is not a comparison of both harnesses on every task. Log actual selected_harness; aggregate and stratify results accordingly.

In the reviewed runtime, from the pinned VeRL repository root, set the following after replacing the shared paths. Both submodules must already be present at their pinned revisions. All commands in subsequent sections assume these exports in the same shell.

set -euo pipefail
export LAB_ROOT=/shared/agentic-lab
export MODEL_PATH=/shared/models/mimo-distill-9b-pinned
export TRAIN_DATA="$LAB_ROOT/data/train.parquet"
export VAL_DATA="$LAB_ROOT/data/dev.parquet"
export KUBECONFIG=/shared/credentials/task-cluster.yaml
export MIMOAGENT_HARNESS_SPEC="$LAB_ROOT/harness/two-arm.yaml"
export MIXED_HARNESS_MODE=prompt MIXED_HARNESS_SEED=0

export TRAIN_NNODES=1 TRAIN_NGPUS_PER_NODE=8 ROLLOUT_NNODES=0
export ACTOR_TP=8 ACTOR_PP=1 ACTOR_CP=1 ACTOR_EP=1 ROLLOUT_TP=2
export N=4 TRAIN_BATCH_SIZE=4 PPO_MINI_BATCH_SIZE=4
export MAXLEN=32768 PROMPT_LENGTH=8192 RESPONSE_LENGTH=24576
export PPO_MAX_TOKEN_LEN_PER_GPU=32768
export AGENT_NUM_WORKERS=2 GATEWAY_COUNT=1 MAX_CONCURRENT_SESSIONS=8
export ROLLOUT_MAX_RUNNING_REQUESTS=8 TRAJECTORY_TIMEOUT=1800
export FILTER_GROUPS_ENABLE=False
export VAL_N=1 VAL_DO_SAMPLE=False VAL_BATCH_SIZE=8
export TOTAL_STEPS=20 TOTAL_EPOCHS=100 SAVE_FREQ=5 TEST_FREQ=-1
export EXP_NAME=code-two-arm-diagnostic

ROLLOUT_NNODES=0 means colocated rollout, not zero rollout GPUs. This retains the pinned colocate_async trainer and its two-step stale-sample threshold; the resolved-config validator rejects switching this recipe to synchronous mode. The four-prompt batch represents 16 requested attempts, not 16 simultaneously live pods. Disabled group filtering makes saturated groups visible during diagnosis rather than repeatedly searching a tiny pool for mixed outcomes. It does not make their zero advantages informative.

PREFLIGHT_ONLY=1 RUN_DIR="$LAB_ROOT/runs/preflight" \
  bash scripts/code/train.sh
Gate: inspect resolved_config.yaml, provenance.json, and command.json. Confirm the topology, budgets, paths, harnesses, and output destinations. PREFLIGHT_ONLY runs cluster/import/config checks and writes artifacts; it is not an offline dry run, a task execution, or proof of memory fit. Do not set SKIP_CLUSTER_CHECK=1 to conceal a failed prerequisite.

5. Execute one episode, then measure the baseline

Use validation-only mode for the smoke task. It still initializes substantial trainer/runtime infrastructure; it is not a laptop inference shortcut. Use a fresh output directory for each run.

VAL_DATA="$LAB_ROOT/data/smoke.parquet" VAL_BATCH_SIZE=1 \
  MAX_CONCURRENT_SESSIONS=1 RUN_DIR="$LAB_ROOT/runs/smoke" \
  bash scripts/code/train.sh \
  trainer.val_before_train=True trainer.val_only=True

Both flags matter. In this revision, the val_only return is inside the val_before_train branch, while the launcher defaults the latter to false. Passing only trainer.val_only=True is not a safe no-training instruction.

Trace one task through pod creation, gateway calls, filesystem changes, agent termination, verifier execution, reward delivery, and cleanup. Keep the test output and completion/error classification. A completed agent process is not proof of task success; a timed-out process is not automatically an infrastructure failure.

RUN_DIR="$LAB_ROOT/runs/base-dev" \
  bash scripts/code/train.sh \
  trainer.val_before_train=True trainer.val_only=True

VAL_DATA="$LAB_ROOT/data/train.parquet" VAL_N=4 VAL_DO_SAMPLE=True \
  RUN_DIR="$LAB_ROOT/runs/base-train-diagnostic" \
  bash scripts/code/train.sh \
  trainer.val_before_train=True trainer.val_only=True

The first command establishes the fixed greedy, one-attempt development baseline. The second measures reward variation on training tasks using four sampled attempts. It is a diagnostic, not the same metric as the greedy baseline. Record all-pass, all-fail, mixed-outcome, invalid, and truncated groups. If no valid group varies, inspect task difficulty, the checker, token budgets, and sampling before launching optimization.

Gate: one complete episode plus negative/positive verifier controls, then baseline records keyed by task ID, harness, attempt and model revision. For this small preflight cohort, resolve or explicitly exclude with a recorded reason every unexplained infrastructure/verifier failure before interpreting learning curves.

6. Audit what the trainer will actually learn from

The runner calls environment.calculate_reward() and posts the result to the session's reward endpoint. The separate recipes/code/reward.py callback is a fallback that reads a supplied reward and otherwise defaults to zero; it does not execute the tests. A plausible scalar alone therefore proves very little.

AuditRequired evidence
Episode identityTask, session, harness, image digest, policy version and verifier result join unambiguously.
Token identityCaptured token IDs are the sampled IDs, not a newly tokenized text transcript; retain the tokenizer/chat-template identity.
Loss mask and probabilitiesEvery trained assistant token has the correct behavior logprob; prompt/tool observations are not policy targets. Audit schema-aligned lengths and non-finite values.
Branch selectionThe recipe selects trajectory_selection=longest. Inspect which chain survives, especially with subagents; do not assume every captured call is trained on.
Reward attachmentTrace the actual verifier verdict through the reward POST to the sampled training payload, including error metadata and terminal/truncation state.
Async reuseRecord generation/update versions and stale-sample decisions; server-mode async alone does not explain training staleness.

Keep human-readable messages under the runner's agent logs, but audit raw payloads at the gateway/TransferQueue-to-batch boundary. If the configured dumps do not expose these fields, capture an explicit debug batch before proceeding; rendered conversations cannot substitute for them. The payload contract, stitching guide, and token/mask walkthrough own the deeper explanations.

Gate: annotate at least one multi-turn sample and one mixed-reward prompt group through reward attachment, advantage construction, and the first update. Valid text plus nonzero reward is not enough if the trained token sequence or mask is wrong.

7. Run a bounded learning experiment

First run one update on the 32-task diagnostic pool, then start the independent 20-update experiment from the same base model. Keep these runs separate so a smoke checkpoint does not silently change the starting policy.

TOTAL_STEPS=1 SAVE_FREQ=1 RUN_DIR="$LAB_ROOT/runs/one-update" \
  bash scripts/code/train.sh

RUN_DIR="$LAB_ROOT/runs/fit" TEST_FREQ=5 \
  bash scripts/code/train.sh

Confirm an optimizer update, changed policy parameters, durable checkpoint files, and subsequent rollouts using the updated weights. Track accepted versus attempted groups, raw verifier success, error categories, truncation, token lengths, advantages, gradient norms, entropy, stale-sample drops, and valid completed episodes per wall-clock hour. Use the monitoring reference rather than inventing new universal thresholds.

The inspected configuration uses adv_estimator=grpo, norm_adv_by_std_in_grpo=False, loss_agg_mode=prompt-mean, and no enabled KL-loss or reward-KL term. This is not automatically the textbook z-scored GRPO example. A nonzero kl_loss_coef does nothing if the corresponding loss is disabled. Keep these choices in the manifest and do not change several at once. See loss aggregation for the distinctions.

Overfit before scaling. Improvement on the training pool is a debugging gate, not generalization. Twenty updates need not suffice. If valid, variable rewards fail to produce improvement, follow the reward-to-gradient path before spending more compute. If the tiny pool saturates, larger batches cannot recover missing reward variation.

Gate: preserved baseline, traceable updates/checkpoints, and training-pool learning under unchanged task/harness/budget conditions. Expand the task pool and reconsider dynamic filtering only after that gate; benchmark environment reliability before increasing pod concurrency or GPU scale.

8. Compare checkpoints without changing the experiment

Select a checkpoint using development results, not the final-test pool. The following uses the trainer's native checkpoint restore, avoiding an unverified Megatron-to-Hugging-Face export for the chosen model. Keep the original MODEL_PATH, training split/order, runtime, and topology; this is a full trusted-checkpoint restore, not merely loading arbitrary weight files.

export CANDIDATE_CKPT="$LAB_ROOT/runs/fit/checkpoints/global_step_20"
test -d "$CANDIDATE_CKPT/actor"

RUN_DIR="$LAB_ROOT/runs/candidate-dev" \
  bash scripts/code/train.sh \
  trainer.resume_mode=resume_path \
  trainer.resume_from_path="$CANDIDATE_CKPT" \
  trainer.val_before_train=True trainer.val_only=True

Replace global_step_20 with a checkpoint that actually exists and was selected by the declared development rule. The pinned trainer loads checkpoint state before validation, and the colocated trainer synchronizes weights after loading. Confirm the logged restored step and policy identity; do not mistake evaluation of the base model for evaluation of the candidate. Checkpoints can restore dataloader and TransferQueue state, so use a fresh run directory and only trusted artifacts.

Once the candidate and protocol are frozen, evaluate the base and candidate on the locked test.parquet using the same commands as their development evaluations with only VAL_DATA and the output directories changed. Do not train on or tune against these final results. Keep the same task order, harness assignment, model-facing prompts/tools, image digests, verifier, token/turn/time limits, and decoding settings.

ReportDefinition / interpretation
Task performanceSuccesses / valid graded attempts, plus successes / all scheduled attempts. Label greedy one-attempt success as such; do not silently substitute best-of-N.
ReliabilityInfrastructure/verifier-invalid attempts / all scheduled attempts, with categories and a fixed retry policy. Do not inflate accuracy by silently dropping failures.
Paired changeFor the same tasks, count fail→pass and pass→fail, stratified by actual harness. Report uncertainty; 64 tasks are a small study.
Cost and behaviorTokens, tool calls, elapsed time, truncation and resource use under the same budgets. Higher reward obtained solely by extra inference compute is a different result.
ProvenanceBase/candidate identity, selected step, protocol hashes, split provenance, runtime/hardware, and raw per-attempt records.

For stochastic repeats, summarize uncertainty at the task level, not by pretending all attempts on one task are independent tasks. Include per-harness results: fixed assignment controls the base/candidate comparison but does not estimate a head-to-head harness effect.

Gate: only claim a learning gain when held-out performance improves under the frozen protocol, with reliability, cost and uncertainty visible. Otherwise report the narrower result: environment works, one update works, or training tasks overfit.

9. Diagnose the first broken boundary

SymptomFirst check / action
ImagePullBackOff or setup errorsBare image name, digest mapping, registry credentials, shared paths and pod quota. Not evidence of weak coding ability.
Every reward is zeroSeparate genuine failed tests from patch/reset errors and missing reward delivery; the fallback callback can return zero without running a verifier.
One-arm spec fails before rolloutThe pinned runner requires at least two entries. Use the documented two-arm path or a reviewed fix, not a fake duplicate arm.
Validation unexpectedly begins trainingInspect both val_before_train and val_only in the resolved config.
Sampling runs but no useful updatesAll-pass/all-fail groups, dynamic-filter acceptance, dropped stale work and reward variance. More GPUs do not create a missing signal.
Reward rises but held-out results do notTask memorization, changed harness/budget, grader exploitation, training/eval leakage, or checkpoint identity. Do not call training reward a benchmark gain.
OOM, timeouts or long-tail stallsModel/context/KV fit, active sessions, tool output size, verifier latency and Kubernetes limits. Reduce one concurrency/budget control at a time and re-baseline after behavioral changes.

A complete experiment bundle contains the pinned inputs and resolved configuration, split/image manifests, baseline records, annotated trajectory and verifier controls, update/checkpoint evidence, and a paired held-out report. Review/redact logs and provenance before sharing: they can contain commands, local paths, credentials, or unrelated checkout files. The companion pages remain the references; this guide owns the sequence and its evidence gates.

Sources and evidence boundary

  • Dataset card and image mapping: released task configurations and external image references.
  • MiMo recipe README: five reproduction arms, linked model, and distinct mimoagent/uni-agent responsibilities.
  • Wrapper, launcher, and base YAML: layered defaults, output artifacts, and the proposed overrides.
  • Resolved-config validator: enforced colocated-async mode and configuration checks.
  • mimocode profile, bash profile, and session runner: actual profile selection, task lifecycle and reward delivery.
  • Fallback reward hook and code verifier: metadata fallback versus actual execution-based grading.
  • V1 trainer and colocated-async lifecycle: restore, validation-only control flow, and weight synchronization.

These sources establish interfaces and configuration behavior, not a reproduced model-quality result. This public task bundle is not evidence that the complete frontier-training corpus or every production-system component has been released.
