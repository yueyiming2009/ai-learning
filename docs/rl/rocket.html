Rocket — MAI's Asynchronous RL Framework

A controller and two kinds of workers connect YOLO learning to SGLang generation. The challenge is not merely overlapping work: it is keeping group rewards, policy versions, sampling distributions, weight layouts, and a failure-prone inference fleet consistent.

In-house system, not an open-source installation guide. The MAI-Thinking-1 report, §3.6 describes Rocket, but the public sources checked on November 1, 2026 do not establish a released Rocket repository, license, or supported package. SGLang and Ray being public does not make Rocket public. Compare its design with the framework landscape; keep the model's specialist climbs and consolidation on MAI-Thinking-1, and the learner's kernels and sharding on YOLO.

1 · Separate the algorithm controller from the GPU engines

Rocket is Microsoft AI's orchestration framework for large-scale distributed RL. The report motivates building it around MAI's need for asynchronous runs across several thousand GPUs. That is the team's account of its requirements and implementation choice, not a controlled demonstration that current public frameworks cannot reach that scale.

1. ControllerSample tasks, dispatch work, filter completed groups, and assemble learner batches.
2. Problem workersOwn groups of responses, pass-rate selection, group grading when needed, and normalized advantages.
3. Rollout workersOwn individual episodes: prompt, generation, tool calls, observations, stopping, and optional grading.
4. SGLang + routerServe model generations; route traffic, reuse prefixes where useful, and isolate unhealthy replicas.
5. YOLO learnerConsume filtered training batches and update the policy with the reported GRPO-derived objective.
6. Weight publicationReshard and transform learner weights for inference; repeat while other work is in flight.

The request path is controller → problem worker → rollout worker → serving pool; results return to the problem worker, then the controller sends accepted batches to the learner. The controller and each problem/rollout worker are Python processes / Ray actors. The GPU learner and inference pools have their own distributed execution. Figure 19 also includes checkpointing, metrics, persistent rollout storage, and curriculum feedback; it does not specify their complete storage schemas or a prioritized-replay algorithm.

Controller implementations can switch between on-policy and off-policy RL. MAI reports using off-policy execution for large jobs and reserving on-policy mode for smaller experiments and debugging. These are execution choices, not different model architectures.

Sources: §§3.6.1–3.6.3, Figure 19; Appendix L.3 separates Kubernetes/Kueue admission from Ray's in-job runtime.

2 · Follow one task, not just one generated sequence

  1. Probe a problem. The problem worker asks rollout workers for an early group, retries worker failures, and aggregates graded outcomes into a task pass rate. The reported recipe uses 16 early responses and an acceptable interval of 0.05–0.8.
  2. Spend more only on accepted problems. Generate the full group and apply a second pass-rate filter, reported as 0.1–0.8. Nearly uniform success or failure gives little group-relative reward signal; filtering also changes which problems reach the learner.
  3. Build each episode. A rollout worker sends a prompt to inference, parses the response, executes tools, appends observations, and repeats until a final answer or a step/time limit. It is not necessarily a single HTTP generation request.
  4. Grade at the right scope. Independent answers can be graded on the rollout worker; pairwise or group-dependent judgments belong on the problem worker. A user-defined aggregation policy combines multiple grades into an overall reward.
  5. Normalize and train. The problem worker computes response-level advantages (with task-specific penalties/heuristics); the controller filters the returned results and forms batches for YOLO.
A disclosed counting ambiguity: §3.1.5 specifies 128 total rollouts with 16 early rollouts, while §3.6.2 describes an additional 128 after the early 16. The report does not reconcile these descriptions. Do not silently turn either 128 or 144 into a universal Rocket group-size invariant.

The reported objective uses \(A_i=(R_i-\mathrm{mean}(R_{1:G}))/\mathrm{std}(R_{1:G})\), shared across response \(i\)'s tokens. Loss normalization is over tokens in the global batch, not an equal average of per-response means. Its stability modifications include an entropy-controlled upper clip bound and a separate outer ratio clip. These belong to GRPO and the adaptive-clipping derivation, not to Ray scheduling.

Sources: §3.1.1, §3.1.3, §3.1.5, §§3.6.2–3.6.3.

3 · Bounded lag is still off-policy

The recipe publishes learner weights to inference every five gradient steps and discards a rollout if its generating policy is more than eight inference updates stale. The report translates eight publication intervals to 40 gradient steps. A serving-policy version, a gradient step, and elapsed seconds are different units.

For a simple illustration, assume the rollout uses version zero, published at learner step zero; publication is instantaneous and occurs every \(k\) steps. After \(s\) learner steps:

\[ a(s)=\left\lfloor \frac{s}{k}\right\rfloor,\qquad \mathrm{admit}(s) \iff a(s)\leq A_{\max}. \]

This models a publication-version gate, not Rocket's undisclosed implementation. At publication boundaries with \(k=5\), age eight is reached at step 40; age nine first occurs at step 45. Passing that gate does not imply equality with the current learner policy.

Version age (dot = selected step) Inclusive admission limit

At step 40: version age 8; passes the age gate. First rejected step: 45.

A version limit is not a wall-clock deadline. Change publication cadence without changing the allowed age: the same version budget spans a different number of learner steps. This is a synthetic single-version rollout, with no transfer delay, queue delay, or in-flight weight change; it is not measured Rocket throughput or a reconstruction of its token-level version bookkeeping.

Longer generations increase latency without increasing learner step time proportionally. Hard, long-running problems therefore tend to become more off-policy and risk rejection. MAI reports lowering the learning rate from \(10^{-6}\) to \(9\times10^{-7}\) at higher lengths for stability. This changes policy movement; it does not make an old sample fresh. See lag distributions and async diagnostics.

Source: §3.1.5. Exact mixed-version episode accounting, partial-rollout policy, and queue eviction details are not supplied by that paragraph.

4 · Three mismatches require three different controls

Do not collapse freshness, numerical alignment, and sampling support into one “on-policy” switch.
MismatchReported controlWhat it does not establish
Policy changed over timeBound rollout age; train with a GRPO-derived token ratio against the generating policy.Bounded off-policy data is not current-policy data.
Different execution numerics or MoE routesBF16 on both YOLO and SGLang, plus MoE routing replay.Shared dtype and replay do not prove bitwise equality across kernels, schedules, and parallelism.
Different sampling supportSave and replay the rollout's top-p mask before the learner softmax; the reported nucleus value is 0.97.Matching token IDs or replaying expert routes alone does not reproduce the truncated action distribution.

If \(M_t\) is the recorded nucleus at token \(t\), replay changes the learner distribution to

\[ \widetilde{\pi}_{\theta}(v\mid h_t,M_t) =\frac{\mathbf{1}[v\in M_t]\exp z_\theta(v\mid h_t)} {\sum_{u\in M_t}\exp z_\theta(u\mid h_t)}. \]

The mask is the one recorded during generation, not a newly selected nucleus under the updated learner. Replay also changes the softmax denominator and gradients for retained tokens. The report finds unmasked training can diverge rapidly; carrying the masks has storage and transfer overhead. MoE routing replay instead concerns internal expert choices, not the vocabulary mask.

Public SGLang RL documentation explains deterministic inference and notes that matching deterministic learner kernels is also needed for true training/inference alignment. That is useful context, not evidence that Rocket uses Miles' true-on-policy implementation. The MAI report establishes its own BF16/replay recipe.

Sources: §3.1.3, §3.6.4. Background: numerical TIM versus token/sampling fidelity.

5 · The rollout workload determines the serving optimization

The largest reported RL job uses 4,864 GB300 chips: 4,096 for inference and 768 for learning. That split is about 84% inference, or 5.33 inference chips per learner chip. It describes one allocation, not a recommended ratio or a framework speedup.

WorkloadPressureReported choice
Single-turn reasoningShort prompts, generations up to 128k; KV-cache capacity dominates.Reduce weight/KV footprint using expert parallelism and DP attention. Disable prefix caching so sliding-window tokens can be evicted during long generations.
Multi-turn tools / codingGrowing prompts and relatively short generations; repeated prefill dominates.Lean on prefix reuse; reported prefix-cache hit rates reach 97–98% in production RL runs.

MAI also describes communication optimizations using DeepEP and expert load balancing. The cache result is workload-specific: it does not imply a 97–98% throughput improvement, or that caching remains valid across arbitrary weight updates.

The public SGLang Model Gateway guide explains cache-aware routing, worker health, and flow control. Its current feature set is broader than the report's deployment description. A capability in today's upstream gateway is not automatically a capability of MAI's pinned production version.

Source: §3.6.4, pp. 51–52. Related: RL inference and KV-cache mechanics.

6 · Weight publication is a compiled redistribution problem

A learner rank and an inference rank need not own the same part of a parameter. Different FSDP, pipeline, attention-DP, layout, or precision choices make a whole-model broadcast an inadequate description of the handoff.

  1. Intersect layouts once. At job start, the planner intersects source and destination shards. Every nonempty overlap produces a transfer entry with source rank, destination rank, byte extent, and required casts or layout permutations.
  2. Move only needed slices. Resharding follows from those overlaps, without first materializing full tensors. Transformations run on the cheaper side; packing, transfer, and unpacking are pipelined across sub-shards.
  3. Expand across live replicas. The logical plan targets one learner and one inference server. Runtime transfer groups expand destination ranks to live replicas, allowing replacement or membership changes without rebuilding that logical plan.
  4. Exploit DP replication. A subset of learner DP groups can each serve a separate slice of inference replicas. The report illustrates 36 inference servers split into four independent nine-server transfers, limiting both fan-out and failure scope.

Transfer latency creates serving idleness and policy lag; it is not merely checkpoint I/O. The report discusses possible dtype/layout transformations, but separately says the reported RL learner and inference computations use BF16. Do not infer an FP8 RL recipe from general transfer-planner flexibility or YOLO's pre-training kernels.

Upstream mechanism versus Rocket implementation: SGLang's public guide documents disk, tensor, and distributed weight updates, with explicit pause/refit/resume coordination. This explains the serving-side problem. The MAI report does not identify a public Rocket API, exact SGLang endpoint sequence, or transport protocol for its custom plan; do not label it NCCL, RDMA, or a particular checkpoint-engine integration without evidence.

Source: §3.6.5, pp. 52–53. Compare verl resharding and verl's checkpoint engine.

7 · “Alive” is weaker than “making progress”

At thousands of inference chips, failures are normal pool behavior. Rocket's reported defenses operate at different scopes:

ScopeDetection / actionFailure contained
ReplicaSelf-watchdog probes generation and scheduler memory; unhealthy servers restart gracefully.Hung or unhealthy serving process.
RouterPer-backend circuit breaking, staged recovery probes, rediscovery, and per-replica flow control.Failed replicas or slow backends spreading backlog across the pool.
Task / rolloutProblem workers retry failed rollout work; failed inference requests can be retried on another replica.One worker or server failure aborting otherwise usable task work.
JobActor-class liveness thresholds trigger clean restarts; a separate step-progress watchdog detects stalls.A job that lacks sufficient healthy capacity, or looks alive but no longer advances.

Retries preserve useful work, but the report does not establish exactly-once rollout delivery, tool side-effect deduplication, or a transactional snapshot across every async component. Those are additional contracts, especially for stateful tools; do not infer them from fault tolerance alone.

Sources: §3.6.2, §3.6.4, Appendix L.3. Upstream context: SGLang gateway reliability.
