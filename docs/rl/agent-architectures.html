Agent Architectures — Deep Agents and the Alternatives

Build the idea from first principles: one model proposes an action, a runtime executes it, the environment returns an observation, and the cycle continues. Agent architectures arise by changing who controls that cycle, where its state lives, and how several cycles compose.

Modern agents are feedback systems made from three very different components: a model that proposes what to do, a runtime that controls execution, and an environment that supplies real consequences. This page builds that system one mechanism at a time, then shows how planning, delegation, reflection, search, and Deep Agents emerge by composing the mechanisms.

An agent architecture is the design of a stateful feedback loop.
To understand one, trace who chooses each transition, what state the next model call can see, how actions become observations, and which guarantees are enforced outside the model.

1. The Smallest Useful Agent

An LLM call is not yet an agent. A call maps an input context to output tokens. An agent closes a loop around that call: some outputs are interpreted as actions, those actions change an environment, and the resulting observations become input to the next call.

1 · Observe The runtime builds the model context from the request, current state, and prior tool results.
↓
2 · Propose The model emits either a candidate action—such as a tool call—or a final response.
↓
3 · Validate and execute Trusted code checks syntax, permissions, budgets, and approvals before invoking the tool.
↓
4 · Transition The environment changes and returns an observation: output, an error, a file diff, or a test result.
↺ append the observation, then repeat

The separation between proposal and execution is fundamental. A model can write “delete the file,” but only the runtime can actually delete it. Likewise, the model can claim that a test passes, but only an executed test produces that observation. The model is a policy over possible next actions; the runtime and environment determine what really happened.

A concrete two-turn trace

Suppose the task is “find why the parser test fails and fix it.” One short trajectory might be:

Observation 0

The request, repository instructions, visible files, and available tools are placed in the initial context.

Action 0

The model proposes running the failing test. The runtime validates the command and executes it in the repository sandbox.

Observation 1

The real stack trace is appended. It points to an empty-token edge case in parse(); this evidence changes the next decision.

Action 1

The model reads the relevant code, proposes a patch, and asks the runtime to rerun the focused test.

Termination

A passing test is observed, broader checks run, and the model returns a summary. A hard step or time limit could also terminate the loop.

ReAct is one way to train or prompt the model’s inner policy for this cycle: reason from the current observation, choose an action, receive the result, and continue. The architecture is everything that specifies how the cycle is hosted and composed: what state is visible, who may choose transitions, which actions exist, and when another loop is created.

First understand one loop; then understand architectures as transformations of it.
Planning adds explicit task state. Delegation forks another loop. Reflection adds an evaluator loop. Search copies state into branches. A workflow moves some transition choices into code.

2. State, Context, Control, and Trust

Long-horizon agents rarely fail because they cannot emit another token. They fail because the right fact is no longer visible, stale state is mistaken for current state, two workers overwrite each other, or the model is allowed to judge a claim that only the environment can verify. Architecture starts by keeping several kinds of state distinct.

Task state

The goal, constraints, completed work, unresolved questions, and termination condition. A plan is one representation of task state.

Model context

The tokens visible on this inference call: instructions, selected history, tool schemas, retrieved text, and recent observations.

Working state

Files, scratch artifacts, structured records, and checkpoints that survive context compaction and can be inspected again exactly.

Durable memory

Facts or procedures intentionally carried across runs. This is different from a long transcript and different again from model weights.

Environment state

The world outside the prompt: repository contents, browser state, databases, deployed services, and the actual effects of tool calls.

Runtime state

Budgets, permissions, active worker identities, pending approvals, retry counts, locks, checkpoints, and audit records.

Context is a view of state, not the state itself

Before every model call, the runtime constructs a context view. It may select recent messages, retrieve a relevant file, summarize older turns, hide secrets, or include only the portion of a task assigned to a worker. This operation is part of the architecture. If a summary replaces details, the exact details must still live somewhere if later steps may need them.

  • Select: choose which state is relevant to this decision.
  • Transform: summarize or normalize large observations while retaining a path back to exact evidence.
  • Isolate: give a worker the minimum useful context instead of copying the manager’s entire transcript.
  • Persist: checkpoint state that must survive interruption, retry, or a fresh context window.

How context compaction actually works

Compaction is a runtime operation that replaces an old part of the active conversation with a smaller checkpoint. It does not squeeze the original tokens into a denser hidden memory, and it does not update the model’s weights. The complete transcript and artifacts can remain in external storage; only the context supplied to the next model call becomes smaller.

Canonical run state Full messages, exact tool outputs, files, checkpoints, and audit records remain externally available.
↓ select an old prefix
Compaction pass Extract goals, constraints, decisions, evidence pointers, completed work, open questions, and the next step.
↓ rebuild the model view
Next active context Stable instructions + compact checkpoint + recent turns + retrieved artifacts relevant to the next decision.

A typical harness compacts before a request would exceed its input budget—or earlier, when a long noisy history begins to hurt quality. It chooses a cut point, preserves protected content such as system instructions and tool schemas, summarizes the older prefix into structured task state, keeps a recent suffix verbatim, and constructs a fresh prompt from those pieces.

Before

The live context contains the migration request, twelve documentation reads, twenty file inspections, three edits, verbose test output, and five recent turns.

Checkpoint

The compactor records the unchanged requirements, verified API rules, files modified, passing checks, one unresolved test, and pointers to /work/api-notes.md and the current diff.

After

The next model sees that checkpoint plus the five recent turns. The raw documentation pages and old test logs are absent from the prompt but still retrievable from external state.

Retrieve

If an omitted signature matters later, the agent follows the artifact pointer and loads the exact source instead of trusting a lossy recollection.

The compact checkpoint should preserve provenance and uncertainty. “The tests pass” is unsafe if only one focused test ran; “focused parser test passed; full suite not yet run” preserves the distinction. Repeatedly summarizing a summary without retaining raw evidence causes drift: caveats disappear, tentative beliefs become facts, and old constraints are silently rewritten.

The post-compaction prompt is a new context segment, not an append-only extension of the old prompt. The old KV cache cannot simply continue across that rewrite. During RL, the pre- and post-compaction calls must likewise remain separate training chains; concatenating them would train on a token history the policy never observed. See verl Agentic Training for that reconstruction problem.

Control answers “who chooses the next transition?”

In a model-controlled loop, the model chooses among tools and decides when to stop. In a code-controlled workflow, application logic selects the next node and the model only fills in bounded decisions. Most useful systems are hybrid: code enforces gates and invariants, while the model handles decisions whose branches cannot be enumerated in advance.

A good trust boundary follows evidence. Let the model propose a command, a patch, or a verdict; let trusted code enforce permissions, execute actions, record effects, and apply hard limits. “The model believes it succeeded” and “the environment produced evidence of success” are different system states.

Delegation requires a protocol, not merely another role prompt

A real delegation operation has four parts: a bounded subtask, an initial context view, a capability set, and a return contract. The child loop should know what artifact or answer to produce and when to stop. The parent needs a deliberate join operation that validates and integrates the result. Without those pieces, “multi-agent” often means several models chatting in one increasingly noisy transcript.

3. Core Patterns, Derived from the Loop

The common architecture names become easier to understand when each is expressed as a small change to the basic cycle. They are composable mechanisms, not mutually exclusive products.

Single-loop agent: improve observation and action before adding topology

The base architecture keeps one controller and one evolving context. Retrieval makes relevant state visible; summarization controls context growth; better tools expose safer, more meaningful actions; tests and structured outputs improve feedback. Many apparent “reasoning” failures are actually missing observations or a poorly designed action space.

Invariant: each action result returns to the same loop, and one loop owns the final answer. This preserves causal clarity: it is easy to tell which observation led to which next action.

Plan → execute → replan: make task state explicit

A planner turns the goal into an ordered or dependency-aware plan. The executor performs one step against the real environment. A replanner then consumes both the old plan and the new observation to mark work complete, revise later steps, or stop.

  1. Create plan state with explicit completion criteria.
  2. Select one ready step; do not treat the whole initial plan as ground truth.
  3. Execute it and attach evidence to the step.
  4. Update the remaining plan from what actually happened.

A plan that is written once and never consulted is decoration. The architectural change is not “the model made a list”; it is that later transitions read and mutate the same task state.

Code-owned workflow or graph: move transitions outside the model

Here the application defines nodes, edges, branch conditions, joins, and loops. A model can still act inside a node—for example, extracting fields from an invoice—but code decides that a high-value invoice must next pass through approval. The graph gives deterministic structure around locally probabilistic decisions.

Invariant: graph state has a schema, and every node has a defined input, output, and transition rule. Retries must distinguish an idempotent read from a side effect that cannot safely be repeated.

Supervisor → workers: fork context, then join results

A supervisor decomposes the task and creates child loops. Each worker receives a focused prompt, selected evidence, and only the tools it needs. Its intermediate trajectory stays local; the parent receives a result or artifact through an explicit return channel.

The important operations are fork and join. Forking decides which state is copied, referenced, or hidden. Joining decides how conflicts are resolved, how claims are checked, and who remains accountable for the final output. Parallel execution is an optional scheduling choice, not the definition of delegation.

Peer handoff: transfer ownership of the active loop

A handoff does not create a manager above the specialists. The current agent selects a new specialist, constructs handoff context, and transfers responsibility for the next turn. The system must record who currently owns the conversation and define terminal conditions; otherwise specialists can bounce control back and forth without advancing task state.

Reflection or critic loop: add an evaluation signal

A generator creates an attempt. An evaluator inspects the attempt against a rubric or external evidence and returns defects. The generator revises from that feedback. A coded acceptance rule, iteration limit, or budget terminates the cycle.

The evaluator only adds information when it has a stronger signal than the generator had: executable tests, a reference answer, a formal constraint, a different context, or a genuinely independent review. Asking the same model to “check again” with no new evidence can amplify confidence without improving correctness.

Tree search: copy state and explore competing continuations

Search turns one trajectory into a tree. A node is a snapshot of task and environment state; an edge is a candidate action or reasoning continuation. The search controller expands several children, scores them, selects promising branches, and may backtrack. Tree of Thoughts and LATS differ in how they generate, evaluate, and revisit nodes, but both need three things a normal loop does not: state copying, a value signal, and a branch-selection policy.

This is deeper than running several workers. Workers normally solve complementary subtasks and combine their results; search branches compete as alternative continuations of the same state.

Environment-native agent: redesign what the loop can see and do

Some of the largest gains come without another model role. A coding agent becomes far more capable when its environment offers repository search, bounded file views, syntax-aware edits, shell execution, tests, diffs, and a sandbox. The environment defines the observation and action spaces on which the policy operates; architecture is partly interface design.

Every added loop must own state, receive evidence, and have a stopping rule.
If a planner, worker, critic, or search branch has no distinct state transition or information source, it is probably adding ceremony rather than capability.

4. Deep Agents — Assembling the Primitives

A Deep Agent is easiest to understand now as a composition, not a new inner reasoning algorithm. Start with a normal model/tool loop. Give it an external workspace so exact artifacts need not remain in the prompt. Add a context policy that decides what to load and summarize. Let it fork bounded subagent loops. Place the whole system inside a durable runtime that owns execution, permissions, checkpoints, and approvals.

LangChain’s original Deep Agents article emphasized a detailed system prompt, explicit planning, subagents, and a filesystem. The concrete deepagents library has evolved into a configurable implementation around LangChain’s agent loop and the LangGraph runtime. Context compaction, storage backends, skills, memory, human approval, and task-list planning are separable capabilities; the category should not be defined by one fixed middleware checklist.

Trusted runtime and environment Execute tools, enforce permissions and budgets, checkpoint, pause, resume, and audit.
↑ supplies real observations
Context and storage layer Select prompt context, compact history, route files, load skills, and preserve exact artifacts.
↑ constructs each model view
Manager loop Choose tools, maintain task state, optionally plan, delegate bounded work, and integrate results.
↕ forks tasks and joins results
Subagent loops Run with focused context, capabilities, return contracts, and normally isolated trajectories.
↕ read and write
External working state Plans, source notes, patches, test output, status records, and durable memory.

A worked execution, with the state changes exposed

Suppose the task is “upgrade a repository to a new payments API, preserve behavior, and explain the migration.” Watch how context is forked and results are joined:

Initialize

The runtime opens a checkpointed thread. The manager records success criteria and unresolved questions in task state, then writes exact constraints to /work/constraints.md.

Fork research

The manager creates a worker with the API-version question, documentation tools, and a return contract. The worker does not receive unrelated repository history.

Return evidence

The research worker stores exact signatures and migration rules in /work/api-notes.md, then returns a compact summary plus pointers to its evidence.

Fork code

A code worker receives the scoped change, relevant files, and the research artifact. It edits call sites and reports changed files and uncertainties, not its entire transcript.

Verify

The runtime executes tests in the sandbox. Failures become new observations and update task state; the producing worker does not get to self-certify success.

Join

The manager reconciles the patch, evidence, and test results. It delegates follow-up work if a criterion remains open, otherwise it produces the final patch and explanation.

The architecture extends the effective horizon in three ways. External artifacts survive when the live transcript is compacted. Isolated workers spend their context on one bounded problem. Checkpoints let execution pause and resume without asking the model to reconstruct the world from memory. None of these capabilities comes merely from a longer prompt.

How the pieces relate

ReAct-like loop

The local policy primitive: observe, propose an action, receive the real result, and continue until a stopping condition.

⊂

Deep-agent harness

The composition layer: manage context and working state, fork subagent loops, join their results, and run everything inside trusted infrastructure.

A Deep Agent is therefore usually hierarchical delegation plus external working state and a durable runtime. It is not automatically tree search: workers normally solve complementary subtasks rather than compete as scored continuations. It is not automatically parallel either; concurrency is a runtime scheduling decision.

5. The Moving Boundary — When the Model Absorbs the Harness

“The model swallows the harness” contains two claims that should be separated. The first is already plausible: training internalizes behavioral scaffolding, so the model needs fewer prompt rules to choose tools, decompose tasks, recover from errors, or decide what context matters. The stronger claim is that persistent state, permissions, execution, and governance become properties of the model itself. That does not follow.

Thick harness

Prompts and code prescribe planning, routing, retries, compaction, critique, and delegation around a relatively generic model.

Co-designed system

The model has learned agentic behavior; the runtime supplies state, tools, policies, and checkpoints while intervening less often.

Thin trusted kernel

The model chooses most cognitive actions, but external infrastructure still validates, executes, persists, limits, observes, and rolls back them.

Four kinds of “memory” that should not be collapsed

StateWhere it livesWhat it means
Parametric behavior Model weights General learned tendencies: tool syntax, decomposition habits, recovery strategies.
In-run state Prompt, tool results, KV cache The current episode’s working context; normally gone unless the runtime retains it.
Provider continuation Conversation or response service External service state supplied to later inference calls, not a weight update.
Application state Files, databases, checkpoints, stores Durable, auditable facts, artifacts, identities, budgets, and execution history.

The model can increasingly own

  • task decomposition and replanning;
  • tool and specialist selection;
  • context triage and summarization proposals;
  • error recovery and escalation decisions;
  • critique, revision, and uncertainty reporting.

The trusted runtime must still own

  • tool execution, authentication, and authorization;
  • durable storage, deletion, checkpoints, and replay;
  • sandboxes, network policy, secrets, and tenant isolation;
  • hard budgets, timeouts, rate limits, and termination;
  • independent verification, audit logs, deployment, and rollback.
The model may swallow the behavioral harness, but it cannot safely swallow the trust boundary.
The likely end state is not “no harness.” It is a thinner harness that looks less like a prompt author and more like an operating system kernel for state, capabilities, policy, and evidence.

This reframes Deep Agents too. Today’s explicit task lists, delegation prompts, context files, and retry policies can generate the trajectories from which a future model learns those behaviors. Some scaffolding may disappear into the policy. Files, permissions, sandboxes, independent verifiers, and durable execution remain external because they are facts and guarantees about the world—not merely better next-token predictions.

6. Architecture Becomes Part of the Policy’s Training Distribution

Changing the architecture changes what the model observes and therefore what policy is being trained. A single ReAct loop produces one mostly linear trajectory. A deep-agent harness may compact context, fork subagent prompts, merge summaries, and turn one task reward into several trainable model-call sequences. A deterministic graph inserts code-authored state between model calls. Tree search samples many branches but deploys only a selected path.

Architecture featureTraining consequence
Context compaction or file offload The post-compaction prompt may no longer extend the earlier token prefix; the compacted text is environment-produced context, not sampled policy output.
Subagent delegation One episode becomes several model-call histories with one shared terminal outcome and a harder credit-assignment problem.
Code-owned graph transitions Transitions are easier to replay and audit, but the policy only learns decisions exposed at agentic nodes.
Reflection or critic calls The learner must distinguish policy-generated tokens from evaluator feedback and decide which sequence receives the reward.
Tree-search selection Generated-but-rejected branches contain behavior data too; training only on the winner introduces a selection mechanism that must be understood.

The Harnessed Agentic RL page covers the systems consequence: if the production harness owns the graph, the trainer must recover faithful tokens, masks, behavior log-probabilities, and causal structure from the model calls it observes. The Production Learning Loop covers the longer-term consequence: real harness behavior can become training data, but new policies still need independent evaluation, promotion gates, and rollback.

Summary

Loop vs. architecture

ReAct is an inner control loop. Architecture places that loop inside a topology of planning, state, delegation, search, and execution.

Deep Agents

An opinionated harness around a normal model/tool loop: external context, subagents, memory, runtime services, and optional explicit planning.

Patterns transform the loop

Plans add task state, workers fork context, critics add evidence, search copies branches, and graphs move transitions into code.

Environment first

Tool feedback, safe execution, and a good computer interface often matter more than adding another model role.

Future boundary

Models can internalize planning and routing behavior; trusted infrastructure must still own authority, persistence, limits, evidence, and rollback.

Train what you ship

Compaction, delegation, graphs, and selection alter the policy’s observations. The deployed harness is part of the training distribution.
