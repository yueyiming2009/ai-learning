Agent Architectures — Deep Agents and the Alternatives

ReAct explains what happens inside one reason–act–observe turn. Architecture decides who plans, who controls the next step, where context lives, when work is delegated, whether alternatives branch, and which guarantees remain outside the model.

An agent framework name is not an architecture. The same framework can run one tool-using model, a deterministic graph, a manager with workers, a handoff network, or a search tree. Conversely, the same architecture can be implemented in several frameworks. The useful question is not “which agent library won?” but where control, state, context, and trust live.

Deep Agents are one important composite architecture, not the parent category.
They bundle a normal model/tool loop with external context management, delegation, memory, and runtime services. Those pieces can be removed, replaced, or combined with other patterns.

1. From an Agent Loop to an Agent Architecture

The ReAct loop answers a local question: after observing the current state, how does the model reason, choose an action, and incorporate the result? An architecture answers the system-level questions around that loop.

Control policy

Does the model choose the next step, does application code choose it, or does a deterministic outer workflow contain agentic nodes?

Execution topology

One loop, planner–executor, supervisor–worker, peer handoff, or an explicit search tree over several candidate trajectories.

Context topology

One shared transcript, filtered handoff context, isolated worker contexts, or external working memory in files and stores.

Improvement mechanism

Continue from tool feedback, replan, ask a critic to revise, or generate and score multiple alternatives.

State and durability

Ephemeral prompt state, checkpointed thread state, cross-session memory, or a durable workflow that can pause and resume.

Environment boundary

What tools exist, where they execute, which side effects are allowed, and which sandbox, approval, and audit controls are enforced.

These axes compose. A code-authored graph can invoke a Deep Agent node; a supervisor can delegate to workers that each run ReAct; a reflection loop can wrap plan-and-execute; and a tree search can branch entire tool-using trajectories.

2. Deep Agents — The Composite Case

LangChain’s original Deep Agents article described an ordinary LLM/tool loop augmented with four pieces: a detailed system prompt, an explicit planning tool, subagents, and a filesystem used for both work products and context management. That is a useful description of the generic deep-agent pattern. The concrete deepagents library is an evolving implementation of that pattern, not the definition of the category.

As of September 2026, create_deep_agent() builds on LangChain’s normal agent loop and the LangGraph runtime. It assembles middleware, storage backends, context compaction, subagents, skills, optional memory, and optional human approval around the model/tool loop. One important version caveat: since deepagents 0.7.0, task-list planning through TodoListMiddleware is supported but no longer installed by default. The architecture should therefore be understood as a configurable bundle, not a fixed checklist.

What each layer buys

Filesystem-backed context

Large observations and intermediate artifacts move out of the live transcript. Summaries keep the active context small while files retain exact details for later retrieval.

Subagent delegation

A manager gives a bounded task to a specialist with a focused prompt and tool set. The worker returns a result instead of polluting the manager’s context with every intermediate step.

Optional explicit planning

A task list can make progress inspectable and revisable, but a list is useful only when later actions actually consult and update it. Planning middleware is configuration, not magic.

Memory and skills

Project instructions, reusable procedures, and cross-session facts can be loaded from external stores. Persistence depends on the configured backend; it is not automatically encoded in model weights.

Durable execution

Checkpoints can support pause, approval, retry, replay, and recovery. Durability comes from the runtime and persistent checkpointer, not merely from calling the agent “deep.”

Capability boundaries

Tools, backends, middleware, and sandboxes determine what the agent can actually do. The model proposes actions; trusted code validates and executes them.

A worked execution

Suppose the task is “upgrade a repository to a new payments API, preserve behavior, and explain the migration.” A Deep-Agent-style harness might execute it as follows:

Manager

Inspects the task, optionally writes a plan, and creates shared artifacts such as /work/constraints.md and /work/status.md.

Research worker

Reads the migration documentation in an isolated context, records exact API changes in /work/api-notes.md, and returns a short summary.

Code worker

Inspects call sites, applies the migration, and writes changed-file and uncertainty notes without carrying the research worker’s full transcript.

Verifier

Runs tests and static checks in the sandbox. Failures become observations; they do not become self-certified success claims.

Manager

Reads the artifacts, reconciles conflicts, requests follow-up work if necessary, and produces the final patch and migration explanation.

This is hierarchical delegation plus external working memory. It is not tree search: the workers are not competing branches whose values are backed up. It is also not automatically parallel; a runtime may execute delegated work serially or concurrently.

How Deep Agents relate to ReAct

ReAct

The inner control primitive: observe the current context, reason about the next move, call a tool, append the real result, and repeat.

⊂

Deep-agent harness

A larger architecture that can run several ReAct-like loops while managing plans, contexts, files, memory, delegation, persistence, and approvals.

Deep Agents do not replace ReAct at the same abstraction level. The manager and each subagent may still use a ReAct-style model/tool loop; the deep-agent architecture determines how those loops are composed and what state surrounds them.

3. The Alternative Architecture Patterns

“Alternative” does not mean mutually exclusive product choice. These are reusable patterns. A system should add the smallest pattern that addresses its observed failure mode.

Enhanced single-agent ReAct

One coherent model/tool loop with better tools, retrieval, summarization, guardrails, approvals, and perhaps a scratchpad. Lowest coordination overhead and the right default while one context still works.

Plan → execute → replan

A planner creates explicit remaining work; an executor performs one step; a replanner updates or terminates the plan. Best when decomposition is stable enough to inspect but observations still change the route.

Deterministic workflow or graph

Application code owns transitions, branches, joins, loops, and approvals; models are nodes inside the flow. Best when predictability, auditability, or bounded cost matters more than open-ended autonomy.

Supervisor → workers

A central manager decomposes work, delegates bounded subtasks, and retains responsibility for integration. This is the topology Deep Agents most directly emphasize.

Peer handoffs or “swarm”

The active specialist transfers control to another specialist. In common SDKs, “swarm” usually means model-directed handoff—not necessarily decentralization, parallelism, or emergent collective intelligence.

Reflection or critic loop

A generator produces work, a critic evaluates it, and the system revises until a coded acceptance or stopping rule fires. The critique normally changes context, not model weights.

Tree search and branching

Several candidate thoughts, states, or trajectories are generated and scored. ToT and LATS buy breadth and backtracking at much higher inference and environment cost.

Environment-native agent

The differentiator is a purpose-built computer interface: bounded file views, repository search, syntax-gated edits, shell execution, tests, patch extraction, and a sandbox. For coding, the environment can matter more than another model role.

Representative implementations, not categories

  • LangGraph, AutoGen GraphFlow, and CrewAI Flows can encode explicit state graphs, conditions, loops, and joins.
  • OpenAI Agents SDK, AutoGen, AG2, and CrewAI expose manager, specialist, or handoff patterns in different forms.
  • OpenHands and SWE-agent emphasize the workspace, shell/editor/test interface, sandbox, and trajectory around software work.
  • Reflexion, Tree of Thoughts, and LATS are improvement/search patterns that can wrap or branch ordinary agent loops.
Framework names hide composition. “Multi-agent” may mean one manager calling workers, serial handoffs through a shared transcript, or genuinely parallel isolated tasks. Those designs have different costs, failure modes, and training traces even when a library exposes all of them under one API.

4. How to Choose

Single ReAct Model One context Low Lowest baseline Open-ended tasks that still fit one coherent trajectory
Deep-agent harness Model inside runtime Filesystem + isolated workers Low–medium Medium–high Long-horizon research or coding under context pressure
Plan / execute Planner + replanner Explicit plan state Medium Medium Tasks with inspectable decomposition and changing observations
Workflow / graph Code State passed by nodes Highest Predictable Regulated, transactional, repeatable processes
Supervisor / worker Manager model Focused worker contexts Low–medium High, parallelizable Decomposable tasks needing specialists and final synthesis
Peer handoff Active specialist Shared or filtered handoff Low Medium–high Conversational routing among specialists
Reflection / critic Generator + evaluator Attempt and critique Medium with coded stop Iteration-dependent Outputs with a stable rubric: code, writing, structured analysis
Tree search Search controller Isolated candidate branches Medium Highest Hard tasks where candidates can be scored and compute is justified
  1. Start with one loop. Better tools and environment feedback often beat extra agent roles.
  2. Add explicit planning when long-horizon drift—not tool weakness—is the dominant failure.
  3. Add code-owned structure when predictability, approval, or bounded cost matters more than adaptation.
  4. Add workers when subtasks need different tools, prompts, or isolated context—not merely because the task is large.
  5. Add a critic only when an independent rubric can recognize improvement.
  6. Add search only when alternative trajectories can be scored well enough to justify their cost.
  7. For coding, improve the environment first: repository search, file views, safe edits, tests, and sandboxing define the action space the policy can learn.

Common architecture mistakes

Premature multi-agent design

Several copies of the same weak policy add token cost and coordination errors without adding genuine specialization.

Shared-context pollution

Every worker sees every intermediate message, so delegation multiplies context instead of isolating it.

Decorative planning

The model writes a todo list once, then ignores it. A plan matters only if execution and replanning consume the same state.

Handoff loops

Specialists keep transferring control because ownership and terminal conditions are ambiguous.

Self-verification

The agent that produced an action also declares it safe and correct, with no independent test or policy boundary.

Architecture by brand name

A framework is selected before the required topology, state, trust boundaries, and failure modes are understood.

5. The Moving Boundary — When the Model Absorbs the Harness

“The model swallows the harness” contains two claims that should be separated. The first is already plausible: training internalizes behavioral scaffolding, so the model needs fewer prompt rules to choose tools, decompose tasks, recover from errors, or decide what context matters. The stronger claim is that persistent state, permissions, execution, and governance become properties of the model itself. That does not follow.

Thick harness

Prompts and code prescribe planning, routing, retries, compaction, critique, and delegation around a relatively generic model.

Co-designed system

The model has learned agentic behavior; the runtime supplies state, tools, policies, and checkpoints while intervening less often.

Thin trusted kernel

The model chooses most cognitive actions, but external infrastructure still validates, executes, persists, limits, observes, and rolls back them.

Four kinds of “memory” that should not be collapsed

StateWhere it livesWhat it means
Parametric behavior Model weights General learned tendencies: tool syntax, decomposition habits, recovery strategies.
In-run state Prompt, tool results, KV cache The current episode’s working context; normally gone unless the runtime retains it.
Provider continuation Conversation or response service External service state supplied to later inference calls, not a weight update.
Application state Files, databases, checkpoints, stores Durable, auditable facts, artifacts, identities, budgets, and execution history.

The model can increasingly own

  • task decomposition and replanning;
  • tool and specialist selection;
  • context triage and summarization proposals;
  • error recovery and escalation decisions;
  • critique, revision, and uncertainty reporting.

The trusted runtime must still own

  • tool execution, authentication, and authorization;
  • durable storage, deletion, checkpoints, and replay;
  • sandboxes, network policy, secrets, and tenant isolation;
  • hard budgets, timeouts, rate limits, and termination;
  • independent verification, audit logs, deployment, and rollback.
The model may swallow the behavioral harness, but it cannot safely swallow the trust boundary.
The likely end state is not “no harness.” It is a thinner harness that looks less like a prompt author and more like an operating system kernel for state, capabilities, policy, and evidence.

This reframes Deep Agents too. Today’s explicit task lists, delegation prompts, context files, and retry policies can generate the trajectories from which a future model learns those behaviors. Some scaffolding may disappear into the policy. Files, permissions, sandboxes, independent verifiers, and durable execution remain external because they are facts and guarantees about the world—not merely better next-token predictions.

6. Architecture Becomes Part of the Policy’s Training Distribution

Changing the architecture changes what the model observes and therefore what policy is being trained. A single ReAct loop produces one mostly linear trajectory. A deep-agent harness may compact context, fork subagent prompts, merge summaries, and turn one task reward into several trainable model-call sequences. A deterministic graph inserts code-authored state between model calls. Tree search samples many branches but deploys only a selected path.

Architecture featureTraining consequence
Context compaction or file offload The post-compaction prompt may no longer extend the earlier token prefix; the compacted text is environment-produced context, not sampled policy output.
Subagent delegation One episode becomes several model-call histories with one shared terminal outcome and a harder credit-assignment problem.
Code-owned graph transitions Transitions are easier to replay and audit, but the policy only learns decisions exposed at agentic nodes.
Reflection or critic calls The learner must distinguish policy-generated tokens from evaluator feedback and decide which sequence receives the reward.
Tree-search selection Generated-but-rejected branches contain behavior data too; training only on the winner introduces a selection mechanism that must be understood.

The Harnessed Agentic RL page covers the systems consequence: if the production harness owns the graph, the trainer must recover faithful tokens, masks, behavior log-probabilities, and causal structure from the model calls it observes. The Production Learning Loop covers the longer-term consequence: real harness behavior can become training data, but new policies still need independent evaluation, promotion gates, and rollback.

Summary

Loop vs. architecture

ReAct is an inner control loop. Architecture places that loop inside a topology of planning, state, delegation, search, and execution.

Deep Agents

An opinionated harness around a normal model/tool loop: external context, subagents, memory, runtime services, and optional explicit planning.

No universal winner

Single loops, graphs, managers, handoffs, critics, and search solve different failure modes and can be composed.

Environment first

Tool feedback, safe execution, and a good computer interface often matter more than adding another model role.

Future boundary

Models can internalize planning and routing behavior; trusted infrastructure must still own authority, persistence, limits, evidence, and rollback.

Train what you ship

Compaction, delegation, graphs, and selection alter the policy’s observations. The deployed harness is part of the training distribution.
