ReAct — Reasoning + Acting

The agent loop that interleaves free-form reasoning with tool calls: thought → action → observation, repeated until the model has gathered enough grounded evidence to answer. The scaffold underneath almost every modern LLM agent.

A chain-of-thought prompt lets a model reason, but its reasoning is sealed inside its own weights — if it doesn't know a fact, it invents one. A tool-use prompt lets a model act on the world, but with no reasoning trace it can't plan multi-step lookups or recover from a bad result. ReAct (Yao et al., 2022) is the observation that these two failure modes cure each other: interleave a reasoning step and an action step so that thoughts decide what to do next, and observations feed back into the next thought. This page covers the loop itself, the prompt and control machinery that run it, where it sits relative to plain CoT and tree-search agents, and how it connects to the trained agents in the rest of these notes.

1. Why Interleave — Reasoning vs. Acting

Consider a multi-hop question: "Aside from the Apple Remote, what other device can control the program the Apple Remote was originally designed to interact with?" Three ways to attack it, and why two of them break:

Reason-only (CoT)

Thinks step by step but never looks anything up. If it doesn't already know the Apple Remote controlled Front Row, it hallucinates a plausible-sounding answer (e.g. "iPod") and confidently commits. No grounding, no way to check.

Act-only

Issues searches but emits no reasoning between them. It can fetch pages, but with no thought to track the plan it doesn't know what to search next after the first hop, loops on the same query, or stops early. Acting without a plan.

ReAct

Reasons about what it just observed, then acts on that reasoning. "It was designed for Front Row → search Front Row → that page says it's also controlled by keyboard function keys → finish." Each thought is grounded in a real observation.

The synergy runs both directions. Reasoning helps acting: the thought trace lets the model decompose the goal, decide the next action, parse what came back, and handle exceptions ("that page doesn't exist — try the disambiguation"). Acting helps reasoning: each observation injects external, up-to-date facts into the context, so the chain of thought is anchored to reality instead of drifting on the model's priors.

2. The ReAct Loop

One ReAct step produces a Thought (free-form natural language) and an Action (a structured call from a fixed action space). The harness executes the action and returns an Observation, which is appended to the context. The model then generates the next Thought conditioned on everything so far. The loop ends when the model emits a terminal action (Finish[...]) instead of another tool call.

The canonical trajectory for the Apple Remote question, against a Wikipedia API with three actions — Search[entity], Lookup[string], Finish[answer]:

Q
Aside from the Apple Remote, what other device can control the program the Apple Remote was originally designed to interact with?
think 1
I need to search Apple Remote, find the program it was designed to interact with, then find what else controls that program.
act 1
Search[Apple Remote]
obs 1
The Apple Remote is a remote control … originally designed to control the Front Row media center program …
think 2
It was designed to control Front Row. I need to search Front Row next and find what other device can control it.
act 2
Search[Front Row]
obs 2
Could not find [Front Row]. Similar: ['Front Row Seat to Earth', 'Front Row (software)', …]
think 3
Front Row is not found. I should search Front Row (software) instead.
act 3
Search[Front Row (software)]
obs 3
Front Row is a discontinued media center software … controlled by an Apple Remote or the keyboard function keys.
think 4
So Front Row is controlled by an Apple Remote or the keyboard function keys. The answer is keyboard function keys.
act 4
Finish[keyboard function keys]
✓
Correct — grounded in obs 1 and obs 3, with a recovery at think 3.
Thought (reasoning) Action (tool call) Observation (from env) Outcome

Two details make this work and are easy to get wrong. First, think 3 is error recovery — a failed search becomes an observation the model reasons about, rather than a crash. This is exactly what act-only cannot do. Second, the model generates the Thought and the Action but never the Observation — the observation comes from the real tool. The next section is how the harness enforces that.

3. Anatomy of a ReAct Prompt

ReAct in its original form is a prompting method: no fine-tuning, just a few-shot prompt whose exemplars are themselves Thought/Action/Observation trajectories. The model learns the format by imitation and produces the same interleaved structure on the new question.

# System / instruction
Answer the question using interleaved Thought, Action, Observation steps.
Action must be one of: Search[entity], Lookup[string], Finish[answer].

# Few-shot exemplar (one of several)
Question: Musician and satirist Allie Goertz wrote a song about … "The Simpsons" …
Thought 1: The question is about a song parody. I should search Allie Goertz …
Action 1: Search[Allie Goertz]
Observation 1: Allie Goertz is an American musician … wrote a song about Milhouse …
Thought 2: The song is about Milhouse. I need who Milhouse was named after.
Action 2: Lookup[named after]
Observation 2: Milhouse was named after U.S. president Richard Nixon …
Thought 3: The answer is Richard Nixon.
Action 3: Finish[Richard Nixon]

# Live question — model continues in the same format
Question: Aside from the Apple Remote, what other device …
Thought 1: <-- generation starts here, stop sequence = "\nObservation"

The three moving parts:

  • Action space. A small, named set of tools with a fixed argument syntax. The original Wikipedia setup used Search (find a page), Lookup (find a string within the current page, mimicking Ctrl-F), and Finish (terminate with the answer). Modern agents swap in bash, read_file, web_search, etc. — the pattern is identical.
  • Exemplars. A handful of full trajectories that demonstrate good reasoning–action interleaving, including a recovery from a failed action. The model copies the cadence: one thought, then one action, never two actions in a row.
  • The stop sequence. Generation is halted as soon as the model writes Observation: (or finishes the Action line). This is the load-bearing trick — without it the model happily hallucinates the observation too, defeating the entire point of acting on a real tool.
Modern chat models replace the text format with native tool-calling: the "Action" is a structured function-call object the API emits, and the "Observation" is a tool-result message appended to the conversation. The control flow — reason, emit one call, get a real result, reason again — is exactly ReAct. The text protocol above is just the same loop before function-calling APIs existed.

4. The Control Loop

ReAct lives half in the prompt and half in the harness that drives generation. The harness owns the loop: generate up to the stop sequence, parse the action, execute it, append the observation, repeat — with guard rails on iterations and parse errors.

def react(question, tools, max_steps=8):
  ctx = few_shot_prompt + f"Question: {question}\n"
  for step in range(max_steps):
    text = llm(ctx, stop=["\nObservation"]) # Thought + Action only
    ctx += text
    action = parse_action(text)
    if action.name == "Finish":
      return action.arg # terminal action
    if action is None:
      obs = "Invalid action. Use Search[…], Lookup[…], or Finish[…]."
    else:
      obs = tools[action.name](action.arg) # real tool call
    ctx += f"\nObservation {step+1}: {obs}\n"
  return "No answer within step budget." # max_steps fallback

What the harness is responsible for, none of which the model can do for itself:

  • Stopping at the action. The stop sequence cuts generation before the model can fabricate an observation.
  • Parsing. Extracting the action name and argument from free text (or reading the structured tool-call object). Malformed actions become an observation that tells the model how to fix the format — the loop self-corrects instead of crashing.
  • A step budget. max_steps bounds cost and breaks infinite reason–act loops (see failure modes). On exhaustion you can return a best-effort answer or force a Finish.
  • Context growth. Every observation is appended, so the context grows each step. Long trajectories need truncation or summarization of stale observations.

5. ReAct vs. CoT vs. Tree-Search Agents

ReAct is one point on a spectrum of test-time reasoning strategies. The axes are grounding (does reasoning touch the external world?) and search breadth (one trajectory or many?).

Method Grounded in tools? Search shape Best for
Chain-of-Thought No — internal reasoning only Single linear trace Closed-book reasoning where the model already knows the facts (math, logic)
CoT-SC (self-consistency) No Many independent traces, majority vote Reducing variance on reasoning tasks; no external info needed
ReAct Yes — observations feed each thought Single linear trajectory, greedy Knowledge-intensive QA and tool use where facts must be fetched
Tree search (ToT / LATS) LATS yes; ToT typically no Branch, evaluate, backtrack over many trajectories Hard tasks where one greedy path is unreliable and you can afford the compute

The key contrast: ReAct commits to one trajectory and never backtracks. If think 2 makes a wrong turn, the only recovery is a later thought noticing it — there's no mechanism to abandon the branch and try another. Tree-search agents (Tree of Thoughts, LATS) wrap the ReAct step inside an explicit search: generate several candidate thought/action pairs at each node, score them with a value function or self-evaluation, expand the promising ones, and back up the results — the same MCTS machinery used for games, applied to reasoning. You buy reliability with many times the token cost. ReAct is the greedy, depth-first special case: branching factor one, no value function, no backup. For most tool-use tasks that single grounded trajectory is enough, which is why ReAct is the default scaffold and tree search the escalation.

ReAct and CoT are complementary, not rivals. A robust recipe is ReAct → CoT-SC fallback: run ReAct first for grounded retrieval, and if it fails to reach a confident answer within the step budget, back off to chain-of-thought self-consistency on the model's internal knowledge. The original paper found this hybrid beat either method alone.

6. Failure Modes

Most ReAct failures are not the model "not being smart enough" — they are loop-level pathologies the harness has to defend against.

Reasoning / action loops

The model repeats the same thought and re-issues the same action, getting the same observation, forever. Common when a search returns nothing useful and the model can't think of an alternative. Defenses: the max_steps budget, detecting repeated actions and injecting a nudge observation ("you already tried this — try a different query"), and exemplars that demonstrate switching strategy after a dead end.

Hallucinated or malformed actions

The model invents a tool that doesn't exist (GoogleScholar[…]) or breaks the argument syntax. The parser must reject these and return a corrective observation rather than executing garbage. Native tool-calling APIs reduce this by constraining the output to a schema.

Hallucinated observations

Without a stop sequence, the model continues past the action and writes its own fake Observation: — then reasons over a fact it made up. This silently reintroduces the exact CoT failure ReAct was meant to fix. The stop sequence is non-negotiable.

Context bloat

Verbose tool outputs (a full web page, a long file) accumulate in the context and crowd out the reasoning, eventually overflowing the window. Mitigations: truncate or summarize observations, return only the relevant span (the Lookup action exists precisely to fetch a substring instead of a whole page), and drop or compress stale early observations.

7. From Scaffold to Trained Policy

Everything above is inference-time prompting — no weights change. But a ReAct trajectory is literally a rollout of a policy in a Markov Decision Process: the state is the running context, the action is the tool call, the transition is the environment executing it, and the reward is whether the final answer is correct. That framing is the bridge to the trained agents in these notes.

MDP component In a ReAct trajectory
\(s_t\) — state The full context so far: question + all prior thoughts, actions, and observations
\(a_t\) — action The next thought + tool call the model emits
\(P(s_{t+1}\mid s_t,a_t)\) The environment running the tool and appending the observation (stochastic — searches can fail)
\(R\) — reward Terminal: was the Finish[…] answer correct / did the task verify?

Two ways to turn the scaffold into a better policy:

  • Imitation (SFT on traces). Collect successful ReAct trajectories — from a strong model or from few-shot rollouts that happened to succeed — and fine-tune on them. The model internalizes the thought/action format so it no longer needs few-shot exemplars, and gets better at the specific tools. This is rejection-sampling / trajectory distillation applied to agent traces (cf. distillation).
  • Reinforcement learning. Treat the trajectory as an episode and optimize the terminal reward directly with policy gradients. This is exactly Agentic RL — long-horizon tool use, sparse terminal rewards, and the credit-assignment problem of which of N tool calls deserves the reward. ReAct supplies the rollout structure; Agentic RL supplies the learning signal that makes the policy better than its few-shot starting point.

So ReAct is the connective tissue: it is the inference-time agent loop that the RL pages then train. Read this for the loop; read Agentic RL for how to optimize it and Tree Search for LLMs for how to search instead of commit.

Summary

The idea

Interleave reasoning and acting: thought → action → observation → thought. Reasoning plans the actions; observations ground the reasoning.

Why it beats CoT

CoT alone hallucinates facts it doesn't know; act-only can't plan or recover. ReAct's observations anchor each thought in real, fetched evidence.

The machinery

A named action space, few-shot trajectories as exemplars, and a stop sequence so the model never fabricates the observation. The harness parses, executes, and bounds the loop.

Where it sits

Greedy, single-trajectory, grounded. CoT is ungrounded; tree search branches and backtracks at far higher cost. ReAct is the default; tree search the escalation.

Failure modes

Reason/action loops, hallucinated or malformed actions, hallucinated observations (no stop token), and context bloat from verbose tool output.

The bridge to RL

A ReAct trajectory is an MDP rollout. SFT on successful traces, or RL on the terminal reward (Agentic RL), turns the prompting scaffold into a trained policy.
