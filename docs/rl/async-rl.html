Async RL for LLM Post-Training

Scheduling regimes, policy-version staleness, three-policy correction, training–inference mismatch, and the controls that make streaming RL reliable.

Prerequisite: RLHF (PPO, policy gradient, GAE) and Importance Sampling (the IS identity, variance, self-normalized IS). This page covers the async-specific complications that arise when generation and training decouple. Systems walkthroughs: PPO in VeRL · PPO in slime/Miles. The environment side of the idle-GPU problem — slow env steps, sandbox fleets, oversubscription — is Scaling Environments. Ecosystem state: September 2026.

1. What Async RL Is Trying to Remove

In synchronous on-policy RL, generation and training alternate in strict lockstep:

rollout → [wait for slowest trajectory] → compute rewards → train → repeat

The problem is not simply that generation is slower than backpropagation. The ratio varies with model size, sequence length, parallelism and hardware. The structural problem is that one phase cannot make progress while the other owns the GPUs or while the batch waits for its slowest dependency.

BarrierWhy capacity goes idle
Trajectory tailA few long reasoning or tool-use episodes hold the entire rollout batch open.
Environment and grader tailSandboxes, tests and model judges complete at different times.
Phase switchColocated inference must release weights and KV cache before training can use the same memory.
Weight publicationRollout workers cannot use the new policy until weights are reshaped, transferred and loaded.

Async systems attack these barriers through streaming, buffering, admission control and overlap. They do not make an individual rollout cheaper. The gain comes from keeping useful work available when another request, service or phase is late.

2. Async RL Is a Scheduling Family

“Async” is not one architecture. Modern systems expose three scheduling regimes:

sync
  one pool:       [generate full batch] → [update] → [publish weights]

collocated async
  one pool:       [stream until enough] → [pause/abort requests] → [update] → [resume]

separate async
  rollout pool:   [generate continuously] ───────────────────────────────▶
  trainer pool:          [consume] → [update] → [consume] → [update] ───▶
RegimeGPU placementWhat overlapsMain cost
Sync Usually one colocated pool Requests may run concurrently, but generation and update remain batch barriers Long-tail drain and phase bubbles
Collocated async One pool time-shared by inference and training Agent trajectories stay live across phase boundaries; enough completed samples can trigger training before every trajectory ends Pause/abort, KV-cache rebuild and no simultaneous generation during the update
Separate async Dedicated rollout and trainer pools Generation and optimization execute concurrently through a bounded buffer Extra GPUs, queue control, staleness and weight-transfer complexity

Collocated async: one pool, interrupted phases

Agent Lightning v1.0 names the middle regime; current verl exposes trainer_mode: colocate_async. Once enough data is ready, the system stops admitting model work and switches the shared GPUs to training. The exact boundary is implementation-specific: Agent Lightning waits for current model requests to complete, while verl's V1 path can abort inference requests, release KV cache, update, then resubmit the kept token prefix. In both cases, a long-lived agent trajectory can survive the phase switch even though an individual model request cannot execute concurrently with training.

This avoids waiting for the slowest trajectory without paying for a permanently separate rollout fleet. Agent Lightning reports roughly 2× end-to-end speedup over its synchronous setup while using fewer GPUs than separate-pool async; that number is workload-specific, not a universal property of the schedule.

Two unrelated settings are often both called async. An inference server may handle requests asynchronously while the trainer still waits for a complete on-policy batch. In verl, rollout.mode: async selects server/request concurrency; trainer.v1.trainer_mode: colocate_async|separate_async is what permits training on older policy versions. Only the second meaning creates policy staleness.

3. Staleness Is a Distribution, Not One Steady-State Number

Stamp every sampled token or trajectory segment with the weight version that generated it. If the trainer is at version \(v_{\mathrm{train}}\), its version lag is:

Version lag
\[ K_{i,t}=v_{\mathrm{train}}-v_{i,t}. \]

\(K=0\) means same-version data; it does not imply a synchronous scheduler. A partial or multi-turn rollout may contain several \(v_{i,t}\) values, so report at least the oldest, newest and mean version—or retain the version per segment. A single trajectory-level scalar hides the oldest context that conditions all later actions.

Where age comes from

  • Generation age: updates completed while a long trajectory was still producing tokens or waiting on tools.
  • Reward age: tests, judges or remote environments finished after generation.
  • Queue age: a completed group waited in the buffer before the trainer consumed it.
  • Publication age: rollout engines continued using an older checkpoint between weight synchronizations.

A useful approximation is therefore based on measured delay, not a worker-count formula:

Operational approximation
\[ K \approx K_{\mathrm{publication}} +u\,(T_{\mathrm{generation}}+T_{\mathrm{reward}}+W_{\mathrm{queue}}) \]

\(K_{\mathrm{publication}}\) = rollout engine's initial version lag · \(u\) = trainer updates per second. This estimates a distribution, not a guarantee.

Queue balance

Rollout production < trainer demand

The buffer empties and the trainer waits. More tolerated staleness cannot manufacture samples; increase rollout/environment capacity or reduce trainer demand.

Rates approximately balanced

A small bounded buffer absorbs jitter. This is the target operating region: low idle time without a growing age tail.

Rollout production > trainer demand

The queue and lag grow unless capacity, admission or freshness rules apply backpressure. Old work must eventually block, drop or retry.

Little's law, \(Q\approx\lambda W\), is useful for sizing a stable completed-sample buffer, but it does not predict policy lag by itself. The age distribution also depends on rollout duration, reward latency, sync cadence, partial-rollout policy and whether the freshness gate uses each sample's newest, mean or oldest weight version.

4. Three Policies and Three Different “Sequence” Quantities

Async implementations become easier to reason about when the policies are named explicitly:

PolicyRoleWhen fixed
\(\mu\) Behavior policy: the rollout engine and weight version that sampled the token At generation time, potentially per token or segment
\(\pi_{\mathrm{prox}}\) Proximal policy: the frozen anchor used for PPO clipping At the beginning of the update or sync cycle
\(\pi_\theta\) Current policy: the actor being optimized Changes after each optimizer step

Decoupled PPO separates the rollout-to-proximal correction from the proximal-to-current trust region:

Three-policy surrogate (schematic)
\[ b_t=\frac{\pi_{\mathrm{prox}}(a_t|s_t)}{\mu(a_t|s_t)}, \qquad q_t=\frac{\pi_\theta(a_t|s_t)}{\pi_{\mathrm{prox}}(a_t|s_t)} \] \[ L(\theta)=- \mathbb{E}_{(s,a)\sim\mu} \left[ \operatorname{stopgrad}(\tilde b_t)\, \min\!\left(q_t A_t,\operatorname{clip}(q_t,1-\epsilon_l,1+\epsilon_h)A_t\right) \right]. \]

Bypass mode sets \(\pi_{\mathrm{prox}}=\mu\) and uses rollout log-probs directly as the PPO anchor, avoiding a trainer-side old-log-prob forward pass. It is still a mathematically meaningful two-policy objective; it is not restricted to perfectly on-policy data. The trade-off is that behavior correction and proximal update control are no longer independently tunable.

Exact trajectory importance sampling

For a complete trajectory sampled from \(\mu\), the exact change-of-measure weight is:

\[ W(\tau)=\frac{P_{\pi_{\mathrm{prox}}}(\tau)}{P_\mu(\tau)} =\prod_{t=1}^{T} b_t. \]

This is the sequence product. For step-dependent returns, classical per-decision IS uses prefix products through the relevant timestep. These estimators are exact under the usual support assumptions, but products over thousands of autoregressive decisions have enormous variance and can underflow or overflow numerically.

Token-level rollout correction

What LLM systems commonly call token-level IS does not multiply all token ratios. It applies each \(b_t\) independently to that token's policy-gradient term:

\[ \hat g_{\mathrm{token}} =\sum_{t=1}^{T}\tilde b_t\,A_t\,\nabla_\theta\log\pi_\theta(a_t|s_t). \]

This has much lower variance and works well as a practical correction, but for a sequence-level outcome reward it is not the exact trajectory change of measure. GSPO's critique is precisely that GRPO uses one sampled token from each next-token distribution as though it independently corrected the sequence objective.

Sequence products versus GSPO's geometric score

GSPO does not use the raw trajectory product as an unconstrained importance weight. It defines a length-normalized sequence score:

\[ s_i(\theta) = \left( \frac{\pi_\theta(y_i|x)}{\pi_{\mathrm{old}}(y_i|x)} \right)^{1/|y_i|} = \exp\!\left( \frac{1}{|y_i|} \sum_t \log \frac{\pi_\theta(y_{i,t}|x,y_{i,<t})} {\pi_{\mathrm{old}}(y_{i,t}|x,y_{i,<t})} \right), \] and clips the response as one optimization unit. The geometric mean keeps different response lengths on a comparable numerical scale and aligns clipping with sequence-level reward. It is a deliberate surrogate, not the exact unbiased trajectory IS weight.

QuantityDefinitionStrengthCost / limitation
Per-token correction Use \(b_t\) independently Low variance; localizes outliers Biased for a sequence-level change of measure
Exact trajectory IS \(\prod_t b_t\) Exact change of measure under support assumptions Variance and numerical range explode with horizon
Geometric sequence score \(\exp(\frac{1}{T}\sum_t\log q_t)\) in GSPO Length-comparable sequence-level trust signal Not exact IS; behavior depends on clipping/masking objective
Framework names are not a proof of semantics. In verl, rollout_is: sequence means a product of token correction ratios broadcast back over the sequence. GSPO's “sequence-level ratio” is the geometric mean. Other systems use mean or max token KL only as a rejection statistic. Inspect the formula, not the label.

5. Stabilization: Weight, Clip, or Reject

Once \(b_t\) or \(W(\tau)\) has a heavy tail, the exact estimator may be unusable. Modern systems deliberately trade bias, variance and sample efficiency in several orthogonal ways. Keep these mechanisms separate from PPO clipping on \(q_t\).

Continuous weighting — token or sequence IS

Multiply the policy-gradient term by a detached correction weight. Token mode uses one \(b_t\) per token; sequence mode uses one product \(W(\tau)=\prod_t b_t\) for the response. This is the correction mechanism; it does not decide whether the sample remains in the training mask.

TIS — truncate the continuous weight

Bound extreme correction coefficients, commonly with an upper cap:

\[ \tilde b_t=\min(b_t,C) \qquad\text{or}\qquad \widetilde W(\tau)=\min(W(\tau),C). \]

Truncation lowers variance but biases the change of measure. Some implementations normalize the resulting weights back to batch mean 1; that changes scale, not the lost tail.

Ratio masking / IcePop-style bounds

Set a correction coefficient to zero outside a lower/upper interval instead of pinning it to the boundary:

\[ \tilde b_t=b_t\, \mathbf{1}[C_{\mathrm{low}}\le b_t\le C_{\mathrm{high}}]. \]

This removes extreme gradient contributions completely. It wastes those tokens but avoids letting a clipped outlier continue to steer the update.

Rejection sampling and trust-region masking

Change the binary response mask using a token- or sequence-level statistic: raw ratio, summed/mean/max \(k_1\), \(k_2\), or \(k_3\) divergence estimates, or a sequence trust-region bound. Sequence masking is attractive for long-horizon rewards because one extreme token can invalidate the whole trajectory-level approximation; it also discards more expensive data.

MechanismActs onMain benefitMain cost
PPO clip\(q_t=\pi_\theta/\pi_{\mathrm{prox}}\)Limits movement during optimizationBiased surrogate when active
Token TISEach \(b_t=\pi_{\mathrm{prox}}/\mu\)Low-variance rollout correctionNot exact sequence change of measure
Sequence TIS\(\prod_t b_t\)Sequence-consistent correctionExtreme variance and length sensitivity
Ratio / KL maskingTokens or full sequencesRemoves toxic tailsThrows away collected experience
GSPO-style clippingGeometric sequence scoreMatches sequence-level reward and normalizes lengthSurrogate, not exact IS
No correction recovers missing support: if \(\mu(a|s)=0\) where the target policy needs probability mass, importance sampling has nothing to reweight. Nor can a ratio repair a changed state or action sequence caused by retokenization, context rewriting or an altered tool trace. Those are data-fidelity failures, not merely high-variance off-policy data.

6. Three Mismatches That Must Not Be Conflated

MismatchWhat differsCan IS repair it?
Temporal lag The rollout used an older weight version than the trainer. Sometimes, if the exact behavior log-probs and support are preserved.
Training–inference mismatch (TIM) Nominally identical weights and tokens produce different probabilities in rollout and training engines. It can be reweighted or filtered, but correction adds variance/bias and may retain a deployment gap.
Trajectory reconstruction mismatch The trainer sees different token IDs, context, tool serialization or history from what the model sampled against. No. The state/action pair changed; preserve tokens or fork the sample instead.

Numerical TIM

For the same nominal checkpoint and exact token prefix, compare rollout policy \(\mu\) with the training implementation \(\pi_{\mathrm{train}}\):

\[ \Delta_t = \log\pi_{\mathrm{train}}(a_t|s_t)-\log\mu(a_t|s_t). \]

Sources include batch-dependent reduction order, different tensor-parallel reductions, precision and quantization contracts, fused-kernel differences, MoE routing flips, and nondeterministic sparse-attention top-\(k\) selection. These range from small numerical perturbations to structurally different forward passes.

Token fidelity is a separate prerequisite

Decode–retokenize cycles, chat-template re-rendering, tool-call serialization, context compaction and subagent branching can change \(s_t\) or \(a_t\) before the trainer evaluates the sample. TITO, exact token capture and prefix/fork checks prevent that failure. Calling it TIM understates the problem: once the token trajectory changes, the stored rollout log-prob is no longer the probability of the action being trained. See why text cannot cross the harness seam.

Diagnosis

  • Controlled same-version replay: recompute the exact sampled tokens under the trainer and compare absolute log-prob error and ratio tails.
  • Distribution summaries: Pearson correlation, mean/max probability difference, \(k_1/k_2/k_3\) divergence statistics and sequence-level maxima.
  • Correction activation: TIS clip fractions and rejection rates show how much of the batch the mismatch treatment changes.
  • Keep PPO separate: in decoupled three-policy training, pg_clipfrac measures \(\pi_\theta/\pi_{\mathrm{prox}}\), not \(\pi_{\mathrm{prox}}/\mu\). Use rollout-correction metrics for TIM and staleness.
Aggregate KL is necessary but insufficient. A small mean can coexist with a toxic ratio tail, sign-asymmetric gradient distortion, or one dataset/harness whose mismatch is much worse than the global average. The monitoring page gives the full diagnostic stack.

Mitigation families

Eliminate or align

  • Batch-invariant and topology-aligned kernels
  • Matched precision and quantization contracts
  • Routing replay for MoE; deterministic sparse selection
  • Zero-KL alignment where the model/topology is explicitly supported

Reduce

  • Use a more stable precision where validated
  • Match TP degree and implementation paths
  • Shorten weight-sync intervals and queue residence
  • Keep sensitive layers out of aggressive quantization

Correct or reject

  • Decoupled PPO with explicit \(\pi_{\mathrm{prox}}/\mu\)
  • Bypass mode using rollout log-probs as the proximal anchor
  • Token/sequence TIS and ratio/KL rejection masks
  • Sequence-level trust-region masking for long horizons

The FP16 result belongs in the reduce family, not as a universal prescription. One study reports roughly a 24× mismatch reduction and stronger MATH performance than its IS baselines when switching BF16 RL fine-tuning to FP16. Whether that transfers depends on model, kernels, topology and numerical stability.

Miles's Zero-KL Alignment demonstrates the eliminate path for supported configurations by aligning attention, GEMM, operator precision and batching behavior across SGLang and the trainer. Miles also retains IS, masking and low-precision recipes when exact alignment is not available. It is therefore misleading to classify an entire framework as only “eliminate” or only “correct.” These are per-recipe choices.

7. The Controls That Actually Bound an Async Run

ControlQuestion it answersFailure if omitted
Placement modeDo rollout and training time-share GPUs or use separate pools?Wrong resource model and misleading utilization expectations
In-flight admissionHow many trajectories may be generating at once?KV-cache pressure, environment overload and unbounded future work
Completed-buffer capacityHow far may rollout production run ahead?Queue age grows even if the in-flight count is bounded
Weight-sync cadenceHow many optimizer updates occur before rollout engines receive new weights?Publication lag or excessive synchronization overhead
Freshness gateWhich version span is still trainable?Arbitrarily stale samples enter the objective
Unused-sample policyDrop, retry or wait for stale/failed groups?Silent compute waste or reintroduced tail stalls
Partial-rollout policyDrain, retract, abort/resubmit or resume in place?Lost tokens, repeated prefill, or mixed-version trajectories without provenance
Evaluation placementShared engines, dedicated fleet or external evaluator?Eval silently stalls rollout or is attributed to the wrong checkpoint

Current verl naming

The V1 trainer uses trainer.v1.trainer_mode: sync|colocate_async|separate_async. Its replay buffer applies a version-span gate such as max_off_policy_threshold; the companion Async Training in verl page traces the exact code path, partial resubmission and checkpoint-engine weight synchronization.

The separate experimental fully_async_policy recipe uses trigger_parameter_sync_step, staleness_threshold and partial_rollout. Its staleness_threshold is a fractional allowance for stale production, not a maximum age in policy versions. These namespaces describe related mechanisms but are not interchangeable.

Current Miles naming

Miles uses a persistent rollout worker, a bounded data buffer and controls such as --async-max-concurrent-samples, --async-data-buffer-capacity-factor, --update-weights-interval and --max-weight-staleness. Its --pause-generation-mode determines whether requests retract and rebuild KV cache or pause in place across weight publication.

Monitor the causal chain

sample age
  → rollout/train probability mismatch
    → TIS or rejection activation
      → PPO update clipping
        → reward, entropy, gradient and evaluation outcome

Log system state beside optimization state: queue depth and age, oldest/newest weight version, discarded or retried groups, partial-span distribution, rollout/trainer idle ratios, environment and grader failures, and weight-sync duration. Large-scale cases and reported speedups

GLM-5 remains a useful operational case for the older slime lineage: threshold-triggered training, weight publication every \(K\) updates, optimizer-state reset at publication, staleness filtering by the oldest version in a multi-turn trajectory, explicit environment-failure masking, TITO, and double-sided token-ratio masking. Its later SAO work (arXiv 2607.07508) removes the GRPO group synchronization barrier by moving to one rollout per prompt plus a value model. These are recipe choices, not requirements of async RL itself.

The headline speed numbers below are not an apples-to-apples benchmark:

  • AReaL: reports up to 2.57× throughput and scaling to 512 GPUs on its evaluated reasoning/code workloads.
  • verl fully_async_policy: reports 2.35–2.67× on Qwen2.5-7B with 128 GPUs and no significant result degradation in its setup.
  • Agent Lightning: reports roughly 2× end-to-end over its synchronous baseline while using fewer GPUs than separate-pool async.
  • Miles: publishes a 744B-A40B, 16-node GLM-5.2 recipe and detailed continuous-rollout, buffer, evaluation and weight-transfer mechanics; its blog is a system capability report, not the same benchmark as the rows above.
  • MiMo: exposes live trainer and sampler telemetry, but has not yet published the controlled ablations needed to attribute quality or speed to one mechanism.
Practical choice: start synchronous while validating rewards, masks and log-prob semantics. Use collocated async when GPUs are constrained and long-tail trajectories dominate. Use separate async when continuous rollout, heterogeneous parallelism or independent scaling justifies a second pool. In every mode, preserve exact tokens and sampling-time log-probs before tuning correction thresholds.
