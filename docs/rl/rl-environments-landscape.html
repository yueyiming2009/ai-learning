RL Environments — Anatomy & Landscape

What an agentic-RL training environment actually is — a task distribution, a harness, a verifier, and managed state — and the map of the ecosystem that exploded around that idea: OpenEnv, verifiers and the Environments Hub, Harbor, the domain gyms, and the sandbox substrate underneath.

This is the entry page for the RL Environments series. The prerequisite is Agentic RL — the rollout is a multi-turn MDP, and the environment is the thing the policy interacts with. From here go deep: OpenEnv (the interface standard) → verifiers & the Environments Hub (environments as packages) → Verifiers & Reward Design (the grading problem) → Scaling & Sandboxing (the systems layer) → Task Generation & Curriculum (where the tasks come from).

1. From Datasets to Environments

Pretraining consumes a dataset: a static pile of tokens, the same for every model that trains on it. Agentic RL consumes something different — the model acts, something answers, and the next token the model sees depends on what it just did. That "something" is the environment: the terminal that runs the agent's command, the browser that renders the page it clicked, the codebase whose tests its patch must pass. A dataset is a recording; an environment is a counterparty.

Through 2023–24 this was an afterthought — each RL paper hand-built one environment and one reward function, welded to its training code. Around late 2025 it became the field's central bottleneck, for three converging reasons:

  • Verifiable rewards scaled. RLVR-style training (DeepSeek-R1) showed that a checkable reward — a unit test, an exact answer — is enough for large capability gains. The reward lives in the environment, so more and better environments became the direct path to more and better RL. The framing is often credited to Silver & Sutton's "Era of Experience" essay: the next scaling axis is experience generated by interaction, not text scraped from the web.
  • Agents went long-horizon. Coding agents, terminal agents, and browser agents take dozens-to-hundreds of steps per episode. Training them needs thousands of concurrent, isolated, resettable copies of realistic software worlds — a systems problem no static dataset has.
  • Money followed. Reporting in late 2025 put frontier-lab spending on RL environments ("RL gyms" — simulated enterprise apps plus hired domain experts) at around $1B/year for Anthropic alone, with a wave of startups selling environments the way Scale AI once sold labels. "Environments are the new datasets" became the standard one-liner.

The result: in roughly twelve months the ecosystem went from bespoke, per-paper environments to specs, hubs, package registries, and managed APIs serving hundreds of thousands of tasks. This page maps that ecosystem; the rest of the series goes deep on each layer.

2. Anatomy — What an Environment Actually Is

The word "environment" suggests a simulator with a physics loop. For LLM agents that intuition misleads. Across every 2025–26 framework the same decomposition keeps reappearing (verifiers v1 calls the pieces taskset / harness / runtime; Hanchung Lee's taxonomy writes \(E = \{\text{Tasks},\ \text{Harness},\ \text{Verifier},\ \text{State}\}\)). An agentic-RL environment is four things bundled:

ComponentWhat it isExample (SWE environment)
Task distribution The instances you sample an episode from — prompt, initial state, success criteria. This is the part that plays the role a dataset used to play. 2,438 PR-derived issues (SWE-Gym), each with a repo snapshot and hidden tests
Harness The interaction protocol: what counts as an action, how observations are rendered into context, when the episode ends. The ReAct loop and its tool schemas live here. An agent scaffold with bash, edit, submit tools and a max-turns budget
Verifier The grader that turns a finished episode into reward — unit tests, end-state checks, rubrics, judges. Deep-dive: Verifiers & Reward Design. Run the repo's hidden test suite against the agent's patch
State & runtime Where the world lives between steps and what isolates it — a container, a VM, a browser session — plus reset/snapshot semantics. Deep-dive: Scaling & Sandboxing. A Docker container per episode, reset from an image between rollouts

Contrast this with the classic Gym environment from the MDP and DQN pages. There, the interface is obs = env.reset(), obs, reward, done = env.step(action) with fixed observation and action spaces, and the environment is small, fast, and stateless between episodes. The LLM version keeps the interface — nearly every modern spec is still reset/step underneath — but changes every assumption around it:

Classic Gym (CartPole, Atari)LLM-agent environment
Action spaceSmall, fixed, enumerableOpen-ended text / tool calls with typed schemas
ObservationDense vector or pixelsText rendered into a context window (tool output, terminal, DOM)
Step costMicroseconds, in-processMilliseconds–minutes, usually over HTTP to a container
RewardEmitted by the simulator every stepComputed by a verifier, usually once, at episode end
ResetFreeContainer restore / snapshot fork — an engineering problem
Episodes neededMillions, cheapThousands–millions, each expensive → massive parallelism
The mental model

An RL environment is a dataset with an executable inside: a task distribution, plus the machinery (harness + runtime) to let a policy act on each task, plus the machinery (verifier) to score what it did. Every project in §3 is a different answer to "which of those pieces do I standardize, and where do they run?"

3. The Stack — Who Owns Which Layer

The 2026 ecosystem did not converge on one winner; it converged on layers. Specs compete within a layer and compose across them — the same environment can be an OpenEnv container, distributed as a Hub package, graded by a Harbor-format checker, running on a Modal sandbox, feeding a TRL trainer.

Trainer

The layered stack, mid-2026. Convergence happened at the top (trainers expose one env hook) and the bottom (everything runs in containers); pluralism persists in the middle. When you meet a new project, the first question is which row it lives in.

4. The Projects

OpenEnv

Meta PyTorch + Hugging Face → multi-org technical committee · open spec

The Gymnasium of the LLM era: a typed reset()/step()/state() client–server spec where each environment is a Docker-containerized FastAPI server, deployable as a Hugging Face Space, with MCP tool exposure first-class. Went multi-org in June 2026 (Nvidia, Microsoft, Modal, Prime Intellect, Mercor, Fleet on the committee); consumed by TRL, verl, SkyRL, torchforge, Unsloth. The front-runner for the interface layer. Full write-up →

verifiers + Environments Hub

Prime Intellect (library by Will Brown) · open source + hosted hub

Environments as versioned Python packages: an env bundles dataset, rollout logic, tools, and a composable Rubric of reward functions, installable with prime env install and runnable against any OpenAI-compatible endpoint. The v1 rewrite (July 2026) split the abstraction into taskset / harness / runtime and added an interception proxy that records agent↔model traffic. Powers prime-rl and INTELLECT-3; the Hub serves 365k+ tasks behind one API. Full write-up →

OpenReward / Open Reward Standard

OpenReward · open protocol + commercial managed endpoints

"MCP for environments": ORS extends the MCP wire protocol with RL primitives — episodes, reward signals, tasks, train/eval splits, curriculum — so an environment is an HTTP endpoint speaking a standard protocol rather than a package you install. The company serves 330+ environments over ~4.5M tasks as managed, autoscaled endpoints; the same env runs hosted, self-hosted, or local. TRL ships a first-party integration alongside OpenEnv.

Harbor (Terminal-Bench)

Stanford + Laude Institute · open source

Grew out of Terminal-Bench: a framework for running any agent — Claude Code, OpenHands, Codex CLI, Terminus — against containerized tasks with pytest-style end-state verification, parallelized across cloud sandbox providers, exporting rollouts for SFT/RL. Its task format is becoming the de facto taskset interchange: SkyRL, verifiers v1, and TRL all consume Harbor tasksets directly.

GEM & AgentGym-RL

SEA AI Lab (Axon-RL) · Fudan NLP · academic open source

The academic gym suites. GEM ("General Experience Maker", ICLR 2026) is an OpenAI-Gym-style env suite for LLM agents — ~24 envs with async vectorized execution and integrated tools, deliberately trainer-agnostic with single-file adapters for verl, Oat, OpenRLHF. AgentGym pioneered the env-as-HTTP-server pattern back in 2024; AgentGym-RL (ICLR 2026) adds the decoupled env/agent/training architecture and horizon-curriculum training (ScalingInter-RL).

agent-lightning

Microsoft · open source

The inverted design: instead of porting your agent into an env framework, instrument the agent you already have (LangChain, AutoGen, OpenAI SDK, anything) and stream its traces and rewards to a training server that does the RL and re-serves updated weights behind an OpenAI-style API. "The environment is wherever your agent already runs." Interesting precisely because it shows the env abstraction can live at the trace level rather than the protocol level.

Also on the map: SkyRL (Berkeley) spans layers — trainer, gym suite, agent layer, and a local Tinker-API backend; SWE-ReX (Princeton/Stanford) is the runtime-abstraction layer under SWE-agent (one shell API over Docker/Modal/Fargate); CUBE (AI Alliance, 2026) proposes wrap-once-use-everywhere benchmark packaging. New entrants appear monthly — place them on the §3 stack rather than memorizing names.

6. Inside the Labs

The open ecosystem above is one half of the story; the frontier labs run internal versions of the same stack, and the public record — tech reports plus journalism — is enough to see the shape:

  • Moonshot / Kimi K2 (tech report): agentic training data synthesized by simulating thousands of MCP and synthetic tools; RL over verifiable-reward environments plus self-critique rubrics; a fully async server-based orchestrator for actors, environments, and reward computation — the same trainer/env/verifier decomposition as §2, at lab scale.
  • Alibaba / Qwen3-Coder: the most concrete public scaling number — 20,000 independent environments running in parallel on Alibaba Cloud for long-horizon code RL. That number is the design target the sandboxing page works back from.
  • Anthropic & OpenAI (reported, not confirmed by the labs): training in "RL gyms" — high-fidelity replicas of enterprise software plus hired domain experts writing tasks and rubrics — with environment spending reported around $1B/year and growing. Neither lab has published its env infrastructure; their public role in the open ecosystem is as buyers.

7. The Market — Environments as a Product

Because environments are the new datasets, an industry formed to sell them, echoing the data-labeling wave. Worth knowing as context (numbers are point-in-time, from Epoch AI's Jan 2026 FAQ and press reporting):

  • Sellers: startups building environments as the product — Mechanize ("replication training": agents recreate existing software from spec, so the original serves as a free reference verifier), Fleet (enterprise-app replicas), Kaizen, Bespoke — plus every incumbent data vendor pivoting: Mercor, Scale, Surge, Turing, Snorkel.
  • Economics: lab contracts commonly $300–500k/quarter; individual tasks $200–$2,000 to author; a Slack-class app replica can run $300k+. Exclusivity commands 4–5× pricing.
  • Quality bar: vendors calibrate task difficulty to low single-digit pass rates for frontier models (the reward-design page covers why), and name reward hacking — agents exploiting verifier gaps — as the top quality concern, ahead of task volume.

8. How to Place Anything New

This space produces a new name weekly. Five questions place any of them on the map:

QuestionWhat it tells you
Which §3 layer does it own — interface, packaging, tasks, verifier, or substrate?Its actual competitors (most "vs" debates compare projects on different layers)
What is an action — free text, typed tool calls, MCP?The harness design, and which agents can run in it unmodified
Where does the verifier run, and can the policy see it?Reward-hacking surface — hidden tests and end-state checks resist gaming; visible rubrics don't
What does reset cost — process restart, container rebuild, snapshot restore?Whether it can serve RL (thousands of cheap episodes) or only evals
Which trainers consume it today?Whether it is infrastructure or a paper artifact
The short version

An environment = tasks + harness + verifier + state. The ecosystem standardized in layers: OpenEnv owns the interface, verifiers/Hub owns packaging, Harbor owns the taskset format, sandbox vendors own the substrate, and trainers consume all of them behind one hook. The hard open problems are not interfaces but content: verifiers that resist reward hacking and task generation that scales — the subjects of the reward-design and task-generation pages.
