RL for Generative Recommendation
Concepts & Landscape

First identify what the model generates. Then ask what its reward measures—and which evidence connects optimization to better recommendations for real users.

1 · Concepts & landscape → 2 · Ranking RL training Continue to the detailed training loop →

The central distinction: generative recommendation specifies an action representation and model family; reinforcement learning specifies a way to optimize a policy. Neither implies the other.

A model can generate catalog IDs with supervised training alone. A conventional recommender can use RL without generating text. A list generator only learns useful list interactions if its data, objective, and constraints actually teach them.

1. What is being generated?

A familiar recommender pipeline is retrieval → ranking → reranking → serving. Retrieval reduces a large catalog to candidates; ranking estimates relevance or outcomes; reranking applies list-level objectives and constraints. These are functional roles, not a rule that every product must have three separate models.

Item
A recommendable entity: a video, product, song, article, or another catalog entry. Its ID is not the item’s natural-language description.
Slate
An ordered collection of items shown together. Position and co-occurrence can affect utility; a page may have additional row and layout structure.
Request
One decision occasion, conditioned on available user history, context, eligibility rules, and possibly an explicit candidate set.
Session
An overloaded industry term. It can mean a request-sized item batch, a browsing visit with several requests, or a longer interaction sequence. Check each paper’s definition.
“Generative recommendation” can replace different pieces of the pipeline.
FormGenerated actionWhat still matters
Generative retrievalOne or more catalog IDs, often represented as token sequences, retrieved directly from user context.Catalog coverage, valid IDs, recall, and efficient search. A downstream ranker may remain.
Constrained candidate-set rerankingAn ordering or subset of an already supplied candidate set.Cannot recover a good item that retrieval omitted. Candidate order must not become a label shortcut.
End-to-end item-and-list generationA sequence of items, where later selections can depend on earlier selections.Eligibility, deduplication, diversity, and serving remain necessary even when retrieval and ranking are unified.
Whole-page generationStructured choices such as rows, entities within rows, and their ordering.Hierarchy, row/entity candidate constraints, page validity, and the page’s engagement objective.

Generative does not necessarily mean an LLM, natural-language output, or RL. A compact encoder–decoder trained to emit discrete IDs is generative too. Reasoning text is optional; even a training-time reasoning model may serve direct outputs after distillation.

2. From a user request to an exact catalog action

Two common item representations

  • Item token: one dedicated token per item. Identity is direct, but the vocabulary grows with the catalog and new items require an update strategy.
  • Semantic-ID sequence: represent an item with several discrete codes, for example [12, 7, 43]. Codes may be learned from item embeddings, allowing shared coarse-to-fine structure. A shared prefix is a modeling choice, not a guarantee of human-interpretable meaning.

User conditioning \(x\) can include interaction history, profile/context features, request intent, and candidate metadata. An encoder may summarize this context for a decoder, or a decoder-only model may consume a serialized context prefix. History length, feature freshness, and privacy constraints remain recommendation-system design problems.

\[ \pi_\theta(y\mid x) = \prod_{t=1}^{T}\pi_\theta(y_t\mid x,y_{<t}), \qquad y=\operatorname{encode}(i_1,\ldots,i_K). \]

Here \(y_t\) is an output token, not necessarily a complete item. An item can span several tokens; a slate can contain separators or structural tokens. At the item level, a list policy can be written as \(\pi_\theta(i_1,\ldots,i_K\mid x)=\prod_k \pi_\theta(i_k\mid x,i_{<k})\). This permits earlier choices to influence later ones without proving that the model has learned a desirable joint objective.

Generation must end in a valid, eligible item

Decoding free-form text that resembles an item ID is not enough. Catalog-aware systems can use a trie of valid semantic-ID prefixes, candidate-specific masks, or a grammar for structured pages. Apply the allowed-token mask and renormalize at each step; the complete code must resolve to an exact catalog entry. Shared-code collisions need a disambiguating suffix or another explicit resolution mechanism.

For a no-repeat slate, eligibility changes after each completed item. Inventory, geography, safety, and commercial rules can further restrict the action set. Training, rollout sampling, log-probability calculation, and serving must agree on what distribution these constraints define. See behavior policies and log probabilities for the probability bookkeeping.

A representation is not a planner. Generating 30 semantic-ID tokens for a single request does not establish 30 user-interaction steps. Token-prefix credit assignment and long-horizon user decision-making are different problems.

3. Imitating logged choices is not the same as optimizing a slate

Supervised fine-tuning (SFT) often teaches the model to reproduce a target item or list, using a next-token loss such as \(-\sum_t\log\pi_\theta(y_t^*\mid x,y_{<t}^*)\). Targets may come from logs, a teacher, or curated examples. This teaches format and useful behavior, but can inherit the historical system’s exposure patterns and optimization priorities.

A desired outcome might instead balance relevance, redundancy, satisfaction, and business guardrails. Conventional rankers can model item interactions too: listwise scoring, cross-item attention, and constrained reranking are not exclusive to generation. The useful distinction is the objective and action space—not “independent old models” versus “joint new models.”

A small exact example: relevance versus redundancy

Choose three different items from a six-item catalog. A slate is ordered, so there are \(6\cdot5\cdot4=120\) possibilities. Use position weights \(w=[1,0.8,0.6]\) and these deliberately simple quantities:

\[ B(s)=\frac{\sum_{k=1}^{3}w_k q_{i_k}}{2.4}, \qquad D(s)=\frac{\sum_{1\leq j<k\leq3}\mathbf{1}[c_{i_j}=c_{i_k}]}{3}, \qquad U_\lambda(s)=B(s)-\lambda D(s). \]

\(q_i\) is the assigned relevance score and \(c_i\) is the category. Redundancy \(D\) is the fraction of the three unordered pairs sharing a category. Compare the fixed relevance-ranked slate A → B → C with an exhaustive search over all 120 slates under exactly the same utility.

At scale, exhaustive search is usually infeasible. A learned policy may amortize the search into fast generation, but reward quality, exploration, and approximation error now matter. Merely outputting a list does not cause the model to optimize \(U_\lambda\); it needs training signal that distinguishes the slates.

4. Three training routes—and a separate reward axis

Many systems start from a supervised model and combine several methods. The following categories describe the update mechanism, not a mandatory progression toward RL.

RouteTraining signal and updateMain limitation
Supervised / reward-weighted learningSFT fits target tokens; reward-weighted fitting emphasizes higher-value examples. Other supervised objectives include weighted binary classification over scored examples.Learns from supplied targets or examples and their weights. Its support and selection bias depend on how examples were collected.
Preference learning: DPO / ORPOIncrease the relative likelihood or odds of a preferred response over a rejected one. DPO typically uses a reference policy; ORPO combines a supervised term with an odds-ratio preference term.Pair construction defines what “better” means. These are not PPO/GRPO-style sampled-return policy-gradient updates, even when a paper describes the larger system as RL.
Policy-gradient RL: PPO / GRPO and variantsSample actions, score rewards, estimate advantages, and update action probabilities with mechanisms such as clipping and a reference KL penalty. PPO commonly learns a value baseline; GRPO uses relative rewards within sampled groups.Exploration, unreliable rewards, low-signal groups, and distribution mismatch can dominate optimizer choice. Named variants are not interchangeable.

For the mechanics, see DPO, PPO, GRPO, and the broader RLHF pipeline. The next page specializes rollout, reward, masking, advantage, and policy-update bookkeeping to ranking.

Orthogonal question: where does the reward come from?

Reward sourceWhat is observedWhat is not established
Logged-label metricScore a generated ranking using labels on logged candidates: e.g. NDCG, Recall, or AUC, where the metric is defined.The real response to a new slate or new exposure is not observed. Historical labels may depend on position and selection.
Learned reward model (RM)A predictor scores generated items, lists, or pages; it may be trained on genuine engagement data.A prediction for a hypothetical page is not actual feedback on that page. Optimization can exploit model errors.
Actual user feedbackThe deployed policy exposes recommendations; impressions and later responses are joined to those actions.A raw behavioral metric is not automatically satisfaction or causal long-term value. Delay, censoring, assignment, and guardrails still matter.

On-policy generation ≠ real-user exposure. Sampling fresh lists from the current policy and scoring them against fixed labels or an RM can be on-policy for the optimizer, entirely offline with respect to users. DPO pairs can also be refreshed using generated samples. Conversely, real feedback collected under an older deployed policy is not automatically on-policy for the current training checkpoint.

Version names matter. The original OneRec’s DPO should not be conflated with the June 2025 OneRec technical report’s later RM-based policy-gradient method, ECPO, or with OneRec V2’s GBPO/user-feedback setup. Cite the actual paper and version rather than assigning one optimizer to the entire family.

Three separate claims to audit: (1) the complete system improves an online metric; (2) an RL component improves a controlled comparison; (3) the reward predicts the outcome of interest. Evidence for one does not automatically establish the others. An online metric and an offline NDCG gain are also not directly comparable effect sizes.

6. What can fail—and what would count as convincing evidence?

Exposure bias: unshown is not negative

Logs record what the historical policy chose to expose, at particular positions, to particular users. An unshown item has an unobserved outcome, not a negative label. Even a shown-but-unclicked item may not have been examined. Changing a list can alter attention and item interactions, so replaying the old labels on a new list is a surrogate evaluation, not observed counterfactual engagement.

The update ratio \(\pi_\theta(y_t\mid x,y_{<t})/\pi_{\text{old}}(y_t\mid x,y_{<t})\) concerns the policy that sampled the training action. It does not, by itself, correct historical logging-policy exposure bias. Off-policy evaluation requires its own estimand, logged propensities or justified models, adequate action support, and care with slate/position effects. Exact-slate propensity estimates can have severe variance. See importance sampling.

Sparse groups and seductive reward shortcuts

With exact-item rewards and a huge catalog, every sampled completion may miss the target. A GRPO group with identical rewards provides no relative reward direction; numerical epsilon avoids division by zero but does not create information. Early semantic-ID mistakes can eliminate the target before later tokens are sampled. HCGRec’s hints are one proposed training intervention—not a license to leak the target into inference.

Ranking rewards can be hacked by copying candidate input order, exploiting position-label correlations, repeating a high-scoring item, emitting malformed lists that a permissive parser accepts, or satisfying an RM rather than a user. Format validity should be checked separately from quality; enforce exact IDs, membership, no repeats, and slate length. Shuffle candidate order where appropriate, audit label leakage, and keep an independent evaluation path. Reward and verifier design explains why the evaluator is part of the learning system.

Cold start, constraints, and serving are not optional details

  • Cold start and catalog churn: shared semantic codes can reuse item features, but do not guarantee discovery of new items. Codebooks, ID mappings, eligibility, and fresh feedback must remain synchronized.
  • Hard constraints versus soft rewards: unavailable or prohibited items should not become admissible merely because another reward term is high. A reranking policy also remains bounded by candidate recall.
  • Latency and policy mismatch: beam width, token length, reasoning, caching, and candidate masking affect cost. Greedy or beam-search serving differs from stochastic rollout sampling; verify the deployed decision rule, not only the training sampler.
  • Metric trade-offs: watch time, clicks, novelty, supplier coverage, and user satisfaction can conflict. Normalization or shaping helps define a signal; it does not establish that the signal is the desired outcome.

A true long-horizon problem has users and transitions

\[ J(\pi)=\mathbb{E}_{\pi,P}\!\left[\sum_{n=0}^{H-1}\gamma^n r_n\right], \quad a_n=\text{a slate or page},\quad s_{n+1}\sim P(\,\cdot\mid s_n,a_n). \]

Here \(n\) indexes user decision occasions, not output tokens. The state may include history, evolving interests, and fatigue; an action changes subsequent observations and possibly future preferences. Those states are often only partially observed. Optimizing this objective requires meaningful trajectories, delayed-outcome attribution, and evidence that the model learns beyond an immediate proxy. A terminal reward on a token sequence can instead train a one-request policy—often usefully viewed as a contextual-bandit problem at the user level.

Calling an output a “session,” training on several items at once, or reporting app stay time does not establish multi-session planning. For the larger production feedback loop, see production agent learning.

An evidence ladder for a ranking project

  1. Validity and offline generalization: exact-item/constraint checks; time-separated, leakage-audited evaluation; metrics broken down by user cohorts, candidate sources, and cold-start items.
  2. Independent outcome evidence: do not judge an RM-optimized policy only with that same RM. Use held-out observed outcomes, independent audits, and, where feasible, randomized exposure.
  3. Controlled online A/B: specify the randomization unit, exposure, duration, uncertainty, delayed metrics, and safety/business guardrails. Measure real engagement separately from predicted reward.
  4. Isolate the RL contribution: compare SFT-only, preference/reward-weighted, and policy-gradient variants with matched architecture, candidates, data access, and serving budget. If the treatment changes all of them, report a whole-system gain—not an isolated RL gain.
