Scaling Environments — Sandboxes & Rollout Infrastructure

RL wants thousands of cheap, disposable, restorable copies of a software world. The isolation spectrum from containers to microVMs, snapshot/fork as the reset primitive, the provider-abstraction layers, and the oversubscription math that keeps GPUs busy while environments think.

Part of the RL Environments series (landscape) — this is the substrate layer of the stack. It pairs with the systems pages: Async RL (staleness and IS correction), verl async training, and reward pipelining all attack the same idle-GPU problem from the trainer side; this page attacks it from the environment side.

1. The Requirement: Disposable Worlds, by the Thousand

A developer sandbox is one long-lived, carefully maintained machine. An RL environment fleet is the opposite object: thousands of short-lived, identical, mutually isolated worlds, each born for one episode, mutated arbitrarily by an agent, graded, and destroyed. The public design point is Qwen3-Coder: 20,000 independent environments in parallel on Alibaba Cloud for long-horizon code RL. Every property follows from the workload:

  • Cheap creation. An episode may last a minute; if provisioning takes 30s, a third of the fleet is always warming up. Providers compete on cold start — tens to a few hundred milliseconds is the current bar.
  • Real isolation. The agent executes untrusted, model-generated code — rm -rf, fork bombs, network scans are all in-distribution. One episode must not corrupt another, the host, or the grader (reward hacking gets much easier if it can).
  • Deterministic reset. Every episode must start from a bit-identical world, or reward becomes noise and rollouts aren't comparable within a GRPO group.
  • Hermeticity. Pinned dependencies, no uncontrolled network egress — both for reproducibility (a task that breaks when PyPI changes is not a task) and for containment.

2. The Isolation Spectrum

Every sandbox technology is a trade between isolation strength, startup latency, and density (how many fit per host). The fleet vendors are all points on one spectrum:

MechanismHow it isolatesCold startUsed byThe catch
Container (Docker/K8s) Namespaces + cgroups; shared host kernel ~100ms–1s (image cached) Default everywhere — OpenEnv, Harbor tasks, SWE gyms Kernel exploits escape; weakest boundary for hostile code
gVisor User-space kernel intercepting syscalls ~100s of ms Modal (with GPU support in sandboxes) Syscall interception overhead on I/O-heavy work
MicroVM (Firecracker) Hardware virtualization, minimal device model ~125–150ms E2B, Morph Cloud (AWS Lambda's engine) Own kernel per VM — more memory per instance; GPU passthrough is work
Dev-container platforms Containers + orchestration polish ~27–90ms claimed (Daytona) Daytona (an OpenEnv provider), cloud dev boxes Same kernel-sharing caveat as any container

The practical resolution most fleets land on: containers for density, microVM or gVisor tiers for hostile or internet-touching work — and the choice is increasingly made per environment by declaring a runtime requirement and letting the provider layer (§4) place it. Numbers above are vendor point-in-time claims; the ordering, not the digits, is the durable content.

3. Reset, Snapshot, Fork

Classic Gym's reset() is free; here it is the dominant cost decision. Three implementations, in ascending sophistication:

  1. Rebuild — recreate the container from its image every episode. Simple, bit-exact, and slow when setup is heavy (clone repo, install deps, seed DB — SWE tasks can take minutes to build).
  2. Pre-warm pools — keep a pool of already-built idle environments; reset() pops one. Hides latency, costs standing memory/CPU, and is how most hosted providers actually serve fleets.
  3. Snapshot / restore — checkpoint the running world (filesystem + memory) after setup, then restore in ~100ms per episode. Morph Cloud's Firecracker snapshots are the exemplar; the expensive setup runs once, and every episode boots from the frozen instant.

Snapshotting has a second, more interesting consequence: fork. If you can restore a snapshot, you can restore it N times — branching a live trajectory into parallel continuations from the same mid-episode state. That primitive is exactly what search-flavored RL wants: MCTS-style expansion over real environment states, GRPO groups launched from a shared prefix state instead of re-executing the prefix G times, and cheap counterfactuals ("what if the agent had run the tests here?"). Classic RL got this free from cheap simulators; systems RL had to rebuild it as infrastructure.

4. Provider Abstraction & Env-as-a-Service

Nobody wants their environment code married to one vendor's sandbox API, so 2025–26 grew a provider-abstraction layer, the same way training frameworks abstracted accelerators:

  • SWE-ReX (the runtime under SWE-agent): one "spawn a shell session, run a command" interface with Local/Docker/Modal/AWS Fargate/Daytona backends — the same agent code runs on a laptop or as 100+ parallel rollouts in the cloud.
  • Harbor: containerized tasks executed across Daytona, Modal, and other providers, with the checker and rollout export riding along — the taskset layer handling placement.
  • OpenEnv container providers: the spec separates the env server from where it runs (local Docker, Kubernetes, hosted sandbox), so the trainer's from_docker_image() doesn't change when the fleet moves.

Above raw placement sits env-as-a-service plumbing, the unglamorous half of the OpenEnv/ORS designs: session routing (thousands of episodes multiplexed onto env servers, each episode's step() calls reaching its world), crash containment (an env that dies takes one episode, and the trainer must treat the loss as censored data, not silently drop it), and backpressure when the fleet saturates. This is the same shape as the sticky-session routing the verl agentic page covers for tool servers, promoted to a first-class service.

5. The Utilization Problem — Oversubscription Math

Now the systems tension that shapes every agentic-RL trainer. During rollout, a trajectory alternates two phases: generation (the policy emits an action — GPU busy) and the environment step (code runs, tests execute, pages load — GPU idle for that trajectory). Let \(x = t_{\text{env}}/t_{\text{gen}}\) be their ratio per turn. A trajectory only occupies the GPU a fraction \(1/(1+x)\) of its wall time — for a coding env where generation takes 2s and the test suite 20s, that's 9%.

The fix is the same as any latency-hiding problem: oversubscribe. Run \(k\) concurrent trajectories per GPU batch slot; expected slot occupancy is

\[ U(x; k) \;=\; \min\!\left(1,\; \frac{k}{1+x}\right). \]
k = 1 (no oversubscription) k = 2 k = 8 k = 32

GPU slot occupancy \(U = \min(1, k/(1+x))\) vs. the env-to-generation latency ratio \(x\). Without oversubscription (dashed) utilization collapses as soon as the environment is slower than generation. Each curve stays saturated exactly until \(x = k - 1\): to hide a 7×-slower environment you need ~8 trajectories per slot; a 31×-slower one needs ~32. That is why agentic trainers run hundreds of concurrent episodes per GPU — and why Qwen3-Coder's fleet is 20k environments, not 20k GPUs.

Three real-world corrections to the idealized curve, each pushing toward more machinery:

  • Variance, not just means. Env steps are heavy-tailed (most commands are fast; occasionally the build takes 10 minutes). Batch-synchronous rollouts stall on the straggler, so schedulers detach trajectories from batches — continuous batching on the inference side, fully async episode management on the env side (Kimi K2's orchestrator, verl's AgentLoop).
  • Oversubscription costs staleness. More in-flight episodes means episodes finishing under older policy weights — the exact off-policy trade the Async RL page prices out with importance-sampling corrections. The env fleet sets how much asynchrony you need; the trainer decides how much it can afford.
  • Memory bounds \(k\). Every in-flight trajectory pins KV-cache on the inference engine, so \(k\) is capped by rollout-engine memory long before the env fleet runs out of containers — one more place the placement trade-offs bite.
The mental model

The environment fleet is a latency-hiding machine wrapped around untrusted code: isolation chosen per-risk (container → gVisor → microVM), reset made O(100ms) by snapshots (and fork turned into a search primitive), providers abstracted so the fleet is portable, and concurrency \(k\) sized to the env-to-generation ratio \(k \gtrsim 1 + t_{\text{env}}/t_{\text{gen}}\) — with the resulting staleness handed to the async-RL machinery to correct.
