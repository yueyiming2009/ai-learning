GRPO Training Walkthrough in VeRL

One complete GRPO step on LLaMA-7B across 8 GPUs — group rollout batching, the z-score advantage reshape, the k3 KL estimator, and exactly what disappears relative to PPO.

This page assumes you've read the PPO walkthrough (tensor shapes, TP/DP, hybrid engine, FSDP, flash attention). It focuses on what changes. Algorithm background: GRPO; monitoring: Monitoring & Diagnosis.

1. Concrete Configuration

1.1 Model and Hardware

Same as the PPO walkthrough: LLaMA-7B (\(H\)=4096, \(L\)=32, \(V\)=32 000) on 8 GPUs (TP=2, DP=4). The difference is model count: GRPO needs only the policy and the reference — no critic.

Why G=8? The group mean is the variance-reduced baseline. With G=1 every advantage is zero (only one sample, mean equals itself). With G=4–8 the MC baseline is stable enough; diminishing returns above G=16. Larger G costs more rollout compute and memory — the 128 sequences here already 2× the 64 in the PPO walkthrough.

2. Memory Layout — What Disappears

With TP=2, DP=4, each GPU holds \(1/8\) of every weight shard (FSDP) or \(1/2\) during rollout (AllGathered per TP rank).

ComponentBytes / paramPPO (per GPU)GRPO (per GPU)
Policy weights (bf16) 2 7B × 2 / 8 ≈ 1.75 GB 1.75 GB
Policy optimizer (Adam fp32) 8 7B × 8 / 8 ≈ 7 GB 7 GB
Reference weights (bf16, frozen) 2 1.75 GB (shared via LoRA) 1.75 GB (shared via LoRA)
Critic weights (bf16) 2 1.75 GB 0 — eliminated
Critic optimizer (Adam fp32) 8 7 GB 0 — eliminated
Total (approx) ~17.25 GB ~10.5 GB (−39%)

The saving is almost entirely in optimizer state — Adam's \(m\) and \(v\) vectors cost 4× the weight memory in fp32. Dropping the critic frees ~8.75 GB per GPU, enough to raise \(G\), extend the response length, or reduce the TP degree.

3. Phase-by-Phase Walkthrough

GRPO has 7 phases versus PPO's 10. The three that disappear are the critic forward pass (Phase 6), the GAE backward scan (part of Phase 7), and the critic update (Phase 9). The advantage computation is replaced by a cheap CPU z-score, and the KL penalty moves from the reward signal into the actor loss.

Phase 1

Data Loading and Group Expansion

Ray controller samples B=16 prompts and expands each G=8 times before scatter.

# Controller CPU:
prompts          : (16, 512)  int64
prompts_expanded : (128, 512) int64   ← repeat_interleave(prompts, G=8, dim=0)

# Each DP rank receives its slice:
prompts_local : (32, 512)   ← 128 / DP=4   per DP rank

The interleave ordering matters for the z-score step: prompt 0's 8 completions must land in consecutive rows so they can be grouped back together with a simple .view(B, G). VeRL preserves this ordering through all phases.

Phase 2

Group Rollout — G Completions per Prompt

Each DP rank generates R=512 tokens for its 32 sequences. Communication is identical to the PPO rollout (TP AllReduce per layer per decode step) — only the batch dimension is larger.

Prefill and decode (same ops as PPO, larger batch)

# Per DP rank (32 sequences, TP=2 split):
x_prefill : (32, 512, H=4096)

# Decode: 512 steps, each:
x_decode  : (32,   1, H=4096)
KV_cache  : (32, 16, P+t, 128)  bf16  ← grows each step
NCCL — AllReduce (SUM) × 2 per layer · TP group (NVLink)
Prefill: (32, 512, 4096) bf16 · 128 MB per AllReduce · 32 layers × 2 = ~8 GB
Decode: (32, 1, 4096) bf16 · 256 KB per AllReduce · 512 steps × 32 layers × 2 = ~8 GB

Phase 3

Reward Scoring

One scalar reward per sequence. Either a rule-based verifier (exact-match for math, unit tests for code) or a learned reward model forward pass.

# Rule-based (no GPU):
rewards : (128,)  float32   ← e.g., 1.0 if correct, 0.0 if wrong

# Learned RM (GPU forward, same structure as PPO Phase 3):
rewards : (128,)  float32   ← scalar from reward head on final response token
GRPO requires only outcome rewards — one scalar per complete response. Process supervision (per-step rewards) is also supported (see grpo.html §3) but changes the advantage formula; most production uses are outcome-only.
Phase 4

Reference Policy Log-Probs

Non-autoregressive forward over all 128 sequences to get \(\log\pi_\text{ref}(o_{i,t})\) for the KL penalty. Same computation as PPO Phase 5 with a larger batch.

# Per DP rank micro-batch of 8 sequences:
ref_log_probs_local : (8, 512)  float32

# 3-step distributed log-prob (no full-vocab V=32000 materialization):
m_global   = AllReduce(max(logits_local, dim=-1), op=MAX)    # (8, 512)
sum_global = AllReduce(exp(logits_local - m_global).sum(-1), op=SUM)  # (8, 512)
log_prob   = AllReduce(log_prob_of_target, op=SUM)           # (8, 512)
NCCL — AllReduce × 2 per layer (TP) + 3 × AllReduce per token (log-prob)
Per-layer: (8, 1024, 4096) bf16 · 64 MB each · 32 layers × 2 = ~4 GB (per micro-batch)

Global output on controller: ref_log_probs : (128, 512) float32

Eliminated PPO Phase 6 — Value Estimation (Critic): no critic network exists; no forward pass, no AllReduce, no value tensor.
Phase 5

Group-Relative Advantage — The Z-Score Reshape

Controller CPU. No GPU, no NCCL. Replaces GAE entirely.

The critical step is reshaping the flat (128,) reward vector into (16, 8) — 16 prompts × 8 completions — so the group mean and std are computed within each prompt's group, then broadcasting the per-sequence advantage back to per-token shape.

Core computation
# rewards : (128,)  — one scalar per sequence
rewards_g = rewards.view(B=16, G=8)          # (16, 8)
mean_r    = rewards_g.mean(dim=1, keepdim=True)  # (16, 1)
std_r     = rewards_g.std(dim=1, keepdim=True).clamp(min=1e-8)  # (16, 1)

adv_g = (rewards_g - mean_r) / std_r         # (16, 8)  — z-scores
adv_flat = adv_g.view(128)                   # (128,)

# Broadcast: all tokens of sequence i get advantage adv_flat[i]
advantages = adv_flat.unsqueeze(1).expand(-1, R=512)  # (128, 512)
advantages = advantages * response_mask               # (128, 512) — zero padding

No whitening across the batch. PPO whiten() standardizes advantages to zero mean and unit variance across the whole batch to calibrate the clip threshold. GRPO's z-score already operates within each group, so the global distribution is roughly zero-mean by construction. Batch-level whitening on top would re-scale advantages and distort the group-relative signal — verl skips it for GRPO.

Edge case: all-same-reward group. If every completion in a group gets identical reward, std_r ≈ 0 and all advantages are 0/ε ≈ 0 after clamping. That prompt contributes no gradient this step — a "dead batch." The clamp(min=1e-8) prevents NaN; the batch just makes no progress on those prompts. Monitor within-group reward std (see monitoring §7).

Eliminated PPO Phase 7 — GAE backward scan: no critic values, no \(\delta_t\) recurrence, no returns tensor. Advantage is just the broadcast z-score above.
Phase 6

Actor Update — Clipped Surrogate + KL Penalty

All 8 GPUs. K=4 epochs, mini-batch per DP rank = 8 sequences (32 global / DP=4).

6a. FSDP AllGather + forward pass (same as PPO)

NCCL — AllGather (DP, InfiniBand) + AllReduce (TP, NVLink) per layer
AllGather: ~56 MB per layer · 32 layers = ~1.8 GB per forward pass
TP AllReduce: (8, 1024, 4096) bf16 · 64 MB each · 32 layers × 2 = ~4 GB

6b. GRPO loss

# new_log_probs : (8, 512)  from the current forward pass
# old_log_probs : (8, 512)  rollout log-probs (stored from Phase 2)
# ref_log_probs : (8, 512)  from Phase 4
# advantages    : (8, 512)  from Phase 5

log_ratio = new_log_probs - old_log_probs     # (8, 512)
ratio     = log_ratio.exp()                   # (8, 512)  importance ratio ρ_{i,t}

# Clipped surrogate (identical to PPO):
surr1     = ratio * advantages
surr2     = ratio.clamp(1 - eps, 1 + eps) * advantages
clip_term = torch.min(surr1, surr2)           # (8, 512)

# k3 KL estimator: u - log(u) - 1 where u = π_ref / π_new
# Always ≥ 0; unbiased estimate of KL(π_new ‖ π_ref)
u         = (ref_log_probs - new_log_probs).exp()  # (8, 512)
kl_est    = u - (ref_log_probs - new_log_probs) - 1  # (8, 512)  u - log(u) - 1

per_token = (clip_term - beta * kl_est) * response_mask  # (8, 512)
loss      = -per_token.sum() / response_mask.sum()        # scalar  (token-mean)
KL placement. PPO folds the KL into the reward signal as a per-token penalty on top of \(R_t\), then computes advantages with GAE over those penalized rewards. GRPO puts the KL directly in the loss — it has no GAE to fold it into, and the k3 estimator (\(u - \log u - 1\)) is always non-negative, preventing the KL from acting as a reward bonus on any individual sample. The net effect on the gradient is similar, but the implementation differs.

6c. Backward + optimizer (same as PPO Phase 8)

NCCL — AllReduce (TP) + ReduceScatter (DP) per layer
TP AllReduce: ~4 GB (same as forward) · DP ReduceScatter: ~1.8 GB (FSDP re-shards grads)

K=4 epochs total: the 128 sequences are re-used for 4 optimizer steps (16 mini-batch passes of 32 sequences each). Each pass recomputes new_log_probs from the current (updated) policy weights. Since there's no critic whose value predictions go stale, GRPO tolerates more epochs than PPO before gradient variance dominates.

Shared-prefix redundancy. The rollout engine computes the shared prompt KV once per group (prefix caching), but this actor update recomputes it for every sequence — the same prompt prefix goes through forward and backward G times per pass. Schedule-level shared-prefix reuse (Li, Sheng et al., 2026 — co-authored by verl's lead) reorders the schedule: prefix forward once (cache K/V, keep the autograd graph), suffixes run as ordinary microbatches reading the cached K/V while accumulating gK/gV, then prefix backward once on the accumulated gradients. The reorder is exact up to floating-point, because the prefix backward is a vector-Jacobian product — linear in the incoming gradients. Payoff scales with prefix ratio and G: up to ~4.4× for prefix-dominant workloads (fixed-context RAG, video), only ~1.17× for short-prompt math/code.
Eliminated PPO Phase 9 — Critic Update: no value regression loss, no separate critic backward, no second optimizer step.
Phase 7

Weight Synchronization

After K=4 epochs, push updated actor weights to the rollout engine. Simpler than PPO: only one model to sync (no critic).

# verl hybrid engine (same GPU, time-multiplexed):
1. sleep_rollout_replicas()
2. For each TP rank:
     for layer in actor.layers:
         AllGather(actor.W_Q_shard) → W_Q_full   # reconstruct from FSDP shards
         rollout_engine.update_layer(W_Q_full)   # push to vllm/SGLang
3. wake_rollout_replicas()

# Miles (separate SGLang server):
actor_trainer.broadcast_weights_to_rollout_server()
# HTTP POST with new weight tensors; rollout server hot-swaps them without restart
NCCL — AllGather (DP, InfiniBand) per weight tensor during sync
7B params × 2 bytes = 14 GB total · DP=4 shards = ~3.5 GB AllGather per DP rank

GRPO's actor-update communication is larger in total (K=4 epochs × 16 mini-batch passes vs. PPO's K=1 epoch × 4 passes) but each individual pass is cheaper (no GAE recomputation, no critic forward). The rollout phase is heavier per step (batch size 128 vs 64) but prefill/decode AllReduce volumes scale with sequence count, not sequence length — doubling \(N\) doubles the allreduce tensor width but not the number of calls.

6. Dr.GRPO — Loss Aggregation in Practice

Standard GRPO averages the per-token clipped term over each sequence's response tokens, then averages over sequences. Longer correct sequences contribute proportionally more gradient — a length bias that can push the policy toward verbosity.

Standard GRPO loss (token-mean)

# per_token : (8, 512)  — already masked
loss_per_seq = per_token.sum(dim=-1) / response_mask.sum(dim=-1)  # (8,) token-mean per seq
loss = -loss_per_seq.mean()                                        # scalar

Dr.GRPO loss (token-sum, constant divisor)

D = 1000.0  # constant — e.g. mean sequence length at start of training

loss_per_seq = per_token.sum(dim=-1)  # (8,) token-SUM, no division by length
loss = -loss_per_seq.mean() / D       # divide by constant, not by variable token count

Each sequence contributes gradient proportional to its raw token-sum (not normalized by its own length), so a 200-token correct answer and a 400-token correct answer with the same reward contribute the same gradient per token on average — length neutrality.

Dr.GRPO also disables std normalization in the advantage:

# Standard GRPO:
adv_g = (rewards_g - mean_r) / std_r    # z-score

# Dr.GRPO:
adv_g = rewards_g - mean_r              # mean-centered only, no std division
