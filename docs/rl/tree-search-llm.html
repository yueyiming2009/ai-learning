Tree Search for LLMs

Spend more compute at inference time instead of at training time. Search over reasoning steps using a process reward model as the value function — the AlphaZero idea applied to language.

🎓
David Silver's Reinforcement Learning Course (DeepMind/UCL)

The planning and search ideas here extend Lectures 8 (simulation-based search) and 10 (MCTS in classic games) to the LLM setting.

A trained LLM generates one token at a time, left to right, committed to each choice before seeing its consequences. On hard problems — multi-step math, formal proofs, competitive coding — this greedy commitment is the bottleneck. The model knows how to reason; it just makes mistakes it could catch with a little more thought.

Tree search at inference time decouples generation from commitment: explore multiple continuations, score them with a reward model, and keep only the promising ones. The rest of this page is about how to do that well.

1. LLM Generation as a Tree Search Problem

Recall the MDP formulation of LLM generation. Each state \(s_t\) is the prompt plus tokens generated so far. Each action is either:

  • Token-level: one token per step (huge branching factor, sparse reward). Intractable to search directly.
  • Step-level: one reasoning step per action (smaller branching factor, PRM can score each step). This is what modern LLM tree search targets.
Q: "Solve: 3x + 7 = 22" │ ├── Step 1a: "Subtract 7 from both sides → 3x = 15" PRM: 0.92 ✓ │ ├── Step 2a: "Divide both sides by 3 → x = 5" PRM: 0.97 ✓ │ │ └── "Answer: x = 5" ← correct │ └── Step 2b: "Multiply by 3 → x = 45" PRM: 0.04 ✗ │ └── Step 1b: "Add 7 to both sides → 3x = 29" PRM: 0.08 ✗ └── "Answer: x = 29/3" ← wrong

The tree has branching at each reasoning step. Without a value function we can't tell whether a branch is worth following until we reach the answer — which means wasting compute on dead ends. A process reward model (PRM) solves this: it scores each intermediate step, giving us AlphaZero's \(V_\theta(s)\) for language.

2. Reward Signals — ORM vs PRM

Outcome Reward Model (ORM)

Score the final answer

Takes the complete response and returns a scalar quality score.

  • Cheaper to label: just need "correct / wrong"
  • Good for: Best-of-N sampling, reranking
  • Bad for: guiding search mid-generation — no signal until the end
  • Analogous to AlphaZero's game outcome \(z\)
Process Reward Model (PRM)

Score each reasoning step

Takes a partial reasoning chain and returns a score at each step boundary.

  • Expensive to label: requires per-step human labels or automatic annotation
  • Good for: MCTS, beam search — guides search before the answer is complete
  • Bad for: open-ended tasks without step boundaries
  • Analogous to AlphaZero's value head \(V_\theta(s)\)
What a PRM actually predicts

A PRM is trained to predict \(P(\text{final answer correct} \mid \text{prefix up to step } k)\). Given a state \(s_k\) — the problem statement plus the first \(k\) reasoning steps — it returns a scalar in \([0, 1]\). This is exactly the value function \(V^\pi(s_k)\) from the RL theory: the expected return (correctness) from this partial state under the policy (the LLM). You can aggregate per-step PRM scores as a product (each step's probability of being correct) or take the minimum across steps (the weakest link).

3. Best-of-N — The Simplest Baseline

Sample \(N\) complete responses independently from the LLM, score each with an ORM (or verify directly), and return the highest-scoring one.

Best-of-N
candidates ← [] for i in 1..N: response_i ← LLM.generate(prompt) # full rollout score_i ← ORM(prompt, response_i) candidates.append((response_i, score_i)) return max(candidates, key=score)

Best-of-N is essentially Monte Carlo for the full sequence — each call is an independent rollout, and we pick the maximum instead of averaging. Its strength grows predictably with \(N\):

Best-of-N expected performance
\[ \mathbb{E}\!\left[\max_{i=1}^N r_i\right] \;\text{ is monotonically increasing in } N \]

assuming i.i.d. samples \(r_i \sim p_\theta(\cdot \mid x)\), where \(r_i\) is the score of response \(i\). The gain diminishes (the max of \(N\) i.i.d. samples grows as \(O(\log N)\) for light-tailed distributions), but is never negative.

Best-of-N compute scales with the number of complete responses. If a response is 512 tokens, \(N=64\) means 32,768 tokens just to pick one answer. Beam search and MCTS amortize this by pruning bad branches early.

4. Beam Search with a PRM

Maintain a beam of \(K\) partial reasoning chains. After generating each step, score every candidate with the PRM and keep only the top-\(K\).

Beam search with PRM (step level)
beam ← [(prompt, score=1.0)] # K=beam_width candidates while not all terminated: candidates ← [] for (chain, score) in beam: ── expand ─────────────────────────────────────── steps ← LLM.sample_steps(chain, n=M) # M continuations per beam for step in steps: new_chain ← chain + step new_score ← PRM(new_chain) candidates.append((new_chain, new_score)) ── prune ──────────────────────────────────────── beam ← top_K(candidates, key=score) return best(beam, key=score)

Beam search is more compute-efficient than Best-of-N because it prunes bad prefixes before they generate the full response. The tradeoff: the beam can collapse — all \(K\) candidates converge on the same wrong path if the early PRM scores are misleading. MCTS avoids this via explicit exploration.

5. MCTS for Reasoning

Apply the full MCTS algorithm where each node is a partial chain and each edge is a reasoning step. The PRM replaces the rollout — instead of completing the response randomly (expensive), evaluate the partial chain directly.

MCTS for LLM reasoning
root ← Node(state=prompt, N=0, Q=0) for simulation in 1..K: ── selection ──────────────────────────────────── node ← root while node is fully expanded and not terminal: node ← argmaxchild PUCT(child) # LLM prior + Q + exploration ── expansion ──────────────────────────────────── if node is not terminal: step ← LLM.sample_next_step(node.state) child ← Node(state=node.state + step) node.add_child(child) node ← child ── evaluation ─────────────────────────────────── value ← PRM(node.state) # no rollout needed ── backpropagation ────────────────────────────── while node is not null: node.N += 1 node.Q += (value − node.Q) / node.N # running average node ← node.parent return best child of root by Q or N
The three ingredients and where they come from
  • LLM as prior \(P_\theta(\text{step} \mid \text{chain})\) — the language model proposes the next reasoning step, exactly as AlphaZero's policy head proposes moves. PUCT selection uses this to weight exploration toward likely steps.
  • PRM as value function \(V_\theta(s)\) — evaluates the partial chain without completing it, replacing MCTS's random rollout. This is the critical speedup.
  • MCTS as policy improvement — concentrates simulations on the promising branches the greedy LLM would have missed. The visit count distribution \(\pi_\text{MCTS}\) is a better policy than the raw LLM.

Comparing the three approaches

Best-of-N

Search: None — N independent rollouts

Reward needed: ORM (outcome only)

Efficiency: Low — N × full response length

Best for: Simple tasks, fast iteration, any task with a verifier

Beam Search + PRM

Search: Width-K, depth-first

Reward needed: PRM (per-step)

Efficiency: Medium — prunes early, but no backtracking

Best for: Tasks with clear step boundaries, latency-sensitive

MCTS + PRM

Search: Adaptive tree, exploration + exploitation

Reward needed: PRM (per-step)

Efficiency: High — concentrates compute on hard subproblems

Best for: Complex multi-step reasoning, when PRM is reliable

6. Training a Process Reward Model

A PRM needs step-level labels — for each step in a solution, was it correct? Three annotation strategies:

StrategyHowScale / Quality
Human labelling Human annotators mark each step as correct or incorrect High quality, expensive. OpenAI's PRM800K: 800K step labels from 12 annotators on 75K solutions
Automatic via MC rollouts For each step, complete the solution many times with random rollouts. If \(\ge\) 50% rollouts reach the correct answer, label the step as correct (Math-Shepherd, Lightman et al.) Scalable, noisier. Step label = \(\hat{P}(\text{correct} \mid \text{prefix})\) estimated by MC sampling
Distillation from a stronger model Use a larger model (or formal verifier) to judge each step Cheap if verifier exists; limited by verifier quality

The MC rollout method is particularly interesting: it estimates \(V^\pi(s_k)\) by running many completions from step \(k\), computing the empirical fraction that succeed. This is exactly Monte Carlo value estimation applied to LLM reasoning. The PRM is then trained to predict these MC-estimated labels — a supervised distillation of the MC value estimate into a fast neural network.

This creates a virtuous loop: a strong LLM generates rollouts to label the PRM; the PRM enables better search; better search generates better training data for the LLM. This is the AlphaZero self-play cycle applied to language.

7. Test-Time Compute Scaling

The fundamental insight behind o1, o3, and DeepSeek-R1: compute spent at inference scales in a predictable way. More search budget → better answers, with a different scaling curve than model parameters.

Training-time scaling
More parameters + data

Chinchilla law: loss scales as \(N^{-\alpha}\) with model size \(N\). Compute-optimal requires scaling both model and data.

Test-time scaling
More search budget

Accuracy scales with \(N\) in Best-of-N, with tree depth in MCTS. Different curve, different sweet spot per problem difficulty.

Compute-optimal inference
Smaller model + more search

Snell et al. (2024): for a fixed inference budget, a smaller model + Best-of-N search can outperform a larger model with greedy decoding.

The key question is: given a fixed inference budget (total FLOPs), how should you allocate it? Generate one long chain-of-thought? Or many short ones and take the best? The answer depends on the task difficulty distribution and the quality of the reward model.

Why reasoning models generate long thinking traces

Models like o1 and DeepSeek-R1 generate explicit "thinking" chains before answering. One interpretation: the model has internalised search — it learned to simulate tree search within its own forward passes, proposing steps, backtracking when they look wrong, and verifying conclusions. The long thinking trace is the linearised output of an implicit search process. Verifiable training signals (math correctness, code tests) trained this behaviour via RL, without explicitly specifying the search algorithm.

8. Search-Generated Data for Training

Search at inference time produces better solutions than greedy generation. Those better solutions can be used as training data, closing the AlphaZero loop:

  1. Run tree search at inference to find solutions the base model couldn't produce greedily
  2. Filter to solutions verified as correct
  3. Fine-tune the model on these solutions
  4. The improved model produces better rollouts → better training data → repeat
MethodMechanismAlphaZero analogue
STaR (Zelikman et al.) Generate rationales; keep only those that reach the correct answer; fine-tune on them Self-play: correct solutions are the training signal
ReST (Gulcehre et al.) Best-of-N → score with reward model → fine-tune on high-reward outputs → repeat Self-play + ORM-scored selection + policy update
RLVR (DeepSeek-R1-Zero) PPO/GRPO with outcome-based verifier reward; no supervised rationale data needed AlphaZero without a PRM: game outcome verifier replaces value network
rStar (Microsoft) Mutual consistency: generate N solutions, cross-check for agreement, use consistent ones as training data Ensemble verification replacing a game simulator
The key constraint

All of these methods require a reliable verifier — something that can tell correct from incorrect solutions without human annotation. This is easy in math (exact-match answer), code (unit tests), formal proofs (proof checker), and board games (did you win?). It is hard for open-ended generation (helpfulness, style, nuance) — which is exactly why RLHF with human preference labels remains necessary for the latter.

9. Where LLM Search Differs from AlphaZero

Transplanting MCTS from board games to language isn't free. Several assumptions break:

AlphaZero assumptionLLM realityConsequence
Perfect, fast simulator — play out games in milliseconds LLM inference is expensive — one forward pass per token Tree search budgets are much smaller; each node expansion costs real GPU time
Clean discrete states — every board position is uniquely identified Text is open-ended — "let me reconsider" is a valid action at any step State space is unbounded; step boundaries need heuristic definition
Exact ground-truth reward — win/loss is unambiguous ORM/PRM is noisy — reward hacking is possible Search can exploit PRM errors, finding high-scoring but wrong answers
Two-player zero-sum — self-play provides diverse opponents Single agent vs. a problem — diversity must come from sampling temperature or different prompts The self-play diversity mechanism doesn't directly apply
Symmetric game — both players are the same model Verifier and generator may be separate models at different capability levels Mismatched verifier quality creates different failure modes than game mismatch

Despite these differences, the core insight transfers cleanly: a fast value estimate at each step enables planning, and planning produces better solutions than greedy generation. The engineering challenges are real but solvable — the field has moved from "MCTS for LLMs is impractical" to deploying it in production reasoning systems within about two years.

Summary

PRM = value function

\(V(s_k) \approx P(\text{correct} \mid \text{prefix}_k)\) — enables planning without completing the response

Best-of-N

Simplest baseline: N independent rollouts + ORM reranking. No PRM needed, linearly more expensive

Beam search

K partial chains, PRM-pruned at each step. Efficient but no exploration or backtracking

MCTS

Full UCT/PUCT tree over steps; LLM = prior, PRM = value. Best for hard, multi-step problems

PRM training

Human labels or MC rollout estimates for \(P(\text{correct} \mid \text{prefix}_k)\); MC is cheap and scalable

The AlphaZero loop

Search finds better solutions → verified solutions become training data → stronger model → better search
