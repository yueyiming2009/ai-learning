Task Generation, Curriculum & Contamination

Where the tasks come from: back-translating software history into verified tasks, replication training against reference implementations, fully synthetic tool worlds — and the two disciplines that keep a generated task supply usable: curriculum and contamination control.

Last page of the RL Environments series (landscape). It leans on the reward-design page throughout: generation is only useful if each generated task carries a trustworthy verifier, and curriculum exists to serve the pass-rate curve derived there.

1. The Task Supply Problem

RL consumes tasks. A supervised example can be revisited for many epochs; an RL task is spent once the policy saturates it — when the pass rate approaches 1, the signal goes to zero and the task is mileage-exhausted. Meanwhile hand-authoring is expensive: market rates run $200–$2,000 per task, and expert-built app replicas cost six figures. A frontier RL run needs more tasks, and harder tasks, every month.

The observable consequence in 2026: the supply went from hundreds of hand-built environments to hundreds of thousands of generated tasks in about a year — Prime Intellect's 365k-task API, OpenReward's ~4.5M-task catalog. That two-orders-of-magnitude jump did not come from hiring more task authors. It came from three generation strategies, §2–§4, each defined by where it gets ground truth for the verifier — because generating a task is easy; generating a task whose grader you can trust is the whole problem.

2. Mining Reality — Back-Translation from Software History

The richest free source of verified tasks is version control. Every commit in every real repository is a certificate: some change was needed, and this diff satisfied it. Generation pipelines run that certificate backwards — back-translation:

  1. Pick a commit from a real repo (a bug fix, a feature).
  2. Rewind the repo to the parent state — that's the environment snapshot.
  3. Generate the task description from the diff (an LLM writes the "issue" the commit resolves) — the back-translation step.
  4. Derive the verifier: tests added by the commit, or newly generated tests that the post-commit code passes and the pre-commit code fails.

SWE-Gym (2024) proved the recipe with 2,438 human-issue tasks; R2E-Gym's SWE-Gen (COLM 2025) removed the human-issue dependency entirely — synthesizing issues and tests directly from commits, no GitHub issue or human-written test required — yielding 8,100+ executable tasks. Scaled industrially, the same idea produced Prime Intellect's ~198k software tasks across 20+ languages, and Endless Terminals (Jan 2026) did the analogous thing for terminal tasks, procedurally generating them at scale rather than curating benchmarks.

The catch is verifier trust: machine-generated tests are weaker than human ones — they can under-specify the fix or accidentally accept the broken state. R2E-Gym's answer is the hybrid verifier — execution-based and execution-free checks voting — plus filtering the generated pool for tasks whose checks discriminate cleanly. Generated supply and verifier ensembles arrived together because neither works alone.

3. Replication Training — the Reference as the Verifier

Mechanize's "replication training" solves verifier trust differently: task = recreate an existing piece of software from its specification. The original implementation is the ground truth — its observable behavior on any input is the reference the agent's version is checked against. That buys three things:

  • Automatic verification at any scale — differential testing against the reference needs no human grading and no hand-written suite;
  • Unbounded difficulty — pick a bigger target (a function → a module → a CLI tool → a service) and the task hardens without any authoring;
  • Long-horizon realism — replicating real software exercises exactly the sustained multi-step work agentic RL wants to train.

The limits mirror the strengths: replication only covers "software whose behavior is the spec," the agent may see the original in its pretraining data (a contamination problem, §6), and behavioral equivalence is only as strong as the input distribution you test on.

4. Synthetic Worlds — Simulated Tools at Scale

The third strategy abandons real-world grounding entirely. For tool-use training, Kimi K2's pipeline simulated thousands of MCP-style tools and synthetic domains — invented APIs with invented state — then generated agents, tasks, and rubrics inside that simulated universe, with multi-turn trajectories rolled out and filtered by quality judges before training. When the world is synthetic:

  • Consistency substitutes for truth — the simulated tool's responses just have to be internally coherent and the task checkable against the simulated state;
  • Coverage is designable — you can enumerate tool-use patterns (retries, errors, multi-tool workflows) that are rare in the wild but must be learned;
  • Cost collapses — a simulated CRM is a prompt and a state dict, not a $300k replica. The trade is fidelity: policies can overfit simulator quirks, which is why labs mix synthetic tool worlds with real verifiable environments rather than replacing them.

5. Curriculum — Serving the Pass-Rate Curve

A generated pool spans difficulty from trivial to impossible, but the useful-group curve says training only extracts signal at moderate current-pass-rate. Curriculum is the machinery that keeps the sampled distribution in that band while the policy moves:

  • Difficulty ordering. Sort the pool (by model-measured pass rate, task size, horizon) and advance as the policy improves — the classic curriculum, now applied to task sampling weights rather than a fixed syllabus. The one-shot version is a pass-rate filter on the training set itself. Agent Lightning v1.0's SWE-smith pipeline is a clean worked example: start from 59,136 tasks, drop 18,033 with empty problem statements, 1,265 whose problem branch is missing from the image, and any task with more than 200 tests; then roll the base policy four times per task, discard everything solved 4/4, keep the mixed-outcome tasks (~5K), and deliberately add back 1K tasks failed 4/4 so the set does not become a victory lap — ~6K train / 400 test, enough for a 14.6-point SWE-bench Verified gain on a 9B model.
  • Horizon curricula. AgentGym-RL's ScalingInter-RL: start episodes with short interaction budgets and progressively lengthen them, so early training learns single-skill competence before long-horizon credit assignment (why that's hard) is even in play.
  • Adaptive samplers. Track per-task pass rates online; oversample tasks near the signal peak, retire saturated ones. The sandbagging caveat applies — any loop from policy behavior to task selection is optimizable by the policy.
  • Splits as protocol. The Open Reward Standard makes train/eval splits and curriculum stages first-class protocol objects, so a hosted environment can refuse to train on its eval split — versioned, like datasets learned to be.

6. Contamination — When Training Envs Meet Eval Benchmarks

The same forces that generate training tasks corrupt evaluation. The failure modes:

  • Benchmark-to-gym reuse. The natural lifecycle — a benchmark (Terminal-Bench) generalizes into a training framework (Harbor) — means yesterday's held-out eval is today's training distribution. Scores on any benchmark whose tasks circulate as training environments measure familiarity, not capability.
  • Shared upstream sources. Mined tasks (§2) come from the same repos benchmarks mine — training on generated PyTorch-repo tasks then reporting SWE-bench-style numbers on the same repos is contamination one hop removed, even with disjoint instances.
  • Pretraining leakage. The agent may have memorized the repo, the issue thread, or (for replication) the reference implementation itself from pretraining text — contamination that no split of the RL task pool can fix.

The defenses are the dataset world's, upgraded: strict provenance metadata on generated pools (which repos, which date cutoffs), repo-level (not instance-level) train/eval separation, private eval suites — and most structurally, dynamic generation: if fresh instances can be minted on demand from held-out or post-cutoff sources, the eval can always outrun memorization. Procedural generation, introduced to solve supply (§2), turns out to be the contamination fix too — the two problems share a solution.

The mental model

Task generation is verifier generation — the three scalable sources are distinguished by where ground truth comes from: software history (back-translation), a reference implementation (replication), or internal consistency (synthetic worlds). Curriculum keeps sampled difficulty on the productive part of the pass-rate curve as the policy moves, and contamination control — provenance, repo-level splits, dynamic generation — keeps the eval meaning something after the gym ate the benchmark.
