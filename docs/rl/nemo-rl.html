NeMo RL — NVIDIA's Scalable Post-Training Framework

The Ray-orchestrated successor to NeMo-Aligner: a single-controller driver over isolated worker groups, a swappable training backend (PyTorch DTensor for the small end, Megatron-Core for the large end), vLLM generation that colocates or disaggregates, and an environment interface built for multi-turn RL — plus how it compares to verl.

Read this beside verl Architecture and TRL. NeMo RL sits at the opposite end of the scale axis from TRL: it is the framework whose whole reason to exist is the same recipe from 1 GPU to a thousand, on the NVIDIA Megatron stack. The Landscape page places it among the rest.

1. What NeMo RL Is

NeMo RL (NVIDIA-NeMo/RL) is NVIDIA's open-source library for LLM post-training — SFT, DPO, reward modeling, and online RL (GRPO and friends) — and the replacement for the older NeMo-Aligner. Aligner was tightly welded to the NeMo/Megatron model classes; the headline change in NeMo RL is that the model backend is a pluggable detail. A run is described once (a YAML config plus a ~200-line driver script), and the same run can execute through plain PyTorch on a handful of GPUs or through Megatron-Core with TP/PP/EP/CP on a cluster.

As with the TRL page, this is about the engineering; the algorithms live at GRPO, DPO, PPO, and Distillation. The thing worth understanding here is how NeMo RL decomposes an RL job into pieces that can each be swapped and placed independently.

2. The Stack — Five Layers

NeMo RL is a layered design, and almost every design question maps to one layer:

AlgorithmA plain Python loop in nemo_rl/algorithms/ — grpo_train(), dpo_train(), sft_train(). Runs in the driver process. Calls the layer below through interfaces, never touches GPUs directly.
LossA callable object: ClippedPGLossFn, DPOLossFn, NLLLoss, DistillationLossFn. Signature is loss_fn(next_token_logits, data, global_valid_seqs, global_valid_toks) — the global counts let token-level vs sequence-level normalization be exact across data-parallel ranks.
InterfacesPolicyInterface (train / get logprobs / save / refit generation weights), GenerationInterface (generate, sleep/wake), EnvironmentInterface (step). The algorithm only knows these.
WorkersRay actors implementing the interfaces: DTensorPolicyWorker, MegatronPolicyWorker, VllmGenerationWorker, environment actors. Grouped into a RayWorkerGroup that fans a method call out to every rank and gathers the results.
ClusterRayVirtualCluster — a named slice of the Ray cluster, carved as placement groups (bundles of GPUs per node). Worker groups are created on a virtual cluster; two worker groups on the same cluster are colocated, two on disjoint clusters are disaggregated.

This is the single-controller pattern: one driver holds handles to every worker group and writes the dataflow as ordinary sequential Python, while each worker group executes its slice SPMD-style. It is the same split verl calls "hybrid-flow" (verl Architecture) — NeMo RL arrived at it independently and keeps the two halves cleaner: the driver owns control, the workers own parallelism, and the thing that moves between them is a BatchedDataDict (a dict of padded tensors with shard/gather helpers), never a model.

Isolated environments per worker. Megatron-Core, vLLM, and the plain-PyTorch path pin incompatible dependency sets. NeMo RL sidesteps the usual "one giant image" problem by running under uv and giving each worker type its own virtual environment (py_executable per actor); Ray launches the vLLM actors in a vLLM venv and the Megatron actors in a Megatron venv, on the same node, without either seeing the other's packages.

3. Two Training Backends, One Recipe

The policy worker is where the scaling story lives. Both backends expose the same PolicyInterface, so the algorithm loop and the config above the policy.* block are unchanged when you switch:

DTensor backend (policy.dtensor_cfg)

  • Loads any HuggingFace model directly; no conversion step.
  • Parallelism via PyTorch native DTensor: FSDP2 sharding, optional tensor and context parallel, activation checkpointing.
  • Sequence packing for SFT/RL; LoRA via PEFT-style adapters.
  • Sweet spot: prototyping, dense models up to the tens of billions.

Megatron backend (policy.megatron_cfg)

  • Megatron-Core model classes; the HF checkpoint is imported on first use (Megatron-Bridge).
  • Full TP / PP / EP / CP + data parallel, sequence parallel, distributed optimizer — the 4-D parallelism of TP / PP / EP / CP.
  • Performance features: fused kernels, FP8 training, MoE token dispatch, pipeline-aware microbatching.
  • Sweet spot: large dense and MoE models (DeepSeek-V3-class, Qwen3-MoE) across many nodes.

The practical workflow this enables: bring up a recipe with DTensor on one node while the reward and data are being debugged, then flip policy.megatron_cfg.enabled=true and set the parallel sizes for the real run. Because the loss, the environment, and the generation config are shared, what changes is the arithmetic of where the parameters live — not the experiment.

# same driver, two backends — override YAML keys on the command line
uv run python examples/run_grpo_math.py \
    --config examples/configs/grpo_math_1B.yaml \
    policy.model_name=Qwen/Qwen2.5-1.5B \
    cluster.gpus_per_node=8 cluster.num_nodes=1

uv run python examples/run_grpo_math.py \
    --config examples/configs/grpo_math_8B_megatron.yaml \
    policy.megatron_cfg.enabled=true \
    policy.megatron_cfg.tensor_model_parallel_size=4 \
    policy.megatron_cfg.pipeline_model_parallel_size=2 \
    cluster.gpus_per_node=8 cluster.num_nodes=4

4. Anatomy of a GRPO Step

Here is what grpo_train() does per step, with the worker group each phase lands on. Read it against the generic loop in GRPO:

1 · Refit — policy → generation

If the policy changed last step, push the new weights into vLLM. Colocated: the policy worker hands over CUDA IPC handles to its parameter tensors and vLLM copies them GPU-to-GPU on the same device — no host round-trip. Disaggregated: weights are broadcast over NCCL to the generation nodes. Either way the policy does the FSDP/TP→vLLM-layout reshard, the same problem verl's sharding manager solves (resharding).

2 · Rollout — generation ⇄ environment

The driver takes a batch of prompts, repeats each num_generations_per_prompt times (the GRPO group), and runs the rollout loop: vLLM generates, the environment's step() returns observations/rewards/done flags, and any unfinished trajectories go back to vLLM for the next turn. For single-turn math this is one generate + one verifier call; for a game environment it is a genuine multi-turn episode. Output: a BatchedDataDict of full token sequences, per-token masks (which tokens are the policy's), and a scalar reward each.

3 · Log-probs — policy (and reference)

In colocated mode vLLM goes to sleep (frees its KV cache and weights) and the policy worker wakes. It runs a forward pass over the rollouts to get \(\log \pi_{\theta_\text{old}}(y_t \mid y_{<t}, x)\) — the "old" log-probs for the PPO ratio — and, if a KL term is on, the reference model's log-probs (the reference is the policy worker with the initial weights swapped in, not a separate pool).

4 · Advantages — driver

Pure CPU tensor math on the driver: for each prompt's group, \(A_i = r_i - \bar r\), optionally divided by the group std (normalize_rewards); the per-sequence scalar is broadcast over the response tokens. Any "leave-one-out"/RLOO baseline variant is a one-line change here.

5 · Train — policy

The batch is sharded across data-parallel ranks and microbatched; each microbatch runs through ClippedPGLossFn: \[\mathcal{L} = -\frac{1}{Z}\sum_t \min\!\big(\rho_t A_t,\ \mathrm{clip}(\rho_t, 1-\epsilon_\text{lo}, 1+\epsilon_\text{hi})\,A_t\big) + \beta\,\mathrm{KL}_t\] with \(\rho_t = \pi_\theta/\pi_{\theta_\text{old}}\). The normalizer \(Z\) is global_valid_toks (token-level, DAPO-style) or global_valid_seqs (sequence-level, original GRPO) — computed once globally so that microbatching and DP sharding cannot change the gradient. Multiple optimizer epochs over the same rollouts are allowed (num_epochs), which is where the clip actually bites.

6 · Validate / checkpoint — driver

Every val_period steps the generation pool runs the validation prompts greedily; checkpoints save policy + optimizer (DCP/Megatron format) and optionally an HF-format export for serving.

Notice what is not in the list: there is no critic. NeMo RL's online-RL center of gravity is GRPO-family (group baselines), matching where the field moved after DeepSeek-R1; PPO with a learned value head is what NeMo-Aligner offered and is not the primary path here.

5. The Environment Interface

Where TRL takes a reward function, NeMo RL takes an environment. The difference matters once interactions are multi-turn. The contract is deliberately small:

class EnvironmentInterface(ABC):
    def step(
        self,
        message_log_batch: list[LLMMessageLogType],   # full chat history per sample
        metadata: list[dict],                          # per-sample state (e.g. ground truth, game board)
    ) -> EnvironmentReturn:
        # returns: observations (next user/tool messages), metadata,
        #          next_stop_strings, rewards (float per sample), terminateds (bool per sample)
        ...

    def global_post_process_and_metrics(self, batch) -> tuple[BatchedDataDict, dict]:
        ...   # e.g. compute accuracy over the whole batch for logging

Environments are themselves Ray actors (often CPU-only, many replicas) so slow verifiers or sandboxed code execution scale out independently of the GPUs — the design argued for in Environment Scaling & Sandboxing. The rollout loop in §4 is generic over this interface: a math verifier returns terminated=True after one step; a sliding-puzzle environment returns a new board observation and keeps the episode open; a tool-using agent environment returns tool output as the next observation. Because the loop tracks the message_log rather than a flat token string, the per-token loss mask (train on assistant tokens only, never on tool/user turns) falls out automatically — the same masking requirement discussed in Agentic RL.

6. Async GRPO and Off-Policy Correction

The synchronous step in §4 idles the training GPUs during rollout and the generation GPUs during training; colocation with vLLM sleep/wake hides the memory cost of that but not the time. NeMo RL's async mode (grpo.async_grpo.enabled) disaggregates the two pools and runs them concurrently:

  • Generation workers continuously produce trajectories into a replay buffer; the trainer consumes batches from it as soon as enough are ready.
  • Each trajectory is tagged with the policy version that generated it. max_trajectory_age_steps bounds how stale a sample may be before it is discarded — the policy-lag knob from Async RL.
  • Weight refits happen on the trainer's schedule; vLLM picks up new weights between requests without draining.

Staleness (and, even in sync mode, the vLLM-vs-trainer numerical mismatch) is corrected at the loss: the generation-time log-probs are kept with the sample, and use_importance_sampling_correction multiplies each token's loss by \(\pi_{\theta_\text{old}}^\text{train}/\pi^\text{gen}\) (truncated — the TIS correction), so the gradient is taken with respect to the distribution the trainer actually computes rather than the one the sampler used. This is the same fix the Async RL page derives; NeMo RL ships it as a config flag and reports the train/gen log-prob divergence as a standard metric so you can see when it is needed.

7. NeMo RL vs verl

These are the two frameworks most likely to be compared head-to-head, because they solve the same problem with the same controller model. The differences are in emphasis:

AxisNeMo RLverl
Controller modelSingle-controller driver + Ray worker groups on virtual clustersSingle-controller fit() + multi-controller WorkerGroups on resource pools
Training backendsPyTorch DTensor (FSDP2/TP/CP) or Megatron-CoreFSDP/FSDP2 or Megatron-Core
GenerationvLLM; colocated (sleep/wake, IPC refit) or disaggregatedvLLM or SGLang; colocated (HybridEngine) or disaggregated
Dependency isolationPer-worker uv venvs — first-classOne environment; users manage compatible image
Reward / interactionEnvironmentInterface — multi-turn native, env actors scale separatelyReward managers + agent loop / tool-calling layer (Agentic Training)
AlgorithmsSFT, DPO, RM, GRPO (+async), distillationPPO, GRPO and many variants (DAPO, RLOO, REINFORCE++, …), SFT; broad community recipe set
Async / off-policyAsync GRPO with replay buffer + age bound + IS correctionDisaggregated async + IS correction (Async Training)
Performance ownershipNVIDIA-tuned: FP8, Megatron fused kernels, MoE on the latest GPUs land firstCommunity-driven; broad hardware and engine coverage
Center of gravityReproducible, scalable recipes on NVIDIA hardware (the Nemotron post-training stack)Research velocity — new algorithm papers ship as verl recipes

A fair summary: verl is where new RL ideas appear first; NeMo RL is where the Megatron-scale, FP8, MoE performance work on NVIDIA's own models appears first. Both read the same papers, and recipes port between them with modest effort because the abstractions rhyme.

8. When to Reach for NeMo RL

Choose NeMo RL when…

  • You are on an all-NVIDIA cluster and want the Megatron-Core path with vendor-tuned kernels, FP8, and MoE support.
  • You want to start small (DTensor, one node) and scale the same config to many nodes.
  • Your task is multi-turn — games, tools, agents — and an environment abstraction fits better than a reward function.
  • You need the full post-training sequence (SFT → DPO/RM → GRPO → distillation) in one codebase with one launch convention.

Look elsewhere when…

  • You are on 1–2 GPUs inside the HF ecosystem and want a ten-line script → TRL.
  • You need a specific recent algorithm variant or SGLang rollout that the community has already built → verl.
  • You want SGLang-native, fully async training with a lighter codebase → slime (walkthrough).
  • You are on non-NVIDIA accelerators — the Megatron path is the point of the framework.
The one-line distinction

NeMo RL is verl's controller model with NVIDIA's training stack underneath and a swappable small-scale backend on top — pick it when the target is the Megatron-Core end of the scale ladder and you want the path there to be a config change.
