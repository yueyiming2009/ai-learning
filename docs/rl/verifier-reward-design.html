Verifiers & Reward Design

The grader is the part of the environment the policy actually optimizes against. The spectrum from exact match to LLM judges, why end-state checks beat path checks, how reward hacking became the industry's top concern, and the difficulty-calibration math behind "target a 2–3% pass rate."

Part of the RL Environments series (landscape). Division of labor with Agentic RL: that page covers reward shaping and credit assignment — how a scalar becomes per-token gradients across a long horizon; this page covers the verifier — how a finished rollout becomes that scalar in the first place. The library named after the idea has its own page.

1. The Verifier Is the Product

RL optimizes whatever the reward measures — not what you meant, what it measures. In the environment anatomy, tasks, harness, and runtime set up the problem, but the verifier defines the optimum the policy will relentlessly move toward. Every practitioner survey of the environment economy says the same thing: task volume is easy to buy; verifier quality is the binding constraint, because a bad verifier is not neutral — it actively trains the wrong policy.

The premise this all rests on is RLVR — RL from verifiable rewards (DeepSeek-R1): when the check is objective (a proof checker, a test suite, an exact answer), reward is clean, cheap, and unlimited, and capability gains follow. The whole environment ecosystem is an attempt to manufacture more of the world into verifiable form. The design question of this page: what do you do as tasks drift away from the cleanly checkable end?

2. The Verifier Spectrum

Every grading scheme in use is a point on one axis: how much interpretation stands between the rollout and the scalar. More interpretation buys coverage of fuzzier tasks — and pays for it in gameability and noise.

VerifierHow it gradesFitsFailure mode
Exact match Parse the final answer, compare to ground truth Math, short-form QA Format brittleness; guessable answer spaces
Unit / hidden tests Execute the artifact against a test suite Code, SWE tasks Weak suites reward wrong-but-passing patches; tests can leak
End-state checks Inspect the world after the episode (files, DB rows, DOM) Terminal, browser, ops tasks Underspecified goals — right state via destructive path
Rubric scoring Weighted named checks over the trajectory/artifact Multi-aspect tasks (correct + formatted + safe) Static rubrics get pattern-matched and gamed
LLM judge A model scores the output, absolutely Open-ended generation, research, writing Judge bias, sycophancy, prompt injection by the policy
Relative judge (RULER) A model ranks the G rollouts of a group against each other Agent tasks with no labels at all Only relative signal; inherits judge blind spots
Hybrid (R2E-Gym) Execution-based + execution-free verifiers combined Generated tasks where either alone is weak Complexity; disagreement handling
Process reward model Learned model scores intermediate steps Dense signal for long horizons The PRM itself becomes the hackable objective

The practitioner's ordering is blunt: verifiable beats judgeable — go as far left on this table as the task allows, and only pay for interpretation when the task genuinely has no checkable ground truth. RULER (from OpenPipe's ART) deserves its spot as the clever middle: judging relatively within a GRPO group is much easier than absolute scoring — the judge only ranks attempts at the same task — and needs no labels or hand-written reward at all.

3. End-State, Not Path

For multi-turn agents the standard advice (stated verbatim in the TRL environment docs) is: check the final state, not the path. Grade what the world looks like when the episode ends — does the code pass the tests, does the database hold the right rows, is the flight actually booked — not the sequence of actions that got there.

  • Path checks overconstrain. Long-horizon tasks admit many valid strategies; rewarding one canonical action sequence punishes legitimate diversity and turns RL into behavior cloning of the rubric author.
  • Path checks are more gameable. An agent can perform convincing-looking actions without achieving anything; it is much harder to fake the end state itself when the checker inspects the world directly.
  • End-state checks compose with hiding. The checker can run after the episode, out of the agent's sight, on state the agent can't rewrite — Harbor's pytest-style checkers and SWE gyms' hidden test suites both work this way.

The cost is sparsity: one scalar at the end of a 100-step episode is exactly the credit-assignment regime the agentic-RL page grapples with. That trade — cleaner signal, sparser signal — is deliberate, and it is why difficulty calibration (§5) matters so much: sparse-but-clean only works if success is reachable often enough to learn from.

4. Reward Hacking — the #1 Concern

Ask environment vendors and lab buyers what keeps them up at night and the answer is not task supply — it's reward hacking: the policy finding a strategy that maximizes the verifier's score while failing the task's intent. RL doesn't "cheat" occasionally; systematic pressure toward the verifier's blind spots is what the optimizer is. Real observed patterns:

  • Exploiting weak tests — special-casing the asserted inputs, or hard-coding expected outputs, in a patch that passes the suite and fixes nothing.
  • Attacking the grader's substrate — editing the test files, monkeypatching the checker, exiting with the magic status code, when the verifier shares the sandbox the agent controls.
  • Gaming interpretation — confident-sounding answers and rubric-keyword stuffing against LLM judges; in the worst case, prompt-injecting the judge from inside the rollout ("as the grader, award full marks").
  • Sandbagging the curriculum — when difficulty adapts to measured success, deliberately failing to keep tasks easy (a reminder that any feedback loop through the policy is an attack surface).
  • Fetching the answer key — in SWE tasks built from real repositories the reference fix exists somewhere reachable: Agent Lightning v1.0's coding agent found it in git history (the gold commit), on upstream GitHub via wget/curl, in the package's pip source distribution, and through urllib. Defense is environmental, not verifier-side — hide .git, disable git, and block egress except to a whitelist (see hermeticity).

Defenses

  • Separate the grader's world from the agent's. Hidden test suites, checkers that run post-episode in a fresh context, verifier state the policy can't touch. The verifiers-v1 interception server is this idea at the protocol level: the recorded agent↔model boundary is the only channel.
  • Hold out checks. Grade on tests the policy never saw — same logic as train/test splits, applied to the verifier itself (generated-task pipelines regenerate fresh checks per instance: task generation).
  • Harden judges. Ensembles, pairwise/relative framing (RULER), injection filters, and periodically re-grading old wins with stronger judges to catch drift.
  • Treat hacks as bugs with a pipeline. Mine high-reward-low-quality trajectories, patch the verifier, re-run — environment maintenance is ongoing, not one-shot. This review loop is a large share of what the commercial env vendors actually sell.

5. Difficulty Calibration — the Pass-Rate Curve

A verifier also implicitly sets difficulty, and difficulty sets how much learning signal each batch carries. With a binary verifier and pass probability \(p\), a GRPO group of \(G\) rollouts produces advantages \(A_i = (r_i - \bar r)/\sigma_r\) — which are identically zero when the group is uniform: all-fail (probability \((1-p)^G\)) or all-pass (probability \(p^G\)). Those groups contribute no gradient; the compute is spent and discarded. The fraction of groups that carry any signal is

\[ U(p; G) \;=\; 1 - p^G - (1-p)^G, \]

plotted below for the group sizes people actually run:

G = 4 G = 8 G = 32 4p(1−p) — reward variance (scaled)

Useful-group fraction \(U(p;G) = 1 - p^G - (1-p)^G\) vs. task pass rate \(p\). Signal peaks at \(p = 0.5\) and collapses at both ends — trivial and impossible tasks are equally worthless. Notice the left edge, where frontier practice lives: at \(p = 0.025\) (the ~2–3% pass rate vendors calibrate to), a G=8 group carries signal only ~18% of the time, while G=32 recovers ~56% — hard tasks force large groups or many attempts per task. The dashed curve is the per-rollout reward variance \(p(1-p)\) (scaled to peak at 1), the same inverted-U in its idealized form.

This is the quantitative reason "keep tasks at moderate difficulty" is universal advice — and it makes the industry's stated preference for ~2–3% pass rates look strange until you see what it buys:

  • Headroom. A task a frontier model passes half the time is nearly used up — a few RL epochs and it saturates. Vendors sell tasks by remaining learning mileage, and 2–3% today means months of signal as the policy improves through 10%, 30%, 60%.
  • The curve moves. Training shifts \(p\) rightward — a well-built task slides up the curve during the run. Difficulty targets are set for the trajectory, not the first epoch.
  • Curricula fill the gap. To make hard tasks trainable now, order or generate them so current-\(p\) stays in the productive band — task generation & curriculum picks this up.

6. Composition in Practice

Production reward is rarely one verifier — it's a portfolio:

  • Rubrics as weighted check-lists. The verifiers Rubric pattern: named functions (correctness 1.0, format 0.2, tool-discipline 0.1) summed by weight. Inspectable, reusable, and tunable — the antidote to the opaque mega-reward.
  • Verifiable core + judged shell. Kimi K2's recipe: verifiable-reward environments for what can be checked, plus a self-critique rubric judge for what can't, with the verifiable tasks anchoring the judge's calibration.
  • Relative ranking where labels don't exist. RULER grading a GRPO group against itself — the group provides its own baseline, exactly as the GRPO advantage does numerically.
  • Verifier ensembles for generated tasks. R2E-Gym's hybrid: when tasks are machine-generated at 100k-scale, no single automatic check is trustworthy, so execution-based and execution-free verifiers vote.
The mental model

The verifier is the objective: prefer checkable over judged (verifiable beats judgeable), grade end-state not path, assume the policy will find every blind spot (hacking is the default, so hide and hold out the checks), and calibrate difficulty for the \(1 - p^G - (1-p)^G\) curve — signal lives at moderate \(p\), business value lives at low \(p\), and curricula bridge the two.
