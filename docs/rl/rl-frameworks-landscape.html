RL Frameworks Landscape

The map of LLM-RL execution — self-hosted frameworks such as verl, TRL, OpenRLHF, NeMo, slime and SkyRL, training APIs from Tinker, Fireworks and Microsoft Foundry, and managed reinforcement-tuning jobs. Compare who owns the loop, not just who supplies the GPUs.

Read this first as the map, then go deep: verl Architecture and TRL are the two anchor write-ups; the slime / Miles walkthrough traces a third design step-by-step. Everything here builds on the algorithm pages (PPO, GRPO) and the systems pages (Async RL, Placement).

1. The Axes That Actually Separate Them

Every online-RL system must connect the same loop — generate, score, compute advantage, update, and make updated weights available to sampling. A framework and a managed service expose different parts of that loop. Start with who operates it, then compare the architecture:

AxisThe questionThe options
Operating boundaryWho runs the GPU fleet and distributed execution?Self-operated runtime · cloud-hosted user training job · remote training primitives · managed tuning job
Algorithm ownershipWho chooses rollouts, advantages, and optimizer steps?Your trainer code · your client loop over primitives · provider workflow configured with data and graders
Controller modelWho orchestrates the dataflow between stages?SPMD Trainer · hybrid single/multi-controller · server-centric · client loop over remote primitives
Training backendHow are weights/optimizer sharded, and is that choice exposed?DeepSpeed ZeRO · FSDP · Megatron (TP/PP/EP/CP) · service-managed backend
Trainable parametersWhich weights may the experiment update?Full fine-tuning · LoRA/adapters · model/service-specific restrictions
Rollout engineWhat generates the responses?HF generate · vLLM · SGLang · service sampling API
Generation placementDo training and rollout share GPUs?Colocated · disaggregated sync · disaggregated async
Overlap and freshnessWhich policy versions produced the training data?Same-version data can overlap computation · stale or mixed-version data needs off-policy treatment; API futures alone say neither
Agent-graph couplingWho owns the multi-turn agent loop?Trainer-owned token loop · chat API + token capture · black-box harness behind a proxy
Method breadthHow many algorithms ship?RL-focused · full preference + RL menu
Target scaleWhere is it happiest?1 GPU → modest · multi-node large dense/MoE

Operation and algorithm ownership are separate axes. A managed service can run the distributed computation while the researcher still owns rewards, advantage estimation, update scheduling, and evaluation. That does not imply access to backend kernels, arbitrary model internals, or placement controls. Conversely, configuring a grader for a managed RFT job does not expose the rollout loop or individual optimizer operations. Hosting your own trainer script on cloud compute is a third boundary, not the same service as either of those.

Within the self-operated stack, the controller model is a central split. An SPMD Trainer keeps all roles in one process (simple, bounded scale); a hybrid controller separates roles into pools the driver orchestrates (complex, scales to 4-D parallel + disaggregated rollout). The full reasoning is on the verl page.

2. Frameworks and Managed Training

Provider additions checked October 28, 2026. The profiles below summarize public documentation, not executed compatibility tests or training benchmarks. Model, region, parameter-mode and preview restrictions are specific to each offering.

verl

ByteDance · Ray · open source

The reference implementation of HybridFlow's hybrid single/multi-controller model. Both FSDP and Megatron training backends; vLLM and SGLang rollout; colocated HybridEngine plus first-class disaggregated async. The most complete and most scalable of the open frameworks, at the cost of the most concepts to learn.

TRL

HuggingFace · Trainer / accelerate · open source

The widest method menu (SFT, reward modeling, DPO/KTO/ORPO/CPO, PPO/GRPO/RLOO/online-DPO, GKD) behind one Trainer API, deeply wired into the HF ecosystem (Hub, PEFT/LoRA, quantization). SPMD launch with DeepSpeed/FSDP; vLLM colocate or server generation. The fastest on-ramp; best for 1–8 GPUs and algorithm iteration. Full write-up →

OpenRLHF

Community · Ray + DeepSpeed + vLLM · open source

The pragmatic middle ground: Ray-based role distribution with DeepSpeed ZeRO-3 training and vLLM generation, supporting PPO, GRPO, REINFORCE++, and the DPO/KTO family. Simpler than verl (no Megatron — DeepSpeed only), but more scalable and disaggregation-friendly than a single Trainer. A common choice when verl is more than you need but TRL is less.

NeMo-Aligner / NeMo-RL

NVIDIA · Megatron-Core · open source

The maximum-scale, NVIDIA-stack option: built on Megatron-Core/NeMo with full TP/PP/EP/SP and TensorRT-LLM-class generation, targeting the largest dense and MoE models on NVIDIA clusters. Heaviest setup; enterprise-grade scale. (NeMo-RL is the newer, more modular successor to NeMo-Aligner.)

slime (& Miles)

Zhipu AI / Tsinghua · SGLang + Megatron · open source

An SGLang-native design: rollout runs as a standing SGLang HTTP server, training on Megatron-LM with expert parallelism for MoE, and async by construction. It leans on TIM-style elimination of training–inference mismatch rather than IS correction. The slime / Miles walkthrough traces one PPO step on a 30B MoE through it.

SkyRL

NovaSky / Berkeley / Anyscale · self-operated full-stack RL

The October 28 repository snapshot unifies the earlier skyrl-train and skyrl-tx work under skyrl. SkyRL-Agent supplies the long-horizon agent layer; SkyRL-Gym supplies environments. These are different layers, not competing trainers.

Its Tinker-compatible API exposes self-operated FSDP/Megatron training and vLLM sampling, with LoRA and full-parameter training. This is not Thinking Machines Lab's hosted service: the latter's LoRA restriction is not a property of the API name. Compatibility is bounded: SkyRL currently wires cross_entropy and importance_sampling through that API, not every native loss. See the contract comparison and fully async endpoint/cache restrictions.

Tinker

Thinking Machines Lab · managed training API · overview/custom-loss docs checked October 28, 2026

The researcher runs a CPU-side Python loop for data, environments, rewards, advantages, and evaluation; the service handles distributed model computation. The exposed primitives include forward_backward for gradient accumulation, optim_step for updates, sample, and state-saving/loading operations. This is a managed execution option, not another self-hosted parallelism engine.

The documented service supports LoRA fine-tuning, not full fine-tuning, across supported dense, MoE, and vision-language models. Its algorithm menu is broader than one fixed trainer recipe, but experiments remain bounded by the exposed operations, supported models, and trainable parameters. The overview permits downloading trained weights for use elsewhere; export does not expose the provider's backend implementation or prove compatibility with a particular serving stack.

Choose it for: algorithm and reward iteration without operating distributed GPUs, when the service's model and LoRA scope fit. Do not assume: full-parameter updates, custom kernels, or caller-controlled GPU placement. An async API future means a nonblocking request, not necessarily asynchronous/off-policy RL; that depends on the client loop and which policy versions produced the data. Token alignment and loss-specific contracts →

Custom loss is a logprob-gradient interface. forward_backward_custom runs a remote forward pass, then computes a local scalar loss and \(g=\partial L/\partial\ell\) for the returned target-token logprobs \(\ell\). A second remote forward/backward evaluates the linear surrogate \(\sum_i \ell_i\,\mathrm{stopgrad}(g_i)\), with the same parameter gradient at that forward point. The callback can couple sequences; it is not uploaded to the server and does not expose arbitrary activations. The documentation reports about 1.5× FLOPs and up to 3× wall time versus a built-in forward_backward, from the extra forward and scheduling. These are documented implementation costs, not a universal bound or a reproduced benchmark.

Fireworks Training API

Provider-operated computation · client-owned loop

Serverless uses a shared pool, supports LoRA, and bills per token. Dedicated provisions trainer and deployment resources, supports LoRA or full-parameter training, and uses time-based billing. Both expose training primitives, but their lifecycle is not interchangeable: serverless sampling binds to a saved adapter snapshot; dedicated sampling refreshes a deployment. Serverless cross-run resume is limited.

The experimental async_rl_loop cookbook owns grouping, advantages and update scheduling around your rollout function; the serverless adapter has a separate snapshot-publication path. See agentic TITO and scheduling. BYOT rollout inference is a separate option for your own trainer; external-bucket hotload is private preview. The training overview routes RL to the Training API while the BYOT guide still names turnkey “Managed RFT”; its availability is not resolved by these pages.

Microsoft Foundry: interactive training versus managed RFT

Two different algorithm-ownership boundaries

Interactive training exposes stateful sampling, forward/backward, optimizer steps and checkpoints over open-weight models with serverless LoRA updates. Your driver owns rewards, advantages, masks, batch construction and scheduling. It is an approval-gated preview without an SLA, not recommended for production. Loss names are primitives, not complete algorithms; the preview SDK and cookbook wrappers have different interfaces and completion patterns.

Managed reinforcement fine-tuning instead takes datasets, a grader, response format and supported job settings. Foundry owns the training workflow. String, similarity, model, Python and composite graders provide reward control, not arbitrary optimizer control. Model/region eligibility, grader hosting and parameter scope must be checked for that workflow; do not inherit interactive training's LoRA scope or preview status. See state and completion gates and managed-job reporting.

Gemini reinforcement learning fine-tuning

Google Cloud · service-owned adapter-tuning workflow

Supply prompts/references, reward configuration and job hyperparameters; the service samples and updates the model. String/regex, Gemini autorater, sandboxed Python and Cloud Run scorers can be combined. An external reward callback does not grant control over the harness or individual optimizer operations. The overview documents adapters and a v1beta1 API, not a disclosed PPO/GRPO recipe or full-parameter contract.

Tuning and serving locations differ: us-central1 maps to us multi-region serving, and europe-west4 to eu. A successful tuning job from a base model deploys the last checkpoint; intermediate checkpoints can be evaluated independently. Deployment is not evidence that the final checkpoint is best. Metric and selection caveats →

Scope boundary: SageMaker AI RL is job infrastructure, not another LLM-RFT trainer. The linked AWS guide describes RLEstimator submitting your environment, presets and trainer script to CPU/GPU jobs with container selection, artifacts and metrics. Its distributed examples separate rollout and learner compute, including heterogeneous instances; that proves neither async policy-update semantics nor large-model sharding support. The page lists TensorFlow/MXNet and Coach/RLlib. Treat that as the source's inventory, not a verified current SDK/container support matrix or a description of AWS foundation-model tuning.
The field moves fast — AReaL (Ant, fully-async RL), ROLL (Alibaba), and others share these same axes. You do not need to track every name; place any new framework on the §1 axes and you know what it is.

The short version

First choose the operating boundary and trainable-parameter scope: client-owned primitive loops → Tinker, Fireworks or Foundry interactive; service-owned grader-configured jobs → Foundry RFT or Gemini; hosted user scripts → job infrastructure such as SageMaker. A self-operated Tinker-compatible stack → SkyRL. For self-operated execution, sort by scale and controller model. One Trainer on a few GPUs → TRL. Ray + vLLM at mid-scale without Megatron → OpenRLHF. Hybrid controller, every backend, async at production scale → verl. NVIDIA Megatron stack at the frontier → NeMo. SGLang-native async → slime. The axes matter more than the names — frameworks come and go, the design trade-offs persist.
