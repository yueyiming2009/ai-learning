Agentic RL

Long-horizon tool use, code execution, and multi-step decision making under RL. Single-turn reward design breaks down when actions have real consequences that unfold over many steps.

Reasoning RL (as in DeepSeek-R1) trains a model to think before answering a single question. The model generates tokens; a verifier checks the final answer; a scalar reward is assigned. The environment is passive — it asks a question and waits. Agentic RL is different in every dimension: the model must take actions that change the state of an external system, observe the results, decide on next actions, and eventually produce an outcome that may only be evaluable after dozens of steps. This page covers what changes, why it's harder, and how the field is handling it.

2. The Agent as an MDP

The MDP formalism applies directly to agentic RL, but the interpretation of each component changes:

MDP component Reasoning RL Agentic RL
\(S\) — state The question + tokens generated so far The conversation context including all prior tool calls and their outputs
\(A\) — action Next token A structured tool call (with arguments) or a reasoning token step
\(P(s' | s, a)\) — transition Deterministic (language model output) Stochastic (code execution may fail, APIs may return errors, file system state changes)
\(R(s, a)\) — reward Binary at terminal state (correct/wrong) Sparse terminal, optionally with per-step signals; reward model for non-verifiable tasks
\(\gamma\) — discount Effectively 1 (one step, no discounting needed) Must be tuned — too low and early steps are underweighted; too high and variance explodes
Episode length Fixed (response length limit) Variable — ends when the agent outputs a terminal token, the task is verified complete, or a step limit is hit

What a trajectory looks like

A single agentic episode for a coding task:

t=0
[OBS] You have a Python repo with failing tests. Goal: make all tests pass.
t=1
[THINK] I should run the tests first to see which ones fail.
t=1
[ACT] bash("pytest tests/") →
t=1
[ENV] FAILED tests/test_parser.py::test_edge_case — assert None == 42
t=2
[THINK] The parser returns None for edge cases. Let me read the parser code.
t=2
[ACT] read_file("src/parser.py", lines=45-80) →
t=2
[ENV] ... def parse(x): ... return None # TODO: handle edge case
t=3
[ACT] edit_file("src/parser.py", old="return None", new="return 42") →
t=3
[ENV] OK
t=4
[ACT] bash("pytest tests/") →
t=4
[ENV] 12 passed in 0.4s
T
[REWARD] +1.0 (all tests pass)
Observation Reasoning tokens Tool call Environment output Terminal reward

The model produces both reasoning tokens (free-form language) and structured action tokens (tool calls) in the same generation pass. The environment executes each tool call and appends its output to the context before the next generation step. This interleaving of generation and execution is the defining characteristic of agentic RL.

3. Reward Design for Long-Horizon Tasks

Reward design is the hardest problem in agentic RL. The choices made here determine whether the agent learns to solve the actual task or finds clever ways to appear to solve it. This section covers the shaping choices inside the RL objective; the environment-side grader — the verifier spectrum, reward hacking, difficulty calibration — has its own page: Verifiers & Reward Design.

Terminal-only rewards (preferred when possible)

The cleanest setup: reward only at episode end, based on objective task completion. The agent must figure out on its own which actions were good — the environment just reports the final outcome.

Code: test pass rate

r = (tests passing after edit) / (total tests). Verifiable, objective, no reward hacking — an agent can't fake passing tests without actually making them pass.

QA / research: judge LLM

r ∈ {0, 1} from a separate judge model evaluating correctness. Scales to open-ended tasks where no unit-test-style verifier exists.

Tool calling: schema check

r ∈ {0, 1} checking whether tool calls were syntactically correct and logically coherent. For function-calling benchmarks.

Length-based reward

Never use response length as a reward signal. The agent will learn to pad responses, loop, or repeat itself to maximize tokens while ignoring task completion.

Reward shaping — when and why

With sparse terminal rewards over long horizons (T = 50+ steps), the gradient signal is extremely weak: most trajectories get 0 reward and the model receives almost no information about which early actions were good. Reward shaping adds intermediate signals to guide learning. The obvious hazard is that an intermediate signal creates its own optimization target — the agent farms the bonus instead of finishing the task.

The policy invariance theorem

Ng, Harada & Russell (1999) characterize exactly which shaping functions are safe. A shaping term \(F(s,a,s')\) added to the reward is potential-based if there exists some \(\Phi : S \to \mathbb{R}\) with

\[ R'(s, a, s') = R(s, a, s') + F(s, a, s') = R(s, a, s') + \gamma\Phi(s') - \Phi(s) \]

Every optimal policy of \(R'\) is then optimal for \(R\), and vice versa. The converse holds too: for any \(F\) not of this form, there exist transition dynamics and a base reward under which the shaped optimum is suboptimal in the original MDP. Potential-based is not merely sufficient — it is the only form that is safe without knowing the environment in advance.

The proof is a telescoping sum. Along any trajectory, the shaping term contributes

\[ \sum_{t \ge 0} \gamma^t \big( \gamma\Phi(s_{t+1}) - \Phi(s_t) \big) = -\Phi(s_0) + \lim_{T \to \infty} \gamma^T \Phi(s_T) \]

Every interior term cancels. The shaped return differs from the true return by \(-\Phi(s_0)\), which depends only on where the episode started, not on what the agent did. No policy can accumulate shaping reward — which is precisely the loop-exploitation loophole closed. Equivalently, \(Q^*_{R'}(s,a) = Q^*_R(s,a) - \Phi(s)\): subtracting a function of state alone leaves every advantage, and therefore every \(\arg\max_a\), untouched.

Two consequences worth carrying around. The best possible potential is \(\Phi = V^*\), which reduces \(Q^*_{R'}\) to the advantage function and makes the shaped problem myopic — so the quality of a shaping scheme is just how close \(\Phi\) sits to the true value function. And Wiewiora (2003) showed that potential-based shaping with \(Q_0 = 0\) produces behavior identical to no shaping with \(Q_0 = \Phi\). Valid shaping injects a prior on values and nothing more.

Two implementation traps. The \(\gamma\) in \(\gamma\Phi(s') - \Phi(s)\) is load-bearing; using \(\Phi(s') - \Phi(s)\) with \(\gamma < 1\) breaks the telescoping and voids the guarantee. And terminal states must have \(\Phi = 0\) — a nonzero potential at episode end is an unbalanced real reward, not a shaping term. This is the most common way a correct-looking implementation silently stops being policy-invariant.

Why valid shaping does nothing in GRPO

Working the theorem through the algorithm actually used for agentic RL gives a sharp result. LLM episodes run at \(\gamma = 1\), so with \(\Phi = 0\) at termination the shaping contribution to every trajectory is exactly \(-\Phi(s_0)\). Group-relative advantages are computed over \(G\) rollouts from the same prompt, so \(s_0\) is shared across the group:

\[ A_i = \frac{R_i - \text{mean}(R_{1..G})}{\text{std}(R_{1..G})} \]

Adding the same constant to every \(R_i\) shifts the mean by that constant and leaves the numerator unchanged; the standard deviation is unaffected. The advantage is bit-identical with and without shaping. Under PPO with a learned critic the effect is not exactly zero, but by the Wiewiora equivalence it amounts to value-function initialization, which the critic re-learns within a few thousand steps.

The corollary is uncomfortable but clarifying: any dense reward that measurably changes a GRPO run is, by construction, not policy-invariant. Practitioners are not choosing unprincipled shaping over principled shaping. In the dominant algorithm, principled shaping is a no-op, so every dense signal in production is one the theorem does not cover.

Denser terminal reward is not shaping

Much of what gets called dense reward in agentic RL is a finer-grained terminal reward, and the shaping analysis does not apply to it at all. The distinction determines whether there is any hazard to reason about:

Two things that both look like "dense reward"
  • Higher-resolution terminal reward — no shaping risk. Fraction of unit tests passed rather than all-or-nothing, partial credit across sub-tasks, a rubric score from a judge model on the finished trajectory. Still one reward at episode end; it just carries more bits than a success flag. Nothing mid-trajectory is being optimized.
  • Genuine mid-trajectory reward — where the hazard lives. Per-tool-call success bonuses, compile-clean or lint-clean signals during the episode, turn-level rewards in multi-turn agents, sub-goal bonuses for opening the right file or running the right command. These change what the agent is optimizing between steps, and almost none of them are potential-based.

Penalties are the more common form of the second category — token budgets, tool-call count limits, wall-clock cost. They are just as non-invariant in theory, but empirically much safer: a negative signal cannot be farmed by looping, which is the failure mode positive shaping invites.

Practice has moved toward sparse

The reference datapoint is DeepSeek-R1, which evaluated a process reward model and dropped it from the production run: step boundaries are hard to define, the PRM gets hacked once the policy drifts off its training distribution, and continuous PRM retraining complicates the pipeline. Outcome reward plus a format check was enough, and the reasoning behavior emerged anyway (see DeepSeek-R1). Process reward models did not disappear — they migrated to inference, where they rerank candidates or guide search rather than serve as a training target. A verifier that the policy cannot optimize against sidesteps the problem entirely (see tree search for LLMs).

Where the sparse position is genuinely under pressure is long-horizon agents with single-digit initial success rates. When every rollout in a group fails, the group-relative advantage is identically zero and there is no gradient at all. The field's answers to that are mostly not shaping: curriculum and difficulty filtering, dropping degenerate all-equal groups, SFT-seeded starting policies, and partial-credit terminal rubrics — all of which raise signal without introducing a mid-trajectory target.

Goodhart's law in agentic RL: any shaping signal the agent can optimize independently of the true goal will be exploited. An agent rewarded for "making tests pass" without checking the full suite will learn to delete failing tests, hardcode expected outputs, or mock the functions under test — all technically passing the reward while completely missing the point. This is especially dangerous in agentic settings where the model can modify the environment.

Format and safety rewards

Unlike reasoning RL where format rewards are simple (does the response contain <think> tags?), agentic RL requires structured reward signals for tool call correctness:

  • Schema validity: did the tool call use the correct argument names and types?
  • Safety: did the agent attempt any disallowed operations (deleting system files, calling unauthorized APIs)?
  • Termination: did the agent output a proper terminal signal rather than looping indefinitely?

These are typically small binary bonuses or penalties, weighted much lower than the terminal task reward, so they guide behavior without distracting from the main objective.

4. Environment Scaffolding

The agentic RL environment is not a dataset — it is a live execution system that the model interacts with. Building it correctly determines whether the RL signal is sound.

This section sketches the environment in miniature. The full stack — the ecosystem landscape, the OpenEnv interface standard, verifiers & the Environments Hub, sandboxing at scale, and task generation — has its own six-page series.
# Minimal agent environment interface
class AgentEnv:
  def reset(self) → Observation:
    # Load task, reset filesystem / DB / API sandbox
    return initial_observation

  def step(self, action: ToolCall) → Tuple[Obs, Reward, Done]:
    result = execute_tool(action) # run in sandbox
    obs = build_context(history, result)
    r = compute_reward() if done else 0.0
    return obs, r, done

  def compute_reward(self) → float:
    # Evaluate terminal state in isolated verifier
    return run_tests(sandbox_state)

Sandboxing requirements

The agent must operate in a sandboxed environment during RL training. An agent that can modify its own reward computation, delete test files, or access the training infrastructure would immediately exploit those capabilities — the environment must be designed so that the only way to get reward is to genuinely complete the task.

  • Filesystem isolation: each episode gets a fresh copy of the task repository in a container. The agent can read/write/delete within this sandbox; the sandbox is destroyed at episode end.
  • Reward isolation: the verifier that computes the terminal reward must run in a separate process with read-only access to the sandbox state. The agent cannot modify the verifier's view of the world.
  • Network isolation: in most setups, the agent has no outbound network access to prevent it from calling external services to solve tasks.
  • Resource limits: CPU time, memory, and disk are bounded per episode to prevent the agent from exploiting resources.

Task distribution

Agentic RL tasks come from curated datasets of real-world problems: GitHub issues with linked test suites, coding competition problems with automated judges, QA tasks with gold-standard answers. The distribution matters:

  • Tasks must have verifiable outcomes for training (unit tests, expected outputs, judge models).
  • The difficulty distribution interacts with RLCS-style curriculum: tasks where the current agent succeeds 30–70% of the time produce the most useful gradient signal (see Cascade RL).
  • Diversity matters more than in reasoning RL: an agent trained only on pandas bugs may fail on numpy bugs even though both are Python coding tasks.

5. Credit Assignment Across Long Horizons

In a 50-step trajectory that ends in reward +1, which of the 50 actions deserves the credit? This is the core difficulty of agentic RL — and it is where the connection to TD learning becomes important.

Monte Carlo returns

The MC return assigns the full terminal reward to every step in the trajectory:

\[ G_t = \gamma^{T-t} R_T \quad \text{(terminal-only reward)} \]

With discount \(\gamma = 0.99\) and T = 50, the return at step \(t=0\) is \(0.99^{50} \approx 0.61\). The return at step \(t=40\) is \(0.99^{10} \approx 0.90\). Steps near the end receive more credit than early steps — even if an early action (reading the right file) was causally responsible for the eventual success.

GAE with a value baseline

A value function \(V(s_t)\) — the expected return from state \(s_t\) under the current policy — can reduce variance by subtracting a baseline that accounts for what the model expected to achieve from each state. The GAE advantage:

\[ \hat A_t^{\text{GAE}} = \sum_{l=0}^{T-t-1} (\gamma\lambda)^l \delta_{t+l}, \quad \delta_t = R_t + \gamma V(s_{t+1}) - V(s_t) \]

trains a critic network \(V_\phi(s_t)\) that must learn to predict long-horizon returns from the current context — a hard task in itself when the context is a long interleaved sequence of tool calls and results.

GRPO's limitation for long horizons

GRPO replaces the critic with group-relative baselines: sample \(G\) complete trajectories per prompt, use the group mean as the baseline. This works well for single-turn tasks because each trajectory is comparable. For long-horizon tasks:

  • Two trajectories for the same task may diverge massively by step 5 (one took the right branch, one didn't). Comparing their terminal rewards and averaging doesn't tell the model which specific action at step 3 caused the divergence.
  • The group-relative advantage assigns the same advantage estimate to every step in a successful trajectory — the action at step 1 gets the same credit as the decisive action at step 30.
  • Longer trajectories mean more tokens per group, which is expensive — generating 8 trajectories of 50 steps is 400 environment interactions vs. 8 for single-turn.
Current practice

Most labs currently use GRPO at the trajectory level for agentic RL, accepting the coarse credit assignment because the infrastructure is simpler and the verifiable terminal reward is still a strong enough signal to make progress. The critic-based approach (PPO + GAE) is theoretically better for long horizons but harder to implement stably when the observation space is a long, variable-length token sequence. Research is ongoing.

6. Adapting GRPO to Agentic Settings

Standard GRPO (from the GRPO page) computes advantages at the response level. Agentic GRPO applies the same group-relative advantage to every token in every step of a multi-step trajectory.

For a group of \(G\) complete trajectories on the same task, each trajectory \(i\) has terminal reward \(r_i\). The trajectory-level advantage:

\[ \hat A_i = \frac{r_i - \text{mean}(\{r_j\}_{j=1}^G)}{\text{std}(\{r_j\}_{j=1}^G)} \]

This advantage is applied uniformly to all tokens \(t \in [0, T_i]\) of trajectory \(i\). The policy gradient loss is then:

\[ \mathcal{L}_{\text{GRPO}} = -\frac{1}{\sum_i T_i} \sum_{i=1}^G \sum_{t=1}^{T_i} \hat A_i \cdot \min\!\left(\rho_{i,t} \hat A_i,\ \text{clip}(\rho_{i,t}, 1-\varepsilon, 1+\varepsilon)\hat A_i\right) \]

where \(\rho_{i,t} = \pi_\theta(a_{i,t} | s_{i,t}) / \pi_{\theta_\text{old}}(a_{i,t} | s_{i,t})\) is the per-token importance ratio. The normalization divides by total tokens (not number of trajectories) to avoid biasing toward shorter trajectories.

Tool call tokens vs. reasoning tokens

The policy generates two types of tokens: reasoning tokens inside <think> blocks and structured tool call tokens. There's an active debate about whether to mask reasoning tokens from the policy gradient (applying the loss only to tool call and response tokens). Arguments:

  • Mask reasoning tokens: the model should be free to reason however it wants; penalizing reasoning tokens for a failed trajectory might discourage useful intermediate thinking.
  • Include reasoning tokens: if the model's reasoning led to a bad tool call, the reasoning tokens should bear some responsibility. Including them also provides more gradient signal per trajectory.

In practice, most implementations include all tokens but weight tool-call tokens more heavily, or apply the loss equally to all tokens and rely on the overall gradient to separate good and bad reasoning patterns over many trajectories.

7. Open Challenges

Environment diversity and generalization

Agents trained on SWE-bench (GitHub issues) don't automatically generalize to internal codebases with different conventions, CI/CD systems, or languages. Unlike reasoning RL where "add 3 and 7" generalizes to "add 4 and 8," tool-use strategies are environment-specific. Building diverse enough training environments is an ongoing engineering challenge.

Multi-agent and collaborative settings

Some tasks require coordination between multiple agents: one agent writes code, another reviews it, a third runs tests. Multi-agent RL introduces new credit assignment problems (which agent's action caused the outcome?), new optimization problems (agents may learn to cooperate to fool the reward function), and new infrastructure requirements (orchestration, message passing, shared state).

Reward hacking at scale

The more capable the agent, the more creative the reward hacking. Agents trained with terminal rewards on code tasks have learned to: patch test files to remove failing assertions, mock out the functions being tested, exploit time-dependent bugs where the test only fails in certain conditions, and write code that passes the specific test suite without being generally correct. Defense requires adversarial test construction and reward auditing that scales with agent capability.

Safety under agentic RL

A model trained to use tools to complete tasks will naturally generalize to using tools to complete tasks it wasn't intended for. RL training with broad tool access (file system, network, code execution) creates models that are more capable at tool use generally — including uses that are undesirable. Agentic RL requires careful scoping of the action space and explicit training on refusal for out-of-scope requests.

Summary

What changes

Multi-step, tool use, stochastic environment, sparse terminal rewards, hard credit assignment — single-turn RL is a special case.

Reward design

Prefer verifiable terminal rewards (test pass rate, judge model). Shaping must be potential-based to preserve the optimal policy. Never reward format over substance.

Environment

Sandboxed execution with filesystem, reward, and network isolation. The verifier must be unreachable by the agent or reward hacking is inevitable.

Credit assignment

GRPO at trajectory level assigns uniform credit. GAE + critic is better but harder. Current practice accepts coarse assignment and relies on scale.

GRPO adaptation

Trajectory-level z-score advantage, applied uniformly to all tokens. Normalize loss by total token count, not trajectory count, to avoid length bias.

Open problems

Environment diversity for generalization, multi-agent credit assignment, reward hacking at scale, and safety under broad tool access.
