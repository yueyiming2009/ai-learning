Agentic RL Training in verl

How a multi-turn, tool-calling rollout becomes a trainable batch. The AgentLoop stack, sticky-session routing, the token-in-token-out invariant that keeps the loss mask honest, and the sandbox layer that runs the tools.

Prerequisites: verl Architecture (WorkerGroup, ResourcePool, DataProto, the HybridEngine) and Agentic RL (the agent-as-MDP framing, reward design over long horizons). Companion pages: Async Training in verl (what happens when the trainer stops waiting for the whole batch) and GRPO Training Walkthrough (the single-turn version of the same loop).

In single-turn RL, generation is one function call: hand generate_sequences a batch of prompts, get back a batch of responses. Every token in the response came from the policy, every sequence is the same shape, and the reward is a function of the final string.

Agentic RL breaks all three of those assumptions at once. This page traces what verl does about it — not the config surface, but the mechanism underneath: which object runs the turn loop, how it reaches the inference engine, and what invariant has to hold for the resulting tensors to be a valid policy-gradient batch at all.

1. Three Things a Turn Loop Breaks

AssumptionHow multi-turn violates itverl's answer
The batch is one forward pass A trajectory alternates generate → tool call → generate. The number of round trips is data-dependent: one prompt finishes in 2 turns, another in 15. A single batched generate across SPMD ranks cannot express that. Server mode. Each rollout replica runs behind an OpenAI-compatible server; an agent loop per trajectory issues its own requests and awaits them independently. rollout.mode: async.
Every response token is policy output Tool results are injected into the context. The model did not generate them, so they carry no log π the gradient may touch — but they do occupy the response, and later tokens are conditioned on them. The response mask. AgentLoopOutput carries a per-token mask that is 1 on assistant tokens and 0 on tool tokens. §4.
Reward is a function of a string The score may depend on environment state the string never shows — did the unit tests pass, did the SQL return the right rows, is the file system in the right state. Stateful tools. A BaseTool instance lives for the duration of one rollout and exposes calc_reward alongside execute. §6.
rollout.mode: async is not async training. It selects per-request concurrency against a rollout server — which is exactly what multi-turn needs — and says nothing about whether the trainer consumes stale data. That is trainer.v1.trainer_mode, covered on the async training page. Agentic rollouts are the main reason server mode exists, but they are on-policy until you change the other knob.

2. The AgentLoop Stack

Four layers sit between the trainer's generate_sequences call and the inference kernel. Each is a Ray actor tier with one job:

AgentLoopManager

Top-level orchestrator, owned by the trainer. Spins up dp_size server actors with node affinity so each is co-located with the compute workers holding that data-parallel shard's weights, spawns num_workers AgentLoopWorkers, chunks the prompt batch across them, and brackets the whole generation phase with wake_up() / sleep() to release inference KV memory back to training.

↓ one chunk of prompts per worker
AgentLoopWorker

Stateful Ray actor. Instantiates one AgentLoop per prompt in its chunk — roughly train_batch_size / num_workers of them — resolved from the _agent_loop_registry by agent_name, runs them concurrently as asyncio tasks, then post-processes the returned outputs into padded tensors.

↓ one generate() call per turn, per trajectory
AsyncLLMServerManager

Client-side load balancer. Least-request routing over a weighted heap, plus sticky sessions so every turn of one trajectory lands on the same server. §3.

↓
AsyncSGLangServer / vLLM equivalent

Ray actor wrapping the engine, exposing a token-in-token-out generate() that forwards to the tp_rank=0 master worker. Both SGLang and vLLM are supported backends.

The shape worth noticing: the agent loop runs on CPU actors, not on the GPU workers. Tool execution, HTTP calls to a sandbox, parsing, and turn bookkeeping all happen off the critical GPU path, and the only thing crossing into GPU-land is a token-level generate request. This is the same trainer/agent disaggregation that Agent Lightning and SkyRL-Agent arrive at independently — it is the dominant design in the field, not a verl idiosyncrasy.

3. Least-Request Routing, and Why Sessions Are Sticky

AsyncLLMServerManager keeps a weighted heap of server handles keyed by in-flight request count, so a new trajectory's first turn goes to the least-busy replica. That part is ordinary load balancing. The interesting part is what happens on turn two:

if request_id in self.request_id_to_server:
    return self.request_id_to_server[request_id]   # session affinity
# else: pop the least-loaded server off the heap

An LRU map pins request_id → server for the life of the trajectory. The reason is the KV cache: turn \(k{+}1\)'s prompt is turn \(k\)'s prompt plus the assistant response plus the tool result — a strict extension of a prefix that server already has resident. Routing that turn elsewhere throws away the prefix and re-prefills the entire conversation from scratch. With a 10-turn trajectory and a growing context, the difference between sticky and round-robin is the difference between prefilling \(O(n)\) new tokens per turn and \(O(n^2)\) total.

Stickiness and least-request pull against each other: pinning long trajectories to a replica means load imbalance persists for the whole trajectory, and one server can accumulate several 15-turn sessions while another drains. The heap only rebalances at trajectory boundaries. This is the multi-turn version of the straggler problem that partial rollout exists to absorb.

4. Token-in-Token-Out, and the Response Mask

This is the section that matters most, because getting it wrong produces a run that trains without erroring and simply fails to converge.

An agent loop returns an AgentLoopOutput with three fields:

AgentLoopOutput

prompt_ids — the initial templated prompt
response_ids — everything after it: assistant tokens and tool-response tokens, interleaved in generation order
response_mask — 1 where the policy generated the token, 0 where the environment did

The mask is what makes the batch trainable. The PPO/GRPO objective sums over tokens the policy is responsible for; a tool result has no \(\log \pi_\theta\) to differentiate, and including it would have the model optimizing to predict the sandbox's stdout. So the mask zeroes those positions in the loss — while the tokens stay in input_ids, because the assistant's later tokens were conditioned on them and the forward pass must see the same context the rollout saw.

Why the tokens must be spliced, not re-tokenized

The tempting implementation is to accumulate a chat-message list, then at the end call apply_chat_template once and tokenize the whole conversation. verl explicitly does not do this, and the docs flag it as a correctness issue that "significantly impacts RL training convergence."

The problem is that tokenization does not commute with concatenation. Let \(T(\cdot)\) be the tokenizer and \(a, b\) two adjacent message strings:

The invariant that fails
\[ T(a \mathbin{\|} b) \;\neq\; T(a) \mathbin{\|} T(b) \]

BPE merges across the seam. A trailing space plus a leading word may merge into one token; a tool result that ends mid-word changes how the next chat-template delimiter tokenizes. Decode-encode round trips during tool-call extraction introduce further drift. The consequence is that the token sequence you'd get by re-tokenizing at the end is not the sequence the model actually sampled — so the log-probs you compute in the training forward pass belong to a slightly different string than the one the policy produced, and the importance ratio \(\pi_\theta / \pi_{\text{old}}\) is silently wrong on exactly the tokens near every turn boundary.

verl avoids it two ways at once. Generation is token-in-token-out: the agent loop passes token IDs to the server and receives token IDs back, never round-tripping through text. And where text must be templated — the tool-result messages — it uses delta tokenization: template the message list at length \(i\) and at length \(i{+}1\), and take the difference as the new turn's tokens. A tokenization_sanity_check_mode (strict / ignore_strippable / disable) audits the result against a full re-tokenization and warns on divergence.

If you write a custom agent loop (§10), this invariant is your responsibility. Building response_ids by tokenizing strings you assembled yourself is the single most common way to produce a silently broken agentic run. Turn tokenization_sanity_check_mode to strict while developing one.

Where the response budget actually goes

The mask has a second consequence that is easy to miss until a run underperforms: tool tokens consume response_length without contributing gradient. A verbose tool — a stack trace, a full file dump, an un-truncated SQL result set — can eat most of the budget, leaving few trainable tokens per trajectory and truncating the trajectory before the task is finished.

assistant tokens (mask = 1, trainable) tool tokens (mask = 0) past response_length — never generated

Tool output is charged to the response budget at full price and refunded no gradient. Push tool tok/turn up and watch the trainable fraction collapse while the truncation line marches left — the trajectory dies mid-task and the turns past the dashed line never happen. The fix is rarely a bigger budget: it is truncating tool output at the tool, which is why execute() returning a summarized result is a modelling decision, not plumbing.

5. ToolAgentLoop — the Built-In ReAct Loop

verl ships ToolAgentLoop, a ReAct-style loop that covers the common case. Its body, stripped to the essentials:

One iteration
  1. server_manager.generate(prompt_ids) → response tokens.
  2. Append them to prompt_ids; append 1s to the mask.
  3. Parse the response for tool calls in the configured multi_turn.format. No tool call → the trajectory is done.
  4. Dispatch the calls concurrently via _call_tool(); await all results.
  5. Template the results into tool messages, delta-tokenize, append; append 0s to the mask.
  6. Loop, unless max_assistant_turns is reached or the accumulated length would exceed response_length.

Three termination conditions, and they mean different things for the reward. A clean stop (no tool call) is the agent declaring it is finished. Hitting max_assistant_turns or the length cap is a truncation — the trajectory is still trainable, but the task was never attempted to completion, and whether that scores as failure or as neutral is a reward-design choice you have to make deliberately. Silently scoring truncations as 0 teaches brevity; scoring them as failure teaches the model to hurry. See Agentic RL §3.

6. Defining Tools — Two Levels

Tools come in a stateless and a stateful flavor, and the choice is about whether the tool needs to remember anything across turns of one rollout.

@function_toolBaseTool subclass
Shape A decorated Python function. The OpenAI-style JSON schema is inferred from the signature and docstring. A class implementing four async methods; the schema is declared explicitly in YAML.
State None. Each call is independent. Per-rollout instance state, keyed by instance_id.
Config key multi_turn.function_tool_path multi_turn.tool_config_path
Use when Pure functions — a calculator, a formatter, a stateless lookup. Anything with a session: a database connection, a checked-out repo, a browser, a sandbox whose file system must persist across turns. Also required if the tool contributes to the reward.

The BaseTool lifecycle

MethodCalledDoes
create(instance_id)Once, at rollout start Provision the session — open the connection, clone the repo, allocate the sandbox.
execute(instance_id, parameters)Every tool call Run it; return the tool result plus metadata. This is the string that becomes mask-0 tokens, so its length is a budget decision (§4).
calc_reward(instance_id)At rollout end Turn accumulated tool state into a scalar — tests passed, rows matched, goal reached. This is how environment state that never appeared in the text reaches the advantage.
release(instance_id)At rollout end Tear down. Non-optional at scale — a leak here is a leaked container per trajectory, thousands per step.

Tools may also return multi-modal content — ToolResponse(image=[...], video=[...], text="...") — for VLM agents. Note the sharp edge: the docs call for return_multi_modal_inputs: False in the dataset config to avoid a key conflict during multi-turn training.

7. Sandbox Fusion — Running Code Without Melting the Cluster

The canonical stateful tool is code execution, and verl integrates Sandbox Fusion: a FaaS endpoint that runs the model's code out-of-process and returns stdout as the tool result. The RL-specific engineering here is not the execution — it is the backpressure.

Consider the arithmetic. A batch of 512 prompts × 8 rollouts per prompt = 4096 concurrent trajectories, each of which may fire a code execution every turn. Without a limiter, one training step opens tens of thousands of near-simultaneous connections to the sandbox service, which either falls over or degrades until every rollout times out — and a timed-out tool call becomes garbage training data, not a dropped request.

verl throttles with a global token bucket implemented as a Ray actor, TokenBucketWorker, holding a semaphore shared across every data-parallel rank. The detail worth stealing is its concurrency-group split: acquire is single-threaded, release runs with 10 threads. Serializing acquisition imposes a fair FIFO order on submission so no rank starves, while parallel release keeps token return from becoming the new bottleneck.

KeyDefaultMeaning
sandbox_fusion_url—The FaaS endpoint.
rate_limit10Max concurrent executions globally. The single most important knob; it is a property of your sandbox service's capacity, not of your GPU count.
enable_global_rate_limitTrueWhether the token bucket is active at all.
default_timeout30 sPer-execution wall clock. Interacts with the straggler tail — a long timeout multiplied by max turns is your worst-case trajectory latency.

Grader isolation is on you. If the reward's test suite runs in the same sandbox the agent controls, the policy can find it — writing to the test file, monkey-patching the assertion, or exiting 0. Prime Intellect, which hosts one of the largest environment catalogs, withholds grading material until scoring time and still describes co-locating agent and grader as mitigation rather than a guarantee. Treat any reward computed inside the agent's own sandbox as a reward-hacking surface.

8. The Interaction API — When the Environment Talks Back

Tools model the agent acting on the world. Some tasks need the other direction: a user or environment that responds in the user role — clarifying a request, rejecting a plan, supplying the next observation. That is a separate abstraction, BaseInteraction, configured by multi_turn.interaction_config_path and bounded by max_user_turns alongside max_assistant_turns.

MethodReturnsRole
start_interaction(...)instance_idOpen a session for this rollout.
generate_response(...)(should_terminate, response, score, metadata)Produce the next user-role turn — and decide, per turn, whether the episode ends.
calculate_score(...)scalarTurn-level score, for denser credit assignment than a single terminal reward.
finalize_interaction(...)—Clean up.

The should_terminate flag in the return tuple is the notable bit: the environment, not the agent, holds the stopping decision. That is the right shape for tasks where success is environment-observable — the customer got their refund, the form validated — and it is what lets the same machinery express a simulated-user dialogue and a stateful game with one interface.

The per-turn score is likewise worth using. A single terminal reward over a 15-turn trajectory is a brutal credit-assignment problem; turn-level scores let you shape it. The credit assignment section of the Agentic RL page covers when that helps and when it just adds bias.

9. Back to a DataProto

Whatever the loop did, the trainer needs the same rectangular batch it always got. The worker's _postprocess() does the reconciliation:

prompt_ids    ← left-padded  to prompt_length
response_ids  ← right-padded to response_length
input_ids      = concat(prompt_ids, response_ids)
attention_mask = 1 on real tokens, 0 on padding
position_ids   = (attention_mask.cumsum(dim=1) - 1) * attention_mask

Left-padding the prompt and right-padding the response is the standard trick that puts the prompt/response boundary at a fixed column for every row, so the loss can be sliced without per-row indexing. The position_ids line is doing real work: because padding sits on both ends, positions must be counted over real tokens only, which is exactly what the cumulative sum of the attention mask gives — then multiplied by the mask again to zero out the pad positions.

The result is wrapped in a TensorDict whose meta_info carries per-trajectory turn counts and rollout timing. Log those. Mean turns per trajectory and the truncation rate are the two agentic-specific health metrics that no single-turn dashboard will show you, and both move before reward does. See Async RL Monitoring.

Note where the padding waste lands: response_length must be sized for the longest trajectory, so a batch where most rollouts finish in 3 turns and one takes 14 is mostly padding. This is the multi-turn form of the same length-variance problem that makes agentic rollout throughput so much worse than its token count suggests.

10. Custom Loops, and the Harness-Parity Question

A custom agent loop is one class: inherit AgentLoopBase, implement run(), register it under a name, and point rollout.agent.agent_loop_config_path at it. Inside run() you may do anything — call the LLM, query a database, search the web, run a planner, reflect, recurse — as long as you return an AgentLoopOutput whose three fields are mutually consistent.

verl is explicit that AgentLoopManager is a reference implementation and is meant to be replaceable by another agent framework entirely. That framing matters, because it puts verl on one side of the central design question in agentic RL: do you port your agent into the trainer, or point the trainer at the agent you already ship?

ApproachWhat it optimizesCost
Reimplement in AgentLoopBase Full control of tokenization, masking, and turn accounting — the invariants of §4 are handled for you if you follow the built-in patterns. Your training harness and your production harness are now two codebases that drift. Every prompt tweak in prod is a train/serve mismatch until someone ports it.
Wrap the production agent Harness parity by construction. Cursor trains Composer inside the same harness users hit — same tools, same prompt format, same system message — precisely to kill this mismatch. You must recover token-exact response_ids and a correct mask from an agent that was never written to expose them. Trace-based systems exist for this, but the tokenization seam of §4 is exactly where they get hard.

verl sits closer to the first row, with the escape hatch of the second. If you go that way, the discipline that makes it survivable is to define the tool set and prompt template once, in a form both the trainer and the server load, rather than maintaining two copies that agree by convention.
