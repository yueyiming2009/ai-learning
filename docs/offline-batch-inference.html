Batch Offline Inference

Offline batch jobs have no latency SLO and all inputs are known in advance. The single objective is maximizing output tokens per GPU-hour. Every optimization should be evaluated against this metric.

Offline batch inference is the simplest inference workload from an operational standpoint but the most demanding from a throughput perspective. Common use cases: dataset annotation, embedding generation, evaluation benchmarks, LLM-as-judge pipelines, synthetic data generation, reward model scoring. The user isn't waiting — the job runs overnight or over a weekend. The cost is measured in GPU-hours per million tokens.

2 · The single objective: output tokens / GPU-hour

All tradeoffs should be evaluated against cost per output token. The relevant formula from the compute model: in the memory-bandwidth-bound regime,

Decode throughput ceiling
\[ \text{Throughput}_{\max} = \frac{B \cdot \text{peak\_bw}}{2N \cdot \text{bytes/param}} \]
\(B\) = concurrent tokens in decode step, \(N\) = parameter count, bytes/param = weight precision.
Maximizing throughput means maximizing \(B\) (fill the batch) and minimizing bytes/param (quantize).

There is no latency term in this objective. TTFT (Time to First Token) doesn't matter. Individual request TPOT (Time Per Output Token) doesn't matter. Only the aggregate GPU-wide tokens/second matters. See Batching → TTFT vs. TPOT for definitions.

3 · Optimization stack

Layer 1 — Maximize batch size

The single most impactful lever is running the largest possible decode batch. This means:

  • Pack the KV cache. Use PagedAttention-based allocation to avoid fragmentation waste. Fill all available GPU memory with KV pages.
  • Reduce KV footprint per request. Use models with GQA/MQA (LLaMA-3, Mistral, Qwen2) which have 4–8× fewer KV heads. At fixed GPU memory, this means proportionally more concurrent requests.
  • Limit max output length. Don't set max_new_tokens=2048 if the task never needs more than 256. Each token of output holds a KV slot for the full duration of the request.

Layer 2 — Reduce bytes per parameter (quantization)

For the offline case, the right quantization choice is usually W4A16 (AWQ or GPTQ):

  • W4 halves HBM bandwidth required per decode step compared to W8, roughly doubling throughput in the bandwidth-bound regime.
  • Accuracy loss at W4 is acceptable for most annotation/extraction tasks (MMLU degradation is typically 1–3 points).
  • If accuracy is critical, use W8A8 or FP8 (on H100) — still 2× better than BF16 throughput while near-lossless.

Layer 3 — Length-sorted batching

Static batching pads shorter requests to the length of the longest in the batch, wasting compute proportional to the length variance. Sort all inputs by (input_length + expected_output_length) and form batches of requests with similar lengths. This reduces padding waste from 30–50% to under 5% in typical datasets with wide length distributions.

Layer 4 — Prefix caching for repeated prompts

If the dataset uses a shared system prompt or task instruction, prefix caching via a radix trie stores the KV for the shared prefix once and reuses it across all requests. For a 2K-token system prompt in a 3K-token request, this skips 67% of the prefill work per request — a large TTFL reduction that increases prefill throughput.

Layer 5 — Speculative decoding for greedy/low-temperature tasks

Greedy decoding (temperature=0) has acceptance rate α→1 for a good draft model. From the speculative decoding page, speedup = \(E[\text{tokens}] / (\gamma c + 1)\). At α=0.9, γ=4, c=0.1: \(E[\text{tokens}] = 4.6\), speedup ≈ 3.8×. This is multiplicative on top of the quantization and batching gains.

4 · Offline batch playbook

1
Profile your dataset

Histogram input and output lengths. Identify if there is a shared prefix. Note whether sampling is greedy or stochastic. These three facts determine which optimizations are most valuable.

2
Pick model precision

H100: default to FP8. A100/older: W4A16 (AWQ) for max throughput, W8A16 if accuracy is critical. Validate on a sample of your dataset before committing.

3
Sort inputs by length

Sort all requests by (input_len + estimated_output_len). Use bucket-based batching — group into buckets of ±10% length and serve each bucket with a tightly padded batch. Reduces padding waste 5–10×.

4
Enable prefix caching

Set the shared prompt prefix as a prefix to cache. Even for a 512-token instruction prefix shared across 100K requests, the cumulative prefill savings are substantial: 512 × 100K = 51M input tokens avoided.

5
Enable speculative decoding (if greedy)

Add a small draft model (same family, 1B-7B) with γ=4–6. Measure wall-clock throughput vs. baseline. If α>0.8 for your task, expect 2–4× speedup.

6
Saturate the batch

Set max_num_seqs (vLLM) or equivalent as high as KV memory allows. Monitor GPU memory utilization — target >90%. If below, increase concurrent requests. If OOM, reduce max_tokens or switch to INT8 KV.

7
Scale horizontally

Multiple independent GPU workers process disjoint shards of the dataset in parallel. No coordination needed (unlike online serving). Linear throughput scaling with GPU count.

6 · Summary

Core metric

Output tokens per GPU-hour. No latency SLO. All throughput optimizations apply simultaneously.

Top lever

Max batch size + quantization. W4A16 roughly doubles throughput vs. BF16 in the bandwidth-bound regime.

Often overlooked

Length-sorted batching. Wide length distributions cause 30–50% padding waste in naive batching — sort by length first.

Greedy tasks

Speculative decoding with a small draft model achieves 2–4× additional speedup when α > 0.8.

Scaling

Horizontal scaling is trivial — partition dataset, one GPU fleet per shard. Linear scaling with GPU count.

Key tools

vLLM offline batch API, SGLang, TensorRT-LLM. All support PagedAttention + continuous batching + quantization.
