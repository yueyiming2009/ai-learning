KV Cache — Trading Memory for Compute

Without caching, each decode step recomputes key and value projections for every prior token — cost grows quadratically with context length. The KV cache stores these tensors once and reuses them, at the price of GPU memory that directly caps how many requests can run concurrently.

Autoregressive generation requires the new token at position \(t\) to attend over all prior tokens \(0 \ldots t-1\). Naively, that means recomputing the key and value projections for every prior token at every step. The KV cache is the solution: compute K and V once per token (during prefill or the step that generated it) and store the result — so each decode step only computes K and V for the one new token, and reads the rest from cache. This turns quadratic cost into linear, at the expense of memory.

1 · The recomputation problem

In a decoder-only transformer, attention at position \(t\) is:

Attention at decode step t
\[ \text{Attn}(q_t, K_{0:t}, V_{0:t}) = \text{softmax}\!\left(\frac{q_t K_{0:t}^{\!\top}}{\sqrt{d_h}}\right) V_{0:t} \]
\(q_t\) is the query for the new token; \(K_{0:t}, V_{0:t}\) are keys and values for all tokens \(0\) through \(t\).

Computing \(K_{0:t}\) and \(V_{0:t}\) requires projecting all prior hidden states through \(W_K\) and \(W_V\):

Without KV cache — recomputation cost

At decode step \(t\), to compute \(k_j = W_K x_j\) and \(v_j = W_V x_j\) for all \(j < t\), the model must execute \(2t\) matrix-vector products per layer. Over a full generation of \(T_d\) output tokens, the total recomputation cost for the attention projections grows as \(O(T_d^2)\) — it doubles every time the output length doubles.

For a 7B model generating 2K tokens with \(L = 32\) layers: roughly \(\sum_{t=1}^{2048} 2 \times t \times 2 \times 32 \approx 8.6 \times 10^9\) redundant matrix-vector products — equivalent to an extra forward pass through the entire model for every other step.

The solution is trivial in principle: once a token's K and V are computed (during prefill, or when the token is first generated), cache them. Subsequent decode steps append one new K and V entry per layer, and read the full cache for attention.

2 · What the cache stores

After the prefill phase, the KV cache holds, for each transformer layer \(\ell\):

  • \(K^\ell \in \mathbb{R}^{T \times h_{\rm kv} \times d_h}\) — all key projections for the \(T\) prompt tokens.
  • \(V^\ell \in \mathbb{R}^{T \times h_{\rm kv} \times d_h}\) — all value projections for the \(T\) prompt tokens.

\(h_{\rm kv}\) is the number of KV heads (equal to query heads in MHA; smaller with GQA/MQA — §6) and \(d_h\) is the head dimension. Each decode step extends the cache by appending one new row to \(K^\ell\) and \(V^\ell\) across all layers.

The access pattern during a single decode step:

One decode step with KV cache
  1. Compute \(q_t = W_Q^\ell \cdot x_t\) — new query for the current token (one matrix-vector multiply).
  2. Compute \(k_t = W_K^\ell \cdot x_t\) and \(v_t = W_V^\ell \cdot x_t\) — new key and value (two more matrix-vector multiplies).
  3. Append \(k_t\) and \(v_t\) to the cache: \(K^\ell \leftarrow [K^\ell;\, k_t]\), \(V^\ell \leftarrow [V^\ell;\, v_t]\).
  4. Read the full cache \(K^\ell, V^\ell\) from HBM to compute the attention scores and weighted sum.

In code, this is a pre-allocated buffer filled one slot at a time:

import torch

# Pre-allocate KV buffers for one layer; T_max = maximum context length
# Shape: [T_max, h_kv, d_h]
K_cache = torch.zeros(4096, 8, 128, dtype=torch.bfloat16, device="cuda")
V_cache = torch.zeros(4096, 8, 128, dtype=torch.bfloat16, device="cuda")

def decode_step(x_t, W_Q, W_K, W_V, t):
    # x_t: [1, D] — hidden state of the single new token
    q_t = x_t @ W_Q     # [1, h_q, d_h]
    k_t = x_t @ W_K     # [1, h_kv, d_h]
    v_t = x_t @ W_V     # [1, h_kv, d_h]

    K_cache[t] = k_t    # O(1) append — one slot written
    V_cache[t] = v_t

    K = K_cache[:t+1]   # O(T) HBM read — all prior keys
    V = V_cache[:t+1]

    scale  = K.shape[-1] ** 0.5
    scores = (q_t @ K.transpose(-2, -1)) / scale  # [1, h_q, T]
    return  (scores.softmax(-1) @ V)               # [1, h_q, d_h]

The key insight: steps 1–3 require \(O(1)\) new computation per layer. Step 4 reads \(O(T)\) bytes — growing with context length, but serving as a simple sequential HBM read rather than recomputed matrix multiplications.

3 · Memory cost formula

The total KV cache size for a single request at context length \(T\) (prompt + generated tokens):

KV cache per request
\[ \text{KV bytes} = 2 \;\times\; L \;\times\; h_{\rm kv} \;\times\; d_h \;\times\; T \;\times\; \text{bytes\_per\_element} \]
Factor of 2 for K and V. Bytes per element: 2 (FP16/BF16), 1 (INT8 or FP8), 0.5 (INT4).

Worked out for two representative models at FP16 (\(\text{bytes} = 2\)):

4 · The memory–throughput bottleneck

The model weights occupy a fixed slice of GPU memory. The KV cache occupies everything that remains. The available KV budget directly caps the maximum batch size, which in turn caps inference throughput:

Maximum concurrent requests
\[ B_{\max} = \left\lfloor \frac{M_{\rm GPU} - M_{\rm weights}}{\text{KV bytes per request}} \right\rfloor \]

This is why KV cache management is the central resource allocation problem in serving systems. Three levers reduce the per-request KV footprint:

  1. KV quantization — store K and V in INT8 or FP8 instead of FP16. Halves memory with modest quality impact. More sensitive than weight quantization because attention scores are sensitive to small perturbations in K values.
  2. Shorter context — truncate prompts, use RAG to replace long contexts with relevant excerpts, or apply sliding-window attention for very long sequences.
  3. GQA / MQA — reduce \(h_{\rm kv}\) through architectural changes. Up to 8× reduction with no inference-time overhead (§6).
Memory fragmentation is a separate problem: if each request pre-allocates a contiguous \(T_{\max}\)-length KV buffer, short requests waste most of it. PagedAttention (covered later in this series) solves fragmentation by paging the KV cache into fixed-size blocks, similar to OS virtual memory.

5 · Prefix caching and sharing

Many production workloads send the same long system prompt with every request — a shared preamble that can be hundreds or thousands of tokens. Without prefix caching, each request recomputes (and re-stores) the KV cache for this shared prefix independently.

Prefix caching — compute once, share across requests

When the KV cache for a token prefix is already stored from a prior request, a new request with the same prefix skips its prefill for those tokens entirely. It reads the cached K and V blocks directly, reducing TTFT for all requests that share the prefix.

Savings: if a 2K-token system prompt is shared by 100 requests, prefix caching replaces 100 prefill computations with 1 and 99 cache reads. Memory: the shared prefix occupies one set of KV blocks instead of 100.

Radix-trie structure (SGLang)

SGLang implements prefix caching via a radix trie over token sequences. Each node in the trie represents a token subsequence and stores a pointer to the corresponding KV blocks. Lookup is O(prefix length). When two requests share a prefix to some depth, they reference the same trie node — and the same physical KV memory.

Copy-on-write at divergence

Once two requests diverge (their token sequences differ), they must have independent KV state. The serving system uses copy-on-write: shared blocks remain shared and read-only; the first write (appending a new token to a block that is shared) triggers a copy of that block into a request-private one. This ensures correctness without eagerly duplicating memory.

Prefix caching only helps when the same prefix appears in multiple requests. For diverse workloads with no repeated prompts, the memory overhead of maintaining the trie is wasted. Production systems typically enable it for API endpoints with system prompts, and disable it for offline batch jobs.

6 · GQA, MQA, and MLA — shrinking the cache footprint

Standard multi-head attention (MHA) uses \(h\) query heads and \(h\) KV heads. The KV cache scales with \(h_{\rm kv} = h\). Three architectural variants reduce \(h_{\rm kv}\):

VariantKV heads \(h_{\rm kv}\)Cache reduction vs. MHAQuality impactExamples
MHA — Multi-Head Attention \(h\) 1× Baseline LLaMA-2 7B, GPT-2
GQA — Grouped-Query Attention \(h / g\) (group size \(g\)) \(g\)× (typically 4–8×) Minor degradation vs. MHA; preferred sweet spot LLaMA-3, Mistral, Qwen
MQA — Multi-Query Attention 1 \(h\)× (maximum) Noticeable quality loss at large scale PaLM, Falcon
MLA — Multi-head Latent Attention Compresses K, V into a low-rank latent vector per token; expanded at attention time Near-MHA quality with very low KV memory DeepSeek-V2/V3

GQA mechanics

GQA partitions the \(h\) query heads into \(g\) groups of \(h/g\) heads each. Each group shares a single K and V head. In the attention computation, each query head attends using the K and V of its group — so all \(h\) outputs are distinct, but only \(h/g\) KV heads need to be stored. The arithmetic is identical to MHA; only the number of KV projections is reduced.

GQA vs. MHA — LLaMA-2 70B example
  • MHA baseline: \(h = 64\), \(h_{\rm kv} = 64\). KV at T=4K, FP16: \(2 \times 80 \times 64 \times 128 \times 4096 \times 2 \approx 10\) GB per request.
  • GQA (g=8): \(h_{\rm kv} = 8\). Same formula: \(\approx 1.25\) GB per request — an 8× reduction. On a 80GB H100 with 140 GB model weights across 2 GPUs (TP-2), available KV budget goes from ~30 GB to ~62 GB, supporting ~24× vs. ~3 concurrent requests at T=4K.

MLA (DeepSeek-V2/V3)

Instead of caching full K and V tensors, MLA caches a low-rank compressed latent vector \(c_t \in \mathbb{R}^{d_c}\) (with \(d_c \ll h \cdot d_h\)) and expands K, V from it at attention time via learned up-projection matrices. This achieves KV memory near the MQA floor while preserving near-MHA expressivity. The trade-off: a small compute overhead per attention call to perform the up-projection.

7 · Summary

What's cached

K and V projections per layer, per token. Appended each decode step; read in full for every attention computation.

Memory formula

\(2 \times L \times h_{\rm kv} \times d_h \times T \times \text{bytes}\). Grows linearly with context length and number of KV heads.

The bottleneck

Available GPU memory after weights sets a hard cap on concurrent requests. More KV memory = more batching = higher throughput.

Prefix sharing

Shared system prompts compute KV once and reference the same blocks across all requests. Radix-trie lookup enables this efficiently.

GQA sweet spot

\(g = 8\) reduces KV memory 8× with minimal quality loss. Now the default for modern 7B–70B models.

What's next

PagedAttention eliminates fragmentation via KV block paging. KV quantization halves bytes. Continuous batching maximizes the budget's utility.
