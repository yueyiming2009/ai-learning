Online Inference: SLO-Driven Serving

Online serving must satisfy two latency SLOs simultaneously: TTFT (time to first token) and TPOT (time per output token). Both can be violated independently, and the system must keep both within budget while maximizing throughput and minimizing GPU cost.

Online serving is the most constrained inference workload. Users are waiting — each extra 100 ms of TTFT is a perceptible delay before the response appears; each extra 50 ms of TPOT is visible as a slower streaming rate. The system must balance user experience against GPU cost, handling spiky demand without over-provisioning.

2 · TTFT and TPOT SLOs

From the compute model: TTFT is dominated by prefill time (scales with input length and is compute-bound), while TPOT is determined by the decode bottleneck (bandwidth-bound at practical batch sizes). These are independent constraints with different levers:

TTFT budget decomposition

For a typical P99 TTFT budget of 500 ms, the time is spent as:

Network + queue: ~50ms
Prefill compute: ~300ms (8K prompt @ H100)
First token gen: ~50ms
Buffer: ~100ms

Long prompts consume almost the entire TTFT budget in prefill. With an 8K prompt on H100 (prefill throughput ~300 TFLOP/s effective, 8B model), prefill alone takes ~100 ms. A 32K prompt takes ~400 ms — violating a 500 ms TTFT SLO. Chunked prefill or disaggregation is needed.

TPOT budget

A 50 ms TPOT target at N=70B BF16 requires decode throughput of at least \(B \geq 50\text{ ms} \times \text{BW} / (2N \cdot 2\text{ bytes}) = 0.05 \times 3.35\text{e}12 / (2 \times 70\text{e}9 \times 2) \approx 600\) concurrent tokens. This means the system must have at least 600 active decode tokens in flight simultaneously to hit the TPOT floor — impossible if there are fewer concurrent users. At lower load, TPOT is better than the SLO, which is fine.

3 · The latency–throughput tradeoff curve

Online serving faces a fundamental tradeoff: increasing batch size (more concurrent users) improves GPU utilization and throughput but increases per-request latency due to queuing and resource contention. The operating point must be chosen to keep P99 latency within SLOs while maximizing concurrency.

Good utilization target

Target GPU memory utilization at ~85–90% (leave 10–15% headroom for new arrivals and bursty prefills). Target inference GPU compute utilization at ~70–80% (leave headroom for TPOT SLO during load spikes). Operating at 95%+ memory triggers preemptions; operating at 95%+ compute causes persistent TPOT SLO violations.

4 · Optimization stack for online serving

Continuous batching — non-negotiable baseline

Continuous batching is mandatory for any production serving system. It eliminates the idle waiting in static batching, enabling 5–10× better GPU utilization. All modern serving frameworks (vLLM, SGLang, TGI, TensorRT-LLM) implement it.

PagedAttention — memory fragmentation elimination

PagedAttention is equally non-negotiable. Without it, KV memory fragmentation limits effective concurrent requests to 20–40% of the GPU's KV capacity. With it, 90%+ memory utilization is achieved.

Chunked prefill — TPOT smoothing under mixed load

For workloads with varied prompt lengths, enable chunked prefill with a chunk size C tuned so that each chunk takes ~20% of the TPOT budget. This prevents long prefills from causing TPOT spikes for other users. Typical C = 512–2048 tokens per chunk.

Quantization — TPOT floor reduction

On H100, default to FP8 (Transformer Engine). This halves the TPOT floor vs. BF16, allowing the same TPOT SLO to be met with half the GPU count, or doubling the number of concurrent users at the same hardware cost. FP8 quality loss is near-zero for most conversational tasks.

Prefix caching — TTFT reduction for templated prompts

If requests share a common system prompt, prefix caching via a radix trie eliminates the prefill cost for the shared prefix. For a 2K-token system prompt, this reduces TTFT by up to 80% for short user messages — making the difference between hitting and violating the TTFT SLO.

Speculative decoding — TPOT reduction at low-to-medium load

Speculative decoding helps when the decode batch is small (low concurrency). At high concurrency, the batch is large enough that the GPU is saturated and speculative decoding doesn't improve wall-clock TPOT. Add speculative decoding for chatbot workloads where user queries tend toward common continuations.

CUDA graph capture — per-step launch overhead

With eager execution, each decode step pays CPU kernel-launch overhead for every CUDA op in the step. CUDA graph capture records the step once and replays it with minimal CPU involvement. In vLLM, this is enabled by default (enforce_eager=False). In online serving, where TPOT is the primary SLO, eliminating this overhead reduces median TPOT by 5–15% and flattens the TPOT curve at mid-concurrency.

FlashAttention-3 and tensor/pipeline parallelism

FlashAttention-3 (H100/H200): async-pipelined attention kernel that saturates HBM bandwidth on the attention GEMM. Enabled by default in vLLM/SGLang on H100.

Tensor / pipeline parallelism (TP/PP): when the model does not fit on a single GPU, shard it across GPUs using TP (within a node) or PP (across nodes). For a 70B model on H100-80GB (140 GB weights in BF16), TP=2 is the minimum. TP reduces per-GPU memory but introduces AllReduce collectives per decode step — each collect adds ~5–10 ms on NVLink at TP=8. Minimize TP size and prefer data-parallel replicas for throughput when the model fits on fewer GPUs.

5 · Prefill–decode disaggregation at scale

At production scale (20+ GPUs, mixed prompt lengths), prefill–decode disaggregation removes the fundamental hardware compromise:

  • Prefill workers (compute-optimized) handle all prompt processing. They are scaled to handle peak prefill token rate.
  • Decode workers (bandwidth-optimized) run continuous batching at maximum concurrency. They are scaled to maintain TPOT SLO at peak output token rate.
  • The prefill-to-decode worker ratio is tuned based on the actual prefill:decode token ratio in traffic, which can be measured from request logs.

The key benefit for online serving: TPOT SLO is now guaranteed independently of prefill traffic spikes. A burst of long-prompt requests fills the prefill worker queue but doesn't affect the decode pool.

Autoscaling is critical for online serving cost efficiency. Track tokens/second and P99 TPOT; scale up when P99 TPOT exceeds 80% of SLO for 2+ minutes and scale down when GPU utilization falls below 50% for 10+ minutes. Latency SLOs have hysteresis — build in head room before scaling decisions trigger.

7 · Summary

Dual constraint

TTFT (dominated by prefill latency) and TPOT (dominated by decode bandwidth) must both stay within SLO.

Non-negotiable baseline

Continuous batching + PagedAttention. Every production system needs both. FP8 on H100 adds zero quality cost for a 2× TPOT improvement.

TTFT management

Chunked prefill (aggregated serving) or prefill–decode disaggregation (at scale) prevents long prompts from spiking TPOT for other users.

Cost efficiency

Target 70–80% GPU compute utilization. Autoscale on P99 TPOT. FP8 quantization halves GPU count needed to meet the same TPOT SLO.

Scale threshold

Disaggregation pays off at 20+ GPUs with high-bandwidth interconnect and mixed prompt length traffic.

Monitoring

Track P50/P95/P99 TTFT and TPOT separately. A P99 spike in TPOT while P50 is fine indicates prefill interference — add chunked prefill.
