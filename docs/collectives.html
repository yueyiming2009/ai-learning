Sharding & Collectives — The Communication Math

Every flavor of parallelism is the same matmuls and norms you already know, split across devices and stitched back with four collective operations. This page builds the notation and the cost model: how a sharded array is described, what communication a sharded matmul forces, and exactly how much each collective costs.

Training a large model on ten thousand accelerators looks, abstractly, identical to training on one: the same matmuls, the same nonlinearities, the same backward pass. The only new thing is that the arrays no longer fit in the memory of a single device, so we split them up — we shard (or partition) them across a mesh of devices. The moment a computation needs to reduce or contract along a dimension that has been split, the devices must talk, and that conversation is a collective.

This is the foundation page for the whole parallelism series. Tensor, data, pipeline, sequence, and expert parallelism are all just different choices of which array dimensions to shard — and the bill always comes due in the same four collectives priced below. Get this page right and the rest is bookkeeping.

The cost model here follows the partitioning notation popularized by “How to Scale Your Model” (Google DeepMind). It is written for a ring-connected mesh (TPU ICI, NVLink islands), but the FLOPs-vs-bytes reasoning transfers to any topology.

1 · Why we shard

A 70B-parameter model in bf16 is 140 GB of weights alone. Add the Adam optimizer state — two moments plus an fp32 master copy, roughly 6 bytes more per parameter on top of the weights — and the resident footprint is well past 1 TB before a single activation is stored. No accelerator has that much high-bandwidth memory (HBM is \(O(10\!-\!100)\) GB per chip). So we cut each array into blocks and scatter them across many devices.

A sharded array has two shapes:

  • a global (logical) shape — what the math sees, e.g. a weight matrix \([D, F]\);
  • a device-local shape — the block that physically lives on one device, e.g. \([D, F/|X|]\) if the second axis is split across \(|X|\) devices.

The art is choosing shardings so that as much arithmetic as possible stays local (no communication), and so that the communication you cannot avoid is the cheap kind.

2 · A notation for sharding

Picture the devices arranged in a grid — a device mesh — whose axes are given names \(X, Y, Z\). The mesh axis \(X\) has \(|X|\) devices along it. We then describe a sharding by writing, next to each logical array axis, which mesh axis it is split over, as a subscript.

Reading the notation
  • A[IX, JY] — the array \(A\) with its first axis \(I\) split across mesh axis \(X\) and its second axis \(J\) split across \(Y\). Each device holds \(1/(|X|\,|Y|)\) of the tensor.
  • No subscript ⇒ replicated. A[I, JX] means \(I\) is fully present on every device; only \(J\) is split.
  • A[IXY, J] — axis \(I\) split across the flattened \(X\!\times\!Y\) mesh (all \(|X||Y|\) devices). Subscript order sets the traversal order across the grid.
  • Rule: a given mesh axis may appear at most once across a tensor — you cannot shard two logical axes onto the same physical axis (there aren’t enough devices to be in two places at once).

The unreduced marker \(\{U_X\}\)

There is one more state an array can be in, and it is the crux of the whole subject. Suppose two operands are each split along a contracting dimension. Every device can multiply its local blocks, but the product it gets is only a partial sum — the piece of the dot product that used the data it happened to hold. The full result is the sum of these partials across the mesh. We mark that “sum still owed” state as

Unreduced along X
C[I, K] {UX}  —  “each device on \(X\) holds a different partial sum; a reduction along \(X\) is pending.”

\(\{U_X\}\) is not a sharding (every device has a full-shape \([I,K]\) array) and it is not replication (the arrays disagree). It is an obligation. Resolving it — turning partial sums into the true sum — is exactly what the reducing collectives do.

3 · The ring cost model

Accelerators in a training mesh are wired as a ring (or torus): each device has a fast link to its neighbors, not an all-to-all crossbar. Every collective below is, under the hood, the same motion — each device passes a block to a neighbor, again and again, around the ring. So one cost model prices them all.

Let a collective move an array of \(V\) bytes around a ring of \(N=|X|\) devices, where each device starts with a \(V/N\) shard, and let \(W\) be the (bidirectional) per-link bandwidth. To get every shard to every device, each link must carry \(N-1\) of the \(N\) shards. The link is the bottleneck, so the time is the bytes-per-link divided by the bandwidth:

Throughput-bound collective time
\[ T \;=\; \underbrace{\frac{V}{W}}_{\text{full array}}\cdot\frac{N-1}{N} \;\xrightarrow[\;N\ \text{large}\;]{}\; \frac{V}{W}. \]

Two facts fall out of this, and they drive every parallelism decision in the series:

  1. The cost barely depends on \(N\). For \(N\ge 4\) the factor \((N-1)/N\) is already within 25% of 1. Adding more devices to a ring does not make its collectives meaningfully slower — even though the devices are only locally connected, locality doesn’t bite. You are bottlenecked by the speed of a single link, not by the diameter of the ring.
  2. The cost scales with the array size \(V\), not the mesh. So the lever you actually control is how big the communicated tensors are — which is what each parallelism scheme trades against.

Latency floor and the small-message regime

Reaching every device takes \(O(N)\) hops, and each hop has a fixed latency \(T_{\min}\) (≈1 µs on typical hardware) regardless of payload. So the real cost is a max of the two regimes:

\[ T \;=\; \max\!\Big(\; \underbrace{N\,T_{\min}}_{\text{latency-bound}}\;,\; \underbrace{\tfrac{V}{W}\cdot\tfrac{N-1}{N}}_{\text{bandwidth-bound}} \;\Big). \]

Big reductions (the gradients and activations of training) are solidly bandwidth-bound; tiny ones (a single token at sampling time) are latency-bound. The crossover is \(V \approx N\,T_{\min} W\): for a device with \(W\!\approx\!45\) GB/s and \(T_{\min}\!\approx\!1\,\mu\text{s}\), anything under ~45 kB is latency-bound.

Multiple mesh axes add bandwidth. Gathering over two mesh axes at once uses both sets of links, so the effective bandwidth is \(W\cdot n_\text{axes}\) and the time drops by that factor. This is why a 2-D torus beats a 1-D ring for the same device count.

4 · AllGather — undo a sharding

The first primitive removes a subscript: it reassembles a split axis so every device ends up with the full, un-sharded array along that axis.

AllGather over X
A[I, JX]  →  A[I, J]

Mechanically: each device sends its shard to a neighbor around the \(X\) ring, keeping every shard it receives, until all \(|X|\) shards have visited all \(|X|\) devices. That is \(N-1\) hops carrying \(V/N\) each, so by the model above:

AllGather cost
\[ T_\text{AG} \;=\; \frac{V}{W\,n_\text{axes}}\cdot\frac{|X|-1}{|X|}\;\approx\;\frac{V}{W}, \qquad V = \text{bytes of the full (gathered) array.} \]

AllGather does not have to remove all sharding — it can collapse one mesh axis while leaving others — and, in a matmul, you are free to do it before or after the local multiply, whichever keeps the moved tensor smaller.

▸ AllGather on a 4-device ring Each device starts with one shard; after 3 hops everyone has all four.
Hop 0 / 3 — each device holds only its own shard.

5 · ReduceScatter — reduce, but stay split

ReduceScatter resolves an unreduced axis and leaves the result sharded. It is the same ring motion as AllGather, except that instead of keeping each block a device receives, it adds the block into its running shard. Each device walks away owning the fully-summed value of just one slice.

ReduceScatter over X, sharding the J axis
A[I, J] {UX}  →  A[I, JX]

Because it does the same amount of link work as AllGather — \(N-1\) shard-hops — it costs the same:

\[ T_\text{RS} \;=\; \frac{V}{W\,n_\text{axes}}\cdot\frac{|X|-1}{|X|}\;\approx\;\frac{V}{W}. \]

Note the freedom: a ReduceScatter introduces a new sharded dimension, and you get to pick which one. Resolving \(\{U_X\}\) on a \([I,K]\) array, you may land on either A[IX, K] or A[I, KX] — the modeling context usually forces the choice, which is why we write the target axis explicitly, e.g. ReduceScatterX,K.

6 · AllReduce — reduce and replicate

The most familiar collective (it is what vanilla data-parallel training calls on its gradients) resolves an unreduced axis and leaves the true sum replicated on every device.

AllReduce over X
C[I, K] {UX}  →  C[I, K]

But notice what it is: first sum the partials and scatter (ReduceScatter), then gather the scattered sums back to everyone (AllGather). Two ring traversals.

AllReduce = ReduceScatter ∘ AllGather
\[ T_\text{AR} \;=\; T_\text{RS} + T_\text{AG} \;=\; 2\cdot\frac{V}{W}\cdot\frac{|X|-1}{|X|}\;\approx\;\frac{2V}{W}. \]
AllReduce is twice the price of the others. Whenever the downstream computation can live with a sharded result, prefer a ReduceScatter and skip the gather — you only pay to re-replicate when you actually need the full array on every device. Half the comm volume of a layer can hinge on this single choice.

7 · AllToAll — move a subscript sideways

The fourth primitive is a resharding / transpose: it takes an axis that is split and replicates it, while splitting a different axis along the same mesh dimension. It is how a computation hands off between two regions that want incompatible layouts — most notably the token routing around a Mixture-of-Experts block.

AllToAll over X
A[IX, J]  →  A[I, JX]

Because an AllToAll never needs to replicate a whole shard onto every device — each device only ships the slice destined for each peer — the data travels, on average, only a quarter of the way around a bidirectional ring:

\[ T_\text{A2A} \;\approx\; \tfrac{1}{4}\,T_\text{AG} \;=\; \frac{1}{4}\cdot\frac{V}{W}\cdot\frac{|X|-1}{|X|}. \]

8 · What a sharded matmul forces

Now the payoff. Take any matmul \(A \cdot B \to C\) contracting over a shared axis \(J\). Whether it needs communication — and which collective — is decided entirely by how the contracting axis \(J\) is sharded. Three cases cover everything.

Case 1 — contracting axis not sharded → free

A[IX, J] · B[J, KY] → C[IX, KY]
Each device holds whole rows and whole columns of the contraction, so the local block product is already a correct shard of the output. No communication. The output simply inherits the input shardings on the non-contracting axes.

Case 2 — one operand sharded on the contraction → AllGather

A[I, JX] · B[J, K] → C[I, K]
\(A\) is missing the rest of its contracting axis. AllGather it first, then multiply locally:
AllGatherX: A[I, JX] → A[I, J], then A[I, J] · B[J, K] → C[I, K]. Cost = one AllGather.

Case 3 — both operands sharded on the contraction → AllReduce or ReduceScatter

A[I, JX] · B[JX, K] → C[I, K] {UX}
Local block products are valid partial sums — the output is born unreduced. Resolve it:

  • need the full result everywhere → AllReduceX (cost \(2V/W\)); or
  • happy to keep it split → ReduceScatterX → C[I, KX] (cost \(V/W\), half as much).

Non-contracting dimensions never force communication — they pass their sharding straight from inputs to output. And a sharding that puts the same mesh axis on two axes of one tensor, e.g. A[IX, J] · B[J, KX] → C[IX, KX], is simply illegal (\(X\) can’t appear twice); you fix it by AllGathering one of the axes before the multiply.

The one-sentence summary of Section 8

A sharded matmul is free unless its contracting axis is split — in which case you pay one AllGather (if one operand is split) or one AllReduce / ReduceScatter (if both are). Every parallelism scheme in this series is a way of arranging matmuls to land in Case 1 as often as possible, and to make the unavoidable Case 3 reductions small.

9 · Forward/backward duality

A convenient theorem ties the collectives together under autodiff: the backward pass of an AllGather is a ReduceScatter, and vice versa. Intuitively, if the forward pass copied a shard to many devices (AllGather), then in the backward pass many devices each produce a gradient contribution for that shard, and those must be summed back down (ReduceScatter).

Adjoint pairs
AllGatherX (fwd)  ⟺  ReduceScatterX (bwd)
ReduceScatterX (fwd)  ⟺  AllGatherX (bwd)
AllReduceX (fwd)  ⟺  AllReduceX (bwd, self-adjoint)

This is why counting communication for a forward pass immediately gives you the backward cost: replace each collective with its dual (same price), and an AllReduce stays an AllReduce. It is also why the tensor-parallel Megatron block reports “one AllReduce forward, one AllReduce backward” — the same self-adjoint reduction shows up on both legs.

10 · Summary

CollectiveWhat it doesSharding changeTime (throughput-bound)
AllGather Reassemble a split axis; remove a subscript. A[JX] → A[J] \(V/(W\,n_\text{axes})\)
ReduceScatter Sum a partial axis and re-split along another; add a subscript. A{UX} → A[JX] same as AllGather
AllReduce Sum a partial axis; replicate the result. Removes a \(\{U_X\}\). A{UX} → A \(2\times\) AllGather
AllToAll Replicate one axis while splitting another on the same mesh axis (resharding / transpose). A[IX] → A[JX] \(\tfrac14\times\) AllGather
Sharding

A mesh names physical axes \(X,Y\); a sharding maps logical array axes onto them. No subscript = replicated; \(\{U_X\}\) = a sum still owed.

When comm happens

Only when you reduce/contract along a sharded axis. Element-wise ops on sharded arrays are always free.

The cost law

\(T \approx V/W\), set by the moved-array size \(V\) and link bandwidth \(W\) — almost independent of device count.

Cheapest first

Prefer ReduceScatter (\(V/W\)) over AllReduce (\(2V/W\)); AllToAll is cheapest (\(V/4W\)). Keep results sharded when you can.
