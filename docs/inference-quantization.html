Quantization for Inference

LLM decode loads the full model weights each step — cutting bytes per parameter directly cuts TPOT. Quantization reduces weight precision to INT8, INT4, or FP8, trading a small accuracy loss for a proportional throughput gain in the memory-bound regime, and for memory footprint reduction in all regimes.

From the compute model: decode is memory-bandwidth-bound at practical batch sizes, with TPOT bounded below by \(2N / \text{peak\_bw}\). This floor scales with bytes per parameter — halving precision halves the floor. Quantization is the most direct lever to improve decode throughput without changing model architecture or buying faster hardware.

1 · Why quantization helps inference more than training

Decode is bandwidth-bound → bytes per weight is the lever

At small batch sizes (\(B \ll I^*\)), the GPU is bottlenecked by HBM bandwidth. Adding more compute (larger GPU) doesn't help — the silicon is already idle waiting for weight transfers. Reducing bytes per weight at fixed bandwidth directly reduces load time:

\[ \text{TPOT}_{\min}(k\text{-bit}) = \frac{k/16 \cdot 2N}{\text{peak\_bw}} = \frac{k}{16} \times \text{TPOT}_{\min}(\text{FP16}) \]

INT8 (\(k=8\)): half the TPOT floor. INT4 (\(k=4\)): quarter. This is a direct 2× or 4× throughput gain in the bandwidth-limited regime.

Training is compute-bound for most of the run — the model weights cycle through the GPU fast enough that weight size is not the primary limit. Quantization during training is used to save memory (for larger models or batches) or to access faster hardware paths, but the throughput argument is much weaker than for inference.

Impact on memory footprint
\[ \text{Model memory}(k\text{-bit}) = \frac{k}{16} \times \text{Model memory}(\text{FP16}) \]
70B FP16: 140 GB. INT8: 70 GB (fits on one H100 80GB instead of two). INT4: 35 GB. Fitting a larger model on fewer GPUs also eliminates inter-GPU communication overhead.

2 · Weight-only quantization (W4A16, W8A16)

In weight-only quantization (W\(k\)A16), model weights are stored in reduced precision (\(k\)-bit integers) but activations remain in FP16. Before each matrix multiply, weights are dequantized back to FP16 on-the-fly on the GPU. The actual computation uses FP16 Tensor Cores.

W8A16 — INT8 weights, FP16 compute

Each weight \(w\) is stored as a signed 8-bit integer with a scale factor \(s\) (and optionally a zero-point \(z\)): \(w_{\rm float} = s \cdot (w_{\rm int8} - z)\). Scale factors are stored per-tensor or per-channel (one scale per output dimension) to reduce quantization error on channels with large values.
Dequantization: load 1 byte per weight from HBM instead of 2 → halves effective weight bandwidth. Convert to FP16 in registers (single instruction). Proceed with FP16 matmul.

W4A16 — INT4 weights, FP16 compute

Weights stored as 4-bit integers with per-group scales (one scale per 128 weights, for example). Two weights packed into one byte. Dequantize pairs to FP16 before the matmul. Group quantization: instead of one scale per channel (which can't capture sub-channel variation), use one scale per group of \(g\) consecutive weights within a channel. Smaller groups (\(g = 64\) or \(g = 128\)) reduce quantization error at the cost of more scale storage.

The key tradeoff of weight-only vs. W+A quantization:

Weight-only vs. weight+activation
  • Weight-only (W4/W8 A16): weights are stored compressed and load faster from HBM → bandwidth gain. But the actual matmul runs in FP16, so there is no compute speedup. Gains are purely from reduced weight bandwidth. This is the right choice in the memory-bandwidth-bound regime (small batch, single user).
  • Weight+activation (W8A8, FP8): both weights and activations are quantized → use hardware INT8 or FP8 Tensor Cores, which run at higher throughput than FP16. This provides a compute speedup in addition to bandwidth reduction. The right choice at large batch sizes where the model is compute-bound.

3 · Weight + activation quantization (W8A8)

Quantizing activations is harder than quantizing weights: activations have dynamic values that change per-token and are not known at calibration time. The challenge is that LLM activations have large outliers — a small fraction of channels consistently have values 10–100× larger than average, making uniform quantization inaccurate.

SmoothQuant — migrating quantization difficulty

SmoothQuant observes that weights are smooth (small per-channel variance) while activations have outliers. It introduces a per-channel scaling factor \(s_j\) that migrates the quantization difficulty:

SmoothQuant transformation
\[ Y = (X \cdot \text{diag}(s)^{-1}) \cdot (\text{diag}(s) \cdot W) \]
\(\hat{X} = X \cdot s^{-1}\) is easier to quantize (outliers reduced). \(\hat{W} = \text{diag}(s) \cdot W\) absorbs the scale into the weights (still easy to quantize). Both \(\hat{X}\) and \(\hat{W}\) quantize well to INT8.

The scale \(s_j = \max(|x_j|)^\alpha / \max(|w_j|)^{1-\alpha}\), with \(\alpha \in [0,1]\) controlling how much of the difficulty is pushed to weights vs. activations. \(\alpha = 0.5\) works well in practice. The transformation is absorbed into the preceding layer's weights at deployment time — zero runtime overhead.

4 · FP8 — the production sweet spot

H100 and later GPUs support FP8 Tensor Cores natively via NVIDIA's Transformer Engine. FP8 offers a middle ground between FP16 quality and INT8 throughput:

FormatBitsRepresentationRangeUse case
E4M381 sign, 4 exponent, 3 mantissa[-448, 448]Weights and forward-pass activations
E5M281 sign, 5 exponent, 2 mantissa[-57344, 57344]Gradients (larger range needed)

FP8 Tensor Cores on H100 SXM5 deliver 1979 TFLOP/s — exactly 2× the BF16 throughput. Combined with the 2× bandwidth reduction from halved weight size, FP8 inference at large batch sizes can approach 4× the FP16 throughput.

Quality compared to INT8: FP8 E4M3 has the same number of bits as INT8, but the floating-point representation handles outliers more gracefully because the exponent field provides dynamic range. In practice, FP8 quantization requires minimal calibration and achieves near-BF16 quality on most benchmarks. DeepSeek-V3 was both trained and served in FP8.

5 · KV cache quantization

The KV cache grows with context length and limits batch size (see KV Cache). Quantizing K and V tensors from FP16 to INT8 or FP8 halves KV memory, enabling either 2× more concurrent requests or 2× longer contexts at the same request count.

Why KV quantization is harder than weight quantization

Attention scores are computed as \(q k^\top / \sqrt{d}\). Small errors in \(k\) translate to errors in attention scores, which are then passed through softmax — a nonlinearity that can amplify differences in the top scores significantly. Key quantization error is particularly impactful: a few tokens with wrong attention weights can degrade output quality noticeably, especially for tasks that require attending to a specific position (e.g., retrieval, key-value lookups in long context).

Mitigations:

  • Per-head scales: use separate scale factors per attention head (rather than per-tensor) to capture the different value ranges across heads. This reduces quantization error significantly with minimal storage overhead.
  • Key-only quantization: some deployments quantize only the V cache (less sensitive) and leave K in FP16, achieving 1.5× compression instead of 2× with better quality preservation.
  • FP8 KV (vs. INT8): FP8's floating-point representation handles the dynamic range of K/V values better than INT8, with similar compression. Preferred when the hardware supports it.

6 · Calibration methods — AWQ, GPTQ, and SmoothQuant

MethodCategoryCore ideaBest for
RTN (round-to-nearest) W-only Round each weight to the nearest quantized value. No calibration needed. W8A16 where quality loss is acceptable; INT8 baseline
GPTQ W-only Minimize the output error layer-by-layer using a Hessian-based reconstruction (inverse Hessian update). Compensates errors in later weights for each channel. W4A16 — GPTQ at 4-bit substantially outperforms RTN at 4-bit
AWQ (activation-aware) W-only Scale salient weight channels (those with large corresponding activations) before quantization. Calibrate scales from a small dataset of representative inputs. W4A16 — often better than GPTQ, especially at group size 128
SmoothQuant W+A Channel-wise scale migration from activations to weights (§3). Enables INT8 activations with minimal quality loss. W8A8 on A100/H100; the standard for production INT8 serving
FP8 (TE) W+A Per-tensor or per-token dynamic scaling at runtime using NVIDIA Transformer Engine. Minimal calibration needed. W8A8 (FP8 variant) on H100+; preferred over INT8 for quality

Throughput gains are in the bandwidth-bound regime (small batch). At large batch sizes where the model transitions to compute-bound, weight-only quantization (W4/W8 A16) provides no compute speedup — only memory footprint reduction. W+A quantization (W8A8, FP8) benefits both regimes.

8 · Summary

The mechanism

Decode is memory-bandwidth-bound: TPOT ≈ bytes per weight × N / bandwidth. Halving bytes per weight halves TPOT in the bandwidth-bound regime.

Weight-only (W4/W8 A16)

Store weights in INT8/INT4, dequantize before FP16 matmul. Bandwidth gain only. Best for small-batch latency and memory footprint reduction.

W+A (W8A8, FP8)

Quantize both weights and activations for true INT8/FP8 matmuls. Compute gain in addition to bandwidth. Best for large-batch throughput.

FP8 sweet spot

H100 FP8 Tensor Cores: 1979 TFLOP/s (2× BF16). Better quality than INT8 due to floating-point dynamic range. DeepSeek-V3 trains and serves in FP8.

KV cache quantization

INT8/FP8 KV halves cache memory → 2× more concurrent requests. Quality risk: attention is sensitive to K precision. Use per-head scales.

Method choice

W8A16: RTN or GPTQ. W4A16: AWQ or GPTQ. W8A8: SmoothQuant. FP8: Transformer Engine with minimal calibration.
