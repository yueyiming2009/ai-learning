NCCL — How Collectives Actually Run

The library that turns an abstract AllReduce into real GPU-to-GPU transfers that saturate your hardware. The five-layer stack — topology, algorithm, protocol, channels, selection — and where the cost model's ring/tree, busbw, and latency-vs-bandwidth choices actually live.

This page is the implementation layer beneath Sharding & Collectives →. That page defines the four primitives and the \(T \approx V/W\) cost; this one is how NCCL (NVIDIA Collective Communications Library) realizes them on real GPUs — and where the “ring vs tree” and bus-bandwidth numbers come from.

When PyTorch calls all_reduce(grad), nothing about which GPUs talk to which, in what order, over which links, at what message size, is specified. NCCL fills that gap. Its job: take the abstract collective and the discovered hardware graph, and produce a concrete schedule of sends and receives that runs as close as possible to peak link bandwidth. There is no single “NCCL algorithm” — there is a stack of five decisions, made fresh for every call.

1 · The five-layer stack

1
Topology detection
Discover the hardware graph (NVLink, NVSwitch, PCIe, NIC, IB); build rings & trees over it.
2
Algorithm — the pattern
Ring, Tree (double binary), or NVLS/CollNet. Sets the latency vs bandwidth shape.
3
Protocol — the packing
Simple, LL, or LL128. How data and synchronization flags are interleaved. Sets the effective bandwidth.
4
Channels — the parallelism
Split the collective across many parallel rings/trees on different links + SMs to reach aggregate bandwidth.
5
Selection — the tuning
Estimate time = latency + size/bandwidth for each (algo, protocol, #channels); pick the cheapest per message size.

Read those as: where (topology) → what shape (algorithm) → how packed (protocol) → how wide (channels) → which combination (selection). The rest of the page is one section per layer.

2 · Topology detection & graph search

At communicator init, NCCL probes the machine and builds an internal graph of every GPU and every link — NVLink lanes, NVSwitch, PCIe switches, host bridges, and the NICs out to InfiniBand/Ethernet — annotated with bandwidths. It then runs a graph search to lay out one or more rings and trees that maximize usable bandwidth without oversubscribing any link.

This is the step that makes “logical ring” concrete: on a GPU there is no physical ring (the NVSwitch is a crossbar), so NCCL constructs rings as orderings of GPUs and maps each onto a set of links. The same search builds the trees used by the tree algorithm. Its output — the rings, the trees, and how many parallel channels to run — is what the later layers schedule onto.

3 · The ring algorithm

The ring algorithm is bandwidth-optimal: it moves the theoretical minimum number of bytes per GPU, at the cost of latency that grows linearly with the GPU count. A ring AllReduce is two passes around the ring, each of \(N-1\) steps:

  1. ReduceScatter — the array is split into \(N\) chunks. Each step, every GPU sends one chunk to its successor and adds the chunk it receives. After \(N-1\) steps, each GPU owns one fully-summed chunk.
  2. AllGather — circulate those complete chunks around the ring for another \(N-1\) steps, until every GPU has every chunk.

Each GPU sends and receives \(N-1\) chunks of \(V/N\) bytes in each phase, so it moves \(2(N-1)/N \cdot V\) total — exactly the AllReduce multiplier behind bus bandwidth. Step through it (\(N=4\), so \(2(N{-}1)=6\) steps):

Because the per-GPU byte movement never exceeds \(2V/N \cdot (N-1)\) regardless of how the GPUs are wired, the ring saturates the slowest link in the path and runs at peak bandwidth. Its weakness is the \(2(N-1)\) serial steps: at large \(N\), or for small messages where each step’s latency can’t be amortized, that hurts — which is what the tree fixes.

4 · The tree algorithm

A tree AllReduce reduces up to a root and broadcasts down, so its latency is \(O(\log N)\) hops instead of \(O(N)\). The naive cost is that a plain binary tree only uses half its links (interior nodes receive from two children but the leaves and root sit idle in one phase). NCCL’s fix is the double binary tree: build two complementary trees so that a node that is interior in one is a leaf in the other, and split the data between them. Now every link carries traffic in both directions — full bandwidth and logarithmic latency.

▸ Double binary tree — two complementary trees over the same 7 ranks
Solid = interior (relays two children, heavy traffic); outline = leaf (one link). A rank that's interior in one tree is a leaf in the other, so its links stay busy in both — full bandwidth at ~2·log₂N latency.

The tree wins exactly where the ring struggles: small to medium messages and large node counts, where latency dominates. For the big gradient and activation tensors of training, the ring’s bandwidth edge usually wins; for latency-sensitive collectives the tree does. NCCL keeps both and chooses per call (§7).

5 · In-network reduction: NVLS and CollNet

The newest algorithms move the arithmetic off the GPUs entirely. With NVLS (NVLink SHARP), the NVSwitch itself performs the reduction: GPUs send their data into the switch, the switch sums it and multicasts the result back. Because the switch does the add, each GPU sends its data roughly once instead of the ring’s \(2(N-1)/N\) round-trip — less data movement and fewer steps. CollNet/SHARP is the same idea on the InfiniBand switch for cross-node reductions.

NVLS needs the hardware (NVSwitch with SHARP, Hopper+). When available it can beat both ring and tree for AllReduce/ReduceScatter, which is why current NCCL adds it as a third algorithm rather than replacing the others — selection (§7) still decides per call.

6 · Protocols: how bytes and flags are packed

Orthogonal to the algorithm is the protocol — how each chunk is actually written to the peer and how the receiver knows it has arrived. The tension is synchronization overhead vs payload efficiency:

ProtocolSyncLine layoutUsable BWBest for
Simplememory fencesfull payload~100%large messages (bandwidth-bound)
LL128flag-based, no fence120 B data + 8 B flag / 128 B~95%NVLink, mid-size messages
LL (low-latency)flag-based, no fence4 B data + 4 B flag / 8 B~50%tiny, latency-critical messages

LL and LL128 avoid expensive memory fences by writing a flag alongside the data; the receiver spins on the flag word to know the payload is complete. LL pays for that with half its bandwidth (every 8 bytes is half flag), so it’s only for the smallest messages. LL128 packs the flag into a 128-byte line — keeping ~95% of bandwidth while staying fence-free — but it relies on NVLink’s ordering guarantees, so it isn’t used over slower fabrics where the per-line cost dominates. Simple uses fences and the full payload: highest bandwidth, highest latency, the choice for big transfers.

Algorithm ⟂ Protocol
The algorithm sets the latency shape (ring \(O(N)\) vs tree \(O(\log N)\)); the protocol sets the effective \(W\) (Simple ~100% vs LL ~50%). Any algorithm can run with any protocol.

7 · Channels and selection

A single ring or tree uses one path through the links; to use all of a GPU’s NVLinks at once, NCCL splits the collective across multiple parallel channels, each its own ring/tree instance on a subset of links, driven by a few SMs. More channels → more aggregate bandwidth, up to the point where you run out of links or SMs.

Finally, selection. For each call, NCCL estimates the time of every viable (algorithm, protocol, #channels) combination with a simple cost model,

\[ T_\text{est} \;\approx\; \underbrace{L_\text{algo}}_{\text{latency: ring } \propto N,\ \text{tree} \propto \log N} \;+\; \underbrace{\frac{\text{size}}{B_\text{proto}}}_{\text{transfer at the protocol's effective BW}} \]

and picks the minimum — using tuned constants per GPU architecture and topology, decided per collective, per communicator, even per channel. The upshot is the familiar crossover: small messages → Tree + LL; large messages → Ring + Simple; mid-size on NVLink → often LL128. Drag the GPU count to see why the latency term flips the choice:

▸ Ring vs tree latency (serial steps)
Ring AllReduce = 2(N−1) steps; double-tree ≈ 2·⌈log₂N⌉. The gap is why small messages go to the tree.

8 · Seeing it in practice

You can watch every one of these decisions. NCCL_DEBUG=INFO prints, at init, the rings and trees it built, the channel count, and the algorithm/protocol it selects: 

export NCCL_DEBUG=INFO
# ... in the log:
# NCCL INFO Channel 00 : 0 1 2 3 4 5 6 7        ← the ring order
# NCCL INFO Trees [0] 1/-1/-1->0->-1 ...        ← the double binary tree
# NCCL INFO Connected all rings, all trees
# NCCL INFO Using network IB ; 8 channels

And nccl-tests reports the bus bandwidth (busbw) discussed on the collectives page — the per-GPU byte movement over time, normalized so it approximates peak link bandwidth. When busbw plateaus near your NVLink/NIC number, the chosen algorithm/protocol/channel combination is doing its job. A few knobs to force NCCL’s hand when debugging:

Env varEffect
NCCL_ALGO=Ring|Tree|NVLSForce the algorithm (skip selection)
NCCL_PROTO=Simple|LL|LL128Force the protocol
NCCL_MAX_NCHANNELS=nCap the number of parallel channels
NCCL_DEBUG=INFOPrint topology, rings/trees, and selections
These are for diagnosis, not production: NCCL’s tuned selection beats hand-forcing in almost all real cases. Reach for them to confirm a hypothesis (“is my AllReduce stuck on LL?”), then remove them.

9 · Summary

Not one algorithm

A stack: topology → algorithm → protocol → channels → selection, decided per call.

Ring vs tree

Ring = bandwidth-optimal, \(O(N)\) latency. Double-tree = full bandwidth, \(O(\log N)\) latency. NVLS = the switch does the sum.

Protocols

Simple (fences, ~100% BW) / LL128 (120B+8B, ~95%) / LL (4B+4B, ~50%). Sets effective \(W\).

Ties to the math

Ring AllReduce moves \(2(N{-}1)/N\,V\) per GPU — the busbw factor. NCCL is what realizes \(T \approx V/W\).
