MFU — Model FLOPs Utilization

The one number that grades an entire training run against the hardware: how to count a transformer’s FLOPs per token (the 6N rule and its attention correction), turn measured tokens/sec into achieved FLOP/s, and divide by peak — plus MFU vs HFU, and why 40% is good.

The roofline grades one kernel: arithmetic intensity in, achievable FLOP/s out. MFU is the same verdict for the whole training run. Instead of asking how fast one matmul went, it asks: of all the matmul throughput the cluster could theoretically deliver, what fraction did the model’s useful math actually consume? It is the standard single-number health check for a training job — comparable across codebases, cluster sizes, and even hardware generations.

Model FLOPs Utilization
\[ \text{MFU} \;=\; \frac{\text{model FLOPs per token} \;\times\; \text{tokens per second}} {\;n_\text{GPUs} \times P_\text{peak}\;} \]

The denominator is easy — count your GPUs and look up the spec sheet. The whole craft of computing MFU is the numerator: counting the model’s FLOPs per token analytically, from the architecture, not from a profiler. That is what the next two sections derive.

1 · What exactly gets counted

Three choices define the metric, and all three are about keeping the numerator honest:

  • Model FLOPs, not hardware FLOPs. Count only the math the model architecture requires — forward pass and backward pass. Work your implementation added (activation recomputation, a fused kernel’s extra arithmetic) does not count. If you recompute the forward pass to save memory, your GPUs do more FLOPs but your model learns from the same ones — MFU should drop, not rise (§4).
  • Analytical count, not profiler count. FLOPs per token comes from a formula over the architecture (\(N\), layers, width, context). That makes MFU reproducible and comparable across stacks.
  • Dense peak, at your training precision. \(P_\text{peak}\) is the dense Tensor-Core number for the dtype you train in — 989 TFLOP/s bf16 on an H100 SXM5, never the “with sparsity” marketing figure.
Quote the peak that matches your matmul dtype. Training in bf16 but quoting the fp8 peak (or vice versa) is the most common way two teams report incomparable MFU numbers for the same run.

2 · Counting model FLOPs: the 6N rule

The famous estimate — used by the scaling-law papers as compute \(C = 6ND\) for training on \(D\) tokens — is that a transformer with \(N\) parameters spends

FLOPs per token (matmuls only)
\[ \underbrace{2N}_{\text{forward}} \;+\; \underbrace{4N}_{\text{backward}} \;=\; 6N \]

Both factors fall out of one observation about matmuls. Take any weight matrix \(W \in \mathbb{R}^{D\times F}\) in the model, computing \(Y = XW\) for one token (\(X \in \mathbb{R}^{1\times D}\)):

Forward: 2 FLOPs per parameter

The matmul costs \(2DF\) FLOPs — every one of the \(DF\) weights is touched exactly once, in one multiply and one add (a fused multiply-accumulate = 2 FLOPs). So the forward cost of one token through one weight matrix is \(2 \times (\text{its parameter count})\). Summing over every matmul in the model: \(\text{forward} = 2N\) FLOPs per token, where \(N\) counts the parameters that participate in matmuls.

Backward: 2× the forward, so 4 FLOPs per parameter

The backward pass through \(Y = XW\) needs two matmuls of the same shape as the forward one:

  • \(\partial X = \partial Y \, W^{\!\top}\) — the activation gradient, to keep backpropagating: \(2DF\) FLOPs.
  • \(\partial W = X^{\!\top} \partial Y\) — the weight gradient, for the optimizer: \(2DF\) FLOPs.

Same shapes, same cost each, so backward \(= 2\times\) forward \(= 4N\) per token. Total: \(6N\).

Two bookkeeping conventions to be aware of when you compare numbers across papers:

  • Embeddings: the input embedding is a lookup, not a matmul — it does ~no FLOPs and is usually excluded from \(N\) (Kaplan et al.’s “non-embedding parameters”). The unembedding / lm_head is a real matmul and belongs in the count (for large \(N\) the difference is <1–2% either way).
  • What 6N ignores: everything that isn’t a parameter matmul — norms, softmax, activations, rotary embeddings (negligible FLOPs), and, much more importantly, the attention score matmuls, whose cost scales with sequence length and involves no parameters at all. That is the correction term.

3 · The attention correction: + 12·L·D·T per token

Inside each attention layer, two matmuls multiply activations by activations — \(QK^{\!\top}\) (the scores) and \(\text{scores}\times V\) — so the 6N rule never sees them. Per layer, across all heads (the heads partition the model width \(D\), so head count drops out):

Counting the score matmuls

For a sequence of length \(T\): \(QK^{\!\top}\) is \([T,D]\times[D,T] = 2T^2D\) FLOPs, and \(\text{scores}\times V\) is \([T,T]\times[T,D] = 2T^2D\) more — forward total \(4T^2D\) per layer, i.e. \(4TD\) per token. Backward is again 2× forward (each of the two matmuls needs two same-shaped gradient matmuls), giving \(12TD\) per token per layer.

FLOPs per token, full estimate (PaLM Appendix B)
\[ F_\text{token} \;=\; 6N \;+\; 12\,L\,D\,T \]
\(L\) layers, model width \(D\), sequence length \(T\)  ·  (PaLM writes \(12\,L\,H\,Q\,T\) with \(H\cdot Q = D\))

When does the correction matter? For a standard transformer \(N \approx 12LD^2\), so the ratio of attention FLOPs to dense FLOPs is

\[ \frac{12LDT}{6N} \;\approx\; \frac{12LDT}{72LD^2} \;=\; \frac{T}{6D}. \]

At \(T = D\) (e.g. 4K context on a 4096-wide model) attention adds ~17% — already too big to drop. At short context (\(T \ll D\)) the bare \(6N\) is fine; at long context the attention term dominates, which is exactly why long-context training feels so much slower per token.

Convention sensitivity: with a causal mask, FlashAttention computes only the lower triangle — roughly half those FLOPs. Some codebases therefore count \(6LDT\) instead of \(12LDT\). Either is defensible; MFU just shifts by a few percent. State which one you used (the PaLM convention — full \(12LDT\) — is the most common default, and is what e.g. Megatron-LM reports).

4 · MFU vs HFU: the recomputation trap

Large-model training often uses activation recomputation (gradient checkpointing): discard activations in the forward pass and recompute them during the backward pass to save HBM. The GPUs then execute the forward math twice — roughly \(8N\) hardware FLOPs per token instead of \(6N\). This forces a fork in the metric:

Two utilization numbers
  • MFU divides the model’s \(6N\)-based FLOPs by peak. Recomputation makes the step slower with no new model FLOPs → MFU drops. This is the honest end-to-end number: it measures progress on the training objective per unit of hardware.
  • HFU (hardware FLOPs utilization) divides the FLOPs the hardware actually executed (\(\approx 8N\) + recomputed attention) by peak. It measures how busy the silicon was, and is always ≥ MFU. Useful for kernel work; flattering for system comparisons.

A system can raise its HFU by doing more redundant work — that is the trap. When two papers disagree about “utilization,” check which one they report: the Megatron-LM paper’s famous “52% of peak” on its 1T-parameter benchmark counts the recomputed FLOPs — it is HFU; on the same runs the PaLM paper tabulates MT-NLG 530B at 36% HFU but only 30% MFU. Always optimize and report MFU; glance at HFU only to ask “is the gap recomputation, or real idleness?”

5 · The recipe, end to end

Step 1 — measure tokens per second

\(\text{tokens/s} = \dfrac{\text{global batch size} \times \text{sequence length}}{\text{measured step time}}\). Use wall-clock time over many steps in steady state (skip warmup/compilation steps), and count all tokens that went through the model — this is why frameworks AllGather per-rank token counts each step (the verl walkthrough meets exactly such an AllGather, whose only purpose is the MFU denominator).

Step 2 — compute FLOPs per token from the architecture

\(F_\text{token} = 6N + 12LDT\) (§2–3). For MoE models, \(N\) here is the activated parameter count per token, not the total. See MoE Parallelism §8 → for how AlltoAll dispatch adds a communication ceiling on top of this formula.

Step 3 — divide by what the cluster could do

\(\text{MFU} = \dfrac{F_\text{token} \times \text{tokens/s}}{n_\text{GPUs} \times P_\text{peak}}\), with \(P_\text{peak}\) the dense peak at your training dtype.

Worked example: a 7B model on H100s

LLaMA-7B-style model: \(N = 6.7\times10^9\), \(L = 32\), \(D = 4096\), trained at \(T = 4096\) in bf16. Measured throughput: 10,000 tokens/s per GPU.

Line by line: \(6N = 4.02\times10^{10}\); \(12LDT = 12 \cdot 32 \cdot 4096 \cdot 4096 = 6.4\times10^{9}\) (the \(T/6D \approx 16\%\) correction); total \(F_\text{token} = 4.66\times10^{10}\) FLOPs/token. Times \(10^4\) tokens/s = \(4.66\times10^{14}\) FLOP/s = 466 TFLOP/s per GPU. Against the 989 TFLOP/s bf16 peak: MFU = 47% — a healthy number. Had we dropped the attention term we’d have reported 41% and undersold the run. If this run used full recomputation, the hardware also executed an extra forward (\(2N + 4LDT\) more per token), so HFU ≈ 63% — same training run, very different-looking number.

7 · Why nobody hits 100%

MFU charges all wall-clock time against a peak that only the biggest matmuls can touch. Every second spent anywhere else is pure MFU loss. The budget leaks in a fixed set of places:

LeakWhy it costs MFU
Memory-bound opsNorms, softmax, rotary, residual adds sit far left of the roofline ridge — they burn wall time while contributing ~zero counted FLOPs. Fusion (FlashAttention, fused norms) exists to shrink this slice.
Matmul efficiencyEven a good GEMM reaches ~80–90% of peak, not 100% — tile quantization, wave quantization, epilogue overhead. This alone caps MFU near ~85% before anything else leaks.
Exposed communicationAny collective not hidden under compute — a straggling DP AllReduce, FSDP AllGathers on the critical path, cross-node TP — is idle Tensor-Core time.
Pipeline bubblesPP warmup/drain steps where some stages have nothing to do; bubble fraction translates one-for-one into lost MFU.
Host-side gapsDataloader stalls, kernel-launch gaps, optimizer step, logging, checkpointing — anything that leaves the GPU idle between kernels.

Calibration for what “good” means in practice:

RunMFU
GPT-3 175B (2020 stack, V100s)~21%
Megatron-Turing 530B (A100)~30% (36% HFU)
PaLM 540B (TPU v4)46%
Well-tuned dense LLM, A100 era~50–60%
Well-tuned dense LLM, H100 era~35–45%
The H100 numbers being lower than A100’s is not a regression — peak FLOP/s grew ~3× while HBM and network bandwidth grew much less, so the roofline ridge moved right and the same code is now more memory-and-comm-bound. Same lesson as everywhere on this page: MFU is a ratio, and the denominator is doing a lot of work. Compare MFU across same-generation hardware; compare tokens/s/GPU (or cost/token) across generations.

8 · Summary

The metric

MFU = (FLOPs/token × tokens/s) ÷ (n_GPUs × dense peak). Whole-run roofline verdict in one number.

The 6N rule

2 FLOPs/param forward (one MAC per param per token), 4 backward (∂X and ∂W matmuls) → 6N per token.

Attention term

+12·L·D·T per token for QKᵀ and scores·V. Relative size ≈ T/6D — dominant at long context.

MFU vs HFU

Recomputation raises hardware FLOPs (~8N) but not model FLOPs. Report MFU; HFU only diagnoses the gap.

Honest denominators

Dense peak at your matmul dtype; activated params for MoE; all tokens across all ranks in tokens/s.

Calibration

40–50% is a well-tuned run; 20% means something is exposed; >60% on H100 deserves an audit of the count.
