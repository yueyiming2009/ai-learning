PPO Training Walkthrough in slime / Miles

One complete PPO step on a 30B MoE model — SGLang as the HTTP rollout server, Megatron-LM as the training engine, expert parallelism (EP) with AlltoAll dispatch, and TIM elimination instead of IS correction.

Prerequisites: RLHF, Tensor Parallelism, FSDP / ZeRO. For the verl approach to the same problem, see PPO Walkthrough in verl. For the async/TIM theory behind the architectural choices here, see Async RL. For the theory behind why EP with AlltoAll is chosen over TP for expert FFNs, see MoE Parallelism →.

1. Concrete Configuration

1.1 Model — Qwen3-MoE style (dense attention, sparse FFN)

MoE replaces the dense FFN in each transformer layer with \(E=64\) independent expert FFNs plus a learned router. Only \(K=2\) experts are activated per token; the other 62 are skipped entirely.

1.2 Hardware and Parallelism

Total GPUs: 8  (2 nodes × 4 GPUs, NVLink intra-node, InfiniBand cross-node)

TP = 2   tensor parallel (attention weight sharding)
EP = 2   expert parallel (expert sharding across GPUs)
DP = 2   data parallel (ZeRO-3 / Megatron distributed optimizer)
PP = 1   pipeline parallel (disabled)

TP × EP × DP × PP = 2 × 2 × 2 × 1 = 8  ✓

GPU layout (DP × EP × TP):

Node 0:
  GPU 0  →  DP=0, EP=0, TP=0
  GPU 1  →  DP=0, EP=0, TP=1
  GPU 2  →  DP=0, EP=1, TP=0
  GPU 3  →  DP=0, EP=1, TP=1
Node 1:
  GPU 4  →  DP=1, EP=0, TP=0
  GPU 5  →  DP=1, EP=0, TP=1
  GPU 6  →  DP=1, EP=1, TP=0
  GPU 7  →  DP=1, EP=1, TP=1

Each EP rank (a TP-parallel pair within one DP rank) holds \(E/EP = 32\) experts.

1.3 Architecture: Server Boundary vs. HybridEngine

This is the defining structural difference from verl.

verl — HybridEngine (co-located monolith): training and rollout workers share the same GPU memory and NCCL process group. Weight updates flow in-process via NCCL AllGather — no network hop, no process boundary.

slime/Miles — hard server boundary: SGLang runs as a standalone HTTP inference server. The training cluster (Megatron) and the rollout server (SGLang) are separate OS processes, possibly on separate GPU pools. Weight updates are serialized and pushed over HTTP.

verl:
  [FSDP training workers] ──NCCL AllGather──▶ [vLLM rollout workers]
   same process group, shared GPU memory

slime/Miles:
  [Megatron training workers] ──HTTP POST /update_weights──▶ [SGLang server]
   separate processes; may share or split GPUs across nodes

The server boundary is the source of both the flexibility (rollout and training can scale independently) and the engineering complexity (weight serialization, format conversion, HTTP latency).

2. Parallelism Strategies

2.1 Tensor Parallelism (TP=2)

Identical to verl. Column-parallel Q/K/V projections, row-parallel output projection, one AllReduce per attention sub-layer. See the verl walkthrough §2.1 for the full derivation with explicit tensor shapes.

WeightShape (full)Shape per TP rankParallel type
W_Q(2048, 2048)(2048, 1024)column
W_K(2048, 2048)(2048, 1024)column
W_V(2048, 2048)(2048, 1024)column
W_O(2048, 2048)(1024, 2048)row → AllReduce

2.2 Expert Parallelism (EP=2) — new vs. verl

In MoE models the dense FFN is replaced by \(E=64\) parallel expert FFNs plus a learned router. With EP=2, each EP rank (a TP-parallel pair of GPUs) holds \(E/EP = 32\) experts.

Expert weight memory per EP rank:

32 experts × 2 matrices (W_up, W_down) × (2048 × 1024) × 2 bytes ≈ 256 MB per EP rank
(vs. ~512 MB without EP)

The two AlltoAll operations per MoE FFN layer (training mini-batch, 8 sequences × 1024 tokens = 8192 tokens per DP rank):

# Step 1 — Router (local, no communication)
scores  = x @ W_router           →  (8192, E=64)   bfloat16
top_idx, top_weight = topk(k=2)  →  (8192, 2)  each

# Step 2 — AlltoAll dispatch: send tokens to the GPU holding their experts
# EP rank 0 holds experts 0–31; EP rank 1 holds experts 32–63
dispatch_in : (8192×K=16384, H=2048)  bfloat16   tokens reordered by expert assignment
NCCL — AlltoAll (EP group, intra-node NVLink)
Each GPU sends tokens targeting experts on the other EP rank and receives tokens targeting its own 32 experts. Cross-EP volume per GPU: ≈ 32 MB 
# Step 3 — Local expert FFN (no communication)
# Each of the 32 local experts processes the tokens it received
expert_out : (tokens_received, H=2048)

# Step 4 — AlltoAll combine: return expert outputs to token origin GPUs
NCCL — AlltoAll (EP group, intra-node NVLink)
Inverse of dispatch — outputs flow back to the GPU that owns each token. Cross-EP volume per GPU: ≈ 32 MB 
# Step 5 — Weighted sum (local)
out : (8192, H=2048)   bfloat16   K=2 expert outputs combined by router weights

Compared to verl's dense FFN (one AllReduce of ~16 MB for this hidden size), the MoE layer pays two AlltoAll calls of ~32 MB each. AlltoAll avoids the full ring-reduction overhead; its volume scales with dispatched tokens × hidden dim, independent of model width.

Expert load imbalance: if the router sends many tokens to a few popular experts, some GPUs do far more compute than others, stalling the pipeline. Miles applies an auxiliary load-balancing loss to keep per-expert token counts close to uniform.

2.3 Data Parallelism (DP=2, Megatron ZeRO)

Functionally identical to verl's FSDP (ZeRO-3): each DP rank holds 1/DP of each parameter. AllGather before compute; ReduceScatter after backward. Implemented via Megatron's distributed optimizer rather than PyTorch FSDP, but the NCCL primitives are the same.

2.4 SGLang as Rollout Server

SGLang replaces vLLM and runs as an HTTP inference server with continuous batching (PagedAttention). The controller does not call a library — it sends HTTP requests.

Training controller
    │  HTTP POST /generate
    │  { "prompts": [...], "n": 4, "max_new_tokens": 512, "return_logprobs": true }
    ▼
SGLang server  (continuous batching, PagedAttention KV cache)
    │  — prefill: parallel forward over prompt tokens (with EP AlltoAll per layer)
    │  — decode:  autoregressive, K=2 experts per step
    │  — stores:  log_prob_behavior for each generated token
    ▼
    │  HTTP response  { "sequences": [...], "log_probs": [...] }
    ▼
Training controller

TIM elimination (Training-Inference Mismatch): slime/Miles ensures that SGLang and Megatron compute numerically identical log probs for the same token under the same weights. Required conditions: same FP precision, same TP degree, same attention kernel, same expert routing. When these hold, log_prob_behavior ≡ log_prob_training and the IS ratio \(\rho = 1\) by construction — no IS correction layer needed. See Async RL for the contrast with IS-correction approaches.

3. Phase-by-Phase Walkthrough

Phase 1

Data Loading

Where: Training controller (CPU)

prompts_global : (B=16, P=512)  int64   on controller CPU
Differs from verl
Prompts are HTTP-posted to the SGLang server rather than scattered via the Ray object store to co-located vLLM workers. The controller may pipeline requests — sending the next batch before the current one completes — to keep SGLang's continuous batcher saturated.
Phase 2

Rollout (SGLang Server)

Where: SGLang server

2a. Prefill

For each of L=24 layers, the attention sub-layer is identical to verl (TP AllReduce after W_O):

NCCL — AllReduce ×2 (TP group, intra-node, per layer)
tensor: (B_seq/DP=32, P=512, H=2048) bfloat16  ·  volume: 64 MB each

MoE FFN per layer (replaces the dense FFN AllReduce in verl):

# Router (local)
scores = x @ W_router  →  (32, 512, E=64)
top2_idx, top2_weight = topk(k=2)          →  (32, 512, 2)
NCCL — AlltoAll dispatch (EP group, intra-node NVLink)
input: (32×512×K=32768, H=2048) bfloat16  ·  cross-EP volume per GPU: ≈ 64 MB 
# 32 local experts process their tokens (local compute)
NCCL — AlltoAll combine (EP group, intra-node NVLink)
cross-EP volume per GPU: ≈ 64 MB

Per-layer total (prefill): 2 TP AllReduce × 64 MB + 2 EP AlltoAll × 64 MB = 256 MB.
Prefill total: 24 layers × 256 MB = 6 GB.

2b. Decode (R=512 steps, one token at a time)

Each step processes a single new token per sequence (32, 1, H=2048):

NCCL — AllReduce ×2 (TP group, per layer, per step)
tensor: (32, 1, 2048) bfloat16  ·  volume: 128 KB each
NCCL — AlltoAll ×2 (EP group, per layer, per step)
input: (32×K=64, H=2048) bfloat16  ·  cross-EP volume per GPU: ≈ 256 KB each

Per-decode-step total: 24 layers × (2×128 KB + 2×256 KB) ≈ 18 MB per step.
Decode total for R=512: 512 × 18 MB ≈ 9 GB.

2c. Log-Prob Collection

SGLang records log_prob_behavior for each sampled token during decode — the log prob of the generated token under the current expert+router forward pass.

log_probs_behavior : (B_seq=64, R=512)  float32   stored on SGLang server

2d. Output

SGLang returns via HTTP response:

sequences   : (64, S=1024)  int64
log_probs   : (64, R=512)   float32
Phase 3

Reward Computation

Identical to verl Phase 3.

token_level_rewards : (64, 512)  float32
Phase 4

Old Log-Probs

Where: SGLang server (already computed during rollout)

Key difference from verl
verl runs a separate non-autoregressive forward pass for numerical stability. In slime/Miles, log_probs_behavior was already recorded in Phase 2c and returned in the HTTP response. When TIM elimination holds, no extra forward pass is needed. 
old_log_probs = log_probs_behavior   # (64, 512)  float32   zero extra compute

If TIM cannot be guaranteed (e.g., TP degree changes between rollout and training), a Megatron recompute pass is run with matched precision and kernel settings.

Phase 5

Reference Policy Log-Probs

Where: Megatron reference policy workers (frozen weights)

Full non-autoregressive Megatron forward over all 64 sequences. MoE layers add 2 AlltoAll per layer in addition to the TP AllReduce.

NCCL per layer — TP AllReduce ×2 + EP AlltoAll ×2
TP AllReduce: (32, 1024, 2048) bf16 · ~128 MB each  ·  EP AlltoAll: ~64 MB each  ·  Megatron ZeRO AllGather: ~28 MB (attention weights) 
ref_log_probs : (64, 512)  float32
Phase 6

Value Estimation (Critic)

Where: Megatron critic workers

Same structure as Phase 5. Value head projects last hidden state to a scalar per token:

values : (64, 1024)  float32
Phase 7

Advantage Estimation (GAE)

Where: Controller CPU — identical to verl Phase 7. No communication.

advantages : (64, 512)  float32
returns    : (64, 512)  float32
Phase 8

Actor Update (PPO)

Where: Megatron actor workers (all 8 GPUs). Mini-batch per DP rank: 8 sequences.

8a. Megatron ZeRO AllGather (weight reconstruction per layer)

NCCL — AllGather (DP group, cross-node InfiniBand, per layer)
Reconstructs full TP-sharded attention weights from ZeRO shards. Per layer: ~28 MB (H=2048, smaller than verl's ~56 MB at H=4096)

8b. Forward Pass — Attention (TP AllReduce)

NCCL — AllReduce ×2 (TP group, intra-node, per layer)
tensor: (8, 1024, 2048) bfloat16  ·  volume: 32 MB each

8b. Forward Pass — MoE FFN (EP AlltoAll)

# Router (local)
scores = x @ W_router  →  (8, 1024, 64)
NCCL — AlltoAll dispatch (EP group, intra-node NVLink)
input: (8×1024×K=16384, H=2048) bfloat16  ·  cross-EP volume per GPU: ≈ 32 MB 
# 32 local experts process their assigned tokens
NCCL — AlltoAll combine (EP group, intra-node NVLink)
cross-EP volume per GPU: ≈ 32 MB

8c. PPO Loss

Because TIM is eliminated, old_log_probs ≡ log_probs_behavior at step 0. The importance ratio \(\rho \approx 1\) initially — no IS weighting overhead:

log_ratio  = new_log_probs - old_log_probs   # (8, 512)  float32
ratio      = exp(log_ratio)                  # ≈ 1.0 at start of each PPO epoch
actor_loss = -mean(min(ratio * adv, clamp(ratio, 1-eps, 1+eps) * adv) * mask)

8d. Backward Pass

Mirror of forward: TP AllReduce for attention gradients, EP AlltoAll for expert gradients, Megatron ZeRO ReduceScatter to re-shard across DP ranks.

NCCL — ReduceScatter (DP group, cross-node InfiniBand, per layer)
Attention weight gradients re-sharded across DP ranks. Per layer: ~28 MB
NCCL — AlltoAll ×2 (EP group, intra-node, per layer)
Expert input gradient dispatch and combine. Per AlltoAll: ≈ 32 MB

8e. Optimizer Step (local, no NCCL)

Megatron distributed optimizer: AdamW on each GPU's ZeRO shard. No communication.

Phase 9

Critic Update

Same structure as Phase 8, using value regression loss. Identical NCCL operations.

value_clipped = clip(value_pred, old_values - eps_v, old_values + eps_v)
value_loss    = 0.5 * mean((value_clipped - returns)^2 * mask)
Phase 10

Weight Synchronization

Where: Megatron training workers → SGLang server via HTTP

Key difference from verl
verl AllGathers weights in-process and hands them to the co-located vLLM rollout engine via shared GPU memory. Miles serializes weights from Megatron's layout and HTTP-pushes them across the process boundary to the SGLang server. 
Step 1 — Megatron AllGather (reconstruct full TP-sharded model from ZeRO shards):
  NCCL — AllGather across DP group (2 GPUs, cross-node):
    input:   ~875 MB ZeRO shard per GPU   (attention + expert weights, 24 layers)
    output:  ~1.75 GB full TP=2 copy per GPU

Step 2 — HTTP weight push to SGLang:
  Controller serializes weights from Megatron's TP-sharded layout
  HTTP POST /update_weights  { "state_dict": <binary blob ~1.75 GB> }
  Runs every K training steps (async) or every step (sync)

Step 3 — SGLang hot-swap:
  Drains or pauses in-flight requests
  Loads new parameter tensors into existing memory allocations
  Resumes accepting generation requests

The HTTP boundary adds ~100–500 ms of serialization + network latency per sync, but enables independent process lifetimes and separate GPU allocation for training vs. rollout.

5. verl vs. slime/Miles: Side-by-Side

Dimensionverlslime / Miles
Rollout engine vLLM (in-process, SPMD) SGLang (HTTP server, continuous batching)
Training engine PyTorch FSDP (ZeRO-3) Megatron-LM (ZeRO + PP + EP)
Rollout–training boundary In-process NCCL (same process group) HTTP (separate processes)
MoE / expert parallelism Dense-first; EP not in core path MoE-native; EP AlltoAll built into every layer
FFN communication primitive AllReduce (dense W_down row-parallel) AlltoAll ×2 (expert dispatch + combine)
Weight sync primitive NCCL AllGather in-memory (~3.5 GB) HTTP push (~1.75 GB for this config)
Phase 4 (old log-probs) Separate recompute forward pass Returned by SGLang in Phase 2 (zero extra compute)
Training-inference mismatch IS correction (ρ = exp(log_new − log_old)) Elimination (bitwise-identical SGLang ↔ Megatron)
Rollout scheduling Co-located with training (shared GPUs) Separate GPU pools possible
Battle-tested scale Dense models up to ~70B MoE models up to 355B+ (GLM-4.6, DeepSeek-V4)

Choose verl when: dense models, FSDP-based training stack, simpler ops setup, tight in-memory weight coupling is preferred.

Choose slime/Miles when: MoE models, Megatron training stack, need separate scaling of rollout vs. training capacity, or want SGLang-native features (prefix caching, speculative decoding, structured output).
