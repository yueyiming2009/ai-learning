Batching for Inference — Static, Continuous, and Chunked

Serving LLMs efficiently requires running many requests together to raise arithmetic intensity. The challenge: requests finish at different times, and long prefills disrupt in-flight decodes. Continuous batching and chunked prefill are the two techniques that solve this.

From the prefill & decode analysis: decode throughput scales linearly with batch size \(B\) until the GPU ridge point (~295 tokens on H100). The higher \(B\), the better the hardware utilization. The challenge in practice is that requests arrive at different times and finish at different lengths — keeping \(B\) high requires active management of what is running in each decode step.

1 · Static batching — the padding waste

The simplest approach: collect a fixed batch of requests, run them all together, wait until every request has finished, then accept the next batch. This is how most frameworks work out of the box.

Why static batching wastes GPU cycles

All sequences in a batch must run for the same number of steps — determined by the longest sequence in the batch. Shorter sequences either pad their output to match (wasting compute) or sit idle once they hit their end-of-sequence token (wasting GPU slots). Either way, the GPU does work or waits for the stragglers.

The waste fraction depends on the output length distribution. If most requests are short and a few are long — common in API workloads — static batching can achieve <40% utilization. Five requests waiting on one slow one is the norm, not the exception.

2 · Continuous batching — iteration-level scheduling

Continuous batching (also called dynamic batching or in-flight batching) changes the scheduling granularity from batch to decode step. After every single step, the scheduler checks: did any sequence just emit an EOS token or hit its length limit? If so, retire it and immediately admit a waiting request into the freed slot.

The key insight

All decode steps across all sequences in a batch run in lockstep — they are one fused kernel invocation. Retiring sequence B at step 6 and starting sequence F does not require pausing the other sequences; F's prefill can run in the same kernel as the next decode step for A, C, D, E. The batch size stays constant; only its composition changes.

3 · Throughput gains in practice

The theoretical gain equals the ratio of total useful work to total steps:

Utilization ratio
\[ \eta_{\rm static} = \frac{\sum_i T_i}{B \times T_{\max}}, \qquad \eta_{\rm continuous} \approx 1 \]
\(T_i\) = output length of request \(i\), \(B\) = batch size, \(T_{\max} = \max_i T_i\). Continuous batching replaces the numerator with the full \(B \times T_{\max}\) by filling freed slots immediately.

Measured throughput improvements from continuous batching are typically 2–5× over static batching on real API workloads (where output lengths are highly variable). The gain is largest when the output length distribution is heavy-tailed — a few very long responses drag down the static batch.

Continuous batching is now the standard in all production serving stacks: vLLM, TGI (Hugging Face), SGLang, TensorRT-LLM, and the inference backends in VeRL and slime/MILES all use iteration-level scheduling.

4 · TTFT vs. TPOT — the scheduling tension

Continuous batching maximizes throughput but creates a new tension: a waiting request can only be admitted when a slot is free — and until it is admitted, its TTFT grows. Meanwhile, once admitted, its prefill computation runs in the same steps as the ongoing decodes, competing for GPU time.

The two-way tradeoff
  • Optimize for TTFT: admit new requests as soon as possible, even if the batch is "full" — preempt or pause a decode to run the new prefill immediately. Cost: every in-flight decode stalls for the duration of the preempted request's prefill → TPOT spikes.
  • Optimize for TPOT: only admit new requests when a natural slot opens, never interrupting ongoing decode. Cost: new requests wait longer → TTFT grows, especially for high-traffic endpoints.

The standard resolution is to set target batch sizes and queue depths: maintain a target in-flight batch size of \(B_{\rm target}\), admit up to \(B_{\rm max}\) requests at admission time, and use priority queuing for SLO-critical requests. The scheduler does not admit more than \(B_{\rm max}\) simultaneously to protect TPOT SLOs.

5 · Chunked prefill — smoothing the prefill spike

A long prefill (e.g., 8K-token context) runs as a single large matrix multiply. While it runs, all in-flight decode steps are blocked — causing a large TPOT spike for every current user. The longer the prompt, the worse the spike.

The problem: prefill monopolizes the GPU

Prefill for a single 8K-token prompt on a 7B model takes roughly the same wall-clock time as ~50–100 decode steps for a batch of 32 sequences. Every one of those 32 in-flight responses stalls for that duration. P99 TPOT can spike 50–100× during heavy prefill traffic.

Chunked prefill splits the new request's prefill across multiple decode steps, processing \(C\) tokens per chunk. Each step runs: decode all in-flight sequences + prefill chunk \([iC : (i+1)C]\) of the new request.

The chunk size tradeoff

Chunk size \(C\) controls the balance between TTFT and TPOT:

  • Large \(C\): fewer chunks, faster TTFT (the new request reaches first-token sooner), but each decode step is more disrupted (more prefill tokens compete with decode).
  • Small \(C\): more chunks, smoother TPOT (decode steps are barely affected), but TTFT grows (the new request waits many steps before completing prefill).

A practical heuristic: set \(C\) such that prefill tokens per step roughly equals decode tokens per step — i.e., \(C \approx B_{\rm decode}\), the current decode batch size. This balances compute between the two workloads per step. vLLM and SGLang both expose this as a tunable parameter.

Chunked prefill also reduces peak memory pressure: a full 8K prefill allocates 8K KV blocks upfront, which may not be available. By processing in chunks of \(C\) tokens at a time, PagedAttention (covered later) allocates blocks incrementally rather than reserving the full context length in advance.

6 · Summary

Static batching

All sequences run to the longest; short requests pad or sit idle. GPU utilization as low as 40% on variable-length workloads.

Continuous batching

Retire finished sequences each decode step; admit waiting requests immediately. Near-100% GPU utilization; 2–5× throughput gain over static.

TTFT vs. TPOT

Admitting new requests immediately improves TTFT but can spike TPOT for in-flight requests. Schedulers set target batch sizes to balance both.

Chunked prefill

Split a long prompt's prefill across multiple steps, interleaved with ongoing decodes. Smooths TPOT spikes at the cost of slightly longer TTFT for the new request.

Chunk size heuristic

Set chunk size \(C \approx B_{\rm decode}\) (current decode batch size) to balance prefill and decode compute per step.
