Nemotron 3.5 Super VL

A 120B hybrid model becomes a visual agent through base-model transfer, targeted mid-training, multimodal SFT, specialist RL, and deployment-aware distillation.

Nemotron family · Released October 15, 2026

Lineage: Nemotron 3 Super Base supplies the initial weights; Ultra Base supplies teacher supervision. Super VL later supplies the parent checkpoint for Bolt 74B.

Architecture · Training handoffs · Memory and serving · Evaluation

Evidence: official report, model card and pinned configuration, checked November 1, 2026. Source inspection and analytical budgets, not a reproduced training run.

1. One family, three different transfer relationships

Super VL is not merely the original Super with a vision API wrapper. Its language backbone starts from Super Base, is distilled using Ultra Base, receives domain/context training, then acquires visual and agentic behavior. Its NVFP4 release is refined from the BF16 model through quantization-aware distillation (QAD).

Super Base weights → MTP warm-up → Ultra Base teacher data/distributions → continued pre-training and mid-training → C-RADIO + connector + multimodal SFT → RL teachers → MOPD → BF16 model → QAD → NVFP4 release.

Keep teacher transfer separate from weight initialization: a 120B student does not inherit Ultra's 550B tensor shapes. Likewise, Nano Omni contributes vision-data lineage, not the language backbone of Super VL.

Accounting matters: the 2.83T-token released Indic corpus is much larger than the 10B Indic tokens actually used inside the 100B CPT mixture. The technical report describes 65.4B SWE mid-training tokens while the card summarizes 67B; keep that source difference explicit rather than silently adding both.

The report also describes test-time parallel agents and self-verification. Their gains are not additional training stages or guaranteed single-agent checkpoint improvements. Compare the baseline and augmented inference procedures separately.

4. Hybrid state, quantization, and the serving budget

With one request, context \(T\), KV element size \(b_k\), and recurrent-state element size \(b_s\):

\[ M_{\rm KV}=8\cdot2\cdot2\cdot128\cdot T b_k,\qquad M_{\rm SSM}=40\cdot128\cdot64\cdot128\cdot b_s. \]

At 1,048,576 tokens and BF16 KV, target KV is 8 GiB. The main recurrent state is 80 MiB at BF16 or 160 MiB at FP32. These exclude convolution state, prefix snapshots, the vision encoder's activations, padding, workspaces, and draft state. One fixed SSM state does not mean prefix reuse is free.

X: Ki tokens. Y: GiB for target KV plus one BF16 SSM state/sequence. Analytical payload only; no prefix-snapshot, draft or peak-allocation claim.

A nominal 120B model has 240GB of raw BF16 weights or 60GB at ideal four-bit packing. The actual NVFP4 release is mixed precision: the pinned map assigns FP8 to many attention/Mamba projections, four-bit blocks to expert matrices, and retains sensitive components at higher precision. “NVFP4” does not make every byte four-bit.

Native MTP and the optional LiLiCorr drafter are different serving choices. LiLiCorr models dependencies among parallel candidates; its reported speedup is workload-specific. Source recipes also change SSM cache dtype and prefix-checkpoint behavior. Such settings affect numerical behavior and state memory, not just throughput.

5. Evidence, limits, and reproducible adaptation

The card reports BF16/NVFP4 pairs with non-model settings held fixed: SWE-bench Pro 51.78/51.30, Terminal-Bench 2.1 60.67/62.78, and CharXiv reasoning 80.82/79.88. A quantized checkpoint winning one metric does not establish lossless quantization. Keep reasoning mode, harness, tools, and precision attached to each score.

The public NeMo Gym reproducibility instructions describe benchmark setup. Some visual benchmarks use separate implementations or internal scaffolds; “all recipes open” is not proof that every reported result is reproducible with one command.

For customization, select the intended BF16/quantized checkpoint and processor, preserve visual token/label alignment, establish a held-out task baseline, and verify the saved adaptation reloads. A deployment example using one DGX Spark sequence is not proof that maximum context and high concurrency fit together.

The release is governed by OpenMDW-1.1. No weights, containers, remote-code loaders, or GPU training were run for this page.
