MAI-Thinking-1: Architecture and Training

How a base model becomes a reasoning assistant: design the base, prepare it for long contexts, develop specialists, carry progress through restarts, and consolidate one final model.

Microsoft MAI family · Model-centered reading map

Lineage: MAI-Base-1 → independent specialists → trace consolidation → Thinking-1. MAI-Base-2 is a later base generation, not Thinking-1’s parent.

Architecture · Training flow · Systems · Evaluation

1. The checkpoint and data flow

2. Before the large run: make design choices at scale

Input
Human-generated public/licensed data, candidate architectures, and the target training/inference stack.
Reported work
Build data pipelines in-house and compare architecture/data changes on a ladder of model sizes at fixed tokens per active parameter within an experiment. Fit baseline loss-versus-cost curves; check whether candidate gains survive increasing scale.
Output
The MAI-Base-1 configuration, tokenizer, corpus mixture, and training recipe—not yet a reasoning assistant.
Decision evidence
Held-out pre-training evaluations and cost comparisons. The report distinguishes FLOPs-based efficiency gain from time-based gain on the actual stack.

The selected base uses 78 layers, five local-attention layers per global-attention layer, and alternating dense/MoE feed-forward layers. LatentMoE routes each token to eight of 512 experts. The existing o200k_base tokenizer simplifies integration. These are choices for this model, not requirements for the lifecycle.

One backbone, chosen for both learning and generation

The shared Latent MoE guide explains why compression changes both expert compute and dispatch traffic. MAI-Base-1's specific routed width is 3,072 from a 6,656-wide backbone, with eight of 512 experts and alternating dense FFNs; keep those choices separate from Kimi, Nemotron, and Muse variants.

3. Pre-training produces the base, not the finished assistant

Input
Initialized MAI-Base-1 weights and the curated pre-training mixture.
Weight update
Language-model training with AdamW in YOLO, Microsoft's training stack. The report specifies 30T tokens at a 16,384-token context on 8,192 GB200 GPUs.
Output
Pretrained base weights, ready for further domain/context adaptation.
Why continue?
Broad predictive competence is not the same as long-context adaptation, an assistant protocol, or a policy trained to solve tasks against feedback.

The report excludes LM-generated synthetic data from pre-training and reports no third-party-model distillation. Do not extend that into “no model-generated data anywhere”: later stages include model-assisted task construction and self-generated traces.

Execution details belong under this stage

Pre-training uses expert parallelism and ZeRO-2; the longest mid-training phase uses ZeRO-3/FSDP. The precision recipe mixes BF16 defaults, FP8 forward/data-gradient GEMMs, and FP32-sensitive operations and optimizer state. That is different from the BF16 learner/inference alignment used during RL. Copying one precision label across the entire lifecycle would erase a consequential stage boundary.

Source: §2.6; data boundary: §1. Mechanics: next-token loss and training loop.

5. Three independent specialists learn different behaviors

The reported RL climbs start without prior exposure to reasoning traces. Prompts elicit an initial reasoning format; task feedback then selects useful behavior. Each specialist uses the shared RL recipe but different prompts, environments, and rewards. Output: three teacher policies, not yet one generalist.

STEM and competitive coding

Input: problems paired with answers or executable tests. The report describes over five million STEM samples and 160K competitive-coding problems. Update: sample responses and reward task success using mathematical checks, answer judges, or code execution. Capability: single-turn reasoning across math, science, and programming.

Quality is a data-pipeline problem before it is an optimizer problem: extraction, question–answer pairing, faulty-answer checks, difficulty assessment, and benchmark decontamination determine what the policy is rewarded for learning.

Agentic coding and general tool use

Input: a task, repository/environment state, tools, and graders. Update: the model repeatedly acts, observes tool results, and continues; completed trajectories receive task feedback. Capability: solving work that requires interacting with an environment, not merely writing a plausible answer.

For software engineering, SEE provides fresh isolated containers. The task-construction pipeline checks that an empty patch fails and the reference patch succeeds, including repeated trials in the training infrastructure. Tests alone are not a complete integrity guarantee: the report also describes hidden-test handling, repository-history sanitation, network controls, and rollout monitoring.

Helpfulness and safety

Input: conversational tasks and constraints, alongside a separately trained human-preference reward model and AI judges. Update: optimize a combination of preference, rubric, and verifiable signals. Capability: instruction following, useful responses, safety, honesty, and style.

This is not just summing every score. In some contexts, lower-priority rewards matter only when higher-priority rewards tie across the group; in others, a threshold gates lower-priority scoring. The point is to avoid trading a required constraint for a large gain on an easier stylistic reward.

What makes the shared RL update sustainable?

The recipe uses a GRPO-derived token-level policy objective, normalized over tokens in the global batch. Group rewards supply response-level advantages. Two distinct controls address stability:

  • Adaptive upper clipping: keep the lower ratio bound at 1 - epsilon and adjust the upper bound 1 / (1 - epsilon) + k. A controller raises k when estimated entropy is below target and lowers it when above target. This is not an adaptive entropy-bonus coefficient; the report says an explicit bonus underperformed.
  • Outer ratio clipping: separately constrain extreme ratios in branches the usual surrogate leaves unbounded. The reported purpose is reducing gradient-norm spikes, not replacing the entropy controller.

Early pass-rate filtering reduces spending on unhelpful groups; output-length expansion avoids paying for long generations at the beginning of a climb. These choices change data selection and compute allocation, not only the algebra of the loss.

Sources: §3.1, §3.2, §3.3, §3.4. Mechanics: GRPO, adaptive entropy feedback, outer clipping and its gradient, reward/verifier design, harness/learner contracts.

6. Self-distillation carries progress across a restart

A long climb can become unstable, or a stronger pre-/mid-trained base can become available. Rather than always resume the latest RL weights, MAI collects strong rollouts and SFTs a chosen mid-trained checkpoint on those traces. That model becomes the starting point for another RL climb.

Transferred
Behavior encoded in selected response/trajectory data, with formatting converted when needed.
New starting point
The selected mid-trained weights plus the SFT result—not a weight average and not an exact continuation of the failed RL checkpoint.
Reported benefit
Carry progress around numerical instability, move to newer bases, adopt the native chat format, and remove undesirable traces.
Unknown
A complete per-restart checkpoint manifest and optimizer/RNG-state migration history are not supplied. Do not invent which moments or data cursors were preserved.

The report finds approximately one million traces sufficient in its experiments. Diverse prompts and traces from multiple strong later checkpoints help; very early traces hurt, while only the final checkpoint gives weaker subsequent RL performance. Mixing mid-training data with traces helps retain long-context behavior. These are reported recipe findings, not universal dataset-size or filtering rules.

Why this belongs inside the story: self-distillation is a way to continue model development, not merely compress a finished model. “No third-party distillation” and “uses self-distillation” describe compatible facts.

The report cites Huang (2022), STaR (2022), ReSTEM (2023), and OPSD (2026) as background. Its described restart is offline SFT on earlier RL traces, not OPSD's same-weight, privileged-context distribution matching. See the four-method comparison and sources for why these are different self-distillation mechanisms.

Source: §3.1.4. Mechanics: offline trace distillation. General contract: resume versus stage reset versus transfer.

7. Under the RL stages: Rocket keeps the loop moving

For the reusable framework design, see Rocket — architecture, task execution, an interactive lag illustration, and comparison with public RL frameworks. Rocket is described as in-house; model availability does not establish a public Rocket release.

Rocket couples a YOLO learner with SGLang inference. A controller dispatches tasks; problem workers assemble groups and advantages; rollout workers drive generation, tools, and grading; the learner consumes filtered batches. Updated weights flow back to inference. This is the execution machinery for the climbs, not an additional learned capability.

The serving bottleneck changes with the workload. Long single-turn generations emphasize KV-cache capacity; MAI disables prefix caching there to allow sliding-window tokens to be evicted. Multi-turn tasks repeatedly reuse long prefixes, so caching is valuable. “Optimize inference” therefore means different things for different specialist climbs.

Sources: §3.1.5 and §3.6. Mechanics: lag distributions, mismatch taxonomy, monitoring.

8. Turn three teachers into one candidate

Input: traces from the three specialist policies, with source-specific filtering. For STEM/agentic data, MAI favors later checkpoints but samples across multiple checkpoints; helpfulness/safety traces also receive style, structure, and defect checks. Update: supervised trace distillation into one model. Output: a consolidated checkpoint, followed by a final RL refinement.

The team balances the mixture by samples; long reasoning traces dominate tokens. It reports four SFT epochs and mixture/hyperparameter iteration using public and internal benchmarks plus human evaluation. The resulting quality balance is an observation about this recipe, not proof that token imbalance never matters.

Why run RL again after the merge?

Trace imitation transfers capabilities but does not finish optimizing how the combined model behaves. The final lightweight RL stage emphasizes safety, over-refusal, and style. It retains a small STEM/code mixture and a 128K maximum sequence length; the report says these help avoid gradual degradation of complex reasoning.

Interpretation: final alignment is not “polish with no trade-offs.” Retention data and regression measurements are part of producing the final model. Independent specialist peaks are not automatically preserved by either SFT or later RL.

Source: §3.5. Pattern reference: consolidation mechanisms.

9. What the final evidence establishes—and does not

The report evaluates MAI-Thinking-1 on reasoning, coding, general capabilities, human preference, and safety. It reports 97.0% on AIME 2025, 87.7% on LiveCodeBench v6, 73.5% on SWE-bench Verified, and 52.8% on SWE-Bench Pro. These are author-reported results under specified evaluation protocols, not outcomes reproduced here.

  • Budget matters: §4.1 reports four-run averages with temperature 1 and top-p 0.97 unless otherwise stated. Table 11 uses 256K total context for agentic coding and a 256K maximum output budget for its other evaluations—distinct from the 128K RL output cap.
  • Comparison protocol matters: Table 11 takes other models' results from their official reports. Table 12's Sonnet comparison instead uses MAI's evaluation suite. These are not one uniformly controlled cross-model experiment.
  • Harness matters: agentic evaluations use a simple ReAct loop. Terminal-Bench's predefined timeouts are ignored, limiting direct comparability with timeout-constrained results.
  • Aggregate metrics are incomplete: human side-by-side judgments and safety/red-team evaluations address different questions from math or coding accuracy. They do not prove safety for every deployment.

Unknown: the report is not a complete reproducible build manifest or an independently audited release gate. It does not supply every dataset, intermediate checkpoint, transition threshold, and operational deployment contract needed to recreate the entire lifecycle. The last box in this story is a reported final model and evaluation evidence—not an invented public deployment procedure.

Sources: §4, §5, Appendices H–K. General requirements: evaluation and release.
