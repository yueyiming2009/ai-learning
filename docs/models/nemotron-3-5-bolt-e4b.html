Nemotron 3.5 Bolt E4B

A different Bolt branch: preserve Gemma's conversational strengths, improve tool use through RL, and package the resulting text model for responsive local agents.

Nemotron family · Released October 23, 2026

Lineage: initialized from Gemma-4-E4B-it, then post-trained by NVIDIA. It is not a tiny Super VL, a pruned Bolt 74B, or a latent MoE.

Dense backbone and PLE · RL-only adaptation · Memory and drafting · Behavior/evidence

Evidence: the official card and dated report confirm a released checkpoint, not merely the earlier October 23 schedule. Configuration fields and original Gemma implementation are distinguished from supported Bolt inputs.

1. E4B is an effective-size label, not top-4B expert activation

The card describes 8B total / 4B effective parameters and a text-in/text-out interface. The BF16 configuration sets enable_moe_block=false; no routed-expert count or top-\(K\) is configured. The “Bolt” brand groups local deployment goals, not one architecture family.

Gemma-4-E4B-it weights → multi-environment RLVR/RLHF in two reasoning modes → selected BF16 policy → importance-matrix Q4_K_M calibration → GGUF release, with a separately trained DFlash drafter.

Voice and device assistants can place ASR, vision, or TTS around this model. The published Bolt interface is still text-only. Retained vision/audio config objects in a parent-compatible BF16 artifact do not establish supported multimodal Bolt behavior.

2. Dense transformer plus per-layer input embeddings

PartPinned BF16 configurationInterpretation
Backbone42 layers, width 2560, dense gated MLP intermediate width 10,240.All dense layers process each token; “effective 4B” is not sparse expert selection.
Attention8 Q heads, 2 KV heads; local head dimension 256, global head dimension 512.Do not use one head dimension for the entire cache calculation.
Context pattern35 sliding-window layers (window 512), 7 full-attention layers, 64K limit; 18 later layers configured for KV sharing.Local-window eviction and shared KV sources both affect realized memory.
Per-layer inputsVocabulary 262,144; 256 features per layer, packed across 42 layers.Large lookup storage can contribute little per-token matrix work compared with evaluating a similarly sized dense matrix.

The packed PLE table alone has \(262144\times42\times256=2.819\) billion entries. Each input token selects a row, rather than multiplying through every vocabulary entry. This explains one source of the storage-versus-effective-compute distinction; it is not a reconstruction of NVIDIA's complete effective-parameter metric.

The reference decoder's PLE branch gates the 256-wide per-layer signal, projects it to model width, normalizes, and adds it residually after the FFN. Source: pinned Gemma 4 implementation.

3. Why NVIDIA rejected an extra SFT stage

The starting checkpoint is already instruction-tuned. NVIDIA tried additional multi-teacher SFT: it improved tool calling and reduced the RL steps needed, but regressed conversational quality and verbosity. The released Bolt E4B therefore uses RL-only additional post-training, not a universal “SFT then RL” template.

  1. Adapt the interface. When an assistant turn contains text and tool calls, the chat template places text first. conversational_mode adds a concise, speech-friendly system instruction; it is not a separate set of weights.
  2. Train across outcomes. NeMo RL/Gym supply instruction following/hierarchy, tool calling/schema, structured/free-form output and GenRM environments. Both RLVR and RLHF are used.
  3. Train both reasoning modes. The blend deliberately favors non-reasoning over reasoning 2:1. The report gives global batch 256, eight rollouts/prompt, and generation limits of 4096 for reasoning versus 1024 for non-reasoning samples.
  4. Control verbosity while preserving quality. Group-relative penalties and overlong-filter choices are adjusted during RL. Shorter answers are judged for quality, not automatically rewarded as better.
  5. Calibrate deployment quantization. Convert the selected BF16 checkpoint to Q4_K_M with an importance matrix calibrated on about one million tokens of its own RL rollouts. This is not the IQ2/QAD pipeline of Bolt 74B.

The report describes English-only additional post-training and evaluates multilingual retention. Broader inherited language capability does not mean NVIDIA retrained every language. The model card's generic corpus inventory is not a precise token count for this RL adaptation.

4. Four gigabytes is a workload target, not free context

For a deliberately conservative estimate that ignores cross-layer KV sharing but assumes window eviction, with \(T\) tokens and two-byte cache elements:

\[ M_{\rm KV}=2\cdot2\cdot2\,[7\cdot512T+35\cdot256\min(T,512)]. \]

At 65,536 tokens this is about 1.784 GiB. The configured 18 shared-KV layers can reduce the number of distinct caches in a supporting engine. This calculator is a no-sharing cache scenario, not the measured cache of NVIDIA's deployment. Weight residency, PLE lookup placement, the drafter, and runtime workspaces need separate budgets.

The companion DFlash model has five Transformer layers and 360M parameters excluding reused target embeddings/head, and proposes seven tokens. The report gives 2.74× per-user decode speed at concurrency one over no speculation; it does not promise that multiplier at every batch size or for prefill.

5. The unit of success is a conversation with actions

The report evaluates 21 benchmarks covering conversation, tool use, instruction control, context and state grounding, with task-specific repeat counts. Q4_K_M examples include MultiChallenge 55.60, ToolSandbox 74.13 and IHEval 82.40. Different benchmarks use different reasoning modes; the same mode flag is not used indiscriminately.

For voice/device agents, latency, concise useful responses, tool correctness and state grounding must be checked together. Text output does not directly synthesize speech. A short response can still trigger the wrong action; a high reasoning score can still make an interactive system too slow.

The template has a specific asynchronous-tool protocol: immediately acknowledge a pending call, then deliver a later structured update in the supported message form. Do not forge completed tool actions into conversation history or assume every API-compatible harness permits stray tool-result turns.

The release uses OpenMDW-1.1, with parent-model terms linked in the card. No model, drafter, plugin, or container was run for this page.
