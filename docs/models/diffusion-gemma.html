1. Which model is this?

DiffusionGemma 26B A4B IT is Google's experimental, open-weight diffusion model based on the Gemma 4 mixture-of-experts backbone. Its official model ID is google/diffusiongemma-26B-A4B-it. It is not a renamed Gemini Diffusion demo or an arbitrary community conversion of an earlier Gemma.

2. One backbone, two attention modes

The model card describes encoder and decoder roles. The architecture explainer clarifies that a shared, fine-tuned backbone switches modes; this is not two independently stored 26B models.

1 · Encode contextCausal prefill produces the prompt KV cache.
2 · Refine canvasBidirectional denoising attends to the active 256 positions and cached context. Repeat.
3 · Commit blockCausally encode finalized tokens and append their states to the context cache.
4 · ContinueStart a fresh canvas conditioned on all committed context, until generation ends.

During denoising, earlier cached context does not need to be recomputed at every pass. The changing canvas does. Its bidirectional denoiser states cannot simply be treated as the causal cache for the next block; the incremental encoding phase creates that committed representation. See the general KV-cache trade-off.

The resulting model is block-autoregressive, not globally non-autoregressive: later canvases depend on finalized earlier ones. Within the active canvas it can revise positions; after a block is committed, this generation loop does not revise it.

3. Uniform-state diffusion, not mask-only completion

DiffusionGemma starts from random vocabulary tokens and repeatedly denoises them. Unlike an absorbing [MASK] process, a visible token need not be trusted. Positions can be replaced with new random tokens as the surrounding predictions change.

The basic uniform-corruption marginal, using the previous page's notation, is:

\[ q(z_{t,i}=v\mid x_i)=a(t)\mathbf 1[v=x_i]+\frac{1-a(t)}{V}. \]

This equation explains the noise family; it is not a claim about an undisclosed production training schedule. There is no permanent "this token is clean" marker. The sampler uses model distributions to decide what to retain or re-noise.

Self-conditioning carries more than sampled words

Google also discloses passing information from the previous denoising prediction into the next pass. If \(P^{(k)}\in\mathbb R^{B\times V}\) is a pass's token probability matrix and \(E\in\mathbb R^{V\times d}\) the embedding table, then

\[ H_{\mathrm{self}}^{(k+1)}=P^{(k)}E\in\mathbb R^{B\times d} \]

is a per-position expected embedding carrying soft predictions. This describes the disclosed information flow, not the exact fusion layer or training gradient policy. Self-conditioning is different from the causal context KV cache.

4. Entropy-bounded denoising and adaptive stopping

The recommended configuration sets a maximum of 48 passes per canvas, with logit temperature declining linearly from 0.8 to 0.4. It selects a set of low-entropy positions under a stated mutual-information bound of 0.1, and fully re-noises the non-selected positions.

Do not turn this into "every token with entropy below 0.1 is accepted." The selection rule is a bound on the selected set's dependency approximation, not the same threshold as early stopping. Use the official sampler implementation for its precise bound and selection procedure.

Early stopping requires both conditions:

  1. The mean model entropy over the canvas is below 0.005.
  2. The highest-probability token predictions are unchanged across two consecutive passes.

The documentation reports roughly 12–16 passes as typical, depending on the task. Forty-eight is the cap, not the default number of passes every canvas must execute. Reaching the cap is also a termination path.

Confidence and stability are not correctness checks. A wrong answer can have low entropy and stop early. This is not target-model verification and does not preserve Gemma 4's autoregressive output distribution. Contrast exact speculative decoding.

5. Adapted weights, not an inference flag on ordinary Gemma

Google states that Gemma 4 is fine-tuned for the encoding and denoising roles. Bidirectional generation and uniform-state denoising therefore require the DiffusionGemma checkpoint and a compatible runtime—not just removing a causal attention mask from the ordinary Gemma 4 model.

The public developer guide links a task-specific fine-tuning recipe. That recipe demonstrates adaptation, not the full released model's training provenance. The sources used here do not establish its complete conversion dataset, token budget, objective weights, or all post-training stages. Those details should not be inferred from the generic masked-diffusion loss on the previous page.

6. The speed–quality trade-off has conditions

The launch post advertises up to 4× faster generation, including over 1,000 tokens/s on a single H100 and over 700 tokens/s on an RTX 5090. These are vendor-reported operating points, not universal improvements over every autoregressive runtime. The model card separately reports over 1,100 tokens/s in a low-batch H100 FP8 setting. Do not combine claims from different settings into one benchmark.

The central systems argument is plausible but conditional: several canvas tokens share weight access and exploit compute that single-user autoregressive decoding may leave idle. The advantage can shrink when concurrent requests already fill the accelerator. MoE routing, precision, context length, sampler overhead, and quality targets all affect the result.

For one full 256-token block, normalize an autoregressive token step to one time unit. If a denoising pass costs \(d\) units and committing the block costs \(e\), the simplified generation-only speedup is:

\[ S(K)=\frac{256}{Kd+e}. \]

The launch post recommends ordinary Gemma 4 when maximum output quality is the priority. Faster text generation need not mean faster completion of a task if retries or longer reasoning are needed.

7. What to establish before deployment

Start from the official inference guide or a supported serving implementation. Pin the checkpoint and runtime versions, confirm that they support uniform-state diffusion and the recommended sampler, and then measure the intended workload. A generic causal-LM loader may not implement this generation loop.

Report hardware, quantization, concurrency, prompt/output lengths, actual denoising passes, time to first finalized output, end-to-end latency, and task quality together. The advertised quantized 18 GB footprint is not a universal memory budget: weights, the context KV cache, canvas activations, and runtime workspace still count. Consult quantization and batching for those separate trade-offs.

The official weights and documentation are linked here for study; this page does not install packages, download model weights, or execute external inference code.
