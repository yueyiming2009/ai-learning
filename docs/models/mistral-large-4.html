Mistral Large 4 — Le Chonk

Two kinds of sparsity, a vision encoder, and a large-scale RL loop: how the public preview became an improved open-weight model.

1. Preview, released weights, and parameter accounting

The October 6 preview announcement promised a later weights release. The subsequent release announcement and official checkpoint establish that weights are now available. Preview benchmark numbers should not silently stand in for this improved checkpoint.

The model is branded as 1T total/52B active. Mistral's docs give 1.05T total, while the checkpoint card distinguishes 49B active excluding embeddings/output layers from 52B including embeddings and output layers. Keep that accounting distinction when comparing sparse models. It accepts text and images, emits text, and supports a 1,048,576-token context.

Walk the actual attention path

The pinned implementation's MistralLarge4TextAttention has no Q-LoRA: \(x\in\mathbb R^{6144}\) projects directly to \(64\times128=8192\) query features. For a RoPE layer, each head splits into 64 unrotated and 64 rotated coordinates. A NoPE layer uses all 128 as unrotated coordinates.

There are two independent reuse maps. In the released configuration, nine late NoPE layers (1-based layers 40, 44, …, 72) reuse layer 36's KV source. That leaves 63 unique target-KV sources. Separately, 28 layers reuse index results, leaving 44 indexers. Neither “shared” label means the entire attention block shares weights.

Sparse semantics do not guarantee sparse execution. The pinned eager/SDPA path expands KV and constructs a dense mask; specialized attention paths consume sparse indices. At 1M tokens, materializing one layer's 64-head K and V tensors at BF16 would already take 32 GiB, before attention scores. A dense fallback is therefore not an interchangeable performance baseline for the optimized serving recipe.

Implementation: indexer and attention. Inspection only; no backend was executed.

Walk the FFN: expert count is not expert width

The FP32 router scores the full 6144-wide input with a softmax, selects four of 128 routed experts, and renormalizes the selected weights. Each expert has two \(6144\times6144\) gated-FFN input matrices and one return matrix. One always-on shared expert runs alongside the routed sum:

\[ y_{\rm FFN}=\sum_{i\in\mathcal S}p_i\, \big(\operatorname{SiLU}(xW_{g,i})\odot xW_{u,i}\big)W_{d,i} + e_{\rm shared}(x). \]

Per MoE layer, routed matrices contain 14.496B parameters; four selected experts touch 452.985M matrix parameters for one token, plus 113.246M for the shared expert. Their forward matrix work is about 1.132 GFLOPs/token/layer, excluding attention, routing, activation, and normalization. Layer 1 instead uses a dense FFN with intermediate width 24,576. The ratio \(24576/6144=4\) explains the reported expert granularity of four: each expert's intermediate width is one quarter of that reference FFN, not one quarter of the model hidden width. The 128 experts are independent networks, not four fixed slices of one matrix. See the shape and stored-versus-active parameter example; the shared expert adds work beyond the routed top-four budget.

This is not Latent MoE: there is no shared 6144 → narrower-expert-width → 6144 pair surrounding these experts. Contrast Muse's 8192 → 4096 routed path. Sparse activation saves computation; it does not let a multi-request batch store only four experts, because different requests can choose different experts.

Source: FFNs, router, expert sum, and residual block.

3. The reported training progression

  1. 1. Train a multimodal foundationThe technical report specifies 3,840 GB200 GPUs near Paris and 45 days of pretraining. The announcements describe multilingual data spanning more than 160 languages.
  2. 2. Supervised fine-tuning and RLThe preview account attributes gains to both SFT and RL. Tasks cover scientific reasoning, chat, factuality, safety, and long-horizon tool use, sharing composable environment and verification interfaces.
  3. 3. Continue improving after previewThe open-weight announcement reports three additional weeks of RL, incorporating feedback and improving coding and token efficiency.
  4. 4. Release an improved checkpointOne weight set supports low, medium, and high reasoning effort. The released package includes a speculative draft head and an additional official NVFP4 variant.

Pretraining evidence from §§2.2–2.3: a two-phase curriculum allocates 65% to broad coverage and 35% to a higher-quality, more STEM-focused mixture. The second phase raises the code share from 16.9% to 39% and sequence length from 4K to 40K. The report specifies AdamW with \((\beta_1,\beta_2)=(0.975,0.975)\), rather than leaving the optimizer entirely undisclosed.

Hardware and execution: the report names fine-grained FP8 training, a larger NVLink domain for wide EP, NVLink-C2C to Grace for activation offload, ZeRO-2, selective recomputation, kernel fusion, and compute/communication overlap. It also names SM margin to reduce cross-stream contention, asynchronous data/checkpoint/metrics work, and monitoring for CPU stalls, non-finite values, and NFS slowdowns. These are reported mechanisms, not a complete set of launch parameters.

Why ZeRO-2, not ZeRO-3? §2.3 names ZeRO-2 but gives no direct comparison or decision rationale. Avoiding repeated parameter gathers when working weights already fit is a general memory/communication trade-off, not a confirmed Mistral explanation. MAI's YOLO account separately documents activation offload enabling ZeRO-2; do not transfer that finding to Mistral as fact.

Granularity and balancing are model–systems choices

Why granularity four? In Mistral's comparison, increasing granularity to eight reduced the FLOPs needed to match perplexity by about 4.3%, with reported uncertainty of 0.5 percentage points, but incurred approximately 5% training slowdown. That motivated granularity four. The report does not attribute the slowdown among individual kernels or communication stages: fewer quality-matched FLOPs are not automatically less wall-clock time.

Balance the executing EP group, not only the global batch. Mistral aggregates statistics over the tokens handled by each EP group and balances expert inbound tokens. Its comparisons favored this choice when trading off imbalance and validation perplexity; the coefficient was tuned against load, perplexity, and downstream evaluations. Changing partitioning also changes this objective's statistics, so small-scale experiments must preserve or explicitly study that difference.

Mechanics: why opposing local imbalances can disappear in global counts and EP group → rank → local expert group. MAI-style local capacity borrowing is a separate scheduling mechanism; the Mistral balancing disclosure does not establish that it uses MAI's runtime design.

Source: technical report, §§2.2–2.3, pp. 2–3. Compare quality per FLOP versus time to quality without equating different models' measurements.

Post-training runtime reported in the announcements

What the runtime contributes: an autoscaling actor fleet collects tens of thousands of rollouts concurrently while training runs asynchronously. Shared sandboxes, search, and APIs support multiple task types; verifiers combine tests, reward models, judges, and static checks. The preview account reports about 33B generated tokens/day on roughly 3,000 GPUs, of which about 16B are trainable completion tokens after filtering and masking. These are different denominators, not interchangeable throughput measures.

Long trajectories can span multiple context compactions. The announcement reports low-staleness/off-policy controls, but does not specify enough to reconstruct token provenance, the exact objective, or freshness thresholds. Do not substitute another framework's defaults for those missing details.

Evidence boundary: the report adds concrete pretraining disclosures beyond the launch announcements. This page summarizes selected sections, not every post-training method in the report. The reported mechanisms and the public inference implementation do not by themselves constitute a reproducible training launch recipe; undisclosed settings must not be filled with another framework's defaults.

4. A model package is more than the target weights

The main official checkpoint uses blockwise FP8 quantization with higher-precision exceptions. The NVFP4 variant targets Blackwell serving. Neither storage format alone establishes the precision used throughout the original training run.

The card describes an embedded DSpark draft head: three dense MLA draft layers in BF16 proposing a three-token block. It reports up to 1.9× serving throughput versus the target alone, dependent on workload and hardware. This is a serving comparison, not an RL sample-efficiency gain.

The recommended settings are temperature 1.0, top-p 0.95, and reasoning effort low, medium, or high (default). Correct reasoning/tool parsing and a combined reasoning-plus-output budget are part of the interface. Follow the card's version-specific engine guidance; no weights, container, or model code was installed or executed for this page.

Mechanics: speculative decoding and quantized serving.

Worked memory budget: 2048 selected keys does not mean a 2048-token cache

The indexer needs candidates from the growing history. Let \(T\) be cached tokens and \(C\) independent requests. For uniform \(b\)-byte cache elements, the reference layout gives the following payload estimate, not peak allocated memory:

\[ M_{\rm cache}=CTb\,[54(512+64)+9(512)+44(128)]. \]

The terms are RoPE KV sources, NoPE KV sources, and indexer keys. At \(T=2^{20}\), \(C=1,b=2\), they occupy 69.75 GiB target KV + 11 GiB index keys = 80.75 GiB. No-cache/index-sharing at otherwise identical dimensions would be 96.75 GiB. Sparse index selection reduces attention work, not this history's length.

X: context in Ki tokens (1024 means 1,048,576). Y: aggregate GiB. Excludes padding, scales, workspaces, draft caches and prefix sharing between requests. The 8-bit option is an arithmetic scenario, not a verified backend setting.

Separately, 1.05T parameters at one byte each are about 977.9 GiB; an idealized four-bit payload is about 488.9 GiB. The real release has precision exceptions, scales, and a draft head. Equal weight sharding across eight devices is only an average payload budget; it does not establish that the largest intermediate tensors or a chosen batch/context fit each device.

What a grounded customization walkthrough must preserve

  1. Separate the initial checkpoint from the desired task. Start from the released model and processor, not an assumption that a serving FP8/NVFP4 path supports all training operations. Record the engine, checkpoint, quantization, and adapter policy.
  2. Preserve the model's input contract. The processor merges image features into the token stream and renders reasoning/tool turns. Audit target masks after rendering; raw conversational text is not automatically an aligned SFT batch.
  3. Choose placement from stored state, not 52B active parameters. EP distributes routed experts; TP/PP handle dense projections and depth. Check activations, image tokens, logits, and largest gathers in addition to resident weights.
  4. Qualify updates separately from inference. A forward pass with DSpark does not prove correct learner gradients, and a small-memory quantization does not prove a trainable optimizer path. Compare held-out full agent behavior after a bounded update.

These are implementation-grounded experiment gates, not a claim about Mistral's original optimizer or an executed fine-tuning recipe. They explain why a command that serves the model is not yet an end-to-end training procedure.

5. Preserve the checkpoint and benchmark version

The weights-release account reports Terminal-Bench 4.0 improving from roughly 28% at preview to 41%, with 30% fewer output tokens. It reports 48% on the Artificial Analysis Coding Agent Index and a favorable quality/token trade-off. These remain source-reported results, not independently reproduced measurements.

Some integration documentation still repeats preview-era scores. Prefer the release source when discussing the released checkpoint, and retain the benchmark version, harness, and reasoning effort. In particular, Mistral's card cites Intelligence Index v5; the October Muse Spark Open methodology uses v4.3. Their raw aggregate numbers are not directly comparable.

Benchmark attack resistance is measured under a test setup, not a guarantee that any self-hosted agent is safe without deployment-specific controls.

6. Open weights, with a custom license

The Mistral Ecosystem Open-Weight License is modified from MIT, not unmodified MIT. It requires attribution/notices and a separate commercial license when the licensee or an affiliate operates a Model-as-a-Service business and uses the model commercially, subject to its definitions and exceptions. Its internal-use and official-product exceptions are explicit; it does not use the revenue threshold found in some other open-weight licenses.
