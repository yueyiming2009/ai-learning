1. The open-weight branch, not merely the API model

Meta released Muse Spark Open on October 15, 2026. Its official checkpoint card lists 816B total parameters, 42B active per token, and a 1M-token inference context. Text, images, video, and audio are inputs; text is the output.

Shared base → Muse Spark 1.3 and the Muse Spark Open development branch.
Open-release difference → additional safety post-training for use outside the hosted system's guardrails → downloadable Muse Spark Open.

The shared-base relationship comes from the PyTorch release account. It does not establish every intermediate checkpoint or the order of all capability-training stages. Muse Glimmer is a separate small dense member, not a smaller checkpoint automatically obtained by pruning this MoE.

The card's image-encoder fields do not describe every modality. The public model path packs images and video frames into one vision forward, applies an adapter/projection and perception normalization, then gathers the resulting feature banks at token-aligned indices. Audio has its own waveform encoder and feature bank, normalized before the same token-alignment step. This is more specific than “multimodal embeddings are concatenated.” The useful contrast with Le Chonk's indexed MLA and K3's KDA/MLA hybrid is the disclosed attention mechanism, not an inferred common architecture.

Mechanics: attention, MoE routing, KV-cache accounting.

Read one block in execution order

For each normalized input \(x\in\mathbb R^{8192}\), the fused QKV projection produces \((128+2\times16)\times64=10240\) features: 8192 Q, 1024 K, and 1024 V. Eight query heads share each KV head. Per-head Q/K normalization precedes positional encoding. One-based layers 2, 6, 10, …, 62 are global and use no RoPE; the other 46 layers use a 2048-token sliding window and complex RoPE.

The attention result is normalized per head, flattened to 8192 features, multiplied by an input-dependent sigmoid gate of the same width, and projected with \(W_o\). That full-width gate is a learned \(8192\times8192\) projection, not one scalar per head.

A second, different gate controls the residual connection after branch normalization:

\[ \beta=\sigma(g/\tau),\qquad \alpha=\sqrt{\max(1-\beta^2,\epsilon)},\qquad h_{\rm next}=\alpha\odot h+\beta\odot {\rm branch}. \]

The gate \(g\) is a learned per-channel parameter, not the attention output's input-dependent gate. Away from the floor, \(\alpha^2+\beta^2=1\); this does not guarantee an exactly preserved norm for correlated streams and branches. The pinned implementation carries the residual in FP32 while attention/expert branches use BF16.

Sources: attention order, residual gates and block, production flavor.

Muse's compressed experts: the detail the model-card summary missed

The router reads all 8192 features and computes FP32 sigmoid scores. Expert bias affects top-8 selection; mixture weights use the selected unbiased scores, normalized across those eight experts. A load-based bias update handles balancing. Meanwhile the compute path applies a shared 8192 → 4096 projection and normalization before dispatch.

Each selected expert computes a gated \(4096\to4096\to4096\) FFN. Its output is normalized before weighting and aggregation; the combined 4096-wide result is then projected back to 8192. No full-width shared expert is configured—the class explicitly rejects one. Compare with Kimi's norm after the sum and Nemotron's two-matrix ReLU² experts.

The routed matrices alone contain 12.885B parameters per layer, 798.864B over 62 layers. The two compression projections add 67.109M/layer. At top-8, forward matrix work for this branch is about 0.940 GFLOPs/token/layer; full-width experts at the same intermediate width would cost 1.611 GFLOPs. This is a shape-controlled counterfactual, not a claim that equal quality survives removing compression.

The Latent MoE guide owns the shared tensor/gradient derivation and calculator. Here the defining choices are full-width routing, half-width expert computation, per-expert normalization, and no shared branch.

Sources: compressed MoE forward and router/expert configuration.

3. What is known about how the model was trained

The model card describes multimodal data from public sources, web crawling, acquired data, Meta products/services, and synthetic generation, with cleaning, deduplication, processing, and filtering. It reports more than 100 languages. These are broad source categories, not a released corpus or an independently audited provenance ledger.

The release accounts describe training for multi-file coding, tool use, browsing, computer interaction, and long-horizon workflows. The model learns to plan, act, observe, and recover from errors; the open release adds safety post-training because downstream deployments may not retain the hosted product's safeguards.

Missing original-training details: the exact pre-training token budget, optimizer/schedule, full SFT/RL ordering, reward objectives, specialist/consolidation structure, and intermediate checkpoint handoffs are not supplied here. Do not draw a precise nine-teacher or SFT → GRPO pipeline just because another model uses one.

Customization is a separate story. TorchTitan's public support for multi-turn SFT, LoRA, and TitanRL lets users further tune the released model. That capability does not prove TorchTitan or TitanRL was the original production training stack.

Sources: training-data disclosure and PyTorch integration account. Context: stage handoffs and TorchTitan. The concrete customization path below is separately supported by public code.

4. Portability and memory are workload-dependent

Meta lists BF16 and NVFP4 weights, support across multiple inference engines, and an MLX deployment on two M5 Ultra Mac Studios. The combined memory capacity of two systems is not a guarantee that any precision, concurrency, and 1M-context workload fits. Budget weights, caches, activations, and runtime overhead separately.

Helion implementations cover operations such as RoPE, RMSNorm, and quantization. The release reports 1.03–3.95× kernel-level speedups on the tested GPU paths and 3% end-to-end throughput improvement on AMD MI350. Those are different measurement scopes. A fast kernel does not imply the same whole-model speedup, and portability does not remove the need to tune shapes and hardware.

The card recommends temperature 1.0, top-p 1.0, and disabled top-k. Reasoning effort supports low, medium, high, and xhigh, with xhigh the default. The card and deployment documentation, not a generic OpenAI-compatible request shape, define this model's supported interface.

Sources: release account, kernel integration, and the model card. No hardware, kernels, model code, or weights were run for this page.

Worked cache budget: local/global layout changes the answer

At two bytes per element, one token's K and V in one attention layer occupy \(2\times16\times64\times2=4096\) bytes. Assuming a serving backend evicts local KV outside its window, \(C\) independent requests of length \(T\) require:

\[ M_{\rm KV}=C\cdot4096\,[16T+46\min(T,2048)]. \]

At \(T=2^{20}\) and \(C=1\), that is 64.36 GiB, versus 248 GiB if all 62 layers retained full history. A training sliding-window mask does not by itself guarantee this cache-eviction implementation. Prefix sharing, quantization, metadata, and engine-specific allocation can change actual usage.

Weights are the other large term. 816B BF16 parameters imply about 1519.9 GiB of raw weight payload; ideal four-bit packing implies 380.0 GiB before scales and higher-precision exceptions. One-device “42B active” arithmetic cannot size an 816B deployment.

With an illustrative EP16 placement, the calculated 798.864B routed expert parameters contribute 93 GiB BF16 per rank. The remaining nominal parameters add roughly 31.9 GiB/rank if replicated, before activations, adapters, scratch, and cache. This explains why even a LoRA run needs a serious placement plan.

A real public SFT recipe—not a reconstruction of Meta's original run

The pinned TorchTitan recipe muse_spark_816b_a42b_ultradata_lora_sft_cp16_128k provides a concrete post-release adaptation path. Its stated target is 16 GB300 GPUs, 128K sequences, CP16/EP16/TP1, BF16 Dist-MoE and FA4. This is a source example, not a run performed here.

Multimodal distributed training adds a participation contract. Enabled perception encoders run on every DP rank, using dummy media where necessary, so FSDP all-gathers/reduce-scatters stay aligned. Unlisted modalities are skipped consistently; unused encoder gradients remain None. Rank-dependent “no image, skip the encoder” logic can hang even when the text tensors look correct.

Full-parameter Adam-style training at an illustrative 16 bytes/parameter would require about 13.1 TB of aggregate state before activations. LoRA reduces trainable gradient/ optimizer state, not the need to place the frozen expert weights. The README further restricts TP/EP/CP combinations; e.g. Ulysses requires TP × CP to divide 16 KV heads. Do not multiply individually valid parallelism flags arbitrarily.

5. A score table is a mixture of measurement protocols

The October card reports 61.8 on JobBench, 89.2 on MCP-Atlas, 76.4 on Terminal-Bench 2.1 with the Terminus 2 agent, and 80.4 on OSWorld-Verified. The accompanying eight-page methodology is essential to interpreting those values.

  • Mixed sources: results come from official leaderboards, internal runs, or providers' self-reports. When leaderboard coverage is incomplete, the method selects the highest comparable available primary-metric value, rather than one uniform laboratory rerun of every model.
  • Harness differences: DeepSWE uses preferred/self-reported harnesses; the Terminal-Bench 2.1 comparison mainly uses Terminus 2. OSWorld uses a 361-task subset, 200-step cap, and four attempts per task, with some competitors self-reported.
  • Version and date: the Intelligence Index is v4.3 with scores sourced October 7. Do not directly compare it with Mistral's later v5 number, or mix preview and weights-release checkpoints.
  • Safety scope: Meta's release criteria and measured refusal behavior apply to the tested checkpoint/configurations. The card still recommends system-level guardrails; downstream modifications can change those results.

6. The Muse Model License and gated distribution

The Muse Model License includes notices, a Usage Policy, and a “Built with Muse Spark Open” attribution requirement. For a Model-as-a-Service business above the stated aggregate $20M revenue threshold over a consecutive twelve-month period, it requires notification and a separate written agreement before offering the model or derivatives in that business. Internal use and qualifying product-feature uses have explicit exclusions.

This is not an unmodified MIT/Apache license. The official Hugging Face distribution also presents an access form and license conditions. No form was submitted, terms accepted, or weights downloaded during this documentation task; only public documentation was read.
