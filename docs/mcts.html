RL Foundations

Monte Carlo Tree Search

Build a search tree at decision time. Simulate possible futures, back up the results, and use visit counts and value estimates to find the best action — without needing a perfect model.

🎓
David Silver's Reinforcement Learning Course (DeepMind/UCL)

Covers MCTS from Lectures 8 (integrating learning and planning — simulation-based search) and 10 (classic games — MCTS for Go).

DQN learns to act greedily from a single forward pass — no lookahead, no planning. MCTS does the opposite: at every decision point it simulates hundreds or thousands of possible futures, building up a local search tree before committing to an action. The key insight is that you don't need to search the entire game tree — you only need to search well enough to find a better action than greedy. UCB tells you where to focus the search budget.

Notation

SymbolDescription
\(N(s)\)Visit count of node (state) \(s\)
\(N(s,a)\)Visit count of edge (state–action pair) \((s,a)\)
\(W(s,a)\)Total value accumulated through edge \((s,a)\)
\(Q(s,a)\)Mean value of edge \((s,a)\): \(W(s,a) / N(s,a)\)
\(c\)Exploration constant — scales the UCB bonus
\(P(a \mid s)\)Prior probability of action \(a\) from state \(s\) (from policy network in neural MCTS)
\(V_\theta(s)\)Value network estimate of expected return from state \(s\)
\(K\)Number of simulations (search budget)

1. The Four Phases

Each MCTS simulation repeats four steps. Run \(K\) simulations, then act.

1
Selection

Traverse the existing tree from the root, choosing the child with the highest UCT score at each node, until reaching a leaf or terminal state.

2
Expansion

If the leaf is not terminal and has been visited at least once, add one (or more) child nodes to the tree by expanding an unvisited action.

3
Simulation

From the new node, run a rollout — play to the end using a fast (often random) policy and observe the terminal return \(G\).

4
Backpropagation

Walk back up the path from leaf to root. For every edge \((s,a)\) on the path: \(N(s,a) \mathrel{+}= 1\), \(W(s,a) \mathrel{+}= G\), \(Q(s,a) = W / N\).

After \(K\) simulations, select the action from the root with the highest visit count \(N(s_0, a)\) — the most-explored action is typically the most reliable, since UCB concentrates visits on promising branches.

The simulation phase is the "Monte Carlo" in MCTS — it estimates the value of a node by sampling a random trajectory from it, exactly like the MC rollouts page describes. The "tree search" part is UCB-guided selection, which concentrates those rollouts on promising branches instead of sampling uniformly.

2. UCB and UCT — The Selection Formula

At each selection step, MCTS must choose which child to visit. A purely greedy choice (\(\arg\max_a Q(s,a)\)) would exploit known good actions but never discover better ones. A purely random choice would explore uniformly but waste budget on bad branches. UCB1 (Auer et al., 2002) solves the multi-armed bandit version of this dilemma:

\[ \text{UCB1}(a) = \bar{r}_a + c\sqrt{\frac{\ln N}{N_a}} \]

UCT (Upper Confidence bounds applied to Trees, Kocsis & Szepesvári 2006) lifts UCB1 into the tree by applying it at every node:

UCT selection score
\[ \text{UCT}(s, a) = \underbrace{Q(s,a)}_{\text{exploit}} + c\,\underbrace{\sqrt{\frac{\ln N(s)}{N(s,a)}}}_{\text{explore}} \]
Exploitation term
\(Q(s,a) = W(s,a) \,/\, N(s,a)\)

Mean return from all past simulations through \((s,a)\). High \(Q\) → this action has historically led to good outcomes.

Exploration bonus
\(c\,\sqrt{\ln N(s) \,/\, N(s,a)}\)

Grows large when \(N(s,a)\) is small relative to the parent's visit count. Forces the search to eventually visit every action.

How UCT concentrates budget

When \(N(s,a) = 0\) (action never tried), the exploration bonus is infinite — UCT always tries unvisited actions before revisiting. Once every action has been tried, UCT balances: a good-but-well-visited action competes with a mediocre-but-rarely-visited one. As \(N(s,a) \to \infty\), the exploration bonus shrinks to zero and UCT converges to greedy. The constant \(c\) controls how long exploration persists — larger \(c\) = more exploration.

UCT is theoretically grounded: for multi-armed bandits, UCB1 achieves \(O(\log N)\) regret — optimal up to a constant. In trees the analysis is more complex, but empirically UCT finds near-optimal actions with far fewer simulations than exhaustive search.

3. The Full MCTS Algorithm

Algorithm — MCTS with UCT
Require: root state s₀, simulation budget K, exploration constant c
Initialize: N(s₀) ← 0;  for each a: N(s₀,a) ← 0,  W(s₀,a) ← 0

for simulation = 1 to K do
    s ← s₀;  path ← []

    ▷ Selection
    while s is in tree and s is not terminal do
        a ← argmaxa' UCT(s, a')             ▷ exploit + explore via UCB
        path.append(s, a);  s ← transition(s, a)
    end while

    ▷ Expansion
    if s is not terminal then
        add s to tree;  N(s,·) ← 0;  W(s,·) ← 0
        a ← any unvisited action from s
        path.append(s, a);  s ← transition(s, a)
    end if

    ▷ Simulation
    G ← rollout(s)                           ▷ random play to terminal state

    ▷ Backpropagation
    for (s, a) ∈ reversed(path) do
        N(s, a) ← N(s, a) + 1
        W(s, a) ← W(s, a) + G
        Q(s, a) ← W(s, a) / N(s, a)
        N(s)    ← N(s) + 1
    end for
end for
return argmaxa N(s₀, a)                      ▷ most-visited action at root
Acting by \(\arg\max_a N(s_0, a)\) (most visited) is more robust than \(\arg\max_a Q(s_0, a)\) (highest mean value) because visit counts are less noisy — a good action gets visited many times, while a single lucky rollout can inflate Q for a rarely-visited action.

4. Neural-Guided MCTS

Pure MCTS with random rollouts works well in games with short episodes and dense reward (Go, chess). It struggles when:

  • Rollouts are expensive (long episodes, slow simulators)
  • Random play is uninformative (the rollout policy is too bad to reach meaningful terminal states)
  • The branching factor is huge (many possible actions — uniform UCB exploration wastes budget)

Neural networks address all three by replacing the two weakest parts of MCTS:

Pure MCTS
Random rollout

Play randomly until terminal. Cheap but uninformative in complex domains — the signal from a random-play game is barely related to the value of the starting position.

Neural MCTS
Value network \(V_\theta(s)\)

Evaluate the leaf directly with a learned value function. No rollout needed — one forward pass replaces an entire trajectory. Dramatically reduces simulation cost.

Pure MCTS
Uniform prior over actions

UCT treats all unvisited actions equally. In Go (∼250 legal moves) or LLM token generation (∼100k vocab), this wastes budget on obviously bad moves.

Neural MCTS
Policy network \(P_\theta(a \mid s)\)

Use the network's prior probability as an initial bias in UCB. Focus early simulations on plausible actions; let the search refine from there.

5. PUCT — AlphaZero's Selection Formula

AlphaZero (Silver et al., 2017) replaces UCT's exploration bonus with a policy-weighted version called PUCT (Predictor UCT):

PUCT selection score
\[ \text{PUCT}(s, a) = Q(s,a) + c \cdot P(a \mid s) \cdot \frac{\sqrt{N(s)}}{1 + N(s,a)} \]

Compared to UCT, two changes:

  • \(P(a \mid s)\) multiplier: the policy network's prior probability scales the exploration bonus. Actions the network thinks are likely start with a larger bonus, focusing early simulations on plausible moves rather than exploring uniformly.
  • \(\sqrt{N(s)} / (1 + N(s,a))\): functionally similar to \(\sqrt{\ln N(s) / N(s,a)}\) but cheaper to compute and smoother when \(N(s,a) = 0\) (bonus is \(\sqrt{N(s)}\) rather than \(\infty\)).
The interplay between search and network

The policy network \(P_\theta\) shapes where the search looks; the search corrects the network's mistakes. A node that looks bad to the network but good after careful search will accumulate visits and update \(Q(s,a)\) upward — overriding the prior. In AlphaZero training, the visit count distribution \(\pi_\text{MCTS}(a) \propto N(s_0, a)^{1/\tau}\) is used as a training target for the policy network, so the network gradually learns to agree with the search. This self-reinforcing loop is the engine of AlphaZero improvement.

6. MCTS in LLM Reasoning

MCTS has become an active tool for scaling test-time compute in LLMs — spending more inference budget to produce better answers to hard problems.

MDP componentIn LLM MCTS
State \(s_t\)Prompt + reasoning steps generated so far (partial chain-of-thought)
Action \(a_t\)The next reasoning step — typically a sentence or paragraph, not a single token
TransitionAppend the step to the context (deterministic)
Rollout / valueEither continue generating to a final answer and score it, or query a process reward model (PRM) to score the current step
Terminal rewardOutcome reward model (ORM) score on the final answer, or ground-truth correctness
Policy prior \(P(a \mid s)\)The LLM's own next-step probabilities — concentrated on likely continuations

Process reward models (PRMs) as the value function

In standard MCTS the value network \(V_\theta(s)\) evaluates intermediate states. For LLM reasoning, a process reward model plays this role: it scores each reasoning step, not just the final answer. This is the LLM equivalent of AlphaZero's value head — a signal that tells the search whether the current chain of thought is on a good path, without needing to generate a complete answer.

PRMs are hard to train (they require human annotations or strong automated verifiers for intermediate steps), which is why many LLM MCTS systems fall back to outcome-based rollouts — generate a complete answer, check correctness, backpropagate. More expensive, but avoids the PRM training problem.

Branching at step level, not token level

Applying MCTS at the token level is computationally intractable — the branching factor equals the vocabulary size (~50k), and each node requires a full forward pass. Practical systems instead branch at the reasoning step level: generate one complete sentence or thought, evaluate it, and branch from there. This keeps the branching factor manageable (typically 2–8 continuations per node) at the cost of reduced granularity in the search.

Test-time compute scaling

The central empirical finding: for hard reasoning problems (math, code, logic), spending more MCTS simulations at inference time — without changing the model's weights — consistently improves accuracy. This is "test-time compute scaling": trading inference FLOPs for answer quality. OpenAI's o1/o3 and DeepSeek-R1 are examples of models trained to exploit this — though their exact search strategies are not fully public.

Summary

Four phases

Select → Expand → Simulate → Backpropagate. Repeat \(K\) times, then act.

UCT

\(Q(s,a) + c\sqrt{\ln N(s)\,/\,N(s,a)}\) — exploit good actions, explore undervisited ones

Action selection

\(\arg\max_a N(s_0, a)\) — most visited, not highest Q, for robustness

PUCT

\(Q(s,a) + c \cdot P(a|s) \cdot \sqrt{N(s)}\,/\,(1+N(s,a))\) — policy-weighted exploration

Replace random rollout with \(V_\theta(s)\); replace uniform prior with \(P_\theta(a|s)\)
