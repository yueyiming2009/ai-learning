Reward Pipelining in RL Post-Training

Decoupling reward computation from trajectory generation to hide reward latency, queue mechanics, and how reward pipelining composes with async RL.

Prerequisite: Inference in RL (rollout vs. reward model serving, throughput matching) and Async RL (policy lag, IS correction). This page covers the reward-specific latency problem and how to pipeline around it.

1. The Reward Bottleneck

In synchronous RL, reward computation is on the critical path between rollout and training:

rollout → [wait for all rewards] → train → repeat

For simple rule-based rewards — format checks, exact-match, regex — the cost is negligible. For richer sources it is not:

Reward sourceLatency per trajectoryBlocking?
Rule-based verifier (math, code)1–50 msMild
Process reward model (PRM)0.5–2 s (N forward passes)Yes
LLM-as-judge2–15 s (separate model call)Yes
Sandboxed code execution5–60 s (spawn + run)Severe

When generation takes 3 s and the reward call takes 8 s, rollout workers sit idle for 8 s per step. You can speed up decoding all you want and the bottleneck remains — the two latencies do not trade off against each other in a synchronous design.

2. Reward Pipelining: Decoupling Reward from Generation

Reward pipelining overlaps reward computation with the next generation batch:

rollout pool:   [gen batch 1] → [gen batch 2] → [gen batch 3] → ...
reward workers:              [rew batch 1] → [rew batch 2] → ...
trainer:                                   [train on batch 1] → ...

Trajectories are submitted to a reward queue immediately upon completion. Generation starts on the next prompt batch before any rewards return. Rewards trickle back asynchronously and are matched with their trajectories in a training buffer. The trainer drains the buffer whenever a sample has both a trajectory and a reward attached.

The reward workers form an independent service — one or more reward models, verifiers, or judge LLMs running continuously, processing trajectories from the queue and writing scalars back.

What this requires:

  • A queue or buffer holding (trajectory, prompt_id, reward_placeholder) tuples
  • A matching step that joins trajectory + reward before the trainer sees the sample
  • A staleness policy for rewards that take too long (drop or use a fallback)

3. Reward Sources and Batching

The pipelining benefit depends on how reward calls can be structured:

Batched verifier calls

Rule-based verifiers and lightweight discriminators are embarrassingly parallel. Accumulate \(B\) trajectories and evaluate them in one call — per-trajectory overhead amortizes across the batch. The reward worker runs the verifier in a loop; the main loop never blocks.

Batched reward model inference

A PRM or outcome reward model is a standard LLM inference job. Treat it like the rollout model: batch trajectories, run prefill + a short decode (or just prefill for the scalar head), return results. With prefix caching the shared prompt prefix is computed once per batch. The reward worker is a vLLM/SGLang instance, not a bespoke service.

Key sizing constraint: the reward throughput \(T_r\) must satisfy:

Throughput requirement
\[ T_r \;\geq\; T_{rollout} \]

If reward throughput falls behind rollout throughput, the queue grows without bound — reward becomes the new bottleneck regardless of pipelining.

LLM-as-judge

The judge is a separate (often larger) model. Reward pipelining is most valuable here — judge latency (2–15 s) far exceeds generation latency for short responses. The judge call goes into the queue; generation continues. Satisfying \(T_r \geq T_{rollout}\) usually requires either a smaller judge or multiple judge replicas.

Multi-source rewards

Production systems mix reward sources: a fast rule-based component (grammar, format) plus a slow judge. Pipeline only the slow component. The fast reward is computed inline and attached immediately; the slow reward is added asynchronously. The training buffer waits for the union of both.

4. Queue Depth and Back-Pressure

The natural queue depth — the number of in-flight reward requests at steady state — is:

Steady-state queue depth
\[ d \approx L_{reward} \times T_r \]

\(L_{reward}\) = end-to-end latency of one reward call  ·  \(T_r\) = reward throughput (trajectories / s)

Too shallow

Reward is still on the critical path — the trainer drains the buffer faster than rewards arrive and stalls waiting for completions. Pipelining bought nothing.

Too deep

High memory pressure (all in-flight trajectories held in the buffer) and high reward staleness — rewards arrive well after the trainer has moved on.

Back-pressure: if the trainer is slower than reward computation, the buffer fills. Bound the buffer and pause submission of new trajectories to the reward queue when the buffer is full — this propagates back-pressure to the rollout pool and prevents unbounded memory growth.

5. Off-Policy Implications

For most reward formulations, reward pipelining does not introduce off-policy bias. The reward is a function of the trajectory alone — correctness of an answer, format compliance, code execution output — and does not depend on the current policy \(\pi_\theta\). A trajectory generated at step \(t\) gets the same reward whether it is evaluated at step \(t\) or step \(t+K\).

The exception is a policy-conditioned reward: a value-based PRM that uses \(V^\pi\) to score intermediate states, or a relative reward that compares the trajectory against the current policy's distribution. If the reward explicitly depends on \(\pi_{\theta_{current}}\) and the policy has advanced \(K\) steps, the reward is stale in a way IS correction cannot fix — the reward function itself has drifted, not just the generation distribution.

In practice most deployed reward sources (outcome RM, LLM-as-judge, code verifier) are trajectory-only and do not condition on the policy. The policy-conditioned concern applies mainly to PRM designs that incorporate a learnable value function.

Reward staleness budget

Bound the reward queue age independently of the generation staleness budget. Define a reward freshness threshold \(K_{rew}\): if a reward has not arrived within \(K_{rew}\) training steps since the trajectory was generated, drop the sample (or substitute a fallback reward). This is analogous to staleness_threshold for generation lag but operates on reward latency, not policy lag.

6. Composing with Async RL

Async RL decouples generation from training. Reward pipelining decouples reward from generation. The two compose naturally into a fully decoupled three-stage pipeline:

generation workers:   [gen] → [gen] → [gen] → ...    (continuous)
reward workers:       [rew] → [rew] → [rew] → ...    (continuous)
trainer:              [step] → [step] → [step] → ...  (continuous)

There are now two independent lag parameters:

LagSourceCorrected by
\(K_{gen}\) Policy drift between generation and training IS correction (token-level or sequence-level), staleness_threshold
\(K_{rew}\) Delay between trajectory completion and reward arrival Queue depth bound, reward freshness threshold \(K_{rew,max}\)

The total staleness is the sum. If \(K_{gen} + K_{rew}\) is large, IS correction must handle a wider distribution shift — the IS ratio \(\pi_{new}(a_t|s_t)/\pi_{old}(a_t|s_t)\) is more extreme because \(\pi_{old}\) is further back in training history.

Tuning priority: minimize \(K_{rew}\) first — reward lag adds staleness with no IS correction benefit. Then tune \(K_{gen}\) to the maximum value stable under IS correction. Do not let a large reward queue silently inflate the effective policy lag beyond what IS can handle.
