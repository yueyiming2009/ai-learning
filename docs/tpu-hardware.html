TPU Hardware for ML

How a TPU computes and communicates: the MXU systolic array that streams a matmul through a grid of multiply-accumulators, the VMEM/HBM memory it feeds from, and the ICI torus that wires thousands of chips as nearest neighbors — the hardware that makes the collective cost model's "ring" literally true.

A TPU (Tensor Processing Unit) is Google’s ML accelerator, and it is interesting precisely because it makes different choices than a GPU. Where a GPU is a general parallel processor with caches and a crossbar, a TPU is a matmul machine: a big systolic array, a simple memory system, and chips wired into a nearest-neighbor torus. Those choices are why the collectives cost model was originally written in “ring” language — on a TPU the ring is the hardware. We use the TPU v5p as the running example.

1 · The mental model: a matmul machine

A single TPU chip has just a few big functional units, not thousands of little cores:

  • MXU — the Matrix Multiply Unit, a 128×128 systolic array of multiply-accumulators. This is where essentially all the FLOPs happen.
  • VPU — the Vector Processing Unit, for the elementwise work (activations, norms, the softmax) that isn’t a matmul.
  • VMEM — a small on-chip scratchpad (like GPU shared memory) that feeds the MXU.
  • HBM — high-bandwidth memory holding weights and activations.

The design philosophy is determinism over flexibility: no speculative caches, an explicitly scheduled dataflow, and an interconnect that the compiler can reason about exactly. That makes TPUs predictable to model — which is exactly why a clean cost model like this series’ comes out of the TPU world.

2 · The MXU: a systolic array

The MXU computes a matmul by pumping data through a fixed grid rather than reading operands from memory for each multiply. Each cell holds one stationary weight; activations flow in from the left, march one step per cycle, and each cell multiplies the passing activation by its weight and adds it to a partial sum flowing downward. After the wavefront sweeps through, the column sums at the bottom are the matmul result. One load of the weights, then a whole stream of activations reuses them — enormous arithmetic intensity with almost no memory traffic.

Weights stay put; activations flow → and partial sums flow ↓. Step the wavefront through.

Because each of the \(128\times128\) cells does a multiply-accumulate every cycle once full, the array delivers \(2\times128^2\) FLOPs per cycle at peak — and reuses each loaded weight across the entire activation stream, so the operation is firmly compute-bound (the good side of the roofline). The trade-off is that the MXU is happy only when matmul dimensions are large and a multiple of 128; small or oddly-shaped matmuls leave cells idle. This is why TPU code is written to keep tensors big and aligned.

3 · Memory: HBM and VMEM

The memory system is deliberately shallow. There are essentially two levels that matter:

LevelRoleSizeBandwidth (v5p)
VMEMOn-chip scratchpad feeding the MXU (compiler-managed)~128 MB~10s of TB/s
HBMWeights, activations, optimizer state95 GB2.76 TB/s

The same roofline logic from the GPU page applies: the MXU can only run at peak if HBM (or VMEM) can feed it operands fast enough. VMEM matters most for operations with poor arithmetic intensity — its much higher bandwidth lets the chip stage data on-chip and avoid repeated HBM reads, the TPU analogue of GPU kernel fusion.

4 · The ICI: a nearest-neighbor torus

Here is the defining difference from a GPU. TPU chips are connected by the Inter-Chip Interconnect (ICI) directly to their nearest neighbors in a grid that wraps around at the edges — a torus. A v5p chip has 6 ICI links (a 3-D torus, neighbors in ±x, ±y, ±z); a v5e chip has 4 (a 2-D torus). There is no central switch: to reach a non-adjacent chip, data hops across intermediate chips.

▸ A 2-D ICI torus (4×4)
Each chip links only to its 4 neighbors; edges wrap around. No crossbar — this is the literal ring.

This wiring is why collectives on a TPU genuinely are ring/torus operations: an AllReduce passes partial sums around the torus axis, chip to neighbor to neighbor. The bandwidth cost model is the same as on a GPU (\(T \approx V/W\), each chip moves \(V(N{-}1)/N\) bytes), but two things are TPU-specific:

  • Latency grows with distance. A ring AllReduce on \(N\) chips takes \(O(N)\) hops — there is no double-binary-tree shortcut, because the tree would still have to traverse physical links. Big training reductions are bandwidth-bound so this rarely bites, but it is real.
  • Multiple axes multiply bandwidth. A reduction can run over several torus dimensions at once, using all their links in parallel — effective bandwidth scales with the number of axes used. This is the TPU way to “add more links,” analogous to multi-rail networking on GPUs.
ICI per chip (v5p)
4,800 Gbps ≈ 600 GB/s spread over the torus links — comparable to a GPU’s NVLink, but reaching thousands of chips at this speed instead of stopping at 8.

5 · Pods and the data-center network

The torus scales much further than a GPU node. A v5p pod is up to 8,960 chips wired in one 3-D torus, all at full ICI bandwidth — so the fast, ring-shaped interconnect spans the entire pod, not just 8 accelerators. (A v5e pod is 256 chips in a 2-D torus.) This is the structural reason TPUs lean on larger tensor-/data-parallel meshes than GPUs: the high-bandwidth domain is enormous.

Beyond a pod, chips talk over the standard data-center network (DCN) — ordinary, slower host-to-host Ethernet, the TPU analogue of crossing the GPU node boundary onto InfiniBand. As with GPUs, the job of the parallelism layout is to keep chatty collectives inside the fast domain (here, the pod’s ICI) and only the rare ones on the DCN.

The one idea to carry away

The bandwidth cost model \(T \approx V/W\) is identical on both — it is just bytes-per-device over link bandwidth. What differs is where the fast \(W\) runs out: at 8 GPUs on a crossbar, or at thousands of chips on a torus — and whether the ring in “ring AllReduce” is an algorithm (GPU) or the actual wires (TPU).

7 · Summary

MXU

A 128×128 systolic array: load weights once, stream activations through. Compute-bound by design — loves big, 128-aligned matmuls.

Shallow memory

HBM (95 GB @ 2.76 TB/s) + a VMEM scratchpad. Same roofline rules; VMEM is the fusion analogue.

ICI torus

Chips wired to nearest neighbors with wraparound — no crossbar. Collectives really are ring/torus ops; ~600 GB/s/chip.

Pod scale

The fast torus spans ~8,960 chips, not 8 — a huge high-bandwidth domain. Beyond it, the slower DCN.

Back to the math: Sharding & Collectives → uses the \(T \approx V/W\) model these links define, and GPU Hardware → is the crossbar counterpart to this torus. Then Tensor Parallelism → spends that bandwidth on a real layer.
