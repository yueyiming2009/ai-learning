Why mini-batches? Rollout is ~100× more expensive than a training step. Mini-batches amortize that cost: collect 64 sequences once, then extract 4 gradient updates cheaply (M=16, E=1). Multiple updates on the same batch let the policy climb further up the advantage landscape — the same intuition as running multiple SGD steps on a fixed dataset.

2. Parallelism Strategies

2.1 Tensor Parallelism (TP=2)

Model weights inside each transformer layer are split across the two GPUs of a DP rank using Megatron-LM column/row-parallel conventions — designed so each sub-layer needs only one AllReduce.

  • Column-parallel — split \(W\) along the output dimension; each TP rank holds \((H,\, K/TP)\) and produces a partial output. No communication.
  • Row-parallel — split \(W\) along the input dimension; each TP rank produces a partial sum; AllReduce (sum) across the TP group combines them.

Column-parallel and row-parallel are always paired: column feeds directly into row, so only one AllReduce is needed at the end of each pair.

Attention (TP=2, per DP rank)

x : (16, 512, H=4096)   — same on both TP ranks

# Column-parallel: split heads across TP ranks, no comm
W_Q_local : (4096, 2048)    Q_local = x @ W_Q_local  → (16, 512, 2048)
W_K_local : (4096, 2048)    K_local = x @ W_K_local  → (16, 512, 2048)
W_V_local : (4096, 2048)    V_local = x @ W_V_local  → (16, 512, 2048)

# Local flash attention over 16 heads, no comm
attn_out : (16, 512, 2048)

# Row-parallel: AllReduce to reconstruct full hidden
W_O_local : (2048, 4096)    partial = attn_out @ W_O_local  → (16, 512, 4096)
                             ► AllReduce (SUM) across TP group
out : (16, 512, 4096)       — full hidden, same on both ranks

FFN — SwiGLU (TP=2)

SwiGLU(x) = (x @ W_up) * Swish(x @ W_gate)
          = (x @ W_up) * (x @ W_gate * sigmoid(x @ W_gate))

# Column-parallel gate + up, no comm
W_gate_local : (4096, 5504)   gate = x @ W_gate_local  → (16, 512, 5504)
W_up_local   : (4096, 5504)   up   = x @ W_up_local    → (16, 512, 5504)
hidden = SiLU(gate) * up                               → (16, 512, 5504)

# Row-parallel down: AllReduce
W_down_local : (5504, 4096)   partial = hidden @ W_down_local  → (16, 512, 4096)
                               ► AllReduce (SUM) across TP group
out : (16, 512, 4096)

Each transformer layer requires exactly 2 AllReduce calls per forward pass (one after \(W_O\), one after \(W_{down}\)), and 2 more in the backward — 4 AllReduce per layer per forward-backward.

2.2 Data Parallelism (DP=4, FSDP)

The global batch is split evenly across 4 DP ranks. FSDP (ZeRO-3 equivalent) shards every weight across DP ranks — each GPU holds only \(1/DP\) of each tensor.

# Forward — AllGather to reconstruct weights before compute:
Each GPU holds shard:  W_shard : (rows/DP, cols)
AllGather across DP →  W_full  : (rows,    cols)   ← used for compute, then discarded

# Backward — ReduceScatter to sync and re-shard gradients:
Each GPU computes:      dW_full  : (rows,    cols)
ReduceScatter across DP → dW_shard : (rows/DP, cols)   ← sum-reduced + sharded

# Optimizer step — local, no communication:
W_shard -= lr * AdamW(dW_shard, m_shard, v_shard)

Memory footprint per GPU:

Parameters  : 7B × 2 bytes / (TP=2 × DP=4) ≈ 437 MB
Optimizer   : 7B × 8 bytes / (TP=2 × DP=4) ≈ 875 MB   (Adam m + v in float32)

2.3 Hybrid Engine

VeRL's hybrid engine time-multiplexes all four RL models (actor, reference, critic, reward) on the same 8 GPUs rather than dedicating separate hardware to each.

Actor = Reference + LoRA: the base model weights are frozen and shared. The reference policy runs with LoRA disabled; the actor runs with LoRA enabled. Only the LoRA adapter weights are trained — roughly \(2 \times r \times H \times L \approx 4M\) params vs 7B base. If LoRA is disabled (full fine-tuning), a separate frozen reference copy must be kept, doubling weight memory.

2.4 Flash Attention

Standard attention writes the full \((seq, seq)\) score matrix to HBM — O(seq²) memory. Flash attention (Dao et al. 2022) is an IO-aware rewrite: tiles Q, K, V into blocks that fit in SRAM, fuses softmax + matmul into one kernel using the online softmax trick, and never writes the score matrix to HBM.

# Online softmax update (per tile of K, V):
m_new = max(m_old, m_tile)
l_new = l_old * exp(m_old - m_new) + sum(exp(s_tile - m_new))
out   = (out_old * l_old * exp(m_old - m_new) + exp(s_tile - m_new) @ V_tile) / l_new

# Kernel structure:
for each block of Q (fits in SRAM):
    m = -inf,  l = 0,  out = 0
    for each block of K, V (streamed from HBM):
        s = Q_block @ K_block.T    ← stays in SRAM
        m, l, out = update(m, l, out, s, V_block)
    write out_block to HBM         ← only output written to HBM

Memory: O(seq) instead of O(seq²). The backward pass recomputes tiles on the fly from saved Q/K/V rather than storing the score matrix.

Phase 7

Advantage Estimation (GAE)

Controller CPU — no GPU, no NCCL. Pure scalar operations.

KL penalty

kl = old_log_probs - ref_log_probs                    # (64, 512)
penalized_rewards = token_level_rewards - beta * kl   # (64, 512)

GAE backward pass

GAE interpolates between one-step TD (low variance, high bias) and Monte Carlo (low bias, high variance) via \(\lambda\):

\[ A_t^{GAE} = \delta_t + (\gamma\lambda)\,A_{t+1}^{GAE}, \qquad \delta_t = r_t + \gamma\,V(t+1) - V(t) \] 
nextvalues = 0
lastgaelam = 0
advantages = []

for t in reversed(range(R=512)):
    delta       = penalized_rewards[:, t] + gamma * nextvalues - values[:, t]  # (64,)
    lastgaelam  = delta + gamma * lam * lastgaelam * response_mask[:, t]       # (64,)
    nextvalues  = values[:, t] * response_mask[:, t]
    advantages.append(lastgaelam)

advantages = stack(reversed(advantages))   # (64, 512)
returns    = advantages + values           # (64, 512)
advantages = whiten(advantages, response_mask)   # zero mean, unit variance
response_mask zeros the recurrence at padding positions and after EOS so advantages don't leak across sequence boundaries. Typical: \(\gamma=1.0\), \(\lambda=0.95\).

Whitening

whiten standardises the advantages to zero mean and unit variance across all valid (non-masked) tokens in the batch:

valid = response_mask.bool()                            # (64, 512)
mean  = advantages[valid].mean()                        # scalar
var   = advantages[valid].var(unbiased=False)           # scalar
advantages = (advantages - mean) / (var + eps).sqrt()  # (64, 512)
advantages = advantages * valid                         # re-zero padding positions

Why it's needed — the clip threshold problem. The PPO surrogate clips the importance ratio at \(1 \pm \epsilon\) (\(\epsilon = 0.2\)). Whether a token's gradient is clipped depends on both the ratio and the advantage: the effective gradient is \(\min(\rho,\, \text{clip}) \times A_t\). If raw advantages are on the order of 10–50 (typical cumulative reward scales), then even a ratio of 1.0 produces a large update, and the clip threshold of 1.2 barely constrains it. Whitening brings advantages to unit scale so that \(\epsilon = 0.2\) is calibrated to a meaningful signal range — the clip then consistently limits updates regardless of the reward magnitude in this particular batch.

Why returns is not whitened. returns is the regression target for the critic (\(\mathcal{L}_v = (V_\theta - \text{returns})^2\)). Whitening the returns would rescale the target, corrupting the value predictions used to compute future advantages — the circular dependency between critic and advantage would break. The actor loss is scale-invariant (the clipped ratio removes magnitude from the gradient direction); the critic loss is not.

Why the mask matters. Padding tokens have \(A_t = 0\) by construction. Including them in the mean/variance estimate would deflate the variance and distort the normalisation. The mask restricts statistics to tokens that actually carry signal.

9. Async PPO

The walkthrough above describes synchronous PPO: each phase blocks until the previous one completes, so the GPUs alternate between being idle during rollout (training workers wait) and idle during training (generation workers wait). Async PPO breaks this barrier by running generation and training concurrently.

9.1 Motivation: GPU Utilization in Sync vs Async

In sync mode a single training step looks like:

[──────── Rollout (~80% of wall clock, sequential token-by-token) ────────][Reward][LogP][Ref][GAE][Train][WeightSync]
 Training workers: IDLE ▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲▲
 Rollout workers:                                                                           IDLE ▲▲▲▲▲▲▲▲▲▲▲

Rollout dominates because autoregressive generation is serial (one token per step), while a training forward+backward is massively parallelized. Typical split: generation takes ~80% of wall-clock time per iteration.

Async PPO overlaps the two:

Gen workers:   [─── gen batch 1 ───][─── gen batch 2 ───][─── gen batch 3 ───] ...
Train workers:          [─ train batch 1 ─][─ train batch 2 ─][─ train batch 3 ─] ...
                        ↑                  ↑                  ↑
                  weight sync         weight sync         weight sync   (every K train steps)

Generation workers push completed sequences to a shared buffer; training workers pull from it as soon as enough data is available. Neither side idles waiting for the other.

Generation workers run an AsyncLLMEngine (vLLM or SGLang) with continuous batching. They accept new prompts and stream out completed sequences without waiting for a global batch barrier. They use a potentially stale copy of the actor weights.

Training workers run the same FSDP actor+critic setup as in the sync walkthrough (Phases 4–10). They pull a mini-batch from the buffer once buffer_size ≥ M and broadcast updated weights back to generation workers every K training steps.

Data buffer is a bounded queue. If it fills, generation workers backpressure until training catches up; if it empties, training workers block until new sequences arrive.

9.3 The Staleness Problem

Because training workers update the policy independently of generation, sequences in the buffer were generated by a policy that is up to K training steps old. In sync PPO, the behavior policy (πold) and the current training policy (πnew) differ only within a single mini-batch. In async PPO they can be K updates apart, widening the importance ratio π_new / π_old beyond the range PPO was designed for.

Importance sampling correction. Each sequence in the buffer carries log_prob_behavior — the log prob recorded at generation time under the weights that produced it. The PPO surrogate uses this instead of a separately stored old_log_probs:

# log_prob_behavior stored in buffer at generation time
# log_prob_new   computed fresh in the training forward pass

rho = exp(log_prob_new - log_prob_behavior)   # (M, R)  importance weight

surr1 = rho * advantages
surr2 = clamp(rho, 1-eps, 1+eps) * advantages
actor_loss = -mean(min(surr1, surr2) * response_mask)

The formula is identical to sync PPO; the difference is that rho can be meaningfully far from 1 when K is large.

Staleness bound. verl exposes a max_policy_lag hyperparameter. If generation workers' weights are more than max_policy_lag training steps behind, generation pauses until the next weight broadcast catches up.

max_policy_lag = K   # typical: 1–4 training steps

With K=1, data is at most 1 step stale — nearly on-policy. With K=4, the IS ratio distribution widens and the clipped surrogate is under more stress.

9.4 Weight Synchronization Cadence

In sync PPO, weight sync happens once per step (Phase 10): ~3.5 GB AllGather per training iteration. In async PPO the sync is decoupled:

Every K training steps:
  1. Training workers: FSDP AllGather → full TP-sharded weights
     NCCL — AllGather across DP group:
       input per GPU:   ~875 MB FSDP shard (bfloat16)
       output per GPU:  ~3.5 GB full TP=2 copy (bfloat16)

  2. Ray broadcasts weights to generation workers via object store:
       payload: ~3.5 GB (once per K steps)

  3. Generation workers load new weights into AsyncLLMEngine
       (brief pause to swap parameters; in-flight sequences may be drained first)

Amortized per training step: 3.5 GB / K. With K=4 that is ~875 MB/step vs 3.5 GB/step in sync mode — a 4× reduction in weight-sync bandwidth.

9.5 Phase Correspondence

The per-sequence computation is the same as the sync walkthrough. The structural difference is when and on what each phase runs.

Sync phaseAsync equivalent
Phase 1 — Data loadingController streams prompts to gen workers continuously
Phase 2 — RolloutGen workers, running concurrently with training
Phase 3 — RewardApplied before sequences enter the buffer
Phase 4 — Old log-probsRecorded at generation time; stored in buffer as log_prob_behavior
Phase 5 — Ref log-probsRef workers run concurrently with generation (or collocated)
Phase 6 — Value estimationCritic forward on training workers when batch is pulled
Phase 7 — GAEController CPU, same as sync
Phase 8 — Actor updateTraining workers, same FSDP/TP mechanics as sync
Phase 9 — Critic updateTraining workers, same as sync
Phase 10 — Weight syncEvery K steps instead of every step

For tasks where rollout dominates (long responses, large models), async PPO with K=2–4 is the standard choice. For tasks where training dominates (many PPO epochs, large critic, short responses), sync PPO may match throughput with better sample efficiency.
