Resource Pool Placement in VeRL

GPU allocation strategies for actor, rollout, and critic — how the hybrid engine works, how to budget memory across phases, and how to size each pool for throughput.

Prerequisite: PPO Training Walkthrough in VeRL (worker roles, FSDP + vLLM layout) and Async RL (policy lag, weight sync, IS correction). This page focuses on the GPU allocation decisions that determine throughput and memory headroom.

1. VeRL's Worker Model

VeRL represents each logical role in RL training as a worker class, scheduled onto GPU resources via Ray. Four worker types participate in a standard PPO/GRPO run:

Worker Responsibility Memory profile
ActorRollout Policy training (FSDP) and token generation (vLLM) — the hybrid engine hosts both. Largest; holds two copies of weights at transition boundary.
Reference Frozen reference policy used for KL penalty. Weights never change. Usually colocated with ActorRollout; shares weights at startup.
Critic Value function for advantage estimation (PPO only; absent in GRPO). Typically a smaller model; can share or separate pool from actor.
RewardModel Scores completed rollouts. May be a neural RM or a rule-based function. Light if rule-based; full model footprint if neural.

A resource pool is a named set of GPUs. Each worker class is assigned to exactly one pool. Workers in the same pool share GPU memory and are co-scheduled by Ray. Workers in different pools have independent memory spaces and can run concurrently.

The assignment is specified as a Python mapping dict passed to the ResourcePoolManager:

# pool_name → list of GPUs per node
resource_pool_spec = {
    'actor_rollout_ref': ResourcePool(process_on_nodes=[8]),  # 8 GPUs, 1 node
    'critic':            ResourcePool(process_on_nodes=[4]),  # 4 GPUs, 1 node
}
mapping = {
    ActorRolloutRefWorker: 'actor_rollout_ref',
    CriticWorker:          'critic',
}

How you draw these pool boundaries is the central placement decision.

2. The Hybrid Engine — One GPU Set, Two Roles

VeRL's key innovation is the HybridEngine: the actor and rollout workers occupy the same GPUs and alternate between two modes within a single step.

Phase transitions within one RL step

Phase A — Rollout (generation)
  1. AllGather: FSDP param shards are gathered into a full model copy on each GPU.
  2. Weight load: vLLM initializes (or reuses) its engine with the gathered weights.
  3. Free FSDP copy: the AllGathered buffer is freed; vLLM now owns the weights.
  4. vLLM runs autoregressive generation; trajectories land in the sample buffer.
Phase B — Training
  1. vLLM teardown: KV cache and activation buffers released; vLLM engine suspended.
  2. Restore FSDP shards: each GPU returns to holding 1/N of the full param tensor.
  3. FSDP forward + backward + optimizer step.
  4. Reference model forward (frozen; same GPU set; weights kept separately in memory).

The critical observation: steps A1–A2 create a brief window where two full copies of the weights coexist — the FSDP AllGathered buffer and the nascent vLLM engine. This is the GPU memory peak for the colocated configuration.

vLLM tensor parallelism within the pool

vLLM uses tensor parallelism (TP) for generation. If your pool has N GPUs and vLLM TP degree is t, you get N/t independent vLLM instances running in parallel — each handling a separate subset of the rollout batch.

vLLM instances per pool
\[ \text{n\_instances} = \frac{N_{\text{pool}}}{t_{\text{TP}}} \]

\(t_{\text{TP}}\) must evenly divide \(N_{\text{pool}}\). Each instance generates concurrently; total rollout throughput scales linearly with n_instances.

Choosing a smaller TP degree packs more instances (higher rollout throughput) at the cost of more memory per GPU (each instance holds a larger weight shard). The sweet spot depends on model size and GPU VRAM.

3. Placement Strategies

The right pool layout depends on your algorithm first, then on two orthogonal dimensions: whether the rollout runs synchronously on the actor's GPUs or asynchronously on a dedicated pool, and — for PPO only — where the critic lives.

GRPO — no critic

GRPO removes the critic and derives advantages from the rollout batch itself. There is exactly one placement decision: does the rollout share GPUs with the actor, or get its own pool?

Colocated (default)

Actor, rollout, and reference policy share one pool. The hybrid engine alternates between FSDP training mode and vLLM generation mode on the same GPUs. Keep gpu_memory_utilization low enough that FSDP can resume after vLLM releases.

resource_pool_spec = {
    'actor_rollout_ref': ResourcePool(process_on_nodes=[8]),
}
mapping = {
    ActorRolloutRefWorker: 'actor_rollout_ref',
}

Disaggregated sync

Rollout workers move to a dedicated GPU pool, but the step loop stays synchronous: training waits for rollout to finish before starting, and rollout waits for the updated weights before generating again. The two pools take turns.

This is useful when the colocated memory constraint is the bottleneck — the rollout pool can run vLLM at near-maximum gpu_memory_utilization (no FSDP ever runs there), while training retains full GPU memory for FSDP. Policy lag is zero; no IS correction needed.

resource_pool_spec = {
    'actor_ref': ResourcePool(process_on_nodes=[8]),   # training
    'rollout':   ResourcePool(process_on_nodes=[8]),   # generation (dedicated)
}
# fully_async=False (default) — synchronous even with separate pools
# Weight sync happens at step boundary; rollout idles during training and vice versa
The price of disaggregated sync is GPU idle time: the rollout pool sits idle during every training phase, and the training pool sits idle during every rollout phase. Total GPU-hours consumed is 2× what colocated uses for the same work. Disaggregated async recovers this by overlapping the two — see below.

Disaggregated async

Rollout workers move to a dedicated GPU pool and run continuously; the trainer never idles waiting for generation. Generation scales by adding rollout replicas without touching the training cluster. The rollout pool can use near-maximum gpu_memory_utilization because FSDP never runs there.

resource_pool_spec = {
    'actor_ref': ResourcePool(process_on_nodes=[8]),   # training
    'rollout':   ResourcePool(process_on_nodes=[8]),   # generation (dedicated)
}
# fully_async=True in the trainer config
Weight sync (async only): VeRL pushes updated weights from the actor pool to the rollout pool via NCCL AllGather every trigger_parameter_sync_step training steps. For a 7B BF16 model: ~5–15 s over NVLink, 3–5× slower over InfiniBand. This introduces policy lag — pair with IS correction. See VeRL async knobs.

PPO — two independent dimensions

PPO adds a critic, introducing a second placement choice that is orthogonal to the sync/async decision. Reason through them separately.

Dimension 1 — Critic placement

In synchronous PPO the critic computes value estimates after every rollout. You decide whether it shares the actor's pool or runs on its own GPUs:

Fully colocated

Actor + rollout + ref + critic on one pool.

  • Minimum GPU count
  • Critic and actor forward passes serialize
  • Lowest gpu_memory_utilization needed
  • Best for: small clusters, critic is a lightweight value head

Split critic pool

Critic on a dedicated pool; actor+rollout+ref on another.

  • Critic forward can overlap actor update step
  • Critic pool sized independently (often a smaller model)
  • Higher gpu_memory_utilization on actor pool
  • Best for: 30B–70B; critic is a separate full model
# Fully colocated PPO
resource_pool_spec = {
    'shared': ResourcePool(process_on_nodes=[8]),
}
mapping = {
    ActorRolloutRefWorker: 'shared',
    CriticWorker:          'shared',
}

# Split critic pool PPO
resource_pool_spec = {
    'actor_rollout_ref': ResourcePool(process_on_nodes=[8]),
    'critic':            ResourcePool(process_on_nodes=[4]),
}
mapping = {
    ActorRolloutRefWorker: 'actor_rollout_ref',
    CriticWorker:          'critic',
}

Dimension 2 — Sync vs async rollout

Independently of critic placement, you can move the rollout worker to its own pool. This is the same async pattern as GRPO above — the critic pool is a third independent pool:

# Disaggregated async PPO (with split critic)
resource_pool_spec = {
    'actor_ref': ResourcePool(process_on_nodes=[8]),   # training
    'rollout':   ResourcePool(process_on_nodes=[8]),   # generation (dedicated)
    'critic':    ResourcePool(process_on_nodes=[4]),   # value function
}
# fully_async=True; critic still advances synchronously with the actor update
Even in async mode, the critic runs synchronously with the actor update — only the rollout is decoupled. Critic pool GPUs are idle during generation but active during training, so the split-critic overlap benefit is preserved.

Effective cluster utilization

gpu_memory_utilization is a vLLM KV-cache knob — it says nothing about whether SMs are doing useful work. Autoregressive generation is memory-bandwidth-bound (SM utilization 20–45%); FSDP training is compute-bound (50–80%). In synchronous runs the two phases alternate and are separated by a transition penalty (FSDP AllGather + vLLM init/teardown, typically 5–30 s per step). In async runs they fully overlap.

Effective cluster utilization over one RL step:

\[ U_{\text{eff}} = \frac{U_{\text{rollout}} \cdot T_{\text{rollout}} \;+\; U_{\text{train}} \cdot T_{\text{train}}} {T_{\text{rollout}} + T_{\text{train}} + T_{\text{transition}}} \]

With \(T_{\text{rollout}} = 60\text{ s}\), \(T_{\text{train}} = 20\text{ s}\), \(T_{\text{transition}} = 10\text{ s}\): \(U_{\text{eff}} \approx 0.42\) — less than half of GPU-seconds on useful compute.

Config Applies to Rollout phase Training phase Typical \(U_{\text{eff}}\)
Colocated, sync GRPO / PPO All GPUs generate (mem-BW bound) All GPUs train (compute bound) 35–50%
Disaggregated, sync GRPO / PPO Rollout pool generates; training pool idle Training pool trains; rollout pool idle 20–35% (pools take turns — low utilization, but full memory for each)
Split critic, sync PPO only Actor pool generates; critic pool idle Actor + critic pools run concurrently 45–60%
Disaggregated async GRPO / PPO Rollout pool generates continuously Training pool trains continuously; fully overlap 65–80%

If rollout dominates step time, disaggregated async is the single highest-leverage utilization improvement. Splitting the critic is a cheaper incremental gain when the critic is large enough to meaningfully serialize with actor training.

4. Memory Budget Per GPU

GPU memory must cover all live tensors in the most demanding phase. For colocated setups the constraint is the A1–A2 transition (FSDP AllGather + vLLM init). For disaggregated rollout pools the constraint is during generation (vLLM only, so less pressure).

Notation

  • \(P\) — number of model parameters
  • \(b\) — bytes per parameter in working precision (2 for BF16/FP16)
  • \(N\) — GPUs in the pool
  • \(t\) — vLLM TP degree
  • \(u\) — gpu_memory_utilization (fraction reserved for KV cache)
  • \(V\) — total GPU VRAM (e.g., 80 GB for A100-80G)

Colocated pool — peak (transition phase)

Peak GPU memory — colocated, transition
\[ M_{\text{peak}} = \underbrace{\frac{P \cdot b}{N}}_{\text{FSDP shard}} + \underbrace{P \cdot b}_{\text{AllGathered full copy}} + \underbrace{\text{optim}}_{\text{Adam states}} \]

The AllGathered full copy (\(P \cdot b\)) is the dominant term and is not divided by \(N\). Every GPU holds a complete copy during the FSDP→vLLM handoff.

Adam optimizer states in FP32 add \(3 \cdot P \cdot 4 / N\) bytes per GPU (momentum, variance, FP32 param copy), but these are zeroed during the rollout phase (FSDP is suspended), so they don't overlap with the AllGathered copy in practice if VeRL offloads them to CPU during rollout.

Colocated pool — training phase

\[ M_{\text{train}} = \frac{P \cdot b}{N} \;(\text{params}) + \frac{P \cdot b}{N} \;(\text{grads}) + \frac{3 P \cdot 4}{N} \;(\text{Adam FP32}) + M_{\text{act}} \]

where \(M_{\text{act}}\) is activation memory (sequence-length and batch-size dependent).

vLLM KV cache available after model weights

After vLLM loads weights into each TP shard, the remaining GPU memory is handed to the KV cache pool:

\[ M_{\text{KV}} = \left(V - \frac{P \cdot b}{t}\right) \cdot u \]

Setting gpu_memory_utilization too high in a colocated pool causes OOM when FSDP resumes after rollout because the KV cache hasn't fully released yet. Typical safe values:

PlacementRecommended gpu_memory_utilizationRationale
Fully colocated 0.40 – 0.55 Must leave ~40% for FSDP params + grads + optimizer + activations during training phase.
Split critic pool (actor+rollout on one pool, critic on another) 0.55 – 0.70 Slightly more headroom since critic optimizer states are on a separate pool.
Disaggregated async (dedicated rollout pool) 0.85 – 0.92 No FSDP ever runs on this pool; near-maximum KV cache is safe.

Worked example — 7B model, 8× A100-80G, colocated

Parameters: \(P = 7 \times 10^9\), BF16 (\(b = 2\)), 8 GPUs, vLLM TP \(t = 4\), \(V = 80\) GB.

  • FSDP shard per GPU: \(7\text{B} \times 2 / 8 = 1.75\) GB
  • AllGathered full copy (peak, every GPU): \(7\text{B} \times 2 = 14\) GB
  • vLLM weight shard (TP=4): \(14 / 4 = 3.5\) GB
  • Adam FP32 states (ZeRO-3): \(7\text{B} \times 12 / 8 \approx 10.5\) GB (FP32 param + m + v)
  • KV cache with \(u = 0.50\): \((80 - 3.5) \times 0.5 \approx 38\) GB

Peak at transition: 14 GB (AllGather) + headroom for vLLM init ≈ 20 GB committed before KV cache allocation. With 80 GB per GPU this is comfortably feasible. The binding constraint is training phase: 1.75 + 1.75 + 10.5 + activations, with 38 GB KV cache pre-allocated but idle — vLLM must release cleanly before FSDP needs the memory.

5. Throughput Balancing

In synchronous RL, generation and training execute sequentially: the GPU cluster alternates between rollout phase and training phase. Total step time is:

\[ T_{\text{step}} = T_{\text{rollout}} + T_{\text{train}} \]

GPU utilization suffers when one phase dominates. LLM RL with long responses (1K–8K tokens) typically makes rollout the bottleneck: generation is autoregressive and memory-bandwidth-bound, while training runs a single large batched forward+backward.

Estimating the rollout-to-train ratio

Let \(B\) be the global batch size (sequences per step), \(L\) the mean response length, and \(G\) the number of rollouts per prompt (the GRPO group size).

Rough throughput balance
\[ \frac{T_{\text{rollout}}}{T_{\text{train}}} \approx \frac{G \cdot L \cdot N_{\text{pool}}}{t_{\text{TP}} \cdot \text{tok/s}_{\text{vllm}}} \cdot \frac{\text{tok/s}_{\text{fsdp}}}{B \cdot L} \]

When this ratio > 1 the rollout is the bottleneck. Use a larger vLLM batch, smaller TP, more rollout GPUs (disaggregated), or shorter rollouts.

Levers to reduce rollout time

LeverEffectTrade-off
Decrease tensor_model_parallel_size More vLLM instances per pool → higher parallel throughput More memory per GPU for KV cache needed; must not OOM
Increase max_num_seqs Larger decode batch → better GPU utilization Longer prefill latency; more KV memory required
Enable enable_chunked_prefill Interleaves prefill and decode; reduces time-to-first-token Slightly higher memory overhead; minimal downside for RL rollouts
Add dedicated rollout GPUs (disaggregated async) Rollout and training fully overlap; near-zero rollout wait More GPUs; policy lag; requires IS correction
Reduce response length cap Shorter rollouts; better throughput balance May hurt task performance on long-horizon reasoning

Levers to reduce training time

Training time matters less when rollout dominates, but for long-context training (32K+ tokens) with large batches, training can become the bottleneck instead:

  • Gradient checkpointing — trades compute for activation memory; allows larger batch sizes
  • Sequence packing — pack multiple short trajectories into one training sequence to reduce padding waste
  • Reduce critic size — a smaller value head or a shallower critic model speeds up the critic forward pass

6. Config Walkthrough

Setup A — 7B model, 8× A100-80G, synchronous, fully colocated

The simplest configuration. All workers share 8 GPUs. TP=4 gives 2 vLLM instances for parallel generation. Critic colocates with actor (no separate pool needed for GRPO since there is no critic, or for small PPO critic models).

# trainer section of VeRL YAML
trainer:
  n_gpus_per_node: 8
  nnodes: 1

# resource pool: default colocated (all workers share the 8 GPUs)
# no explicit resource_pool_spec needed — VeRL defaults to fully colocated

actor_rollout_ref:
  model:
    path: meta-llama/Llama-2-7b-hf
  actor:
    strategy: fsdp
    ppo_micro_batch_size: 4
    optim:
      lr: 1e-6
  rollout:
    name: vllm
    tensor_model_parallel_size: 4    # 8 GPUs / 4 = 2 vLLM instances
    gpu_memory_utilization: 0.50     # 50% KV cache; 50% left for FSDP
    max_num_seqs: 64
    enable_chunked_prefill: true
  ref:
    fsdp_config:
      param_offload: false           # keep ref weights on GPU (14 GB shared with actor)

Setup B — 70B model, 32× A100-80G, split pools

A 70B BF16 model requires 140 GB just for weights — 2 GPUs minimum for vLLM TP=2. With 32 GPUs available, assign 24 to actor_rollout_ref and 8 to critic (which can be a smaller model or a pruned value head).

trainer:
  n_gpus_per_node: 8
  nnodes: 4                          # 32 GPUs total

# Explicit pool split
resource_pool_spec:
  actor_rollout_ref:                 # 24 GPUs (3 nodes)
    process_on_nodes: [8, 8, 8]
  critic:                            # 8 GPUs (1 node)
    process_on_nodes: [8]

actor_rollout_ref:
  rollout:
    tensor_model_parallel_size: 8   # 24 / 8 = 3 vLLM instances for 70B
    gpu_memory_utilization: 0.65    # more room vs colocated critic
  actor:
    strategy: fsdp
    fsdp_config:
      param_offload: false
      grad_offload: false

critic:
  strategy: fsdp
  model:
    path: meta-llama/Llama-2-7b-hf  # critic can be a smaller model than actor

Setup C — 7B model, disaggregated async, 8 training + 8 rollout GPUs

Training and generation run concurrently. The rollout pool dedicates full VRAM to vLLM KV cache (gpu_memory_utilization: 0.90). Weight sync triggers every 10 training steps, keeping policy lag small.

trainer:
  n_gpus_per_node: 8
  nnodes: 2                          # 16 GPUs total: 8 training + 8 rollout

resource_pool_spec:
  actor_ref:                         # 8 GPUs — training only
    process_on_nodes: [8]
  rollout:                           # 8 GPUs — generation only
    process_on_nodes: [8]

actor_rollout_ref:
  rollout:
    tensor_model_parallel_size: 4   # 8 rollout GPUs / 4 = 2 vLLM instances
    gpu_memory_utilization: 0.90    # dedicated pool → near-max KV cache
  actor:
    strategy: fsdp

async_config:
  fully_async: true
  trigger_parameter_sync_step: 10   # push weights every 10 train steps
  staleness_threshold: 20           # discard samples older than 20 steps
  rollout_is: sequence              # sequence-level IS for lag correction
NVLink vs InfiniBand: weight sync in disaggregated mode sends \(P \times b\) bytes across the interconnect. For a 7B BF16 model that is 14 GB. Over NVLink (600 GB/s) this takes ~25 ms; over InfiniBand HDR (25 GB/s) ~560 ms. If training steps take <1 s, IB sync every 10 steps adds <6% overhead. Over Ethernet (<5 GB/s) sync becomes the bottleneck — raise trigger_parameter_sync_step or colocate instead.

7. Decision Guide

Scenario Recommended placement Key config knob
Tight GPU budget; 7B–13B model; <1K response tokens Fully colocated gpu_memory_utilization: 0.45–0.55
30B–70B model; critic is a separate model PPO split critic pool gpu_memory_utilization: 0.60–0.70 on actor pool
Long responses (2K–8K tokens); rollout is the bottleneck Disaggregated async fully_async: true; trigger_parameter_sync_step: 5–20
MoE model (expert parallelism) Split critic pool (PPO) or colocated (GRPO); actor pool must match rollout TP degree for TIM control Set equal tensor_model_parallel_size in both engines
Maximizing rollout throughput on fixed hardware Colocated; reduce TP to pack more vLLM instances tensor_model_parallel_size: 1 or 2; monitor for OOM
Multi-node; cross-node NVLink not available Avoid disaggregated if weight sync crosses IB; prefer colocated per-node Keep nnodes per pool to minimize cross-node weight sync

Quick diagnostic: is rollout or training the bottleneck?

Add a timing log around each phase. In VeRL, enable trainer.logger: ['console'] and watch for timing/rollout_time vs timing/training_time in the step log. A ratio rollout_time / training_time > 2 signals you should either disaggregate or reduce vLLM TP to pack more instances.

# Check in logged metrics
timing/rollout_time     # seconds spent in vLLM generation this step
timing/training_time    # seconds spent in FSDP forward+backward+optim
timing/weight_sync_time # seconds for NCCL AllGather (disaggregated only)
