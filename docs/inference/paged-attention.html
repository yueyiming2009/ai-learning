PagedAttention — Virtual Memory for KV Cache

Static KV cache allocation wastes most of GPU memory: each slot reserves space for the maximum possible sequence length, leaving the unused tail as internal fragmentation. PagedAttention maps KV blocks to physical GPU memory non-contiguously — like OS virtual memory pages — eliminating fragmentation and enabling prefix sharing without copying.

The KV cache stores key and value tensors for every past token. Without careful memory management, serving many concurrent requests leads to massive waste: either you over-allocate and fragment, or you under-allocate and reject requests that would fit if the memory were packed. PagedAttention, introduced with vLLM, solves this with the same mechanism operating systems have used for decades: virtual memory paging.

1 · The fragmentation problem

In a naive serving system, each request's KV cache is pre-allocated as a contiguous memory region sized for the maximum output length \(T_{\max}\). This causes two types of waste:

Internal fragmentation — wasted space inside each allocation

A request that generates 50 tokens still holds a \(T_{\max} = 2048\) token buffer. The unused 1998 slots (\(97.5\%\)) are wasted for the duration of the request. In practice, output length distributions are heavy-tailed — the average request uses a small fraction of its reserved buffer.

External fragmentation — wasted space between allocations

As requests of different lengths come and go, they leave gaps between allocations in GPU memory. A new request might have enough total free memory but not enough contiguous memory to fit its buffer. The allocator rejects the request even though the space technically exists.

2 · The OS virtual memory analogy

Operating systems solved an identical problem for CPU processes in the 1960s. The parallel is exact:

OS Virtual MemoryPagedAttention
Process virtual address spaceA request's logical KV sequence (token positions 0…T)

The key property of paging: a sequence's KV tokens no longer need to be stored contiguously in physical memory. The block table indirection layer lets the serving system scatter blocks anywhere in free GPU memory and reassemble them at attention computation time.

3 · Block manager mechanics

The block manager maintains a pool of fixed-size KV blocks and a free list. All physical blocks have the same size — block_size tokens, e.g., 16. This eliminates external fragmentation entirely: any free block fits any request.

Lifecycle of a request's KV memory
  1. Prefill admission: allocate \(\lceil T_p / B \rceil\) physical blocks for the prompt's KV, where \(B\) = block size. Store the mapping in a per-request block table: logical block \(i\) → physical block \(p_i\).
  2. Each decode step: append new K, V to the current last block. When the last block fills (every \(B\) steps), allocate one new physical block and extend the block table.
  3. Request completion: release all physical blocks back to the free list. Freed blocks are immediately available to new requests — no defragmentation needed.

Because allocation is incremental, a request only uses as much memory as it actually needs — no over-allocation. Internal fragmentation is at most one partial block per request (the last block), giving at most \(B - 1\) tokens of waste per request — negligible for \(B = 16\). 

class BlockManager:
    """Maps a request's logical KV positions to physical GPU memory blocks."""
    def __init__(self, total_blocks, block_size=16):
        self.block_size = block_size
        self.free       = list(range(total_blocks))  # free block indices
        self.tables     = {}   # req_id -> [phys_block_idx, ...]
        self.ref_counts = [0] * total_blocks
        self.seq_lens   = {}

    def allocate(self, req_id, prompt_len):
        n = (prompt_len + self.block_size - 1) // self.block_size
        blocks = [self.free.pop() for _ in range(n)]
        self.tables[req_id], self.seq_lens[req_id] = blocks, prompt_len
        for b in blocks: self.ref_counts[b] = 1

    def append_token(self, req_id):
        self.seq_lens[req_id] += 1
        if self.seq_lens[req_id] % self.block_size == 1:  # current block just filled
            b = self.free.pop()
            self.ref_counts[b] = 1
            self.tables[req_id].append(b)

    def free_request(self, req_id):
        for b in self.tables.pop(req_id):
            self.ref_counts[b] -= 1
            if self.ref_counts[b] == 0:
                self.free.append(b)   # immediately available to another request
        del self.seq_lens[req_id]

    def physical_block(self, req_id, logical_idx):
        return self.tables[req_id][logical_idx]
Maximum waste per request
\[ \text{wasted tokens per request} \leq B - 1 \qquad (B = \text{block size}) \]
For B = 16: at most 15 tokens of KV memory wasted per request, regardless of generation length.

Block size selection

Smaller blocks reduce fragmentation but increase block table overhead and attention kernel complexity (more pointer indirections). Larger blocks improve throughput but waste more at sequence ends. vLLM defaults to 16 tokens per block, which empirically balances these tradeoffs well. The block size must also be a multiple of the GPU's warp size to ensure coalesced memory access in the attention kernel.

4 · Copy-on-write for prefix sharing

Multiple requests that share the same prompt prefix (e.g., a system prompt) can share the physical KV blocks for that prefix rather than duplicating them. The block manager tracks a reference count for each physical block.

Shared prefix — no copy needed while read-only

When Request B arrives with the same 512-token system prompt as Request A (already in memory), the block manager points B's block table entries for positions 0–511 to the same physical blocks as A. Reference counts on those blocks rise to 2. Both requests read from the same blocks during attention — no memory copy required.

Copy-on-write — triggered when a shared block must be written

When a decode step appends a new token to a block with reference count > 1, that block is about to diverge between the two sequences. The block manager copies it to a new physical block, decrements the original's reference count, and updates the writing request's block table to point to the copy. The original block remains intact for the other request(s) still pointing to it.

This implements the KV prefix cache described in the KV Cache page at the memory management level: shared prefixes require zero additional memory until divergence, and then only the diverging block is copied.

6 · Integration with continuous batching

PagedAttention and continuous batching are deeply intertwined: each depends on the other to work well at scale.

Why they need each other
  • Continuous batching needs PagedAttention for safe preemption. When the KV cache fills during continuous batching, the scheduler must evict (preempt) some requests. With static allocation, evicting means freeing a large contiguous buffer and restarting from scratch. With paging, the scheduler can evict individual blocks — or swap specific blocks to CPU — without disrupting the entire request.
  • PagedAttention needs continuous batching to stay near its utilization ceiling. Without iteration-level scheduling, slots sit idle after short sequences finish. With continuous batching, freed blocks are immediately reused by newly admitted requests, keeping the block pool active.

Preemption strategies

When the block pool is nearly exhausted and a new high-priority request must be admitted, the scheduler can:

  • Swap to CPU: copy physical GPU blocks to CPU RAM, free the GPU blocks. Expensive (PCIe bandwidth ~64 GB/s, much slower than HBM), but the request can resume without re-running prefill.
  • Recomputation: discard the KV blocks and recompute from the stored prompt tokens when the request is readmitted. Cheaper in bandwidth but costs the prefill computation again. Preferred for short prompts.
  • Block donation: for low-priority requests, release their most recent blocks (newest output) and restart generation from an earlier checkpoint.

7 · Summary

The problem

Static KV pre-allocation wastes 60–80% of GPU memory via internal and external fragmentation. Limits batch size; limits throughput.

The solution

Fixed-size KV blocks (e.g., 16 tokens) mapped via per-request block tables. Scatter KV tokens anywhere in GPU memory; reassemble at attention time.

Fragmentation

External fragmentation: eliminated (all blocks same size, any free block fits any request). Internal: at most B−1 tokens per request.

Copy-on-write

Shared prefix blocks are reference-counted. Copy triggered only at the first write that diverges two sequences — zero overhead for read-only sharing.

Utilization

GPU memory utilization: 20–40% (static) → >90% (paged). 2–5× more concurrent requests; 2–4× throughput on variable-length workloads.

Ecosystem

PagedAttention is the memory backend in vLLM, SGLang, TGI, and TensorRT-LLM. It is the enabling infrastructure for continuous batching at scale.
