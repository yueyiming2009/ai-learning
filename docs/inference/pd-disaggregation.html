Prefill–Decode Disaggregation

Prefill is compute-bound; decode is memory-bandwidth-bound. Running them on the same GPU means one phase is always wasteful for that hardware. Disaggregation routes each phase to the GPU pool optimized for it, eliminating the fundamental compromise.

In standard LLM serving, each request runs prefill and then decode on the same GPU replica. The compute model shows these phases have opposite bottlenecks: prefill processes many tokens in parallel (compute-bound, using Tensor Cores efficiently) while decode generates one token at a time (memory-bandwidth-bound, wasting most of the GPU's compute capacity). Serving both phases on the same hardware forces a compromise — and the chunked prefill page shows how even scheduling around this is tricky. Prefill–decode disaggregation separates the hardware entirely.

1 · The coexistence problem

When prefill and decode requests share GPU replicas, two conflicts arise:

Conflict 1 — TPOT spikes during prefill

A long prefill (e.g., 8K token prompt) takes tens of milliseconds. Every decode request co-located on the same GPU is paused for the full prefill duration. A typical 8K prefill at 10 ms blocks all ongoing decode steps, causing TPOT to spike by 10 ms for all concurrent users. Chunked prefill mitigates this by interleaving prefill with decode in small chunks, but it adds scheduling complexity and still consumes GPU memory bandwidth for the chunk.

Conflict 2 — Hardware under-utilization

During decode, the GPU's compute units are mostly idle — the bottleneck is HBM bandwidth. During prefill, the GPU's HBM bandwidth is mostly idle — the bottleneck is compute. The same GPU switches between two inefficient states depending on the phase mix of the current batch. You cannot simultaneously optimize MFU (model FLOP utilization) for prefill and bandwidth utilization for decode on the same hardware.

2 · Disaggregated architecture

Disaggregation routes each phase to a separate pool of GPU workers:

Prefill workers
Process full prompt (all T tokens at once)
Large MFU: Tensor Cores near saturation
Each worker handles one request at a time (large batch N is the single prompt)
Produces: 1st token + KV cache
Scale: match to input token rate
→
Decode workers
Autoregressively generate output tokens
Many requests batched together → bandwidth saturated
Continuous batching within the decode pool
Receives: KV cache from prefill worker
Scale: match to output token rate × latency SLO

Each pool can be independently scaled (prefill workers : decode workers ratio is a config knob) and optimized. Prefill workers can use FP8 attention and aggressive compute parallelism. Decode workers can use INT4 quantized weights for maximum bandwidth efficiency and larger KV caches.

Different hardware choices per pool
  • Prefill workers: H100 (or A100) with high Tensor Core throughput, reasonable HBM bandwidth. Can use smaller HBM if KV cache footprint per request is bounded (short context or prefix caching).
  • Decode workers: Benefit from very high HBM bandwidth relative to compute. A hypothetical "wide, slow" GPU (many HBM stacks, fewer SMs) would be ideal. In practice, HBM3e variants (H100 SXM5 vs. PCIe) give ~25% more bandwidth for decode, or use more replicas per request volume.

3 · KV cache transfer

After prefill, the KV cache must be sent from the prefill worker to the decode worker that will own the request. This transfer is the central engineering challenge of disaggregation.

Transfer size

From the KV cache page: \(\text{KV bytes} = 2 \times L \times h_\text{kv} \times d_h \times T \times \text{bytes/elem}\). For LLaMA-3 70B (BF16, no GQA) at 4K tokens: \(2 \times 80 \times 8 \times 128 \times 4096 \times 2 = 1.34\text{ GB}\). With INT8 KV quantization: 670 MB. This is the payload that must cross the network (or NVLink) per request on each prefill completion.

Transfer bandwidth requirements

If a prefill worker processes 100 requests/second with 1.34 GB KV each, the outgoing transfer rate is 134 GB/s — comparable to full InfiniBand bandwidth (HDR200 = 25 GB/s per link, so you need 6 links saturated). This is why disaggregation systems use RDMA (NVLink for intra-node, RoCE/InfiniBand for inter-node) and why co-locating prefill and decode workers on the same host (NVLink-connected) is preferred when scale allows it.

Practical mitigations for transfer overhead:

  • KV quantization: INT8 or FP8 KV halves the transfer size. This is doubly valuable in disaggregated setups — memory savings and bandwidth savings.
  • Prefix caching on decode worker: if the decode worker already has the KV cache for a shared prefix (e.g., a system prompt), only the incremental KV needs to be transferred.
  • Chunked KV streaming: begin sending KV blocks as prefill produces them (via chunked prefill) rather than waiting for full completion, overlapping network transfer with prefill compute.

4 · Request routing and scheduling

A global scheduler (sometimes called the "disaggregation proxy" or "router") receives incoming requests and orchestrates the prefill–decode handoff:

  1. Assign to prefill worker: pick the least-loaded prefill worker (or route based on prefix cache hits if the prefill worker caches prefix KV). The request's prompt is sent to this worker.
  2. Prefill completes: the first token is returned and KV cache is ready. The prefill worker signals the router.
  3. Assign to decode worker: the router picks a decode worker with sufficient free KV cache space. The KV transfer is initiated (RDMA write from prefill GPU memory to decode GPU memory).
  4. Decode proceeds: the decode worker receives the KV and joins the continuous batch. Subsequent tokens are streamed to the client.
The TTFT (time to first token) in a disaggregated system includes both the prefill compute time and the KV transfer time. For large prompts, the transfer can add 50–200 ms. This is acceptable if TPOT SLOs are the binding constraint, but disaggregation is not a free lunch for TTFT-sensitive workloads.

6 · When disaggregation is worth it

Disaggregation adds significant operational complexity. It is worth it when:

  • You have strict TPOT SLOs with mixed prompt lengths. Long prompt traffic causes TPOT jitter in aggregated systems that chunked prefill can only partially absorb. Disaggregation eliminates the interference.
  • You have enough scale for dedicated pools. At small scale (a few GPUs total), the overhead of running two separate fleets and the waste of under-utilized pools outweighs the benefits. At 20+ GPUs, the ratio flexibility pays for itself.
  • Prefill-to-decode ratio is stable enough to tune. If your traffic is bursty or the prompt/completion length ratio varies widely, the optimal pool ratio changes constantly. Aggregated serving with chunked prefill is simpler to tune in these cases.
  • High-bandwidth networking is available. InfiniBand HDR or NVLink between nodes is needed to keep KV transfer latency below 100 ms for multi-GB KV caches. On commodity 10 GbE, the transfer bottleneck makes disaggregation impractical.

Production deployments at scale (Mooncake, DistServe, disaggregated vLLM) consistently find 2–3× throughput improvement over aggregated serving at the same SLO level, driven primarily by better GPU utilization in each pool.

7 · Summary

Core insight

Prefill = compute-bound; decode = bandwidth-bound. One GPU cannot be optimal for both simultaneously.

Solution

Route prefill to compute-optimized pool, decode to bandwidth-optimized pool. Transfer KV cache between them via RDMA.

Key cost

KV transfer: 1–3 GB per request, adds 50–200 ms to TTFT. Requires InfiniBand or NVLink infrastructure.

Key gain

TPOT becomes stable (no prefill-induced spikes). Decode throughput improves 2–3× vs. aggregated at same SLO.

Synergies

KV quantization helps doubly: halves memory and halves transfer size. Prefix caching on decode workers reduces what needs to be transferred.

When to use

At scale (20+ GPUs), with strict TPOT SLOs, mixed prompt lengths, and high-speed interconnects.
