Prefill & Decode — Two Phases of LLM Inference

Every LLM inference request splits into two phases with fundamentally different hardware bottlenecks: a compute-bound prefill and a memory-bandwidth-bound decode. Every optimization in the inference stack — KV cache, continuous batching, speculative decoding — traces back to this split.

Training a transformer is a single-regime problem: large matrix multiplications with high arithmetic intensity, comfortably compute-bound on modern accelerators. Inference is not. Generating text requires two phases that are bottlenecked by completely different hardware resources, and understanding why is the prerequisite for every technique in this series.

1 · The two phases

Prefill — process the prompt in parallel

The model receives all \(T_p\) prompt tokens simultaneously. Every token attends to every prior token in the prompt. All linear projections run over the full sequence, producing query, key, and value tensors for the entire input in a single forward pass. The output: logits for the last token (the first generated token) and a populated KV cache for every prompt position.

Shape: weight matrices \(W \in \mathbb{R}^{D \times D}\) multiply an activation matrix \(X \in \mathbb{R}^{T_p \times D}\). This is a large matrix–matrix multiply — the shape that Tensor Cores are designed for.

Decode — generate one token at a time

After prefill, tokens are generated autoregressively. Each step takes the most recent token, computes its query projection, attends over all cached keys and values from previous positions, and produces the next token's logits. One token in, one token out, per step.

Shape: weight matrices \(W \in \mathbb{R}^{D \times D}\) multiply a single-token activation \(x \in \mathbb{R}^{1 \times D}\). This is a matrix–vector multiply — and matrix–vector multiplies are bandwidth-bound, not compute-bound.

The two phases do not just differ in shape — they differ in which hardware resource is the bottleneck. The roofline model makes this precise.

2 · Arithmetic intensity — where each phase sits on the roofline

Arithmetic intensity \(I\) is the ratio of floating-point operations to bytes transferred from memory: \(I = \text{FLOPs} / \text{bytes}\). A GPU's achievable throughput is bounded by the lower of two limits — memory bandwidth or peak compute (full hardware derivation: GPU Hardware § roofline):

Roofline bound
\[ \text{Achievable TFLOP/s} = \min\!\bigl(I \times \text{peak bandwidth},\ \text{peak FLOP/s}\bigr) \]
Left of the ridge (\(I < I^*\)): memory-bound. Right (\(I > I^*\)): compute-bound. Ridge point \(I^* = \text{peak FLOP/s} / \text{peak bandwidth}\).

For a single linear layer \(W \in \mathbb{R}^{D_{\rm in} \times D_{\rm out}}\), computing \(Y = XW\) for a batch of \(B\) tokens:

Arithmetic intensity of a linear layer at batch B
  • FLOPs: \(2 \cdot B \cdot D_{\rm in} \cdot D_{\rm out}\) — each of the \(B \cdot D_{\rm out}\) output elements requires a length-\(D_{\rm in}\) dot product (multiply + accumulate = 2 FLOPs each).
  • Weight bytes (FP16): \(2 \cdot D_{\rm in} \cdot D_{\rm out}\) — loaded once from HBM, reused across all \(B\) tokens in the batch.
  • Intensity: \(I = \dfrac{2B \cdot D_{\rm in} D_{\rm out}}{2 \cdot D_{\rm in} D_{\rm out}} = B\) FLOP/byte.
Key result
\[ I = B \;\; \text{FLOP/byte} \]
Independent of layer size. Each additional token in the batch raises intensity by exactly 1 FLOP/byte.

3 · The memory wall in decode

At batch size 1, every decode step loads essentially the entire model's weight parameters from HBM to compute a single output token. For a model with \(N\) non-embedding parameters stored in FP16, that is \(2N\) bytes per step. This sets a hard lower bound on time-per-output-token:

Minimum TPOT at batch = 1
\[ \text{TPOT}_{\min} = \frac{2N}{\text{peak HBM bandwidth}} \]

Plugging in concrete numbers for a single H100 SXM5 (3.35 TB/s HBM bandwidth):

These are theoretical floors assuming 100% HBM bandwidth utilization — actual single-stream TPOT is higher due to attention over the KV cache, non-weight memory reads, and kernel launch overhead. But two practical consequences follow directly:

  • Larger models are strictly slower per token in single-user decode, proportionally to parameter count.
  • Nothing in the software stack can escape this floor; only wider HBM bandwidth, reduced precision (fewer bytes per weight), or multi-GPU tensor parallelism can lower it.
The KV cache also contributes to memory bandwidth consumption during decode. Each step reads the cached K and V tensors for all prior tokens: \(2 \times T \times h_{\rm kv} \times d_h \times 2\) bytes (K and V in FP16). At long context this term grows with generation length and becomes non-trivial — which is precisely why KV cache quantization and GQA exist.

4 · Batch size and the crossover point

Serving multiple requests concurrently raises the effective batch size \(B\). From the intensity formula \(I = B\), each additional concurrent request adds 1 FLOP/byte of intensity. The weights are loaded once and shared across all \(B\) requests, so throughput scales linearly with \(B\) — until the linear layers hit the compute ceiling at \(B = I^*\), after which adding more requests no longer improves tokens/s.

Decode throughput as a function of batch size
\[ \text{tokens/s}(B) \;=\; \min\!\left(\frac{B \cdot \text{peak\_bw}}{2N},\;\frac{\text{peak\_flop/s}}{2N}\right) \]
Memory-bound (left term, linear in \(B\)) until \(B = I^*\), then compute-bound (right term, constant).

Regime: Memory-bandwidth-bound

Two practical implications follow directly:

  1. Batching is the primary lever for decode throughput. Every additional concurrent request improves GPU utilization proportionally until \(B = I^*\). This is why continuous batching (keeping \(B\) high at all times) is the single most important serving technique.
  2. Weight quantization helps only in the memory-bound regime. Halving weight precision (INT8) halves \(2N\) bytes → doubles memory-bound throughput. Above the ridge, the bottleneck shifts to compute and quantization no longer helps throughput (though it reduces memory footprint).
Caveat: the calculator above covers only linear layers. Attention does not follow the same batch-size scaling, and it is why measured GPU utilization stays low even at large batches.

Why attention's arithmetic intensity doesn't scale with \(B\). For a linear layer, batching \(B\) sequences shares the weight matrix across all \(B\) tokens — one load, \(B\) reuses, so intensity is \(I = B\). Attention is different: each sequence has its own KV cache, and computing attention for sequence \(i\) requires reading the entire KV history of sequence \(i\) from HBM. Adding more sequences adds more independent memory reads, not more reuse. The arithmetic intensity of the attention kernel is therefore bounded by the sequence length \(S\), not the batch size: \[ I_{\text{attn}} \;\approx\; \frac{2 \cdot S}{\text{bytes per KV entry}} \] This is a fixed number for a given sequence length — adding more sequences in the batch doesn't change it. Attention stays memory-bound at all practical batch sizes.

Consequence: the whole-step utilization ceiling. Decode alternates between linear layers (intensity scales with \(B\)) and attention (intensity fixed). Even when the linear layers reach the compute ridge at \(B = I^*\), the attention kernels remain memory-bound and continue to dominate total step time at long context. Empirically this shows up as:

  • No model exceeds ~35% average warp utilization during decode, even at maximum batch sizes (across OPT, Llama-2 families on A100/H100).
  • H100 decode SM utilization: ~30% at production batch sizes, vs. 92% during prefill.
  • Tensor cores >88% idle during decode across tested architectures — the HMMA pipeline sits empty while warps wait for KV cache reads.
  • At large batches, DRAM bandwidth saturates first; adding more sequences stalls on bandwidth before hitting the compute ceiling.

The practical implication: techniques that target the linear-layer bottleneck (weight quantization, larger batch) help decode throughput but cannot push SM or tensor-core utilization to prefill-like levels, because attention always pulls it back down. Techniques that reduce KV memory traffic — KV quantization, sliding-window attention, MLA — are the only lever that moves the attention bottleneck.

5 · TTFT and TPOT — what each workload optimizes for

Two numbers describe the latency of an inference request end to end:

The two latency metrics
  • TTFT (Time To First Token) — elapsed time from request arrival to the first output token. Dominated by: queuing delay + prefill computation. Prefill time grows with prompt length \(T_p\) and is roughly compute-limited for long prompts.
  • TPOT (Time Per Output Token) — time between successive tokens during decode. At low batch sizes, TPOT approaches the bandwidth floor derived above. At high batch sizes, TPOT rises as the batch competes for compute capacity. This is what users perceive as "streaming speed."

End-to-end latency for a request generating \(T_d\) output tokens:

End-to-end latency
\[ \text{latency} = \text{TTFT} + \text{TPOT} \times (T_d - 1) \]

The dominant term depends on output length:

  • Short completions (RAG, classification, short answers): TTFT dominates. A slow prefill is the entire user experience problem.
  • Long completions (code generation, reasoning chains, long-form writing): TPOT × \(T_d\) dominates. Users wait for the stream.
  • Offline batch inference: neither per-request metric matters directly — only aggregate tokens/s and cost.
  • RL rollout generation: total throughput across the batch matters; strict per-request TPOT SLOs do not.
TTFT and TPOT can conflict. Running a long prefill for a new request steals GPU cycles from ongoing decode steps, spiking TPOT for all in-flight requests. Chunked prefill — interleaving the new prompt in small pieces with ongoing decode — is the standard mitigation (see Batching for Inference).

6 · Summary

Two phases

Prefill processes all prompt tokens in parallel (matrix–matrix, compute-bound). Decode generates one token at a time (matrix–vector, memory-bandwidth-bound).

Arithmetic intensity

For a linear layer at batch \(B\): \(I = B\) FLOP/byte. Single-token decode sits at \(I = 1\), far left of the GPU roofline ridge.

Ridge point

H100: \(I^* \approx 295\) tokens. Below this, throughput scales linearly with batch size. Above it, the GPU is compute-saturated.

TPOT floor

Minimum decode latency = \(2N / \text{peak\_bw}\). ~4.2 ms for 7B on a single H100. Larger models are proportionally slower.

TTFT vs. TPOT

TTFT is driven by prefill compute and prompt length. TPOT is driven by HBM bandwidth and batch size. Short completions care about TTFT; long completions about TPOT.

The implication

Every inference optimization targets this split: KV cache (avoid recompute), batching (raise intensity), quantization (reduce bytes per weight), speculative decoding (reduce decode steps).
