MoE Serving — The Expert Coverage Law

A dense decode step reads every weight once, so batching \(B\) requests amortizes the read \(B\) ways. An MoE decode step reads only the experts somebody routed to — and at small batch, each new request pulls in a nearly disjoint set. This page derives \(C(B) = 1-(1-k/E)^B\), the fraction of experts touched, and follows it out to the roofline, to expert parallelism, and to why RL rollout generation on an MoE hurts.

The dense inference compute model rests on one fact: a weight matrix loaded from HBM is reused by every token in the batch. One load, \(B\) reuses, arithmetic intensity \(I = B\). That single identity is what makes continuous batching the dominant serving lever, and it is what makes decode throughput scale linearly until the compute ridge.

A Mixture-of-Experts model breaks it. Each token activates only \(k\) of \(E\) experts, so a weight matrix is not reused by every token in the batch — it is reused only by the tokens that happened to route to it. Whether batching still amortizes anything depends on how much the batch's routing decisions overlap. The coverage law is the answer to that question, and almost every distinctive property of MoE serving falls out of it.

SymbolMeaning
\(E\)Number of routed experts per MoE layer
\(k\)Experts activated per token (top-\(k\) routing)
\(B\)Requests in the running batch — at decode, one token each
\(P_e\)Parameters in one expert's FFN
\(C(B)\)Expected fraction of experts touched by the batch — coverage
\(\lambda\)\(Bk/E\) — mean token-assignments per expert, the load factor
\(I^*\)Roofline ridge, peak FLOP/s ÷ peak bandwidth (H100: ≈295)

1 · What a decode step actually reads

Decode is one token per request per step. The GPU must stream from HBM every weight that step will touch, and the coverage question is entirely about the expert FFNs — attention is dense and replicated, so it is read in full every step regardless.

Bytes moved per decode step, per MoE layer (FP16)
ModelFLOPsExpert weight bytesReuse
Dense FFN\(2 B \cdot N_{\rm ffn}\)\(2 N_{\rm ffn}\)Every token uses every weight
MoE, top-\(k\) of \(E\)\(2 B k \cdot P_e\)\(2 \, C(B) \cdot E P_e\)Only the tokens that routed there

The FLOPs line is the familiar one — it is the activated-parameter count that MoE Parallelism § throughput ceiling uses, \(N_{\rm act} = N_{\rm attn} + \frac{k}{E}N_{\rm ffn}\), and it is why an MoE is cheap to compute. The bytes line is the one nobody writes down, and it carries a completely different factor. Compute scales with \(k/E\); memory traffic scales with \(C(B)\), which is not \(k/E\) except at \(B = 1\).

This is the gap between "activated parameters" and "resident parameters" as a serving cost. DeepSeek-V3 activates ~37B of 671B parameters per token — a 18× FLOPs saving. It does not get an 18× bandwidth saving at serving batch sizes, because with a hundred concurrent requests the batch collectively touches nearly all 671B.

2 · The coverage law

Fix an expert \(e\). Under balanced routing, one token selects it with probability \(k/E\), so one token misses it with probability \(1 - k/E\). The \(B\) requests in the batch are different sequences with independent routing decisions, so \(e\) is missed by all of them with probability \((1-k/E)^B\). By linearity of expectation over the \(E\) experts:

The expert coverage law
\[ C(B) \;=\; 1 - \left(1 - \frac{k}{E}\right)^{B} \]
Expected fraction of experts that at least one request in the batch routes to — i.e. the fraction of expert weights the decode step must read.

Linearity of expectation is doing real work here: the \(k\) choices within one token are not independent (top-\(k\) picks a \(k\)-subset without replacement), but that never enters the derivation. Only independence across requests is assumed — and §5 is about when even that fails.

Two sanity checks. At \(B=1\), \(C = k/E\): a single user reads exactly the \(k\) experts their token routes to, which is the whole promise of sparsity. At \(k = E\) (every expert active) \(C = 1\) for all \(B\) — the dense model, where the law correctly says batching changes nothing about what gets read.

The load factor collapses it to one variable

For \(k \ll E\), \((1-k/E)^B = e^{B\ln(1-k/E)} \approx e^{-Bk/E}\). Writing \(\lambda = Bk/E\) — the mean number of token-assignments per expert, exactly the occupancy parameter of throwing \(Bk\) balls into \(E\) bins:

Poissonized form
\[ C \;\approx\; 1 - e^{-\lambda}, \qquad \lambda = \frac{Bk}{E} \]

So \(B\), \(k\) and \(E\) never matter separately — only the ratio \(\lambda\). A batch of 32 on a 256-expert top-8 model (\(\lambda = 1\)) is in exactly the same regime as a batch of 4 on an 8-expert top-2 model. The natural unit of batch size for an MoE is \(E/k\) requests, not one request.

\(E/k = 4\) — Mixtral 8×7B \(E/k = 16\) — Qwen3-235B \(E/k = 32\) — DeepSeek-V3 \(E/k = 128\) — top-1 routing

Coverage saturates, and where it saturates is set entirely by \(E/k\). Every curve is the same shape shifted along the log-\(B\) axis: coverage passes \(\tfrac12\) at \(B \approx 0.69\,E/k\) and 95% at \(B \approx 3\,E/k\). The consequence is the flat left shoulder — while \(C(B)\) rises linearly in \(B\), each added request brings its own experts and the per-token cost does not fall at all. Only past the knee does an extra request become nearly free.

Batch thresholds

Inverting the law gives the batch size at which a target coverage is reached, \(B(c) = \ln\!\frac{1}{1-c} \big/ \ln\!\frac{1}{1-k/E}\), or in load-factor form simply \(\lambda = \ln\frac{1}{1-c}\):

Coverage \(c\)\(\lambda = Bk/E\)Batch size \(B\)Reading
50%0.69\(0.69\,E/k\)Half the expert table is already resident traffic
90%2.30\(2.3\,E/k\)Sparsity has stopped buying bandwidth
99%4.61\(4.6\,E/k\)Effectively reading the dense model

These are small numbers. Even at \(E/k = 32\), a batch of 148 requests reads 99% of every expert in the model — and 148 concurrent requests is an unremarkable load for a single production serving replica.

3 · The shifted roofline

Now divide the two rows of §1's table. Arithmetic intensity for the expert FFNs, in FP16:

Intensity of an MoE decode step
  • FLOPs: \(2 B k P_e\) — every token does its \(k\) expert FFNs.
  • Bytes: \(2\, C(B)\, E P_e\) — every touched expert is streamed once, whether one token needs it or a hundred.
  • Intensity: \(I = \dfrac{2BkP_e}{2\,C(B)\,EP_e} = \dfrac{Bk/E}{C(B)} = \dfrac{\lambda}{C(B)}\).
MoE decode intensity
\[ I(\lambda) \;=\; \frac{\lambda}{1 - e^{-\lambda}}, \qquad \lambda = \frac{Bk}{E} \]
Identically: the average number of tokens routed to each expert that gets read. That average is the reuse factor.

The interpretation is worth pausing on. Dense decode has \(I = B\) because every weight is reused by all \(B\) tokens. MoE decode has \(I = \lambda/C\) because a touched expert is reused by \(\lambda E / (C E)\) tokens on average. Reuse is not the batch size; it is the batch size per expert. Both limits follow immediately:

Two regimes
  • Small batch, \(\lambda \ll 1\) (\(B \ll E/k\)): \(C \approx \lambda\), so \(I \to 1\). The \(B\)'s cancel. Batching buys no weight-read amortization whatsoever — every added request drags in a nearly disjoint set of experts, and per-token bandwidth cost is flat. An MoE at \(B=64\) with \(E/k=128\) is as bandwidth-bound as a dense model at \(B=1\).
  • Large batch, \(\lambda \gg 1\): \(C \to 1\), so \(I \to \lambda = Bk/E\). Amortization resumes at full slope, but permanently offset: the MoE sits a factor \(E/k\) below the dense curve, because the FLOPs were cut by \(k/E\) while the bytes were not cut at all.
dense: \(I = B\) \(E/k = 4\) \(E/k = 32\) \(E/k = 128\) H100 ridge \(I^*\!\approx\!295\)

MoE decode pays twice: a flat shelf, then a permanent offset. Both axes are \(\log_2\). Every MoE curve leaves the origin flat at \(I \approx 1\) — batching does nothing — until \(B \approx E/k\), then turns and runs parallel to dense, displaced downward by exactly \(\log_2(E/k)\). Where the dense model crosses the H100 ridge at \(B \approx 295\), the \(E/k=32\) model needs \(B \approx 9{,}400\) and never reaches it on one GPU. MoE decode is memory-bound essentially always.

Ridge batch size
\[ B^{*}_{\rm MoE} \;\approx\; I^{*} \cdot \frac{E}{k} \]
On an H100 (\(I^* \approx 295\)) with \(E/k = 32\): ~9,400 concurrent requests to become compute-bound. This is the number that decides serving architecture.

The trend across generations is the point. Mixtral's \(E/k = 4\) saturates by \(B \approx 10\) — at any realistic serving load it behaves like a dense model of its total size, and coverage is not a design consideration. Every model since has pushed toward finer granularity (more, smaller experts) because fine-grained routing improves the quality-per-activated-FLOP tradeoff. That same move multiplies \(E/k\), which pushes the coverage knee to larger batch and drives the ridge batch out of reach. Fine-grained MoE is a training-side win paid for on the serving side in bandwidth.

5 · When the law is optimistic — and when it's the wrong average

\(C(B)\) as derived is an idealization in three specific ways, two of which make real coverage lower and one of which makes the mean the wrong statistic entirely.

Correlated routing across requests

Requests in a batch are not independent draws. A serving replica handling one workload — all code completion, all one language, all the same system prompt — gets routing that clusters, since experts specialize by domain. Correlation means the batch's experts overlap more than chance, so true coverage sits below \(1-(1-k/E)^B\). This is good for bandwidth. It is also fragile: it evaporates the moment traffic is heterogeneous, so it is not something to provision against.

Non-uniform expert popularity

The derivation used a uniform \(k/E\) per expert. With unequal marginals \(p_e\) (summing to \(k\)), expected coverage is \(\sum_e [1-(1-p_e)^B]\), and since \(1-(1-p)^B\) is concave in \(p\), any imbalance reduces the sum. Uniform routing maximizes coverage. This yields an irony worth stating plainly: the auxiliary load-balancing loss, whose job is to flatten expert utilization so training doesn't waste capacity, is also pushing decode coverage up toward the law's upper bound. Balanced routing is optimal for training throughput and pessimal for decode bandwidth.

Under expert parallelism, the mean is the wrong statistic

With EP across \(G\) devices, each device holds \(E/G\) experts and reads its own covered fraction. In expectation that fraction is the same \(C(B)\), but the step does not finish until the slowest device finishes — step time tracks \(\max_g\) load, not the mean. At small \(\lambda\), where the number of touched experts per device is a handful, that maximum is well above the mean and the variance is large. This is the same tail that motivates redundant/replicated hot experts and dynamic expert placement in production MoE serving.

All three caveats are about how much worse or noisier than \(C(B)\) reality is — none of them restore amortization at small \(\lambda\). The flat shelf in the intensity plot is a structural property of sparse routing, not an artifact of the independence assumption.

6 · What follows for serving

Batch aggregation is the whole game, and the target is \(E/k\)× larger

For a dense model, "keep the batch full" means keep it near \(I^*\). For an MoE it means keep it near \(I^* E/k\) — thousands of concurrent requests. No single replica gathers that from one GPU's worth of KV cache, which is why large-scale MoE decode is deployed as a wide, disaggregated cluster: prefill and decode split onto separate pools (P/D disaggregation) so the decode pool aggregates requests from many prefill workers, with expert parallelism spread across many nodes purely to make the batch big enough. The deployment shape is a direct consequence of the coverage law, not of model size.

EP + DP beats TP at decode

Two ways to split experts across devices, and coverage decides between them:

Tensor parallelExpert parallel
What's shardedEach expert's weight matrices, columnwiseWhole experts, by index
Bytes read per device\(C(B) \cdot E P_e / \mathrm{TP}\) — a shard of every touched expert\(C(B) \cdot E P_e / \mathrm{EP}\) — only its own experts
Comms per layerAllReduce of activations, \(B \times D\), latency-bound at decodeAllToAll of \(B k \times D\) tokens — small at decode batch
GEMM shapeThin and getting thinner as TP growsFull-width, batched by expert

Both reduce per-device bytes by the parallel degree, so bandwidth is a wash. The difference is everything else: TP adds a latency-bound AllReduce on the critical path of every layer and shrinks the already-tiny decode GEMMs, while EP's AllToAll moves activations whose size is \(Bk D\) — negligible at decode batch sizes, in contrast to training, where AllToAll on the full token batch is the dominant cost. Hence the standard serving recipe, EP + DP with TP=1, which shows up in vLLM as --enable-expert-parallel with data parallelism rather than tensor parallelism (the same configuration RL Inference recommends for MoE reward models).

RL rollout generation is the worst case

Rollout generation for GRPO-style training sits exactly in the flat shelf. Batches are bounded by the group size and prompt set rather than by arriving traffic; sequences finish at ragged times so the running batch decays through the step; and the long tail of a reasoning rollout can be a handful of live sequences generating thousands of tokens each. When \(B\) falls below \(E/k\), intensity is pinned at \(I \approx 1\) — the rollout phase reads a large fraction of a 671B-parameter expert table to produce a few dozen tokens. This is a large part of why the generation phase dominates MoE RL step time far more than the activated parameter count suggests, and why async RL's ability to keep many rollouts in flight matters more for MoE than for dense models: it is buying \(\lambda\), not just utilization.

It also reframes speculative decoding and multi-token prediction for MoE. Verifying \(\gamma\) draft tokens per request makes the step carry \(B(\gamma{+}1)\) tokens, which moves right along the coverage curve. On a dense model that mostly trades wasted FLOPs for fewer steps; on an MoE in the flat shelf, the extra tokens ride along on expert reads that were happening anyway — the drafted tokens are close to bandwidth-free.

Expert offload works only at \(B \lesssim E/k\)

Keeping cold experts in CPU RAM or on SSD and paging them into HBM on demand is viable exactly when the working set is small — that is, when \(C(B)\) is small. Single-user local inference (\(B=1\), \(C = k/E\), a few percent of the table) is the regime where offload and LRU expert caching genuinely work, and it is why consumer MoE inference is practical on hardware that cannot hold the model. Past the knee the working set is the whole expert table every step, and a cache with a ~100% miss-stream has nothing to exploit. The coverage law is the precise criterion for which side of that line a deployment is on.

Weight quantization pays disproportionately

On the dense page, quantization helps only below the ridge. An MoE decode step is essentially never above the ridge, so the FP8/INT4 win on expert weights is close to fully realized — bytes halve, \(I\) doubles, throughput doubles. Sparse models are the case where weight-only quantization is least likely to be wasted, and the experts, being the overwhelming majority of parameters, are exactly what to quantize.

7 · Is MoE a decode win at all?

Everything so far has compared an MoE to itself at different batch sizes. The sharper question is architectural: given a workload, would a dense model serve it more cheaply? The coverage law answers this, and the answer has a clean form — but it is easy to state wrongly, so it is worth building carefully.

Which parameter count you're billed for

The phase decides the bill
\[ \text{compute-bound phase} \;\to\; N_{\rm act} \qquad\qquad \text{bandwidth-bound phase} \;\to\; C(B)\cdot N_{\rm total} \]
Sparsity cuts FLOPs unconditionally. It cuts bytes only by \(C(B)\) — and \(C\) saturates.

Prefill is the first case, decode is the second. That is the entire asymmetry. It is tempting to summarize it as "MoE is a prefill play, not a decode play," and that is nearly right — but the comparison is meaningless until we say which dense model.

Against which dense model?

Three candidate baselines for DeepSeek-V3 (\(N_{\rm act} = 37\)B, \(N_{\rm total} = 671\)B), and they give wildly different verdicts:

BaselinePrefillDecode at \(C \to 1\)
iso-active — 37B densetieMoE 18× worse
iso-total — 671B denseMoE 18× bettertie
iso-quality — ~158B denseMoE 4.3× betterMoE 4.3× worse

Only the third is a real serving decision — nobody deploys an architecture to match a FLOP count. Taking the common heuristic that an MoE matches a dense model of \(N_d = \sqrt{N_{\rm act}N_{\rm total}}\) and writing \(s = \sqrt{N_{\rm total}/N_{\rm act}}\), the two factors in that row are identical, and not by coincidence: \(N_d/N_{\rm act} = N_{\rm total}/N_d = s\) is an algebraic identity of the geometric mean.

The trade, stated exactly

MoE buys a factor \(s = \sqrt{N_{\rm total}/N_{\rm act}}\) on compute-bound phases and pays the same factor \(s\) on bandwidth-bound phases at saturated batch. It is a pure exchange of decode bandwidth for prefill compute, at an exchange rate of \(\sqrt{\text{sparsity}}\).

The geometric-mean heuristic is the weakest link in this whole section. It is folklore, not a measured law, and the conclusions are sensitive to it: the decode crossover below moves from \(B \approx 3.5\) to \(B \approx 29\) as the assumed iso-quality dense goes from 70B to 400B. The structure of the argument survives any choice; the specific batch numbers do not. Treat them as order-of-magnitude.

The decode crossover is at nine requests, not "high concurrency"

Per-token decode bytes are \(C(B)N_{\rm total}/B\) for the MoE and \(N_d/B\) for the dense model. The \(1/B\) cancels, so MoE decode is cheaper precisely when

Decode crossover
\[ s\,C(B) < 1 \quad\Longleftrightarrow\quad C(B) < \frac{1}{s} \quad\Longleftrightarrow\quad B \lesssim \frac{E}{k}\ln\!\frac{s}{s-1} \]
For V3: \(C^* = 0.235\), reached at \(B \approx 9\). Nine concurrent requests.

This is the load-bearing correction to the intuition. The thing that destroys MoE's decode advantage is not high concurrency — it is the coverage knee, and the knee is at single-digit batch. By \(B \approx 100\) the penalty has already reached its asymptote \(s\) and stops getting worse. Everything above that is one regime, not a spectrum.

More concurrency favours MoE, not dense

Total time per request is a prefill term plus a decode term, and only one of them shrinks with batching:

Cost per request
\[ t \;\propto\; \underbrace{\frac{N_{\rm act}T_p}{F}}_{\text{compute-bound, } B\text{-independent}} \;+\; \underbrace{\frac{C(B)\,N_{\rm total}\,T_d}{\text{BW}\cdot B}}_{\text{bandwidth-bound, falls as } 1/B} \]

Setting MoE cost below dense cost and solving for the workload ratio:

MoE wins the total bill iff
\[ \frac{T_p}{T_d} \;>\; \frac{s\,\bigl(s\,C(B)-1\bigr)}{s-1}\cdot\frac{I^{*}}{B} \]

The \(I^*/B\) is the tell. Decode cost per token falls as \(1/B\) for both architectures while their ratio stays pinned at \(s\); the prefill term, where MoE wins, does not shrink at all. So as concurrency rises, the term MoE loses on becomes a smaller share of the bill. Raising concurrency shifts the balance toward MoE.

break-even \(T_p/T_d\) RAG-like workload (\(T_p/T_d = 10\)) reasoning workload (\(T_p/T_d = 0.1\))

MoE's worst regime is the middle, not the top. Above the violet curve MoE is cheaper; below it, dense is. The curve has a vertical asymptote at \(B \approx 9\) — below that, MoE wins at any workload mix — then peaks at \(B \approx 29\), where coverage has saturated but decode still dominates the bill, then decays as \(1/B\) as prefill takes over. The RAG line makes the point: at \(T_p/T_d = 10\) the workload clears the curve at small batch and again past \(B \approx 122\), but dips under it through \(B \in [12, 122]\) — a prefill-heavy workload served more cheaply by the dense model, purely because that window straddles the peak. Staying above the curve at every batch takes \(T_p/T_d \gtrsim 21\). A reasoning workload is below it until \(B \approx 12{,}500\). Both axes \(\log_2\); V3 routing, \(s = 4.26\), H100 ridge.

What actually decides it

  • Prefill-heavy — RAG, reranking, classification, long-context summarization, \(T_p/T_d \gtrsim 20\). MoE wins at every batch size. The compute-bound phase is the whole bill and it is billed at \(N_{\rm act}\).
  • Generation-heavy — reasoning, agentic loops, long-form writing, \(T_p/T_d \approx 0.1\). MoE needs \(B \approx 12{,}500\) to break even, which no single replica reaches. Dense wins at every practical batch above the coverage knee.

So the workload's prompt-to-generation ratio decides it, against a threshold that scales as \(1/B\). Concurrency is a modifier, and its sign is the opposite of the intuitive one.

Four reasons this doesn't settle the architecture question

The most generation-heavy workload in existence is long-chain reasoning, and essentially every reasoning model shipped is an MoE — R1, Kimi K2, Qwen3-235B. Under the analysis above that looks like a systematic mistake. It isn't, for four reasons that bound how far the serving argument reaches:

  1. The iso-quality dense model doesn't exist. A 158B dense costs several times the MoE's training FLOPs to reach the same quality — that is the entire reason MoE was adopted. The real choice is not "V3 versus an iso-quality dense" but "V3 versus a smaller dense that is worse." Training economics, not serving economics, selected the architecture; serving only gets to price it.
  2. Capacity is a separate bill, and it strengthens the argument. \(N_{\rm total}\) must be resident: 671B in FP8 needs 9+ H100s before any KV cache, against 2–3 for a 158B dense. But note this makes the penalty a cost claim (GPU-seconds per token), not a latency claim — wide EP hands you 9× the aggregate bandwidth, so TPOT can be perfectly good while the bill is 4× worse.
  3. MoE bundles other architectural choices. V3 pairs MoE with MLA, which cuts KV to a 576-element latent per token per layer — across 61 layers, ~34 KB/token at FP8 or ~69 KB at FP16. Holding both sides at FP8 (the precision the 671 GB above assumes; the roofline in §3 is FP16), \(B = 256\) at 8K context is ~74 GB of KV traffic against ~671 GB of weights — so weight traffic still dominates by ~9×, or ~4.6× with the KV cache left at FP16, and the coverage argument is more central for V3-class models, not less. But a clean MoE-versus-dense pair rarely exists to compare.
  4. \(B = 1\) inverts everything. Local and edge inference reads only \(k/E\) of the table, and MoE beats iso-quality dense on decode by the same factor \(s\). Sparsity's decode win is real — it just lives entirely below nine concurrent requests, which is exactly the regime where expert offload also works.
The claim, restated

MoE trades decode bandwidth for prefill compute at a rate of \(\sqrt{N_{\rm total}/N_{\rm act}}\) against an iso-quality dense model. The decode side of that trade turns negative once coverage saturates — around \(B \approx 9\), not at high concurrency — and is fully saturated by \(B \approx 100\). Prefill-heavy workloads therefore favour MoE and generation-heavy workloads favour dense, with break-even at \(T_p/T_d \approx s\,I^{*}/B\). Raising concurrency shifts the balance toward MoE, because it shrinks the decode term both architectures share. Above ~100B, though, the iso-quality dense model is a hypothetical.

8 · Summary

The law

\(C(B) = 1-(1-k/E)^B\) — the fraction of experts a decode step must read with \(B\) requests in flight. Only independence across requests is assumed.

One variable

Everything depends on \(\lambda = Bk/E\) alone: \(C \approx 1-e^{-\lambda}\). The natural batch unit for an MoE is \(E/k\) requests.

Intensity

\(I = \lambda/C(B)\) = mean tokens per activated expert. \(I \to 1\) at small batch, \(I \to Bk/E\) at large batch.

The flat shelf

For \(B \ll E/k\), batching buys zero weight-read amortization — each request brings disjoint experts. Per-token bandwidth cost is flat.

The offset

Past the knee, MoE runs parallel to dense but \(E/k\) below it. Ridge batch \(\approx I^{*}E/k\) — ~9,400 requests for DeepSeek-V3 on an H100.

Direction of travel

Finer-grained routing raises \(E/k\), which is a training win paid for in serving bandwidth. Balanced routing maximizes coverage — and thus cost.

Deployment shape

Wide EP + DP with TP=1, P/D disaggregation, huge aggregated decode batches. All of it is chasing \(\lambda\).

Where it hurts

RL rollouts and low-traffic replicas live in the shelf. Offload and expert caching only work there — and only there.

Versus dense

A pure trade: \(\sqrt{N_{\rm total}/N_{\rm act}}\) gained on compute-bound phases, the same factor paid on bandwidth-bound ones. Decode turns negative at \(B\approx9\), not at high concurrency.

What decides it

The workload's \(T_p/T_d\), against a threshold falling as \(1/B\). Prefill-heavy favours MoE; generation-heavy favours dense. More concurrency favours MoE.
