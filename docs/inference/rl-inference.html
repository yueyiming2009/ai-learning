Inference in RL: Rollout and Reward Model Serving

RL training (PPO, GRPO) alternates inference and training. Inference generates rollouts (actor model) and scores them (reward models). Both are serial dependencies on the training step — inference throughput directly determines how fast the policy improves.

RL-based post-training (RLHF, RLVR) is increasingly important for creating capable models. The inference phases — rollout generation and reward scoring — are not independent serving workloads. They are tightly coupled to the training loop: training cannot proceed until inference completes, and inference cannot begin the next batch until training updates the policy weights. Understanding the inference workload here requires understanding the RL loop structure first.

1 · RL loop anatomy

1
Sample prompts
Draw a batch of prompts from the dataset (e.g., math problems, instructions). Batch size = number of prompts × responses per prompt (G in GRPO).
2
Generate rollouts
Run actor model inference to generate G complete responses per prompt. Each response is an independent autoregressive decode. This is the dominant inference cost: potentially thousands of output tokens per prompt.
3
Score rollouts
For each (prompt, response) pair, compute a scalar reward. Source: learned reward model (RM), rule-based verifier (correct/incorrect answer check), or a combination.
4
Compute log-probs (if needed)
For PPO: compute per-token log-probabilities from a frozen reference policy (to compute KL divergence penalty). This is a forward pass over the response tokens — expensive for long outputs.
5
Training step
Compute advantages (GRPO: group relative; PPO: GAE). Run policy gradient update on the actor. Update critic (PPO). Steps 1–5 repeat for each RL iteration.
Inference fraction of total RL time

For most RL setups, 60–90% of wall-clock time is spent in steps 2–4 (inference), not in the training step. Optimizing inference throughput has a proportionally larger impact on total training speed than optimizing the training step itself. Every 2× improvement in rollout throughput translates roughly to a 1.5–1.8× reduction in total RL wall-clock time.

2 · Rollout generation

Rollout generation is effectively batch offline inference on the actor model: all prompts for a batch are known before generation starts, there is no per-request latency SLO (only a batch completion deadline to not starve the training step), and outputs can be arbitrary length. However, it has unique constraints:

Unique constraint 1 — multiple responses per prompt

In GRPO (and any group-relative RL), G responses are generated per prompt (commonly G=8–16). The prompt tokens are identical across all G responses and only differ in the sampled continuations. This creates a massive prefix caching opportunity: the shared prompt KV is computed once and reused for all G rollouts. The speedup is proportional to the fraction of total tokens that are shared: if the prompt is 1K tokens and each response is 2K tokens, caching saves 1K / (1K + 2K) = 33% of prefill compute per group. At G=16 with a 2K prompt and 1K response, the savings are 2K / (2K + 16K) = 11% — still meaningful at large G.

Unique constraint 2 — weight freshness requirement

After each training step, the actor weights are updated. The rollout workers must use the most recent weights for the next batch of rollouts — they cannot be stale. This means: (a) rollout workers must receive weight updates after each training step, and (b) rollout generation for batch N+1 cannot begin until the training step on batch N is complete (strictly, unless off-policy algorithms are used). This creates a hard synchronization point.

Unique constraint 3 — variable and long outputs

For reasoning tasks (math, code, science), outputs can be 2K–32K tokens — chain-of-thought reasoning traces. Long outputs dominate the KV memory budget. Unlike online serving, you know the approximate output length distribution from prior iterations, so you can tune max_new_tokens tightly and use INT8/FP8 KV quantization aggressively to fit more concurrent rollouts in memory.

Sampling temperature in rollouts

Rollouts use positive temperature (typically T=0.7–1.0) to explore the response space — not greedy. This limits the effectiveness of speculative decoding (acceptance rate α falls with temperature). At T=1.0, a draft model may achieve α≈0.7–0.8, giving a speedup of ~2× for γ=4 — still worthwhile, but less so than for greedy tasks.

3 · Reward model serving

Reward models (RMs) take a (prompt, response) pair and produce a scalar score. From an inference perspective, this is a prefill-only workload: the response tokens are already generated (by the rollout step), so the RM just runs a single forward pass over the full (prompt + response) sequence. There is no autoregressive decode.

RM inference characteristics

Input: prompt + complete response (potentially 4K–32K tokens). Output: one float. The computation is a single forward pass — highly parallelizable, compute-bound for long sequences, memory-bandwidth-bound for short ones. Throughput: a reward model forward pass is 2× faster than a policy forward pass of the same token count (no KV cache needed; no decode loop). It is also batched across all G responses for a prompt simultaneously. Memory: no KV cache is accumulated (single pass); only activation memory is needed, which is bounded by sequence length and model size.

For rule-based rewards (e.g., exact match for math problems, unit test pass/fail for code): the "reward model" is a Python function, not a neural network. There is no GPU inference cost. GRPO for math (DeepSeek-R1 style) uses this approach and avoids the RM inference bottleneck entirely.

For learned reward models: the RM can be a different size than the actor. A smaller RM (1B–7B) scoring responses from a larger actor (70B+) is common — RM inference is not the bottleneck in this case.

5 · Inference optimizations for RL

Rollout generation

  • Large effective batch: generate G responses for each of B prompts simultaneously. The total decode batch size is G × B. Use PagedAttention to fit this large batch. For G=8, B=32: 256 concurrent response generations.
  • Shared prompt prefix caching: all G responses for a given prompt share the exact same prompt KV. Compute once, reuse G times. Reduces prefill time by (prompt_len / total_len) for each group. Cross-step caching does not apply — weights change after each training update, invalidating all KV.
  • W4A16 quantization: long output lengths and large batches make rollout generation highly bandwidth-bound. W4 doubles decode throughput with minimal quality loss — and quality loss matters less for exploration (diverse trajectories) than for evaluation tasks.
  • KV-cache fp8 quantization: for long rollouts (2K–32K output tokens), KV memory is the binding constraint. FP8 KV cache roughly halves the KV footprint, allowing ~2× more concurrent rollout sequences at fixed memory. Set kv_cache_dtype=fp8 in vLLM.
  • Chunked prefill for long prompts: when rollout prompts are long (e.g., multi-turn contexts or chain-of-thought seed prompts of 4K+ tokens), chunked prefill prevents OOM from full-context KV allocation at the start. It also smooths the prefill spike for any in-flight sequences sharing the same decode step.
  • Length bucketing (use_dynamic_bsz): within a rollout batch, prompts can have widely varying lengths. Sorting and bucketing by length before feeding the vLLM engine reduces padding waste and decode straggler wait. In VeRL, use_dynamic_bsz=True with max_token_len implements this — effective batch size varies per step to keep token count roughly constant.
  • CUDA graph capture: the decode phase fires the same kernel sequence every step. Enable CUDA graph capture (enforce_eager=False) to eliminate CPU launch overhead, typically a 5–15% decode throughput gain at practical rollout batch sizes.
  • Tensor parallelism: the actor is often large (70B+). Use tensor parallelism across 4–8 GPUs per actor instance; run multiple independent actor instances in parallel for different prompt batches.
  • FlashAttention-3: on H100/H200, FA3's async-pipelined attention kernel achieves near-peak HBM throughput. Enabled by default in current vLLM on H100.

Reward model scoring

  • Batched prefill: pad all (prompt+response) sequences to a common length and process in a large batched forward pass. If responses are variable length, sort by length first and use the smallest pad size per bucket.
  • FP8 compute (W8A8): the reward model is never trained — aggressive quantization carries no stability risk. On H100, --quantization fp8 in vLLM applies dynamic per-tensor FP8 scaling to both weights and activations, firing native FP8 Cutlass kernels on every GEMM. This reduces compute time on the matrix multiplies themselves — the primary bottleneck for large reward models (e.g., a 235B MoE RM). Distinct from W4A16 weight-only quantization, which keeps activations in FP16 and does not change the GEMM kernel.
  • AllReduce reduction for TP'd reward models: if the reward model requires tensor parallelism (too large for one GPU), each TP-fused GEMM ends with an AllReduce across the TP group. Three levers in order of ease: (a) data-parallel + expert parallelism for MoE reward models (--tensor-parallel-size 1 --data-parallel-size N --enable-expert-parallel) — routes tokens to experts without AllReduce, replacing TP collectives with AllToAll; (b) reduce TP degree and use pipeline parallelism instead (AllReduce size scales with TP); (c) custom AllReduce (vLLM's CUDA IPC path, faster than NCCL) — reduces latency but does not overlap with compute.
  • Independent of rollout GPUs: RM scoring can overlap with rollout generation for the next batch if the architecture allows pipelining. This requires decoupling the RM workers from the actor workers.

Reference policy log-probs (PPO)

  • The reference policy is frozen — its weights never change. It can be served as a standard offline batch inference workload.
  • Weights can be quantized aggressively (W4A16 or W8A8) since it is never trained and only used for KL computation. A small quality loss in the reference policy doesn't affect training stability significantly.
  • Log-prob computation over a complete generated response is a single forward pass (same as RM scoring but over more tokens), heavily parallelizable.

6 · GPU placement strategies

Collocated vs. disaggregated placement

Two main placement strategies for RL inference + training workers:

  • Collocated (same GPUs for inference and training): actor inference (rollout) and actor training (policy gradient update) share the same GPU pool. Avoids weight-update transfer overhead. Works well at small scale (8–32 GPUs). The downside: during training, inference is idle; during inference, training is idle. GPU utilization is limited by the serial dependency.
  • Disaggregated (separate inference and training workers): dedicated rollout GPU workers and dedicated training GPU workers. After training, weights are broadcast from training workers to rollout workers. Allows training and inference to run on different hardware (e.g., more inference workers for high-throughput rollouts, fewer training workers). Scales to large clusters. Used by Megatron-Core RL, veRL, OpenRLHF at scale.
Weight synchronization in disaggregated placement adds overhead — the full actor weight tensor must be transferred from training workers to all rollout workers after each training step. For a 70B BF16 model: 140 GB × number of rollout worker groups. On InfiniBand (200 Gb/s ≈ 25 GB/s), this takes ~5–6 seconds. This must be factored into the per-iteration wall-clock time and is why collocated placement is preferred at small scale.

7 · Summary

Dominant cost

Rollout generation (60–90% of RL iteration time). Optimizing rollout throughput has the largest impact on total training speed.

Key difference vs. offline batch

Multiple responses per prompt (GRPO G-factor), weight freshness constraint after each training step, and no latency SLO but a batch completion deadline.

Prefix caching payoff

All G rollouts for a prompt share the same prompt KV. Cache the prompt prefix once per group — large win for long prompts or large G.

Reward model

Prefill-only forward pass over (prompt + response). Rule-based verifiers avoid GPU cost entirely. Smaller RM than actor is typical.

Quantization choice

W4A16 for rollout generation (bandwidth-bound, large batch). W8A16 for reference policy (accuracy matters slightly more). Aggressive INT8 KV for long rollouts.

Placement

Collocated at <32 GPUs (simpler, no weight sync). Disaggregated at scale (separate inference/training workers, broadcast weights each step).
