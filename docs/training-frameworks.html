Training Frameworks — Megatron-LM, DeepSpeed, and FSDP/TorchTitan

The parallelism math is public and identical everywhere. What frameworks actually sell is an implementation: which state they shard, which kernels they fuse, and what they overlap behind compute. This page compares the three main pretraining stacks — and locates the throughput crossover between them.

This page assumes the strategy pages: Data Parallelism & the ZeRO ladder →, Tensor Parallelism →, Pipeline Parallelism →, and Sequence Parallelism →. RL post-training frameworks (verl, TRL, slime) are a layer above these — see the RL framework landscape → and verl →, which swap Megatron-Core or FSDP in as their training backend.

Read the parallelism papers and you could conclude the frameworks are interchangeable: they all implement the same collectives over the same process groups. Then you benchmark a 7B model and find a 20–30% MFU spread between stacks running the same nominal strategy. The gap is not the math — it is engineering: kernel fusion, communication overlap, memory management. This page is about that gap: what each framework is actually optimizing for, where each one wins, and why.

1 · What a training framework actually is

Every distributed training stack decomposes into the same three layers, and keeping them separate is the key to comparing frameworks honestly:

LayerThe question it answersWhere it's decided
Parallelism strategy Which collectives run over which process groups — DP, TP, PP, SP, EP, and their composition into a device mesh. Public math. Identical across frameworks; covered by the parallelism pages.
Memory strategy What each GPU keeps resident: replicated vs. sharded optimizer state / gradients / parameters (the ZeRO ladder), activation recomputation, CPU/NVMe offload. Public math too — but frameworks differ in which rungs they implement well.
Step implementation What kernels actually launch, in what order, and what communication hides behind what compute. This is the product. Fusion, overlap, buffer management — where the 20–30% lives.

The three stacks stake out different corners: Megatron-LM is model-parallelism-first (a vertically integrated NVIDIA stack where layer 3 is hand-written), DeepSpeed is memory-first (the ZeRO ladder plus offload, attachable to any PyTorch model), and FSDP/TorchTitan is composability-first (sharded data parallelism as a native PyTorch primitive, with the compiler doing the fusion). None dominates: which one is fastest depends on where your run sits on the model-size × cluster-size plane.

2 · Megatron-LM — model parallelism first

Megatron began as the 2019 NVIDIA paper that introduced tensor parallelism for transformers, and accreted the rest of the modern parallelism toolbox: interleaved-1F1B pipeline parallelism, sequence parallelism with selective recomputation, expert and context parallelism, and a ZeRO-1-style distributed optimizer. Today the parallelism engine and transformer building blocks live in Megatron-Core (a library others build on — NVIDIA's NeMo, and verl's Megatron backend), with Megatron-LM proper being the reference pretraining scripts on top.

The design philosophy is vertical integration on NVIDIA hardware. The model must be expressed in Megatron's own transformer blocks — you don't bring an arbitrary nn.Module — and in exchange every layer of the stack is co-designed: the parallelism knows the model structure, the kernels know the parallelism, and the communication schedule knows both. That bargain is exactly what a compiler can't yet give you across TP/PP boundaries.

2.1 The strategy layer: 4-D parallelism + distributed optimizer

Strategy-wise, Megatron is the reference implementation of everything on the parallelism pages: TP within a node, SP to shard the norms/dropouts TP leaves replicated, interleaved 1F1B PP across nodes, and DP outermost — with the distributed optimizer sharding optimizer state and fp32 master weights over the DP group (ZeRO-1 in Megatron's dialect). What makes it "Megatron" is not any one axis but that all of them compose out of the box, with the process-group bookkeeping done for you.

2.2 The implementation layer: why it's fast even at TP = 1

Run Megatron-LM with --tensor-model-parallel-size 1 — pure data parallelism — and it can still beat a naive PyTorch loop on the same model. That advantage is the step-implementation layer, and it decomposes into fusion and overlap.

Fusion — starve the memory bus

A transformer step is matmuls interleaved with bandwidth-bound pointwise ops, each of which normally costs a full HBM read + write of an activation tensor. Megatron fuses the standard chains into single kernels:

  • Bias + activation (GeLU / SwiGLU) in the MLP — one kernel forward, one backward.
  • Bias + dropout + residual-add after attention and MLP — three ops, one kernel.
  • Persistent LayerNorm/RMSNorm — the row stays in registers/shared memory across the whole reduction.
  • Scaled masked softmax — scaling, implicit causal masking (the triangular kernel never materializes a mask tensor), and the max-subtraction trick fused, in fp16/bf16 end-to-end. Superseded by FlashAttention / Transformer Engine fused attention, which Megatron selects automatically — see FlashAttention.
  • Fused RoPE and a vocab-parallel fused cross-entropy that never materializes the full softmax over the vocabulary — the largest single activation in a small model.
  • Gradient-accumulation fusion: the weight-gradient GEMM accumulates directly into the persistent fp32 main-grad buffer via the GEMM epilogue, instead of emitting a bf16 gradient and launching a separate cast-and-add. With gradient accumulation this saves a full read+write of every weight gradient per micro-batch.
  • Fused optimizer + multi-tensor apply: Adam updates, grad-norm computation, and clipping batched across all parameter tensors into a handful of launches — thousands of small kernels removed per step, which matters most precisely when the model is small.
Overlap — never let a collective idle the SMs
  • --overlap-grad-reduce — gradients live in one contiguous, bucketed buffer; each bucket's reduce-scatter launches the moment backward fills it, hiding DP communication behind the rest of backward.
  • --overlap-param-gather — with the distributed optimizer, the all-gather of updated parameters for layer \(n{+}1\) prefetches while layer \(n\) computes forward.
  • --tp-comm-overlap — the one that attacks TP's intrinsic critical-path cost: GEMMs are split into chunks and the TP all-gather/reduce-scatter ring-pipelines against the compute chunks ("userbuffers", direct NVLink writes).
  • Interleaved 1F1B — the virtual-pipeline schedule shrinks the bubble by the interleave factor; see Pipeline Parallelism.

On top sits Transformer Engine: FP8 GEMMs on Hopper/Blackwell with per-tensor scaling handled for you — for large-model pretraining this is routinely another 1.3–1.6× step-time win, and for a long time Megatron was the only stack where FP8 was turnkey.

The costs are the mirror image of the benefits: NVIDIA-only in practice, a rigid model zoo (anything that isn't a Megatron transformer block is a porting project), its own checkpoint format (conversion tooling to/from Hugging Face is a perennial friction point), and a large, research-hostile codebase — the price of hand-written layer 3.

3 · DeepSpeed — memory first

DeepSpeed's organizing idea is the ZeRO ladder — it is the framework that introduced it (see the ZeRO ladder for the math). Where Megatron asks "how do I split the computation," DeepSpeed asks "how do I stop replicating state," and then pushes that question further than anyone else:

RungWhat it shards / moves
ZeRO-1 / 2 / 3Optimizer state → + gradients → + parameters, sharded over the DP group. Stage 3 ≈ FSDP.
ZeRO-OffloadOptimizer state and the update step move to CPU RAM — a 10B-parameter fine-tune on one GPU.
ZeRO-InfinityParameters, gradients, and optimizer state page between GPU, CPU, and NVMe — capacity bounded by disk, not HBM.
ZeRO++Attacks stage 3's communication bill: quantized all-gather/reduce-scatter and hierarchical (intra-node secondary) partitioning to cut inter-node volume.

The second defining trait is the adoption model: DeepSpeed wraps your existing nn.Module — no rewrite — and is driven by a JSON config, which is why it became the default scaling engine inside Hugging Face Trainer/Accelerate. The typical DeepSpeed user never calls DeepSpeed directly: 

{
  "train_micro_batch_size_per_gpu": 4,
  "bf16": { "enabled": true },
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": { "device": "cpu" },
    "overlap_comm": true
  }
}

DeepSpeed also ships a pipeline engine, MoE support, and inference kernels, but its center of gravity has always been memory: it is the stack you reach for when the model doesn't fit and you can't (or won't) restructure it. The honest caveats: tensor parallelism is not a first-class native axis the way it is in Megatron (you bring Megatron-style TP to it, or go without), the hooks-based ZeRO-3 machinery interacts awkwardly with torch.compile, and offload trades step time for capacity — NVMe paging keeps a run alive, not fast.

DeepSpeed ZeRO-3 vs. FSDP — same math, different engineering
DeepSpeed ZeRO-3
Per-parameter partitioning via Python hooks that intercept module access; JSON-config driven; richest offload story (CPU/NVMe); turnkey inside HF Trainer. External library with its own runtime and optimizer wrappers.
FSDP2
Per-parameter sharding as DTensor — a core PyTorch type. Composes natively with torch.compile, TP, and device meshes. Leaner offload (CPU only), but no impedance mismatch with the rest of the PyTorch stack.

4 · FSDP & TorchTitan — composability first

FSDP is PyTorch's answer to ZeRO-3, and its second generation is the interesting one. FSDP1 flattened each wrapped module's parameters into one FlatParameter — efficient, but a monolith that fought the compiler and made anything per-parameter (partial freezing, mixed dtypes, TP composition) painful. FSDP2 (fully_shard) re-implements the same collective schedule with per-parameter DTensor sharding: every parameter is individually a distributed tensor carrying its own sharding spec on a device mesh. 

from torch.distributed.fsdp import fully_shard

for block in model.layers:
    fully_shard(block, mesh=dp_mesh)   # each block = one all-gather / reshard unit
fully_shard(model, mesh=dp_mesh)
model = torch.compile(model)           # fusion comes from the compiler, not hand-written kernels

That last line is the philosophy: where Megatron hand-writes its fused kernels, the PyTorch stack expects torch.compile to fuse the pointwise chains, FlashAttention/SDPA to cover attention, and torch.optim.AdamW(fused=True) to cover the optimizer — the individual Megatron advantages of §2.2, delivered by a compiler over an unmodified model.

TorchTitan is PyTorch's reference pretraining stack built from these parts: FSDP2 for the DP axis (including HSDP hybrid sharding), TP/SP expressed as DTensor layouts on the same device mesh, pipeline parallelism, torch.compile, float8 training, async TP (compiler-driven micro-pipelining of TP communication against GEMMs — the same idea as Megatron's userbuffers), and distributed checkpointing. It is best read as "Megatron rebuilt from composable, native PyTorch parts" — a few thousand lines of readable code rather than a monolith, at the cost of being younger, Llama-shaped, and still chasing Megatron's last few MFU points at the largest scales.

6 · Where the crossover lives

"Is Megatron faster than FSDP?" has no context-free answer, but it has a clean structure. The two families pay for fundamentally different things:

The one-line model
TP communication scales with activations (tokens per micro-batch × hidden size);
sharded-DP communication scales with weights (hidden size²) — and overlaps.
Where the numbers come from

Per transformer layer, per GPU, with bf16 (2 bytes) and ring collectives (each rank moves ≈ 2× the tensor size; see the communication math). Let \(T = b \cdot s\) be tokens per micro-batch and \(h\) the hidden size:

  • Tensor parallel: 4 all-reduces per layer (2 forward, 2 backward), each on a \(T \times h\) activation: \(\;4 \times 2 \times 2\,T h = 16\,Th\) bytes — per micro-batch, on the critical path.
  • FSDP / ZeRO-3: a layer holds ≈ \(12h^2\) parameters (QKVO \(4h^2\) + MLP \(8h^2\)). All-gather forward + all-gather backward + reduce-scatter grads ≈ \(3 \times 2 \times 12h^2 = 72h^2\) bytes — independent of batch, and overlappable.
  • Crossover: \(16\,Th = 72h^2 \;\Rightarrow\; T \approx 4.5\,h\) tokens per micro-batch. For \(h = 4096\) that's ≈ 18k tokens; for \(h = 8192\), ≈ 37k.
TP all-reduce, h = 4096 TP all-reduce, h = 8192 FSDP/ZeRO-3, h = 4096 FSDP/ZeRO-3, h = 8192

Bytes moved per layer, per GPU, per micro-batch. TP's cost (sloped lines, \(16\,Th\)) grows with tokens; FSDP's (flat lines, \(72h^2\)) is fixed by the weights. Left of a crossover dot, TP moves fewer bytes than FSDP — increasingly true as \(h\) grows, which is one reason TP+DP hybrids win at frontier scale. But raw bytes aren't the whole story: FSDP's bytes hide behind compute while TP's sit on the critical path, which is why FSDP still wins until memory pressure forces the issue.

Overlaying the byte-counting with the two facts it omits gives the practical decision surface:

  • Criticality beats volume at small scale. FSDP's communication is asynchronous — bucketed, prefetched, hidden behind backward. TP's all-reduces are synchronous walls inside every layer (userbuffers/async-TP chip at this, they don't remove it). A model that fits comfortably under sharded DP should stay there: for small models FSDP ≥ Megatron on throughput, and the residual gap is §2.2's kernels, not the parallelism.
  • Memory pressure flips the sign. When per-GPU state forces tiny micro-batches or full activation recomputation, sharded DP throughput collapses — you burn ~⅓ of compute re-running forward. TP/PP restore arithmetic intensity, and their byte bill (already sub-FSDP at large \(h\)) is worth paying. This — not communication — is usually what actually moves the crossover.
  • Networks decide the hybrid shape. TP wants NVLink, so it stays intra-node (≤ 8); PP's skinny point-to-point activations cross nodes; sharded DP spans the rest. Every frontier recipe — Megatron's or TorchTitan's — is some instance of this layout; the frameworks differ in how well each axis is engineered, not in the layout itself.

7 · Choosing — a decision guide

  1. Model + optimizer state fits one GPU with headroom? DDP (or single-GPU). No sharding tax at all.
  2. Fits when sharded across your GPUs? FSDP2 — add HSDP across nodes, torch.compile for the kernel gap, activation checkpointing only where needed. This covers most research and most fine-tuning.
  3. Doesn't fit, and you won't restructure the model? DeepSpeed — ZeRO-3, then Offload/Infinity as capacity demands, accepting step-time cost. The natural path inside HF Trainer/Accelerate.
  4. Pretraining at ≳10B on an NVIDIA cluster, chasing MFU? Megatron-LM/-Core (or NeMo) — TP+SP+PP+DP with FP8; the hand-tuned layer 3 is the last 10–20%. TorchTitan is the credible native-PyTorch alternative when hackability and a small codebase matter more than the final few points.
  5. RL post-training? You pick twice: verl exposes both an FSDP backend (flexibility, HF-native models) and a Megatron-Core backend (scale) under one API — see verl.
Benchmark claims between these stacks go stale in months — FSDP2 + compile closed much of the historical gap, ZeRO++ cut stage-3's comm bill, TE keeps moving the FP8 goalposts. The structure above (what scales with what, what overlaps, what memory pressure does) is the durable part; re-measure the constants on your own model and cluster.

8 · The wider landscape

Around the big three sits a ring of frameworks that mostly compose or repackage them:

FrameworkOne-line identity
HF Accelerate / Trainer Not an engine — a unified launcher and config layer that dispatches to DDP, FSDP, or DeepSpeed underneath. The default answer for fine-tuning.
Nanotron Hugging Face's minimalist 3-D-parallel pretraining library — Megatron's strategy layer reimplemented small and readable (used for SmolLM); fewer kernels, more clarity.
Lightning / Fabric Training-loop abstraction with pluggable strategies (DDP/FSDP/DeepSpeed) — organizes your code, delegates the distributed engineering.
Composer / LLM Foundry MosaicML's FSDP-centric recipe stack (MPT models) — opinionated defaults and speedups over PyTorch-native parts.
Colossal-AI Broad-spectrum parallelism toolkit (TP variants, ZeRO-like "Gemini" memory manager) — wide feature menu, smaller production footprint than the big three.
MaxText, Levanter (JAX) The compiler counterpoint: declare shardings (GSPMD/named axes) and XLA emits the collectives, fusion, and overlap that Megatron hand-writes. MaxText is the TPU-first reference; Levanter adds named tensors and bitwise reproducibility.

The JAX row is worth dwelling on for a moment: it is the strongest version of the FSDP/TorchTitan bet — that layer 3 belongs to a compiler, not to hand-written kernels. On TPUs, where XLA is the only path, that bet already won; on GPUs, the hand-tuned stack still holds the MFU crown, which is a fair one-line summary of the whole page.

Summary

Three layers

Strategy and memory math are public and shared; frameworks compete on the step implementation — fusion, overlap, buffers. That's where the 20–30% MFU spread lives.

Three bets

Megatron: vertically integrated model parallelism. DeepSpeed: shard and offload memory, wrap any model. FSDP/TorchTitan: native primitives + compiler fusion.

The crossover

TP comm scales with tokens (\(16Th\), critical path); sharded-DP comm scales with weights (\(72h^2\), overlappable). Memory pressure, not bytes, is what usually flips a run from FSDP to Megatron.

Default picks

Fits sharded → FSDP2 + compile. Doesn't fit, can't restructure → DeepSpeed. Frontier NVIDIA pretraining → Megatron (or TorchTitan for hackability). Fine-tuning → Accelerate on top.
