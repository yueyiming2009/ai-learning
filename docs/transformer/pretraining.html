Transformer & Pretraining

Pretraining the Transformer

The objective that turns a stack of blocks into a language model — next-token prediction — and the single-device training loop that optimizes it: shifted-label cross entropy, gradient accumulation, mixed precision, and activation checkpointing.

The previous page assembled the model; its \(12Ld^2\) weights are still random. Pretraining is what fills them with knowledge. The remarkable thing is how simple the objective is: predict the next token, over and over, on a large corpus. Everything a base model knows is squeezed out of that one self-supervised signal.

1. The Objective — Next-Token Prediction

Factor the probability of a sequence with the chain rule of probability — exactly, with no approximation:

\[ p_\theta(x_1, x_2, \ldots, x_T) = \prod_{t=1}^{T} p_\theta(x_t \mid x_{<t}) \]

The model's whole job is to produce each conditional \(p_\theta(x_t\mid x_{<t})\): given everything so far, a distribution over the vocabulary for what comes next. Training maximizes the likelihood the model assigns to real text, which — taking logs and negating — is the negative log-likelihood objective this whole site keeps returning to:

\[ \mathcal{L}(\theta) = -\sum_{t=1}^{T} \log p_\theta(x_t \mid x_{<t}) \]
This is why pretraining is called self-supervised: nobody labels the data. The label for position \(t\) is just the token that actually occurred at \(t+1\), already sitting in the corpus. A single document of length \(T\) yields \(T-1\) prediction targets for free.

2. Teacher Forcing & Shifted Labels

Here is the trick that makes this efficient on a transformer. Naively, producing \(T\) conditionals sounds sequential — predict token 2, then 3, then 4. But during training we already know the true sequence, so we feed the real tokens as input rather than the model's own predictions. This is teacher forcing, and it lets all \(T\) positions train in one parallel forward pass.

The mechanism is just a one-position shift: the input is the sequence, the label is the same sequence shifted left by one.

input Thecatsatonthe
target catsatonthemat

Position 1 sees The and is trained to predict cat; position 2 sees The cat and predicts sat; and so on. In code the shift is one line:

# tokens: (B, T+1) batch of token ids
inputs  = tokens[:, :-1]   # everything but the last
targets = tokens[:,  1:]   # everything but the first
logits  = model(inputs)     # (B, T, V) — one distribution per position
loss    = cross_entropy(logits.reshape(-1, V), targets.reshape(-1))
The causal mask is what makes teacher forcing valid: even though the full sequence is fed in at once, position \(t\) physically cannot attend to positions \(>t\). Without the mask, predicting the next token would be trivial — the answer is right there in the input. The mask is what keeps each position honest.

3. The Loss in Practice

Each position contributes a cross-entropy term between the predicted distribution \(\mathrm{softmax}(\mathbf{z}_t)\) and the one-hot true token. Averaged over all positions in the batch:

\[ \mathcal{L} = -\frac{1}{B\,T}\sum_{b=1}^{B}\sum_{t=1}^{T} \log \mathrm{softmax}(\mathbf{z}_{b,t})_{\,x_{b,t+1}} \]

Two quantities are worth knowing because they are how everyone actually talks about training progress:

  • Perplexity \(= e^{\mathcal L}\) — the effective number of equally-likely tokens the model is choosing between. A perplexity of 10 means the model is about as confused as if it were guessing uniformly among 10 options.
  • Bits per token \(= \mathcal L / \ln 2\) — the same loss in compression units. Pretraining is, quite literally, learning to compress the corpus.
A useful sanity check: an untrained model outputs near-uniform logits over a vocab of size \(V\), so its initial loss should be \(\approx \ln V\). For \(V=128{,}000\) that is \(\ln(128000)\approx 11.76\). If step 0 isn't near that number, something is wrong with the init or the loss.

4. The Training Loop

With objective and loss defined, the loop is the same five-beat cycle as any neural net — only the scale differs. Each iteration consumes one batch of token sequences:

The five beats of one optimizer step
  1. Forward — run the batch through the stack to logits, compute the shifted-label loss.
  2. Backward — backpropagate to get \(\partial\mathcal L/\partial\theta\) for every weight.
  3. Clip — rescale gradients so \(\lVert g\rVert \le\) some max (typically 1.0); tames the rare loss spike.
  4. Step — the AdamW update applies the gradients under the warmup→cosine learning-rate schedule.
  5. Zero — clear the gradient buffers for the next iteration.
for step, batch in enumerate(loader):
    inputs, targets = batch[:, :-1], batch[:, 1:]
    logits = model(inputs)
    loss   = cross_entropy(logits.reshape(-1, V), targets.reshape(-1))

    loss.backward()                              # accumulate grads
    clip_grad_norm_(model.parameters(), 1.0)    # clip
    optimizer.step()                            # AdamW update
    scheduler.step()                            # advance LR schedule
    optimizer.zero_grad()                       # reset for next step

The "loss curve goes down" story everyone shows is just this loop run for \(10^5\)–\(10^6\) steps. The rest of this page is the three modifications that make each step fit and run fast on real hardware.

5. Gradient Accumulation — Decoupling Batch Size from Memory

Large-batch training is more stable, but a big batch may not fit in memory. Gradient accumulation buys the statistics of a large batch at the memory cost of a small one: run several micro-batches, summing their gradients, and step only once.

\[ g = \sum_{m=1}^{M} \nabla\mathcal L^{(m)}, \qquad \text{effective batch} = M \times (\text{micro-batch}) \]

Because backward() accumulates into .grad rather than overwriting, you simply call it \(M\) times before stepping. The only subtlety is normalization — divide each micro-batch loss by \(M\) so the summed gradient matches a true average over the full effective batch:

optimizer.zero_grad()
for m in range(M):                      # M micro-batches
    loss = compute_loss(micro_batch[m]) / M    # scale so sum = mean
    loss.backward()                          # grads add up
clip_grad_norm_(model.parameters(), 1.0)
optimizer.step()
Gradient accumulation is the single-device cousin of data parallelism: accumulating \(M\) micro-batches in time is what DP does across \(M\) GPUs in space. Same effective batch, same math — one trades memory for time, the other for hardware.

6. Mixed Precision & Loss Scaling

Storing and multiplying weights in 16-bit instead of 32-bit roughly halves memory and doubles throughput on Tensor Cores. But 16-bit floats have a narrow exponent range, and small gradients underflow to zero — they vanish before the optimizer sees them. Two ideas fix this:

Mixed precision (autocast)

Keep a master copy of the weights in FP32, but run the forward/backward matmuls in BF16 or FP16. Matmuls and convolutions go low-precision; reductions, norms, and the softmax stay FP32 where range matters. BF16 (same exponent range as FP32, fewer mantissa bits) is now the default on Ampere/Hopper and needs no loss scaling.

Loss scaling (FP16 only)

FP16 has the throughput but not the range, so gradients can underflow. The fix: multiply the loss by a large factor \(S\) before backward, shifting every gradient up into FP16's representable range, then divide the gradients by \(S\) before the optimizer step. By the chain rule, scaling the loss scales every gradient by the same \(S\) — the update is unchanged, only the intermediate representation is rescued.

\[ \tilde g = \nabla(S\cdot\mathcal L) = S\,\nabla\mathcal L \quad\xrightarrow{\ \div S\ }\quad \nabla\mathcal L \]

Dynamic loss scaling adjusts \(S\) automatically: raise it when gradients are finite, halve it and skip the step when they overflow to inf/NaN.

Rule of thumb: on modern hardware reach for BF16 and skip loss scaling entirely. FP16 + dynamic loss scaling is the legacy path for hardware without BF16, or where the extra mantissa precision matters. The FP8/FP4 frontier is covered on the hardware generations page.

7. Activation Checkpointing — Trading Compute for Memory

The forward pass stashes every intermediate activation because the backward pass needs them. For a deep model on long sequences, these activations — not the weights — are usually the largest single consumer of memory.

Activation checkpointing (a.k.a. gradient checkpointing) keeps only a few activations — typically each block's input — and recomputes the rest on the fly during backward. The trade is explicit:

StrategyWhat is kept residentActivation memoryForward FLOPs
Store everythingall internals, all blocks\(O(L)\) — grows with depth1× (baseline)
Per-block checkpointeach block's input only\(O(L)\), tiny constant~1.33×
\(\sqrt{L}\) segmentingevery \(\sqrt{L}\)-th boundary\(O(\sqrt{L})\)~1.33×

The \(O(\sqrt{L})\) row is the classic sublinear-memory result of Chen et al. (2016), Training Deep Nets with Sublinear Memory Cost — checkpoint every \(\sqrt{L}\)-th block and recompute the rest, which also generalizes to \(O(L^{1/(c+1)})\) memory for \(c\) extra forward passes. PyTorch's torch.utils.checkpoint implements the per-block variant.

Roughly one extra forward pass (≈33% more compute) buys a large drop in activation memory — frequently the difference between a model fitting on a GPU or not. This is exactly the "HFU vs MFU" gap quantified on the MFU page: recomputation inflates the hardware FLOPs without doing new useful work.

9. Summary

Objective

Maximize \(\prod_t p_\theta(x_t\mid x_{<t})\) → minimize summed NLL

Teacher forcing

Feed true tokens; label = input shifted left by 1; all \(T\) positions in parallel

Loop

forward → backward → clip → step → zero, ×10⁵–10⁶

Grad accumulation

Sum \(M\) micro-batch grads → big effective batch, small memory

Mixed precision

BF16 compute, FP32 master; FP16 needs loss scaling for range

Checkpointing

Recompute activations in backward: ~+33% FLOPs, big memory cut

One label per position is not the only option: Multi-Token Prediction → keeps this loop intact but has each position predict the next \(D\) tokens, densifying the signal and leaving behind a draft head for speculative decoding.

This is single-device pretraining end to end. The next domain — Systems & Scaling — takes this exact loop and makes it run fast (kernels, FlashAttention) and across many chips (collectives, tensor/pipeline/data parallelism). After that: RL post-trains the result, and Inference serves it.
