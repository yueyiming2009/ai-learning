Model case study · Transformer & Pretraining

Jev

From language generation to probabilistic decisions: change what the model returns, then reconsider the computation, training objective, and policy around it.

A model inside a workflow often needs to select a queue, judge urgency, or score a candidate, not write a paragraph. TypeSafe's Jev makes that restricted interface the product: caller-defined questions in, typed decisions and probabilities out. The interesting change is the alignment between the output contract and the computational job, not the invention of classification.

1. Why generate text for a bounded decision?

Consider a ticket: “My renewal was charged twice. The account portal works, but I need a refund by tomorrow.” Code needs a routing decision and an escalation decision. A fluent explanation may help a person, but it is not required to choose either branch.

Four ways to implement the same bounded decision.

The task-conditioned distinction matters. “Billing / access / other” today and “approve / review / decline” tomorrow can be supplied as descriptions rather than separate fixed-label deployments. This is a general design possibility, not evidence that all such tasks work equally well. Existing classifiers and language-model scoring methods already cover parts of this space.

The System One API accepts a model, shared state, and named questions. Answers use the question names and include the responding model and usage accounting. The launch-era text primitives give a useful minimal picture:

Do not average a queue identifier. A Choice is categorical; a Score's numeric expectation depends on the chosen ordered-level encoding. Neither a schema nor a high confidence value supplies permission to perform a refund.

Four separate checks: Is the value allowed? Is the answer correct? Are its probabilities reliable across comparable cases? Is the resulting action permitted and useful? Type safety answers only the first.

Scope: the current API also documents preview image/box functionality. This page studies the text decision model, not the entire evolving API. The launch's 255-choice limit is a dated product constraint, not proof of a 256-slot neural head.

3. A plausible graph: shared evidence, private questions

One possible implementation encodes the ticket once, then processes each question against that shared representation. A causal transformer's prefill can compute known token positions together within a layer: the mask restricts information flow, not whether those positions can be scheduled in parallel. Layers still depend on previous layers. Autoregressive decoding adds a different dependency: the next input token is not known until the previous output is chosen.

Hume moved a secret between a sibling question and the shared state: the probed question used it in the latter condition but not the former. This supports behavioral isolation on that experiment, not a uniquely identified attention mask. Queue and urgency can still be statistically related because both depend on the ticket. If escalation genuinely needs the selected queue, code must run a second stage or ask a joint question; batching does not erase that dependency.

See KV sharing for the general mechanism and code-owned workflows for who controls transitions. Hydragen demonstrates efficient shared-prefix attention, but is not evidence that Jev uses that implementation.

4. Read probabilities; do not spell them

A generic \(K\)-way readout maps a hidden representation \(h\) to logits and probabilities:

\[ z = Wh+b,\qquad p_i=\frac{\exp(z_i)}{\sum_{j=1}^{K}\exp(z_j)}. \]

For a binary decision, one logit and a sigmoid suffice. This is ordinary classification mathematics; see softmax and cross-entropy. It does not tell us whether Jev has a dedicated head, selected vocabulary rows, or another equivalent output projection.

Two candidate readouts; neither is confirmed for Jev.
CandidateHow new options acquire meaningOpen detail
Slot headA list-conditioned decision representation scores option positions; code maps slots back to caller keys.Slot count, masking, positional effects, and any tied vocabulary rows.
Pointer-style scorerA decision representation scores option representations built from their descriptions.How representations interact and which tokens/positions are read.

Why the irrelevant-option experiment is informative

If options \(a\) and \(b\) retain fixed logits and a fixed softmax temperature, adding an option changes the denominator but not their odds:

\[ \frac{p(a)}{p(b)}=\exp(z_a-z_b)\qquad\text{(temperature absorbed into the logits).} \]

Hume reports that adding an irrelevant choice changed those odds in a randomized follow-up. That challenges unchanged independent scores plus unchanged normalization temperature. It does not distinguish list-conditioned representations from a set-dependent temperature or other processing. The fixed-size description-change intervention was inconclusive.

Options such as “other” and “none of the above” benefit from joint interpretation. But option-order sensitivity can also move an answer across a production threshold. Permute options and perturb the choice set during evaluation; do not assume input reordering is harmless or that an order effect reveals a specific backbone.

5. Three meanings of “confidence”—and one policy

Verbalized confidence is text generated by a model. Predictive probability is a distribution over the defined outcomes. API confidence can be a statistic computed from that distribution. These objects are not interchangeable.

TypeSafe's Choice documentation and the pinned public adapter define, for \(K>1\):

\[ c=\frac{p_{\max}-1/K}{1-1/K}. \]

For the three-queue example, \(p_{\max}=0.80\) gives \(c=0.70\), not another estimate that the choice has a 70% chance of being correct. It is a rescaling of the peak above the uniform baseline. The adapter normalizes its input and returns 1 for a single option. Score confidence uses distance from the modal level instead; Noul returns the yes probability without a separate confidence field. A concentrated distribution can still be wrong.

What training for calibrated decisions could mean

TypeSafe calls its post-training approach RLCD, or Reinforcement Learning for Calibrated Decisions. The public description gives an objective, not a reproducible algorithm: the exact loss, data construction, optimizer, and updated parameters are undisclosed. In particular, we cannot infer PPO or any other RL update from the name.

Two general outcome-based objectives are log loss \(L=-\log p_y\) and multiclass Brier loss \(L=\sum_i(p_i-\mathbf{1}[i=y])^2\). They are strictly proper scoring rules: expected loss is minimized by the true conditional distribution. For log loss, the reason is \(\mathbb{E}_{y\sim q}[-\log p_y]=H(q)+D_{\mathrm{KL}}(q\Vert p)\). These are explanatory alternatives, not claims about Jev's training recipe.

Properness is an ideal expected-risk property, not a deployment guarantee. Finite data, limited capacity, optimization, and distribution shift all matter. Post-hoc calibration can complement training. Evaluate held-out outcomes, reliability by probability range and subgroup, log/Brier loss, and the resulting workflow utility. Agreement of average confidence and accuracy alone can hide offsetting errors; calibration is a population property, not a verdict on one prediction.

Turn a probability into a cost-aware decision

Let \(p\) be the predicted probability that the ticket truly needs urgent attention. In a simplified two-action policy, unnecessary escalation costs \(C_{\mathrm{FP}}\), a missed urgent ticket costs \(C_{\mathrm{FN}}\), and correct decisions cost zero. The expected losses are:

\[ R(\text{escalate})=(1-p)C_{\mathrm{FP}},\qquad R(\text{do not escalate})=pC_{\mathrm{FN}},\qquad p^*=\frac{C_{\mathrm{FP}}}{C_{\mathrm{FP}}+C_{\mathrm{FN}}}. \]

Escalate above \(p^*\); below it, do not escalate; at equality, the two actions tie. With costs 2 and 8, the threshold is 0.20, so the schematic \(p=0.35\) favors escalation. Real systems may add review capacity, action costs even when correct, or a third “gather evidence” action. Those require a richer loss model.

6. Where the efficiency could come from

Avoid output decoding. A numerical readout can remove the repeated model invocations used to spell a response. Application code can serialize many numbers after the model finishes. That makes “response tokens divided by elapsed time” a misleading decode-speed estimate when the reported token count describes the serialized response.

Reuse input computation. With \(Q\) questions and \(S\) shared state tokens, naïvely independent, uncached requests process the state tokens \(Q\) times; a shared-prefix design can encode them once. This is a statement about repeated state processing, not a claim that total attention FLOPs fall from \(QS\) to \(S\). Branches still process their suffixes and attend to the shared state. A fair comparison should include cached/batched LLM baselines, not only uncached sequential calls.

Batch independent work. Questions can be packed or scheduled together without a dependency on sibling answers. Per-branch work, memory reads, batching efficiency, and queueing remain. A shared-prefix attention kernel may improve those costs; reuse alone does not make them disappear.

Do not infer hardware from one latency curve. Hume proposes a sparse MoE backbone as a plausible efficiency explanation. The model identity, parameter counts, expert routing, hardware, and precision are not established. Prefill-only execution removes autoregressive decode costs, but does not eliminate weight memory, expert dispatch, communication, or all possible bandwidth bottlenecks.

TypeSafe's launch reports 70–500 ms responses and a particular workflow comparison at 193.6× speed and 444.6× cost improvement, describing the latter gains as likely high-end. Its workflows compare against averaged frontier-model reference probabilities—not independent ground-truth labels—and its LLM adapter adds probability-output overhead. Hume's timing probes use upstream service-time headers with uncontrolled shared-service load. Neither source supplies a universal model-only latency or throughput multiplier.

For a useful serving comparison, hold the decision workload and quality/utility target fixed; report state length, question count, options per question, concurrency, caching, reasoning settings, error/retry rates, end-to-end latency quantiles, throughput, and cost. See prefill versus decode and SLO-driven serving.

Good fit: bounded questions inside code-owned workflows

Consider this interface when the useful outputs can be defined in advance, a probability distribution improves routing or prioritization, and latency matters. The inference rule can be fuzzy even when the available actions are enumerable. Keep permissions, side effects, audit logs, and fallback paths in code. Include an explicit “other/insufficient evidence” outcome where appropriate; a closed choice set can otherwise force an unsuitable answer.

Not a drop-in replacement for general generation

Code synthesis, arbitrary text extraction, explanations, and open-ended tool arguments need a different output capability. Staged decisions can support larger candidate sets, but add latency and candidate-selection failure modes. A hybrid can use decision calls for gates and a generative model for open-ended work; more calls are justified only by measured workflow value.

A bounded evaluation before automation

  1. Define outcomes and policy first. Specify labels, an abstention/review path, costs, and the held-out deployment population. Evaluate the full workflow, not just argmax accuracy.
  2. Test the interface. Permute options, add irrelevant alternatives, vary descriptions, and move evidence between state and sibling questions. Measure action changes, not only probability deltas; repeat identical requests to estimate ordinary service variation.
  3. Check probabilities against outcomes. Use log/Brier loss, reliability diagrams with counts and uncertainty, subgroup/shift slices, and risk versus automation coverage. Teacher-model agreement is a different target from outcome calibration.
  4. Compare complete systems. Match quality and policy, include cached/batched and appropriately constrained baselines, and account for retries, staged calls, and human review. A schema guarantee does not close an action-safety gate.

The durable lesson is to match the model interface to the job. A transformer can support useful decisions without spelling every answer, but a trustworthy decision service still needs evidence about probability quality and the policy that consumes it.
