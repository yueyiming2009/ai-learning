Async Training in verl

One fit() loop, three trainer modes, and a replay buffer that decides what "too stale" means. How the mechanism behind the config knobs actually works — server-mode rollout, TransferQueue, partial rollout, and the checkpoint engine.

Prerequisites: verl Architecture (WorkerGroup, ResourcePool, the HybridEngine) and Async RL (policy lag, IS correction, TIM) — this page assumes both and covers the implementation that the async page describes at the algorithm level. Companion pages: Resource Pool Placement (how many GPUs each pool gets), Async RL Monitoring (what to log once it's running).

The async page tells you why off-policy data needs correcting. This page traces what verl actually does: which object holds the samples, who decides a trajectory is too old, what physically happens to a half-finished sequence when the weights change underneath it, and how fresh weights reach the inference engine.

1. Two Different Things Are Called "async"

This is the single most common source of confusion, and it is a config-namespace collision:

Config key What it selects Does it make training off-policy?
actor_rollout_ref.rollout.mode
sync | async  (default: async)		 How rollout is driven. sync = one batched generate_sequences call across SPMD workers. async = each replica runs an OpenAI-compatible server; an agent loop issues one request per trajectory and awaits it independently. No. This is per-request concurrency. Multi-turn tool use needs it. The trainer still waits for the whole batch.
trainer.v1.trainer_mode
sync | colocate_async | separate_async  (default: sync)		 How training relates to generation in time. Whether the trainer may consume samples produced under an older weight version. Yes — for the two *_async values. This is the knob that introduces policy lag.
Server mode is now the default, and it is not async training. rollout.mode: async ships as the default in rollout.yaml, so a stock verl run is already using per-request agent loops against an inference server — while remaining strictly on-policy, because trainer_mode is still sync. Seeing "async" in your rollout config tells you nothing about whether your data is stale.

Everything below concerns the second row. Note also that trainer_mode lives under trainer.v1: the V1 trainer (trainer.use_v1: true) is where all three modes live. The legacy main_ppo_v0.py path is deprecated.

2. One Loop, Three Modes, Six Hooks

verl does not have three trainers. It has one PPOTrainer base class whose fit() loop is identical in all three modes, plus a set of lifecycle hooks that each mode fills differently. The subclasses are startlingly small — trainer_sync.py is 42 lines, trainer_colocate_async.py is 59.

The shared loop, from verl/trainer/ppo/v1/trainer_base.py:

fit():
  while training:
    on_step_begin()
    step(metrics, timing) ────────┐
    save_checkpoint()  (periodic) │
    on_step_end()                 │
    validate()         (periodic) │
                                  │
step():                       ◄───┘
  _add_batch_to_generate()                    # submit train_batch_size prompts
  for trigger_idx in range(parameter_sync_step):
      _step_once(sample_batch_size)  ─────┐
                                          │
_step_once():                         ◄───┘
  on_sample_begin()
  batch = replay_buffer.sample(...)           # ← BLOCKS until enough samples exist
  on_sample_end()
  reward → balance → old_log_prob → ref → values → advantage
  update_critic() ; update_actor()

Two facts about this loop carry most of the weight:

  1. Prompts are submitted, not awaited. _add_batch_to_generate() registers prompts in the data plane and hands them to the agent loop manager; it returns immediately. Generation is always fire-and-forget.
  2. The only blocking point is replay_buffer.sample(). That call polls until enough completed trajectories are available. Every difference between sync and async training reduces to what the buffer is willing to hand over and what the rollout engines are doing while the trainer works.

What each mode puts in the hooks

Hook sync colocate_async separate_async
on_sample_end
after a batch is drawn		 sleep_replicas() — free rollout weights + KV cache so the trainer can use the memory abort_replicas() then sleep_replicas() — kill in-flight requests, then free memory Flip the hybrid engine to TRAINER mode: pull its replicas out of the load balancer, abort, sleep
on_step_end
after the optimizer step		 update_weights() update_weights() then resume_generation_replicas() update_weights() on the standalone rollout pool
on_train_begin — Submit num_warmup_batches extra batches so the buffer is never empty at step 1

Read the colocate_async column carefully — that abort_replicas() is the whole idea. In sync, the buffer only releases a batch once every trajectory in it has finished, so by the time on_sample_end fires nothing is in flight and there is nothing to abort. In colocate_async, the buffer releases as soon as enough trajectories are done; the stragglers are still generating, and they get killed mid-sequence so the GPUs can switch to training. Section 7 covers what happens to their tokens.

sync

Colocated. Rollout drains completely, then trains. No partial rollout. On-policy by construction. The default.

colocate_async

Colocated, but generation is interrupted at the training boundary and resumed after. Kimi-1.5-style streaming rollout with capped-length partial rollout.

separate_async

Rollout gets its own GPUs (rollout.nnodes > 0) and runs continuously. AReaL-style disaggregation with staleness control.

3. Where the Bubbles Are

The reason to accept stale data is wall-clock. Generation is latency-bound at the tail: the slowest trajectory in a batch takes as long as it takes, and throwing more GPUs at the pool does not shorten it. In synchronous RL the whole cluster waits for that one sequence.

generating training long-tail drain (pool mostly idle) idle ⋮ weight sync ▲ abort in-flight requests

Async buys back the tail, not the arithmetic. Raise the tail slider and sync's step time grows without bound while colocate_async's does not — aborting stragglers caps generation at its throughput cost. For separate_async, sweep the share slider: the step time is \(\max(G/s,\; T/(1-s))\), minimized at \(s^\star = G/(G{+}T)\), where it equals exactly \(G+T\) — the same as colocated. Perfect overlap on split pools cannot beat sequential execution on the whole pool. Disaggregation wins for the reasons the arithmetic doesn't show: the rollout pool never stops for a weight sync, staleness > 0 absorbs batch-to-batch jitter, and generation and training can run different parallelism strategies. Mis-size the split and it is strictly worse — which is why verl tells you to tune it against rollouter/idle_ratio vs trainer/idle_ratio.

4. The Data Plane: TransferQueue

In the V1 trainer, batches are not passed around as tensors. They are passed as KVBatchMeta — a list of keys into TransferQueue, a distributed KV store. The trainer's control flow moves metadata; the values live wherever the storage units put them.

Two kinds of record share the store:

Prompt records — key {uid}

One per prompt sampled from the dataset. Its tag carries global_steps — the step at which it was submitted for generation — and a status that tracks the whole GRPO group:

pending  → sessions not yet started
running  → all sessions running
finished → all sessions completed cleanly
failure  → all sessions done, at least one failed
Trajectory records — key {uid}_{session_id}_{index}

session_id ranges over [0, rollout.n) — the GRPO group dimension. The value holds the dataset fields plus the agent-loop output (prompt_ids, response_ids, response_mask, log-probs).

Only groups in a terminal status (finished or failure) are candidates for sampling. This is what makes the group the unit of accounting: GRPO computes a group-relative advantage, so half a group is worthless, and the buffer's eviction logic operates on uids, never on individual trajectories.

The global_steps tag on the prompt record is the timestamp that the entire staleness mechanism reads. Everything in the next section is arithmetic on that one number.

5. The Replay Buffer Is the Staleness Gate

ReplayBuffer.sample() is the trainer's only blocking call, and its async subclass ReplayBufferAsync is where "how stale is too stale" is decided. The loop is:

while True:
    snapshot = sync_metadata_from_transfer_queue()     # one consistent view per pass
    evicted  = evict_terminal_groups(stale | dapo_filtered | failed)
    if evicted:
        refill_fn(len(evicted))                        # submit exactly k replacement prompts
        continue
    if has_enough_samples(sampleable, batch_size):
        select and materialize
        break
    sleep(poll_interval)                               # default 2 s

The staleness predicate

A prompt group's version span is how many weight versions have elapsed between submitting it and consuming it:

Eviction test
\[ \underbrace{s_{\text{now}} - s_{\text{submit}} + 1}_{\text{version span}} \;>\; \texttt{max\_off\_policy\_threshold} \]

\(s\) = global_steps  ·  default threshold = 8  ·  span 1 means on-policy

The +1 matters: a group submitted and consumed at the same step has span 1, not 0. So max_off_policy_threshold: 1 is the on-policy setting, and the shipped default of 8 permits data seven versions old. That is a deliberately loose ceiling — it is a safety valve against unbounded drift, not the mechanism that actually keeps lag small. What keeps lag small is the pool sizing.

Two strategies at the threshold

max_off_policy_strategyBehaviorCost
drop
default		 Evict any terminal group past the threshold and immediately submit k fresh prompts to replace it. An assertion after selection re-verifies that no selected group exceeded the threshold. The compute spent generating those trajectories is thrown away.
wait Dropless. Block sampling entirely while any in-flight prompt has reached the threshold, letting it finish so it can be trained on rather than discarded. The trainer stalls on the slowest straggler — reintroducing exactly the bubble async was meant to remove.

The two options are the classic throughput/sample-efficiency trade, made explicit. drop wastes GPU-hours; wait wastes wall-clock.

The sync path is not a no-op

In sync mode the same buffer runs with staleness checking disabled (all data is on-policy by construction, so max_off_policy_strategy is a NO-OP), but the DAPO dynamic-sampling path is live. A group whose reward metric is identical across all its trajectories carries no gradient signal — every advantage in the group is zero — so it is filtered. The sync policy differs from async:

ModeStaleDAPO-filteredFailed
sync NO-OP Evict k, refill 2k, bounded by max_inflight_gen_batches; then drain in-flight and discard surplus NO-OP, or opt-in refill k via sync_refill_failed_groups
*_async All three the same: evict k, refill k — num_warmup_batches already absorbs the retry cost

The 2k over-refill in sync is speculative: with no buffer to fall back on, the trainer must over-generate to have any chance of assembling a full batch of signal-bearing groups in one pass. Once enough are sampleable it stops dispatching, drains what is running, and discards the surplus. Async mode doesn't need speculation — a warm buffer already holds spares.

DAPO filtering requires the reward at sampling time, so it needs either a rule-based reward or reward.reward_model.enable_resource_pool: true. A colocated reward model computes scores after the buffer has already selected — too late to filter on. See Reward Pipelining.

6. parameter_sync_step and the \(\pi_{old}\) Problem

Look again at step(): it splits one train_batch_size into parameter_sync_step mini-batches and runs the full PPO pipeline on each — including an optimizer step. Weight sync happens once, at on_step_end, after all of them.

separate_async invariant (asserted at construction)
\[ \texttt{train\_batch\_size} = \texttt{parameter\_sync\_step} \times \texttt{ppo\_mini\_batch\_size} \]

So with parameter_sync_step: 4, the actor is updated four times between weight pushes. The rollout engines spend all four holding the weights from before update 1. Raising it amortizes sync cost and lets the rollout pool run longer undisturbed; it also makes the last mini-batch three optimizer steps off-policy relative to the data it trains on.

Which policy is \(\pi_{old}\)?

PPO's ratio \(r_t = \pi_\theta(a_t|s_t)/\pi_{old}(a_t|s_t)\) needs a well-defined denominator. Inside a sync cycle the numerator's weights change every mini-batch, so \(\pi_{old}\) must be pinned — otherwise the ratio silently means something different at trigger step 3 than at trigger step 0. verl offers two answers, and they correspond to the algorithm.rollout_correction preset families:

ModeHow \(\pi_{old}\) is obtainedCost
Bypass
bypass_mode: true
the bypass_* presets		 Use the log-probs the rollout engine already returned. The PPO ratio becomes \(\pi_\theta/\pi_{\text{rollout}}\), which absorbs the off-policy correction directly. _compute_old_log_prob is skipped. Two policies instead of three — a whole forward pass per mini-batch disappears. But \(\pi_{\text{rollout}}\) carries TIM: the inference engine's log-probs differ from the training engine's on identical weights.
Decoupled
bypass_mode: false
the decoupled_* presets		 Recompute with the training engine, pinned to the cycle's starting weights. separate_async overrides _compute_old_log_prob to do this by shuttling weights through host memory: save_model_to_cpu(k) → restore_model_from_cpu(0) → compute → restore_model_from_cpu(k) → clear_cpu_model(k). An extra forward pass plus two full model copies over PCIe per mini-batch, but every mini-batch in the cycle shares one stable \(\pi_{old}\). This is AReaL's Decoupled PPO.

The RolloutCorrectionConfig dataclass defaults to bypass_mode: false, but many of the named presets (bypass_ppo_clip, bypass_pg_is, bypass_pg_geo_rs, …) set it true and pair it with a specific loss and rejection-sampling scheme. Choosing a preset chooses both the \(\pi_{old}\) source and the correction algorithm from §5 of the async page in one line.

7. Partial Rollout: How an Interrupted Sequence Survives

When abort_replicas() fires, every in-flight request on every replica is killed so the GPU can be handed to the trainer. A 6000-token reasoning trace that was 4000 tokens in is now a dead request. Discarding it would waste more compute than the tail wait ever did.

The trick is that the abort is invisible to the agent loop. It is absorbed one layer down, in FullyAsyncLLMServerClient.generate(), which wraps the plain client in a retry loop:

final = TokenOutput(token_ids=[])
while True:
    out = await super().generate(
        prompt_ids   = prompt_ids + final.token_ids,   # ← prompt grows by what we kept
        sampling_params = {..., max_tokens: original - len(final.token_ids)},
    )
    final.token_ids.extend(out.token_ids)
    final.log_probs.extend(out.log_probs)

    if len(final.token_ids) >= original_max_tokens:
        final.stop_reason = "length"; break
    if out.stop_reason not in ("aborted", "abort"):
        break                                          # genuine EOS / length stop
    await asyncio.sleep(1)                             # wait out the weight sync, then resume

So a "resumed" sequence is not really resumed. It is re-submitted as a longer prompt. Three consequences follow, and they are the ones worth internalizing:

  • Tokens survive; the KV cache does not. release_kv_cache() frees it before the weight transfer. The continuation re-prefills all 4000 kept tokens. Partial rollout trades a quadratic-ish prefill re-cost against the tail wait — which is why it pays off precisely when responses are long and the tail is severe.
  • One trajectory can span several weight versions. The client records min_global_steps and max_global_steps in extra_fields. The first 4000 tokens came from \(\pi_{v}\), the rest from \(\pi_{v+1}\) — a single sequence whose log-probs are a concatenation from two different policies. No IS scheme models this exactly; it is an accepted approximation.
  • MoE routing is stitched, not recomputed. On resume the client appends routing information only for the newly generated tokens, deliberately keeping the earlier tokens' routing from the older weights.
The v1 client always retries. The partial_rollout opt-out check reads config.async_training.partial_rollout, a key that exists only in the experimental fully_async_policy config tree (§10). Under the v1 trainer that attribute is absent, so should_retry stays True and aborted samples are always resumed — the code says so in a comment. Partial rollout is therefore not an independent knob in colocate_async/separate_async; it is intrinsic to them.

8. Weight Sync: The Checkpoint Engine

Fresh weights reach the inference engines through CheckpointEngineManager. Actor training workers hold a model engine (FSDP / Megatron / VeOmni) and a checkpoint engine in the same process; rollout replicas hold a checkpoint engine in a separate process from the inference worker, and bridge that gap with CUDA IPC.

update_weights(global_steps):
  1. abort_replicas()             # kill in-flight requests (their tokens are kept — §7)
  2. build a temporary WorkerGroup over all replica workers
  3. release_kv_cache_replicas()  # free KV only; weight buffers stay allocated
  4. build_process_group()        # prepare → build_topology → init_process_group
  5. actor.update_weights() ‖ rollout.update_weights()
  6. finalize()
  7. resume_kv_cache_replicas()
  8. resume_generation_replicas()

Step 3 is the detail that distinguishes this from the naive path. sleep() frees weights and KV cache; release_kv_cache() frees only the cache, leaving the weight buffers in place so the transfer writes directly into them rather than reallocating.

BackendMechanismWhere it's used
naive
default		 Short-circuits the whole sequence — a single actor_wg.update_weights() on the colocated pool. No process group, no abort. Colocated sync training.
nccl Collective over a process group spanning actor and rollout workers. Any cross-pool sync. Required for separate_async, which asserts the backend is not naive.
nixl / mooncake RDMA transfer engines. On Ascend, the HCCL engine registers under the nccl name rather than adding a separate one. Large models, cross-node pools, non-NVIDIA hardware.
delta_sharded Sends only changed parameters, reporting a changed-ratio and wire-payload metric back into the step's logs. When sync cost dominates and updates are sparse (e.g. LoRA).

Sync cost is not negligible at scale, and it is the thing parameter_sync_step exists to amortize. verl's published ablation on the Moonshot checkpoint-engine optimization measures a single Qwen3-235B-A22B sync at 58.6 s without it versus 23.7 s with, and a Qwen3-30B-A3B at 15.8 s versus 4.4 s (Megatron, H20, 64 and 16 ranks respectively) — the difference between a tolerable per-step tax and a dominant one.

separate_async's second pool

separate_async is the only mode running two rollout populations at once, and the bookkeeping is worth spelling out:

  • A standalone LLMServerManager on the dedicated rollout.nnodes × rollout.n_gpus_per_node GPUs, created at start_rank past the hybrid replicas, with its own CheckpointEngineManager. This pool is the one that runs continuously.
  • The hybrid replicas on the trainer's own GPUs, which flip between ROLLOUT and TRAINER mode. Switching to trainer removes them from the standalone pool's GlobalRequestLoadBalancer; switching back re-adds them. Requests keep flowing to the standalone servers throughout.
  • _get_n_gpus_for_throughput() is overridden to add the standalone GPUs into the denominator — otherwise the reported throughput silently ignores half the cluster.
The idle-time reclamation this design implies is not yet active: should_switch_to_rollout() currently returns False unconditionally, with a TODO to implement a strategy based on buffer depth and switch overhead. In practice the hybrid engine drops to TRAINER mode after the first sample and only returns to ROLLOUT for validation. Read the mode-flipping machinery as scaffolding for elastic placement rather than a live optimization.

10. Lineage, and a Naming Warning

verl's async support arrived in three waves, and all three are still present in the tree. This matters because they use different config names for the same ideas, and most writing about "async verl" — including §7 of the async page — describes the middle one.

GenerationLocationIts knobs
one_step_off_policy
Jul 2025		 verl/experimental/one_step_off_policy/ None to speak of — the lag is hard-wired at exactly one step. Dedicated rollout resources, remainder to training.
fully_async_policy
2026, from Meituan		 verl/experimental/fully_async_policy/ — separate Rollouter, MessageQueue, Trainer, ParameterSynchronizer, plus a dynamic_schedule/ resource controller async_training.staleness_threshold, async_training.trigger_parameter_sync_step, async_training.require_batches, async_training.partial_rollout
V1 trainer modes
current mainline		 verl/trainer/ppo/v1/ — everything in §2–§8 above trainer.v1.trainer_mode, trainer.v1.sampler.max_off_policy_threshold, trainer.v1.separate_async.parameter_sync_step
Translation table. If you have read the fully_async docs, the mapping into mainline is: trigger_parameter_sync_step → parameter_sync_step; staleness_threshold → max_off_policy_threshold (and the semantics changed — the old one is a fraction of a batch's worth of surplus samples, typically 0–1; the new one is an integer count of weight versions, default 8); partial_rollout: true → implied by choosing an async mode. Setting async_training.* keys on a V1 run does nothing.

The fully_async_policy line remains worth reading for two things the V1 modes don't yet have: streaming production, where the transfer unit is a single sample rather than a batch (require_batches controls how much the trainer accumulates before updating), and the dynamic_schedule controller that reallocates GPUs between rollout and training mid-run. Its reported results — 2.35–2.67× over colocated sync on Qwen2.5-Math-7B at 32/64/128 GPUs, with a staleness ablation showing most of the gain arriving by staleness_threshold ≈ 0.3 — are the best published evidence for how much async is worth in verl specifically.

The one-paragraph mental model

Prompts are submitted, never awaited: _add_batch_to_generate() writes them into TransferQueue and returns. Agent loops drive one server request per trajectory and write completed sequences back. The trainer's only blocking call is replay_buffer.sample(), which polls the queue, evicts groups whose version span exceeds max_off_policy_threshold, refills the hole, and releases a batch once enough terminal groups exist. trainer_mode then decides what happens to the rollout engines while that batch trains — sync sleeps them, colocate_async aborts and sleeps them, separate_async leaves a whole separate pool running. Aborted sequences are not lost: the client re-submits them as prompt + tokens_so_far once weights land. Weights land via the checkpoint engine, once per parameter_sync_step local updates.
