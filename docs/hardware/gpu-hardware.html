GPU Hardware: Inside the Chip

What one training GPU actually exposes — the SIMT execution model (warps, occupancy, latency hiding), the SM with its Tensor Cores and managed scratchpad, the memory hierarchy from registers to HBM, the copy engines behind software pipelining, and the roofline that decides whether a kernel is compute- or memory-bound. Built on the H100, the running example for the whole series.

All the math in this series — every matmul FLOP, every collective’s \(V/W\) cost — ultimately runs on silicon with fixed throughputs. This page is the first of three on that hardware substrate, and it stays inside one chip: what a modern training GPU (we use the NVIDIA H100 SXM5 as the running example) can compute, and how fast each level of memory can feed that compute. Three numbers per level, and almost every performance question reduces to comparing two of them. The story continues off-chip in GPU Interconnect — NVLink, NVSwitch, and the scale-out network — and across parts in GPU Generations: Blackwell, the H100 → B300 lineup, and B300 vs. GB300.

1 · The mental model: compute fed by a bandwidth pyramid

A GPU is an enormous amount of arithmetic throughput attached to a steep hierarchy of memories. The arithmetic is cheap and abundant; the hard part is keeping it fed. Each level up the hierarchy is smaller but far faster, each level down is larger but slower:

  • Compute: 132 streaming multiprocessors (SMs), each running thousands of threads (grouped into warps) and holding Tensor Cores that do the matmuls.
  • On-chip memory: per-SM registers and shared memory — a programmer-managed scratchpad — then a 50 MB L2 shared by all SMs; tens of TB/s, but kilobytes-to-megabytes in size.
  • HBM: 80 GB of high-bandwidth memory at 3.35 TB/s — where the weights, activations, and optimizer state live.
  • NVLink: 900 GB/s to the other 7 GPUs in the node, through an NVSwitch crossbar.
  • Network: ~50 GB/s per GPU across nodes, over InfiniBand or Ethernet.

Performance work is almost always about which level is the bottleneck. A kernel that re-reads HBM is HBM-bound; a tensor-parallel layer is NVLink-bound; a data-parallel cluster is network-bound. This page makes the on-package levels concrete — compute down through HBM; the bottom rungs of the ladder are GPU Interconnect’s subject.

2 · The execution model: SIMT, warps, occupancy

Before the bandwidths mean anything, you need to know how code runs on an SM. A GPU kernel launches a grid of thread blocks; each block is placed on one SM and run as groups of 32 threads called a warp. The 32 threads of a warp execute the same instruction in lockstep, each on its own data — NVIDIA calls this SIMT (single instruction, multiple threads). An H100 SM has 4 warp-scheduler partitions, each issuing one instruction from one ready warp per cycle.

The hierarchy of execution
thread  →  warp (32 threads, lockstep)  →  thread block (on one SM)  →  grid (the whole kernel)

The defining trick of a GPU is latency hiding. A single warp stalls constantly — every HBM load takes hundreds of cycles. Instead of waiting, the SM keeps many warps resident and, whenever one stalls on memory, the scheduler instantly switches to another that is ready. With enough warps in flight, the Tensor Cores and ALUs never idle even though every individual memory access is slow. The fraction of the SM’s warp capacity you actually use (up to 64 warps/SM on Hopper) is called occupancy.

Foundation for kernel optimization → occupancy is the knob that hides HBM latency. Too few warps (often from using too many registers or too much shared memory per block) leaves the SM stalling on memory with no other work to switch to — the “low-occupancy” trap. This is why kernels budget registers and shared memory carefully.
SM utilization ≠ Tensor-Core active. These are two distinct profiler metrics that measure different levels of the hierarchy — and confusing them is the most common misread of GPU profiling output.
  • SM utilization (sm__active_cycles) — fraction of elapsed cycles where the SM has at least one active warp. The SM is “active” even if every warp inside it is stalled waiting for HBM.
  • Tensor-Core active (sm__pipe_tensor_op_hmma_cycles_active) — fraction of cycles where the tensor-core pipeline is actually issuing a matrix-multiply instruction.

During decode on an H100, SM utilization is typically 20–40% (warps are scheduled), but tensor-core active is 5–12% (those warps are mostly stalled on HBM reads, not computing). The gap between the two is the fraction of SM-active time spent waiting for memory — which is the definition of memory-bound.

Warp stall types (visible in Nsight Compute as “warp stall reasons”) tell you why a warp is not issuing:

  • Memory pipe stall — warp is waiting for an HBM or L2 load to return. Dominant during decode; the KV cache and weight reads are what trigger these.
  • Instruction dependency stall — warp is waiting for a prior arithmetic result before it can issue the next instruction. More common during prefill, where large matmuls generate long chains of dependent tile accumulations.
Both phases show ~75% stalled cycles overall (paper: prefill 27% active cycles, decode 24%), but for different reasons — memory waits in decode, compute dependencies in prefill.

3 · Inside an SM: cores, Tensor Cores, and the register file

Each of the 132 SMs is a small independent processor. Splitting it into its four scheduler partitions, one SM holds:

General CUDA-core arithmetic — the elementwise ops, norms, softmaxes — runs at a few tens of TFLOP/s. The headline 989 TFLOP/s bf16 comes entirely from the Tensor Cores: dedicated matrix-multiply-accumulate (MMA) units that, each instruction, multiply a small matrix tile (e.g. \(16\times8\times16\)) and add it into a running accumulator. They take bf16/fp16/fp8/tf32 inputs and accumulate in fp32, and they read their operands from registers and shared memory — never directly from HBM. (A thread’s slice of an operand or accumulator tile, staged in its registers, is what CUDA’s wmma API and CUTLASS/CuTe call a fragment.) They are why we build architectures out of big matmuls: that is the one operation the hardware does at full rate.

Precision matters: peak roughly doubles each time you halve the bits. The H100 does ~989 TFLOP/s at bf16/fp16 and ~1,979 TFLOP/s at fp8 (dense). “With sparsity” marketing numbers double these again but rarely apply to training. Throughout this series we quote dense bf16.
Foundation for kernel optimization → because the Tensor Cores are fed from registers/shared memory, a matmul kernel’s whole job is to stream operand tiles into them without stalling. That is what “tiling” means, and why a matmul \([B,D]\times[D,F]\) (cost \(2BDF\) FLOPs) can run near peak while an elementwise op over the same data (cost \(O(BD)\)) cannot — the mismatch the roofline makes precise.

4 · The memory hierarchy

Every level the data has to travel through has a capacity and a bandwidth, and they trade off against each other across ~6 orders of magnitude. The diagram shows the H100’s levels to scale (log bandwidth):

▸ The bandwidth ladder (H100, log scale)
Each rung down is bigger but slower. The parallelism math lives on the bottom three.

The two boundaries that hurt are the orange jumps: leaving the chip for HBM (the memory wall), and leaving the node for the network (the communication wall). On-chip bandwidth is so high that, once data is resident, arithmetic is essentially free.

The crucial part: the top two levels are yours to manage

Unlike a CPU, where caches are transparent and automatic, a GPU’s registers and shared memory are explicitly programmer-managed. Registers hold each thread’s private working set. Shared memory is a scratchpad you allocate per block and fill by hand — it is the same SRAM as L1, carved out under your control — so a kernel decides exactly which slice of data lives on-chip and gets reused. L2 and HBM are managed for you; registers and shared memory are not.

Foundation for kernel optimization → this scratchpad is the lever. “Tiling” means staging a block of operands in shared memory and reusing it many times before writing back; “fusion” means keeping an intermediate in registers/SMEM instead of round-tripping it through HBM. Both are just choices about what lives in these two levels — and both move an op rightward on the roofline.

5 · Data movement: async copy and TMA

Getting operands from HBM into that scratchpad fast — and without stalling the math — is its own hardware story. Two engines matter:

  • cp.async (Ampere+): an asynchronous global→shared copy that bypasses the register file. A thread issues the load and keeps computing instead of blocking until the data lands.
  • TMA — Tensor Memory Accelerator (Hopper): a dedicated copy engine that moves whole multi-dimensional tiles between HBM and shared memory with the address arithmetic done in hardware. A single thread kicks off a bulk transfer and the SM’s threads are freed entirely for compute.
Foundation for kernel optimization → these are the hardware behind software pipelining: while the Tensor Cores chew on tile \(k\), TMA is already streaming tile \(k{+}1\) into a second shared-memory buffer, so compute and memory overlap and neither waits. A multi-stage pipeline like this is how a well-written matmul or fused kernel stays compute-bound.

6 · The roofline: compute-bound vs memory-bound

Whether a kernel is limited by the Tensor Cores or by HBM is settled by one ratio — its arithmetic intensity, the FLOPs it performs per byte it reads from / writes to HBM:

Arithmetic intensity
\[ I \;=\; \frac{\text{FLOPs}}{\text{bytes moved to/from HBM}} \quad\text{(FLOP/byte)} \]

The achievable throughput is the smaller of the two ceilings: you can never exceed peak FLOPs, and you can never go faster than HBM can feed you (\(I\times\) bandwidth):

\[ \text{achievable FLOP/s} \;=\; \min\big(\underbrace{P_\text{peak}}_{989\ \text{TFLOP/s}},\; \underbrace{I \times W_\text{HBM}}_{I\,\times\,3.35\ \text{TB/s}}\big). \]

The two ceilings cross at the ridge point \(I^\star = P_\text{peak}/W_\text{HBM} = 989/3.35 \approx 295\) FLOP/byte. Below it you are memory-bound (add arithmetic intensity for free speedup); above it you are compute-bound (saturating the Tensor Cores). Drag the slider to see where common operations land:

The same logic governs communication, with HBM bandwidth swapped for link bandwidth: a collective or a parallel layer is “compute-bound” (good — comm hides under the matmul) only when it does enough FLOPs per byte sent. Tensor parallelism works precisely because its AllReduce moves \(O(BTD)\) bytes against \(O(BTDF)\) FLOPs — a high arithmetic intensity over the network.
The roofline grades one kernel; MFU — Model FLOPs Utilization → is the same verdict for an entire training run: count the model’s FLOPs per token (6N + the attention term), multiply by measured tokens/sec, and divide by this page’s \(P_\text{peak}\).

7 · Summary

Execution model

Threads run in warps of 32 (SIMT) on SMs; many resident warps hide HBM latency. Occupancy is that knob.

Tensor Cores

Do matmuls at ~989 TFLOP/s bf16 (fp32 accumulate) — fed from registers/SMEM, so peak needs tiling to keep them fed.

Managed scratchpad

Registers + shared memory are programmer-managed, not caches. Tiling/fusion are choices about what lives there.

Async data movement

cp.async / TMA stream tiles HBM→SMEM while the cores compute — the hardware behind software pipelining.

Memory wall

HBM is 80 GB at 3.35 TB/s — orders of magnitude slower than on-chip SRAM. Keep tiles resident; fuse.

Roofline

Ridge at ~295 FLOP/byte. Below it = memory-bound (fuse for free speedup); above = compute-bound.
