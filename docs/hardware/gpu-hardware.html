GPU Hardware for ML

The compute, memory, and interconnect a training GPU actually exposes — peak FLOPs, the bandwidth hierarchy from registers to HBM to NVLink to the network, and the roofline that decides whether your kernel is compute- or memory-bound. The physical basis for every parallelism and collective cost — built on the H100, then carried across the lineup (H200, B200, B300) and the Blackwell changes that move each constraint.

All the math in this series — every matmul FLOP, every collective’s \(V/W\) cost — ultimately runs on silicon with fixed throughputs. This page is the hardware substrate: what a modern training GPU (we use the NVIDIA H100 SXM5 as the running example) can compute, how fast it can feed that compute from each level of memory, and how fast it can talk to other GPUs. Three numbers per level, and almost every performance question reduces to comparing two of them. The last two sections carry the same mental model onto Blackwell, compare the H100 / H200 / B200 / B300 SKUs you’ll actually be scheduled on, and split the B300-vs-GB300 decision — the same chip in two very different machines.

1 · The mental model: compute fed by a bandwidth pyramid

A GPU is an enormous amount of arithmetic throughput attached to a steep hierarchy of memories. The arithmetic is cheap and abundant; the hard part is keeping it fed. Each level up the hierarchy is smaller but far faster, each level down is larger but slower:

  • Compute: 132 streaming multiprocessors (SMs), each running thousands of threads (grouped into warps) and holding Tensor Cores that do the matmuls.
  • On-chip memory: per-SM registers and shared memory — a programmer-managed scratchpad — then a 50 MB L2 shared by all SMs; tens of TB/s, but kilobytes-to-megabytes in size.
  • HBM: 80 GB of high-bandwidth memory at 3.35 TB/s — where the weights, activations, and optimizer state live.
  • NVLink: 900 GB/s to the other 7 GPUs in the node, through an NVSwitch crossbar.
  • Network: ~50 GB/s per GPU across nodes, over InfiniBand or Ethernet.

Performance work is almost always about which level is the bottleneck. A kernel that re-reads HBM is HBM-bound; a tensor-parallel layer is NVLink-bound; a data-parallel cluster is network-bound. The rest of this page makes each level concrete.

2 · The execution model: SIMT, warps, occupancy

Before the bandwidths mean anything, you need to know how code runs on an SM. A GPU kernel launches a grid of thread blocks; each block is placed on one SM and run as groups of 32 threads called a warp. The 32 threads of a warp execute the same instruction in lockstep, each on its own data — NVIDIA calls this SIMT (single instruction, multiple threads). An H100 SM has 4 warp-scheduler partitions, each issuing one instruction from one ready warp per cycle.

The hierarchy of execution
thread  →  warp (32 threads, lockstep)  →  thread block (on one SM)  →  grid (the whole kernel)

The defining trick of a GPU is latency hiding. A single warp stalls constantly — every HBM load takes hundreds of cycles. Instead of waiting, the SM keeps many warps resident and, whenever one stalls on memory, the scheduler instantly switches to another that is ready. With enough warps in flight, the Tensor Cores and ALUs never idle even though every individual memory access is slow. The fraction of the SM’s warp capacity you actually use (up to 64 warps/SM on Hopper) is called occupancy.

Foundation for kernel optimization → occupancy is the knob that hides HBM latency. Too few warps (often from using too many registers or too much shared memory per block) leaves the SM stalling on memory with no other work to switch to — the “low-occupancy” trap. This is why kernels budget registers and shared memory carefully.
SM utilization ≠ Tensor-Core active. These are two distinct profiler metrics that measure different levels of the hierarchy — and confusing them is the most common misread of GPU profiling output.
  • SM utilization (sm__active_cycles) — fraction of elapsed cycles where the SM has at least one active warp. The SM is “active” even if every warp inside it is stalled waiting for HBM.
  • Tensor-Core active (sm__pipe_tensor_op_hmma_cycles_active) — fraction of cycles where the tensor-core pipeline is actually issuing a matrix-multiply instruction.

During decode on an H100, SM utilization is typically 20–40% (warps are scheduled), but tensor-core active is 5–12% (those warps are mostly stalled on HBM reads, not computing). The gap between the two is the fraction of SM-active time spent waiting for memory — which is the definition of memory-bound.

Warp stall types (visible in Nsight Compute as “warp stall reasons”) tell you why a warp is not issuing:

  • Memory pipe stall — warp is waiting for an HBM or L2 load to return. Dominant during decode; the KV cache and weight reads are what trigger these.
  • Instruction dependency stall — warp is waiting for a prior arithmetic result before it can issue the next instruction. More common during prefill, where large matmuls generate long chains of dependent tile accumulations.
Both phases show ~75% stalled cycles overall (paper: prefill 27% active cycles, decode 24%), but for different reasons — memory waits in decode, compute dependencies in prefill.

3 · Inside an SM: cores, Tensor Cores, and the register file

Each of the 132 SMs is a small independent processor. Splitting it into its four scheduler partitions, one SM holds:

General CUDA-core arithmetic — the elementwise ops, norms, softmaxes — runs at a few tens of TFLOP/s. The headline 989 TFLOP/s bf16 comes entirely from the Tensor Cores: dedicated matrix-multiply-accumulate (MMA) units that, each instruction, multiply a small matrix tile (e.g. \(16\times8\times16\)) and add it into a running accumulator. They take bf16/fp16/fp8/tf32 inputs and accumulate in fp32, and they read their operands from registers and shared memory — never directly from HBM. (A thread’s slice of an operand or accumulator tile, staged in its registers, is what CUDA’s wmma API and CUTLASS/CuTe call a fragment.) They are why we build architectures out of big matmuls: that is the one operation the hardware does at full rate.

Precision matters: peak roughly doubles each time you halve the bits. The H100 does ~989 TFLOP/s at bf16/fp16 and ~1,979 TFLOP/s at fp8 (dense). “With sparsity” marketing numbers double these again but rarely apply to training. Throughout this series we quote dense bf16.
Foundation for kernel optimization → because the Tensor Cores are fed from registers/shared memory, a matmul kernel’s whole job is to stream operand tiles into them without stalling. That is what “tiling” means, and why a matmul \([B,D]\times[D,F]\) (cost \(2BDF\) FLOPs) can run near peak while an elementwise op over the same data (cost \(O(BD)\)) cannot — the mismatch the roofline makes precise.

4 · The memory hierarchy

Every level the data has to travel through has a capacity and a bandwidth, and they trade off against each other across ~6 orders of magnitude. The diagram shows the H100’s levels to scale (log bandwidth):

▸ The bandwidth ladder (H100, log scale)
Each rung down is bigger but slower. The parallelism math lives on the bottom three.

The two boundaries that hurt are the orange jumps: leaving the chip for HBM (the memory wall), and leaving the node for the network (the communication wall). On-chip bandwidth is so high that, once data is resident, arithmetic is essentially free.

The crucial part: the top two levels are yours to manage

Unlike a CPU, where caches are transparent and automatic, a GPU’s registers and shared memory are explicitly programmer-managed. Registers hold each thread’s private working set. Shared memory is a scratchpad you allocate per block and fill by hand — it is the same SRAM as L1, carved out under your control — so a kernel decides exactly which slice of data lives on-chip and gets reused. L2 and HBM are managed for you; registers and shared memory are not.

Foundation for kernel optimization → this scratchpad is the lever. “Tiling” means staging a block of operands in shared memory and reusing it many times before writing back; “fusion” means keeping an intermediate in registers/SMEM instead of round-tripping it through HBM. Both are just choices about what lives in these two levels — and both move an op rightward on the roofline.

5 · Data movement: async copy and TMA

Getting operands from HBM into that scratchpad fast — and without stalling the math — is its own hardware story. Two engines matter:

  • cp.async (Ampere+): an asynchronous global→shared copy that bypasses the register file. A thread issues the load and keeps computing instead of blocking until the data lands.
  • TMA — Tensor Memory Accelerator (Hopper): a dedicated copy engine that moves whole multi-dimensional tiles between HBM and shared memory with the address arithmetic done in hardware. A single thread kicks off a bulk transfer and the SM’s threads are freed entirely for compute.
Foundation for kernel optimization → these are the hardware behind software pipelining: while the Tensor Cores chew on tile \(k\), TMA is already streaming tile \(k{+}1\) into a second shared-memory buffer, so compute and memory overlap and neither waits. A multi-stage pipeline like this is how a well-written matmul or fused kernel stays compute-bound.

6 · The roofline: compute-bound vs memory-bound

Whether a kernel is limited by the Tensor Cores or by HBM is settled by one ratio — its arithmetic intensity, the FLOPs it performs per byte it reads from / writes to HBM:

Arithmetic intensity
\[ I \;=\; \frac{\text{FLOPs}}{\text{bytes moved to/from HBM}} \quad\text{(FLOP/byte)} \]

The achievable throughput is the smaller of the two ceilings: you can never exceed peak FLOPs, and you can never go faster than HBM can feed you (\(I\times\) bandwidth):

\[ \text{achievable FLOP/s} \;=\; \min\big(\underbrace{P_\text{peak}}_{989\ \text{TFLOP/s}},\; \underbrace{I \times W_\text{HBM}}_{I\,\times\,3.35\ \text{TB/s}}\big). \]

The two ceilings cross at the ridge point \(I^\star = P_\text{peak}/W_\text{HBM} = 989/3.35 \approx 295\) FLOP/byte. Below it you are memory-bound (add arithmetic intensity for free speedup); above it you are compute-bound (saturating the Tensor Cores). Drag the slider to see where common operations land:

▸ Roofline explorer (H100, bf16)
Arithmetic intensity → achievable throughput. The ridge is at ~295 FLOP/byte.

OperationArithmetic intensityBound by

The same logic governs communication, with HBM bandwidth swapped for link bandwidth: a collective or a parallel layer is “compute-bound” (good — comm hides under the matmul) only when it does enough FLOPs per byte sent. Tensor parallelism works precisely because its AllReduce moves \(O(BTD)\) bytes against \(O(BTDF)\) FLOPs — a high arithmetic intensity over the network.
The roofline grades one kernel; MFU — Model FLOPs Utilization → is the same verdict for an entire training run: count the model’s FLOPs per token (6N + the attention term), multiply by measured tokens/sec, and divide by this page’s \(P_\text{peak}\).

7 · Inside a node: NVLink and the NVSwitch crossbar

Eight H100s in a server (an HGX/DGX baseboard) are wired together not by a ring or a mesh but by a set of NVSwitch chips that form a non-blocking all-to-all crossbar. Each GPU has 18 NVLink-4 links (each ~50 GB/s, a few 100 Gbps lanes), totalling 900 GB/s bidirectional (≈450 GB/s each way) into the switch fabric, and — crucially — every GPU can drive that full bandwidth to every other GPU at the same time. There is no shared bottleneck and no notion of “distance” between GPUs in a node. Those 18 links are not one fat pipe: they fan out across the 4 NVSwitches, which is exactly what lets the fabric stay non-blocking — and they set the ceiling on how many parallel NCCL channels can run at once.

▸ An 8-GPU node: every GPU reaches every other at full bandwidth
NVSwitch is a crossbar, not a ring — there are no nearest neighbors.

This is the single most important fact for tensor parallelism: a TP group can shard a layer across these 8 GPUs and pay only the NVLink-speed AllReduce, with no penalty for which GPU talks to which. But “non-blocking crossbar” is doing a lot of work in that sentence — it’s worth unpacking.

What “crossbar” actually means

A crossbar is the simplest fabric that connects every input to every output. The mental model is a literal grid: inputs run horizontally, outputs run vertically, and at each intersection sits a switch (a crosspoint). To connect input \(i\) to output \(j\), you close crosspoint \((i,j)\). Two properties make it the gold standard:

  • Any-to-any, one hop. There is no notion of “neighbor” or “distance” — every pair is directly reachable. (Contrast a ring/torus, where reaching a far node costs multiple hops.)
  • Non-blocking. All \(N\) inputs can be connected to \(N\) outputs at once — any permutation — each at full link rate, because no two connections share any wire in the middle.

The only limit is at the endpoints: two inputs can’t both drive one output at full rate (an output-port conflict). So the fabric never blocks — but a single GPU’s own link bandwidth still caps how much can flow into it. Drag a new permutation and notice all four paths stay full-rate simultaneously:

▸ A 4×4 crossbar — any permutation, all at full rate
Inputs → rows, outputs → columns. Filled dots = closed crosspoints. No two paths share a wire.
Each input reaches a distinct output — 4 simultaneous full-rate connections.

How NVSwitch really builds one

NVSwitch is not a grid of analog crosspoints flipping on and off. Since 2018, NVLink has been a packet-switched fabric, so an NVSwitch chip is a small high-speed router that behaves like a non-blocking crossbar. Inside one chip: input ports buffer arriving NVLink packets (using virtual output queues — a queue per destination — to avoid head-of-line blocking); an arbiter solves a bipartite matching each cycle to decide which inputs cross to which outputs; the crossbar datapath carries that permutation; and packets are routed by physical address (a host-side fabric manager programs the tables). The “closing of crosspoints” is done in logic, every cycle.

NVSwitch (gen 3, H100)Value
NVLink-4 ports per chip64 (non-blocking)
Bidirectional bandwidth / chip3.2 TB/s
Chips per 8-GPU baseboard4 — each H100’s 18 links fan out across all four
In-switch compute (SHARP)embedded ALU, ~400 GFLOP/s — sums + multicasts data

That last row is the hardware behind NVLS: because the switch has an ALU, it can sum data from many GPUs and multicast the result — so an AllReduce can be done in the switch instead of circulating partial sums around a ring.

Why the crossbar stops at the node

A crossbar costs \(O(N^2)\) crosspoints, so you cannot build a 10,000-port one — the silicon and wiring blow up. The universal fix is to compose small crossbars into a near-non-blocking fat-tree (Clos network), trading a little blocking and \(O(\log N)\) hops for \(O(N\log N)\) cost. Crossbars are the atom at every tier: one node is a single crossbar (NVSwitch); the InfiniBand network in §8 is a fat-tree of crossbar switch chips. Stepping from one crossbar to a fat-tree of them is exactly the bandwidth cliff at the node boundary — and the reason tensor parallelism is capped at one node.

8 · Across nodes: the scale-out network

A GPU lives in two networks, and “going across nodes” means dropping from the first to the second:

  • Scale-up — the NVLink domain: the fast, non-blocking NVSwitch crossbar. On a classic HGX H100 node that’s 8 GPUs; on a GB200 NVL72 rack it’s 72 GPUs. No cliff inside this domain — it’s all ~450 GB/s/GPU.
  • Scale-out — the data-center fabric (InfiniBand or Ethernet) connecting NVLink domains to each other. This is the slow tier, ~50 GB/s/GPU.

So the boundary that matters isn’t literally “the node” — it’s the edge of the NVLink domain. Cross it and you’re on the scale-out network, built from three things:

  • One NIC per GPU. A DGX H100 has 8 ConnectX-7 adapters at 400 Gb/s (≈50 GB/s), one dedicated to each GPU (plus separate NICs for storage). The 1-NIC-per-GPU ratio holds on NVL72 too.
  • GPU and its NIC under the same PCIe switch, so the GPU reaches the wire without crossing the CPU.
  • A fabric of switches wiring the NICs together (next).

The data path, and why GPUDirect RDMA matters

A transfer from GPU A on one node to GPU B on another follows:

GPU A HBM → PCIe switch → NIC A → optics → leaf switch → [spine] → leaf switch → NIC B → PCIe switch → GPU B HBM

What makes this fast is GPUDirect RDMA: the NIC reads and writes GPU HBM directly over PCIe, bypassing the CPU and host memory entirely. NIC B performs a remote DMA straight into GPU B’s HBM — no CPU copy, no staging in system RAM. Without it, every inter-node byte would detour through the CPU and the effective bandwidth would collapse. (The GPU↔NIC PCIe Gen5 ×16 link is ~64 GB/s, which is why a 50 GB/s NIC fits comfortably under it.)

The topology: a rail-optimized fat-tree

The switches form a fat-tree (Clos network) — the same crossbars-of-crossbars from §7: each switch (e.g. an NVIDIA Quantum-2, 64×400 Gb/s) is a crossbar, composed into a near-non-blocking tree with full bisection bandwidth. Nodes attach to leaf switches; leaves connect through spine switches; the largest clusters add a third core tier.

The GPU-specific twist is rail optimization: with 8 GPUs/8 NICs per node, NIC \(i\) of every node connects to the same “rail” (leaf switch \(i\)) — so there are 8 parallel rails. GPU \(i\) on any node reaches GPU \(i\) on any other node by staying on its rail — one leaf-switch hop, never touching the contended spine. NCCL leans on this: it structures collectives so same-rank GPUs talk on their own rail. Cross-rail traffic either climbs to the spine, or first hops over NVLink inside the node to the GPU on the right rail — combining both networks.

▸ Rail-optimized fat-tree (2 nodes, 4 rails)
GPU i → NIC i → rail i. Same-rail = 1 hop (green); cross-rail climbs to the spine (dashed).

InfiniBand vs Ethernet

Two transport flavors carry this: InfiniBand (NVIDIA Quantum) — lossless, RDMA-native, hardware congestion control, and the default in most large training clusters; its switches can even do in-network reduction (SHARP → NCCL’s CollNet, the InfiniBand analogue of NVLS). And RoCE / Ethernet (RDMA over Converged Ethernet; NVIDIA Spectrum-X) — RDMA over Ethernet, needing careful PFC/ECN tuning to stay lossless, favored by some hyperscalers. Either way the transport is RDMA: the point is to move GPU memory to GPU memory without the CPUs in the loop.

The cliff at the NVLink-domain boundary
NVLink ~450 GB/s → network ~50 GB/s   ≈   ~9–10× less bandwidth per GPU

Everything about multi-node parallelism is organized around hiding this drop. The collectives that must cross it — the gradient AllReduce of data parallelism, the activation sends of pipeline parallelism — are chosen either to be rare (once per step) or to overlap with compute, so the slow fabric is never on the exposed critical path. The chatty, per-layer collectives stay inside the NVLink domain. And the modern trend — NVL72 growing that domain from 8 to 72 GPUs — is precisely about moving this cliff outward so more of your parallelism enjoys scale-up bandwidth.

10 · Blackwell: what changed from Hopper

Everything above uses the H100 as the running example. Its successor, Blackwell — shipping as the B200 (2024) and the B300 / “Blackwell Ultra” (2025) — keeps the exact mental model of this page (compute fed by a bandwidth pyramid) but relaxes three constraints the rest of these notes treat as fixed on the H100. Each lever pulls on a number you now know how to reason about.

10.1 · The dual-die “one GPU” and HBM3e capacity

A single die is capped by the reticle limit — the largest pattern a lithography stepper can print, and Hopper was already near it. Blackwell sidesteps the wall by putting two reticle-sized dies in one package, joined by the NV-HBI interconnect at 10 TB/s die-to-die, and exposing them to software as a single CUDA device with one unified memory space. You program one GPU; the runtime keeps the dies coherent.

That 10 TB/s link is what makes the abstraction hold: it is roughly 5–6× the per-GPU NVLink bandwidth and over an order of magnitude above the network, so cross-die traffic is cheap enough to hide. On the bandwidth ladder from §4 it slots in just below on-die SRAM, at the very top of the pyramid.

Why the capacity bump matters
192 GB (B200) / 288 GB (B300) of HBM3e vs. 80 GB on H100 — 2.4–3.6× the on-package memory.

Capacity is the quietly decisive number. It sets the KV-cache budget (longer context and bigger batches before you spill) and shrinks the GPU count needed to hold a model’s weights — which in turn shrinks the parallelism degrees you need (fewer GPUs, less collective traffic). The bandwidth bump, ~8 TB/s vs. 3.35 TB/s, lifts the memory roof that decode lives under (§6).

10.2 · FP4 & microscaling — the inference headline

The 2nd-generation Transformer Engine adds FP4 (and FP6) next to Hopper’s FP8. Four bits buys huge bandwidth and math savings — but a raw 4-bit float (E2M1: 1 sign, 2 exponent, 1 mantissa) has only 16 levels and almost no dynamic range, so naïve FP4 destroys accuracy. The fix is microscaling: split a tensor into small contiguous blocks and give each block its own scale factor, so the limited 4-bit range is re-centered on the local magnitude.

FormatElementBlockPer-block scaleNote
MXFP4 (OCP)E2M1 (4-bit)32 valuesE8M0 (power-of-two)open standard, coarse scale
NVFP4 (NVIDIA)E2M1 (4-bit)16 valuesFP8 E4M3 + per-tensor FP32finer blocks + higher-precision scale ⇒ better accuracy

The payoff splits along the same roofline the rest of this page is built on:

  • Decode is memory-bandwidth-bound. Halving bytes per weight vs. FP8 roughly doubles the throughput — you stream half the bytes per generated token.
  • Prefill and training matmuls are compute-bound. Blackwell’s FP4 Tensor Cores deliver on the order of 2× the FP8 math throughput — a higher compute ceiling.
FP4 ceiling (~2×) BF16 ceiling

FP4 raises the compute roof on the same HBM bandwidth diagonal. Same axes as §6: x = arithmetic intensity (FLOP/byte), y = achievable throughput (normalized). At decode-level intensity (far left) both curves sit on the shared diagonal — there FP4’s win is moving fewer bytes per token, not more FLOP/s. The raised ceiling pays off for the compute-bound matmuls on the right (prefill, training). FP8 sits between the two lines.

FP4 is not free accuracy. Activation outliers and sensitive layers (e.g. the LM head, some attention projections) are usually kept at FP8/BF16, and quality depends on calibration and block granularity. The numerics — how the block scales are chosen and why NVFP4 beats INT4 — live on the Quantization page; for a clear visual walkthrough of microscaling, see this video.

10.3 · NVL72 — the rack as one NVLink domain

5th-generation NVLink doubles per-GPU bandwidth to 1.8 TB/s. The structural change is what it enables: in a GB200 / GB300 NVL72 rack, NVLink Switch trays wire 72 GPUs into a single, all-to-all NVLink domain (~130 TB/s aggregate) — every GPU talks to every other at NVLink speed, not just the 8 in a box. It is the same non-blocking crossbar from §7, scaled from one baseboard to a whole rack. Note the 72-GPU domain is a property of the Grace-based rack product, not of the chip: the same B200/B300 on an HGX baseboard still lives in an 8-GPU domain (§11.3).

That moves the cliff from §8 outward. On H100 the NVLink domain is the node — about 8 GPUs — so AllReduce-heavy tensor parallelism stops at one node and collectives fall off a bandwidth cliff past it. NVL72 raises that boundary from 8 to 72.

What a 72-GPU NVLink domain unlocks
  • Tensor parallelism past 8. TP can run 16- or 32-way on NVLink before the exposed AllReduce forces you onto a slower axis — the TP↔PP transition moves out.
  • Expert parallelism for a whole MoE. A large model’s experts can sit inside one NVLink domain, so the AlltoAll dispatch stays on NVLink instead of crossing the network — often what makes wide-EP serving practical.
  • Fewer, bigger collectives. More of the parallelism plan fits on the fast fabric, so the cross-node network carries less of the critical path.
Re-read Tensor Parallelism §6 “Why TP stops at one node” with NVL72 in mind: the math is unchanged, but “one node” is now up to 72 GPUs, not 8.

11.1 · H200 = H100 with a bigger memory roof

The H100→H200 step is the cleanest illustration on this page that the memory wall, not FLOPs, gates inference. H200 is the same GH100 die with the same Tensor Cores — 989 TFLOP/s BF16, byte-for-byte identical compute — but its HBM grows to 141 GB at 4.8 TB/s. Nothing about the compute roof moves; the memory roof rises ~43%.

On the roofline (§6)
A higher \(W_\text{HBM}\) lifts the entire memory-bound ramp — so every bandwidth-bound workload (decode, long context, big-batch serving) speeds up, while compute-bound prefill is unchanged.

That is why H200 is a popular inference upgrade despite identical peak FLOPs: it buys KV-cache headroom and a higher decode ceiling without touching the silicon’s arithmetic.

11.2 · B200 vs. B300, and the other variants

B300 (Blackwell Ultra) is a refresh of the same architecture, not a new one — same NVLink 5, same NVL72, same dual-die package. The deltas are capacity (288 vs. 192 GB) and FP4 throughput (~15 vs. ~9 PFLOP/s dense, ~1.7×; NVIDIA markets it as ~1.5× against the higher-clocked GB200 part), both aimed at long-context and reasoning inference, where KV headroom and test-time compute pay off directly.

The SXM modules above are the datacenter mainstream, but the family is wider:

  • PCIe / NVL boards trade bandwidth and TDP for form factor — e.g. H100 NVL pairs two cards at 94 GB each for inference.
  • Grace-X superchips pair an Arm CPU with the GPU(s) over a 900 GB/s NVLink-C2C link: GH200 (Grace + H200), GB200 (Grace + 2×B200), GB300 (Grace + 2×B300). The GB200/GB300 modules are the literal building blocks of the NVL72 rack — and for a training cluster that G prefix changes more than any row of the SKU table; §11.3 unpacks it.

11.3 · B300 vs. GB300 — same silicon, two different machines

The table in §11 describes the chip. “B300 or GB300?” is not a chip question — the GPU package, its FLOPs, and its 288 GB of HBM are identical — it is a question about the machine built around the chip. B300 in practice means an HGX B300 baseboard: eight SXM packages plus two x86 host CPUs, a node that slots into a conventional datacenter. GB300 means the Grace superchip, which only ships inside the liquid-cooled GB300 NVL72 rack: 72 GPUs and 36 Grace CPUs behaving as one machine. Three differences matter for training:

  • Where the network cliff sits. Per-GPU scale-out bandwidth is the same on both, so the real delta is the fast domain’s size. On HGX B300 the cliff from §8 is at the node: TP caps at 8-way, and everything wider — DP, PP, MoE AlltoAll — crosses the 800 Gb/s network. On GB300 the cliff moves to the rack: TP and EP can go up to 72-way on NVLink, and the network carries only the DP/PP axes. Same chip, different parallelism plan.
  • Offload becomes a real memory tier. Over PCIe, host RAM is where ZeRO-Offload pays a steep step-time tax — ~64 GB/s, explicit copies. Grace’s coherent 900 GB/s link is ~14× that, about a quarter of HBM bandwidth, so parking optimizer state, EMA weights, or spilled activations in LPDDR5X stops being a last resort and becomes part of the memory budget: ~38 TB of addressable fast memory per rack instead of ~21 TB.
  • The roofline doesn’t move. Per-GPU FLOPs, HBM bandwidth, and the §6 ridge point are identical — kernels don’t care which machine they run in. What you buy with GB300 is communication topology and memory capacity; what you pay is a rack-scale, liquid-cooled commitment, where HGX B300 deploys node by node in an existing facility.
Naming trap: NVIDIA’s GPU counting changed with Blackwell Ultra. The HGX board is branded HGX B300 NVL16 — eight dual-die packages, each die counted as a GPU — while NVL72 counts the 72 packages (36 superchips × 2). When comparing domain sizes, count packages: 8 vs. 72.

12 · Summary

Execution model

Threads run in warps of 32 (SIMT) on SMs; many resident warps hide HBM latency. Occupancy is that knob.

Tensor Cores

Do matmuls at ~989 TFLOP/s bf16 (fp32 accumulate) — fed from registers/SMEM, so peak needs tiling to keep them fed.

Managed scratchpad

Registers + shared memory are programmer-managed, not caches. Tiling/fusion are choices about what lives there.

Async data movement

cp.async / TMA stream tiles HBM→SMEM while the cores compute — the hardware behind software pipelining.

Memory wall

HBM is 80 GB at 3.35 TB/s — orders of magnitude slower than on-chip SRAM. Keep tiles resident; fuse.

Roofline

Ridge at ~295 FLOP/byte. Below it = memory-bound (fuse for free speedup); above = compute-bound.

Crossbar in, cliff out

NVSwitch gives all-to-all ~450 GB/s within 8 GPUs; the network drops to ~50 GB/s across nodes.

Generations

H100→H200 is a pure memory bump (same FLOPs, +43% bandwidth); Hopper→Blackwell adds dual-die, FP4, and the 72-GPU NVLink domain.

FP4 microscaling

Per-block scales make 4-bit usable; FP4 raises the compute ceiling ~2× over FP8 and halves decode bytes/token.

NVL72

The NVSwitch crossbar scales from 8 GPUs to 72 — moving the network cliff outward so TP/EP fit on NVLink.

Chip vs. machine

B300 vs. GB300 is the machine, not the chip: HGX = 8-GPU domain + PCIe hosts; GB300 NVL72 = 72-GPU domain + coherent Grace memory.
