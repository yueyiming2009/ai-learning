torch.distributed — c10d, DDP & FSDP

The single library under every PyTorch parallelism strategy. Below the launcher and above NCCL sits torch.distributed — process groups and a handful of collective calls. DDP, FSDP, tensor and pipeline parallelism are not separate engines; they are different patterns of collectives over that one foundation.

This page sits between two others. The collectives it issues — AllReduce, AllGather, ReduceScatter — are derived in Sharding & Collectives →, and how they actually run on the wire (rings, trees, NVLS) is NCCL →. Here we cover the PyTorch API over them, and the data-parallel strategies — DDP and FSDP — built directly on top.

A natural question when you first meet these tools is: is DDP the foundation that FSDP and the rest are built on? It is not. DDP and FSDP are siblings, not parent and child — two data-parallel strategies that both sit on the same lower layer. That layer is torch.distributed, historically the c10d library: a process group abstraction plus collective and point-to-point communication primitives. Everything else — DDP, FSDP, tensor parallelism, pipeline parallelism, expert parallelism — is a recipe written in those primitives.

1 · One library under every strategy

A distributed run has three layers. The launcher (torchrun) spawns one process per GPU and sets the environment variables that tell each process who it is. Each process then calls init_process_group, which is torch.distributed — it forms the process group and binds a backend (NCCL on GPUs). The backend is the thing that actually moves bytes. Stacked:

torchrun — launcher · spawns N processes, sets RANK/WORLD_SIZE/MASTER_ADDR
▼ each process calls init_process_group
torch.distributed (c10d) — ProcessGroup + collectives: all_reduce, all_gather, reduce_scatter, broadcast, send/recv
DDP FSDP Tensor Parallel Pipeline Parallel Expert Parallel
▼ backend
NCCL — GPU collective implementation (rings / trees / NVLS)

The reframe that matters: data parallelism (DDP, FSDP) splits the batch and keeps each device computing whole layers; the model-parallel axes (tensor, pipeline, expert) split the model. These are orthogonal axes you compose, not a hierarchy. DDP is simply the thinnest possible use of the foundation — and FSDP is what you get when you shard DDP's redundant state instead of replicating it.

2 · The c10d API surface

The whole API is small. You initialize one process group, query your identity, and issue collectives against the group. 

import os, torch
import torch.distributed as dist

# torchrun has already set RANK / WORLD_SIZE / MASTER_ADDR / MASTER_PORT in the env.
dist.init_process_group(backend="nccl")          # form the default process group
rank       = dist.get_rank()                      # global index, 0 .. world_size-1
world_size = dist.get_world_size()                # total processes
local_rank = int(os.environ["LOCAL_RANK"])        # GPU index on THIS node
torch.cuda.set_device(local_rank)                 # pin this process to its GPU

# collectives — every rank in the group must call the same op, in the same order
dist.all_reduce(t, op=dist.ReduceOp.SUM)          # sum t across ranks; result on all
dist.all_gather(out_list, t)                      # gather each rank's t into a list
dist.reduce_scatter(out, in_list)                 # reduce, then scatter shards
dist.broadcast(t, src=0)                           # rank 0's t -> everyone
dist.barrier()                                     # sync point
dist.send(t, dst=1); dist.recv(t, src=0)           # point-to-point (pipeline parallel)

# a subgroup = one parallelism axis
tp_group = dist.new_group(ranks=[0, 1, 2, 3])     # e.g. a 4-way tensor-parallel group
dist.all_reduce(t, group=tp_group)                 # collective scoped to that axis

Two things are worth pulling out. First, the backend is what binds the abstract collective to hardware:

BackendDeviceUse
ncclGPUThe default for training — NVLink/IB collectives. See the NCCL page.
glooCPUCPU tensors, debugging, or when NCCL is unavailable.
mpiCPU/GPUHPC clusters with an existing MPI stack (must build from source).

Second, the env vars init_process_group reads are exactly the ones the launcher injects — RANK, WORLD_SIZE, MASTER_ADDR, MASTER_PORT, LOCAL_RANK — read out of os.environ. The launcher sets the env; your code reads it; c10d wires the processes together.

Where those env vars come from is the launcher's job — see the rendezvous and env-injection mechanics in the torchrun note (personal PyTorch notebook), and os.environ as the read side.

Subgroups are the key idea for scale. new_group(ranks=[...]) carves a subset of ranks into their own process group with its own NCCL communicator. Each parallelism axis — the tensor-parallel group, the data-parallel group, the pipeline-parallel group — is just one such subgroup. A collective issued on a subgroup only touches its members. This is precisely how Megatron's initialize_model_parallel builds its TP/DP/PP/EP groups once at startup, then routes every collective to the right one.

3 · DDP — replicate and AllReduce

DistributedDataParallel is the simplest strategy. Every GPU holds a full replica of the model: parameters, gradients, and optimizer state. Each process feeds its replica a different shard of the global batch, so the forward and backward passes run independently. The only synchronization is on the gradients:

The DDP step
  1. Each replica runs forward and backward on its own micro-batch → local gradients.
  2. During backward, gradients are AllReduced (averaged) across all replicas — bucketed and overlapped with backward compute, so the reduction of early layers fires while later layers are still computing.
  3. After the AllReduce every replica holds the same averaged gradient → the optimizer takes an identical step → replicas stay in lock-step.
from torch.nn.parallel import DistributedDataParallel as DDP
model = DDP(model.to(local_rank), device_ids=[local_rank])
# train loop is otherwise unchanged — DDP installs gradient hooks
# that launch the bucketed AllReduce during loss.backward()

The cost: one gradient AllReduce per step (≈ \(2M\) bytes moved for a model of \(M\) bytes, since ring-AllReduce is a ReduceScatter followed by an AllGather). The limitation: the whole model, its gradients, and its optimizer state must fit on one GPU — DDP replicates all three. For an AdamW-trained model in mixed precision that is roughly \(16\) bytes per parameter (fp16 weights + fp16 grads + fp32 master weights + fp32 momentum + fp32 variance), so a 7B model already needs ~112 GB of optimizer-related state. That wall is exactly what FSDP removes.

4 · FSDP — shard instead of replicate

FullyShardedDataParallel keeps the data-parallel structure — split the batch, one process per GPU — but shards parameters, gradients, and optimizer state across the data-parallel group instead of replicating them. Each rank permanently owns only \(1/N\) of every weight. The full weights for a layer are reconstructed just-in-time, used, and immediately freed.

The FSDP unit lifecycle

The model is partitioned into units (a wrapping granularity — often per transformer block). For each unit, in both forward and backward:

  1. AllGather the unit's full parameters from all ranks (everyone reconstructs the whole weight).
  2. Run the unit's compute.
  3. Free the gathered parameters — drop back to the local \(1/N\) shard.
  4. In backward only: ReduceScatter the gradients, so each rank keeps just the gradient for its shard.

The optimizer then steps on the local shard alone. Peak parameter memory is set by the largest single unit being gathered, not the whole model.

# FSDP1 — wrap the whole model, choose a unit policy
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
model = FSDP(model, auto_wrap_policy=transformer_auto_wrap_policy, device_id=local_rank)

# FSDP2 (torch >= 2.4) — per-parameter sharding on DTensor
from torch.distributed.fsdp import fully_shard
for block in model.layers:
    fully_shard(block)
fully_shard(model)
DDP vs FSDP — same family, opposite ends of the memory/comm trade
DDP — replicate

Full model on every GPU. One gradient AllReduce per step. Minimal communication; capped by single-GPU memory.

FSDP — shard

Each GPU holds \(1/N\). AllGather params just-in-time (forward and backward) + ReduceScatter grads. ~1.5× the communication, but the model size is no longer bounded by one device.

FSDP1 flattens each unit's parameters into one big FlatParameter and shards that buffer; FSDP2 shards each parameter individually as a DTensor, which composes more cleanly with tensor parallelism and makes distributed checkpointing and partial freezing simpler. New code should prefer FSDP2 (fully_shard).

5 · The ZeRO ladder — DDP and FSDP are two rungs

DeepSpeed's ZeRO formalizes the spectrum between DDP and FSDP. The three replicated tensors — optimizer state, gradients, parameters — are sharded one at a time. Each stage saves more memory and pays a little more communication. DDP is the bottom rung (nothing sharded); FSDP is the top (everything sharded).

StageOptimizer stateGradientsParametersBackward comm
DDP (ZeRO-0)replicatedreplicatedreplicatedAllReduce
ZeRO-1shardedreplicatedreplicatedReduceScatter + AllGather
ZeRO-2shardedshardedreplicatedReduceScatter + AllGather
FSDP (≈ ZeRO-3)shardedshardedshardedAllGather params (fwd+bwd) + ReduceScatter grads
The headline

DDP = ZeRO-0; FSDP ≈ ZeRO-3. Going from DDP to full sharding cuts per-GPU state from \(O(M)\) to \(O(M/N)\) at the cost of roughly 1.5× the communication volume (an extra parameter AllGather in the forward pass).

Megatron's DistributedOptimizer is the ZeRO-1 point on this ladder — it shards optimizer state and fp32 master weights across the data-parallel group and pairs a ReduceScatter gradient path with an AllGather of the updated parameters, while leaving the parameters themselves replicated within the DP group.

6 · Composing axes — DeviceMesh and N-D parallelism

Real large-scale training combines several axes at once: data parallel and tensor parallel and pipeline parallel (and, for MoE, expert parallel). Each axis is one set of process groups; a GPU belongs to one group per axis. DeviceMesh is the modern way to lay this out — it builds the per-axis subgroups for you from a named grid. 

from torch.distributed.device_mesh import init_device_mesh

# 8 GPUs arranged as a 2-D mesh: 2-way data-parallel x 4-way tensor-parallel
mesh = init_device_mesh("cuda", (2, 4), mesh_dim_names=("dp", "tp"))
dp_group = mesh["dp"].get_group()   # AllReduce gradients here
tp_group = mesh["tp"].get_group()   # Megatron AllReduce per layer here

The usual topology mapping — chattiest axis on the fastest link — falls out of the cost model: tensor parallel innermost (an AllReduce on the critical path of every layer → keep it inside one NVLink node), then context/expert parallel, then pipeline parallel (cheap point-to-point activations between stages), with data parallel outermost (one gradient reduction per step, overlappable). In a 3-D layout the DP axis is typically realized as FSDP rather than plain DDP, so each axis is independently memory-efficient.

The tensor-parallel axis is worked out in full — column/row sharding, one AllReduce per block, the single-node cap — in Tensor Parallelism →. To see all the axes fire together on a real step, the verl PPO walkthrough → traces every NCCL call across TP/DP/PP.

7 · In practice

  • The handshake. torchrun --standalone --nproc_per_node=8 train.py spawns 8 processes; each calls init_process_group("nccl"), reads LOCAL_RANK, pins its GPU, and wraps the model in DDP or FSDP. That is the entire bring-up.
  • Collectives must match across ranks. Every rank has to call the same collective the same number of times, or the job hangs — the classic cause is a ragged last batch (uneven WORLD_SIZE division) desyncing the AllReduce; drop_last=True in the sampler avoids it. Mismatched control flow (an early continue on one rank) hangs the same way.
  • NCCL hang at the first step is usually a network/topology issue, not your code — try NCCL_DEBUG=INFO to see the rings being built, and NCCL_P2P_DISABLE=1 as a blunt diagnostic.
  • Direction of travel. FSDP2 and tensor/pipeline parallelism are converging on DTensor — a sharded-tensor type that carries its placement on a DeviceMesh — so the same model can be sharded along several axes by annotation rather than by separate wrappers.

Summary

The foundation

torch.distributed (c10d) = process groups + collectives. Every strategy is a pattern of collective calls over it.

DDP & FSDP are siblings

Both are data-parallel. DDP replicates (ZeRO-0); FSDP shards params/grads/optimizer (≈ ZeRO-3). Neither is built on the other.

Memory ↔ comm

Sharding trades ~1.5× communication for \(O(M/N)\) per-GPU state — the ZeRO ladder is the dial.

Composition

Model-parallel axes (TP/PP/EP) are orthogonal subgroups. DeviceMesh lays out N-D parallelism; DP is usually FSDP.
